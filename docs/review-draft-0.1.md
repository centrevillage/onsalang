## 1. 総評

方向性は良い。特に以下は残すべき核です。

- 「間違いを局所・高速・決定的に機械が否定できる」ことを言語の目的に置いた点（§0）
- 効果をシグネチャに載せる（§4）
- 安定コード + span + 型付きホールの診断、`ori check --json`（§7）
- `ori interface` による骨格抽出、AST を正本とする差分（§6）
- 全域ライフタイムではなく一意バッファで RT を賄う割り切り（§3.3, §8）
- Flow の名前付き `let` と、優先順位表を持たない方針（§5）

一方で、仕様として確定しているのは「表面の見た目」と「禁止リスト」が中心で、言語設計で本当に難しい判断（アドホック多相、数値型、Flow と Core の接続、メモリ管理、並行性、FFI、ターゲット）はほぼ空白です。また **仕様内の例が自分のルールや型規則に違反している箇所が多く**、例をそのまま LLM のプライマーにすると逆効果になります。§13 自身が認めている通り、現状は「制約の宣言」です。

## 2. 矛盾・誤り

### C-01 中置演算子のルールが例で全面的に破られている（重大）

§2 (`:45`) は「中置は `flow` 内の 5 つのグラフ演算だけ」と定めるが、通常コードで `<` `>` (`:55-56`)、`==` (`:300`)、`-` `<` (`:304`)、`%` (`:322`) を使い、flow 内でも `*` `/` `-` (`:341-344`) を使っている。`pi * bw / sr` は優先順位表なしには解釈できない。

**提案**: 現実的に算術・比較の中置は必要。「中置は許すが優先順位を持たず、異なる演算子の混在は必ず括弧」（Pony 方式）に改める。`0.0 - x` の回避策も不要になるよう単項 `neg` を用意する。

### C-02 オーバーロード禁止なのに `<` `==` `+` が Int/Float 両方に効く

§2 (`:78`) で silent overload を禁止、§3.1 に型クラス等の仕組みが無い。にもかかわらず `clamp` は Float で、`gcd` は Int で比較・算術している。→ M-01（アドホック多相）が無いと言語が成立しない。

### C-03 境界の型注釈必須ルールに例が違反

§3.1 (`:111`) は module boundary で注釈必須。しかし `pub fn clamp(x, lo, hi)` (`:54`)、`pub fn unwrap_or(e, d)` (`:64`)、`pub fn gcd(a, b)` (`:319`)、`pub fn phrase_len(path)` (`:329`, 引数のみ省略) が無注釈。

### C-04 効果操作の宣言はカリー化、呼び出しはタプル

`write : Path -> String -> Unit` (`:148`) に対し `fs.write(p, s)` (`:156`)。handler 側も `fs.write(_, _)` (`:170`)。アリティ検査を売りにする言語で関数の基本形が決まっていない。**どちらかに統一**（表面がタプル形式なら型表記も `(Path, String) -> Unit`）。

### C-05 Flow の作例 `formant` が型エラーかつ不安定（重大）

§10.3 (`:339-349`) は「人間は極とエネルギーを監査する」例だが、両方壊れている。

1. **アリティ**: `rec` の型は `(n+k → n) → k → n` (`:204`)。本体は `y0 || y1` で 2 出力なので n=2, k=1 → 結果は `Sig 1 → Sig 2`。宣言 `Sig 1 → Sig 1` と不一致（自分の E0412）。しかも 5 演算に **チャンネルを捨てる演算（FAUST の `!`）が無い** ため、正しく書き直す手段も無い。
2. **符号**: `b2 = -r²` を `sub(..., mul(b2, y2))` で引いているので `y0 = x + b1·y1 + r²·y2`。極は `z² − b1·z − r² = 0` の根になり、fc=500Hz, bw=100Hz, sr=48kHz で |z| ≈ 2.39 の **発散フィルタ**。正しくは `y0 = x + b1·y1 − r²·y2`（|z| ≈ 0.993）。
3. `sr`, `pi` が未束縛。`sr` は `effect audio` (`:151`) の操作のはずだが、flow は「total」(`:214`) で効果行を持たない。

### C-06 `add` / `mul` がグラフノードと標本関数の二重の意味を持つ

`mix = seq(par(id, id), add)` (`:190`) では `add` は 2→1 のグラフノード。`onepole` の `add(in, mul(p, y))` (`:187`) では標本値への関数適用で、しかも `mul(p, y)` は定数 Float と信号の混在。つまり flow 内に **point-free のグラフ記法と、変数を使う標本記法の 2 つのスタイル**が混在し、同名の演算が文脈で意味を変える。§0-4「書き方は一通り」に反する。

### C-07 `in` の 4 重定義と暗黙束縛

`let ... in` (`:195`)、`loop s = acc in` (`:133`)、`for x in xs` (`:134`)、そして flow 内の暗黙入力信号 `in` (`:187`, `:346`)。最後のものは §2 で禁止している「束縛を勝手に生む仕組み」そのもの。`rec` のラムダで入力も明示的に束縛すべき（例: `rec (x; y -> ...)`）。

### C-08 キーワード一覧が不完全

`:72` に無いが使われている: `let`, `in`, `then`, `else`, `end`, `loop`, `continue`, `for`, `do`, `assert`, `rec`（関数扱いか予約語か不明）。LLM 向け言語ならキーワード一覧は網羅的であるべき。

### C-09 ブロック区切りが 3 系統

`match ... end`, `handler ... end`, `for ... do ... end`, `mod ... end` (`:225-228`) は `end`。`effect fs { ... }` (`:146`) は波括弧。`if`, `let ... in` は閉じ無し。§2 のルール（節を持つものは `end`）に `effect` が反する。

### C-10 `mod` の書き方が 2 通り

ファイル先頭宣言 `mod filters` (`:48`) とブロック `mod synth.voice ... end` (`:225`)。また §6 の `pub fn render(...) -> ...` (`:227`) は本体が無く、インタフェース宣言なのか省略なのか不明。

### C-11 レコードは名前的と言いつつ匿名レコード型を使用

§3.1 (`:108`) で records are nominal。`fn main(env: { fs: Cap fs })` (`:158`) は匿名（構造的）レコード。さらに `env` は本体で使われておらず、capability がどうスコープに入るのかが不明（G-02）。`main` は戻り値型も欠落（`:73` の定義形に反する）。

### C-12 `Either` と `Result` の重複

`Either` を §2 で定義 (`:62`)、prelude には `Result` (`:234`) があるが定義が無い。同じ概念が 2 つ。

### C-13 決定性の主張と浮動小数点

§3 (`:92`) "deterministic given the same effect traces"。しかしターゲットが LLVM/WASM/C と複数あり、FMA 縮約、非正規化数、`exp`/`cos` の実装差、ベクトル化による加算順序の変化 (`:279` "vectorised Core") がある限り成立しない。浮動小数点モデルを仕様で固定するか、主張を弱めるか。

### C-14 `type Hz = Float` が型安全に寄与しない

別名なので `Hz` と `Float` は交換可能。§12 で人間の責務に「単位」を挙げているなら newtype か単位型が必要（M-09）。

### C-15 効果・capability・handler の 3 重構造

`Cap e` 型 (`:104`)、効果行 (`:162`)、handler (`:168`) が全て「世界への権限」を表す。§4 (`:163`) "capability in scope, **or** a handler" と 2 経路ある。効果 + handler に一本化し、OS への接続は「`main` を runtime 提供の handler で包む」と定義すれば `Cap` は不要。

### C-16 その他の細部

- `:233` "No glob except `use m.{a, b}`" — これは glob ではなく列挙。表現の誤り。
- `:289-290` "`--rt` crate" — crate が未定義（Rust 用語の混入）。
- `:286` "no exceptions" — 例外は言語全体で禁止済みなので無意味な条項。
- `:279` "SDF graph" — SDF は本来マルチレートのモデル。§1 の "single-rate" (`:36`) と食い違う。
- `:300` `assert clamp(...) == 1.0` — Float の厳密等値比較を推奨例にしている。
- `:303` `[1.0, 0.0, ...]` が `List` / `Array` / `Buf` のどれか不明。`y[0]` の添字構文も未定義。

## 4. 設計提案（要望の 3 点）

### P-01 Flow と通常コードの接続

現状は「Flow は `Buf Float` 上の Core 関数 + `{audio}` に降下する」(`:216`) の一行だけ。以下を提案。

**(a) Flow のコンパイル結果を Core の第一級の値にする**

```ori
;; 標準ライブラリ側
type Proc(i, o, p, s) = {
  init    : (SampleRate, p) -> s,
  process : (s, p, Buf(Frame i), Buf(Frame o)) -> (s, Buf(Frame o)) / {rt},
}

;; 利用側
fn render(v: Proc(0, 1, VoiceParam, VoiceState), ...) -> ... / {rt} =
  proc.process(v.state, params, in_buf, out_buf)
```

状態の所有者・初期化・サンプルレート変更時の再初期化・チャンネルのレイアウト（インタリーブか否か）を型で固定する。ホスト（C++ プラグイン等）から見た API もこれで決まる。

**(b) レートを型で区別する**

| 種別 | 意味 | 例 |
|---|---|---|
| `Const τ` | コンパイル時定数 | 次数、テーブルサイズ |
| `Ctl τ` | ブロックレート（パラメータ、UI） | カットオフ、ゲイン |
| `Sig n τ` | サンプルレート | 音声 |

昇格は `Const → Ctl → Sig` の一方向のみ、明示的な `lift` で（暗黙変換禁止との整合）。現状の `onepole(p: Float)` / `formant(fc: Float, bw: Float)` は定数でしか使えず、母音合成で必須のフォルマント変調ができない。係数計算（`r`, `w`, `b1` …）は `Ctl` で評価し、サンプルループの外へ出すことを型で保証できる。

**(c) Core 関数の持ち込み口**

flow 内から呼べる Core 関数は「効果行が `{}` かつ `rt` 安全」なものに限定し、`map(f)` で 1→1 ノード化する。状態を持つものは `rec` か明示的な状態プリミティブのみ。

**(d) `--rt` をフラグではなく効果で表す**

`alloc`, `block`（ロック・syscall）を効果として定義し、`rt` = これらを含まない行とする。「この関数は RT 安全か」がシグネチャで関数単位に検査でき、`--rt crate` という曖昧な単位 (`:290`) が不要になる。§0 の思想と最も整合する。

**(e) Flow の不足演算子**

C-05 の通り `cut`（チャンネル破棄）が無いと書けないものがある。加えて `delay(n)`（固定・可変遅延線）、読み取り/書き込みテーブル、`select`（チャンネル選択）は DSP の基本語彙として必要。

### P-02 FFI

```ori
extern "C" lib "m" {
  fn sinf(x: F32) -> F32 / {}            ;; 純粋性は人間による宣言（trusted）
  fn rb_push(q: Ptr(U8), n: USize) -> I32 / {ffi, rt}
}

export "C" fn ori_voice_process(...)     ;; C ヘッダを自動生成
```

- extern 宣言の効果行は **検証されない主張**。`ori audit` で一覧化し、人間がレビューする境界とする（§12 の役割分担と一致）。
- `Buf` は呼び出し中のみ `(ptr, len)` として貸し出し、外部に保持させない。外部保持が必要なら明示的な `pin` / `leak` を unsafe 側に置く。
- コールバック（C → Ori）は効果行 `{}` または `{rt}` の関数のみ許可。
- **優先すべきは export 方向**。Ori の DSP を既存の C++ ホスト（JUCE / CLAP / VST3 / AU）に埋め込むのが現実的な導入経路。§8 の "C subset (for existing DSP hosts)" (`:278`) はバックエンドであって FFI ではない。
- `ffi` 効果を持つ関数のみ extern を呼べる。「safe fragment」(`:93`) と言う以上、unsafe fragment を定義する。
- コーパスの無い言語にとって、FFI は唯一のライブラリ調達手段でもある。

### P-03 コンパイル環境の抽象化

- **条件コンパイル (`#if` / cfg) を持たない**。プラットフォーム差はモジュールシグネチャで表し、実装の選択はビルド記述側で行う（ML のファンクタ方式）。ソースの意味が環境で変わらない。
- **ターゲット = 提供される handler の集合** と定義する。例えば Daisy（組込み）ターゲットが `fs` handler を提供しないなら、`main` の効果行に `fs` が残っていればコンパイルエラー。効果システムと自然に統一できる。
- **ターゲットに数値モデルを持たせる**: f32 のみ / f64 可、FTZ・DAZ、FMA 縮約の可否、`exp`/`sin` の精度保証。C-13 の決定性はここでしか担保できない。
- **ビルド記述**は Ori の純粋部分集合（効果行 `{}`）または宣言的マニフェスト。ハーメティック、lockfile、再現可能ビルド。
- ターゲットの例: `native`, `wasm32-webaudio`, `clap`, `vst3`, `au`, `daisy`, `c-subset`。プラグイン形式は「`Proc` を export する薄いアダプタ」として標準ライブラリに置く。

### P-04 人間専有の決定の強制（G-10 への提案）

capability の付与、`rt` 境界、公開インタフェースを **別ファイルのマニフェスト**（例: `ori.policy`）に集約し、ソースがそれを超えたら `ori check` がエラー、マニフェストの変更は `ori audit` で差分表示する。エージェントにはマニフェストの書き込み権限を与えない運用にできる。

## 6. 前提への指摘

- **最大の実務リスクはコーパスがゼロであること**。元のチャットの LLM 向き言語の議論でも Python/TS の強さはコーパス由来と認めている。表面構文は既存言語（OCaml / F# / Koka / Gleam）に寄せるほどモデルの事前知識が効く。
  - 例: `;;` コメント (`:75`) は OCaml ではトップレベル区切り。事前知識と衝突する。`--` か `//` が無難。
- **「LLM 向き」の主張は全て未検証**。早期に「同じ課題を Ori / OCaml 部分集合 / Koka / Faust で書かせ、`check` 通過までの反復回数を測る」ベンチマークを作ると、設計判断を測定できる。
- 仕様の例そのものが LLM のプライマーになるため、**全ての例がコンパイラを通る**（少なくとも手で型検査済み）ことを仕様の品質基準にすべき。C-01〜C-05 はその基準で全て弾ける。

## 7. 推奨する進め方

1. **例の修正**: C-01〜C-12 を潰し、仕様内の全コード例を自己整合させる。
2. **核の決定**: M-01（多相）、M-02（数値型）、M-03（エラー）、G-01（handler 意味論）、C-15（効果と capability の一本化）。
3. **Flow 設計**: P-01（`Proc` 型、レート、`rt` 効果、不足演算子）と G-05（型レベル自然数）。
4. **外部接続**: P-02（FFI、特に C export）と P-03（ターゲット = handler 集合）。
5. **ツール前提**: §13 のロードマップの前に、仕様の例を検査する最小の型検査器を作ると、以降の改訂が回しやすい。
