### S-413 括弧の中の、構造体リテラルとパターンの `{` の前の改行

- **論点:** §2.5「ただし記号の置き場所の規則（…後置の `(` と `[` と空白を空けない位置の印と記号は相手と同じ行、`else`・`with`・`{` は前の `}` や見出しと同じ行）は、括弧の中でも外と同じ」と、同じ節の「ブロックの `{` は、それを持つ宣言や見出し…の最後のトークンと同じ行に書く」。構造体リテラル `S { a: 1 }` と構造体のパターン `S { a: x }` の `{` はブロックでも見出しでもなく、`(`・`[` のように空白を禁じる開きでもない（`S { a: 1 }` は空白を置く形が正規形、`docs/onsa-tools.md` §3.2）。括弧の中で `{` を次の行に書く形を、受けるか、どの誤りにするかを書かない。
  - 決定済み（論点から外す）: 括弧の中の改行の後の `(`（`Some` 改行 `(1)`）は S-89。構造体リテラルの中の `else` と `{` は R-62。見出しの式には括弧の外に構造体リテラルを書けない（§4.4）。
- **今の実装:**
  - 括弧の中は通り、fmt が一行にする: `two(S` 改行 `{ a: 1 }, 2)`、`{` と中身を複数行にした形、`[S` 改行 `{ a: 1 }]`、`(S` 改行 `{ a: 1 }, 2)`、`(S` 改行 `{ a: 1 })`、フィールドの値 `T { s: S` 改行 `{ a: 1 } }`、`one(P::[I32]` 改行 `{ a: 1 })`（E0200 の `::[` だけ）。パターンも、腕の `S` 改行 `{ a: x } => x,`、`Some(S` 改行 `{ a: x }) =>` が通る。`two(S // the value` 改行 `{ a: 1 }, 2)` は、fmt がコメントを `2)` の後へ移す。
  - 括弧の外: `let s = S` 改行 `{ a: 1 }` は 4:8 の E0002「expected newline or `}`, found `:`」（次の行をブロックの文と読む）。`return S` 改行 `{ a: 1 }`、末尾の `S` 改行 `{ a: 1 }`、`let p = P::[I32]` 改行 `{ a: 1 }` も同じ。中身がブロックとして読める `let s = S` 改行 `{ 1 }` は E0401「`S` is not a value」（二つの文）。パターンの `let S` 改行 `{ a: x } = s` は 3:8 の E0002「expected `=`, found newline」。
  - 比べ: `two(N` 改行 `{ 1 })`（`N` は定数）は、大文字で始まる名前の後の `{` を構造体リテラルと読み、E0002「expected field name, found integer literal」。同じ行の `two(N { 1 })` も同じ。`two(n` 改行 `{ 1 })` は E0002「expected `)`, found `{`」（候補なし。S-384 の `,` は W3-06）。
- **案:**
  - (a) `{` の置き場所の規則に入れる。構造体リテラルと構造体のパターンの `{` は型の名前（型引数があれば `::[…]` の `]`）と同じ行に書き、違反は E0003（主の位置は `{`、候補は `{` から同じ行のコメントの前までを名前の行の末尾へ移す、S-216 の移し方）。括弧の中でも、`let` などのパターンの位置でも同じ。括弧の外の構造体リテラルは、名前で行が終わるので今のまま（次の行は別の文）。
    - 実装: `parser.rs` の `parse_postfix` の構造体リテラルの腕と、`parse_pattern_alt` の構造体のパターンで、`{` の前が改行なら `on_same_line` で E0003 を出して読み続ける（各 3〜5 行）。`let S` 改行 `{` は、パターンの後に `=` を期待して改行を見た所で次の行の `{` を見る（約 5 行）。文面 1 つ。候補は `move_up` のまま。計 15〜20 行。データのファイルの行は無い（E0003 は表の外）。
  - (b) S-89 の改行の後の `(` と同じ形にする。括弧の中でも改行の後の `{` は名前に付かず、`,` の無い二つの要素の E0002。候補は、`{` の後が `名前 :` なら改行を除く形、そうでなければ `,` の挿入（字句で決める）。腕のパターンでは `S` が腕として完結しないので、`=>` を期待した所の E0002 に改行を除く形を付ける。
    - 実装: `touches` の記録を構造体の `{` にも使い、`list_failure` と腕の失敗の所に候補の選び方を足す（約 20〜30 行）。
  - (c) 置き場所の規則を持たないとし、括弧の中は改行を空白として受ける（S-374 の `as` と同じ扱い）。fmt が一行にする。実装 0 行。仕様に一句。
  - (d) (a) に加え、括弧の外の `let s = S` 改行 `{ a: 1 }` も E0003 にする。ブロックの文が `{ 名前 :` で始まり、前の行が型の名前で終わる形を、失敗の所で見分ける（約 20〜30 行）。
- **他言語:**
  - rustc 1.94.1 は `two(S` 改行 `{ a: 1 }, 2)` と括弧の外の `let s = S` 改行 `{ a: 1 };` を通し、rustfmt 1.8.0 が `S { a: 1 }` の一行にする。Apple clang 21（C11）は複合リテラル `two((struct S)` 改行 `{ .a = 1 }, 2)` を通す。
  - Go（未確認）は、行の最後が識別子なら `;` を入れるので、括弧の中でも `f(S` 改行 `{a: 1})` は構文の誤りになる（https://go.dev/ref/spec#Semicolons ）。C#（未確認）は、オブジェクト初期化子の `{` を次の行に置く書き方（`new Cat` 改行 `{`）を文書の例で使う（https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/object-and-collection-initializers ）。
  - まとめ: 中身がフィールドの並びなら、どの言語でも読みは構造体リテラル一つで、割れない。名前の後で行を折る流儀（C# の Allman）はある。
- **推奨と理由:** (a)。確度: 中。
  - 一つの規則にできるか（S-415 と並べて）: できる。「`{` は、それが属する形（宣言と見出し、struct / enum の宣言、構造体リテラルとパターン）の最後のトークンと同じ行に書く。違反は E0003」の一文で、S-415 の宣言の本体と、この項目の構造体の `{` を覆う。主の位置、候補、`on_same_line` と `move_up` が全て同じになる。(b) を採ると、S-415 は E0003、この項目は S-89 の E0002 の二つの規則に分かれる。
  - 規則が場所で割れない。(c) は、括弧の外で誤りの字面を括弧の中でだけ通す（S-353 の (c) を退けた理由と同じ）。S-374 が `as`・`at` に置き場所の規則を持たせなかった理由は「どの流儀でも折る位置でない」で、構造体の `{` の前は C# の流儀が折る位置なので当たらない。通ったコードでは `{` が常に名前と同じ行にある（R-62 の理由）。

### S-406 他の言語の文字列の区切り

- **論点:** §2.4「文字列: `"..."`（UTF-8）…文字列リテラルは行をまたげない…文字列と文字のリテラルに接頭辞と接尾辞は無い」。S-400 の決定は名前に接するリテラルだけを扱い、名前でない記号で始まる区切り（C# の `$"…"`・`@"…"`・`$@"…"`、Rust の `r#"…"#`、Swift の `#"…"#`、Python・Swift・Java・C# の `"""…"""`、Python の `'''…'''`、JS / TS の `` `…` ``）を何として報告するかを書かない。今は文字ごとの一般の誤りで、どれも候補も note も無い。
