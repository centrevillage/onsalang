# 第 1 期 M0〜M4 のコードレビュー

- 対象: コミット `346ec50`（M4 完了と S-28 の決定）までの `crates/`、`runtime/`、`std/`、`tests/`
- 仕様: [`spec/`](../spec/README.md)。入力の資料: [`impl-review-0.3.md`](impl-review-0.3.md)
- 日付: 2026-10-02
- 観点（利用者の指定）:
  1. 実装が仕様とずれていないか
  2. プログラムの構造が健全か。これから修正を加え、保守できる状態か
  3. 仕様に無い前提を導入していないか。議論すべき事項を報告せずに独自の判断で仕様の穴を埋めた箇所や、誤った前提で実装を進めた箇所が無いか
- 方法: 6 つの領域に分け、各領域を一つのエージェントがコードを読んで調べた。
  - 6 つの領域: 字句・構文・fmt・診断、モジュール・型・シグネチャ、関数本体の型検査・モード・効果・rt、flow、Core・インタプリタ、C バックエンド・build・std
  - 指摘は、`onsa check` / `test` / `build` で動かすか、生成した C を clang / gcc でコンパイル・実行して再現した。
  - 親（このレビューのまとめ役）は、重大度が高い指摘の約 30 件を自分でも再現した（各項目に「再現（親）」と記す）。
  - 重複を除いてここにまとめた。
- ローカルの検査: CI は準備していない。そこで CI と同じ内容をローカルで実行した。結果は次のとおり。
  - `cargo fmt --check`: 差分なし
  - `cargo clippy --workspace --all-targets`（`-D warnings`）: 警告なし
  - `cargo test --workspace`: 約 190 件が全て成功

各項目の頭の行は「重大度・推奨・観点｜場所｜仕様」の順に書く。

- 重大度
  - **高**: 意味が誤る、コンパイラが落ちる、健全性の穴がある、今後の作業を妨げる
  - **中**
  - **低**
- 推奨
  - **直す**: 仕様が明確なので、実装を仕様に合わせる
  - **仕様へ**: 実装の現状か推奨の形を、仕様に書き足す
  - **要判断**: 利用者の判断が要る。選択肢と推奨を添える。一覧は §6

## 0. 結論

**骨格は健全。** 次の点は、このまま育てられる。

- クレートの分割（syntax → sema → core → interp / backend）
- アリーナと ID の AST
- 型付きの構造化ツリーとしての Core
- 検査付き・ラップ・飽和の演算モードの明示
- `_Static_assert` で配置を C コンパイラに検証させる作り
- `setjmp` のラッパ

clippy の警告は無く、`todo!` / `unimplemented!` / `TODO` も無い。

**ただし「検査を通るが意味が誤る」不具合が多い。** 再現できた主なものは次のとおり。

- **誤コンパイル**
  - `x = f(x)` の別名で、C の結果が壊れる（R-09）
  - `onsa.h` の整数ヘルパに未定義動作と誤りがある（R-10）
  - 値を返す `match` の一般経路が、インタプリタでも C でも動かない（R-06）
  - flow の look-back の入れ子と、分岐の中のインスタンスが、仕様と違う値を出す（R-13、R-14）
  - インタプリタと C で評価順が違う（R-93）
- **健全性の穴**
  - 移動の追跡がループで抜ける（R-28）
  - `?Dup` と総称の型の値を複製できる（R-30）
  - 非 rt の関数を `rt fn` として渡せる（R-26）
  - 効果がクロージャから漏れる（R-27）
- **クラッシュ**
  - 非 ASCII の文字列で字句解析器が落ちる（R-01）
  - 再帰型でスタックが溢れる（R-02）
  - `onsa fmt` が構文エラーのある関数をファイルから消す（R-69）

**見逃した原因は 4 つある。**

1. **テストに独立した期待値が少ない。**
   - 適合性テストは、同じ Core から出たインタプリタと C を比べる。Core の降下の誤りは両方に同じように出るので、一致してしまう。
   - Core のテストは、`dump` の文字列の部分一致を照合するだけである。
   - 手で期待値を書いた意味のテストはわずかだった（§5）。
2. **Core の検証器が弱く、debug ビルドでしか動かない（R-82）。**
   - 検査を通った入力が、後段で panic する。
   - release ビルドでは、そのまま誤ったコードになる。
3. **ワーカーの自己申告に頼った。**
   - `impl-review-0.3.md` §2 は、ワーカーの報告から細則を拾ったものである。
   - 申告されていない独自判断が多く（§3）、申告の記述自体が実装と合わないものもあった（§4）。
4. **同じ判断を複数の場所で行っている。** 組込みの知識、状態の配置、NRVO の判定、到達解析、効果の集計などが、2〜6 か所に重複している（R-79、R-80）。片方だけが直り、食い違いが生まれる。

**次の進め方（§7）。**

1. 期待値付きのテストと、インタプリタと C の差分テストを先に整える。
2. 判断の要らない誤り（クラッシュ、誤コンパイル、健全性の穴）を直す。
3. §6 の判断を受けて、仕様と実装を揃える。
4. Core に評価順・移動・結果の置き場所・bulk を明示する構造の変更を行う。T4-10 はこの構造の変更の上で行う。
5. M5 はその後に行う。
