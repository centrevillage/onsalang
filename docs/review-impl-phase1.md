## 0. 結論

**骨格は健全。** 次の点は、このまま育てられる。

- クレートの分割（syntax → sema → core → interp / backend）
- アリーナと ID の AST
- 型付きの構造化ツリーとしての Core
- 検査付き・ラップ・飽和の演算モードの明示
- `_Static_assert` で配置を C コンパイラに検証させる作り
- `setjmp` のラッパ

clippy の警告は無く、`todo!` / `unimplemented!` / `TODO` も無い。

**ただし「検査を通るが意味が誤る」不具合が多い。** 再現できた主なものは次のとおり。

- **誤コンパイル**
  - `x = f(x)` の別名で、C の結果が壊れる（R-09）
  - `onsa.h` の整数ヘルパに未定義動作と誤りがある（R-10）
  - 値を返す `match` の一般経路が、インタプリタでも C でも動かない（R-06）
  - flow の look-back の入れ子と、分岐の中のインスタンスが、仕様と違う値を出す（R-13、R-14）
  - インタプリタと C で評価順が違う（R-93）
- **健全性の穴**
  - 移動の追跡がループで抜ける（R-28）
  - `?Dup` と総称の型の値を複製できる（R-30）
  - 非 rt の関数を `rt fn` として渡せる（R-26）
  - 効果がクロージャから漏れる（R-27）
- **クラッシュ**
  - 非 ASCII の文字列で字句解析器が落ちる（R-01）
  - 再帰型でスタックが溢れる（R-02）
  - `onsa fmt` が構文エラーのある関数をファイルから消す（R-69）

**見逃した原因は 4 つある。**

1. **テストに独立した期待値が少ない。**
   - 適合性テストは、同じ Core から出たインタプリタと C を比べる。Core の降下の誤りは両方に同じように出るので、一致してしまう。
   - Core のテストは、`dump` の文字列の部分一致を照合するだけである。
   - 手で期待値を書いた意味のテストはわずかだった（§5）。
2. **Core の検証器が弱く、debug ビルドでしか動かない（R-82）。**
   - 検査を通った入力が、後段で panic する。
   - release ビルドでは、そのまま誤ったコードになる。
3. **ワーカーの自己申告に頼った。**
   - `impl-review-0.3.md` §2 は、ワーカーの報告から細則を拾ったものである。
   - 申告されていない独自判断が多く（§3）、申告の記述自体が実装と合わないものもあった（§4）。
4. **同じ判断を複数の場所で行っている。** 組込みの知識、状態の配置、NRVO の判定、到達解析、効果の集計などが、2〜6 か所に重複している（R-79、R-80）。片方だけが直り、食い違いが生まれる。

**次の進め方（§7）。**

1. 期待値付きのテストと、インタプリタと C の差分テストを先に整える。
2. 判断の要らない誤り（クラッシュ、誤コンパイル、健全性の穴）を直す。
3. §6 の判断を受けて、仕様と実装を揃える。
4. Core に評価順・移動・結果の置き場所・bulk を明示する構造の変更を行う。T4-10 はこの構造の変更の上で行う。
5. M5 はその後に行う。

#### R-03 検査を通り、後段の内部エラーになる入力
- 高・直す・観点 1｜各項目に記す｜—
- 共通: debug ビルドでは Core の検証器が panic する。release では検証器が動かないので、誤ったコードになるか、`E0200 internal ...` になる（R-82）。いずれも sema で拒否するか、正しく降下する。
- 入力ごとの原因と直し方:
  - **総称の `-x` を `U32` で使う**: `fn neg[T: Num](x: T) -> T { -x }` と `neg(u)`。`'-' on a non-signed type` で落ちる（`onsa_sema/src/body.rs:1354`）。どう直すかは R-94 で判断する。再現（親）。
  - **リテラルパターンの範囲外**:
    - `x: U8` に対する `300 =>` と、`x: U32` に対する `-1 =>` が `literal 300 out of range` で落ちる（`body.rs:2504-2535`）。再現（親）。
    - 補間を含む文字列パターン `"a{x}b" =>` は、補間を黙って捨てて `"ab"` と照合する。
    - 直し方: パターンのリテラルも範囲を検査する。補間を含む文字列パターンはエラーにする。
  - **`-(I32.MIN)` の畳み込み**: 被演算子がリテラルに降下したものなら、符号を畳む（`onsa_core/src/lower/body.rs:840-846`）。
    - debug では、検証器が `literal 2147483648 out of range` で落ちる。
    - release では、インタプリタが値を折り返して `I32.MIN` を返す。期待は実行時の panic。
    - 直し方: 畳むのは、ソースの数値リテラルに直接付いた `-` だけにする。
  - **未解決の型変数**: `let x = None` と `let b = Buf.zeroed(4); b.len()` は `check` を通る。`test` で `internal lowering error: unresolved type` になる（`body.rs:506-645` の `finish`）。
    - 直し方: リテラル以外の型変数が残ったら、E0406 か E0420 にする。
    - 仕様へ: §4.7 が定める「未解決の報告」は、リテラルの分しかない。
  - **flow の入力名**: `s`、`cfg`、`params`、`sample_rate` や、`let poisoned` で落ちる。R-15 と R-48 で直す。
  - **`par` の中の look-back**: `let a = par i in 0..2 { prev(y, 0.0) }; let y = x` が `local y read before definition` で落ちる（`onsa_core/src/lower/flow.rs:1107-1123`）。R-13 の二相化と一緒に直す。
  - **自分をインスタンスにする flow**: 相互再帰も含め、`check` を通る。その後 `E0200 this version does not lower ...` になり、将来は対応するかのような文面になっている（`lower/flow.rs:165`）。
    - 仕様 §11.5 は「flow 本体の中に再帰は無い」と定める。sema で閉路を検出し、専用の E08xx を仕様に足す。
  - **巨大な `delay`**: `delay(x, 1073741824, 0.0)` は、`interface` で `multiply with overflow` になる（`onsa_core/src/layout.rs:41`）。R-100 で扱う。
  - **`Bool` の `@param`**: `Ctl[Bool]` に `@param(default: 1.0)` を付けると、`internal lowering error` になる（`lower/flow.rs:571`）。R-99 で扱う。

#### R-10 C: `onsa.h` の整数ヘルパに未定義動作と誤りがある
- 高・直す・観点 1｜`runtime/c/onsa.h:198`、`:293`、`:298`、`:404`｜§3.4、§3.3、§9.2｜コードで確認（親）
- **U32 の検査付き乗算**: `(int64_t)a * (int64_t)b` が int64 を超える（未定義動作）。gcc-15 の -O2 では検査が消え、`4294967295 * 4294967295` が panic せずに 1 を返す。既定の `*` がこのヘルパを使うので、影響が広い。
- **I8 / I16 の負数の右シフト**: `(T)~((~(UT)a) >> n)` は `~` の前に int へ昇格する。`-128i8 >> 1` が 64 に、`-32768i16 >> 1` が 16384 になる。どのコンパイラ、どの最適化でも同じ結果になる。
- **u16 / i16 のラップ乗算**: int に昇格して、符号付きのオーバーフローになる（UBSan が報告した）。
- **I64 / U64 の飽和変換**: `(T)(MAXP1 - 1.0)` が範囲外の変換になる。`1e30.trunc_i64_sat()` の結果が、clang -O2 では 6671500168 になる。
- 直し方:
  - u32 は `uint64_t` で掛けるか、`__builtin_mul_overflow` を使う。
  - シフトは各段で `UT` に戻す。
  - 16 ビット以下の乗算は `unsigned` で掛ける。
  - 飽和の上端は定数 `MAX` を返す。

@centrevillage
検査付きの演算については組み込み関数で正確に検査できれば良いと思います。
ただし組み込み環境をターゲットにする場合は検査を消して効率化する仕組みが必要に思います。
仕様にあるか分かりませんが、コンパイル/トランスパイル時に検査レベルを指定できる仕組みがあるとなお良い。

#### R-26 非 rt の関数やクロージャを `rt fn` の型として渡せる

#### R-27 クロージャの効果を照合しない。効果行変数は宣言できるが使えない
- 高・直す + 仕様へ + 要判断・観点 1 / 2｜`crates/onsa_sema/src/body.rs:1758-1776`、`effects.rs:44-119`、`infer.rs:199`、`ty.rs:206`｜§8.1、S-23

#### R-67 GCC ではプラグマが効かず、FMA に縮約される。`-Werror` でも通らない
- 中・直す + 仕様へ・観点 1 / 2｜`runtime/c/onsa.h:29`、`:285`｜§13.4
- プラグマの無視: GCC は `#pragma STDC FP_CONTRACT OFF` を無視する。既定のフラグの -O2 では、resonator に `fmadd` が出る。
  - `onsa build` は `-ffp-contract=off` を渡すので、このビルド経路は安全である。
  - `kind = "source"` の出力やクロスのビルドは、利用者のフラグ次第になる。
- 警告: gcc-15 の `-Wall -Wextra -Werror` では、golden の C が `unknown-pragmas` と `type-limits` で失敗する。
- 直し方: GCC では `#pragma GCC optimize("fp-contract=off")` を出す。`__FAST_MATH__` なら `#error` にする。
- 仕様へ: §13.4 に「プラグマだけでは不十分。フラグが要る」と書く。
- 確認（2026-10-04）: gcc-15 `-O2 -std=gnu11` は `a * b + c` を FMA にし、`-std=c11` ではしない（ISO モードでは `__STRICT_ANSI__` が定義される）。clang はプラグマに従う。gcc の `-Wall -Wextra` は STDC のプラグマに `-Wunknown-pragmas` を出す。
- 決定（2026-10-04）: 直す。S-54: 守られていないと分かるフラグは `#error`（GCC の GNU モードは `ONSA_FP_CONTRACT_OFF` が無ければ止める）。`ONSA_ALLOW_INEXACT_FP` で精度を諦めて検査を外せる。`@relaxed` は C で関数ごとに緩める。`#pragma GCC optimize` には頼らない。生成した C は `-Wall -Wextra` で警告なし。

### 1.5 ツールと診断

#### R-69 `onsa fmt` が、構文エラーのある関数を黙って削除する
- 高・直す・観点 1 / 2｜`crates/onsa_syntax/src/fmt.rs:16`、`parser.rs:278-280`、`:2026`、`naming.rs:168-184`、`groups.rs:12`、`crates/onsa_cli/src/main.rs:195`｜§18.2｜再現（親）
- 原因:
  - fmt は「E0001〜E0020 があれば拒否する」と判定するが、見ている診断は項目ごとに 1 件へ間引いた後のものである。
  - 命名の検査は、失敗した項目の残骸まで走査して E0320 を先に出す。
  - そのため E0002 が消え、fmt は拒否せずに進む。AST に入らなかった失敗項目は出力されない。
- 再現: `fn f() {\n  let badName = 1\n  let = 2\n}\n\nfn g() {}` に `onsa fmt` を実行すると、exit 0 で、ファイルの中身が `fn g() {}` だけになる。`diff --ast` も同じ判定を使う。
- 直し方:
  - 「失敗した項目がある」ことを明示のフラグで持つ。
  - 命名の検査は、AST の根から辿れるノードだけを対象にする。
  - fmt の出力を再解析し、AST が変わらないことを確かめてから書き込む安全装置を入れる。
- 決定（2026-10-04）: 直す。S-56: 構文の診断（E00xx）のあるファイルは書き換えず、複数のファイルは全て処理する。fmt が AST を変える書き換えは閉じた一覧（末尾の `return`、冗長な括弧、既定値と等しい `init`）にし、安全装置はその書き換えを施した AST、doc、コメントの並びを比べる。`diff --ast` も同じ比較を使う。終了コードは全てのコマンドで 0 / 1 / 2 / 101 とし、安全装置が働いたら 101。

#### R-70 fmt がコメントを別の場所・別の宣言へ移す
- 高・直す + 要判断・観点 1 / 2｜`crates/onsa_syntax/src/fmt.rs:151-190`、`:666` 以降、`parser.rs:314`｜§2.1、§18.2、`impl-review` F-4
- 再現: 次のどれも、fmt が冪等で `--check` も通る状態で起きる。
  - **フィールドの `///`**: 次の `pub fn` の doc として解析される。AST が変わり、`diff --ast` が報告する。
  - **引数の行末のコメント**: 関数の本体の先頭へ移る。
  - **空の本体のコメント**: `fn empty() {\n  // todo\n}` が `fn empty() {} // todo` になる。
  - **match の腕と配列の要素（係数表）の行末のコメント**: 全て閉じ括弧の後ろに積まれ、どの要素の注釈か分からなくなる。
- 資料の誤り: `impl-review` F-4 の記述（「式の途中のコメントは文の後ろへ移る」）より、影響が大きい（§4）。
- 構造上の原因: fmt はコメントなどの trivia を AST に持たず、位置を推測して付け直す（R-86）。
- 判断（R-70）: フィールド・列挙子・引数に doc を付けられるようにするか。
  - (a) 付けられるようにする（Rust と同じ。`onsa interface` にも出す）。
  - (b) 付けられないことにし、そこに書いた `///` をエラーにする。
  - 推奨は (a)。`@param` の説明などに要る。

#### R-94 総称の `-x`: `Num` と `Neg` の関係が決まっていない
- 中・要判断・観点 1 / 3｜`crates/onsa_sema/src/body.rs:1354`、`:2764-2777`（`implies`）｜§6.3（演算子 trait の `Neg` は `Num` と別に挙げてある）

- 判断（R-94）:
  - (a) `Neg` を境界として書けるようにし、総称の `-` には `Neg` を要求する（Rust の `num-traits` に近い）。
  - (b) `Num` は符号無し整数を含まないと定める。
  - (c) 総称の単項 `-` を禁止する。
  - 推奨は (a)。
- 範囲（2026-10-05 に追加で確かめた）:
  - 観点: R-56（S-46）で §6.3 に「`Num` に `Neg` を含めないのは、符号なし整数に無いからである」と書いたので、今は仕様と実装のずれ（観点 1）でもある。
  - 原因: 型パラメータの `-x` を `Num` を満たすかで通す（`body.rs:1354`）。二項の算術も `Num` で代わりに判定し（`require_operand`）、ビット演算は具体的な整数だけを受ける。演算子 trait と利用者の trait は境界に書けず、`[T: Num + Neg]` は E0200「user-defined traits as bounds」（`Neg` は標準 trait なので文面も合わない）。具体的な `-u`（`U32`）は E0401 で正しい。
  - 仕様の空白: §6.3 の組込み型の表（閉じた一覧）に演算子 trait が一つも無い（`Neg`、ビット演算）。§3.2 の脱糖先の `WrappingAdd` / `SaturatingAdd` と、`!` の trait が §6.3 の一覧に無く、演算子 trait のシグネチャも無い（R-131 として登録した）。符号付きの `>>` が算術シフトであることも仕様に無い（実装は算術シフト）。
  - 他の言語: 基底に否定を含め、符号なしは折り返す（Haskell の `Num`、Scala の `Numeric`、.NET の `INumberBase`）。符号なしを含む基底に否定を足した細分を置く（Swift の `Numeric` → `SignedNumeric`、num-traits の `Signed: Num + Neg`）。否定を独立の能力にする（Rust の std の `Neg`、Lean、F#）。引き算ごと分ける（PureScript の `Semiring` / `Ring`）。型の分類（Go、C++20、Julia）。符号なし整数を主な「数」の概念から外した主流の例は無い。
  - 再現は `tests/review-phase1/parent/r94/`（`check.onsa` は検査、`run.onsa` は実行。期待値と今の出力は各項目の上のコメント）。既存の `body/t2_neg_generic.onsa` も同じ不具合。
- 決定（2026-10-05）: 原案の (a)〜(c) ではなく、数の trait を組み直した（S-84）。利用者の指摘から: 符号付きは普通の計算に使う値、符号なしは「負数を持たない」制約の付いた特殊な数（ID、添字、アドレス）で、用途が分かれる。違いは否定より引き算に出る（`-x` を使わない `a + (b - a) * t` は、`Num + Neg` の分解では `T: Num` のまま `U32` を受け、普通の入力で panic する）。
  - (1) `AnyNum`（全ての数。`Copy` `Add` `Sub` `Mul` `Div` `Rem` `PartialEq` `PartialOrd` と `ZERO`）と `Num`（`AnyNum` と `Neg`。符号付き整数・浮動小数・固定小数点）に分け、符号なし整数は `Num` を満たさない。既定の数の境界を安全な意味にする（P10）。`std.math` の `min` / `max` / `sum` は `AnyNum`、`abs` は `Num`。`Float` は `Num` を満たすので否定を持つ。
  - (2) `AnyNum` は `Sub` を含み、0 を下回る引き算は実行時に検出する。`Sub` を除いて `+ Sub` を要求する案は、`AnyNum` を選んだこと自体が印なので印が二重になり、具体的な `U32` の引き算と規則が分かれ、符号なしを受ける総称の関数に頻出する（P10。元の推奨を比べ直して改めた）。名前は `AnyNum`（`Arith` は中身と、`NumBase` は .NET の `INumberBase` と、`Numeric` は `Num` と紛れる。`Scalar` は仕様の「スカラ」と衝突する）。
  - (3) `Int`（全ての整数）と `Unsigned`（`Int` の印）を今置く。`Int` は `AnyNum` `Eq` `Ord` `Hash`、ビット演算の 5 つ、`Not`、ラップ・飽和の 6 つを満たし、`ONE` `MIN` `MAX` `BITS` を持つ（`Show` / `Default` は `Num` / `Float` と同じく含めない）。`Unsigned` は負数を持たず `>>` が論理シフト。添字・長さ・大きさは `U32` に固定（§4.2）なので、`Unsigned` が要るのは幅について総称のビット操作（`T: AnyNum + Shr` で書いた最上位ビットのループは `I32` の負の値で終わらない）。符号付き整数は `Num` と `Int` を満たし、別名（`Signed`）は付けない。`Num + Int` が要るのは否定と整数の機能を両方使う稀な場面に限られ、`AnyInt` / `Int`（符号付き）に揃える案は、多い場面に長い名前が付き、他の言語の「整数」（符号なしを含む）と読みがずれる。`Unsigned` と `Num` が両立しない否定の規則は置かない。
