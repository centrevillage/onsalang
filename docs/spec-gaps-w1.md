## 1. 字句と空白

### S-201 空白に当たる文字

- **論点:** §2.5「改行で文と項目が終わる」、§2.3「（文字列とコメントには任意の文字を書ける）」。どの文字が空白で、どれが改行かを §2 が書いていない。
- **今の実装:** U+0020、タブ、`\r` を読み飛ばす。CR LF とタブは通り、fmt が LF と空白に直す。単独の `\r` は空白で、`let x = 1\r  let y = 2` は 1 行として E0002。コメントの中の単独の `\r` の後ろはコメントのまま読まれ、`// note\r  let y = 2` の `let y = 2` が黙って捨てられる。BOM、改頁、NBSP は E0001。文字列リテラルは行をまたげない（生の LF も CR LF も「unterminated string literal」）。
- **案:** (a) 空白は U+0020 と U+0009 だけ。改行は LF で、CR LF も一つの改行として読み、fmt が LF に揃える。単独の CR は、コメントと文字列の中も含めて E0001。他の制御文字と Unicode の空白は今どおり E0001。(b) 単独の CR を改行として読む。(c) 単独の CR を空白として読む（今の実装）。(d) CR LF もエラーにする。
- **他言語:** 単独の CR を、Python・Node・Swift は改行として読み、行コメントもそこで終わる（`# c\rprint("hidden")` で hidden が出る）。Ruby は「treated as a mere space」と警告して空白として読み、コメントは続く。Go は未確認。
- **推奨と理由:** (a)。単独の CR は読みが分かれ（改行か空白か）、エディタとコンパイラの読みが食い違うとコメントの中にコードを隠せる（今の実装はそうなる）。CR LF とタブは意味が一つの無害な余分なので fmt で揃える。(d) は Windows の既定の改行を拒むだけ。後で単独の CR を開ける制限で、増える規則は「空白と改行の閉じた一覧」の一つ。
  - 文字列リテラルが行をまたげないことを §2.4 に書く。これが無いと、fmt の CR LF → LF が文字列の値を変えるかの問いが残る（Fable の指摘）。
  - 別の S にしてよい論点: コメントと文字列の中の U+2028 / U+2029 と双方向の制御文字（Node は U+2028 で行コメントを終え、Python と Swift は終えない）。同じ理由で E0001 にする方向。
- **影響:** §2 に「空白と改行」の段落、§2.3 の括弧書き、§2.4（文字列は行をまたげない）、§18.2 の fmt の正規形（改行は LF）。E0001。W3-04、W3-11。`tools/fmt_props.py` の摂動にタブと CR LF を足せる。

### S-202 見出しが継続するときの `{`

- **論点:** §2.5「ブロックの `{` は、それを持つ宣言や見出し…と同じ行に書く」。見出しが行末の二項演算子で継続するとき（`if a &&` の次の行に `b {`）、どの行を指すかが無い。
- **今の実装:** `if p &&\n    q {` を受理する。`{` を次の行に置くと E0002（§2.5 は E0003）。
- **案:** (a) 「`{` は見出しの最後のトークンと同じ行に書く」。(b) 見出しを 1 行に限る。(c) 継続した見出しだけ `{` を独立の行に置ける。
- **他言語:** Swift は `if a &&\n  b {` も `if a\n  && b\n{` も受理する。
- **推奨と理由:** (a)。複数行の引数を持つ見出し（§11.7 の `) -> F32 at sample {`）が既にこの形で、一つの文で言える。(b) は複数行の引数と矛盾し、(c) は二つの書き方を作る（P2）。継続した見出しの行が本体と同じ深さに並ぶ fmt の字下げは、今の「継続は 1 段」のままにする（規則を増やさない）。
- **影響:** §2.5 の 1 文。E0003。W3-06。

### S-203 `.` の前後と後置の `?` の前の空白

- **論点:** §2.5 は、後置の `(` / `[` の前の空白（R-101、S-123 で E0020）と、次の行が `.` で始まる継続を書くが、行の中の `.` の前後（`a . b`、`a. b`）と、後置の `?` の前（`x ?`）の空白を書いていない。
- **今の実装の挙動:** 受理し、fmt が `a.b`、`x?` に整える（W1-07/b で確かめた）。
- **案:**

  - (b) 受理し、fmt で揃える（意味が一つの無害な余分として扱う）。
- **推奨と理由:** (a)。後置の `(` / `[` の前の空白を E0020 にした決定（R-101、S-123）と同じ種類（後置の記号の前後の空白）で、規則を一つの文にまとめられる（「後置の記号 `(` `[` `.` `?` は、行の中で前の要素に空白を挟まずに付ける」）。`x ?` は、C 系の読み手に条件演算子の始まりとも読める。主な書き手が LLM で、厳格にしても摩擦は小さい。後で (b) に緩められる。
- **影響:** 仕様 §2.5（後置の記号の一文）、E0020 の規則の表（W3-02）、構文解析（W3-06）、fmt の性質テストの摂動（`.` と `?` の隣は今も触らない）。

## 2. リテラルとパターン

S-184 と S-185 は同じ規則（`-` 付きの整数リテラル）を使う。S-185 と S-186 は、S-109 / S-48 の E0020 の規則の当て方。

### S-184 型の最小値の負のリテラル

- **論点:** §4.7「型が決まった時点で範囲外のリテラル…は E0408」。`-128: I8` の範囲を `-` の前に見るか後に見るか。
- **今の実装:** `-128: I8`、`-2147483648: I32`、`-9223372036854775808: I64` を受理する。`-(128): I8` は E0408。R-03 は「畳むのは、ソースの数値リテラルに直接付いた `-` だけ」と決めている。
- **案:** (a) 整数リテラルに直接掛かる前置の `-` を含めた値で検査する。間の括弧は見ない（§2.4「`(e)` は常にグループ化」）。符号なしは今どおり E0401。(b) 括弧を挟むと `-` の前の値で検査する。(c) 常に `-` の前の値で検査する（最小値は `I8.MIN`）。
- **他言語:** Swift は `-128` を通し、`-(128)` は「integer literal '128' overflows」（(b)）。rustc は両方通す（(a)）。
- **推奨と理由:** (a)。(b) では fmt の冗長な括弧の除去（§3.1）が `-(128)` を `-128` に書き換え、誤りのプログラムを通るプログラムに変える。(c) は `-127` が通って `-128` が通らない表面の非一貫性で、PCM の `-32768` も書けない。
- **影響:** §4.7（か §2.4）に 1 文。E0408、E0401。W2-06、W3-05。否定例: `-129: I8`。
- 回答:

### S-185 パターンの負の整数と定数

- **論点:** §7「リテラル: 整数、`Char`、`Bool`、`Str`」。`-1 =>` と定数（`LIMIT =>`、`I64.MAX =>`）が書けるかが無い。§15.1 は「パターンに列挙子でない名前」を E0308 とする。
- **今の実装:** `-1 =>` を受理する。`LIMIT =>` と `I64.MAX =>` は E0302（§15.1 とずれる）。
- **案:** 負の数は (a1) 書ける（範囲は S-184 と同じ）か (a2) 書けない。定数は (b1) E0020 で候補はガード `x if x == LIMIT`、(b2) E0308、(b3) 書ける（`==` で比べる）。
- **他言語:** `case -1:` は Python・Swift・rustc で通る。定数は読みが分かれる: Python の `case LIMIT:` は何にでも一致して束縛し、Swift の `case LIMIT:` と rustc の `LIMIT =>` は定数と比べる。
- **推奨と理由:** (a1) と (b1)。負の整数はどの言語でも同じ値と読む。定数は束縛か比較かで読みが逆なのでエラーにし、ガードの候補が作れるので、浮動小数と `..` のパターン（S-109）と同じ E0020。(b3) は後で開ける。
  - パターンに書いた名前の扱いを字面の種別で閉じる: `UPPER_SNAKE` は E0020（上の定数の規則）、`UpperCamel`（型・trait）は E0308、`snake_case` は束縛（見えている項目の名前と同じなら §5.1 のシャドーイングで E0304）。関数 `f` の `f =>` が E0304 と E0308 の二通りに読めるのを防ぐ（Fable の指摘）。
- **影響:** §7 のリテラルの項と「無いもの」、パターンの名前の扱い、§18.1 の E0020 の一覧。E0020、E0308、E0304、E0408、E0401。W2-06、W4-04。
- 回答:

### S-186 `@` 束縛のパターンのコード

- **論点:** §7「無いもの: …`@` 束縛」。コードが無い。§18.1「候補を作れないときは一般の構文エラー（E0002）とし、…note で示してよい」（S-48）。

### S-187 `Bool` の網羅と到達しない腕

- **論点:** §7「`match` は網羅的（E0501）」。`true` / `false` で網羅か、前の腕で覆われる腕が誤りかが無い。E0503 は文の到達だけを扱う。
- **今の実装:** `true` / `false` で網羅と認める。到達しない腕（`_` の後の腕、重複した `1 =>`、`true` / `false` の後の `_`）を黙って通す。
- **案:** 網羅は (a) `Bool` を二値の列挙として判定。到達しない腕は (b1) E0503（候補は腕を消す形と、覆っている腕が `_` か束縛だけなら最後へ移す形）、(b2) 新しいコード、(b3) 誤りにしない。
- **他言語:** Swift は `true` / `false` で網羅とし、覆われた腕を警告する。rustc も警告。Python は重複した `case 1:` に何も言わない。
- **推奨と理由:** (a) と (b1)。Onsa は警告を持たず、到達しない文（E0503）と使われない束縛（E0309）を誤りにしている。到達しない腕も消し忘れか順の誤りで、直し方が E0503 と同じなので同じコードにまとめる（§18.1）。後で緩められる制限。
  - 網羅に数えるのは `Bool`、enum、それらのタプル・struct だけで、整数・`Char`・`Str` のリテラルは数えない（`U8` に 256 個のリテラルを並べても `_` か束縛が要る）と §7 に書く。判定が単純になり、リテラルの後の `_` は常に到達する（Fable の指摘）。
- **影響:** §7 の網羅と E0503 の項。E0501、E0503。該当する W が無い（網羅の検査に足す作業）。`match~` も同じ。

## 3. 型の推論

### S-174 総称の返り値の型が `let` の時点で決まらないとき

- **論点:** §4.5「期待型が無く決まらなければ E0406」。§4.7「単一化変数で、後の文からの決定を許す」「リテラル以外の型変数（`let x = None` の…、`Buf.zeroed(4)` の要素の型）が関数の終わりに残れば…E0406」。

### S-193 引数の中で同じ変数を `inout` に渡す呼び出し

- **論点:** §5.2「同じ変数を一つの呼び出しで二度 `inout` に渡すとエラー（E0702）…引数の中で同じ変数を読んで値を作るだけなら重ならない」。§3.5「`inout` の排他性は呼び出しの間について判定する」。`f(inout x, g(inout x))` が対象か。

### S-192 無名関数の中の `?` の脱出先

### S-190 捕捉する無名関数を、関数型の引数に渡せるか

- **論点:** §5.3 は捕捉するクロージャを「引数の位置にだけ」現れるとし、§4.1 は関数型を「Copy（捕捉なし）」とする。std の `array.from_fn(f: fn(U32) -> T)` は捕捉する無名関数を受け、§16.1 の `run` は「捕捉を持たない関数値」を要する。同じ `fn(...)` の型で受けるものが違う。
- **今の実装:** 利用者の関数の `fn(I32) -> I32` の引数に捕捉する無名関数を通すので、`fn keep(f: fn(I32) -> I32) -> fn(I32) -> I32 { f }` に渡して返す形が検査を通る（今は降下が E0200 で止める）。`let` とフィールドに置くと E0710。
- **案:** (a) 渡せない。捕捉する無名関数を受けるのは std の 3 関数だけで、std にだけ許す印で区別する。(b) 渡せる。既定のモードの関数型の引数は、関数の中で第二級（呼ぶ、関数型の引数へ渡すだけ。返す・保存する・捕捉するは E0710）。関数値を保存する関数は `move f: fn(...)` と宣言し、捕捉の無い関数値だけを受ける（呼び出し側は `make_op(1, move inc)`、§16.1 の `run` は `move audio`）。(c) 関数値を全て第二級にする。
- **他言語:** Swift は関数型の引数を既定で逃げないものとし、返すと「using non-escaping parameter 'f' in a context expecting an '@escaping' closure」、保存するには `@escaping` を付ける。rustc の `fn` 型は捕捉する closure を受けない。
- **推奨と理由:** (b)。(a) は std だけの特別な印が要り、後で開くと今は書ける `keep` の意味が変わって壊れる（緩める向きにならない）ので、構造は今決める。(b) は「借用は呼び出しの外へ出ない、`move` は受け取って持つ」という引数モードの意味を関数型に当てるだけで、新しい語が要らない。保存する側が注意の要る側なので印を付ける（P10）。第 2 期の `Array` の `map` / `filter` と利用者の高階関数は既定の形で書け、C・WASM では引数を「関数と環境の組」、保存する値を「関数だけ」で表せる。(c) は §16.1 と関数値のフィールドを塞ぐ。
  - §5.4 は「借用束縛は…返り値にするときも Dup 型は複製になる」と書き、関数型は Copy なので、字面どおりだと既定のモードの `f` を返せてしまい、(b) と食い違う。§5.3 と §5.4 に「既定のモードの関数型の引数は捕捉を持ちうるので、複製して持ち出せない（返す、保存する、捕捉するは E0710）。`move` の関数型の引数は、捕捉の無い関数値だけを受けて所有する位置」と書く。これで `move` が Copy の複製と読める迷い（下書きで確度を低くした理由）も解ける（Fable の指摘）。§4.1 の「Copy（捕捉なし）」は、保存・返却・`move` の位置の関数値の性質として読み替える。

## 10. 処理系の限界と内部エラー

### S-183 構文の入れ子の深さの上限

- **論点:** 仕様に上限が無い（§12.5 はインタプリタの呼び出しの深さだけ）。深い入れ子でコンパイラのスタックが溢れると、プロセスがシグナルで終わり、§18.2 の終了コードを守れない。
- **今の実装:** 64 MiB のスタックのスレッドで走り、それを超える深さはシグナルで落ちる（`tools/fuzz.py --deep` の 2000〜20000 段）。macOS ではクラッシュの報告が出るので、onsa に深い入れ子は渡していない。
- **案:** (a) 仕様に固定の上限を置く。数えるのは構文の木の深さ（括弧、ブロック、型、前置演算子、二項演算子の連鎖、後置の連鎖、`else if` の連鎖の全て）。超えたら構文の段の新しいコード（E0006 が空き）で、note で `let` に分けることを示す。値の候補は 256。(b) 括弧とブロックだけを数え、連鎖は処理系が再帰なしで扱う。(c) 上限は処理系が決める。
- **他言語:** Python は丸括弧 201 段で「SyntaxError: too many nested parentheses」、199 段は通る。clang（Apple clang 21）は `-fbracket-depth=256` を明示すると 300 段で「fatal error: bracket nesting level exceeded maximum of 256」になるが、既定のままでは 300 段・512 段・1025 段の丸括弧が全て通った。ドライバは `-fbracket-depth` を渡しておらず（`clang -###`）、既定の上限は 1025 段以上。それより深い入れ子は、clang 自身のスタックが溢れる恐れがあるので試していない（10 段から 1025 段で最大の常駐集合が約 7 MB 増え、既定の 8 MB のスタックに近い）。Fable が挙げた文書上の既定の 256 は、この機械の clang には当てはまらなかった（Fable の指摘を受けて実機で確かめた）。
- **推奨と理由:** (a)。上限が処理系で違うと、ブラウザの IDE（WASM）と CLI で同じファイルの合否が変わる（P8）。木の深さなら全ての段が再帰のまま有界になり、判定は構文解析の一か所で済む。(b) は全ての段に反復の実装を強いる。256 は実際のコード（FIR の 64 項の和など）より十分大きい。値（256 か 1024 か）は低い確度。
  - 生成した C の深さ: C のコンパイラの既定は処理系で違い（上の確かめ）、深い入れ子は C のコンパイラ自身を落としうるので、Onsa の上限だけでなく C のバックエンドの出力の深さも抑える。同じ群の連鎖は括弧なしで平らに出す（`a + b + c` は C でも左結合）方が、一時変数に分けるより安い（Fable の指摘）。
- **影響:** §2（か §18.1）に上限と新しいコード、計画 §5 の登録簿。W3 の構文解析器、C のバックエンドの出力。`tools/fuzz.py --deep` を gate に入れられる。`SPEC-GAP(S-183)` の印を外す。
