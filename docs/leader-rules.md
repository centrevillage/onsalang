# 親の規則

主のセッション（親。監督とレビューの担当）が、担当（`.claude/agents/` の `onsa-*` の 5 つ）と協調して作業するときの規則である。

- 担当と共有する手順（作業票、完了の定義、報告の形、W の進め方、仕様の空白の流れ、検査の回し方）は計画 `docs/implementation-tasks.md` §8、担当の共通の規則は `docs/agent-rules.md` にある。ここには親だけが使う運用の知識を書き、他の文書にある規則は参照だけにする（同じ規則を二か所に書かない）。
- 親も `agent-rules.md` の 1 章（リポジトリとシェル）、3 章（機械を落とさない）、5 章の文書の編集の規則に従う。推奨を出すときは 7 章（推奨の基準）を使う。
- この文書は、親が文を提案し、利用者が了承してから親が書く（2026-10-09、利用者）。日付の付いた注意（費用の目安など）は親が改め、改めたことを報告する。他の文書と食い違いを見つけたら、利用者に知らせて揃える。

## 1. セッションの始めと区切り

1.1 始めに確かめる。
  - エージェントの一覧に `onsa-*` の 5 つがあるか。
  - 記憶の「次のセッションの始め」（今の位置、次の作業、最初にすること）。
  - `git log --oneline -3`、`git status`、`git worktree list` が記憶と合うか。
  - 前のセッションの scratchpad の成果（作業票の下書き、パッチ、報告）が残っているか。

1.2 区切り（2026-10-08、利用者）: 文脈の使用が 8 割を超えたら、区切りの良いところで区切る。新しい作業を始めず、動いている担当の報告を処理し、通ったものをコミットし、残りは作業ツリーと scratchpad に置き、記憶を今の状態に合わせて終える。

1.3 記憶に書くのは今の状態だけにする（段の進捗、次の作業、scratchpad の位置、次に振る番号）。作業ごとの持ち越しは `docs/carryovers.md` に書く。規則と手順は、この文書か、計画・担当の規則に書く。新しい規則が決まったら、この文書に足す案を出す。

1.4 scratchpad はセッションごとに変わる。次のセッションで使う成果（作業票の下書き、パッチ、壊す側の報告）は、記憶に絶対パスを書く。壊す側の報告は後のリファクタリングの材料なので消さない。

## 2. 担当の動かし方

2.1 役割、モデル、同時に動かす数、枠は、計画 §8.6 の「役割の担当」。直しの確かめ（壊す側の再確認か、親の再現か）は §8.6 の「直しの確かめ」。

2.2 担当は Agent の `subagent_type` で呼び、`model` の引数は渡さない（定義のモデルと推論の努力を使うため）。

2.3 並行か直列か（2026-10-09、K-23）: 衝突の重さ（同じ関数を触るか、表の並びの追記だけか）と、後の側の壊す側の確かめをやり直す必要があるかで、親が決め、報告に理由を書く。主のツリーを触る担当は一度に一つ。

2.4 作業票は scratchpad に書き、計画 §8.1 の形で渡す。`docs/carryovers.md` の、その作業 ID の行を範囲か注意に入れ、入れた行はその作業のコミットで消す。

2.5 テストの票と実装の票は並べて走らせてよい。実装は表の骨組みから始め、テストが届いたら親が写す。期待値を変えずに置き場所だけ変える直し（事例ファイルを分けて他の作業へ回す）は、実装の担当に任せてよい。

2.6 直しは同じ担当に SendMessage で返す。前のセッションの担当は SendMessage で呼べないので、新しい担当に、作業ツリーの成果のパッチと前の報告の写しで渡す。前の報告は `~/.claude/projects/-Users-centrevillage-projects-onsalang/<セッション ID>/subagents/agent-*.jsonl` の `SubagentHandback` の入力から取り出せる。

2.7 担当の報告の主張は抜き取りで再現する（Q-11）。担当が「前からの挙動」と書いたものは、dev のバイナリで確かめる（2026-10-09、W3-20 の `g(1).m[I32](2)` は後退だった）。

2.8 費用の目安（2026-10-09 の時点、トークン）: 空白の下書き 1 体 18〜27 万、助言 1 体 10〜20 万（二段）、W の実装 1 回 40〜80 万（直しの往復を含む）、テストの票 39〜53 万、壊す側 28〜40 万、決定の反映 18〜32 万。費用を下げる工夫（自己点検の表で往復を減らす、直しの確かめを親が再現の入力で行う）を続ける。

2.9 担当は `report.md`・`findings.md` のような報告の名前のファイルを Write で書けない（ハーネスが「報告は本文で返せ」と拒む。置き場所によらず、`notes.md` などの名前は通る。2026-10-10 に確かめた）。作業票では報告を最後の返答の本文で返させ、親が `subagents/agent-*.jsonl` の SubagentHandback の入力の `message` をスクリプトで scratchpad に保存する（2.6 と同じ取り出し方）。名前を変えて避けることはしない。

## 3. 作業ツリーと成果の写し

3.1 親は担当の作業ツリーに `cd` しない（主のセッションの作業ディレクトリがその作業ツリーに移る。2026-10-09 に二度起きた）。作業ツリーは `git -C <経路>` と絶対パスで読む。

3.2 写し方（担当は別の作業ツリーへ `git -C` を向けられないので、親が写す）:
  1. 担当の作業ツリーで `git add -A`、`git diff --cached --binary <基のコミット> > <パッチ>`、`git reset`。
  2. 主のツリーで `git apply -3 <パッチ>`、`git restore --staged .`。
  担当どうし（t → i）の受け渡しも同じパッチで行い、担当に `git apply -3` させる。

3.3 基のコミット: 担当が dev を取り込んだ後に dev が文書だけ進んだときは、取り込んだ dev のコミットからの差分で写す。主が進んで担当に取り込ませるときは、WIP のコミットと `git merge dev`（`agent-rules.md` 2 章）。並行の実装では、後に写す側が WIP のコミットの後に `git merge dev` をする。

3.4 `tests/pending.toml` は、3-way の結果を手で直すより、dev の版から作り直す形（dev の版に、その作業で載せる項目と外す項目を当て直す）が安全だった（2026-10-09）。

3.5 `git apply -3` の結果は索引に載る。続けて別のコミットをすると一緒に入る（2026-10-08 に一度起き、`git reset --soft` で作り直した）。写した後は `git restore --staged` で索引から外し、コミットは `git commit <パス>` か、索引を確かめてから行う。

3.6 作業ツリーを消す前に、成果が主のツリーに写ったこと（主のツリーの差分）と、担当の報告を scratchpad に保存したことを確かめる。

## 4. レビューとコミット

4.1 観点は利用者の 3 つ（計画 §8.5 の「壊す側」）。毎回読むもの（〔危険〕の差分、`tools/builtin_names.toml` と `tests/pending.toml` の増分）は §8.6 の「親」。gate を回し直すかは §8.5 の「検査の回し方」。

4.2 実装待ちの一覧で事例ごと黙らせた項目は、後退を隠す（2026-10-09、`range_move.onsa` の `for i in move 0..<n` の後退は、ファズが見つけた）。増分を読むときは、黙らせる範囲がその作業の既知の失敗だけかを確かめる。

4.3 大きさの基準（計画 §8.5）: 報告の見積もりと実際の行数を、dev との差（テストとデータのファイルを除く）で確かめる。

4.4 gate の `test` の段は `cargo test --workspace` を `--no-fail-fast` なしで回すので、最初に落ちたテストのバイナリより後は走らない。直した後は `cargo test --workspace` だけを回し直して、残りを確かめる。

4.5 fuzz の変異体はコーパスの全体に依存し、事例を足すと既存の不具合が新しい型として出る。入力を `tests/fuzz/` に保存し、`fuzz-input` の項目と R を登録する。字句解析器の R-01 の入力は `crates/onsa_syntax/src/cst_tests.rs` の `LEXER_PANICS` にも足す。

4.6 コミット: W の作業は、壊す側と親のレビューが通ったら、作業 ID ごとに親がコミットする（§8.6。✅ の印、途中で見つけた R / S の登録の区切り）。それ以外は、利用者が「コミットして」と言ったときだけ。push はしない。

4.7 コミットの題は英語の命令形で、内容を書き、作業 ID か決めた S を含める（今の慣習: `Call function values with ... (W3-20)`、`Decide S-351 and S-352: ...`、`Register S-353 to S-361 and R-198 found by W3-20/b and W3-09/t`）。

## 5. 利用者との判断

5.1 論点は ID を付けて一覧にし、項目ごとに案、借用元、本言語の方針に触れる点を出す。利用者は項目ごとに「OK / 詳しく / 再検討」で返す。推奨は示すが、決定は待つ。

5.2 推奨の基準は `agent-rules.md` 7 章。重い判断の束と仕様の空白の独立のレビュー（推奨を伏せて選ばせ、次に突き合わせさせる）は計画 §8.6。結果は「一致した項目は確認だけ、割れた項目と新しい論点は判断を」の形で出す。

5.3 調べた結果が元の推奨を覆すときは、推奨を改めて、理由を示す。

5.4 条件付きの了承（2026-10-08、S-281・S-288・S-289）: 推奨には、実装の量の見積もり（どのファイルの何か所か）と、後の作業への影響を添える。利用者が条件（「実装量が見積もれる規模なら」）を添えて了承したら、親が見積もって条件を満たすかを示してから記録する。実装の担当には「費用が高い形は無理にせず、形と見積もりを報告」と伝える。

5.5 了承の範囲を広げて読まない（2026-10-08、S-259）: 回答がどの項目を指すかが一つに決まらないときは、項目の ID を挙げて確かめてから記録する。確認だけの項目も、利用者が ID を挙げて了承したものだけを決定にする。短い返事が指す既決の仕組みも、読みを ID で示して確かめる（S-287 の「仕組みは変えずに」は S-54 を指していた）。

5.6 既決の部分を論点に戻さない（2026-10-08、S-248）: 下書きを確かめる段で、前の決定、付録、登録済みの R と重なる部分を探し、「決定済み」と明記して新しい点だけを渡す。

5.7 回答の書き込み: 利用者は文書に `@centrevillage` の行や「回答:」の行で答えを書くことがある（vim で編集）。回答は「書き終わった」と言われてからまとめて読む。スワップファイルがある間は、その文書を編集せず、会話で知らせる（確かめ方は `agent-rules.md` 5 章）。

5.8 重い処理（gate、多数の担当、ファズ）を足すときや回すときは、並列の数と回数を見積もって示し、全てのコアを使う処理を並べない（2026-10-08、利用者）。

## 6. 決定の反映

6.1 論点を整理する前に、今の挙動や仕様の該当の行を実際に確かめる。他の言語の扱いは記憶だけで答えず、手元で動かすか調べて、出典を付ける。

6.2 揃えて更新する文書:
  - 仕様。
  - 変更点 `docs/onsa-0.3-changes.md` §4（S-29、S-31 を先頭に固定し、その下は新しいものが上）。
  - 計画 §2 の S（S-29 の下に新しいものが上）と、要れば §3・§5。
  - 反映の作業 `docs/rework-phase1.md` の「実現する決定」。
  - 関係するレビューと点検の表（`docs/review-impl-phase1.md` の本文の決定と §8 など）と、空白の資料の状態の欄。

6.3 表を編集したら列の数を検査する（セルの中の `||` は `\|\|`）。計画 §5 の「欠番:」の行と「第 2 期」の M の欄は gate が読むので、書き方を保つ。

6.4 仕様の ```onsa ブロックを変えたら `tools/check_spec_examples.py` を回し、`tests/spec` の写しを直すか、実装待ちの一覧の spec-example に載せる（名前はツールが示す）。仕様に新しい診断コードを書いたら、登録簿 `crates/onsa_diag/src/codes.rs`、計画 §5、実装待ちの一覧の diag-code を揃える（gate の diag-registry が照合する）。

6.5 決定を作業に割り当てるときは、既存の作業の欄に足すだけで終えず、作業が過大にならないか、担う作業の無い決定（実装済みのもののテスト、仕様が約束した性能など）が無いかを確かめ、要れば分ける（K-15）。

6.6 文書は Python の一意一致置換で編集する（ヒアドキュメントの囲み方は `agent-rules.md` 1 章）。追記する本文は、先にファイルに書いてから読み込む。日本語と ID の間には空白を入れる。

6.7 新しい方針が決まったら、`agent-rules.md` 7 章にも足す。担当の定義（`.claude/agents/`）は利用者が編集し、親は文を提案する（2026-10-09）。

## 7. 一般の規則（このプロジェクトで起きたことから）

7.1 状態を確かめる命令と、その状態に頼る変更は、別のコマンドにする。確かめた結果を読んでから変える（2026-10-08、スワップファイルの確かめに編集を続けたため、vim で開いていた計画を書き換えた）。

7.2 記録と報告の前に、主張を再現で確かめる。担当の報告、下書き、記憶にある事実（ファイル、関数、フラグ）も同じ。

7.3 見積もりと実際の差、失敗した検査、飛ばした段は、隠さず報告に書く。

7.4 範囲の外で見つけた問題は直さず、持ち越しか R / S に登録する（担当の §8.2 の 6 と同じ）。
