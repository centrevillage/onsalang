# 親の規則

主のセッション（親。監督とレビューの担当）が、担当（`.claude/agents/` の `onsa-*` の 5 つ）と協調して作業するときの規則である。

- 担当と共有する手順（作業票、完了の定義、報告の形、W の進め方、仕様の空白の流れ、検査の回し方）は計画 `docs/implementation-tasks.md` §8、担当の共通の規則は `docs/agent-rules.md` にある。ここには親だけが使う運用の知識を書き、他の文書にある規則は参照だけにする（同じ規則を二か所に書かない）。
- 親も `agent-rules.md` の 1 章（リポジトリとシェル）、3 章（機械を落とさない）、5 章の文書の編集の規則に従う。推奨を出すときは 7 章（推奨の基準）を使う。
- この文書は、親が文を提案し、利用者が了承してから親が書く。規則に足す案は、一般の手順として効くものだけにし、一つの不具合から引いた細かい注意にしない。日付の付いた注意（費用の目安など）は親が改め、改めたことを報告する。他の文書と食い違いを見つけたら、利用者に知らせて揃える。

## 1. セッションの始めと区切り

1.1 始めに確かめる。
  - エージェントの一覧に `onsa-*` の 5 つがあるか。
  - 記憶の「次のセッションの始め」（今の位置、次の作業、最初にすること）。
  - `git log --oneline -3`、`git status`、`git worktree list` が記憶と合うか。
  - 前のセッションの scratchpad の成果（作業票の下書き、パッチ、報告）が残っているか。

1.2 区切り: 文脈の使用が 6 割を超えたら、区切りの良いところで区切る。作業の区切りが悪いときは 8 割まで続けてよい。区切るときは、新しい作業を始めず、動いている担当の報告を処理し、通ったものをコミットし、残りは作業ツリーと scratchpad に置き、記憶を今の状態に合わせて終える。目安を 6 割にしたのは、長いセッションほど 1 回の呼び出しが高くなるため（費用の内訳は `agent-rules.md` 1 章）。
W の作業のコミットなどタスクの切れ目が近いときは、6 割の前でも区切ることがある。そのときは次の作業を始めず、区切りの準備（記憶、作業ツリー、コミット）を済ませておく。

1.3 記憶に書くのは今の状態だけにする（段の進捗、次の作業、scratchpad の位置、次に振る番号）。作業ごとの持ち越しは `docs/carryovers.md` に書く。規則と手順は、この文書か、計画・担当の規則に書く。新しい規則が決まったら、この文書に足す案を出す。

1.4 scratchpad はセッションごとに変わる。次のセッションで使う成果（作業票の下書き、パッチ、壊す側の報告）は、記憶に絶対パスを書く。壊す側の報告は後のリファクタリングの材料なので消さない。

## 2. 担当の動かし方

2.1 役割、同時に動かす数、主のツリーを触る数、枠は、計画 §8.6 の「役割の担当」（モデルと推論の努力は定義の frontmatter、2.2）。直しの確かめ（壊す側の再確認か、親の再現か）は §8.6 の「直しの確かめ」。

2.2 担当は Agent の `subagent_type` で呼び、`model` の引数は渡さない（定義のモデルと推論の努力を使うため）。

2.3 並行か直列か: 衝突の重さ（同じ関数を触るか、表の並びの追記だけか）と、後の側の壊す側の確かめをやり直す必要があるかで、親が決め、報告に理由を書く。

2.4 作業票は scratchpad に書き、計画 §8.1 の形で渡す。担当ごとに scratchpad の下のディレクトリを決め、書く場所を作業票に明記する（担当どうしでファイルを上書きしないため）。
`docs/carryovers.md` の、その作業 ID の行を範囲か注意に入れ、入れた行はその作業のコミットで消す。
作業票を出す前に、実現する決定の数を計画 §8.5 の「単位の大きさ」の目安と比べ、超えるなら単位に分けて、単位ごとにテストの票と実装の票を出す。

2.5 テストの票と実装の票は並べて走らせてよい。実装は表の骨組みから始め、テストが届いたら親が写す。期待値を変えずに置き場所だけ変える直し（事例ファイルを分けて他の作業へ回す）は、実装の担当に任せてよい。

2.6 直しと次の単位は、同じ担当に SendMessage で返す。ただし担当の文脈が 30 万トークンを超えたときは、新しい担当に引き継ぐ（呼び出しのたびに文脈の全体を読み直すので、引き継ぐと費用がおよそ半分になる。2026-10-13 に確かめた）。
前のセッションの担当は SendMessage で呼べないので、同じく新しい担当に引き継ぐ。担当の文脈の大きさと費用は `tools/handback.py usage` で見る（動いている担当にも使える）。
単位の途中で 30 万を超え、残りが単位の半分を超えるなら、次の区切り（絞ったテストが通る所）で WIP のコミットと「次の担当へ」を書いて止めるよう伝え、新しい担当に引き継ぐ（終わりの近い担当を替えると、新しい担当の読み込みの方が高くつく）。
引き継ぎの作業票（2.10）には、決まったこと（範囲、置き場所と仕組み、親の答え）を親が一枚にまとめて書き、前の設計メモと報告は参照にとどめる（新しい担当が最初に読む量を減らす）。
前の報告は `~/.claude/projects/-Users-centrevillage-projects-onsalang/<セッション ID>/subagents/agent-*.jsonl` の `SubagentHandback` の入力から取り出せる（`tools/handback.py save`）。
親から担当への返事は会話にしか残らないので、壊す側や新しい担当に渡すものは scratchpad のファイルに控える。

2.7 担当の報告の主張は抜き取りで再現する（Q-11）。担当が「前からの挙動」と書いたものは、dev のバイナリで確かめる。

2.8 費用の目安（担当の文脈の最大）: 2026-10-13 の時点で、テストの票 26〜46 万（API 換算 $4〜13）、実装の 1 単位 21〜55 万（$4〜21。設計メモだけで 16〜41 万）、壊す側 27〜32 万（$4〜6）。2026-10-09 の時点で、空白の下書き 1 体 18〜27 万、助言 1 体 10〜20 万（二段）、決定の反映 18〜32 万。
大きさは単位の大きさ（計画 §8.5）でおさえる。費用を下げる工夫（自己点検の表で往復を減らす、直しの確かめを親が再現の入力で行う）を続ける。

2.9 担当は `report.md`・`findings.md` のような報告の名前のファイルを Write で書けない（ハーネスが「報告は本文で返せ」と拒む。置き場所によらず、`notes.md` などの名前は通る。2026-10-10 に確かめた）。
作業票では報告を最後の返答の本文で返させ、親が `subagents/agent-*.jsonl` の SubagentHandback の入力の `message` をスクリプトで scratchpad に保存する（2.6 と同じ取り出し方）。名前を変えて避けることはしない。

2.10 引き継ぎの作業票は、次の欄を持つ。
  - 読む順（作業票、設計メモ、親の返事、前の報告と、その「次の担当へ」の節）。
  - 状態の基: 前の担当の作業ツリーの枝と、その WIP のコミット（`agent-rules.md` 2 章）。新しい担当は自分の作業ツリーでその枝を `git merge` する。
  - 道具: `tools/` の道具（`run_cases.py`、`speed.py`、`handback.py`）と、前の担当が scratchpad に作った道具。
    ファズの許可の一覧（`tests/fuzz/allowed.toml`）に項目と示す入力を足させるときは、ファズの近似（`onsa_cases --fix-same-place`）が第 1 候補しか当てないことも書く。
  - 前の gate の要約と知られた失敗（入力と違反の文字列）。
  - 古くなった注記と、新しい決定とぶつかる既存の事例（親が `tests/` を検索して挙げる。6.5）。
  - 戻す事例と保留の事例: 「期待値を変えずに通す」と書く前に、親が事例の全体（正しい形の並びを含む）を仕様と突き合わせる。
  - 報告の最後の「引き継ぎの記録」の節（文書だけでは足りず補ったこと、食い違い、前の担当に聞きたかった問い、次に足すもの）。親はそれを読み、引き継ぎの作業票の型を直す。

## 3. 作業ツリーと成果の写し

3.1 親は担当の作業ツリーに `cd` しない（主のセッションの作業ディレクトリがその作業ツリーに移る）。作業ツリーは `git -C <経路>` と絶対パスで読み、道具の作業ディレクトリが要るときは道具に引数で渡す。

3.2 写し方（担当は別の作業ツリーへ `git -C` を向けられないので、親が写す）:
  1. `tools/take.py patch <作業ツリー> <基のコミット> <パッチ>` で、パッチと要約を作る。要約にはテストとデータを除いた行数も入る（4.3）。
  2. `take.py check <パッチ>` で、当て方（そのまま、3-way、既に当たっている）と、当てる先の未コミットの変更との重なりを見る。
  3. `take.py apply <パッチ>` で当てる（3-way で当てても索引に残さない）。
  道具は、自分の置かれたツリーを既定の当てる先にする。他のツリーの道具を使うときは `--to` と `--main` を渡す。
  担当どうし（t → i）の受け渡しも同じパッチで行い、担当に `take.py apply` させる。

3.3 基のコミット: 担当が dev を取り込んだ後に dev が文書だけ進んだときは、取り込んだ dev のコミットからの差分で写す。主が進んで担当に取り込ませるときは、WIP のコミットと `git merge dev`（`agent-rules.md` 2 章）。並行の実装では、後に写す側が WIP のコミットの後に `git merge dev` をする。

3.4 `tests/pending.toml` は、3-way の結果を手で直すより、dev の版から作り直す形（dev の版に、その作業で載せる項目と外す項目を当て直す）が安全である。

3.5 `git apply -3` の結果は索引に載る。続けて別のコミットをすると一緒に入る（入ったら `git reset --soft` で作り直す）。写した後は `git restore --staged` で索引から外し、コミットは `git commit <パス>` か、索引を確かめてから行う。

3.6 作業ツリーを消す前に、成果が主のツリーに写ったこと（主のツリーの差分）と、担当の報告を scratchpad に保存したことを確かめる。

## 4. レビューとコミット

4.1 観点は 3 つ（計画 §8.5 の「壊す側」）。毎回読むもの（〔危険〕の差分、`tools/builtin_names.toml` と `tests/pending.toml` の増分）は §8.6 の「親」。gate を回し直すかは §8.5 の「検査の回し方」。

4.2 実装待ちの一覧で事例ごと黙らせた項目は、後退を隠す。増分を読むときは、黙らせる範囲がその作業の既知の失敗だけかを確かめる。

4.3 大きさの基準（計画 §8.5）: 報告の見積もりと実際の行数を、dev との差（テストとデータのファイルを除く）で確かめる。

4.4 gate の `test` の段は `cargo test --workspace` を `--no-fail-fast` なしで回すので、最初に落ちたテストのバイナリより後は走らない。直した後は `cargo test --workspace` だけを回し直して、残りを確かめる。

4.5 fuzz の変異体はコーパスの全体に依存し、事例を足すと既存の不具合が新しい型として出る。入力を `tests/fuzz/` に保存し、`fuzz-input` の項目と R を登録する。字句解析器の R-01 の入力は `crates/onsa_syntax/src/cst_tests.rs` の `LEXER_PANICS` にも足す。
直すかは、先に実害の大きさで決める。見るのは、実際の書き手が書きうる形か（編集の途中のファイルを含む）、候補が新しい誤りを作るのか、最初から隠れていた誤りが見えるだけか。実害が低ければ直さず、R に理由を書いて記録し、入力を許可の一覧（`tests/fuzz/allowed.toml`）に載せる。実害があれば実装待ちの項目（`fuzz-input`）にして、直す作業を決める。内部エラーと異常終了は許可の一覧に載せられないので、直す（編集の途中で切れたファイルは IDE で現実に起きる）。

4.6 コミット: W の作業は、壊す側と親のレビューが通ったら、作業 ID ごとに親がコミットする（§8.6。✅ の印、途中で見つけた R / S の登録の区切り）。それ以外は、利用者が「コミットして」と言ったときだけ。push はしない。

4.7 コミットの題は英語の命令形で、内容を書き、作業 ID か決めた S を含める（今の慣習: `Call function values with ... (W3-20)`、`Decide S-351 and S-352: ...`、`Register S-353 to S-361 and R-198 found by W3-20/b and W3-09/t`）。

4.8 設計メモを読むときは、置き場所と構造に加えて、各判断の仕組み（何を見て、どう知るか）が書かれているかを確かめる。書かれていなければ返事で問う（後の担当が補うことになるため）。

4.9 gate の外の方法（壊す側の切り詰めや手作りの変異の道具など）で見つかった欠陥が gate を通っていたら、その生成の方法を gate の項目（ファズの変異か事例）に入れる。入れるのは、その作業の直しの往復か、次の区切りの作業である。

## 5. 利用者との判断

5.1 論点は ID を付けて一覧にし、項目ごとに案、借用元、本言語の方針に触れる点を出す。利用者は項目ごとに「OK / 詳しく / 再検討」で返す。推奨は示すが、決定は待つ。

5.2 仕様の空白の独立のレビュー（推奨を伏せて選ばせ、次に突き合わせさせる）と結果の出し方は、計画 §8.6 の「仕様の空白の流れ」の 4・5。重い判断の束も、同じ形で助言の担当に回し、同じ形で結果を出す。

5.3 調べた結果が元の推奨を覆すときは、推奨を改めて、理由を示す。

5.4 条件付きの了承: 推奨には、実装の量の見積もり（どのファイルの何か所か）と、後の作業への影響を添える。利用者が条件（「実装量が見積もれる規模なら」）を添えて了承したら、親が見積もって条件を満たすかを示してから記録する。実装の担当には「費用が高い形は無理にせず、形と見積もりを報告」と伝える。

5.5 了承の範囲を広げて読まない: 回答がどの項目を指すかが一つに決まらないときは、項目の ID を挙げて確かめてから記録する。確認だけの項目も、利用者が ID を挙げて了承したものだけを決定にする。短い返事が指す既決の仕組みも、読みを ID で示して確かめる（S-287 の「仕組みは変えずに」は S-54 を指していた）。

5.6 既決の部分を論点に戻さない: 下書きを確かめる段で、前の決定、付録、登録済みの R と重なる部分を探し、「決定済み」と明記して新しい点だけを渡す。

5.7 回答の書き込み: 利用者は文書に `@centrevillage` の行や「回答:」の行で答えを書くことがある（vim で編集）。回答は「書き終わった」と言われてからまとめて読む。スワップファイルがある間は、その文書を編集せず、会話で知らせる（確かめ方は `agent-rules.md` 5 章）。

5.8 重い処理（gate、多数の担当、ファズ）を足すときや回すときは、並列の数と回数を見積もって示し、全てのコアを使う処理を並べない。

5.9 下書きと独立のレビューで案が割れた項目を出すときは、内部処理の複雑さ（今の行数と後の段で要る手当て）と修正候補の確実性（主な誤りの形ごとの候補の有無と当てた後）の比べの表を先に添える。問われたら、これまでの判断との一貫性（既決の項目と原則を挙げる）と、これからの管理のコスト（後の段の作り直しまで含める）も比べる。

5.10 利用者に見える出力が同じで内部だけが違う細部は、親がメンテナンス性の良い方を選び、理由を一行添えて記録する。

## 6. 決定の反映

6.1 論点を整理する前に、今の挙動や仕様の該当の行を実際に確かめる。他の言語の扱いは記憶だけで答えず、手元で動かすか調べて、出典を付ける。

6.2 揃えて更新する文書:
  - 仕様。
  - 変更点 `docs/onsa-0.3-changes.md` §4（S-29、S-31 を先頭に固定し、その下は新しいものが上）。
  - 計画 §2 の S（S-29 の下に新しいものが上）と、要れば §3・§5。
  - 反映の作業 `docs/rework-phase1.md` の「実現する決定」。
  - 関係するレビューと点検の表（`docs/review-impl-phase1.md` の本文の決定と §8 など）と、空白の資料の状態の欄。

6.3 計画 §5 の「欠番:」の行と「第 2 期」の M の欄は gate が読むので、書き方を保つ（表の列の数の確かめは `agent-rules.md` 5 章）。

6.4 仕様の ```onsa ブロックを変えたら `tools/check_spec_examples.py` を回し、`tests/spec` の写しを直すか、実装待ちの一覧の spec-example に載せる（名前はツールが示す）。仕様に新しい診断コードを書いたら、登録簿 `crates/onsa_diag/src/codes.rs`、計画 §5、実装待ちの一覧の diag-code を揃える（gate の diag-registry が照合する）。

6.5 決定を作業に割り当てるときは、既存の作業の欄に足すだけで終えず、作業が過大にならないか、担う作業の無い決定（実装済みのもののテスト、仕様が約束した性能など）が無いかを確かめ、要れば分ける（K-15）。
決定を作業に割り当てるときは、その決定とぶつかる既存の事例を `tests/` から検索し、作業票に挙げる。

6.6 文書は `agent-rules.md` 1 章・5 章の形で編集する。追記する本文は、先にファイルに書いてから読み込む。日本語と ID の間には空白を入れる。

6.7 新しい方針が決まったら、`agent-rules.md` 7 章にも足す。担当の定義（`.claude/agents/`）は利用者が編集し、親は文を提案する。

## 7. 一般の規則

7.1 状態を確かめる命令と、その状態に頼る変更は、別のコマンドにする。確かめた結果を読んでから変える（例: スワップファイルの確かめと編集を一つのコマンドにすると、vim で開いている文書を書き換えうる）。

7.2 記録と報告の前に、主張を再現で確かめる。下書きと記憶にある事実（ファイル、関数、フラグ）も同じ。担当の報告は 2.7 の抜き取りで確かめる。

7.3 見積もりと実際の差、失敗した検査、飛ばした段は、隠さず報告に書く。

7.4 範囲の外で見つけた問題は直さず、持ち越しか R / S に登録する（担当の §8.2 の 6 と同じ）。

7.5 定型の作業で機械的に処理できるものに気付いたら、ツール化の案（何を、入力と出力、確かめ方）を持ち越しの段の区切りの行に足し、利用者に一行で知らせる。導入は利用者と決めた区切りで行う。
