# 組込み API の候補

- 目的: 仕様に無い組込みの API（組込み型のメソッド、`std` の関数）を、実装が黙って足すのをやめ、必要かどうかを議論してから決める
- 始めた日: 2026-10-03（レビュー [`review-impl-phase1.md`](review-impl-phase1.md) R-18 / R-96 の議論から）

## 方針

- 組込みの API は、仕様に載っているものだけを実装する（閉じた一覧）。
- ただし、事前に設計した API が十分とは限らない。実装や Onsa のコードを書く中で「無いと煩雑」と分かったものは、拒否で終わらせず、ここに候補として挙げて議論する。
- 「Rust などの既存言語にあるから」だけの理由は採らない（コーパスの重力）。名前と意味を借りるのは、Onsa で必要と分かった後で、意味が一致するときだけ（§0.3 の規則 3）。
- 不採用の候補も理由とともに残す。同じ API が再び足されるのを防ぐためである。

## 手順

1. 候補を挙げる。ワーカーは実装せずに、ここへ書いて報告する。次の欄を埋める。
   - 名前と型
   - 無いと煩雑になる実例（Onsa のコード）と、無い場合の書き方
   - 借用元と、意味が一致するか（§0.3 の規則 3、4）
   - 既存の書き方と重ならないか（§0.3 の規則 1、P2）
2. 利用者が判断する（採用 / 不採用 / 保留）。採用したら仕様に載せ、`onsa-0.3-changes.md` に記録する。
3. 実装した API が仕様の一覧に無ければ、レビューで指摘する（Q-10 の印の照合と同じ扱い）。

## 候補

| ID | 候補 | 状態 | 実例・理由 |
|---|---|---|---|
| A-01 | `Option.is_some` / `is_none`、`Result.is_ok` / `is_err` | 不採用（2026-10-03） | 仕様に無いまま実装が足していた（R-96）。仕様、`std`、テスト、例のどこでも使われていない。`match` と `==`（中身が `PartialEq` のとき）で書ける（P2）。書いたら E0413 にし、`match` の形を修正候補に示す |
| A-02 | `Option.unwrap_or(d)` | 不採用（2026-10-03） | A-01 と同じく仕様に無く、使われていない。`match opt { Some(v) => v, None => d }` で書ける。実装は Rust と違って `d` を遅延評価しており、偽の友人になっていた（R-18） |
| A-03 | `Str` の検索と切り出し（`find`、`slice(from, to)`、区切りでの分割、前方一致、数値への変換） | 保留（第 2 期、`Str` の実装のとき） | 0.3 で「文字列の用途は作る・比べる・出すだけ」として外した（§4.2、§19.2）が、実装には残っていた（R-96）。無いと煩雑になりうる用途: プリセットや設定のテキストの解析（`name=value`）、OSC のアドレスの照合（`/synth/voice/1/freq`）、`main` の引数の解析。無い場合は `as_bytes()` とループで書く。`Str` を実装するときに、これらを実際の Onsa のコードで書いて煩雑さを示してから決める。名前は Onsa の流儀に合わせる（`Span.slice` に揃えて `slice`。C++ / JS の `substr` は採らない）。位置はバイト単位（§4.2） |
| A-05 | `Bool` の `PartialOrd` / `Ord` | 不採用（2026-10-03） | 真偽値を並べる、`Map` の鍵にする実例が無い。`a < b` を真偽値に書くのは読みにくい。レビューでは一度「Rust に合わせる」と推奨したが、それはコーパスに引かれた理由だった |
| A-06 | `Char` の `Default`（`'\0'`） | 不採用（2026-10-03） | 既定値が要る場面（宣言の `: Default`、S-29 の `prev~` の初期値）の実例が無い |
| A-07 | `Option` / `Result` の `PartialOrd` / `Ord` | 不採用（2026-10-03） | 実装が仕様に無いまま入れていた。意味（`None < Some`、列挙子の順）が仕様に無く、並べる実例も無い。必要な実例が出たら再検討する |
| A-08 | `Bytes` の `Show` | 保留（第 2 期） | 実装が仕様に無いまま入れていた。書式（16 進など）が決まっていない。ログでバイト列を見たい場面はありうるので、実例と書式を決めてから |
| A-09 | 総称の整数（`T: Int`）と具体的な整数の変換（`T` の値から `U32` の添字を作る、`U32` から `T` を作る） | 保留（R-94、2026-10-05） | `Int` と `Unsigned`（S-84）で幅について総称の整数のコードを書けるようになったが、`T` の値で表を引く処理が書けない。実例: CRC の表引き `table[((crc ^ b) & 0xFF) as U32]` を幅について総称にする。無い場合は幅ごとに具体的な関数を書く。決めること: 名前（`narrow_i32` などの具体的な型の変換メソッド、§3.3 と揃える。ただし S-98 で、変換メソッドは `as` で書けない組にだけ置くと決めたので、`Int` に変換メソッドを置くと具体的な型で `as` と二重になる。この規則を壊さない形（目標の型の関連関数など）を選ぶ）、範囲外の扱い（検査付き・切り捨て・飽和）、`Int` に置くか別の trait か。利用者の型が `Int` を実装できるのは第 2 期（trait の実装、S-72）なので、それより前に決めれば `Int` に足しても壊れるものは無い。それ以後なら、別の trait にするか既定の実装を持たせる（計画 §5 の持ち越しの一覧に載せた） |
| A-10 | 整数のリテラルを `T: Int` の値にする（マスクの `0xFF` など） | 保留（R-94、2026-10-05） | 今は、リテラルは型パラメータの値にならない（§6.6）。総称の整数のコードでは、マスクや定数を `T.ONE` とシフトで作る（`(T.ONE << 8) - T.ONE`）か、幅ごとに書く。案: 全ての整数の型に収まるリテラル（0〜127）だけを `T: Int` の値として認める。定義の位置で範囲を確かめられ、使う場所の奥で誤りにならない（§4.5 の const ジェネリクスと同じ考え方）。利用者の型が `Int` を実装する場合にリテラルをどう作るか（変換の関数が要る、A-09）も一緒に決める。規則を緩める方向なので、既存のコードは壊れない |
| A-11 | 数値の書式（小数点以下の桁数などを決めた文字列化） | 保留（R-102、2026-10-05。第 2 期、`Str` の実装のとき） | 補間に書式の指定（`{x:.2}`）は無く（§2.4）、`Show` は読み戻せる最短の表記を出すだけ（§6.3）。UI のラベル（「12.50 dB」）やログで桁数を揃えたい場面はありうる。無い場合は、整数に丸めてから補間するなどの回り道になる。補間の中に書式を書く形ではなく、関数かメソッドで書く形を、実例と一緒に決める |
| A-12 | 切り捨ての整数の変換（Rust / C の `x as u8` のように下位のビットを取る）と、バイト列・ビット列の trait | 保留（R-126、2026-10-05。第 2 期、`Bytes` の実装のとき） | §3.3 の変換は、整数の縮小を `narrow_<型>() -> Option` だけにした（S-98）。バイト列の組み立て（WAV の書き出し、MIDI のメッセージ）では下位のビットを取る変換が要る。無い場合は `((s >> 8) & 0xFF).narrow_u8().unwrap()` と回り道になる（`unwrap` は値の範囲から panic しないが、型からは分からない）。利用者の見立て: バイト列・ビット列の trait は将来必要になるが、今は要らない。変換のメソッドを足すか、バイト列・ビット列の trait（詰める・取り出す）で書くかを、実例と一緒に決める。足しても既存のコードは壊れない |
| A-13 | `@param` に数値の ID を直接指定するキー | 保留（2026-10-06。プラグインの出力を作るとき、第 2 期） | 数値の ID は文字列の ID から決まる（S-104、§11.7）。既存のプラグインを Onsa に移すとき、保存済みのプロジェクトとプリセットとの互換のために、元の製品の数値の ID に合わせたいことがある。ハッシュでは任意の数値を選べない。無い場合は、移す前の製品の数値と一致する文字列を探すことになり、現実的でない。足すなら、`@param` の閉じたキーの一覧（§11.7）と凍結（§15.4）の扱い、文字列の ID との関係（両方を書くか、数値が優先か）を一緒に決める。足しても既存のコードは壊れない |
| A-14 | `Char` と整数の間の変換（コードポイントの値を取る、値から `Char` を作る） | 保留（2026-10-06、点検 C-88。第 2 期、`Str` の実装のとき） | S-98 で組込みのメソッドを閉じた結果、`Char` にはメソッドも `as` の変換も無い（§3.3 の変換の表は数の型だけ）。字句の処理（数字の文字から値を作る、`'a'` からの差で添字を作る）で要る。無い場合は、`match` で文字ごとに値を並べるしかない。値から `Char` を作る向きは、サロゲートと範囲外の値があるので `Option` を返す形になる。名前と形は、`Str` の反復（`chars`）と一緒に、実例が出てから決める |
| A-04 | 浮動小数のメソッド形（`x.sqrt()`、`floor`、`abs`、`min`、`max`、`is_nan` など） | 不採用（2026-10-03） | 仕様に無いまま実装が足していた（R-96）。`std.math` の関数（S-09）と同じ計算に二つの呼び方ができ、一意性の原則（P2、§6.2「同じ関数に二つの呼び方は無い」）に反する。書いたら E0413 にし、`std.math` の関数の形を修正候補に示す。整数の `abs` / `min` / `max` のメソッドも同じ理由で外した（R-126、S-98）。NaN と有限の判定は `std.math` の `is_nan` / `is_finite` で書く |
