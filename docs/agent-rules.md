# 担当の共通の規則

`.claude/agents/` の 5 つの担当（`onsa-test`、`onsa-impl`、`onsa-break`、`onsa-advisor`、`onsa-gap`）が共通に従う規則である。各担当の定義は、役割に固有の規則と、この文書への参照を持つ。定義とこの文書が食い違えば、定義が優先する。

日付の付いた注意（機械の状態、既知の落ちる入力）は、この文書だけに書く。直ったら親が改める。章の見出しの括弧は、対象の役割である（t はテスト、i は実装、b は壊す側）。

## 1. リポジトリとシェル（全員）

- リポジトリは `/Users/centrevillage/projects/onsalang`、ブランチは `dev`。コミットと push はしない（親が作業 ID ごとにコミットする）。助言と空白の下書きの担当は、リポジトリのファイルを編集しない。
- CI は無く、検査は手元で回す。
- Bash の `cd` は持続しないことがあるので、絶対パスを使う。macOS なので `timeout` は無い。止まらない恐れのある実験は、Python の `subprocess.run(..., timeout=…)` で包む。
- `git stash` を使わない。stash は主のツリーと全ての作業ツリーで共有され、親や他の担当の未コミットの変更を巻き込む。確かめのために差分を退けたいときは、スクラッチのディレクトリに写して試す。
- Python のスクリプトをヒアドキュメントで渡すときは、必ず `<<'EOF'` と引用符で囲み、引数は `sys.argv` で渡す。囲まないと、本文のバッククォートや `$` がシェルで展開され、`a > b` のような文がファイルを作りうる（2026-10-09 に親が一度起こした）。

## 2. 作業ツリー（t、i）

壊す側（b）は自分の作業ツリーを持たず、親が示した作業ツリー（実装の担当のもの）を読むだけで、そこでは `git merge` も `git stash` もしない（読むことと、`cargo build` と絞ったテストだけ）。

- git の別の作業ツリー（worktree）で動くときは、始めに `git log --oneline -1` で親が指定したコミットかを確かめる。違えば、作業ツリーの中で `git merge --ff-only dev` をする（`git reset --hard` は許可の判定に拒まれることがある）。
- 作業の途中で主のツリー（`dev`）が進み、親が取り込むよう指示したときは、自分の変更を WIP のコミットにしてから、作業ツリーの中で `git merge dev` をし、衝突を解く。WIP のコミットは、親が成果を写すときに `git diff dev` で読むので、そのまま残してよい。
- 主のリポジトリには書かない。成果は作業ツリーに置いたままにし、親が写す。

## 3. 機械を落とさない（全員）

- この機械（macOS）では、SIGABRT・SIGSEGV・SIGILL・SIGTRAP などで終わるプロセスが、利用者の画面にクラッシュの報告のダイアログを出す（2026-10-07 に大量に出た）。
  - テスト・自己テスト・ファズで意図的に落とす形をまねるときは、SIGKILL か終了コードを使う。
  - sanitizer は、abort や trap でなく終了コードで止まる設定にする。
  - 作ってしまったら報告に書く。
- 既知の落ちる入力（2026-10-08）: `tests/review-phase1/types/` の `constcyc.onsa`・`constcyc2.onsa`・`constcyc3.onsa`・`rec.onsa`・`rec2.onsa` は、`onsa interface`（と、それを通る経路）でコンパイラのスタックが溢れ、SIGABRT で終わる（W4-05 で直す）。
  - `tests/review-phase1/` や `tests/fuzz/` を一括で道具にかけるときは、`interface` や `build` を使わないか、これらを除く。
  - 新しい道具を一括で回す前に、少数のファイルで終わり方（終了コードが 0・1・2・101 のどれか）を確かめる。
- インタプリタの再帰（W2-04 で直した）: `onsa test` とコンパイル時の評価は、呼び出しの深さの上限 128（仕様 §12.5、S-222）で panic するので、深い再帰を走らせても落ちない。
  - ただし、`const` が `const` を読む鎖は呼び出しに数えず、スタックの安全網（内部エラー、終了コード 101）に頼る（W9-03 まで）。
  - 長い鎖を試すときは、浅い鎖で終わり方を確かめてから増やし、2000 個を超えない。
- 深い入れ子: `cargo test` のスレッドは既定のスタック（2 MiB）が小さい。debug のフロントエンドは、入れ子 1 段に約 64 KB を使う（32 段で SIGABRT になった。W2-04/i の測定）。
  - ソースを構文解析・検査・降下するテストで、入れ子や二項演算子の連鎖を 20 段より深くするときは、大きなスタックのスレッド（`onsa_diag::stack`）で走らせる。リポジトリの全てのファイルを読むテスト（`cst_tests` など）も同じ。
  - コマンドで試す入力も、20 段を超えるものは既にある事例の流儀に倣う。上限（§2.5 の 256）を超える入力は作らない。
- 他の言語の処理系（2026-10-08、2026-10-09）:
  - 極端な入力（深いテンプレートや型の鎖、数千段の入れ子）を渡さない。Apple clang 21 に深さ 2000 の C++ のテンプレートの鎖を渡したところ、フロントエンドが SIGILL で落ちた。上限の挙動は、文書を出典付きで引くか、上限のすぐ外の小さな入力（数十段）で確かめる。rustc などの止まりにくい実験は、時間で打ち切る。
  - 実行時に trap する入力を走らせない（Swift の始点が終点より大きい範囲など）。挙動は文書やソースを出典付きで引く。
  - `swift test` を回さない。この機械の Command Line Tools には XCTest も Swift Testing も無く、補助（swiftpm-testing-helper）が SIGTRAP で落ちた。

## 4. 検査の回し方（全員。2026-10-08、利用者の指定。計画 §8.5 の「検査の回し方」）

利用者は、検証が機械の寿命を縮め、時間を延ばすことを気にしている。回す回数と並列の数を抑える。

| 役割 | 作業の途中 | 報告の前 | 回さないもの |
|---|---|---|---|
| t | 書いた事例だけを絞って確かめる（下の「事例を絞って走らせる」、データのファイルの自己テスト `cargo test -p onsa_tests --test foreign_forms`、変えたファイルへの `onsa check` と `onsa fmt --check`）。載せる項目は仮に実装待ちの一覧に入れて回し、回した後は元に戻す | gate は回さない（親が成果を写した後と、実装の担当の報告の前に回る）。絞った確かめの結果を報告に付ける | fuzz（`tools/fuzz.py`）、fmt の性質（`tools/fmt_props.py`）、C の検査とテストベクトル（`onsa_cases --c`、`--vectors`）は、作業がその道具か生成した C を扱うときだけ |
| i | 変えた所に関わるテストだけを絞って回す（`cargo test -p <crate> <テストの名前>`、変えたファイルへの `onsa check`）。広く確かめたいときは `tools/gate.sh --quick` | gate の全体を一度、`tools/gate.sh --work <作業 ID>`。要約を報告に付ける（直しの往復でも、直すたびには回さない） | fuzz（`tools/fuzz.py`）、fmt の性質（`tools/fmt_props.py`）、C の検査とテストベクトル（`onsa_cases --c`、`--vectors`）は、作業がその道具か生成した C を扱うときだけ |
| b | 個々の入力へのコマンドと、絞ったテスト | — | gate（実装の担当が回し、親が要約を読む）。fuzz・fmt の性質・C の検査は、作業票がそれを対象にするときだけ |
| advisor、gap | 個々の入力へのコマンドだけ | — | gate、`cargo test --workspace`、fuzz、fmt の性質、C の検査。自分でビルドしない（親が渡すバイナリを使う） |

- gate は機械で一度に一つだけ走り、他の gate の後ろで待つことがある。Bash の timeout は 600000 にし、待っている間に打ち切られたら回し直す。
- gate の出力の FAIL の行は、実装待ちの項目の中身のことがある。判定は最後の `gate: PASS` / `gate: FAIL` の行で見る。
- 事例を絞って走らせる（2026-10-10）: 事例の器 `onsa_cases --run <根>` の引数は `tests/` を持つ根のディレクトリで、ファイルは受けない。一つの事例だけを走らせるには、作業用のディレクトリ（scratchpad の自分の下）に `tests/<元の経路>` の形で事例と `.fixK` を写し、そのディレクトリを根に渡す。結果は JSON の `cases[].problems`。

  - Python の一意一致置換で編集する。
  - 表を編集したら列の数を確かめる（セルの中の `||` は `\|\|`）。

## 7. 推奨の基準（利用者の方針。gap、advisor）

推奨と独立の判断は、次の方針で比べる。親が作業票で足す方針があれば、それも使う。

1. 規範は仕様。仕様は自己完結の規則で書き、他言語への言及は参考にとどめる。推奨の理由に「Rust（や他の言語）にあるから」を使わない。
2. 他言語の扱いは、手元で動かしたものだけを書き、版を添える。rustc は確かめには使えるが、推奨の理由にしない。確かめていないものは「未確認」と書く。規格や文書を引くときは出典（節、URL）を付ける。
3. Onsa の主な書き手は LLM と想定する。人なら摩擦を嫌って緩い案に傾く場面でも、厳格な案を選ぶ。ただし、LLM のコーパスに少ない書き方であることだけを理由に、言語の規則の一貫性を崩さない（コーパスとの摩擦は代償として示すが、決め手にしない）。
4. 既存言語の間で解釈が分かれる書き方は、コンパイルエラーにする（修正候補は読みごとに並べる）。どう読んでも意味が一つの余分（`return`、`-> ()`、冗長な括弧）は fmt で揃える。書き手の誤解を示す書き方や、読み手に別の読み方を与える書き方はエラーにし、note で正しい規則を示す。
5. 将来開くかもしれない機能でも、今は禁止しておく方を選ぶ（制限を外す変更は後で壊れない）。ただし、境界とは別の条件を足して「特殊な規則が増える」案は不可。推奨では、後で緩められる制限か、規則の数が増えるかを比べて示す。
6. 構造の変更は今のうちに行う。修正コストを理由に、理想の構造より軽い案を推さない（推すなら、コスト以外の利点を示す）。
7. 推奨は、今後の追加（第 2 期の `Str`・`Map` などの API、JS / WASM のバックエンド）でどちらが管理しやすいかを比べて出す。今の量だけで比べない。制限を「今は当たる所が少ない」で小さく見積もらない。
8. 実務の構成を塞がない（F32 主体で精度の要る所だけ F64、など）。検査は代わりの指標ではなく、実際の影響を見る。
9. 利用者は表面の非一貫性に敏感（「`0 - x` が通って `-x` が誤り」）。区別するなら根拠を示す。名前の付いた概念を、能力の組み合わせより好む。
10. 基本仕様には、言語の規則と、利用者・CI・修復ループが依存する出力（診断、終了コード、interface）を書く。fmt の正規形や人が見る表示の約束は `docs/onsa-tools.md` に書く。人が読まない規範の表は、データのファイルに置く。基本仕様に細かすぎる記述を入れない。
11. 前提を問い直す: 穴を埋める前に、仕様の既存の規則そのものが妥当かを確かめる。同一性は構造で決め、名前は表示に使う。
12. 必要と分かっていて、一緒に入れてもコストがほとんど変わらないものは、後回しにせず同じ回に入れる。必要が確かめられていないものは、`docs/api-candidates.md` の候補にとどめる。
13. 段の原則（計画 D-15）: 各処理は一度だけ行い、後の段は前の段が出力した構造を受け取る。
14. 表現（IR の構造、表の欄）は先に入れ、実装していない所は黙って通さず E0200 で知らせる（R-81）。
15. 仕様の空白は、基本は保守的に実装して SPEC-GAP の印を付けて報告する。決めないと空白が連鎖するものだけ止める。
16. ある問題を避けるのに、無関係な名前や構造を変えるしかない設計は推さない。
17. 一度に報告する誤りは、一つの編集の単位に一つ。誤りをまとめる案は、既にある原則の外に出ないかを確かめる。修正候補の約束は、当てた前後の状態だけで判定できる形にする（検証に因果を持ち込まない）。
18. 約束（仕様に書く保証）は、それに頼る使い手（CI、修復ループ、テスト）を示せるものだけにする。
19. 関係する既決の項目の理由（利用者が述べた理由）を読み、新しい項目に当てたときにどの案になるかを確かめてから推奨する。既決の部分を論点に戻さない。
20. 方針の字面を当てるだけでなく、効く場面が実際にあるかを確かめる（読みごとに候補を並べる方針でも、その形を正しい形として書く言語が無ければ読みは割れていない）。推奨では、案ごとに、形ごとの出力の違い・増える規則・実装の量・既決の出力への影響・効く書き手を並べる。修正の量の割に利益が薄い案は推さない（2026-10-09、S-351）。
21. 名前は、略語であることが明らかなら短いものを選ぶ（`@mem`、`@repr`、`@param`）。将来の選択肢が増えそうなものは、分類の属性に値を渡す形にする（`@mem(bulk)`、`@repr(c)`）。属性の名前には主語（何に関わるか）を持たせ、利点（fast、opt）でなく、変わる意味の分類で名付ける（`@fp(relaxed)`、S-57）。
22. 印は、キーワード（`fb y`）より、記号やプレースホルダとして読める簡潔なものを好む（`^y`、S-44）。既にある印の意味を広げて使う形も好む（`if~`・`match~`、S-110）。既に付いている印に別の印を重ねさせない（R-94）。既定の名前は安全な意味に当てる（`Num` は符号なしを含まず、符号なしも受けるときだけ `AnyNum`）。推奨では、ある組み合わせが頻出しないかを用途ごとに見積もって示す。
23. キーワードを必要以上に増やさない。将来の機能の形は、既存のキーワードの入れ子や組み合わせで表せるかを先に検討する（テストのまとまりは `test` の入れ子、S-275）。足すなら一語で、命令でなく条件に読める語にする（`reset_if`）。後から足すと既存のプログラムを壊すもの（キーワード、prelude の名前、flow の組込み名）は、実装しない機能でも予約と意味を先に決める。
24. 今は実装しない機能でも、そのときに構文や意味が破綻しない形を選ぶ。注釈（`at`）と、方法の選択を伴う処理（補間）を同じ構文に混ぜない（C-40）。組込みの型で済む今だけでなく、将来その構文に使える型を広げたときに書けなくなる形が無いかを確かめる（`b + 1` が必ず作れると仮定しない、S-257）。
25. 処理系の資源の上限（呼び出しの深さなど）は、仕様に固定の数を書き、同じ性質のもので一つの数を共有する。値は一般的なコンパイラの上限を超えないものにし、主な処理系の既定値を手元で確かめて並べる。迷えば小さい値を選ぶ（後で上げても既存のプログラムを壊さない。S-222）。
26. 書き方を一つにする原則（P2）に触れそうな機能は、残す前に、具体的な利点（代わりの手段が無い用途）と、害になる使い方を示す（R-105）。
27. 修正候補の規則を推すときは、複数の誤りが並ぶ形で一つずつ当てたときに誤りの無いコードへ収束するかと、どの候補でも安全にできない形を先に示す。安全にできなければ、情報を失っても壊さない候補（削除）に落とす（S-302）。
28. 規則を決めるときは、同じ性質を持つ言語（改行で文が終わり `return` を省ける JS、Ruby、Go、Kotlin、Swift、Scala 3 など）が同じ問題をどう扱うかを調べ、手元で動かせるものは動かす（C-12）。
29. 列挙子は整数との変換（保存したデータ、C の API）で順に意味を持つのが慣習で、順を使わない設計は `match` を増やす（C-22）。性質の種類が違うものは別の概念として定めるが、利用側が区別を意識する利益が薄ければ記法は分けない（C-28）。
30. 組込みの API は仕様の閉じた一覧だけを実装する。必要と分かったものは拒否で終わらせず、`docs/api-candidates.md` に候補として挙げる（実例のコードと、無い場合の書き方を添える）。
31. 少数の言語だけが持つ特殊な規則（MATLAB や Julia の、空白で行ベクトルの要素を区切る書き方など）に合わせるかは、その言語を使う人の数ではなく、合わせるための実装の量と、他の規則への副作用（特殊な規則が増えるか）で決める。厳しい方（誤りにする）から後で緩めても、既存のプログラムは壊れない。迷えば厳しい方を採り、実装が単純な方を選ぶ（2026-10-10、S-398・S-400）。
