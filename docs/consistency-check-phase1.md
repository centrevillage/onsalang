## 1. 手順

1. **機械的な照合（親がスクリプトで）。** 安く拾えるものを先に拾う。
   - 各 S 番号が、変更点（§4）、計画の S の表（§2）、仕様の該当節に揃っているか。
   - レビューの §8 の各行と、本文の「決定」の行が揃っているか。
   - 仕様の中の `§x.y` の参照が、実在する節を指しているか。
   - 仕様に古い書き方が残っていないか（`Sig[` / `Ctl[` / `Init[`、`@derive`、`prev(y, 0.0)`、例の `onsa_` の prefix、`is_empty`、`Ctl` 入力などの古い語）。
   - `tools/check_spec_examples.py` の実装待ちのブロックを、S 番号ごとに分類する（Q-08 の明示の一覧の元）。
2. **主題ごとの点検（エージェントを並べる、読み取り専用）。** 文書ではなく主題で分ける。
   - (a) 構文・字句・fmt（S-44、S-48、S-56、S-58、S-62、S-89、S-100、S-102 の `at` など）
   - (b) 型・trait・数・診断コード（S-46、S-69〜S-74、S-84、S-91、S-98、S-103、S-106）
   - (c) flow・クロック・状態（S-29〜S-33、S-43、S-86、S-88、S-101、S-102）
   - (d) C の API・ビルド・マニフェスト・ターゲット（S-52〜S-54、S-65、S-92〜S-96、S-99、S-104、S-105）
   - (e) 決定から作業への対応（各決定の「実装は第 N 段」とレビュー §7 の段、計画 §4 の T 番号の作業が今の決定と合うか、古くなった作業）

   指摘は次の形で返させる: 種類（矛盾 / 抜け / 文書のずれ / 古い記述 / 作業に落ちていない）、箇所（`ファイル:行`）、根拠の引用、関係する決定、重大度、案。
3. **親が確かめて分ける（Q-11）。** 指摘ごとに引用の行を読み、重なりを除く。
   - 判断の要らない直し（誤記、古い例、参照のずれ）: 一覧を利用者に見せてから、まとめて直す。
   - 判断が要るもの（決定どうしの衝突、新しい空白）: 項目ごとに論点・案・推奨を出し、利用者の判断を待つ。
4. **記録。** 指摘と決定は、この文書の §2 と §3 に置く。決定が仕様を変えるときは、これまでと同じく S 番号を振り、変更点・計画・仕様を揃える。

点検が終わったら、落とし込みの段で、各段の作業を計画 §8.1 の作業票の形に切り出す。Q-14 の判断の置き場所の表も、その段でまとめる。
