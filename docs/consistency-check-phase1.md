#### 2.2.2 構文・字句・fmt

**C-02 P2 の「余分な情報」と、冗長な印を E0020 にする決定の線引き**（中、A-03）
- 論点: P2（仕様:27）は「意味を変えない余分な情報…は受理し、`onsa fmt` が取り除いて唯一の表記に揃える」。一方、定義済みの名前への `^`（仕様:912）、フィールドの `pub`（:1456）、`priv use`（:1458）、`@mem(fast)`（:1161）は、意味を変えない冗長な印なのに E0020。E0020 の定義（:1969、計画:674）は「既存言語の書き方」で、これらを含まない。新しい冗長な形が出るたびに、どちらに入れるかの基準が無い。
- 案: (a) P2 に線引きの基準を書く。(b) P2 に E0020 の閉じた一覧を置き、§18.2 の fmt の一覧と対にする。(c) (a) の基準を P2 に一文で書き、E0020 の全体の一覧は R-87 (4) の規則の表に置いて §18.1 から参照する。
- 推奨: (c)。基準は利用者の整理（R-78、R-101）から書ける: 「書き手が既定の意味や記号の意味を誤解していることを示しうる印・修飾は、値が変わらなくても E0020（修正候補は外すこと）。誤解を示さない表記の揺れは fmt が揃える」。基準があれば新しい形の振り分けが決まり、一覧を二つの文書に持たずに済む（保守）。E0020 の定義も「既存言語・旧版の書き方と、誤解を示す冗長な印」に広げる。

**C-03 fmt が外す括弧の範囲**（中、A-04）
- 論点: P2 は「冗長な括弧」を外すとするが、§3.1（仕様:202）が外すのは強い群を囲む括弧だけで、同じ群の中の括弧は残す（S-45）。`(x)`、`((e))`、`let y = (a + b)`、`if (c) {` の扱いが無い。
- 案: (a) P2 の文言を §3.1 の範囲に狭め、それ以外は書き手のまとまりとして残す。(b) (a) に加え、名前・リテラル・後置式・括弧を囲む括弧と、文・引数・見出しの式の全体を囲む括弧も fmt の一覧に入れる（S-08 の struct リテラルを含む見出しは残す）。
- 推奨: (b)。S-45 の「同じ群は残す」は覆さない。そのうえで、まとまりを表さない括弧（C の習慣の `if (c) {` など）を一つに揃える（P2、P10）。

**C-04 `^名前` を書ける範囲と結合**（中、A-05、FC-05）
- 論点: 仕様:912 は「`^名前` を書けるのは、遅延の組込みの第 1 引数の中だけ」、:915 は「遅延を内部に持つ利用者の flow も `^` の参照は受け取れない」。`prev~(lp~(^y))`（遅延の第 1 引数の中の、利用者の flow の引数）が書けるかが二通りに読める。`^y.l` / `^ys[i]` の結合、§3.1 の結合の強さの並び（:204）に `^` と `!(` が無い。
- 案: (a) 第 1 引数の式の中ならどこでもよいが、利用者の flow の引数の中は不可（:915 のとおり。E0801）。(b) 利用者の flow の引数の中も許す（インスタンスを保存の段で評価する）。(c) 第 1 引数を `^名前` とその経路そのものに限る。
- 推奨: (a)。`prev~(lp~(^y))` と `lp~(prev~(^y))` は同じ帰還をほぼ同じに表すので、両方を許すと書き方が二つになる（P2）。(a) なら、インスタンスは常に普通の段で評価され、保存の段で評価するのは遅延の値の式だけになる（降下と参照評価器が単純）。主題 (c) のエージェントは (b) を推したが、上の理由で (a) を推す。付随して次を書く: `^` は名前に付き、後置はその参照に掛かる（`^y.l` は `y` の過去の値のフィールド）。見えている名前（上の `let`、入力、定数）への `^` は E0020（修正候補は外すこと）。§3.1 の結合の強さに `!(` と `^名前` を足す。

**C-05 E0801 の修正候補が、遅延の外の前方参照で意味を変える**（中、A-06）
- 論点: 仕様:912「印の無い前方参照は E0801（修正候補は `^` の挿入）、遅延の第 1 引数の外の `^名前` も E0801（修正候補は `prev~(^名前)`）」。`let a = b * 2.0`（`b` は下で定義）に候補を当てると `^b` で再び E0801、その候補で `prev~(^b)` になり、1 サンプルの遅延が黙って入る。
- 案: (a) `^` の挿入は、参照が遅延の第 1 引数の中にあるときだけ出す。外では候補を出さず、note で「`let` を上へ移す」「帰還なら `prev~(^名前)`」を示す。(b) 外では、閉路が無ければ `let` を上へ移す候補を出す。(c) 外では `prev~(^名前)` を直接の候補にする。
- 推奨: (a)。修正候補はそのまま当てられる前提（P8）なので、遅延を足す（意味を変える）候補を出さない（R-72 と同じ考え）。(b) は閉路の判定が要るので後で足せる。

**C-06 `as` / `at` の連鎖**（中、A-07）
- 論点: 仕様:204「`as` と `at` > 二項演算子」、:931「結合の強さは `as` と同じ」。`x as F64 at sample`、`p at sample as F64`、`x as I64 as F64` を書けるかが無い。
- 案: (a) 連鎖は不可。二つ目の `as` / `at` の被演算子には括弧が要る（E0011 を広げる）。(b) 左から右への連鎖を認める。
- 推奨: (a)。(b) だと fmt が `(x as F64) at sample` の括弧を外さないので書き方が二つ残る（P2）。前置演算子の重ね（E0012）と同じ扱いで、文法も `Cast = Prefix [ ("as" Type | "at" Clock) ]` で済む。

**C-07 flow の出力の `at`**（中、A-08、FC-20）
- 論点: 仕様:932「flow の入力には `at` が必須（E0810）」で、出力の記述が無い。:1064「v0.2 では、flow の出力は `sample` のクロックだけ」。
- 案: (a) 出力の `at` も必須（無ければ E0810）。この版で `sample` 以外の出力も E0810（note で §19.1）。(b) 出力の `at` は省略でき、既定は `sample`。
- 推奨: (a)。書き方が一つで（P2）、`block` の出力を入れるときに既定の意味が隠れた選択にならない。`block` の出力は §19 の未決定なので E0200 ではなく E0810。計画 §5 の E0810 に出力を足す。

**C-08 `x: Sig[F32]` の E0020 と、利用者の型 `Sig`**（中、A-09）
- 論点: 仕様:932 はレートを型の形で書くと E0020。S-102 で `Sig` `Ctl` `Init` を prelude から外したので、利用者は `struct Sig[T]` を宣言でき、そのとき `fn f(x: Sig[F32])` は正しい。名前を見ないと決まらず、「E00xx は字句・構文」（:1948）と fmt の「構文の診断（E00xx）」（:2002）にも合わない。
- 案: (a) `Sig` / `Ctl` / `Init` が解決できないときだけ E0020（名前の段で判定）。§18.1 に「E0020 は検出できる段で報告する」と書き、§18.2 の「構文の診断（E00xx）」を S-56 の明示の印の言い方に揃える。(b) 三つの名前を予約し、宣言を E0304 にして、構文の段に留める。
- 推奨: (a)。S-102 で普通の名前に戻したものを、診断の便宜のために利用者から取り上げない。R-87 (4) の規則の表は規則ごとに段を持てる。

**C-09 属性の後の改行**（中、A-11）
- 論点: §2.5（仕様:145）の継続の規則を字面どおりに読むと、`@repr(c)`（改行）`pub struct P {…}` が誤りになる。今の実装と `tests/spec/examples/line_count.onsa:5` は属性を独立の行に書く。
- 案: (a) 行末が属性なら継続する。(b) 属性は対象と同じ行に書く（E0003）。
- 推奨: (a)。属性で項目や文が終わることは無いので、S-47 の理由（継続を字面で決める）がそのまま当てはまる。置き方の正規形は C-10 で決める。

**C-10 fmt の正規形が仕様に無い**（中、A-12）
- 論点: S-66 は fmt の正規形を基本仕様に書くとした（`onsa-tools.md`:7）が、§18.2（仕様:1989〜2009）は一部だけで、字下げ 2、並びの 3 形、末尾の `,`、項目の間の空行、`uses {Alloc}` などの空白は、計画（:469、:481）と IR（F-1〜F-5 は「仕様へ」のまま）にだけある。属性の置き場所、`@mem(bulk) let` が `=` の整列の列に入るか（§17.4 の echo は揃えていない）、コメントだけの行で整列の列が切れるか、`^` / `~(` / `at` の空白が決まっていない。
- 案: (a) 実装の規則（T1-9、M1 の注記、IR の F-1〜F-5）を §18.2 に閉じた一覧で書き、上の未決を決める。(b) `onsa-tools.md` に書く。(c) 実装と golden に任せる。
- 推奨: (a)。(b) は S-66 の分け方に、(c) は P2 の「唯一の表記」に反する。細目の推奨: 項目と入力の属性は独立の行、`@mem(bulk) let` は同じ行に書いて整列の列を切る（今の例の形で、印の付いた行が目立つ、P10）、コメントだけの行は列を切らない。

**C-11 `~` / `!` / `^` の前後の空白**（中、A-14）
- 論点: 仕様:155「`~` は名前の直後に空白を空けずに」、:163「`^` は名前の直前に空白を空けずに」とあるが、違反のコードが無い。`saw ~(f0)` は前置の `~` と読まれ、§18.1 の表（:1975）で修正候補が `saw !(f0)` になる（行き止まり）。
- 案: (a) S-89 (4) を広げ、名前と `~` / `!` の間、`^` と名前の間の空白を E0020（修正候補は空白を除く）にする。§18.1 の `~x` の行は「直前が被演算子でない前置の位置」に限る。(b) E0002 にして候補を出さない。
- 推奨: (a)。既に決めた S-89 (4)（`f (x)`）と同じ扱いで、修復のループ（P8）に効く。

**C-12 §2.5 の残りの空白**（低、A-21）
- 論点: 継続の間のコメント行・空行、`handle {…}`（改行）`with h` の `with` の位置、行頭の二項演算子（`^b` が新しい式になり E0801 / E0821 という分かりにくい診断になる）、struct / enum の宣言の本体と `use a.{…}` / `uses {…}` の中の改行が決まっていない（仕様:145、:146）。
- 推奨: 継続はトークンで判定し、コメントと空行は読み飛ばす。`with` は `}` と同じ行（E0003）。行頭の二項演算子は今のとおり継続しないが、note で行末に移すよう示す。宣言の本体と `{…}` の並びは「`,` で区切る並び」として改行を空白にする。

**C-13 flow の本体で使える式の一覧**（低、A-22、IR の FL-4）
- 論点: 仕様:911 の「使える式」に `as`、`at`、`^`、メソッドの呼び出し、リテラルが無く、`handle`、`unsafe`、`inout` / `move` の引数はどちらの並びにも無い。
- 案: (a) 使える式を閉じた一覧にし、それ以外は E0806。(b) 書けない式を閉じた一覧にする。
- 推奨: (a)。新しい構文は既定で flow の中では拒否される（PI:117「受理する側に倒さず、拒否する」と同じ方針）。

**C-14 指数の `e+3`**（低、A-23）
- 論点: 仕様:134 に指数の `+` を書けるかが無い。
- 案: (a) 受理し、fmt が `+` を外す。(b) E0020。
- 推奨: (a)。どの言語でも同じ値に読まれる綴りの揺れで、S-62 の規則に当たる。

**C-119 ブロックの途中の文の値を黙って捨てる**（中、C-12 の議論で追加）
- 論点: 仕様に、型が `()` でない式を文に書いたときの規則が無い。今の実装で、`a` の次の行を `- b` で始めた関数が `a - b` ではなく `-b` を返し、`onsa check` もテストも通る（`a` の行で文が終わり、値が捨てられる）。呼び出しの `Result` も黙って捨てられる。
- 案: (a) 型が `()` でない文は誤り。捨てるときは `let _ = e`。(b) 文に書けるのは呼び出しだけ（Go）。(c) 今のまま。
- 推奨: (a)。値を捨てるのは注意の要る所なので印を付ける（P10）。(b) は呼び出しの返り値を黙って捨てる。Zig は (a) に近い（void でない値を全て使わせ、`_ = e` で捨てる）。`for` / `while` の本体と `()` の関数の最後の式は、既に E0401。

**C-120 発散の後の到達しない文**（中、C-12 の議論で追加）
- 論点: `fn f(inout n: I32) { return` の次の行に `n = 5` を書くと、`return` は行末で終わり、次の行は黙って実行されない（今の実装で確かめた）。JS と Ruby も同じく黙って抜ける。仕様に到達しない文の規則が無い。
- 案: (a) 発散するもの（`return`、`break`、`continue`、`panic`、それで終わるブロックなど）の後の同じブロックの文を誤りにする。修正候補は消す形と、つないだ形。(b) 今のまま。
- 推奨: (a)。消し忘れたコードも捕まえる。Java も到達しない文をコンパイルの誤りにする（JLS §14.22）。構造だけで判定し、条件の値は見ない。

**C-121 使われない束縛**（中、C-12 の議論で追加）
- 論点: flow で `let y = x` の次の行を `-prev~(x)` で始めると、`y` が使われず、`-prev~(x)` が黙って出力になる。C-119 は文の値の規則なので、名前に束縛した値は捕まえられない。fn の `let r = f(x)` も、名前を付ければ黙って捨てられる抜け道になる。
- 案: (a) fn と flow の両方で、使われないローカルの束縛を誤りにする（flow は出力と `let _` からの到達で判定）。(b) flow だけ。(c) 今は入れない。
- 推奨: (a)。C-119 と同じ根で、fn と flow の規則が揃う。代償は試行の途中の摩擦（Go と Zig も誤りにする。Zig は開発中だけ警告にする提案を採らなかった）と、probe のためだけに名前を付けた信号が書けなくなること。後者は必要になったら印を検討する。

#### 2.2.3 型・trait・数・診断コード

**C-15 標準 trait が prelude に無く、仕様の例が自分の規則で E0302 になる**（高、B1）
- 論点: 仕様:1464「暗黙の prelude は、`Option Result Some None Ok Err panic Alloc` と組込み型だけ」「他の標準の効果と std の項目は `use` で取り込む」。一方、例は `use` 無しで標準 trait を使う（:388 `clamp[T: PartialOrd]`、:608、:1329 `impl Drop for Conv`、:1692）。prelude に入れると、今度は §6.3 の例 `pub trait Show {`（:557）が、prelude と同じ名前で E0304（:442）になる。
- 案: (a) §6.3 の標準 trait を全て prelude に入れ（演算子 trait、数の trait、`Copy` / `Dup` を含む）、§6.3 の例の trait を別の名前（`Describe` など）に改める。(b) 境界と derive でよく使う trait だけを prelude に入れ、演算子 trait は `use` で取り込む。(c) prelude は今のままで、全ての例に `use` を足す。
- 推奨: (a)。規則が「§6.3 の標準 trait は全て prelude」の一行で済み、一覧を二つ持たない（保守）。境界と derive は日常の表記で、ファイルごとに `use` を書かせるのは P10 のノイズ。S-79 で prelude の名前は隠せないので、予約される名前の集合が固定され、解決の優先順位も要らない。代償は予約される名前が増えること（`Not`、`Shl` など）。

**C-16 数の trait は利用者が実装できるのに、`std.math` と `vdelay` はプリミティブ**（高、B2）
- 論点: 仕様:579「利用者の型も `impl AnyNum for Q15 {…}` と `impl Num for Q15 {}` のように実装できる」、S-46 は Q15 が `sum` / `abs` / `min` / `max` を使えるように `ONE` を外した。一方、:1268 で `abs` / `min` / `max` は各変換先のプリミティブに対応付け、:566「重複実装、特殊化は無い」。`abs(q)`（`q: Q15`）は型検査を通るが実装が無い。浮動小数の NaN の伝播と符号付きゼロ（:1257）は `PartialOrd` だけの総称の本体では表せない。利用者が `Float` を実装できるなら、`exp[T: Float]` と `vdelay`（`T: Float`、:947）も同じ。
- 案: (a) `Float` は組込み型だけが実装できる。`abs` / `min` / `max` は std に Onsa の本体を持ち、組込み型ではその本体をプリミティブに置き換える（`target` 宣言が既定の本体を持つ形を std の特権に足す）。(b) `std.math` の関数と `vdelay` は組込み型だけを受ける条件を置き、S-46 の理由のうち「`abs` / `min` / `max` を使える」を取り下げる。(c) 第 2 期まで延ばす。
- 推奨: (a)。S-46 / S-84 の意図と、呼び方が一つ（P2）を保ち、浮動小数の意味も変えない。std は既に特権を持つ（計画:351）ので、利用者の構文は増えない。R-79 で std の宣言を書く段の前提なので今決める。持ち越しの表（全体計画 §5）にも載せる。

**C-17 整数の `abs(MIN)`**（中、B4）
- 論点: `abs` は `Num` で符号付き整数も受ける（仕様:1268）が、`abs(I32.MIN)` の意味が無い（§3.4 の表 :249〜260 にも無い）。変換先で折り返し・panic・飽和が分かれうる。
- 案: (a) panic（`-a` と同じ）。(b) 飽和。(c) 折り返し。
- 推奨: (a)。整数の溢れはビルドの種類によらず panic する（:245）規則と同じで、例外を作らない。§3.4 と §9.2 に書く。

**C-18 定数の評価の溢れ・panic のコード**（中、B5）
- 論点: 仕様:399「溢れとゼロ除算は、その式の位置でエラーになる」にコードが無い。`const` の初期化式と `@param` の値（:1081）の評価の panic も同じ。
- 案: (a) 新しいコードを一つ（E04xx の空き。「コンパイル時の評価が panic した」）にし、定数式・`const` の初期化式・`@param` の値・C-34 の定数のクロックの式で共通に使う。(b) 定数式は E0417 に含め、初期化式は別のコード。
- 推奨: (a)。どの場合も直し方は「式か値を直す」の一つで、S-103 の原則でまとまる。

**C-19 定数式の違反のコード**（中、B6）
- 論点: 仕様:399 は定数式でないものを E0417、:951 は遅延線の長さを E0808、:994 の `par` の回数はコードが無い。S-50 は「遅延線の長さと `par` の回数も同じ規則」とした。
- 案: (a) 定数式でないものは位置によらず E0417。E0808 には `vdelay` の範囲（`MAX >= 1`、`MAX <= 2^24`）だけを残す。(b) flow の中は E0808 のまま、`par` の回数も E0808。
- 推奨: (a)。S-50 で同じ規則とし、直し方も同じ（S-103）。E0808 の割り当てを狭める変更になる。

**C-20 属性の診断コードの境界**（中、B8、d20、A-19）
- 論点: 仕様:622「一覧に無い属性と、付けられない種類の項目に付けた属性は E0005。属性の値の誤りは、各属性のコードで報告する（`@param` は E0809、`@mem` は E0818）」。`fn` に付けた `@param` や struct に付けた `@mem` が E0005 と各属性のコードの両方に読める。`@fp(fast)` と `@repr(rust)` の値の誤りにはコードが無い。旧形の `@derive(...)` は E0020（:618）と E0005 の両方に当たり、`@relaxed` / `@bulk` の旧形の扱いが無い。
- 案: (a) E0005 は、未知の属性と、R-36 の表でその種類の構文の場所（項目、フィールド、`let`、flow の入力）に付けられない属性。各属性のコードは、付けられる場所の中の意味の条件（`sample` の入力の `@param`、遅延でない `let` の `@mem`）と値。`@fp` / `@repr` の値の誤りは E0005。置き換え先の決まった旧形（`@derive`、`@relaxed`、`@bulk`）は E0020。(b) 既知の属性の位置の誤りは全て各属性のコードにし、E0005 は未知の属性だけ。
- 推奨: (a)。R-36 の「項目の種類ごとの表で検査する」と一対一で、一つの表から一つのコードが出る。旧形は直し方が違う（書き換え）ので S-103 で分ける。

**C-21 trait の重複実装・同名のメンバのコード**（中、B9）
- 論点: 仕様:566「重複実装、特殊化は無い」、:567「ジェネリック trait は一つの型について高々一つ」にコードが無い。derive と手書きの重なりだけ E0304（:617）。IR:66 の「`impl` の中の同名メンバも E0304」は「仕様へ」のまま。
- 案: (a) 全て E0304 にし、E0304 の範囲を「同じ名前・同じ実装が二つ見える」に広げる。(b) trait の実装の重複を新しいコードにする。
- 推奨: (a)。S-34 の割り当てを保てる。直し方（名前を変える／片方を消す）が少し違い、S-103 とは緊張がある点は承知の上で、「二つあるものを一つにする」としてまとめる。

**C-22 derive した `PartialOrd` / `Ord` / `Show` の意味**（中、B11）
- 論点: 仕様:616 の derive の一覧のうち意味があるのは `Default` だけ。`PartialOrd` / `Ord` は第 1 期の実装の範囲（計画:217）。A-07 は「`None < Some`、列挙子の順の意味が仕様に無い」。
- 案: struct の比較はフィールドの宣言順の辞書式（タプルの規則 :599 と同じ、NaN の扱いも同じ）。enum は (a) 列挙子の宣言順、同じ列挙子なら中身の辞書式、または (b) derive では並べられない（E0416、手で `impl` を書く）。`Show` の書式は Onsa の式として読める形（`Point { x: 1.0, y: 2.0 }`、`Shape.Circle(1.0)`）。
- 推奨: enum は (b)。S-49 の理由（並べ替えで意味が黙って変わる）と A-07 に揃い、後から足すのは容易。`Show` の derive は第 1 期は E0200（`Str` が要る）なので、書式は第 2 期の `Str` と一緒に決める（持ち越しの表に載せる）。

**C-23 タプルの `Show`（`gen.pair`）**（中、B12）
- 論点: `check[T: Show]`（仕様:1102）に `gen.pair` の値（タプル）を渡すが、タプルは `Show` を満たさない（:594）。
- 案: (a) タプルに `Show` を足す（`(1, 2.0)` の形）。(b) `gen.pair` を外す。(c) `check` の境界から `Show` を外す。
- 推奨: (a)。二つの引数の性質を検査する主な手段で、書式は C-22 と同じ規則で決まる。

**C-24 総称の `impl` の構文とタプルの実装**（中、B13）
- 論点: 仕様に `impl[T, const N: U32] Ring[T, N] {` の形（計画:114、`tests/spec/types/const_args.onsa:9`）の規則が無い。S-72 で組込み型の実装は std の `impl` としたが、タプルは要素数ごとに書けない。
- 案: §6.2 / §6.3 に、`impl` の型パラメータと境界の書き方、対象に書ける型の形を定める。タプルは (a) 構造から処理系が与える（derive と同じ扱い）、(b) 要素数ごとの `impl` を std に書いて上限を置く。
- 推奨: (a)。上限という新しい制約を作らない。

**C-25 第 1 期の `Hash` の derive**（中、B14）
- 論点: S-13 は第 1 期の `Hash` の derive を E0200 とした（計画:217）が、S-71 の std の宣言は `pub enum Option[T]: PartialEq + Eq + Hash`（仕様:326）。
- 案: (a) 第 1 期の `Hash` は、S-13 の `Default` と同じく境界の判定だけを実装する。(b) 第 1 期の std は `Hash` を外して宣言し、食い違いを持ち越しの表に載せる。
- 推奨: (a)。S-13 に前例があり、std の宣言を仕様の文面どおりに書ける。

**C-26 番号が仕様に出ない診断コードと、コードの無い拒否の規則**（中、B16）
- 論点: E0410（struct リテラル・パターン）、E0414（`?`）、E0415（代入先）、E0421（型付きホール）、E0502（反駁可能な `let`）、E0712 は計画 §5 と登録簿にあるが、仕様の該当の規則に番号が無い。拒否するのにどこにもコードが無い規則もある: 重複実装（C-21）、定数の評価（C-18）、`@fp` / `@repr` の値（C-20）、`par` の回数（C-19）、`F32.MIN`（:645）、浮動小数のリテラルのパターン（:667）と struct パターンの `..`（:669）、`Buf` / `Span` の Copy でない要素（:402）、`[e; N]` の Dup でない `e`（:131）、補間の値が `Show` でない（:138）、`vdelay` の非 `Float` と `MAX >= 1`・`delay` の `N = 0`（:946〜947）、`panic` の引数がリテラルでない（:827。計画:300 の E0200 は §18.1:1966 の E0200 の範囲に合わない）。Q-01 はテストを仕様だけから書き、Q-08 は否定例をコードごとに数える。仕様にコードが無ければ期待値を書けず、実装は流用に流れる（S-103 で直した失敗と同じ型）。
- 案: (a) 拒否する規則には全て、仕様の本文でコードを書く。(b) 仕様は範囲と原則だけにし、コードは登録簿と `onsa explain` を正とする。
- 推奨: (a)。割り当ての案: trait の不成立（`Buf` / `Span` の要素、`[e; N]`、補間、`vdelay`）は E0416、`F32.MIN` は E0302（修正候補 `-F32.MAX`）、浮動小数のリテラルのパターンと `..` は E0020（修正候補はガードの形と `_` の並び）、`panic` の引数（リテラルでない）は E0401、`delay` の `N = 0` と `MAX >= 1` は E0808、規則の位置に番号の無い 6 つはその位置に番号を書く。割り当ては一組で決め、細部は反映のときに一覧で見せる。

**C-27 E0307 の規則の範囲**（低、B17）
- 論点: E0307 は孤児規則（仕様:566）と、`impl` の対象の別名（:379）の二つに使われる。
- 案: (a) 一つの規則「`impl` の対象は、このモジュールで宣言した型を、宣言の名前で書く」として §6.3 にまとめる。(b) 別名の場合を E0308 へ移す。
- 推奨: (a)。別のモジュールの型の別名は、名前を直しても孤児規則に掛かるので、分けると修復が 2 周になる。

**C-28 `Copy` と `Dup`**（低、B18）
- 論点: §6.3 の標準 trait の一覧（仕様:570）に `Copy` が無いが、:574 などで使う。`: Copy` を並べると E0416 の誤った note（「手で `impl` を書く」）になる。`impl Copy for X` の扱いも無い。
- 推奨: `Copy` を `Dup` と並べ、「種で決まり、`impl` も derive もできない（E0416、note は種の規則 §4.6）」と書く。std に宣言し、実装は種から与える（lang item）。

**C-29 総称の関数の演算子の修正候補**（低、B19）
- 論点: 仕様:580 は否定・ビット演算の修正候補だけを定める。
- 推奨: `==` `!=` は `PartialEq`、`<` 系は `PartialOrd`、`+ - * / %` は `Num` に境界を絞る。比較の演算子は数でない型も持つので、数の trait に絞ると `clamp` のような関数を誤った境界に導く。

**C-30 E0313 と E0650 の範囲**（低、B22）
- 論点: E0313（型の大きさ、仕様:334）は E03xx「モジュール・名前解決・シャドーイング・循環」に、E0650（`Atomic` の大きさ、:1652）は E06xx「効果・…」に合わない（:1950、:1953）。
- 推奨: E0313 は登録簿に入る前に E04xx の空きへ移す（安定コードは実装の前に揃えるのが安い）。E0650 は第 2 期のコードなので、分類の文を広げる。

**C-31 `map_err`**（低、B23）
- 論点: 仕様:534「std の最初の版で無名関数を受け取るのは `array.from_fn` と `std.test.check` だけ」だが、§9.1（:813）は `map_err` を使う。シグネチャが無い。
- 推奨: 一覧に `map_err` を足し、§9.1 に純粋な `fn(move E) -> F` を受け取る形のシグネチャを書く（効果行の変数は第 1 期 E0200）。

**C-32 公開の宣言に見えない型を書く**（低、B25）
- 論点: `pub type A = PrivStruct` や、`pub fn` の引数・返り値に、それより見えない型を書いた場合が決まっていない（仕様:1455）。
- 案: (a) 書けない（E0303）。(b) 書けるが、外からは名前で参照できない。
- 推奨: (a)。外の利用者が名前を書けない型を受け渡すことになり、回り道を強いる。`onsa interface` に引けない名前が出ない。

**C-122 列挙子と 0 始まりの番号の変換**（中、C-22 の議論で追加）
- 論点: 保存したデータの読み書き、C の API、`@param` の enum（§19.1）では、列挙子を 0 始まりの整数で表すことが多い（利用者の指摘）。仕様に変換が無く、enum ごとに番号の `match` を書くことになる（P10）。
- 案: (a) 宣言で `: Ordinal` を付けた、中身の無い enum だけが `ordinal()` / `from_ordinal(n) -> Option` を持つ（Swift の `: Int` の生の値に近い）。(b) 中身の無い全ての enum が印なしで持つ（Java の `ordinal()`）。(c) C のように値を指定できる。
- 推奨: (a)。印が「列挙子の順が外に出る」ことを示し（P10）、印の無い enum に隠れたメソッドを生やさない。Java の文書も `ordinal()` を「ほとんどのプログラマには使い道が無い」とする。

#### 2.2.4 flow・クロック・状態

**C-33 flow の分岐の中で何を評価するか**（高、FC-01）
- 論点: R-14 の決定は「インスタンスの引数」を取られない側でも評価する。§3.5（仕様:302、S-75）は「分岐と `&&` / `||` の右辺の中も評価する」と全ての式に広げ、§11.5（:989）はインスタンスのことだけを書く。`if d != 0 { 100 / d } else { 0 }` や `if i < n { table[i] } else { 0.0 }` が flow で panic するかが節によって分かれる。`match o { Some(v) => lp~(v), None => 0.0 }` で `o` が `None` のときの `v` の値はどこにも無く、インタプリタ・C・参照評価器が別の値を使いうる（ビット一致が崩れる）。
- 案: (A) S-75 の文言どおり、分岐の中を全て評価する。§11.5 に書き、取られない腕の束縛は `T.default()`（`Default` でなければ E0816）。分岐では添字やゼロ除算を守れないことを §11.5 に注意として書く（`x / max(d, 1)` の形を示す）。(B) R-14 の範囲に合わせ、取られない分岐で評価するのはインスタンスと遅延とその引数、巻き上げた部分式（S-33）だけにする。束縛は (A) と同じ。
- 推奨: (A)。巻き上げ（S-33）は既に取られない分岐の部分式を評価するので、(B) だと評価の規則が 3 種類になる（P2）。降下は選択（select）に一本化でき、参照評価器も単純。代償は、flow の中の分岐が panic の守りにならないこと（利用者が `min` / `max` で値を守る）。

**C-34 クロックが定数の複合式の評価の時期**（中、FC-07）
- 論点: §11.3 の表（仕様:924）は定数のクロックを「コンパイル時」とし、rt fn の結果のクロックは引数の最大値（:985）なので、字面どおりなら `exp(-1.0)` はコンパイル時（§6.6 の musl の移植）に評価される。計画（:410）と実装と IR の FL-2 は `init`（変換先の libm）で評価する。生成物のビットと `--backends all` の判定が変わる。
- 案: (a) 字面どおり。定数のクロックの式はコンパイル時に §6.6 の規則で評価する（計画に段を足し、panic は C-18 のコード）。(b) 呼び出しのクロックは `max(init, 引数)` とし、演算子とリテラルの式だけを定数にする。(c) flow の中ではコンパイル時に評価せず、定数のクロックの式は `init` で評価する（IEEE の正確な演算の畳み込みは観測できない最適化として許す）。
- 推奨: (a)。同じ式を `const` に分けても分けなくても同じビットになる（(c) では `const A = exp(-1.0)` と式の中の `exp(-1.0)` が違うビットになる。違うものが同じ形に見えるのを避ける、P10）。定数は全ての変換先でビット一致になり、超越関数に到達する flow が減る。評価器は `const` と同じもの（R-89 (2) の定数の評価の段）で、新しい仕組みは要らない。主題 (c) のエージェントは (c) を推した（rt と非 rt の呼び出しの扱いが一つになる）が、上の理由で (a) を推す。非 rt fn が `init` で評価されるのは、確保などの rt でない処理をサンプルの経路から外すためで、別の理由として残る。

**C-35 非 rt fn に速いクロックの値を渡す誤りのコード**（中、FC-08）
- 論点: 仕様:986「引数のクロックが `init` 以下のときだけ呼べる」にコードが無い。E0814（遅延の `init` 引数のクロック、:953）と E0815（flow の呼び出しの引数と `e at k`、:931、:991）は、どちらも「値のクロックが置く位置より速い」誤りで、直し方が同じ。
- 案: (a) 非 rt fn の場合は E0815。(b) さらに E0814 を E0815 にまとめ、E0814 は欠番にする。
- 推奨: (a) と (b)。S-103 の原則（直し方が同じならまとめる）による。E0814 は登録簿にあるが、文面の更新だけで済む。

**C-36 状態のノードの名前、巻き上げの対象と番号**（中、FC-09）
- 論点: §11.6（仕様:1061）を字面どおりに読むと、`let c = prev~(b)` の遅延も「名前の無いノード」で `c.prev_0` になる。一方、§11.6 の例（`src: saw.State`）と `tests/review-phase1/parent/r98.onsa` の期待値（`b, b.prev_0, c, c.prev_0`）は、`let` の値そのものが呼び出しなら `let` の名前で呼ぶ。巻き上げる部分式の範囲、番号の付け方（「呼び出しの名前が字面に現れる順」は巻き上げた部分式に当てはまらない）、出力の式の巻き上げの位置、遅延の `init` 引数の扱い、名前を束縛しない分解（`let (_, _) = f~(x)`）が決まっていない。配置は `SIZE` を決めるので規範。
- 推奨: §11.6 / §12.4 に次を書く。分解しない `let` の値がインスタンス・遅延・`par` の呼び出しそのものなら、そのノードは `let` の名前で呼び、中のノードは `let` で修飾して 0 から振る。巻き上げるのは遅いクロックの部分式のうち最大のものだけで、名前（入力、`let`、`par` の添字）と `sample_rate()` は巻き上げない。巻き上げの番号は部分式の始まりの字面の順。出力の式の巻き上げは `let` の巻き上げの後。遅延の `init` 引数は `<名前>.init`。名前を束縛しない分解は `_<番号>` の形（番号は分解する `let` の字面の順）。

**C-37 C のフィールド名の写し方と `hoist`**（中、FC-10）
- 論点: 仕様:1061「定数でない `init` の保存先は `<名前>.init`（C では `.` を `_` にする）」。`line.buf` と利用者の `let line_buf`、`a.prev_0` と `let a_prev_0` が C で同じ名前になる（R-48 は生成する名前の単射を決めた）。利用者の flow `hoist` を出力の式で呼ぶと、ノード `hoist_0` と巻き上げのフィールド `hoist_0` が重なる。
- 案: (a) C では `.` を `__` にし（型の `voice__State` と同じ）、識別子に `__` を書けないことを E0320 に足す。`hoist` を予約の名前（flow に使えない）に足す。(b) `_` のまま、衝突する `let` の名前を E0304 で予約する。(c) 衝突したときだけ改名する。
- 推奨: (a)。単射が構造で保証され、型の名前と同じ規則一つで済む（P2）。デバッガで見える名前が予測できる（§11.6 の「同じ名前が見える」）。(c) は名前が入力しだいで変わる。

**C-38 §6.5「属性は受理されるプログラムを変えない」**（中、FC-11）
- 論点: 仕様:624 の文に対し、`@mem(bulk)` は E0819（:1164）、`@param` は `block` の入力に必須（:1084）、`@repr(c)` は FFI で受理を変える（:1318）。S-102 は `@rate` の案をこの約束で退けた（変更点:131）。
- 案: (a) 「属性は型と、受理されたプログラムの計算の結果を変えない。属性に関わる検査（位置と値、`@param` の必須、E0819、`@repr(c)` の FFI）は各節に書く」に精密にする。(b) 文を残して例外を列挙する。
- 推奨: (a)。`@rate` はクロックの推論と評価の段という意味を変えるので、S-102 の判断はそのまま成り立つ。

**C-39 `par` の範囲、入れ子のブロックの `let`、状態の無い `par`**（中、FC-13、IR の FL-4 / FL-5 / C-8）
- 論点: §7（仕様:680）は範囲 `a..b` を `par` の見出しに書けるとするが、§11.5（:994）は `par i in 0..N` だけを定める。IR の「入れ子のブロックは式 1 つ」「`par` の境界は定数で `from < to`」「状態を持たない `par` はフィールドを作らない」が「仕様へ」のまま。
- 推奨: `par i in a..b` は定数の境界を認め、`N = b - a`、`i` は `U32` で `a`〜`b-1`。定数でなければ E0417（C-19）、空の範囲（`a >= b`）は E0808。入れ子のブロック（分岐の腕、`par` の本体）の `let` は E0806（S-86 の名前と C-04 の `^` の範囲がそれを前提にしている）。状態の無い `par` はフィールドを作らない。

**C-40 `e at k` の昇格と巻き上げ**（中、FC-18）
- 論点: `let c = design(freq) at block`（仕様:931）で `freq` が `init` のとき、字面どおりだと `design(freq)` は `block` の段で使われるので巻き上げられ、さらに `c` も `sample` から読まれる `block` の `let` として自分のフィールドを持ち、同じ値が二重に置かれる。
- 案: (a) 昇格は段を作らない。`e` はその推論したクロックの段で評価し、値を置く場所は一つ。(b) `at` で `k` の段に写す。
- 推奨: (a)。「値は変わらない」の文言と一致し、余分なフィールドを作らない。

**C-41 bulk を持つ flow を Onsa の `main` から持つ**（低、FC-19）
- 論点: bulk を持つ状態を関数のローカルに置くと E0819（仕様:1164）で、§16.1 の `main` の形（:1617）では持てない。
- 推奨: §19.1 の「ファームウェアのエントリ」に、bulk を持つ flow は今は C のホストから使うことと、Onsa の `main` から持つ形を決める必要があることを書いて保留する。用途が出てから決める。

#### 2.2.5 C の API・ビルド・マニフェスト

**C-42 `strict` の結果がホストの制御レジスタに左右される**（高、d01）
- 論点: 制御レジスタの保存・設定・復元は `strict-ftz` の入口だけ（仕様:1593）。ホストが FTZ / DAZ（プラグインの音声スレッドでよく設定される）や丸めのモードを変えていると、`strict`（:1588「非正規化数あり」）の生成コードは黙ってその状態で計算する。`round` は C の `rint`（今の丸めのモードに従う、:1257）に対応付けている。S-105 が `strict-ftz` で退けた「設定し忘れで黙って食い違う」（レビュー:2080）が `strict` に残る。
- 案: (a) `strict` の入口でも同じ補助で、FTZ / DAZ を外し、丸めを最近接偶数に設定し、出るとき戻す。(b) ホストの責任として §14.2 に呼び出しの条件を書く。(c) (b) に加え、debug のときだけ入口で検査する。
- 推奨: (a)。一つの仕組みで、両方のプロファイルの約束が呼び出し側の状態に依らなくなる。費用は S-105 と同じ（ブロックごとにレジスタの読み書き 2 回）。(b) では §14.2 が第一の経路とするプラグインで黙って崩れる。

**C-43 生成する C の名前の一覧、Config の渡し方、0 個の場合**（高、d02、FC-17、FC-26）
- 論点: 仕様:1406「flow は、それを頭にした名前（`vc_voice_init`、`vc_voice_params` など）と…マクロ（`VC_VOICE_SIZE` など）も生成する」と「など」で終わり、E1011 が何どうしを比べるかが決まらない。flow どうしも重なる（`voice` と `voice_bulk` の `VC_VOICE_BULK_SIZE`、`voice` と `voice_params` の `vc_voice_params`、`voice` と `voice_param` の `vc_voice_param_info` / `_param_index`）。Config の C の型名と渡し方（:1381「Config が空なので引数は sample_rate のみ」は並べる形を示唆。IR の B-6 は「`_new` は `_init` と同じ引数（`Config` のフィールド）」）、`_new` が bulk 領域を確保するか、`@param` が 0 個のとき（ISO C では `_param_info[0]` も空の構造体も書けない）、`BULK_SIZE` が 0 のときの `BULK_ALIGN` の値が無い。
- 案: §14.2 に生成する名前を表で閉じる（関数 `_init` `_reset` `_process` `_params_default` `_param_index` `_new` `_free`、データ `_param_info`、型（状態、`_params`、`_config`、`_in`、`_out`）、マクロ `_SIZE` `_ALIGN` `_BULK_SIZE` `_BULK_ALIGN` `_PARAM_COUNT`）。E1011 はこの表の名前の集合で判定すると書く。Config は (a) `const <prefix><name>_config*` を `params` と同じ形で受け取る、(b) フィールドを引数に並べる（今の実装と IR の B-6）。0 個の場合（空の Config は引数を省く、`@param` が 0 個なら `_param_info` を出さず `PARAM_COUNT` は 0、`BULK_SIZE` が 0 なら `BULK_ALIGN` は 1）と、`_new` が bulk も確保することを書く。
- 推奨: Config は (a)。`Params` と同じ概念を同じ形で渡せ（P3）、ホストは名前でフィールドを設定するので引数の順の取り違えが起きない。IR の B-6 の書き方を改めることになる。公開の ABI なので、0 個の場合も含めて §14.2 で明示する（R-121 の方針）。

**C-44 `_init` に bulk が NULL のときの値**（中、d11、FC-24）
- 論点: R-49 の決定「`BULK_SIZE > 0` で bulk が NULL なら `_init` が失敗のコードを返す」が仕様に無く、値も決まっていない（仕様:1383 は「0: ok, 1: init が panic した」だけ）。
- 案: (a) 2（呼び出し側の引数の誤り）。(b) 1 に含め、意味を「初期化できなかった」に広げる。
- 推奨: (a)。`process` の 2（重なり、:1405）と意味が揃い、ホストが panic と自分の誤りを区別できる。

**C-45 マニフェストの E0200 の時期と終了コード**（中、d03）
- 論点: 仕様:1541「仕様にあってこの版のコンパイラが未対応のもの（`kind` の `clap`、`lang` の `js`、std 以外の依存、`main_frame` など）は、使った位置で E0200」。:1965「ソースを読む前にマニフェスト全体（全てのターゲット）を検査し、誤りがあれば終了コード 2」。全体の検査で E0200 を出すと、§15.3 の例（`clap`、`js`）が `check` / `test` を止める（R-47 で直した状態に戻る）。`onsa.toml` を指す E0200 と `[export]` の E0302 の終了コードが決まらない。未対応の値の一覧が「など」で閉じていない。
- 案: (a) ターゲットに属する値は、そのターゲットのビルド（と `--target` を取るコマンド）で E0200。std 以外の依存はマニフェストの検査で出す。`onsa.toml` を指す診断は全て終了コード 2。未対応の値の一覧は計画（S-99 の行）に閉じて置く（コンパイラの版で変わる）。(b) 全てを全体の検査で出す。(c) 全てをビルドで出す。
- 推奨: (a)。R-47 の意図と §18.1 の「ターゲットに依る検査はそのターゲットのビルド」に合う。

**C-46 §18.2 に `onsa build` の行が無い。`onsa test --target`**（中、d04）
- 論点: 仕様:1262 などが `onsa build` を使うが、§18.2 の表（:1990 付近）に書式・出力（`target/<名前>/`）・`--target` を省いたときの扱いが無い。`onsa test` がどのターゲットの `fp` / `platform` / `panic` で走るかも決まらない（:1595 の `strict-ftz` の模倣は「ターゲットとして実行するとき」）。§11.8 の `--seed` も表に無い。
- 案: `onsa build --target <名前>` と出力の一覧を足し、`onsa test --target <名前>` を足す（省けば `strict` と既定の panic）。`--target` を省いた `build` は (a) 使い方の誤り（終了コード 2）、(b) 全てのターゲット、(c) 先頭のターゲット。
- 推奨: (a)。§12.1（:1132）の「既定のターゲットを暗黙に選ばない」と同じ理由。

**C-47 `strict-ftz` で、インタプリタがどの判定を模倣するか**（中、d05）
- 論点: 仕様:1589「小さすぎるかの判定を丸めの前に行うか後に行うかが、アーキテクチャで違う」。計画:235 の書き方は丸めの後の判定（x86）で、§15.3 の daisy（ARM）では最小の正規化数の境界でインタプリタと実機が違いうる。
- 案: (a) ターゲットの platform のアーキテクチャの判定を模倣し、同じアーキテクチャの C とビット一致を求める。(b) 判定を一つに固定し、境界の値だけを許容する。(c) 許容誤差で比べる。
- 推奨: (a)。§15.5 の約束をそのまま検査できる。platform は必須なので選ぶ材料があり、違いは 0 にする条件一つで済む。

**C-48 `strict-ftz` とソフトウェアで計算する F64**（中、d06）
- 論点: 単精度の FPU しか無い機器（Cortex-M4F など）では F64 はソフトウェアの浮動小数で計算され、FZ に従わない。F64 だけが黙って `strict` の動きになる。トリプルだけでは F64 がハードウェアかが分からない（仕様:1594、§15.3 の daisy）。
- 案: (a) F64 がハードウェアに無い platform の `strict-ftz` で、F64 の演算に到達するものを E0200。(b) 生成コードがソフトウェアで 0 にする。(c) 約束をハードウェアの演算に限る。
- 推奨: (a)。S-105 の「黙って `strict` にしない」と同じ考え方で、組込みの DSP は F32 が主なので費用が小さい。F64 の有無を決めるプラットフォームの表（IR の B-11）が要る。

**C-49 MSVC を確かめる作業が無い**（中、d08、e-21）
- 論点: 仕様は MSVC について約束している（§13.4 / §14.2 の `/fp:strict`、`/fp:fast` の `#error`）。D-14（計画:172）は「Windows の MSVC で C を生成・ビルド」とするが、CI は用意しない（PI:103）と決め、Q-07 の検査（PI:220）に MSVC は無い。
- 案: (a) 第 1 期は MSVC を未検証と計画に明記し、作業として残す。(b) clang-cl で確かめられる範囲だけ確かめる。
- 推奨: (a)。確かめていない約束を確かめたように見せない（R-113 の反省）。

**C-50 マニフェストを上の階層へ探す**（中、d12）
- 論点: R-47 の決定（レビュー:638「マニフェストを上の階層へ探す」）が仕様に無い。計画:244 は前提にしている。パッケージの中のファイルを渡したとき、何を検査するかも決まっていない。
- 推奨: 渡したファイル（無ければ作業ディレクトリ）から上へ、最初に見つけた `onsa.toml` のディレクトリがルート。見つからなければ単一ファイルのパッケージ。ファイルを渡したときはパッケージ全体を集めて解決し、そのファイルの診断だけを出す（`use` の解決にパッケージ全体が要る）。

**C-51 std の版の例**（中、d13）
- 論点: 仕様:1491 の例 `std = "0.2.0"` に対し、:1565「埋め込みの std の版と一致しなければ E1103」だが、埋め込みの std の版が定義されていない。S-83 で std は暗黙の依存なので、書かなくてよい。
- 案: (a) 例から外し、埋め込みの std の版を表示する場所（`onsa --version`）を決める。(b) 版の決め方を決めて例を合わせる。
- 推奨: (a)。例に書くと毎回書くものと読まれる（P10。S-83 の理由と同じ）。

**C-52 「成果物は同一」の約束と外部の C コンパイラ**（中、d14）
- 論点: 仕様:1564「ネットワークも環境変数も読まない…成果物は同一」。計画:602 は `platform` がホストなら `cc` を呼ぶ（PATH を読む）、クロスは C の出力だけ。`.a` は外部の C コンパイラ次第で変わり、クロスで `.a` を作らないことが仕様に無い（§17.5 は daisy で静的ライブラリにする）。
- 案: (a) 同一の約束を Onsa が生成するファイルに限る。`.a` は外部のツールチェーン（探し方を一つに決める）に依ると書き、クロスはソースだけを出して note で知らせる。(b) §15.3 にツールチェーンのキーを足す。
- 推奨: (a)。閉じた表を、必要が確かめられる前に広げない。

**C-53 `@fp(relaxed)` の flow の `--backends all`**（中、d15）
- 論点: 仕様:1268 は超越関数に到達しない flow をビット一致で比べる。`@fp(relaxed)` の flow はこの比較で落ちる。「対象外」は全体計画:208 にしか無い。
- 案: (a) 同じ到達解析で比較から外し、外した数を表示する。有限で panic しないことは確かめる。(b) 許容誤差で比べる。

**C-54 `onsa transpile` と `kind = "source"`**（中、d16）

**C-55 `flows` / `fns` の経路の意味と例の配置**（低、d22）

**C-56 export する flow の `pub` と誤りのコード**（低、d26、FC-27）

**C-57 計画の旧名のキーの修正候補**（低、d27）

**C-58 生成した C の `-pedantic`**（低、d30）
