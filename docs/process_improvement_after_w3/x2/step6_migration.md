## MG-2 移行の道具

- オーダーと停止: どの道具も、元の文書の行を一度ずつ読み、各行を一つの宛先に割り当てる一回の走査（行の数 n に線形。表の行は最大 551、文書は最大約 100 万バイト）。不動点や繰り返しは無いので止まる。往復の多重集合の比べは並べ替えで O(n log n)。

## MG-6 進め方とリスク

- 各段: 道具（実装か親）→ 乾いた試し → 判断の一覧を親が決める（利用者に出すものは区切りごとに束ねて出す）→ 親が README などを置く → `onsa-docs` が主のツリーで回す → 親が差分を読んでコミット。
- 戻し方: 段の中はコミットしない。
  失敗したら、道具が出す「書いたファイルと除いた範囲」の一覧と `git status` を見てから、`git restore --staged --worktree` をその段の経路に、`git clean` を新しいディレクトリ（`spec`・`decisions`・`issues`・`tasks`・`history`）に限って当てる（見ずに消さない、`git stash` は使わない）。
  段の間で止まるのは安全（状態は「段 k まで済み」のコミットで一意。道具は基の状態に対して冪等なので再実行でよい）。
- 期間: いまは W3 と W4 の間で W の作業は動いていないので、実質の止まりは X-3〜X-9 の後ろ倒し。段を回す時間は区切りごとに 1〜2 時間の見当（未測）。U4・U5 は (3) と並べて作業ツリーで書ける（主のツリーを触るのは一度に一つ）。
- 見落としのリスク:
  - 往復の正規化が広すぎると差を隠す。正規化は閉じた一覧にし、報告に出す。✅ は除かずに `status` との対応を確かめる。
  - 被覆は「どこかに入った」しか見ない。正しい宛先に入ったかは往復と抜き取りで見る。
  - 頭の欄付きのファイルに移った本文の ID と § が、`docs.py check` の参照の確かめで落ちうる（本文の無い ID、仕様の見出しに無い § 9 個）。乾いた試しの `check` で一覧にし、親が字を直す。
  - 移行の道具は README の欄の表を読むので、表が DF-4〜DF-6 と食い違うと移行の全体がずれる。README は段の前に親が置き、乾いた試しで `check` を通してから本番に入る。

## MG-8 もっと単純な代替

- 一つの道具で全部を一度に: コミットとレビューは一回で済むが、失敗の切り分けが難しく、差分が千ファイルを超えて親が読めない。
- (4)・(5) を一つずつの段に（advisor の第 1 段）: 票と gate が減るが、判断の一覧が三種類混ざる。
- (3)・(6) を担当に出さず親が回す（advisor の代替）: 担当の 2 票分（20〜30 万）が減る。DM-7 から外れ、担当の試運転が無くなる。費用が気になれば選べる。
- 往復を省いて `check` だけ: `check` は欄と参照を見るだけで、本文の字が欠けても通る。利用者の「事前のチェックツール」を満たさない。
