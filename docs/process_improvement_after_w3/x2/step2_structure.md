**決定（2026-10-16、利用者）:** この案（DS-1〜DS-10）で良い。もっと単純な代替（ファイルを動かさない案）は、今後のために採らない。次は手順 3（ドキュメントごとのフォーマット）。

手順は利用者の `docs/process_improvement_after_w3.md` の 2 章の 2。材料は `step1_eval.md`。
第 2 版に advisor の独立のレビュー（`adv/handback_stage1.md`・`stage2.md`）を取り入れ、第 3 版に利用者の改め（`issues/` と `tasks/` を分ける、事前検討の資料は `issues/`）と inode の確かめを入れた。
形式（手順 3）、道具（手順 4）、管理の担当（手順 5）、移行（手順 6）は後で決める。ここは構造と、それらへの前提だけ。

## 0. 考え方

- **寿命で分ける**: その文書が何の真実で、誰がいつ変えるか。
- **正本は一つ**: 一つの事実の本文は一か所だけに書き、他は ID で指す。重なりが起きる欄そのものを無くす。
- **一つのファイルを小さく**: 全体を一度に読め、Edit ツールで直せる大きさ。
- **ID と § 番号は変えない**: 置き場所だけを変える。

## DS-1 ディレクトリの形

```
README.md     索引の入口: 各ディレクトリの目的、誰がいつ読むか、役割ごとの「始めに読むもの」
spec/         規範: 言語の仕様とツールの仕様
rules/        規則: 共通、親、手順（今の計画 §8）
decisions/    決定: S、D、K、Q、A（中身が決定そのもの）と、実装の共通の設計の本文（今の計画 §3）
issues/       問題と計画の段: R（見つけた問題と判断）、RF（リファクタリングの候補）、X（改善の項目）、宛先の作業がまだ無い持ち越し、利用者の事前検討の資料
tasks/        実行の段: W、X から生まれた実行の単位、段の一覧、診断コードの実装の表（今の計画 §5）
history/      読み返すだけ: 古い版の仕様とその頃の資料、変更点、レビューの本文、空白の資料、点検の資料、終わった段の計画
```

- ID の種類から経路が規約で決まる（`S-537` → `decisions/S/S-537.md`、`R-235` → `issues/R/R-235.md`、`W3-13` → `tasks/W/W3-13.md`）。
- 状態: `issues/` は「開いている / 直さない（記録） / 済み（作業の ID）」、`tasks/` は PLAN / PENDING / DOING / DONE（DOING の中でどの票かを見る欄は手順 3）。
- 問題と作業の寿命は違う（問題は「直さない」で閉じることがあり、一つの作業が複数の問題を直す）。
- `docs/` は無くなる。道具が読むデータ（`foreign-forms.toml`）の置き場所は移行のときに決める。
- 根拠（手順 1）: 計画の grep の 47%、rework の 58% が複数の文書をまとめて探す読み方。S-300〜S-551 の 73% が 2〜7 個の文書に重なる。

## DS-2 決定の正本: ID ごとに一つのファイル

- `decisions/S/S-537.md` のように決定ごとに一つ（S 551、D 16、K 23、Q 15、A 14）。
- 構造として要る欄（書き方は手順 3）: ID、題、状態、仕様の節、担う作業、見つけた作業、改めた・改められた（後の決定が前を改める鎖）、本文（論点、割れる読み、決定と理由）、元の下書き（履歴のファイルと見出し）。
- **担う作業は決定の側だけに書く**。作業の側の「実現する決定」の一覧は道具が集めて出す。
- 仕様には規範の文だけ。理由と経緯は決定のファイル。
- 今の重なりは一つになる: 計画 §2 の表、変更点 §4、rework の「実現する決定」、空白の資料の状態の欄。
- これから作る空白の下書きと独立のレビューは `decisions/S/S-xxx.draft.md`。

## DS-3 問題と作業: issues と tasks

- `issues/R/R-235.md`: 指摘、判断、状態、直す作業の ID、保存した入力。今のレビューの R の本文と §8 の表（複数行のものは判断の履歴として並べる）を一つにする（235 件）。
- `issues/X/X-2.md`: 改善の項目の問題、手順、評価、決めた基準と策。評価などの材料は横の `issues/X/X-2/` に置く（DS-10）。
- `issues/RF/`: リファクタリングの候補（今の持ち越しの RF-1〜RF-16）。
- 宛先の作業がまだ無い持ち越しは、開いている問題として `issues/` に置く。
- `tasks/W/W3-13.md`: 範囲、状態、依存、規模、単位の分け方と親の答え、その作業に宛てた持ち越し、終わったときのコミットと一行の結果。今の rework の W の表（約 5 万字）と `carryovers.md`（約 4 万字）は解体して、宛先のファイルへ移す。
- 作業票（scratchpad）はリポジトリに入れない。決まったことだけを作業のファイルに残す。
- 状態の一覧は道具が出す。

## DS-4 仕様の分け方: 概要と章

- `spec/README.md` が概要（今の §0・§1 の全文）と、章の一覧と各章の一行の要約。
- 章ごとに一つのファイル（`spec/02-lexical.md` … `spec/20-order.md`）。見出しと § 番号は通しのまま（テストの `spec = ["§6.1"]` 約 1,260 件、相互参照、`SPEC-GAP` の印を変えない）。
- **本文は書き換えない**。利用者の「概要と詳細」は、README（概要）と章（詳細）の形で満たす。規範の文を組み直すのは仕様の改版になり、§ の参照約 8,400 を一度に扱うので、今回は混ぜない。
- ツールの仕様は `spec/tools.md`（§ 番号を保ち、コードとテストの 197 か所は経路だけ道具で置き換える）。§19 は章として残す。
- 道具は章を番号順につないで、今と同じ一つの仕様として読む。

## DS-5 履歴: 日々は読まない

- `history/` に中身を変えずに移す: 古い版の仕様と資料、変更点、レビューの本文の残り、空白の資料の三つ（約 97 万字、分けない）、点検の資料、再発防止の資料、終わった段の計画（計画 §0・§4・§6・§7、rework §4・§5）。
- 計画 §6 は行番号で引く古い表で道具は読まない（履歴へ）。計画 §4 の T の表は `pending.toml` に T が無いので、`pending.py` の読みを外して履歴へ。
- 履歴は直さず、gate も読まない。切り出しの済んだ元の表の写しは残さない（git にある）。

## DS-6 索引と、正本を保つ確かめ

- 直下と各ディレクトリの `README.md`（目的、ID と経路の規約、状態の値の意味、役割ごとの始めに読むもの）。今の `leader-rules.md` の付録の地図は直下の索引へ。
- **ID の一覧はコミットしない**。道具が求めに応じて出す。
- gate に入れる確かめ（手順 4 で道具に）: ID の言及が正本のファイルとして存在する、必須の欄と状態の値、指す § が仕様にある、済んだ作業を担う決定が未決のままでない、README の相対リンク。
- 「本文を写していない」の機械の確かめは入れない（重なりの欄を構造で無くす）。

## DS-7 大きさの目安

- ID ごとのファイル: 数千字。読み物（仕様の章、規則、設計の本文）: 約 2.5 万字まで（今の全ての章が収まる）。履歴は対象外。目安で、gate では落とさない。
- ファイルの数と inode（確かめた）: この機械は APFS で、inode は 64 ビット、空き約 29 億、使用約 260 万（0%）。ファイルが約 850 増えても無視できる（今の inode の大半は `target/` のビルドの出力）。ext4 に写しても足りる。小さなファイルは最低 4 KB を使うので約 850 個で約 3.4 MB。git の追跡は今 2,251 ファイル。

## DS-8 規則の分け方

- 始めに読む: `rules/common.md`（今の `agent-rules.md` の 1 章、2 章、3 章、6 章。約 1 万字以下）。
- 要るときに読む: `rules/checks.md`（4 章）、`rules/documents.md`（5 章）、`rules/criteria.md`（7 章）、`rules/refactoring.md`（8 章）。
- `rules/process.md`（今の計画 §8）、`rules/leader.md`（今の `leader-rules.md`）。
- 担当の定義は利用者が編集する場所のまま、読む順を指す。規則は移すだけで文を変えない。移す前に利用者の了承を取る。

## DS-9 移行の前提と順（手順 6 への申し送り）

- ID と § は変えない。各段の終わりで gate が通る（道具を先に直す）。担当が動いていない区切りで行う。
- 移すだけの段は中身が変わらないことを、表からの切り出し（分割）は新しいファイルから元の表を作り直して一致する往復を、道具で確かめる（利用者の手順 6 の「事前のチェックツール」）。
- コードとテストのコメントの経路は道具で置き換え、同じコミットに入れる。`leader-rules.md` 6.2「揃えて更新する文書」を同時に書き換える。
- 順の案: (1) `repo.py` に経路の抽象 → (2) 規則の分割 → (3) 仕様の章の分割と `tools.md` → (4) 決定の切り出しと gate の読み先 → (5) 問題と作業の切り出しと持ち越しの解体 → (6) 履歴の移動と索引 → (7) 規則の文の見直し。

## DS-10 利用者の事前検討の資料の置き場所

- 計画の段のものなので `issues/` に置く。今の `docs/process_improvement_after_w3.md` の 1 章は `issues/X/X-1.md`、2 章は `issues/X/X-2.md` の本文になる。下書き用の別のディレクトリは置かない。
- 項目で作った評価や案（今は scratchpad の `x1/step1_eval.md` など）のうち残す価値のあるものは、横の `issues/X/X-1/` に置く。scratchpad は `/private/tmp` の下で再起動で消えうるので、長く指す材料はリポジトリに置く。
- 計画が決まって実行に移るときは、`tasks/` に実行の単位を作り、項目のファイルから ID で指す。

## もっと単純な代替（利用者の判断に委ねる）

- ファイルを動かさず、ID の行を読み書きする道具・目次の道具・規則の分割だけを行う案（advisor）。費用だけならこれで大部分が減る。
- 動かす案の利点は、Edit ツールが使えること、並行の編集の衝突が減ること、履歴と日々のものの分離、重なりの欄が構造的に無くなること。親と advisor はこの四つのために動かす方を推す。

## 効果の見込みと確かめていないこと

- ID を探す複数の文書の grep → ID からファイルを開くだけ（逆引きは `grep -rl` のまま）。決定の記録の 3〜7 か所 → 一つ。大きな文書へのヒアドキュメントの置き換え（親 620 回）→ 小さなファイルへの Edit。始めの規則の全文読み → 役割の始めの分だけ。
- 確かめていないこと: ファイルが約 850 に増えた後の、探す費用（ID で辿る道具と README が前提）。
