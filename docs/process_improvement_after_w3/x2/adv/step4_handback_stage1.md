## T4 整形（確信: 中）

**案** `tools/wrap.py [--check] <paths>...`（既定は `spec/ rules/ decisions/ issues/ tasks/ README.md`。`history/` は除く）:
- 規則（持ち越し (10) の今の形を保つ）: 200 字を超える行だけを対象に、括弧 `（）()「」『』【】` の深さ 0、インラインのコード（`` ` ``）と太字の外の `。` の直後で切り、1 行 200 字以下に左から詰める。続きの行は箇条の本文の字下げ（`- ` の後ろの位置）、引用は `> ` を付ける。切ると次の行が箇条・引用・表・見出しの始まりに見える所（`- `、`1. `、`|`、`#`、`>`）では切らない。
- 触らないもの: 頭の欄（先頭の `+++` 〜 `+++`）、見出し、表の行、コードブロックの中、「欠番:」で始まる行（`repo.py` が 1 行として読む）、HTML コメント。
- **分けるだけで、つながない**。短い続きの行を元に戻す処理を持たないので、冪等は自明（1 回目で切れる行は 200 字以下か切れない行になり、2 回目は何もしない）。往復（改行と字下げを除くと元の行に戻る）は、道具が各ファイルの処理の後に必ず確かめ、違えば書かずに落とす。
- 切れない行（200 字の内に深さ 0 の `。` が無い）は `--check` でも落とさず、`note:` で件数と場所を出す（文を分けるのは人の作業）。
- **gate の項目か編集の後か（(10) の問い）: 両方**。編集した人（親、impl）が `wrap.py <file>` を回すのが本来だが、手順 1 は「誰も回し直さない」側の証拠（145 回の個別の確かめ）なので、`wrap.py --check` を gate の `static` の項目にし、`cargo fmt --check` と同じく「道具をかけると変わる行がある」ときだけ落とす（切れない行では落とさない）。導入の前に一度 `wrap.py` を全体にかけるコミットが要る（今 200 字超が 1,041 行。文書だけのコミットにし、仕様の章の分割（移行の (3)）より前に行えば、分割の往復の確かめとぶつからない）。
- **表の列の数の確かめ（(11)）**: 整形でなく `docs.py check` に入れる（T5）。全ての表で、各行のセル数が頭の行と同じ（`\|` とコードスパンの中の `|` を数えない）。48 回のその場のスクリプトがこれで消える。表の自動の直しは作らない（列の抜けはどこを埋めるか人が決める）。
- 計算量と停止: 行ごとに左から 1 回の走査で、切る位置は単調に進む。O(総字数)。約 4 MB で 1 秒未満の見込み（24 回目の `wrap_docs.py` が同じ量を扱った）。
- 副作用: 利用者が vim で書いた長い行も gate が「変わる」と言う（親が `wrap.py` を回せば済み、意味は変わらない）。段落の途中の改行は Markdown の表示では空白になるが、この文書群は端末・vim・Read ツールで読まれ、10-14 の整形で既に受け入れた形。
- 作る量: 200〜250 行 + 自己テスト（冪等・往復・触らないものの各形で 15〜20 件）。
- 確信が中なのは、「切れない行を落とさない」と「gate で落とす」の組み合わせが、利用者の「検証の深さは速さと釣り合わせる」に対して重いと見るかどうかが利用者の判断だから。軽い代替: gate は `note` だけ（判定を落とさない `info=True` の項目）。

## T8 手順 6（移行）の道具との境（確信: 中〜高）

**ここで設計するもの**: 移行の道具が頼る土台。

- `repo.spec_text` の結合（分割後の仕様が今の一本と一字も違わないことの確かめは `spec_text(root) == 旧ファイル` の比較一つ）。

- `wrap.py` は移行の前に一度かける（T4）。
**手順 6 に送るもの**: 一回だけ使うもの。表の切り出し（計画 §2 の 4 列 → S のファイル、rework §3 → W、レビュー §8 → R、`carryovers.md` の振り分け）、旧表の再生成による往復の確かめ、✅ と `status` の食い違いの一覧、`marks` の修飾の落ちる値の一覧、コードとテストのコメントの経路 197 か所の置換、`leader-rules.md` 6.2 の同時の書き換え。置き場所は `issues/X/X-2/tools/`（DS-10 の規約。`tools/` に入れない、gate の自己テストの対象にしない）。

## T9 作らないもの・後に回すもの・異論・リスク（確信: 中）

- 作らない・後に回す: 持ち越し (11) の文書に関わらない候補（fmt の性質の集計、fuzz の許可の一覧の雛形、文脈の内訳の道具、印のある事例の正規形、壊す側の道具の引き継ぎ）は X-2 の外（X-9 か別の項目）。整形で表の列を自動で直すこと、本文のラベルの確かめ（DF-8 で落とさないと決めた）、Markdown の表示（HTML）向けの処理、`history/` への道具の適用。
- もっと単純な代替:
  - 逆引きは `grep -rl`、状態の更新は Edit ツール、で道具なしでも成り立つ。足す価値があるのは「頭の欄の逆引き（道具が出す関係）」「閉じた値と対称を書く前に確かめること」「担当の一行の呼び出し」の三つで、本文の言及の `refs` はただの grep の包み。`refs` を落として `show` の逆向きだけにする案もある（数十行の差）。私は `refs` を残す（担当が `grep` の書き方を毎回考える費用の方が大きい）。
  - 整形を gate に入れず、編集の後に回す規則だけにする案（T4 の軽い代替）。
- 利用者の例への異論:
  - 例 2 の PLAN / PENDING / DOING / DONE は作業（`tasks/`）の状態で、決定（OPEN / DECIDED / DROPPED）と問題（OPEN / WONTFIX / DONE）は別の語彙（手順 3 で決定済み）。一つの `list` で種類ごとに列が違うのはそのため。
  - 例 3 の整形は、LLM の読みには効かない（Read ツールは行の長さで費用が変わらない）。人（利用者）の読みのための道具で、だから「分けるだけ」の最小の形にし、再配置（短い行をつなぐ）を持たせない。
- 見落としやすいリスク:
  - **頭の欄の正規形による差分**: `set` がキーの順と書式を揃えるので、手で書いた直後に差分が広がる。README に「頭の欄は道具が書き直す形」と一行書く。
  - **本文の `+++` 行**: 頭の欄の終わりは「最初の `\n+++\n`」と決める。本文に `+++` だけの行を書かない約束（Markdown の水平線は `---`・`***` なので実害は小さい）。
  - **採番の競合**: 親だけが `new` を使う（担当は `NEW`）。作業ツリーで `new` を呼ばれても主のツリーの番号を見ないので、`repo.tree_kind` が `worktree` なら `new` を拒む。
  - **`spec_text` の結合が隠す誤り**: 章のファイルの順と見出しのずれは `spec-sections` と `check` の `§` の存在で見えるが、章の先頭が `## N.` で始まらない誤りは結合の時点で落とす（README の §0・§1 と章の境の規則を `repo.py` に一つ書く）。
  - **gate の二重の落ち方**: `pending.py` の `reasons`（S・R の存在）と `docs.py check` の `(b)` が同じ事実を別の文面で落とす。`pending.py` の照合は残し、`check` の方は `pending.toml` を対象にしない（境を README に書く）。
  - **移行の前の空白の期間**: `docs.py` の `show` が無い間は「一方にだけ書く」が読み手に見えない（DF-10）。(1) で先に作る順で避ける。
  - **性能**: どの処理も 1 回の走査で、約 1,000 ファイル・4 MB では秒未満。ファイルが数倍になっても線形。停止はループが入力の行・ファイルに沿って進むだけで保証される（固定点・再試行なし）。
