- 欄の規則: 1 行目は `# <ID> <題>`。空行を一つ挟み、`- <欄名>: <値>` の行が続く。最初の `## ` か、箇条でない行で欄は終わる（本文との境）。欄名は閉じた一覧（各ディレクトリの README が定める、F7）。値は行末まで（最初の `: ` で欄名と切る）。複数の ID は `、` で並べる。無い欄は書かない（`—` を書かない）。
- 根拠:
  - 今の文書の形がすでにこれ（R の本文の `- 内容:`・`- 経緯:`・`- 決定:`、K の `- 日付:`、計画 §8.1 の票の `- 段:`）。移行で書き方を変えずに済み、担当が真似る形も変わらない。
  - 読む側は `^- (欄名): (.*)$` の正規表現で足りる。`repo.rows` と同じ程度の単純さで、標準ライブラリだけで済む。
  - YAML を避ける理由: この文書群の題と値に `:` が多い（「決定: …」「fmt の書き込み: rename」）。YAML の素のスカラーは `key: a: b` を受け付けず、引用符が要る。`yaml` モジュールも無い（上の確かめ）。TOML は文字列の引用符とバックスラッシュのエスケープが要り、担当の手書きの摩擦になる。どちらも「同じファイルに二つの文法」になる。
  - 借用元: Rust RFC の雛形は markdown の箇条の頭（`- Feature Name:`、`- Start Date:`、`- RFC PR:`、`- Rust Issue:`、続いて `## Summary`）で、同じ形（https://github.com/rust-lang/rfcs/blob/master/0000-template.md、2026-10-16 に取得して確かめた）。PEP 1 の頭の欄（`Status`、`Replaces`、`Superseded-By`）は欄名の選び方の参考（https://peps.python.org/pep-0001/、同日に確かめた）。
- ID の参照: **裸の ID**（`S-537`）。相対リンクは使わない。経路は規約で決まる（DS-1）ので、道具が ID → 経路を引ける。コードとテストの 1,271 件はもともと裸で、文書だけリンクにすると二重の書き方になる。相対リンクを使うのは README の索引（ディレクトリと文書を指すとき）だけで、DS-6 の確かめの対象。
- 仕様の節の参照: `§6.1` のまま（言語の仕様）。ツールの仕様は `tools.md §3.2`（コードのコメントは `spec/tools.md §3.2` と経路で書く。197 か所の置き換えは DS-4 のとおり）。
- 見出し: ID のファイルは `#` が一つ（ID と題）、本文の節は `##` だけ。`###` 以下を使わない（数千字のファイルに三段は要らない。grep で `^## ` だけ見れば目次になる）。読み物（仕様の章、規則、共通の設計）は今の階層のまま。
- 日付と発言者: 欄には置かない（欄は「今の状態」）。本文の `## 経緯` か `## 判断` の箇条に `- 2026-10-15 利用者: …` の形で書く（履歴の意味を持つ場所。利用者 10-12 の方針）。日付は `YYYY-MM-DD` に揃える。規則と仕様には書かない（今の規則のまま）。
- 字の規則: 日本語と ID の間の空白、200 字程度の改行、表は例外、は今のまま。欄の行は一行で書く（200 字を超える値は本文へ）。
- 副作用: 欄の値に改行を入れられない。入れ子の欄が作れない（要らないと見る）。
- 移行の量: 形の定義だけ。各 ID の切り出しは F4〜F6 の側で数える。

## F10 異論・リスク・単純な代替

- 利用者の項目への異論は無い。4 つの形は上で全て決まる。ただし「報告表」を 担当の報告 と読むなら、F5 の「残すとすれば」の `history/reports/` を足すだけで済み、形の規則は要らない。
- リスク 1: S の `担う作業` の逆引きで、rework の「S-102 の構文」「D-02 の改定」のような修飾が落ちる。移行の道具は修飾を本文の経緯に写し、欄には ID だけを置く。往復の確かめ（DS-9）は「ID の集合が一致」で見る。
- リスク 2: 計画 §2 の S の表は、変更点 §4 と文が違う（§2 は論点と経緯、§4 は決定と理由の要約）。切り出しでは §2 を論点・経緯に、§4 を決定・理由に当てるが、両方に無い S（§4 は 133 件だけ）は親が決定の欄から理由を分ける手作業になる。量が多ければ、移行では §2 の決定の欄を `## 決定` にそのまま置き、理由の分離は読んだときに直す（完璧を求めない）。
- リスク 3: `R` を持ち越しの受け皿に広げると R の数が増える。番号は道具が振るので費用は小さいが、「レビューの指摘」と「見つけた問題」の違いは消える（DS-1 の定義ですでに後者）。
- リスク 4: 欄の値を一行に限ると、`見つけた` のように長くなりがちな欄が切り詰められる。欄は要約、本文は全文、と README に書く。
- もっと単純な代替: 欄の箇条の代わりに、1 行目の見出しの後ろに状態だけを置く案（`# S-537 ✅ …`、今の表の `✅` の延長）。読む道具は最小になるが、`仕様の節` と `担う作業` が本文の中に埋もれ、逆引き（票の生成、§ ごとの決定の一覧）が grep に戻る。手順 1 の問題（ID を探す grep、票への読み集め）を解かないので採らない。
- もう一つの代替: YAML front matter。上の F1 の理由（`:` の衝突、`yaml` モジュール無し、二つの文法）で採らない。GitHub の表示が整う利点はあるが、この文書群は端末と vim と Read ツールで読まれる。
