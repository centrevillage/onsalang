### (A) 整形を `docs.py fmt` に入れるか、別の `wrap.py` にするか（確信: 低。親の案でよい）

### (B) 欄の定義を README の表から道具が読むか、道具が表を持ち README との一致を gate が確かめるか（DT-1。確信: 中。私は代替の方を推す）

- 親: README の `| キー | 形 | 値 | 要る | 意味 |` を道具が読む。正本が一つで済み、欄を足すのは README の一行。
- 私（親の代替）: 欄の表は `repo.py` に持ち、README の表は人のための写しとして置き、`check` が「README の表と道具の表が同じか」を確かめる。
- 事実として、どちらも README の表を読むコードは要る（一致の確かめにも同じ読み手が要る）ので、作る量は同じ。違うのは、食い違ったときにどちらが正しいとされるか:
  - 親の案: README の表の崩れ（列の数、`値` の欄の区切りの書き方 `OPEN / DECIDED` と `OPEN、DECIDED`）が、全ファイルの頭の欄の失敗として出る。README の編集だけで gate の挙動が変わり、自己テストを通らずに変わる。自己テストの作り物にも README が要る。
  - 代替: 崩れは「README と道具の表が違う」の 1 行で出る。欄を足すのは `repo.py` の一行 + README の一行の二か所（gate が揃いを強いる）。
  - どちらでも、関係の意味（`amends` と `amended_by` の対称、`tasks` が全て DONE なら決定は OPEN でない、`fix`、`doing`、`depends`）はキー名ごとにコードに書くほかない。README を正本にしても「一つ」になるのはキー・形・閉じた値までで、関係の規則はコードに残る。この点で親の「正本が一つ」の利点は部分的。
- 選ぶと変わること: 親の案は欄の変更が文書の編集だけで済む（利用者が vim で README を直せば効く）。代替は変更に道具のコミットが要るが、gate の失敗の読み方が単純で、自己テストが欄の表を守る。利用者の「規則と道具は別のコミット」の方針では、欄の定義を文書の側に置く親の案の方が「欄の変更 = 文書のコミット」で素直、という見方もできる。
