# 第 2 段への追加: 責務の範囲の基準（利用者の求め）

求められているのは、編集の一つ一つを、意味の判断なしに「してよい / 報告だけ」に分けられる基準。候補 (1)〜(4) と組み合わせを比べ、境目の編集を分類し、割れる所が残るかを書く。

## 候補の定義（判定の問いの形にする）

- (1) 意味の基準: 「直した後に、読み手が受け取る事実（決定・規則・仕様・状態・関係）が同じか」。
- (2) 確かめの基準: 「その編集が正しいことを道具（往復、`check`、`fmt --check`、`tools/moved_only.py` の類）が確かめるか」。
- (3) 源の基準（出所で判定）: 「書く字の源は、リポジトリに既にある字（移す・写す）、親の票か親の書いたファイルの字（そのまま）、道具の出力（`fmt`、`set` の正規形、`path` の経路）のどれかか。消す字は、正本に同じ字で残るか、親が票で名指ししたものか」。担当は字を起こさない・消さない。
- (4) 場所の基準: 「書いてよいファイル・欄か」（例: `decisions/`・`issues/`・`tasks/` の頭の欄と本文、README、ファイルの移動は可。`spec/` の文、`rules/` の文、`.claude/agents/`、コード・テスト・`tests/pending.toml` は不可）。

## 境目の編集の分類

○ = してよい、× = 報告だけ、△ = 基準だけでは決まらない（判断が要る）。

|---|---|---|---|---|---|

## 基準ごとの評価（判定が割れる所が残るか）

- **(1) 意味**: 判断そのもの（c・e・k・n が △）。「迷えば報告」を足しても、迷わなかった誤判定は防げない。意味の判断なしに決める、という求めを満たさない。
- **(2) 確かめ**: 問いは機械的に見えるが、二つの弱さがある。(ア) 範囲が「今ある道具」で決まり、道具が無い編集（f・m）は全て報告になる。(イ) 「`check` が通る」は「編集が正しい」と同じでない（d・e は `check` が通っても誤りうる）。つまり「確かめる」の意味づけに判断が残る。確かめの**要件**としては良いが、範囲の**基準**には足りない。
- **(3) 源**: 問いは「この字はどこから来たか」で、diff と票を見れば決まる（判断なし）。割れる所は、値は本文にあるがキーや状態への意味づけが要る d・e と、ラベルの字の源が曖昧な m。これらは「親が票で規則か対応表を書けば源が親になる」で解け、票に無ければ報告、と機械的に落ちる。弱さは、源が親なら何でも書けること（p のように利用者の了承の流れを飛ばせる）と、「そのまま」の幅（改行・字下げ・句読点の差を許すか）を決めておく必要があること。
- **(4) 場所**: 問いは機械的（WIP のコミットが触れたファイルの一覧で親が確かめられ、gate にも入れうる）。だが場所だけでは、許した場所の中で c・g・i・k が全て通る（緩すぎ）。一方で a・o（移行で `spec/`・`rules/` を動かす）が不可の場所に当たる（厳しすぎ）。外枠には向くが、単独では範囲の基準にならない。
- **組み合わせ (3) ∧ (4)、確かめに (2)**: (3) が「何を書いてよいか」を字の出所で決め、(4) が「源が親でも担当が書かない場所」（規則・仕様の文、定義、道具が読む README の表、コードとテスト）を外枠で塞ぎ、(2) は「道具で確かめられる編集は確かめを必須にする」という手順の要件に回す。残る △ は、票が規則・対応表を書いたかどうかで ○/× に落ちるので、担当の側の判断は無い。

## 推奨

**(3) 源の基準を範囲の基準にし、(4) を外枠、(2) を確かめの要件にする。** 確信 中〜高（判定の機械性について高、利用者が f（親の文の記録の書き込み）を範囲に入れたいかは利用者の判断で、入れなくても基準の形は変わらない）。

- 利点: 「字の出所」は diff と票で確かめられ、親のレビューが「追加された行は基のコミットか票か道具の出力にあるか、消えた行は正本か票にあるか」の機械的な問いになる（`tools/moved_only.py` の考え方の延長。道具にするかは件数を見てから）。10-10 の提案の「親の指示で決定の組の反映」も、手順 5 の「事実を変えない」も、同じ一つの基準に入る（f は ○、g は ×）。
- 代償: 言い換えの写し（c）と、本文からの欄の補い（d・e）が、票に規則が無い限り全て親に戻る。移行では件数が多いので、移行の道具が機械の規則で一括して行い（源は票に書いた規則）、残りを一覧で親に出す形（DT-8・DF-4 の既決と同じ）が要る。日々の点検では件数が少ない見込みなので、親の手間は小さい。
- 決めておくこと（割れる所を無くすため）:
  - 「そのまま」の幅: 改行・字下げ・句読点・空白の差は許す（`fmt` が直すため）。語の差は許さない。
  - 「親の票」の範囲: 票か親が scratchpad に書いたファイルの字だけ。会話の返事で渡すときは、親が控えのファイルに書く（`leader-rules.md` 2.6 の「返事は会話にしか残らないので控える」と同じ）。
  - 道具の出力が源になるのは、`fmt`・`set`・`amend`・`new` の雛形・`path` の経路・移行の道具（票が指すもの）に限る。

## 規則の文の案（第 1 段の 5.5・5.6 を置き換える）

```markdown
5.5 文書の点検と移行の担当が書く字は、リポジトリに既にある字（移す・写す）、親の作業票か親が書いたファイルの字（そのまま。改行・字下げ・句読点・空白の差は許す）、道具の出力（`docs.py` の `fmt`・`set`・`amend`・`new`・`path`、作業票が指す移行の道具）のどれかに限る。
  消す字は、正本に同じ字で残るものか、親が作業票で名指ししたものに限る。字を起こさない。本文の記述から頭の欄を補う、ラベルを置き換える、持ち越しを振り分ける、は親が作業票に規則か対応表を書いたときだけ行い、無ければ案を報告する。
5.6 源が親でも書かない場所: 仕様・規則・README の規範の文（移す・経路の直し・整形は除く）、担当の定義、道具が読む README の欄の表、コード・テスト・`tests/pending.toml`・SPEC-GAP の印。見つけたことは両側の引用と推奨を付けて報告し、決めるのは親（規則と仕様は利用者）。
5.7 移す・分ける・整形は、往復の確かめと `docs.py check` が通ったものだけを置く。通らなければ戻して報告する。
```
