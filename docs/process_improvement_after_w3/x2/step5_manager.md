## 0. 結論

- 文書の点検と移行の担当 `onsa-docs` を置く。受け持つのは、道具が確かめられない意味の整合の点検（報告）と、移行と構造の変更の実作業と、範囲の基準（DM-2）に入る直し。
- **責務の範囲は「書く字の出所」で決める**（DM-2）。担当は字を起こさない。書いてよいのは、リポジトリに既にある字を移す・写すとき、親の作業票の字をそのまま置くとき、道具の出力を置くときだけ。それ以外は報告する。

## DM-1 要否: 道具が確かめられることと、確かめられないこと

## DM-2 責務の範囲の基準: 書く字の出所

**基準**（範囲）: 担当が書く字と消す字の出所で決める。担当は字を起こさない。
- 書く字は、次のどれかに限る。
  - リポジトリに既にある字（移す、写す）。
  - 親の作業票か親が書いたファイルの字（そのまま）。会話の返事で渡すときは、親が控えのファイルに書いてから渡す。
  - 道具の出力（`docs.py` の `fmt`・`set`・`amend`・`new` の雛形・`path`、作業票が指す移行の道具）。
- 消す字は、正本に同じ字で残るものか、親が作業票で名指ししたものに限る。
- 「そのまま」「同じ字」は、改行・字下げ・句読点・空白の差を許し、語の差は許さない（`fmt` が直す差だけを許す）。
- 本文の記述から頭の欄を補う、ラベルを置き換える、持ち越しを振り分ける、状態を合わせる、は親が作業票に規則か対応表を書いたときだけ行う。無ければ案を報告する。

**外枠**（場所）: 出所が親でも、担当が書かない場所。
- 仕様・規則・README の規範の文（移す・経路の直し・整形は除く）、担当の定義、道具が読む README の欄の表（DT-1）、コード・テスト・`tests/pending.toml`・SPEC-GAP の印。規則の文は親が提案し利用者が了承して親が書く（今のまま）。

**確かめの要件**: 移す・分ける・整形は、往復の確かめと `docs.py check` が通ったものだけを置く。通らなければ戻して報告する。

**判定の例**（○ してよい、× 報告だけ、親 = 親が作業票に書いたときだけ○）:

| 編集 | 判定 | 理由 |
|---|---|---|
| 移す・分ける（移行） | ○（往復が通ったもの） | 既にある字 |
| 同じ字の写しを消して、正本の ID で指す | ○ | 消す字が正本に同じ字で残る |
| 言い換えの写しを ID で指す | × | 消す字が正本に同じ字で無い（差に意味が隠れうる）。「重なり」として両側を引用して報告 |
| 経路・番号の参照の直し、整形 | ○ | 道具の出力と経路の規約 |
| 本文の「W3-13 で揃える」を頭の欄 `tasks` に写す | 親 | どのキーに写すかが判断 |
| 本文の日付付き「決定:」から `status`・`decided` を埋める | 親 | 状態の意味づけが判断（移行の ✅ と `status` の食い違いは、道具の一覧を親が決めて当てる） |
| 決定の記録を、親の票の文のまま置く | ○（親の字） | 2026-10-10 の利用者の案の「親の指示で反映」はここに入る |
| 親の要点から決定の文を起こす | × | 字を起こす |
| 持ち越しの振り分け（移行） | 親 | 担当は案を報告し、親の一覧を当てる |
| 古い記述に印を付ける・消す | × | 「古い」という事実を作る。根拠の ID かコミットを付けて報告 |
| ラベル・見出しを形式に揃える | 親 | 票に対応表（古い → 新しい）があれば○ |
| 規則の文を親の文で直す | × | 外枠（規則は親が書く） |

- この基準で、2026-10-10 の利用者の提案（親の指示で反映、整理の判断は親）と、手順 5 の観点（事実を変えない、リーダーの責務と干渉させない）が一つに入る。判断は全て親か利用者で、担当は出所のある字だけを置く。
- 親のレビューは機械的な問いになる: 足した行は基のコミットか票か道具の出力にあるか、消した行は正本か票にあるか（`tools/moved_only.py` の考えの延長。道具にするかは件数を見て決める）。
- 決定の記録を日々担当に任せるかは、この基準とは別の運用の判断。新しい構造では記録は決定のファイル一つの Edit と `set`・`amend` になるので、日々の記録は親が書き、担当に渡すのは移行と束の反映のときにする（往復が一つ増えるため）。

## DM-4 確かめの進め方（範囲の上限）

1. `docs.py check` を回す。落ちていれば、その出力を報告して止める（道具が先）。
2. 範囲の一覧を作る: 票の差分の範囲の文書と ID の一覧に、`docs.py show --relations` が出す一段の先（決定・作業・問題）と、指す仕様の節と規則を足す。一覧を報告の頭に書く。一覧が上限（決定 30、作業 15、その他の文書 10）を超えるときは、そこで止めて親に票を分けるよう報告する。
3. 一覧のファイルを一度ずつ読む。決定ごとに `show` で本文と関係を読み、`spec` の節の文と決定の文を突き合わせる。`back` の先（R・W・他の決定）と、理由の向きと論点の重なりを見る。同じ節を持つ既決の決定は、題と「空白」の頭だけを並べて重なりの候補を絞り、同じ論点に見えたときだけ両方を読む。
4. 現在形の実装の記述（「今の fmt は」など）は、OPEN の決定と OPEN の R だけで見る（DECIDED・DONE は記録なので古くてよい）。
5. 矛盾の疑いを確かめるときだけ、二段目の先を読む。二段目は 10 ファイルまで。
- 止まる保証: 読むのは手順 2 で決めた有限の一覧と、二段目の 10 ファイルまで。読みながら一覧を広げない（広げたくなったら「見なかったもの」に書く）。文脈が 20 万トークンに近づいたら新しい項目を始めず、残りを「点検しなかったもの」として報告する。

## DM-5 報告の形（計画 §8.4 の後に足す）

```markdown
## 文書の点検 <範囲の名前> の報告

- 範囲: <基>..<先>、ID <…>。読んだファイル <数>（一覧は末尾）。`docs.py check`: PASS。点検しなかったもの: <…>（理由）
- 見つけたこと（一件ずつ）:
  - <種類: 矛盾 / 退行 / 重なり / 古い記述 / 未反映 / 関係の抜け> <ID と経路:行>
    - 引用: 「…」（<ID か §>） / 「…」（<ID か §>）
    - 経路: <`show` → `back` → … の辿り>
    - 直し: 直した（<差分の要約、字の出所、確かめ>） / 報告だけ（推奨: <…>、決める人: 親 / 利用者）
    - 確信: 高 / 中 / 低
- 道具の確かめの案: <機械で見つけられた形なら、どう確かめるか>
- 範囲の外で気付いたこと
- 読んだファイルの一覧
```

## DM-6 他の担当と親との境

- 親: 決定と記録を書く、ID の番号を振る、規則の文を提案する、点検の票を出す、担当の差分を読んで写す、報告の「報告だけ」を処理する（直す、R・S に登録、利用者に問う）、コミットする。登録と決定の瞬間の網（`leader-rules.md` 5.6）は親に残る。
- advisor: 正否の判断が割れたときに親が回す。担当は見つけて並べるまで。
- gap: 下書きの「決定済みで戻さないもの」は gap に残る。担当は記録の後の二つ目の網。
- impl・test・break: コードとテスト。担当はコードとテストに触れない。
- 点検の直し: 作業ツリーで編集し、WIP のコミット（`WIP: docs <範囲の名前>`）を置く。親は `tools/take.py patch` で写し、差分を読み、文書だけのコミットにする。

## DM-7 移行（手順 6）を受け持つ形

- DS-9 の (2)〜(6) の段ごとに一票。(1)（`repo.py` の経路の抽象）は道具の実装（U2）、(7) の規則の文の見直しは親が文を提案する。(7) のうち経路の直しと移すだけの部分は担当が受け持てる。

- 判断の要る段（持ち越しの振り分け、✅ と `status` の食い違い）は、担当が一覧と案を先に出し、親が決めた一覧を当てる（DM-2 の「親」）。
- 場所: 担当が動いていない区切りに主のツリーで行う（DS-9。数百ファイルの移動をパッチで写す往復を避け、往復の確かめをその場で回す）。親はコミットの前に主のツリーの差分を読む（判断を頼む項目の DM-E）。
- 移行の道具を誰が書くか（担当か実装の担当か）は手順 6 で決める。

```markdown
  本文の記述から頭の欄を補う、ラベルを置き換える、持ち越しを振り分ける、状態を合わせる、は親が作業票に規則か対応表を書いたときだけ行い、無ければ案を報告する。
- 出所が親でも書かない場所: 仕様・規則・README の規範の文（移す・経路の直し・整形は除く）、担当の定義、道具が読む README の欄の表、コード・テスト・`tests/pending.toml`・SPEC-GAP の印。
- 移す・分ける・整形は、往復の確かめと `docs.py check` が通ったものだけを置く。通らなければ戻して報告する。
- 点検の範囲は作業票の一覧と、そこから一段だけ辿った先。一覧が決定 30・作業 15・その他の文書 10 を超えるときは、親に票を分けるよう報告する。矛盾の疑いを確かめる二段目は 10 ファイルまで。読みながら一覧を広げない。
- 見つけたことは両側の引用と辿った経路と推奨を付けて報告する。決めるのは親（規則と仕様は利用者）。
- 点検の直しは作業ツリーで行い、WIP のコミットにする（2 章）。移行の段は、担当が動いていない区切りに主のツリーで行う。
```

**他に一言ずつ**（同じ規則を二か所に書かない）:
- `agent-rules.md` の頭と `leader-rules.md` 3 行目・1.1 の「5 つ」は、数を書かず「`.claude/agents/` の `onsa-*` の担当」にする（次に役が増えても古くならない）。役割の括弧の説明に「docs は `onsa-docs`」を足す。2 章の見出しを「作業ツリー（t、i、docs）」にする。
- 計画 §8.6 の「役割の担当」に一行: 「文書の点検と移行（`onsa-docs`）: 段の終わり、規則を改めた後、移行の各段、親が求めたときに、親が範囲を決めて呼ぶ。同時に動かす 4 体に数える。」。§8.4 の後に「文書の点検の報告」の形（DM-5）。
- `leader-rules.md` に一項（4 章）: 「文書の点検の担当の報告は、足した字と消した字の出所（基のコミット、票、道具の出力）を差分で確かめてから写し、文書だけのコミットにする。報告だけの指摘は、決定と派生の文の食い違いなら決定に合わせて親が直し、決定どうし・規則どうしの矛盾は利用者に出す。正否が割れれば助言の担当に回す。」

## DM-10 リスクと、もっと単純な代替

- **点検が新しい読み飛ばしを生む**: 担当が点検した範囲を、親が読まなくなる。親は直した差分を全て読む（文書の差分は小さい）。
- **字の出所の基準で、言い換えの写しと欄の補いが全て親に戻る**: 移行では件数が多いので、移行の道具が機械の規則で一括して行い（規則は票に書く）、残りを一覧で親に出す。日々の点検では件数が少ない見込み。
- **sonnet が微妙な向きの矛盾を見落とす**: 見落としは報告が減るだけで、誤った直しにはならない（直してよいのは出所のある字だけ）。W4 で収穫を測り、足りなければ opus にする。
- **収穫が少ない**: W4 の最初の数回で見つけた件数と費用を数え、空振りが続けば時機を段の終わりと構造の変更だけに減らす（規則に書かず、票の運用で）。
- **移行の段で主のツリーを占める**: DS-9 の前提どおり担当が動いていない区切りで行う。移行は一度きり。
- **もっと単純な代替**: DM-1 の (b)（親が段の終わりに点検）や (c)（advisor が点検、直しと移行は親か impl）。移行の 7 段の実作業を受け持つ役が要るので (a) を推す。差は大きくないので、役を増やしたくなければ (c) でも成り立つ。
