## 1. W2-04 の直しが待つもの

### S-222 コンパイル時の評価の呼び出しの深さ

- **論点:** §12.5「インタプリタ（`onsa test`）は呼び出しの深さに上限を持ち、超えると panic する。上限はビルドの種類によらず同じである」。§6.6 はコンパイル時の評価（定数式、`const` の初期化式、`@param` の値）の panic を、その式の位置の E0419 とし、§11.3 は定数のクロックの式を同じ評価器で評価する。コンパイル時の評価に呼び出しの深さの上限があるか、超えたら E0419 か、`onsa test` と同じ上限か、深さをどこから数えるか（`const` を読んだ呼び出しの深さを引き継ぐか）が書かれていない。`rt` でない `fn` は再帰できる（§10）ので、`const DEEP: U32 = dive(10_000_000)` は書ける。
- **今の実装:** HEAD（深さは 50 まで）: `const OK: U32 = dive(50)` は通る。`const BAD: U32 = under(5)`（再帰の戻りで `1 - 2` が溢れる）は、`onsa check` が 0 件で終了コード 0、`onsa test` はそれを読んだテストの失敗（「integer overflow in `1 - 2` (U32)」）、それを読む関数を export した `onsa build` は「E0200: the C backend does not support this `const` initializer (evaluated at build time)」で、E0419 はどこからも出ない。止まらない初期化式（`while i > 0 { i = i *% 1 }`）は `check` を通り、`onsa test` と `onsa build` は 15 秒で終わらない。W2-04 の作業ツリー（未コミット、上限 2000）について W2-04/b が記録したこと: 深さを `const` を最初に読んだ呼び出しから数えるので、同じ `const` の成否がテストの順と `--filter` で変わる。`test` の本体を 1 段と数え、ビルドの評価は 0 段から数えるので、`dive(1999)` は `onsa test` で失敗し `onsa build` で通る。`const` が `const` を読む鎖に、深さの数えもスタックの安全網も無い。
- **案:**
  - (a) `onsa test` と同じ一つの上限。コンパイル時の評価の一つ一つ（一つの初期化式、一つの定数のクロックの式、一つの `@param` の値）と `test` の本体を評価の入口とし、入口から入れ子になった呼び出しの数を深さとする。`const` の値を読むのは呼び出しではない（その `const` は別の評価で、0 から数える）。超えると、コンパイル時の評価ではその式の位置で E0419（§6.6 の panic）、テストでは panic。
  - (b) コンパイル時の評価だけ、別の小さい上限（C++ の 512 のような値）にする。コンパイルの時間と IDE を軽く保つため。
  - (c) コンパイル時の評価には上限を置かず、スタックが尽きたら内部エラー（終了コード 101）にする。
  - 値の置き場所: (v1) 仕様に数を書く（S-183 の 256 と同じ考え）。(v2) コンパイラの版ごとに一つの値（R-05 のとおり実測で決め、ビルドの種類と環境によらず同じ）で、仕様には書かない。
- **他言語:**
  - Apple clang 21: `constexpr int C = dive(512)`（入れ子の呼び出し 513 回）は「error: constexpr variable 'C' must be initialized by a constant expression」と note「constexpr evaluation exceeded maximum depth of 512 calls」（`dive(511)` は通る）。他の評価の失敗と同じ誤りで、深さは note で示す。止まらないループは note「constexpr evaluation hit maximum step limit; possible infinite loop?」。
  - gcc-15: `dive(511)` は通り、`dive(512)` で「error: 'constexpr' evaluation depth exceeds maximum of 512」。ただし `A = dive(500)` の後に `B = dive(1000)` を置くと通り、順を逆にすると誤りになる（呼び出しの結果を使い回すため。`-fconstexpr-cache-depth`）。clang はどちらの順でも誤り。ループは「'constexpr' loop iteration count exceeds limit of 262144」。
  - rustc 1.94.1（確かめ）: `const B: u32 = dive(200)` で「error[E0080]: reached the configured maximum number of stack frames」。主の位置は初期化式の呼び出しで、note で連鎖を示す。溢れも同じ E0080。長いループは「error: constant evaluation is taking a long time」（既定で誤りになる lint）。
  - 定数を読む側の深さは足されない: rustc で `A = dive(100)` を深さ 100 で読む `B = user(100)`、clang と gcc で `A = dive(500)` を深さ 500 で読む `B = user(500)` は、どれも通る。
  - C++ の [implimits] は最小値の目安として「再帰する constexpr の呼び出し 512」「一つの定数式の中で評価する完全式 1,048,576」を挙げる（https://eel.is/c++draft/implimits）。clang の深さの既定の 512 はこれと同じ。
  - 実行時の上限: Python 3.14.5 は数で決まる（`sys.getrecursionlimit()` が 1000 で、999 段目の呼び出しで RecursionError。本体の式の入れ子を 4 段深くしても同じ）。Node 25.9.0 はスタックの量で決まる（`1 + dive(n - 1)` で 15,541 段、引数と局所変数の多い関数で 8,879 段）。
- **推奨と理由:** (a)。値は (v2) から始め、W9-03 で (v1) にするかを決める。確度: 中（数え方と E0419 は高）。
  - §11.3 は、同じ式を `const` に分けても分けなくても同じビットになると約束する。(a) はこれを失敗する場合にも広げる。(b) では `assert dive(1500) == 1500` がテストで通り、`const D: U32 = dive(1500)` がコンパイルで落ち、同じ呼び出しが置き場所で合否を変える。上限という一つの概念が一つの数を持つので、仕様と `onsa explain` の文も一つで済む。
  - 深さの上限で止まるのはプログラムの誤り（深すぎる再帰、止まらない再帰）で、直すのは式である。§6.6 の E0419 の直し方（式か値を直す）と同じなので、新しいコードは要らない。clang・gcc・rustc も、深さの超過を他の評価の失敗と同じ誤りにしている。(c) の内部エラーは、修復ループにコードの誤りでないと伝えてしまう（§18.2）。
  - 評価ごとに 0 から数えるのは、コンパイル時の値は読む場所によらないからである（§11.3 の表で定数はコンパイル時）。読んだ側の深さを引き継ぐと、同じプログラムの合否がテストの順や評価の順で変わる（W2-04/b の 1。gcc で宣言の順が効くのも同じ種類）。
  - W2-04 の直しで決める必要がある部分:
    1. 評価の入口（`test` の本体、`const` の初期化式、定数のクロックの式、`@param` の値）は 0 段で、深さは入口から入れ子になった呼び出しの数である。`onsa test` とビルドで同じ数え方にする（W2-04/b の 2）。
    2. 評価の途中で `const` を読むのは呼び出しではない。その `const` の評価は 0 段から始める（W2-04/b の 1。評価の前後で深さを保存して戻すか、テストの前に全ての `const` を評価する）。
    3. `const` が `const` を読む鎖は深さに数えない（数えると正しいプログラムを落とす）。W9-03 が依存の順に評価して再帰を無くすまでは、鎖の再帰にスタックの安全網を置き、尽きたら内部エラーにする（W2-04/b の 3）。
    4. 末尾の呼び出しも一段に数える（§7 は末尾呼び出しの最適化を保証しない。W2-04/t が `recursion_deep.onsa` で空白として挙げた点）。

### S-228 const 引数の負の値

- **論点:** §4.5「定数式は、整数のリテラル、定数を指す名前…、算術の演算子（`+ - * / %`）、括弧からなり、型は `U32` である（`U32` でない定数は E0401…）」。前置の `-` が定数式に書けるかが無い。`Ring[F32, -1]` は、文法の外と読めば E0417、リテラルの範囲外と読めば E0408、`U32` の否定と読めば E0401（§3.4「符号なし整数に単項の `-` は無い（E0401）」、§4.7「符号なしの型の `-1` は E0401」、S-184）、`0 - 1` の評価と読めば E0419 になる。
- **今の実装:** 同じ `-1` のコードが位置で違う。
  - `Ring[F32, -1]` は E0408「a const argument must fit in `U32`」。`Ring[F32, -0]` は通る。
  - `let x: U32 = -1`、`let x: U32 = -0`、`const N: U32 = -1` は E0401「`-` on the unsigned type `U32`」。
  - `[F32; -1]` と `[0.0; -1]` は E0200（長さの式は未対応）。`delay(x, -1, 0.0)` と `par i in -1..2` は E0808。
  - `Ring[F32, -(1)]`、`Ring[F32, -ONE]`、`Ring[F32, 0 - 1]` は E0002（今の構文解析器は const 引数に「`-` とリテラル」と名前しか読まない）。
  - 既存のテスト `tests/spec/negative/const_args.onsa:19` は `Ring[F32, -1] //~ E0408`（S-184 より前に書いたもの。作業ツリーも同じ）。
- **案:**
  - (a) E0401。定数式は普通の式と同じ規則で型を検査し（期待型は `U32`）、前置の `-` も書ける形に含める。`U32` に前置の `-` は無いので、`-1`、`-0`、`-(1)`、`-N` は位置によらず E0401。`0 - 1` は値の溢れで E0419（§4.5 の既存の文）。
  - (b) E0417。前置の `-` を定数式の文法に入れない。
  - (c) E0408。`-1` を `U32` の範囲外のリテラルとする（今の実装）。
  - (d) E0419。`-1` を `0 - 1` の評価の溢れとする。
- **他言語:** rustc 1.94.1 は `Ring<-1>`（`const N: u32`）を E0600「cannot apply unary operator `-` to type `u32`」、`Ring<{ 0 - 1 }>` を E0080（定数の評価の溢れ）とし、二つを分ける。clang 21 の C++20 は `Ring<-1>`（`template <unsigned N>`）を「non-type template argument evaluates to -1, which cannot be narrowed to type 'unsigned int'」とし、`Ring<0u - 1u>` は通す（符号なしはラップ）。Swift 6.3.1 の値の総称の引数（`InlineArray< -1, Int>`）は `Int`（符号付き）なので比べられない。
- **推奨と理由:** (a)。確度: 高。
  - `-1` は定数で、(b) の「定数式でない」は誤りの中身と合わず、直し方も E0417 の「`const` の初期化式に分ける」ではない。(c) は S-184 の「符号なしは E0401」と食い違い、(d) は §3.4 が「型だけで誤りと決まる」とした型の誤りを値の誤りとして扱う。
  - `const N: U32 = -1` は既に E0401 で、`let`・`const`・const 引数・配列の長さで、同じ書き方が同じコードになる。符号なしの規則を位置で分けない。
  - 符号付きの const パラメータを将来足しても、(a) は文法を変えずに済む。(b) は文法を変え、`U32` の位置の E0417 を E0401 に付け替える。
  - あわせて決めること: 符号なしの `-0` も E0401（§3.4 は演算子が無いと言い、値を見ない）。§4.7 の例に `-0` を足す。今の実装の `Ring[F32, -0]` は通る。
  - あわせて決めること: 遅延線の長さと `par` の端（§11.4、§11.5。どちらも定数式）の `-1` も E0401。E0808 は値の範囲（`N = 0`、空の範囲）だけ（S-132）。
- **影響:** §4.5 の定数式の文（前置の `-` の扱いと例）、§4.7 の符号なしの例。E0401、E0408、E0417、E0419、E0808。W2-06（今の const 引数の検査）、W5-08（定数式の文法と型）、W7-02（flow の定数式のコード）。テスト: `negative/const_args.onsa:19` の期待値（今は E0408）は、(a) なら E0401、(b) なら E0417 に改める。足す否定例: `[F32; -1]`、`Ring[F32, -0]`、`Ring[F32, -(1)]`、`Ring[F32, -ONE]`、`delay~(x, -1, 0.0)`、`par i in -1..2`、`Ring[F32, 0 - 1]`（E0419）。
- 回答:

(a)でよい。そのほかの記載内容も問題なし。

### S-227 括弧で囲んだ負のリテラルの否定 `-(-2147483648)`

- **論点:** §4.7「整数リテラルに直接付いた前置の `-` は値に含めて検査し、間の括弧は見ない（`I8` に `-128` と `-(128)` は書け…）」。§3.1「前置演算子を重ねるには括弧が要る（`-(-x)`、E0012）」。`-(-2147483648)` の外側の `-` とリテラルの間には、括弧と内側の `-` がある。「直接付いた」が括弧だけを挟む場合か、`-` の連なりも含むかが読めない。前者なら外側は値の否定で、§3.4 の `-a`（`a` が `MIN` なら panic）。後者なら値は `2147483648` で `I32` の範囲外（E0408）。
- **今の実装:**
  - `-(-2147483648)`（`I32`）と `-(-128)`（`I8`）は検査を通り、`onsa test` で内部エラー（Core の検証器の「literal 2147483648 out of range for I32」、終了コード 101）。降下が二つの `-` をリテラルに畳む（R-03 の `-(I32.MIN)` と同じ原因）。`const K: I32 = -(-2147483648)` も同じ内部エラー。
  - `-(-5)` は 5、`-(-127)`（`I8`）は 127。`fn e(x: I32) -> I32 { -(-x) }` の `e(I32.MIN)` は実行時の panic（文面は「integer overflow in `--2147483648`」）。
  - `- -2147483648` と `--2147483648` は E0012（候補は `-(-2147483648)`）。`0 - (-2147483648)` と `0 - -2147483648` は検査を通る。本体の `2147483647 + 1` と `1 / 0` も実行時の panic（本体の式は畳み込まない、W9-03）。
  - パターンの `-(-1) =>` は E0002（文面が「float literals cannot be patterns」で誤り）。
- **案:**
  - (a) 値の否定と読む。リテラルの値に含める `-` は、被演算子が括弧を除いて整数リテラルそのものであるものだけ。`-(-2147483648)` は、内側の `-2147483648`（`I32` に収まる）を外側の `-` が否定する。溢れの段は、関数の本体では実行時の panic（§3.4）、`const` の初期化式と `@param` の値ではコンパイル時の評価の panic で E0419（§6.6）。`U32` の定数式では内側の `-` で E0401（S-228）。`-(-1): U32` も内側で E0401。パターンの `-(-1)` はリテラルのパターンでないので E0002。
  - (b) `-` の連なりもリテラルに畳む。`-(-2147483648)` の値は `2147483648` で、どこに書いても型の段で E0408。`-(-1): U32` は値が 1 で通るので、§3.4 と合わせるには「符号なしでは `-` の数によらず E0401」の規則が別に要る。パターンの `-(-1)` は 1 と読める。
  - (c) (a) に加え、本体の中の必ず panic する定数だけの式を検査で誤りにする。`-(I32.MIN)`、`127 + 1`（`I8`）、`1 / 0` も同じ扱いにしなければ一貫しない。
- **他言語:** 読みが分かれる。Swift 6.3.1 は `-(-2147483648)`（`Int32`）を「arithmetic operation '0 - -2147483648' (on signed 32-bit integer type) results in an overflow」とし、(a) の読みで、定数の畳み込みによりコンパイル時に誤りにする（`127 + 1`（`Int8`）も同じ形の誤り。`-(128)`（`Int8`）は「integer literal '128' overflows」）。`UInt8` の `-(-1)` は誤り。rustc 1.94.1 は `-(-2147483648)`（`i32`）と `-(-128)`（`i8`）を「literal out of range」（deny の lint）とし、(b) の読み（二つの否定が打ち消す）。`u8` の `-(-1)` は E0600。C は負のリテラルを持たず、`-(-2147483648)` は `long` の 2147483648 で、clang 21 は `int32_t` への変換に `-Wconstant-conversion` の警告を出し、gcc-15 の `-Wall -Wextra` は何も言わない。
- **推奨と理由:** (a)。確度: 高。
  - 被演算子の値が同じ `I32.MIN` になる `-(I32.MIN)`、`-LOW`、`-m`、`0 - (-2147483648)` は全て実行時の panic で（§3.4、R-03、作業ツリーの `neg_min.onsa`）、(a) だけがこれと揃う。(b) では `-(-2147483648)` が E0408、`0 - -2147483648` が実行時の panic になり、`-x` と `0 - x` で段が分かれる。
  - S-184 が括弧を見ない理由は、fmt が冗長な括弧を外しても合否が変わらないことだった。`-(-x)` の括弧は無いと E0012 になる括弧で、fmt は外さない（§3.1）。この形に S-184 の理由は及ばない。
  - (b) は `-(-1): U32` を通す（§3.4 と食い違う）か、符号なしだけの規則を足すことになり、規則が増える。R-03 の決定「畳むのは、ソースの数値リテラルに直接付いた `-` だけ」とも (a) が合う。
  - (c) はこの S の範囲を超える。必ず panic する定数だけの式をコンパイル時に誤りにするかは、`127 + 1`、`1 / 0`、`-(I32.MIN)` に共通の問いで、新しい S の候補にする（今の決定は「本体の式は畳み込まない」、W9-03）。(a) はその答えによらず成り立つ。
  - 仕様の文は「被演算子が、括弧を除くと整数リテラルそのものである前置の `-` は、値に含めて検査する」とし、例に `-(-128)`（内側の `-128` がリテラルで、外側は値の否定。`I8` では §3.4 のとおり panic）を足す。§7 のパターンの負の整数も同じ定義で、`-` は一つ。
- **影響:** §4.7 の S-184 の文（「直接付いた」の定義と例）、§7 のパターンの負の整数の括弧書き。E0408、E0419、E0401、E0002。W2-06（R-03 の畳み込みの修正）、W9-03（`const` の初期化式の評価）、W3 の構文の作業（パターンの E0002 の文面）。テスト: (a) なら作業ツリーの `semantics/neg_min.onsa` に `-(-2147483648)`、`-(-128)`（`I8`）、`-(-(2147483648))` の TESTFAIL と `-(-127) == 127` の正例を足し、`const K: I32 = -(-2147483648)` を E0419 の否定例にする（W9-03 まで実装待ち）。(b) なら `negative/literal_range.onsa` に E0408 の事例を足す。作業ツリーの今の期待値（`literal_min.onsa` の `-((2147483648))` は内側だけの形、`neg_min.onsa` は名前の否定）はどちらの案とも矛盾しない。
- 回答:

(a)で良いと思いますが、コンパイル時に計算する関数の結果は検査不能になりますか？
```
const v: U32 = constfunc()
```
リテラルと定数で扱いが同じなのか違うのか、整理して教えてください。

### S-226 頭だけが決まった型を対象にする操作

- **論点:** §4.7「次の操作は、左辺（対象）の型がその時点で解決済みでなければならない（E0420）: フィールドアクセス…、`match` の対象、`?` の対象、関数値の呼び出し」「リテラル以外の型変数（`let x = None` の `Option[T]` の `T`、`Buf.zeroed(4)` の要素の型）が関数の終わりに残れば、その式の位置に E0406」。対象の型の一番外の構成子（以下「型の頭」。`Option`、`Buf`、struct の名前、配列、タプル、関数型）が決まり、型引数に型変数が残る型（`Option[?T]`、`Buf[?T]`）が「解決済み」かが読めない。`match none() { Some(_) => 1, None => 0 }` は、解決済みでなければ `none()` に E0420、解決済みなら関数の終わりに `none()` に E0406。`Buf.zeroed(4).len()` は、`.len()` の受け手に E0420 か、`Buf.zeroed(4)` に E0406。
- **今の実装:** 型の頭だけで判定している（`crates/onsa_sema/src/body.rs` の `known` は、対象が型変数そのものかだけを見る）。
  - `Buf.zeroed(4).len()` と `let b = Buf.zeroed(4); b.len()` は検査を通り、`onsa test` で内部エラー「unresolved type」（R-03）。後の `take(move b)`（`Buf[F32]` を受ける）で決まる形は通り、正しく動く。
  - `let x = None; match x { Some(_) => 1, None => 0 }` も検査を通って内部エラー。腕の `Some(v) => v.round_f32()` は `v` に E0420。
  - リテラルの型変数を含む型: `let xs = [1, 2, 3]` の `xs.len()` と `xs[0]`、`let o = Some(3)` の `match o` と `o.unwrap_or(0)`、`xs.len()` の後で `[I64; 3]` に決まる形は、全て通って正しく動く。
  - 利用者の総称の `match none() {…}` は、`none()` の位置ですぐ E0406（S-174 が未実装）。
  - `let o = None; match o { Some(3) => 1, _ => 0 }` は、パターンの `3` が `T` を整数リテラルの型変数に結ぶ（後に `Option[F32]` で受けると E0401）が、既定の `I32` が当たらず内部エラー「unresolved type」。
- **案:**
  - (a) 「解決済み」は型の頭が決まっていること（対象の型が型変数そのものでない。リテラルの型変数も型変数）。型引数の中の型変数は後の文で決まってよく、関数の終わりに残れば作った式の位置に E0406（`none()`、`Buf.zeroed(4)`）。
  - (b) 「解決済み」は、リテラル以外の型変数を一つも含まないこと（リテラルの型変数は含んでよい）。`match none()` は `none()` に、`Buf.zeroed(4).len()` は受け手に E0420。
  - (c) (b) で、リテラルの型変数も含まないこと。`let xs = [1, 2, 3]; xs.len()` と `match Some(3) {…}` も E0420。
- **他言語:** rustc 1.94.1 は (a) と同じ形。`match none() { Some(_) => 1, None => 0 }` は `none()` に E0282、`zeroed(4).len()` は E0283（どちらも型が残った誤り）で、`let b = zeroed(4); b.len(); let c: Vec<f32> = b;` と `match none() { Some(3) => 1, _ => 0 }` は通る。Swift 6.3.1 は文ごとに解き、`switch none()`、`zeroed(4).count`、`case .some(3)` の `switch` を全て「generic parameter 'T' could not be inferred」とする（`switch nil` は「'nil' requires a contextual type」）。
- **推奨と理由:** (a)。確度: 中。
  - 操作に要るのは、どのフィールド・メソッド・列挙子かを選ぶための型の頭である。メソッドは型の頭と名前で一つに決まる（§6.2: 一つの `impl` が全ての具体化を覆い、具体的な型の `impl` は E0307、同じ型のメソッド名の重なりは E0304）ので、型引数を知らなくても選ぶものは変わらない。
  - 関数の呼び出しと演算子は、オペランドが未解決でも進める（§4.7）。(b) では、総称の関数 `count(b)` は通り、メソッド `b.len()` は E0420 になる。`v == None` は通り、`match v { None => … }` は E0420 になる。同じ対象への同じ問いが、書き方で分かれる。
  - (b) はリテラルの型変数を除く条件が要り、「解決済み」が二つの条件になる。(c) は `let xs = [1, 2, 3]; xs.len()` のような普通のコードを壊す。(b) は後で (a) に緩められるが、(a) を今選んでも後で壊れるものは無く、緩めて変わるのは誤りのコード（E0420 から E0406）だけである。
  - 第 2 期の `Map.new()` や `Array` も、作ってから要素の型が決まる（`var m = Map.new(); m.insert!(k, v)`）。(a) ならこの形を今と同じ一つの規則で扱える。
  - あわせて決めること: パターンの中のリテラルと列挙子は、対象の型引数と単一化する（`Some(3) =>` は `T` を整数リテラルの型変数にし、関数の終わりに `I32`）。`==` の被演算子と同じ扱い。
  - あわせて決めること: 頭で選んだメソッドの境界（`impl[T: Float] Buf[T]` のメソッドを `Buf[?T]` に呼ぶ）は、`T` が決まった時点か関数の終わりに検査し、E0416 は呼び出しの位置に出す。S-174 の総称の呼び出しの境界も同じ問いを持ち、仕様に書かれていないので、新しい S の候補（後で決まる型パラメータの境界の検査の時点と位置）。
  - 別の S にしてよい論点: 空の `[]` は、今の実装では期待型が無いとその場で E0420（§2.4「空の `[]` の型は期待型で決める」）。(a) では型の頭（長さ 0 の配列）が決まっているので、`let x = None` と同じく後の文で決めてよいかが問える。
  - （Fable の指摘）空の `[]` は、別の S にせず S-226 の決定に含める方がよい。(a) の定義（解決済み = 型の頭が決まっている）を書くと、`[]`（長さ 0 の配列）は自動的に「後の文で決めてよい」側に入り、§2.4「空の `[]` の型は期待型で決める」が定義の外の例外として残る。別の S にするなら、同じ回に決めて §2.4 と §4.7 の食い違いを残さない。E0406 の位置は「型変数を作った式」（`none()`、`Buf.zeroed(4)`、`None`、`[]`）と §4.7 に書く。
- **影響:** §4.7 の「その場で既知を要する操作」の文（「解決済み」の定義）と、§4.5 の S-174 の文の例。E0420、E0406、E0416。W2-06。テスト: 作業ツリーの `negative/infer_open_subject.onsa`（対象が型変数そのもの）はどの案でも E0420 のまま。頭だけが決まった形の事例は作業ツリーに無い。(a) なら `match none() { Some(_) => 1, None => 0 }` と `Buf.zeroed(4).len()` を `negative/infer_unresolved.onsa` に E0406 で、`let b = Buf.zeroed(4); b.len(); take(move b)` と `match o { Some(3) => 1, _ => 0 }`（`let o = None`）を `semantics/infer_generic_later.onsa` に正例で足す。(b) なら前の二つを `negative/infer_open_subject.onsa` に E0420 で足す。
- 回答:

(a)で良いと思います。rustに合わせましょう。

### S-225 補間を含む文字列のパターン

- **論点:** §7「リテラル: …`Str`（バイト列の等値）」。§2.4 は文字列に名前の経路の補間（`{x}`）を許し、補間を含む文字列は新しい `Str` を作るので `Alloc` を要するとする。R-03 は補間を含む文字列のパターン `"a{x}b" =>` をエラーにすると決めたが、コードが仕様に無い。パターンに書けない形の既存の割り当ては、浮動小数のリテラル・`..`・書けない型の定数・`-LIMIT` が E0020（候補はガード、S-109、S-185）、`@` 束縛が候補の有無で E0020 か E0002（S-186）。`panic` の引数の補間は E0417（§9.2）。第 1 期の `Str` の出番は `test` の名前、`panic` の引数、`@param` の文字列のキーで、`Str` の値の降下は E0200（第 2 期）。

## 5. 浮動小数（W2-01 のテストベクトル）

S-207 は、S-208 の `abs` の 0、S-212 の `f = dc - k` の 0 の符号の前提になる。S-207〜S-209 はベクトルに保留の節があり、決まれば保留を外して生成し直す（今の実装は保留の 1376 行の全てで IEEE の値と一致した）。S-210〜S-212 は保留の節が無い（計画の行は「`held-S210` の節」などと書くが、生成のプログラムは該当する演算を表から外している。各項目の「影響」）。

### S-207 結果が 0 のときの符号

- **論点:** §3.4 の浮動小数の表は「数学的な結果を、最近接偶数（roundTiesToEven）で型に丸めた値」とだけ書く。数学的な結果が 0 のとき（ちょうど打ち消す和と差、0 との積と商、`sqrt(-0.0)`、`floor` / `ceil` / `trunc` / `round` の 0、`F64` → `F32` で 0 に丸まる値、0 に丸まる積と商）、`+0.0` と `-0.0` のどちらかが書かれていない。`-a`（符号の反転）、`%`（符号は `a` と同じ）、`min` / `max`（`-0.0 < 0.0`）、`strict-ftz`（符号を保った 0、§15.5）は既に書いてある。符号は `to_bits()`、`Show`（`-0.0` と表示する、§6.3）、`1.0 / x`（`±inf`）、`min` / `max`、`pow(x, -1.0)` で見える。§13.4 の「浮動小数の NaN と符号付きゼロは上の規則に従い」も、指す規則が無い。
- **今の実装:** インタプリタと生成した C は IEEE 754 の規則どおりに動く。`1.0 + -1.0` は `+0.0`、`-0.0 + -0.0` は `-0.0`、`-0.0 - 0.0` は `-0.0`、`-3.5 - -3.5` は `+0.0`。`0.0 * -1.0`、`0.0 / -1.0`、`-1.0 / inf`、`F32` の `-1.0e-30 * 1.0e-30` は `-0.0`、`-0.0 * -0.0` は `+0.0`。`sqrt(-0.0)`、`floor(-0.0)`、`ceil(-0.5)`、`trunc(-0.5)`、`round(-0.4)`、`round(-0.5)`、`(-1.0e-300).round_f32()` は `-0.0`。ベクトルの `held-S207` の 1268 行を IEEE の値と照らすと、インタプリタと C（clang の arm64 と x86_64、gcc-15）の全てで一致した（S-208、S-209 の行を含む 1376 行で不一致 0）。
- **案:**
  - (a) 規則を仕様の文で書く。ちょうど 0 になる和は、両方の被演算子が `-0.0` のときだけ `-0.0`、それ以外は `+0.0`（差 `a - b` は `a + (-b)` として扱う）。積と商の符号は、二つの被演算子の符号の排他的論理和（結果が 0 や無限大でも）。0 でない数学的な結果が丸めで 0 になったときは、その結果の符号。`sqrt(-0.0)` は `-0.0`。`floor` `ceil` `trunc` `round` と、`round_f32()`（`F64` → `F32`）、`as`（`F32` → `F64`）は被演算子の符号を保つ。整数から浮動小数への変換の 0 は `+0.0`。
  - (b) 「結果の 0 の符号は IEEE 754 の規則（§6.3）に従う」の 1 文（計画の仮の案）。
  - (c) 0 の結果を常に `+0.0` にそろえる。
  - (d) NaN と同じく未規定にし、`to_bits()` が `+0.0` にそろえる。
- **他言語:** 上の全ての点で (a) と同じだったもの: C の演算と libm（clang 21、gcc-15。`sqrtf`、`floorf`、`ceilf`、`truncf`、`rintf`、`roundf`、`nearbyintf`、`(float)` の丸め）、Node の演算と `Math.sqrt` / `ceil` / `trunc` / `round` / `fround`（`Object.is(x, -0)` で見た）、Node の WebAssembly の `f32.add` `sub` `mul` `div` `sqrt` `ceil` `floor` `trunc` `nearest` と `f32.demote_f64`（手書きのモジュール）、Python の演算と `math.sqrt(-0.0)` と `round(-0.4, 0)`、Swift の `rounded()` と `squareRoot()` と `Float(-1e-300 as Double)`。違ったもの: Ruby の `Math.sqrt(-0.0)` は `+0.0`。Python の `math.floor` / `ceil` / `trunc` と `round(x)`、Ruby の `round` / `ceil` は整数を返すので符号が無い。規格: IEEE 754-2019 §6.3（和・差・積・商、`squareRoot`、`roundToIntegral`、変換の結果の符号。原文は手元に無く未確認）。WebAssembly の仕様は演算ごとに 0 の符号を書く（`fadd`「both z1 and z2 are zeroes of opposite sign, then return positive zero」、`fnearest`「smaller than 0 but greater than or equal to −0.5, then return negative zero」など。https://webassembly.github.io/spec/core/exec/numerics.html ）。
- **推奨と理由:** (a)。確度: 高。全ての変換先（C、WASM、JS）の命令と関数がそのままこの規則で動くので、生成コードに検査が要らず、今の実装も全ての行で既に一致している。(c) と (d) は DSP の内側のループに比較を足し、`-a` を符号の反転とする規則、`min(-0.0, 0.0)` を `-0.0` とする規則、全て `-0.0` の `sum` が `-0.0` になるように `xs[0]` から畳むとした決定（R-23）と食い違う。(d) は `Show`、`1.0 / x`、`pow` で符号が見えるので、`to_bits()` でそろえても見える振る舞いが決まらない（NaN の符号を未規定にできたのは、NaN が `to_bits()` でしか区別できないからだった、S-106）。(b) でなく (a) にするのは、規範を仕様の中で閉じる方針（S-106）による。規則は短い文の 6 つで、JS / WASM の実装者が表から直接書ける。IEEE の節は参考として挙げる。
  - `@fp(relaxed)` の中で符号の規則を緩めるか: (r1) 緩めない（個々の演算は規則に従い、0 の符号が変わるのは並べ替えと縮約の帰結だけ）、(r2) 0 の符号を約束しない（値と同じく、再結合と縮約で違いうる）。(r2) を推す（確度: 中）。clang 21 の関数ごとの `#pragma clang fp reassociate(on) contract(fast)` は、0 の符号を保ったまま和のループをベクトル化した（`x + 0.0f` を `x` にせず、`(a + b) - b` を簡約しない）ので、clang なら (r1) でも足りる。しかし gcc-15 は、コマンドラインの `-fassociative-math` を `-fno-signed-zeros` 無しでは無効にし（警告「'-fassociative-math' disabled」）、関数の属性 `optimize("associative-math")` ではループをベクトル化するが `(a + b) - b` を `a` にして、`a = -0.0`、`b = +0.0` で `-0.0` を返した（strict は `+0.0`）。GCC の文書も「re-ordering may change the sign of zero」「requires that both -fno-signed-zeros and -fno-trapping-math be in effect」と書く（https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html の `-fassociative-math`）。再結合はそれ自体で 0 の符号を変えるので、(r2) は S-57 の「縮約と再結合だけを許す」の中に収まる。`relaxed` の出力はビットで比べず（S-162）、符号だけを守らせても検査できない。NaN と無限大が無いという仮定と近似を含めないこと（S-57）は変えない。§15.5 に 1 文。
  - （Fable の指摘、親が確かめた）上の理由の「再結合はそれ自体で 0 の符号を変える」は、gcc の例では示されていない（`(a + b) - b` を `a` にするのは代数的な簡約で、S-57 が許す縮約と再結合の外）。和と積の純粋な並べ替えだけでは、ちょうど 0 の結果の符号は変わらない。(r2) の理由は縮約に差し替える: 縮約は単独で 0 の符号を変える（`F32` の `1e-23 * -1e-23 + 0.0` は縮約しないと `+0.0`、融合すると `-0.0`。clang 21 の `fmaf` で確かめた）。結論の (r2) は変わらない。
  - （Fable の指摘）gcc の挙動は C のバックエンドの実装の注意に移す: gcc で関数ごとに再結合を効かせると、`-fno-signed-zeros` 相当の簡約（`x + 0.0` を `x` にするなど）も入り、S-57 の「縮約と再結合だけ」を超える。親の推奨: `relaxed` の意味は S-57 のまま一つに保ち、gcc では gcc の再結合を使わず縮約だけにする（再結合が要るなら生成コードの側で行う）。W10 の作業票に書く。
  - `ZERO` の説明「加法の単位元」（§6.3）は、浮動小数では `-0.0 + ZERO` が `+0.0` なので厳密でない。`F32.ZERO` / `F64.ZERO` は `+0.0` と書く（S-211 の定数の値と同じ回）。
  - JS（M8）の実装の注意: `round` の模倣は `[-0.5, -0.0]` で `-0.0` を返す必要があり、`Show` は `String(-0)` が `"0"` なので `-0.0` を別に扱う。仕様は変えない。
- **影響:** §3.4（浮動小数の表に「結果が 0 のときの符号」の箇条）、§13.4（「符号付きゼロは上の規則に従い」を §3.4 を指す文に）、§15.5（`relaxed` の 1 文）、§6.3（`ZERO` の説明）。実装の変更は無い。ベクトル: `held-S207` の 1268 行（`float-f32` 478、`float-f64` 499、`expr-*` の `expr_interp` 52 と `vdelay_f` 216、`conv-f64` の `round_f32` 23）が `edge` / `rand` の行になる。期待はモデルが今計算している IEEE の値で、`model.py` の保留を外して生成し直す（W2-01 の追補。W2-02 の比較はそのまま通る）。帰結として、整数の `d` の `vdelay_f` は `f = dc - k` が `+0.0` で、`expr_interp` は `a = -0.0`、`f = +0.0`、`b >= +0.0` のとき `a` でなく `+0.0` を返す（確かめた）。S-194 で補間の式に場合分けを足さないと決めたことの帰結で、音には影響しない。作業ツリーのテストに、0 の符号に依る期待値は無い。
- 回答:

(a)で良いと思います。

### S-208 `abs(-0.0)`

- **論点:** §3.4「`std.math` の … `abs` … は正確に計算する」。§13.4 は std の本体を `abs(x)` は `if x < T.ZERO { -x } else { x }` とし、「組込み型では本体の代わりにプリミティブを使い、浮動小数の NaN と符号付きゼロは上の規則に従い」と書く。上の規則（§13.4 の第 1 項）は `min` / `max` の 0 しか書かず、`abs` の 0 が無い。本体どおりなら `-0.0 < 0.0` が偽なので `abs(-0.0)` は `-0.0`、IEEE の `abs` なら `+0.0`。
- **今の実装:** インタプリタ（Rust の `abs`）と C（`fabsf` / `fabs`）は、`F32` と `F64` のどちらも `abs(-0.0)` が `+0.0`、`abs(+0.0)` が `+0.0`。`held-S208` の 4 行も `+0.0` で一致した。
- **案:** (a) 組込みの浮動小数の `abs` は、符号のビットを 0 にした値と §3.4 に書く（`abs(-0.0)` は `+0.0`、NaN は NaN）。std の本体は利用者の数の型のためのまま。(b) 本体どおり `abs(-0.0)` を `-0.0` にし、プリミティブを本体に合わせる。(c) 本体を浮動小数でも同じ答えになる形（`if x <= T.ZERO { T.ZERO - x } else { x }`）に変えたうえで (a)。
- **他言語:** 全て `+0.0`: C の `fabsf(-0.0f)`（clang 21、gcc-15）、Node の `Math.abs(-0)`、Node の WebAssembly の `f32.abs`、Python の `abs(-0.0)` と `math.fabs`、Swift の `abs` と `magnitude`、Ruby の `(-0.0).abs`。規格: IEEE 754-2019 §5.5.1 の `abs` は符号のビットを 0 にする（原文は未確認）。WebAssembly の `fabs`「if z is a zero, then return positive zero」（上の URL）。
- **推奨と理由:** (a)。確度: 高。全ての変換先の命令と関数が `+0.0` を返し、(b) は C・WASM・JS の全てに分岐を足す。絶対値の符号のビットが立つのは、`to_bits()` や `1.0 / abs(x)`（`-inf`）で読み手の予想に反する。(c) は `abs` の本体と組込みの答えをそろえるが、`min` / `max` の本体は NaN と 0 の符号で組込みと違うまま（比較だけの本体では表せないと S-108 が承知で決めた）なので、本体とプリミティブが違いうるという規則は残り、規則の数は減らない。利用者の数の型（`Q15` など）には符号付きの 0 が無く、今の本体で困らない。
  - §13.4 の「浮動小数の NaN と符号付きゼロは上の規則に従い」を、§3.4 の `abs` / `min` / `max` の規則を指す文に直す（S-207 と同じ文）。std の `abs` の doc コメントに「組込みの浮動小数は符号のビットを 0 にする」と書き、本体を読んだ書き手の誤解を防ぐ。
  - NaN の `abs` の符号は、§3.4 の NaN の規則のまま未規定（`to_bits()` でそろう）。
- **影響:** §3.4 の `std.math` の箇条、§13.4 の 1 文。実装の変更は無い（W5-02 で std の本体とプリミティブを表に分けるとき、組込みの浮動小数がプリミティブに行くことをテストで固定する）。ベクトル: `held-S208` の 4 行（`f32.abs` と `f64.abs` の `+0.0` と `-0.0`）の期待が `0x00000000` / `0x0000000000000000` になる。
- 回答:

### S-209 有限の数 `%` 無限大

- **論点:** §3.4 の `%` の行は「`fmod`: `a - b * trunc(a / b)` を丸めずに求めた値（符号は `a` と同じ）。…`b` が 0 か `a` が無限大なら NaN」。`a` が有限で `b` が無限大の場合が無い。式を字面で読むと `trunc(a / inf)` は 0 で `inf * 0` が NaN になり、「丸めずに求めた値」を `b` を大きくした極限で読むと `a` になる。
- **今の実装:** インタプリタ（Rust の `%`）と C（`fmodf` / `fmod`）は `a` を返す: `1.0 % inf` は `1.0`、`-1.0 % inf` は `-1.0`、`-0.0 % inf` は `-0.0`、`1.0 % -inf` は `1.0`、`F32.MAX % inf` は `F32.MAX`（`F64` も同じ）。`held-S209` の 104 行も `a` で一致した。
- **案:** (a) `a` が有限で `b` が無限大なら結果は `a`（`-0.0` も保つ）と書く。(b) NaN（式の字面の読み）。(c) 式による定義をやめ、場合の表で書き直す。
- **他言語:** C の `fmodf(1, inf)` は `1`、`fmodf(-0.0, inf)` は `-0.0`、`fmodf(-1, -inf)` は `-1`（clang 21、gcc-15）。Node の `1 % Infinity` は `1`、`-1 % Infinity` は `-1`、`-0 % Infinity` は `-0`。Python の `math.fmod`、Ruby の `remainder`、Swift の `truncatingRemainder(dividingBy: .infinity)` も `a`。Python と Ruby の `%`（床で割る剰余で、別の演算）は `-1.0 % inf` が `inf`。規格: C11 Annex F.10.7.1 の `fmod(x, ±∞)` は無限大でない `x` で `x`（N1570。原文は未確認）。ECMA-262 §6.1.6.1.6 Number::remainder（原文は未確認。挙動は Node で確かめた）。IEEE 754-2019 §5.3.1 の `remainder`（最近接の商による別の演算）も、有限の `x` と無限大で `x`（原文は未確認）。WebAssembly に `fmod` の命令は無い。
- **推奨と理由:** (a)。確度: 高。`|a| < |b|` なら剰余は `a` という有限の場合と続いた値で、C の `fmod` と JS の `%` がそのまま返すので、生成コードに分岐が要らない。(b) は全ての変換先に分岐を足し、有限の位相を無限大の周期で割った値を NaN にして信号を壊す。
  - 文は「`a` が有限で `b` が無限大なら `a`」の 1 句を NaN の場合の文の隣に足し、式 `a - b * trunc(a / b)` を有限の `b` についての定義とする。
  - WASM の `%` は命令が無いので、同梱の実装（計画では musl の移植）で計算する。musl の `fmodf` がこの場合に `a` を返すかは、手元では未確認。（Fable の指摘）Fable が musl の `fmodf.c`（git.musl-libc.org）を読み、有限の `x` と無限大の `y` で `x` を返すことを確かめた。
- **影響:** §3.4 の `%` の行。実装の変更は無い。ベクトル: `held-S209` の 104 行（`f32.rem` と `f64.rem` 各 52）の期待が `a` のビットになる（モデルは今も `a` を計算している）。M6 の WASM の `fmod` の実装で、この行が通ることを確かめる。
- 回答:

(a)で。

### S-210 同じ型への変換

- **論点:** §3.3「`as` は情報を失わない拡大変換だけに使える」。変換の表の `as` の行は異なる型の組だけを並べ、同じ型の組（`F32` → `F32`、`I32` → `I32`）が無い。一方、同じ節の E0413 の文は「同じ型への `round_f32()` など」を `as` で書ける組の変換メソッドとして挙げ、修正候補を `as` の形にする（S-98）。§4.4 は型別名の主な用途を「標本の精度を一か所で切り替えること（`type Sample = F32`）」とする。同じ型の `as` を書けないと、`sample_rate() as Sample`（`sample_rate()` は `F32`、§11.4）が `Sample = F64` では通り、`Sample = F32` では通らない。型パラメータの `x as T`（`x: T`）と、同じ型への `narrow_<型>()`（`I32` の `narrow_i32()`）も書かれていない。
- **今の実装:** `x as F32`（`x: F32`）、`n as I32`（`n: I32`）、`type Sample = F32` の下の `x as Sample` を受理し、値を変えない（`-0.0` と NaN を保つ。C は `return x;` を出す）。fmt は触れない。総称の `x as T`（`x: T`、`T: Float`）は E0411 で、文面は「`T` to `T` needs a conversion method」（そのメソッドは無い）。`I32` の `n.narrow_i32()` と `F32` の `x.round_f32()` も受理する（後者は S-98 の E0413 に反する。`tests/spec/fixes/e0413_forms.onsa` が W5-02 待ちで、E0413 と候補 `x as F32` を期待している）。
- **案:**
  - (a) 組込みの数の型の同じ型の組を `as` の行に足す（値を変えない）。別名は解決した後の型で判定する。同じ型への変換メソッドは S-98 どおり E0413（候補は `as`）。型パラメータの `as` は、`T as T` も含めて E0411（候補は `as T` を外す形）。
  - (b) (a) に加えて、`T as T` も書ける（同じ型なら型パラメータも）。
  - (c) (a) に加えて、同じ型への変換メソッドも書ける（値を変えない）。
  - (d) 同じ型の `as` を全て誤りにする（E0411、候補は `as` を外す形）。
  - (e) 別名を通さずに見えている同じ型（`x as F32`）だけを誤りにする。
- **他言語:** C の `(float)x`、Swift の `Float(x)`（`x: Float`）と `Sample(x)`（`typealias Sample = Float`）、rustc 1.94 の `x as f32` と `x as Sample` は全て書ける。総称の同じ型も、rustc の `x as T`（`T: Copy`）と Swift の `T(x)`（`T: BinaryFloatingPoint`）で書ける。clippy 0.1.94 の `unnecessary_cast` は `x as f32` を警告し、別名を通した `x as Sample` を警告しない（別名の下では余分に見えないことの実例）。
- **推奨と理由:** (a)。確度: 中。同じ型の `as` を書けないと、§4.4 が別名の主な用途とした精度の切り替えで、広げる向きの変換（`F32` の値を `Sample` へ）が `Sample = F32` で壊れる。この余分は型と別名を解決して初めて分かり、別名を変えれば実際の変換になるので、意味が一つの余分として fmt で消すことはできず（fmt は構文だけを見る、§18.2）、誤解を示す書き方でもない。(e) は書かれた名前で規則を変える形で、`x` の型が別名から来るとき（`x: Sample` の `x as F32`）に破れる。(d) は S-98 の E0413 の候補（`as`）を書けない形にし、今の事例の期待とも食い違う。
  - 型パラメータを E0411 のままにするのは、別名が型そのものであるのに対し、型パラメータは境界が与える操作しか持たず、`as` を与える trait が無いからである。`T as T` は具体化によらず何もしないので、書けなくても失うものは無い。(b) は型パラメータに `as` を一つだけ開け、`F32 as T`（`T: Float`）を書けるかの問い（A-09、`Float` を開く §19.1）を先取りする。後で (b) へ緩められる。
  - 同じ型への `narrow_<型>()` も同じ判断でよい。メソッドの名前が行き先の型を書くので、別名で精度を切り替えるコードに役立たず（別名を変えても `narrow_i16()` の行き先は変わらない）、型の組ごとに書き方は一つ（S-98）を保てる。候補 `n as I32` は型が `Option[I32]` から `I32` に変わるが、S-98 が決めた拡大の `n.narrow_i64()` の候補と同じ扱いである。
  - (c) は狭める向き（`Sample` から `F32` へ `round_f32()`）を別名の切り替えに強くするが、`F32` → `F32` に二つの書き方を作り、S-98 を覆す。狭める向きは、別名の隣に変換の関数を一つ置けば、切り替えで直す所が一か所になる。
  - E0411 の文面: 型パラメータには「型パラメータに `as` は無い」と note で示し、`x: T` の `x as T` には `as T` を外す候補を出す。
  - （Fable の指摘）`x: F32` の `x as T` には、何に直すか決められないので候補を出さない、と一言足す。`F32 as T`（`T: Float`）は S にせず、A-09 の問いとして `api-candidates.md` に残す。
- **影響:** §3.3 の表の `as` の行に「同じ型（値を変えない）」、型パラメータの `as` が E0411 である 1 文（§3.3 か §4.5）。E0413 の文は今のまま。W5-02（同じ型への変換メソッドの E0413。`I32` の `narrow_i32()` を含む。E0411 の型パラメータの文面と候補）。ベクトル: 保留の節は無い（`tools/vectors/ops.py` の `conv_forms` は同じ型の組を作らない。計画の「`held-S210` の節」はデータに無い）。決まれば 10 個の同じ型の `as`（`<型>.as_<型>`、期待は入力のビット、NaN は `nan`）を登録簿と fixture に足し、`check_registry` が同じ型の組も表から導くようにする。否定例: `I32` の `n.narrow_i32()`（E0413、候補 `n as I32`）、総称の `x as T`（E0411、候補 `x`）。肯定例: `type Sample = F32` の下の `sample_rate() as Sample`。`e0413_forms.onsa` の今の期待は (a) と合う。

### S-211 `F32.PI` / `F64.PI` の値

- **論点:** §6.6 の関連定数の表は `PI`（`Float`）を挙げるが、値を書かない。π は二進で表せないので、型への丸め方で `F32.PI` のビットが変わる（最近接の `0x40490FDB` は π より大きく、ゼロ方向の `0x40490FDA` は小さい）。`F64` はどちらでも `0x400921FB54442D18`。§2.4 も浮動小数のリテラルの丸め方を書いていない（R-20 で二重に丸めない、R-45 で有限でなければ E0408 と決めたが、文は仕様に無い）。
- **今の実装:** インタプリタと C のどちらも `F32.PI` は `0x40490FDB`、`F64.PI` は `0x400921FB54442D18`（C は `3.1415927f` / `3.141592653589793` と 10 進で書く）。字面 `3.14159265358979323846264338327950288` の `F32` も `0x40490FDB` で、`F32.PI` と等しい。`F32` のリテラルは一度だけ丸めている（二重に丸めると違う値になる字面 `1.00000005960464477550` も `0x3F800001`）。`1.0e40` の `F32` は E0408 にならず無限大（R-45、W3-05 で直す）。
- **案:** (a) π を各型へ最近接偶数で丸めた値（リテラルと同じ丸め）。(b) ゼロ方向に丸めた値（`F32` は `0x40490FDA`）。(c) 値を書かず実装に任せる。
- **他言語:** `0x40490FDB` だったもの: C の `(float)M_PI` と π の字面の `(float)`（clang 21、gcc-15）、Node の `Math.fround(Math.PI)`、Python と Ruby の π を `f32` に詰めた値、Swift の `Float(Double.pi)`。`double` の π（C の `M_PI`、Node の `Math.PI`、Python の `math.pi`、Ruby の `Math::PI`、Swift の `Double.pi`）は全て `0x400921FB54442D18`。Swift の `Float.pi` は `0x40490FDA`（ゼロ方向）で、doc コメントが理由を「rounded toward zero to keep user computations with angles from inadvertently ending up in the wrong quadrant」と書く（`stdlib/public/core/FloatingPoint.swift` の `pi`、https://github.com/swiftlang/swift ）。
- **推奨と理由:** (a)。確度: 高。「定数は数学的な値をリテラルと同じ規則で丸めた値」という一つの規則で、書き手が π の字面を書いても `F32.PI` と同じビットになる。誤差は (a) が小さい（`F32` で約 `8.7e-8`、(b) は約 `1.5e-7`）。DSP の主な使い方（`2.0 * F32.PI * fc / sample_rate()` の角周波数）では誤差の大きさが効く。(b) の利点の象限は式の先まで続かない（ゼロ方向の `F32.PI` でも `3.0 * F32.PI` は 3π を上回る。`F32` の積で確かめた）。(c) はビット一致（§13.4）と相いれない。
  - 規則は `PI` だけでなく浮動小数の関連定数の全てに書く: 「数学的な値を最近接偶数で型に丸めた値」。`ZERO` は `+0.0`、`ONE`、`MAX`（最大の有限値）、`EPSILON`（`2^-23` / `2^-52`）、`INFINITY` は正確に表せ、`NAN` は NaN（ビットは §3.4 のとおり未規定で、`to_bits()` でそろう）。将来 `TAU` や `E` を足しても同じ規則で値が決まる。今は足さない（§6.6 の閉じた一覧。足すなら実例を添えて `api-candidates.md` で）。
  - §2.4 に浮動小数のリテラルの値の文を足す: 10 進の値を型へ最近接偶数で一度だけ丸めた値（R-20）、有限でなければ E0408（R-45）。決定は済んでいて文が無いだけなので、同じ回に入れる。0 でないリテラルが 0 に丸まる場合（`1.0e-50` の `F32`）の扱い（有限なので通る、が自然な読み）も書く。別の S にしてもよい。
  - （Fable の指摘）0 でないリテラルが 0 に丸まる場合は、通すのでなく E0408 にする方がよい。R-45 の理由は「範囲外が黙って無限大になる」ことで、0 でない字面が黙って `+0.0` になるのは同じ性質（DSP の係数の項が消える）。「型が決まった時点で、値が有限でないか、0 でない字面が 0 に丸まるなら E0408」の一つの規則にでき、厳格で後で緩められる。非正規化数に丸まる字面（`1.0e-40` の `F32`）は値が残るので通す。
- **影響:** §6.6（関連定数の表の下に値の規則）、§2.4（リテラルの丸め）。実装の変更は無い（R-20 / R-45 は W3-05）。ベクトル: 保留の節は無い（`tools/vectors/spec_tokens.py` の `CONSTANTS_LEFT_OUT` が `PI` を外している。計画の「`held-S211` の節」はデータに無い）。決まれば除外を消し、`const.tsv` に `f32.PI`（`0x40490fdb`）と `f64.PI`（`0x400921fb54442d18`）の 2 行が入る。
- 回答:

(a)で。

- **今の実装:** `else` だけ（`with` と `{` は W3-06。関数の見出しの次の行の `{` と `if x > 0` の次の行の `{` は今は E0002）。主の位置は `}` の直後から `else` の直前まで（改行と字下げ。4:4〜5:3）で、`found` は `"else"`（範囲の文字列と違う）。テキストの出力は `}` の後ろに `^` を置き、`} // positive` では `^` がコメントの下に並ぶ。修正候補は、間が空白と改行だけならそれを空白一つにし、間にコメントがあれば、`else` からその行のコメントの前までを `}` の直後へ挿入して `else` の行を消す。当てた結果:
  - `} // positive` と `else {` → `} else { // positive`
  - `}`、空行、`// the other case`、`else {` → `} else {`、空行、`// the other case`（コメントは `else` の本体の頭に入る）
  - `} // positive` と `else if x < 0 { // negative` → `} else if x < 0 { // positive` と単独の行の `// negative`（順は保つ）
  - `} // positive`、`else`、`{` → `} else // positive` と `{`（`{` の E0003 が残る。単位ごとに一つなので次の周で出る）
  - 否定例 `tests/spec/negative/syntax_else.onsa` は印を `if` の行に置き、「span は `}` の後の改行」と注記している。
- **案（主の位置）:** (a) 置き場所を誤ったトークン（`else`、`with`、`{`）。(b) `}`（見出しの最後のトークン）の直後から、そのトークンの直前まで（今の実装）。(c) `}`（見出しの最後のトークン）。(d) `}` からそのトークンまで。
- **案（コメント）:** (p) 移すのはトークンからその行のコメントの前まで。前の行の行末のコメントの前に入れ、コメントは書かれた行に残す（今の実装）。(q) 前の行のコメントを `}` の前へ移す（前のブロックの末尾に単独の行で入れる）。(r) 前の行のコメントを、移した後の `{` の次の行へ移す。(s) 間にコメントがあれば修正候補を出さない。
- **他言語:** `}` の次の行の `else` は、Swift 6.3.1、Apple clang 21、gcc-15、rustc 1.94.1 のどれも受理し、同じ規則を持つ処理系は手元に無い（Go は未確認）。似た場面の位置: 行末のコメントの前で `;` が抜けた宣言に、clang 21 は前のトークンの直後（2:12）を指し、`;` の挿入の候補をコメントの前に置く。gcc-15 は次の行のトークン（`return`、3:3）を指し、候補は無い。規格: LSP の `CodeActionContext.diagnostics` は、`textDocument/codeAction` の範囲（カーソルや選択）に重なる診断を渡す（LSP「CodeActionContext」）。
- **推奨と理由:** (a) と (p)。確度: 中。
  - (a): 範囲に見える文字があり 1 行に収まり、`found` と範囲の文字列が揃う。(b) の範囲は空白と改行だけで、カーソルを `else` の上に置いても範囲に重ならない（範囲は `else` の前で終わる。LSP の修正候補は範囲に重なる診断から作る）。テキストの出力の `^` も前の行の末尾やコメントを指す。(c) と (d) は直すべきトークンでない `}` を指す。行頭の二項演算子の E0020（§2.5）と、括弧の中の改行の後の `(` の E0002 も、置き場所を誤ったトークンを指すのが自然で、「行の置き場所の誤りは、その位置にあるトークンを指す」の一つの規則で言える。
  - (p): コメントを書かれた行に残し、順も変えない。§18.2 の fmt の規則（「コメントを書かれた行に残す」、S-56 の比較のコメントの並び）と同じで、候補を当てた結果を fmt が比べても違いが出ない。(q) と (r) はコメントを別の行へ移し、どこへどの字下げで置くかの規則が要る。(s) は「修正候補は前の行へ移すこと」と、E0003 は常に候補を持つ（登録簿の必須）に反する。(p) の代償は、`}` に付けたコメントが `} else {` の行の末尾に来て `else` の注釈に見えうることだが、Onsa のコメントは全て行末のもので（§2.1）、行に属する。
  - あわせて決めること: 同じ規則を、前の行へつなぐ他の候補（行頭の二項演算子の E0020、行頭の `- b` と `^ b` のつないだ形、改行を除く E0002）にも当てる。どれも主の位置は置き場所を誤ったトークンで、前の行のコメントの前に入れる。
  - あわせて決めること: §2.5 の「前の行」を「`}`（見出しの最後のトークン）の行」と言い換える（間のコメントの行と空行は今のまま残り、本体の頭に入る）。
