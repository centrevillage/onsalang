## 1. 実装の判断（D）

全て 2026-10-01 に案の通り決定。

### D-01 字句解析器と構文解析器は手書き（再帰下降）

- 案: パーサジェネレータを使わず、手書きの字句解析器と再帰下降の構文解析器にする。
- 理由: (1) 文の区切りが改行に依存し、文脈（ブロックの中か、括弧の中か）で改行の意味が変わる（§2.5）。ジェネレータでは字句解析器に文脈を戻す経路が要る。(2) 既存言語の書き方への修正候補（§18.1）は、エラー回復の中で「何を書こうとしたか」を推定する専用の規則で、手書きでしか書けない。(3) LSP で編集中のソースを扱うには、エラーから回復して AST を作り続ける必要がある。
- 代替: `lalrpop` / `pest`。文法の検証には使えるが、上記 3 点で結局手書きの層が要る。

### D-02 AST はアリーナ + ID。スパンはバイトオフセット

- 案: 各ノードは `Vec` に置き、`ExprId(u32)` などの ID で参照する。スパンは `Span { start: u32, end: u32 }`（ファイル内のバイトオフセット）。行・列は `LineIndex` で必要なときに計算する。トークンの前後の空白とコメント（trivia）はトークン列に残し、AST はトークン列への索引を持つ（`fmt` と `diff --ast` が使う）。
- 理由: `Box` のツリーは `wasm32` でも動くが、LSP で部分的に差し替えるのと、`fmt` でトークンの前後の空白を再現するのに、ID と索引の方が扱いやすい。rust-analyzer と同じ方向。
- 代替: `Box` のツリー。最初は速いが、`fmt` でコメントの位置を失う。
- 改定（2026-10-05、レビュー R-86）: 段を「字句解析 → CST → AST → sema」にする。CST は全てのトークン（コメント、改行、空白を含む）を持つ損失の無い構文木で、構文解析器が作り、誤りの回復（S-59）もこの木の上で行う。AST は CST から一つの段で作り、ここに書いたアリーナと ID の形のまま sema が使う。
  `fmt` は CST を読み、S-56 の書き換えの一覧も CST の上で行う（取り除くノードに付いたコメントは残す）。診断の修正候補の範囲（R-87）と LSP の位置は、CST のトークンの範囲で表す。CST は自前の簡単な作りにし、外部のライブラリは使わない（D-09）。
  元の案（AST がトークン列への索引を持つ）は実装されず、`fmt` は AST の位置からコメントと区切り文字を推測していた（R-70 の 17 の形のうち 15 を書き換える）。
  トークン列に索引を持つ形より CST を選んだのは、trivia の位置が構造で保証され（ノードの範囲とトークンの境界の一致という不変条件に頼らない）、誤りを含むコードにも完全な木があり（LSP）、差分での再解析と構造を書き換える編集（第 2 期以降の補完やリファクタリング）の土台になるため。S-58（コメントの結び付け）は CST の上で作る（CST が先か同じ回）。
- 改定（2026-10-15、S-534）: AST は doc コメントを持たない。どの宣言に付く doc かは構文解析器が CST の上で決め（E0004 も CST の上）、要る所（fmt の書き込む前の確かめ）は CST から引く。`diff --ast` は AST の構造だけを比べる。
- 実装（2026-10-08、`rework-phase1.md` の W3-01）:
  - 構文解析器はイベントの列（`Start` / `Token` / `Finish`）を出し、ビルダが一度の走査で CST（自前の平らなアリーナ。子は連続した範囲、親への道、絶対の位置）を作る。ノードを開く入口は一つ（`enter`）で、`precede` で左を後から包む。ノードは最初のトークンが来たときに木に置き、それより前の消費されていないトークン（trivia）は外側のノードに付く。trivia の付く場所の規則はビルダの一か所にある（S-58 の結び付けは W3-11）。
  - ノードの種類は一つの列挙 `NodeKind`。構文解析器の分類はノードの種類に記録し、低下（CST → AST）は決め直さない（`_` の無い `match`）。宣言が導入する名前は `Name` のノード、項目の doc コメントは `Item` の最初の子の `Docs` のノード（doc を項目に付ける判断は構文解析器の一か所）、`#[..]` は `HashAttr`。項目のキーワードは一つの表 `DECLARATIONS`。
  - 誤りで抜けたノードは種類を保って不完全の印を持ち（空のこともあり、種類は開いたときの仮のもの）、回復で読み飛ばしたトークンは `Error` のノード（失敗した項目の最後の子か、成功した項目の後ろの余分なトークンは `SourceFile` の子）にする。
  - 低下は根から辿れる完成した項目だけを AST にする（失敗した項目の部分木の孤児を作らない。D10）。これにより、失敗した項目の中で構文の誤りより前に出ていた診断（E0010、E0011、E0012、E0320 など）が、構文の誤り（E0002 など）に代わる。リポジトリでは `tests/review-phase1/` の 3 つの再現の入力が S-59 の期待の向きに変わった。
    それ以外の受け付ける言語・診断・fmt の出力・AST の位置は 81fa1bd と同じで、古い構文解析器と並べて全てのファイルと変形 249,258 件で比べてから切り替えた。位置の癖 3 つ（`#[..]` は `]` を含まない、`loop` の `true`、負の const 引数の数字）は `SPAN-QUIRK` の印で残した。
  - `Parsed { ast, cst, map, diagnostics }`。`AstMap` は AST のアリーナのノードから CST のノードへの表（指す先が式のノードとは限らない）。アリーナに無い部分構造の位置は `covering_node(s)` / `covering_node_of` / `tokens_in` で CST から引く。各ノードは木の高さを持ち、W3-14 の深さの上限は `Parser::height` の一か所で数える。
  - `validate()`（木の不変条件）は全ての `parse()` で回し（R-82 と同じく常に）、崩れは位置付きの内部エラー（101）。`onsa dump --cst [--tree] <file>` は往復のテキスト（既定）か木の表示を出す。gate の `fmt-cst`（実装待ちにできない項目）が、`tests/` の全てのファイル（W3-01/t の往復の入力 `tests/cst/` 160 件を含む）と摂動で往復を確かめる。

### D-03 Core IR は構造化ツリー。flow は `init` / `reset` / `ctl` / `tick` / `process` の 5 関数に落とす

- 案: Core は CFG / SSA ではなく、**構造化された文と式のツリー** にする（`if` / `while` / `for` の範囲、`match` は enum のタグの `switch`）。全てのバックエンドがソース（C / JS）か構造化バイトコード（WASM）なので、CFG に落とすと構造を復元する作業が各バックエンドに要る。
- flow は次の 5 つの Core 関数に落とす（計画 §2.2 の `process` を 2 つに分けたもの）。

| 関数 | 内容 | 呼ばれる場所 |
|---|---|---|
| `f.init(cfg, sr) -> State` | `init` のクロックのノード（`let` と巻き上げた部分式）を評価して状態を構築する。段の順で読む前に必ず書かれるフィールドは設定しない（R-92） | 利用者、親の `init` |
| `f.reset(inout s)` | 遅延の状態を `init` 値へ、`w = 0`、サブインスタンスを `reset`、`poisoned = false` | 利用者、親の `reset` |
| `f.ctl(inout s, params: Params)` | `block` のクロックのノード（`let` と巻き上げた部分式、S-33）を順に評価し、`sample` から読まれるものを状態へ書く。サブインスタンスの `ctl` を呼ぶ | `f.process` の先頭、親の `ctl` |
| `f.tick(inout s, <sample の入力の値>...) -> <出力の値>` | `sample` のクロックのノードを順に評価する 1 サンプル分。遅延の保存は、全ての遅延の出力を読み、保存する値を全て評価した後にまとめて行う（R-13）。サブインスタンスの `tick` を呼ぶ | `f.process` のループ、親の `tick` |
| `f.process(inout s, params, input, output)` | `ctl` を 1 回呼び、`for i in 0..<frames` で入力を全て読み、`tick`、出力を全て書く（§11.6 の不変条件。引数の名前は S-30） | 利用者、export の wrapper |

（2026-10-06、点検 C-66: 表を S-102 のクロック、S-33 の巻き上げ、S-30、R-13、R-92 に合わせた。export の境界の `initialized` は S-27。）

- `process_inplace` は `process` に同じ `Span` を渡すだけの関数。`render` は `Buf` を確保して `process` を 1 回呼ぶ（インタプリタと `Alloc` のあるターゲットだけ）。
- 理由: 親 flow が子を点ごとに呼ぶには、子のブロックレートの計算（`ctl`）とサンプルの計算（`tick`）が分かれていなければならない。FAUST の `compute` を `control` と `loop` に分けた形と同じ。`tick` が関数呼び出しになるのは C コンパイラがインライン化するので問題ない。
- 代替: 子の `process` をブロック単位で呼び、中間バッファを置く。状態の大きさにブロック長が入り、§12.4 の「コンパイル時に決まる」が崩れる。
- 追記（2026-10-04、レビュー R-80）: 降下はターゲットによらない形にし、その後に **ターゲットの pass** を置く。この pass が、bulk の分割（R-90 (i)）、配置（大きさ・アラインメント・オフセット）と溢れの検査を行い、結果を Module に記録する。
  C、`onsa interface`（S-65 の `--target`）、`onsa audit`、E0820、WASM / JS は記録を読むだけで、計算し直さない。sema の `layout.rs` は消す（言語の意味として大きさを使う所は S-32 で無くなった）。
  到達解析は Core に一つ（`reach(module, roots)`）で、C の生成の範囲、`--backends all` の超越関数の判定（§13.4）、`onsa audit --panics` が使い、走査（`walk`）も Core のものだけにする。
  NRVO は Core の一か所で §12.7 どおり（全ての経路で返すローカルが一つ）に判定して記録し、C と監査はそれを読む（R-81 で結果の置き場所を明示するときに行う）。
- 追記（2026-10-04、レビュー R-81）: 降下の最後に正規化の段を置き、次の形にする。R1: 書き込みを持つ式（`inout` を渡す呼び出し、代入）と、文を含む式（`Block`、`IfExpr`、`Switch`）は、文の位置にだけ置く。R2: 文の位置の式の木に含まれる、効果を持つ演算（panic しうる演算、効果を持つ呼び出し）は、木全体で一つまで。
  残りは純粋な演算（panic も書き込みも無い）にする。R3: 文の位置へ出すものは評価順（§3.5）どおりに並べ、書き込みを持つ式を出すときは、それより先に評価される部分のうち、その書き込みが届きうる場所を読むものを先に出す。R4: 条件付きで評価される部分（`&&` / `||` の右辺、`if` / `match` の腕）から出すものは、その条件の内側に出す。
  木の中に書き込みが無く、観測できる演算が一つだけなので、バックエンドは木をどの順で評価してもよく、文を順に出し、条件付きの評価（C / JS の `&&` と `?:`、WASM の `if`）を保つだけでよい。演算の分類（純粋・panic しうる・書き込みを持つ）は Core の一か所で決め、プリミティブの分類は R-79 の `Prim` の表に欄として持たせる。
  検証器（R-82）が R1・R2 を検査し、R3・R4 は評価順の再現の期待値付きテストと、インタプリタと C の差分テストで押さえる。移動とコピーを区別して表す。破棄は `Drop(place)` の文として、sema が経路を見て列挙した破棄の点（R-32）から写す。
  型ごとの破棄の種類（何もしない／ヒープの解放・参照カウント／利用者の `Drop`）は Core で一度だけ決め、各バックエンドは破棄の種類を `_` 無しで網羅し、実装していない種類は生成の前に E0200 にする。
  検証器は「所有する値は全ての経路でちょうど一度、移動か破棄される。移動・破棄の後は使わない」を検査し、インタプリタは破棄・移動した後の値を読むと内部エラーにする（テストでは常に有効）。結果の置き場所は Core に明示する（集成体を作る式に宛先の場所を持たせ、sret の関数には返り値の置き場所のローカルを置き、NRVO はそれへの割り当てとして記録する）。
  宛先が構築に使う値から読まれうる場合は、一時変数に作ってからコピーする（§12.7、S-76）。重なりの判定の関数は一つにし、sema の E0702 と共有する（場所の経路を表す小さな型を共有する）。進め方は R-06 と同じ: 設計メモを先に書かせて親が読み、最も能力の高いモデルに推論を深くして実装させ、別のエージェントが仕様だけから期待値付きのテストを書いて壊しにいく。
- 追記（2026-10-05、レビュー R-89、D-15）: Core の段を「降下 → 正規化 → 定数の評価 → ターゲットの pass → export の計画」とする。定数の評価は、関数を呼ぶ `const` の初期化式を評価してリテラルに置き換える段で、ターゲットによらない（超越関数を含む定数の評価に何を使うかは R-108）。
  今は driver のビルドの経路にだけあり（`inline_consts`）、テストの `emit_c` は通っていない。
  export の計画は、パッケージとターゲットごとに一度だけ作る記録で、flow ごとにシンボル（`prefix` + 名前、重なりは E1011）、生成する API（`init` / `reset` / `process` / `render` と入出力の形、S-30）、状態とパラメータの配置への参照、パラメータの情報（`@param`）、panic の扱い（§9.2）と、そのために状態が持つフィールドを持ち、関数ごとにシンボル、FFI の型のシグネチャ、panic の通知を持つ。
  降下が作る状態のフィールド（`poisoned`、`initialized`、bulk のポインタ）は、作った時点で役割の印を付けて記録し、名前の文字列で探さない。入出力の役割は `FlowMeta` の明示の一覧から取り、引数の位置（`skip(2)`）で決めない。C・WASM・JS のバックエンド、`play`、ブラウザの IDE のパラメータの UI は、この計画を読むだけにする。
  計画の中身のうち、C の API の名前空間・ABI の版・関数の panic の通知（R-121）と、パラメータの ID（§11.7）は、それぞれの決定で埋める。テストは、ビルドと同じ入口（D-05 の改定、R-80 (5)）を通り、定数の評価と export の計画の段まで含める。

### D-04 診断の登録簿はマクロで作る Rust の表。`explain` の本文は markdown ファイル

- 案: `onsa_diag/src/codes.rs` に `codes! { E0010 => { category: Syntax, message: "..." }, ... }` の形で全コードを書き、`explain` の本文は `onsa_diag/explain/E0010.md` を `include_str!` で埋め込む。テストで「仕様 §18.1 の範囲に収まる」「本文のファイルが全コード分ある（M9 の受け入れ）」を検査する。
- 理由: コードの追加漏れをコンパイルエラーにしたい。本文は長文なので Rust ソースから分ける。
- 代替: TOML の登録簿を実行時に読む。`wasm32` で `include_str!` にするなら差は無いが、型の検査が無い。
- 追記（2026-10-05、レビュー R-87、D-15）: 登録簿の各コードに、段（S-78 の構文・名前・型・引数のモードと移動・rt と効果と、降下・ビルド）と、修正候補が必須かを持たせる。CLI、fmt、テストはこの属性を読み、番号の範囲（`number() <= 20`）やテストの中のコードの一覧で判定しない。修正候補が必須のコードで候補が無ければ、全てのテストで落ちる。
  既存言語の書き方の検出（E0020）は一つのモジュールの規則の表に集め（文脈、検出する形、候補の組）、構文解析器は解析に失敗した点でそこに問い合わせる（候補を作れなければ E0002、S-48）。E0020 は名前の段（`Sig[F32]`、S-120）と flow の検査（見えている名前への `^`、S-116）でも出るので、その段も同じ表の項目を引いて出す。
  fmt を止めるかは、コードではなく診断を出した段（字句解析と構文解析）で決める（S-120）。キーワードの判定は、`TokenKind` の宣言の順序に依らない明示の一覧にする。

### D-05 `tests/spec` の形式はインラインのマーカ

### D-07 `std` は Onsa のソースで書き、プリミティブは `target fn` で宣言する。ソースはバイナリに埋め込む

- 案: `std/math.onsa` は次のように書く。

```onsa
pub target rt fn exp[T: Float](x: T) -> T
pub target rt fn sqrt[T: Float](x: T) -> T
```

  各バックエンド（インタプリタ、C、WASM、JS）が `std.math` の `target` 宣言の実装を持つ。`std` のソースは `include_str!` でコンパイラに埋め込み、`wasm32` でもファイル I/O なしで使える。利用者のパッケージの `target` 宣言は、第 1 期では `bind` が無いので E0200。

- 理由: §15.2 の `target` は「実装をビルドターゲットが与える宣言」で、プリミティブの意味そのもの。`extern "C"` にすると核が C 系以外へ出せなくなる（§13.2 の E1010）。
- 代替: コンパイラ組込みの名前。ソースが無いので `onsa primer --std` と `interface` に出すものを別に持つことになる。
- 追記（2026-10-04、レビュー R-79、S-69）: 組込み型のメソッド・関連関数・関連定数も、std の `impl` に Onsa で宣言する（`impl F32 { pub target rt fn to_bits(self) -> U32 }`、`impl[T] Buf[T] { pub target fn zeroed(n: U32) -> Buf[T] uses {Alloc} }`）。
  他の操作で書けるものは本体ごと std に書き、プリミティブだけを `target` にする。`[T; N]` と `Buf[T]` の受け手は `Span[T]` のメソッドを引く（§5.3）。rt・効果・引数のモード・doc は通常の規則で扱い、`rt.rs` / `effects.rs` の名前による特別扱いを無くす。

- 追記（2026-10-04、レビュー R-79、S-71）: Option / Result も std の enum として宣言する（§4.1）。コンパイラが知るのは lang item の表（std の経路 → 役割）の 2 行だけで、使い道は prelude と `?` に限る。sema は `?` ごとに早期に返る列挙子の番号を決めて Core に渡す。
  std の `target` 宣言の引数と返り値には Option / Result を使わない（スカラ、配列、タプル、`Span` だけ）。Option を返すメソッド（`get`、`narrow_*`、`checked_*`）は std に Onsa で書き、範囲の比較などの後で、std の中だけで見える（`pub` の無い）プリミティブを使う。
  バックエンドは Option / Result の配置を知らずに済み、一般の enum に対応すれば動く。
- 追記（2026-10-04、レビュー R-80）: std のモジュールの一覧は、build.rs で `std/` のファイルから生成する（モジュールの経路はファイルの経路から決める。§15.1 と同じ規則）。driver とテストに手書きの表を持たない。std のファイルを足すだけで済む。

### D-10 C の出力単位と名前

- 案: パッケージごとに 1 つの翻訳単位 `onsa_<package>.c` と、export する flow ごとのヘッダ `onsa_<flow>.h`、共通の `onsa.h`。内部の名前はモジュールパスを `__` でつないだ `static` 関数（`dsp__voice__tick`）。型は `dsp__voice__State`。
  export は `prefix` + 名前の最後の要素（§14.2）。固定長配列は `struct { T a[N]; }` で包み、値として扱えるようにする。集成体を返す関数は出力ポインタを第 1 引数に取る（§12.7）。
- 理由: 1 翻訳単位なら C コンパイラが `tick` をインライン化できる。配列を struct で包むのは、C の配列が値でないため。
- 追記（2026-10-06、点検 C-97）: ファイルは S-52 / S-53 / S-95 で改めた。ヘッダはパッケージに一つで、生成するファイルは `<prefix><package>` を幹にする（`<prefix><package>.h`、`<prefix><package>.c`、`lib<prefix><package>.a`）。ランタイムのヘッダは `onsa.h`（公開）と `onsa__runtime.h`（生成した `.c` だけが取り込む）。

### D-11 WASM の libm は musl を Onsa に移植したもの（= `std.math.exact` の先行実装）

- 案: `expf` / `logf` / `sinf` / `cosf` / `tanf` / `tanhf` / `powf` / `exp2f` / `log2f` と F64 版を、musl の実装から Onsa の `rt fn` に移植して `std/math/soft.onsa` に置く。WASM バックエンドは `std.math` の `target` 宣言をこれに束縛する。移植には `F32.to_bits()` / `F32.from_bits()` が要る（S-09）。
- 理由: WASM には libm が無い。C で書いた libm を wasm に別途コンパイルするとツールチェーンが増える。Onsa で書けば核のまま WASM / JS / C の全てで使え、§19 の `std.math.exact` と、libm の精度が足りない組込み向けの差し替え（§13.4）が同じもので済む。
- 代替: JS の `Math` を import する。AudioWorklet から import 関数を呼ぶ往復が重く、精度も環境依存。
- 追記（2026-10-05、レビュー R-108、S-93）: インタプリタ（`const` の評価と `onsa test` を含む）も、`std.math` の超越関数をこの実装に結び付ける。ビルドする機械の libm に依らない成果物（§15.3）のためで、実装は一つのまま（Rust に同じ算法を書かない）。前倒しするかは、レビューの後に着手の時期を決めるときに決める。

### D-12 精度テストの参照値は mpmath で生成した表

- 案: `tools/gen_precision_tables.py`（mpmath）で、関数ごとに 4096 点（境界値、非正規化数、大きな値、乱数）の正しく丸めた値を生成し、`tests/precision/*.bin` に置く。テストは各環境の結果と比べて ULP 差を測る。
- 理由: MPFR を Rust から使う `rug` は C のビルドが要り、`wasm32` でも CI でも重い。表なら依存が無い。

### D-13 `play` は C → 共有ライブラリ → `libloading` + `cpal`。UI は端末

- 案: `onsa play voice` は M4 の経路で C を出力し、ホストの C コンパイラで共有ライブラリにして `libloading` で読み、`cpal` で鳴らす。パラメータは端末のキー操作（`@param` の一覧をスライダ風に表示）。GUI は IDE 側（M7 の `onsa_web` を使うブラウザ IDE）で作る。
- 理由: インタプリタはサンプル単位の `tick` には遅く、実時間の試聴に向かない。共有ライブラリなら M4 の生成物をそのまま使える。
- 代替: インタプリタで実時間。単純な flow なら動くが、保証できない。

### D-15 処理は一度だけ行い、後の段は前の段が出力した構造を受け取る

- 案: コンパイラの各段は、同じ判断や計算を繰り返さない。ある段が決めたこと（型、移動と破棄、評価順、結果の置き場所、配置、到達）は、その段が出力する構造に書き込む。後の段はその構造を入力として受け取り、次の構造を出力する。後の段が前の段の判断をやり直したり、別の規則で計算し直したりしない。
- 複数の段が同じ定義（`Prim` の表、`as` の表、演算の分類、場所の重なりの判定）を使うときは、宣言的な表か一つの関数として一か所に置き、各段はそれを参照する。
- 検証器（§3.4）も同じ原則に従う段である。前の段が出力した構造（Core）を入力にして、その構造が満たすべき性質を確かめる。前の段の処理をやり直さず、計算の結果も計算し直さない（配置なら、値を再計算せずに、オフセットの整列やフィールドの重なりが無いことを確かめる）。
  確かめる材料は前の段の出力の構造そのもので、前の段が構造の外に残した途中の記録（降下の補助関数、別の表に置いた移動の記録など）には頼らない。共有する表に誤りがあれば前の段と検証器の両方を通ってしまうので、表は仕様と照らすテストで確かめる。
- 注意: これは「各段が他の段に頼らず、自分で計算する」という意味ではない。そう読むと、同じ処理を複数の段で作り直すことになる。本質は、各段が同じことをせず、処理済みの構造をもとに次の段が進むことである（利用者の指摘、2026-10-05）。
- 理由: 同じ判断を複数の場所で行うと、片方だけが直って食い違う。レビュー R-80 の重複（配置、NRVO、到達解析、効果の集計など）は、全てこの原則の違反だった。
- 代替: 各段が必要な事実をその場で計算する。今の実装の形で、R-80 の食い違いの原因になった。

## 3. 共通の設計

計画 §2 を実装の型に落としたもの。クレートの境界で共有する。

### 3.1 スパンと診断（`onsa_diag`）

```rust
pub struct FileId(u32);
pub struct Span { pub file: FileId, pub start: u32, pub end: u32 }   // バイトオフセット、半開
pub struct Diagnostic {
    pub stage: Stage,               // 出した段（作る所が渡す。登録簿の「出しうる段」の一つ、W3-02）
    pub code: Code,                 // D-04 の登録簿
    pub message: String,            // 英語。登録簿のテンプレートに名前を埋めたもの
    pub span: Span,
    pub found: Option<String>,      // 問題の箇所のソース
    pub fixes: Vec<Fix>,            // Fix { title: 1 行・60 文字以内, edits: Vec<Edit> }、Edit { span: Span, replace: String }
    pub notes: Vec<Note>,           // Note { span: Option<Span>, message }（位置の無い note は規則を示す、S-114）

```

JSON は §18.1 の形そのもの（`span` は `file` / `line` / `col` / `end_line` / `end_col` に展開し、`end_line` は常に出す。列は文字で数える）。挿入は空の範囲の置き換えで表し、`insert_before` / `insert_after` は持たない（レビュー R-87、S-81）。修正候補の範囲は CST のトークンの範囲から作る（R-86）。

### 3.2 AST（`onsa_syntax`）

- `Token { kind, span }` の列。空白・改行・コメント・doc コメントも独立したトークン（trivia）で、トークンの列はソースの全てのバイトを重ならずに覆う（W3-01）。あるトークンの前が「何も無い・空白・改行」のどれかは、一つの関数 `gap_before` で全体の列から読む（トークンに印を持たない）。
- 構文解析器は CST（全てのトークンを持つ損失の無い構文木）を作り、AST は CST から一つの段で作る（D-02 の改定、レビュー R-86）。CST を出力すると、元のソースと 1 バイトも違わない（性質テストで確かめる）。
- `Item`（`Fn` / `Flow` / `Struct` / `Enum` / `TypeAlias` / `Trait` / `Impl` / `Effect` / `Handler` / `Const` / `Use` / `Extern` / `Target` / `Test`）、`Type`、`Pattern`、`Expr`、`Stmt`、`Attr`。全てのノードが `Span` を持つ。
- 式の二項演算は構文解析では **平らな列** `Binary { operands: Vec<ExprId>, ops: Vec<(BinOp, Span)> }` として保持し、群の検査（E0010）は構文解析の直後の独立した段で行う。これにより E0010 の修正候補（括弧の挿入位置）を列全体から作れる。
- `Call { callee, kind: Plain | Flow (~) | Bang (!) , args: Vec<Arg> }`、`Arg { mode: Borrow | Inout | Move, expr }`。
- `Attr::Param { keys: Vec<(key, const expr)> }` は flow の入力にだけ付く。
- flow の入出力の宣言は値の型とクロック（`at`）を持ち、式は `At { expr, clock }`（`e at k`）と帰還の参照 `Feedback(name)`（`^名前`）を持つ（S-44、S-102）。`let` は属性（`@mem(bulk)`、S-43）を持つ。クロックの名前は型ではなく、クロックの名前空間の名前（§11.3）。

### 3.3 型と種（`onsa_sema`）

- `Ty` はインターン（`TyId(u32)`）: `Int(IntKind)`, `Float(F32|F64)`, `Bool`, `Char`, `Unit`, `Array(TyId, u32)`, `Tuple(Vec<TyId>)`, `Named(DefId, Vec<GenericArg>)`, `Span(TyId)`, `Fn(FnSig)`, `Ptr(TyId)`, `Buf(TyId)`（第 1 期はインタプリタ限定）, `Var(TyVarId)`（推論中）。
  クロックは型ではなく、flow の計画（§3.5）の属性である（S-102 で `Rate(Rate, TyId)` を取り除いた）。
- 種は `Kind::{Copy, Shared, Affine}` を型の構造から計算して `TyId` ごとにキャッシュする。
- 大きさと配置は、Core の降下の後のターゲットの pass が計算して Module に記録する（レビュー R-80、D-03 の追記）。`onsa interface`、`SIZE`、`_Static_assert`、プローブ、ホットリロードは記録を読む。sema は大きさを計算しない。
- 推論の状態は `Infer { vars: Vec<Option<TyId>>, lits: Vec<LitConstraint> }`。文の順に進め、関数の終わりで未解決の `IntLit` は `I32` にし（S-22、仕様 §4.7）、未解決の `FloatLit` を E0405 にする。
- 名前の解決（レビュー R-84、S-78、D-15）: 型付けの前に一つの段を置き、本体の全ての経路と呼び出し先を一度だけ解決して記録する（`PathTarget` / `Callee`）。
  この段が決めるのは、経路の先頭（ローカル、`self`、型と定数のパラメータ、モジュールの項目、`use` の名前、prelude、組込み型）、モジュールと flow の名前空間の経路、列挙子、型の関連項目（`Point.new`、`F32.PI`、`T.ZERO`、`Fs.read`）、flow の予約名（`prev`、`delay`、`vdelay`、`sample_rate`）。
  値の後のフィールドとメソッドの呼び出しは、値の型が要るので型付けに残す。型別名は、この段で一度だけ元の型（型引数を含む）に解決する（S-91）。型付けは解決の記録を読み、解決をやり直さない。名前の隠蔽は全て E0304（S-79）なので、ある位置の名前が指すものは一つで、優先順位の規則は要らない。
- パッケージのモデル（レビュー R-88、S-83、D-15）: パッケージは ID で識別し、パッケージごとに「見える依存の表（キー → パッケージ ID）」を持つ。同じパッケージ（同じ名前と版）は一度だけ解析し、同じ DefId を共有する（菱形の依存で二重に解析しない）。名前で見えるのは、そのパッケージが宣言した依存と暗黙の `std` だけ（§15.1）。
  std は名前ではなく役割（driver が読み込んだ埋め込みの std に付ける印）で見分け、std の特権（`target` 宣言、組込み型への `impl`、効果の宣言、lang item）は全てこの役割を読む。依存の図は driver が一度だけ作り、sema は受け取る。
  今の依存は std だけだが、作りは std 以外の依存を受けられる形にする（取得元と版の解決は第 2 期、計画 §5）。`std = "x.y.z"` は埋め込みの std の版と比べる。

### 3.5 flow の降下の形

- 追記（2026-10-05、レビュー R-92）: flow の計画は、状態のフィールドごとに「`init` で設定する値（遅延の初期値、`T.default()`、0、`false` など）」か「段の順で読む前に必ず書かれる（`init` では設定しない）」かを記録する。`init` の降下はこれを読み、状態を `Zeroed` で作ってから一部だけ代入する作りをやめる（§3.4 の追記、検証器の V-17）。
- 追記（2026-10-05、レビュー R-91、D-15）: sema の flow の検査が、flow ごとに「flow の計画」を一つ作って記録する。
  計画は、ノードの一覧（`let`、巻き上げた部分式（S-33）、インスタンス、遅延の組込み、`par`）、各ノードのレートと評価の段（`init` / `ctl` / `tick`）、状態のフィールドの一覧（§11.6 / S-65 の名前。名前を作る処理は一つの関数）、ノードの所属（スパンの包含ではなく木の構造で）、依存と帰還（`^`）の辺を持つ。
  `let` と入力を状態に入れる判断は、計画を作るときに一度だけ行う（今は `let` を sema の `mark`、入力を Core の `ReadWalk` が判断し、降下が論理和を取っている）。Core の降下、`onsa graph`、`onsa interface` は計画を読むだけにする。子の列挙は一つの関数にする。
  レートは不動点の反復をやめ、`let` の順の一度の走査で決める（名前は上から順に定義し、前方の参照は遅延の第 1 引数の中の `^名前` だけで、その引数は `sample` なので、帰還を除いた依存は閉路を持たない。§11.2、S-44、E0813）。`^` の参照が `sample` であることは、全ての `let` のレートが決まった後に検査する。
  クロックやマルチレート（§19.1）でこの前提が変わるときは見直す。 追記（2026-10-05、R-98、S-86）: 計画は、各ノードの構造上の位置（含む `let` か出力と、式の中の経路）も持ち、LSP の拡張と `onsa interface` に出す。ホットリロードとプローブの付け替えは、生成する名前ではなくこれで旧新を照合する（§18.3）。
  名前は §11.6 の規則（含む `let` で修飾、`let` ごと・種類ごとに字面の順）で、計画を作る一つの関数が付ける。

D-03 の 5 関数。§17.3 の `resonator` なら次の形になる（擬似 Onsa）。

```
struct resonator.State {
  sample_rate: F32   // block の値の計算に使う（§12.4）
  b1: F32            // sample から読まれる block の let。r と w は block の中でしか使わないので置かない
  b2: F32
  y.hoist_0: F32     // 巻き上げた部分式 1.0 - r（S-33。sample の式の中の block の部分式）
  y1: prev[F32]      // prev~(^y) の保存値
  y2: prev[F32]      // prev~(y1) の保存値
  poisoned: Bool
  initialized: Bool  // export の境界（S-27）
}
fn resonator.init(cfg: resonator.Config, sr: F32) -> State {
  // b1、b2、y.hoist_0 は ctl が読む前に必ず書くので設定しない（R-92）
  State { sample_rate: sr, y1: 0.0, y2: 0.0, poisoned: false, initialized: true }
}
rt fn resonator.reset(inout s) { s.y1 = 0.0; s.y2 = 0.0; s.poisoned = false }
rt fn resonator.ctl(inout s, params: Params) {
  let r = exp(-(F32.PI * params.bw) / s.sample_rate)   // 状態に置かないローカル
  let w = (2.0 * F32.PI * params.fc) / s.sample_rate
  s.b1 = 2.0 * r * cos(w)
  s.b2 = r * r
  s.y.hoist_0 = 1.0 - r
}
rt fn resonator.tick(inout s, x: F32) -> F32 {
  let y1 = s.y1                       // 遅延の出力（保存値）を先に読む
  let y2 = s.y2
  let y = s.y.hoist_0 * x + s.b1 * y1 - s.b2 * y2
  s.y1 = y                            // 保存はまとめて最後に（R-13）。prev~(^y): y を保存
  s.y2 = y1                           // prev~(y1): y1 を保存
  y
}
rt fn resonator.process(inout s, params, input: Span[F32], inout output: Span[F32]) {
  // 長さの検査（違えば panic）
  resonator.ctl(inout s, params)
  for i in 0..<input.len() { let xi = input[i]; let yi = resonator.tick(inout s, xi); output[i] = yi }
}
```

- 遅延の保存は、全ての遅延の出力を読み、保存する値を全て評価した後に、`tick` の末尾でまとめて行う（仕様 §11.4、R-13 の二相化）。遅延の値の式の中の遅延（`prev~(prev~(x))`）は保存の前の出力を読む。複数の `prev~` が同じ信号を参照しても、保存は各ノードが独立に持つ。
- `delay` / `vdelay` は §11.4 の演算順をそのまま `tick` の中に展開する（関数にしない。順序を固定したいため）。
- 分岐（S-110）: 普通の `if` / `match` の枝と `&&` / `||` の右辺は、条件の内側に降下する（取られた枝だけを評価する。枝に状態を持つものは無い）。`if~` / `match~` は全ての枝を評価してから選ぶ（評価済みの値の選択）。
  flow の計画は、普通の `if` の枝と評価されないことがある右辺から、panic しうる部分式を巻き上げない（演算の分類は R-81 / R-79 の `Prim` の表。利用者の関数の呼び出しは、panic しないと分からなければ panic しうるとみなす）。
- 親の `tick` は子の `tick` を `Call` で呼ぶ。子の `block` の入力に渡す親の値は、親の `ctl` で子の `Params` を組み立てて子の `ctl` を呼ぶ。
- `par` は `[sub.State; N]` と `ForRange` に落とし、`i` はループ変数（`init` のクロックの値）。
- （2026-10-06、点検 C-66: 例を S-27、S-30、S-33、S-44、S-86、S-102、R-13、R-92 に合わせた。名前と巻き上げの細部は点検の C-36。）
