## 1. 実装の判断（D）

全て 2026-10-01 に案の通り決定。

### D-01 字句解析器と構文解析器は手書き（再帰下降）

- 案: パーサジェネレータを使わず、手書きの字句解析器と再帰下降の構文解析器にする。
- 理由: (1) 文の区切りが改行に依存し、文脈（ブロックの中か、括弧の中か）で改行の意味が変わる（§2.5）。ジェネレータでは字句解析器に文脈を戻す経路が要る。(2) 既存言語の書き方への修正候補（§18.1）は、エラー回復の中で「何を書こうとしたか」を推定する専用の規則で、手書きでしか書けない。(3) LSP で編集中のソースを扱うには、エラーから回復して AST を作り続ける必要がある。
- 代替: `lalrpop` / `pest`。文法の検証には使えるが、上記 3 点で結局手書きの層が要る。

### D-02 AST はアリーナ + ID。スパンはバイトオフセット

- 案: 各ノードは `Vec` に置き、`ExprId(u32)` などの ID で参照する。スパンは `Span { start: u32, end: u32 }`（ファイル内のバイトオフセット）。行・列は `LineIndex` で必要なときに計算する。トークンの前後の空白とコメント（trivia）はトークン列に残し、AST はトークン列への索引を持つ（`fmt` と `diff --ast` が使う）。
- 理由: `Box` のツリーは `wasm32` でも動くが、LSP で部分的に差し替えるのと、`fmt` でトークンの前後の空白を再現するのに、ID と索引の方が扱いやすい。rust-analyzer と同じ方向。
- 代替: `Box` のツリー。最初は速いが、`fmt` でコメントの位置を失う。
- 改定（2026-10-05、レビュー R-86）: 段を「字句解析 → CST → AST → sema」にする。CST は全てのトークン（コメント、改行、空白を含む）を持つ損失の無い構文木で、構文解析器が作り、誤りの回復（S-59）もこの木の上で行う。AST は CST から一つの段で作り、ここに書いたアリーナと ID の形のまま sema が使う。`fmt` は CST を読み、S-56 の書き換えの一覧も CST の上で行う（取り除くノードに付いたコメントは残す）。診断の修正候補の範囲（R-87）と LSP の位置は、CST のトークンの範囲で表す。CST は自前の簡単な作りにし、外部のライブラリは使わない（D-09）。元の案（AST がトークン列への索引を持つ）は実装されず、`fmt` は AST の位置からコメントと区切り文字を推測していた（R-70 の 17 の形のうち 15 を書き換える）。トークン列に索引を持つ形より CST を選んだのは、trivia の位置が構造で保証され（ノードの範囲とトークンの境界の一致という不変条件に頼らない）、誤りを含むコードにも完全な木があり（LSP）、差分での再解析と構造を書き換える編集（第 2 期以降の補完やリファクタリング）の土台になるため。S-58（コメントの結び付け）は CST の上で作る（CST が先か同じ回）。

### D-03 Core IR は構造化ツリー。flow は `init` / `reset` / `ctl` / `tick` / `process` の 5 関数に落とす

- 案: Core は CFG / SSA ではなく、**構造化された文と式のツリー** にする（`if` / `while` / `for` の範囲、`match` は enum のタグの `switch`）。全てのバックエンドがソース（C / JS）か構造化バイトコード（WASM）なので、CFG に落とすと構造を復元する作業が各バックエンドに要る。
- flow は次の 5 つの Core 関数に落とす（計画 §2.2 の `process` を 2 つに分けたもの）。

| 関数 | 内容 | 呼ばれる場所 |
|---|---|---|
| `f.init(cfg, sr) -> State` | `Init` レートの `let` を評価して状態を構築 | 利用者、親の `init` |
| `f.reset(inout s)` | 遅延と `prev` を `init` 値へ、`w = 0`、サブインスタンスを `reset`、`poisoned = false` | 利用者、親の `reset` |
| `f.ctl(inout s, p: Params)` | `Ctl` レートの `let` を順に評価し、`Sig` から参照されるものを状態へ書く。サブインスタンスの `ctl` を呼ぶ | `f.process` の先頭、親の `ctl` |
| `f.tick(inout s, <Sig 入力の値>...) -> <出力の値>` | `Sig` レートの `let` を順に評価する 1 サンプル分。サブインスタンスの `tick` を呼ぶ | `f.process` のループ、親の `tick` |
| `f.process(inout s, p, <Span>...)` | `ctl` を 1 回呼び、`for i in 0..frames` で入力を全て読み、`tick`、出力を全て書く（§11.6 の不変条件） | 利用者、export の wrapper |

- `process_inplace` は `process` に同じ `Span` を渡すだけの関数。`render` は `Buf` を確保して `process` を 1 回呼ぶ（インタプリタと `Alloc` のあるターゲットだけ）。
- 理由: 親 flow が子を点ごとに呼ぶには、子のブロックレートの計算（`ctl`）とサンプルの計算（`tick`）が分かれていなければならない。FAUST の `compute` を `control` と `loop` に分けた形と同じ。`tick` が関数呼び出しになるのは C コンパイラがインライン化するので問題ない。
- 代替: 子の `process` をブロック単位で呼び、中間バッファを置く。状態の大きさにブロック長が入り、§12.4 の「コンパイル時に決まる」が崩れる。
- 追記（2026-10-04、レビュー R-80）: 降下はターゲットによらない形にし、その後に **ターゲットの pass** を置く。この pass が、bulk の分割（R-90 (i)）、配置（大きさ・アラインメント・オフセット）と溢れの検査を行い、結果を Module に記録する。C、`onsa interface`（S-65 の `--target`）、`onsa audit`、E0820、WASM / JS は記録を読むだけで、計算し直さない。sema の `layout.rs` は消す（言語の意味として大きさを使う所は S-32 で無くなった）。到達解析は Core に一つ（`reach(module, roots)`）で、C の生成の範囲、`--backends all` の超越関数の判定（§13.4）、`onsa audit --panics` が使い、走査（`walk`）も Core のものだけにする。NRVO は Core の一か所で §12.7 どおり（全ての経路で返すローカルが一つ）に判定して記録し、C と監査はそれを読む（R-81 で結果の置き場所を明示するときに行う）。
- 追記（2026-10-04、レビュー R-81）: 降下の最後に正規化の段を置き、次の形にする。R1: 書き込みを持つ式（`inout` を渡す呼び出し、代入）と、文を含む式（`Block`、`IfExpr`、`Switch`）は、文の位置にだけ置く。R2: 文の位置の式の木に含まれる、効果を持つ演算（panic しうる演算、効果を持つ呼び出し）は、木全体で一つまで。残りは純粋な演算（panic も書き込みも無い）にする。R3: 文の位置へ出すものは評価順（§3.5）どおりに並べ、書き込みを持つ式を出すときは、それより先に評価される部分のうち、その書き込みが届きうる場所を読むものを先に出す。R4: 条件付きで評価される部分（`&&` / `||` の右辺、`if` / `match` の腕）から出すものは、その条件の内側に出す。木の中に書き込みが無く、観測できる演算が一つだけなので、バックエンドは木をどの順で評価してもよく、文を順に出し、条件付きの評価（C / JS の `&&` と `?:`、WASM の `if`）を保つだけでよい。演算の分類（純粋・panic しうる・書き込みを持つ）は Core の一か所で決め、プリミティブの分類は R-79 の `Prim` の表に欄として持たせる。検証器（R-82）が R1・R2 を検査し、R3・R4 は評価順の再現の期待値付きテストと、インタプリタと C の差分テストで押さえる。移動とコピーを区別して表す。破棄は `Drop(place)` の文として、sema が経路を見て列挙した破棄の点（R-32）から写す。型ごとの破棄の種類（何もしない／ヒープの解放・参照カウント／利用者の `Drop`）は Core で一度だけ決め、各バックエンドは破棄の種類を `_` 無しで網羅し、実装していない種類は生成の前に E0200 にする。検証器は「所有する値は全ての経路でちょうど一度、移動か破棄される。移動・破棄の後は使わない」を検査し、インタプリタは破棄・移動した後の値を読むと内部エラーにする（テストでは常に有効）。結果の置き場所は Core に明示する（集成体を作る式に宛先の場所を持たせ、sret の関数には返り値の置き場所のローカルを置き、NRVO はそれへの割り当てとして記録する）。宛先が構築に使う値から読まれうる場合は、一時変数に作ってからコピーする（§12.7、S-76）。重なりの判定の関数は一つにし、sema の E0702 と共有する（場所の経路を表す小さな型を共有する）。進め方は R-06 と同じ: 設計メモを先に書かせて親が読み、最も能力の高いモデルに推論を深くして実装させ、別のエージェントが仕様だけから期待値付きのテストを書いて壊しにいく。
- 追記（2026-10-05、レビュー R-89、D-15）: Core の段を「降下 → 正規化 → 定数の評価 → ターゲットの pass → export の計画」とする。定数の評価は、関数を呼ぶ `const` の初期化式を評価してリテラルに置き換える段で、ターゲットによらない（超越関数を含む定数の評価に何を使うかは R-108）。今は driver のビルドの経路にだけあり（`inline_consts`）、テストの `emit_c` は通っていない。export の計画は、パッケージとターゲットごとに一度だけ作る記録で、flow ごとにシンボル（`prefix` + 名前、重なりは E1011）、生成する API（`init` / `reset` / `process` / `render` と入出力の形、S-30）、状態とパラメータの配置への参照、パラメータの情報（`@param`）、panic の扱い（§9.2）と、そのために状態が持つフィールドを持ち、関数ごとにシンボル、FFI の型のシグネチャ、panic の通知を持つ。降下が作る状態のフィールド（`poisoned`、`initialized`、bulk のポインタ）は、作った時点で役割の印を付けて記録し、名前の文字列で探さない。入出力の役割は `FlowMeta` の明示の一覧から取り、引数の位置（`skip(2)`）で決めない。C・WASM・JS のバックエンド、`play`、ブラウザの IDE のパラメータの UI は、この計画を読むだけにする。計画の中身のうち、C の API の名前空間・ABI の版・関数の panic の通知（R-121）と、パラメータの ID（§11.7）は、それぞれの決定で埋める。テストは、ビルドと同じ入口（D-05 の改定、R-80 (5)）を通り、定数の評価と export の計画の段まで含める。

### D-04 診断の登録簿はマクロで作る Rust の表。`explain` の本文は markdown ファイル

- 案: `onsa_diag/src/codes.rs` に `codes! { E0010 => { category: Syntax, message: "..." }, ... }` の形で全コードを書き、`explain` の本文は `onsa_diag/explain/E0010.md` を `include_str!` で埋め込む。テストで「仕様 §18.1 の範囲に収まる」「本文のファイルが全コード分ある（M9 の受け入れ）」を検査する。
- 理由: コードの追加漏れをコンパイルエラーにしたい。本文は長文なので Rust ソースから分ける。
- 代替: TOML の登録簿を実行時に読む。`wasm32` で `include_str!` にするなら差は無いが、型の検査が無い。
- 追記（2026-10-05、レビュー R-87、D-15）: 登録簿の各コードに、段（S-78 の構文・名前・型・引数のモードと移動・rt と効果と、降下・ビルド）と、修正候補が必須かを持たせる。CLI、fmt、テストはこの属性を読み、番号の範囲（`number() <= 20`）やテストの中のコードの一覧で判定しない。修正候補が必須のコードで候補が無ければ、全てのテストで落ちる。既存言語の書き方の検出（E0020）は一つのモジュールの規則の表に集め（文脈、検出する形、候補の組）、構文解析器は解析に失敗した点でそこに問い合わせる（候補を作れなければ E0002、S-48）。キーワードの判定は、`TokenKind` の宣言の順序に依らない明示の一覧にする。

### D-05 `tests/spec` の形式はインラインのマーカ

- 案: 期待する診断を、同じ行の末尾に `//~ E0010` と書く（rustc の UI テストと同じ形。`//~ E0010 @13` で列も指定できる）。マーカの無いファイルは診断 0 件を期待する。ファイルの先頭行で検査の深さを指定する:

```
//! mode: none      // 収録のみで実行しない（`...` を含む断片、最上位の文、擬似コード）
//! mode: parse     // 構文解析だけ（第 1 期で未対応の fn 世界の例）
//! mode: check     // check --json の結果をマーカと比較（既定）
//! mode: test      // check の後、test ブロックをインタプリタで実行する
```

- 理由: 別ファイルの `.expect` より、否定例の意図が行の横に見える。仕様の例を含むファイルにマーカを足しても、§6 の同期検査（D-06）はマーカを無視して照合できる。
- 代替: 計画 §1 の `.expect`。JSON の全文を比較できるが、行番号のずれで壊れやすい。
- 改定（2026-10-04、レビュー R-80）: ファイル単位のテストの設定は、先頭のコメントに書く `onsa.toml` の断片に一本化し、`//! mode:` をやめる（S-51 で `//!` はモジュールの doc になり、同じ見た目で違う意味になっていた）。断片は `// onsa.toml` の行の後に続くコメントで、マニフェストと同じ構造体で読む（未知のキーは R-130 の決定に従う）。テスト専用の設定は `[test]` の表に置く（`mode = "none" | "parse" | "check" | "test"`、既定は `check`）。C などのバックエンドの事例は、同じ断片に `[targets.*]` と `[export]` を書き、事例とターゲットの組ごとに期待値を置く（`tests/golden/c/echo.poison.c`）。テスト専用の既定値は作らず、ターゲットの欄は全て書く。複数モジュールの事例は、ディレクトリと `onsa.toml` のパッケージにする（§15.1 の単一ファイルのパッケージとパッケージの 2 つの形と同じ対応）。行ごとの期待値 `//~` は今のまま。golden・C のコンパイル・適合性のテストは、ディレクトリを走査して事例を集め、Rust に事例の表を持たない（表が二つに分かれて食い違っていた）。ビルドの入口をファイルの読み込みから分け、マニフェストの値とソースの一覧を受け取る関数にする（テストと `onsa_web` が使う）。D-06 の同期検査は、ファイルの先頭に断片があっても、仕様のブロックがそのまま含まれていればよい。

### D-06 仕様の例と `tests/spec` の同期を機械的に検査する

- 案: `tools/check_spec_examples.py` が、仕様の全ての ```` ```onsa ```` ブロックについて「`tests/spec/` のどれかのファイルに、行末の `//~ ...` を除いて逐語的に含まれる」ことを検査し、CI で回す。擬似コードや `...` を含む断片は `mode: none` のファイルに収録する（S-15 は不要になった）。
- 理由: P9（仕様の例は全て検査を通る）を仕様の編集のたびに保証する。
- 代替: 仕様から自動で切り出す。断片（§3.1、§5.1、§7）は関数で包まないと検査できないので、手で用意した上で照合する方が確実。

### D-07 `std` は Onsa のソースで書き、プリミティブは `target fn` で宣言する。ソースはバイナリに埋め込む

- 案: `std/math.onsa` は次のように書く。

```onsa
pub target rt fn exp[T: Float](x: T) -> T
pub target rt fn sqrt[T: Float](x: T) -> T
```

  各バックエンド（インタプリタ、C、WASM、JS）が `std.math` の `target` 宣言の実装を持つ。`std` のソースは `include_str!` でコンパイラに埋め込み、`wasm32` でもファイル I/O なしで使える。利用者のパッケージの `target` 宣言は、第 1 期では `bind` が無いので E0200。

- 理由: §15.2 の `target` は「実装をビルドターゲットが与える宣言」で、プリミティブの意味そのもの。`extern "C"` にすると核が C 系以外へ出せなくなる（§13.2 の E1010）。
- 代替: コンパイラ組込みの名前。ソースが無いので `onsa primer --std` と `interface` に出すものを別に持つことになる。
- 追記（2026-10-04、レビュー R-79、S-69）: 組込み型のメソッド・関連関数・関連定数も、std の `impl` に Onsa で宣言する（`impl I32 { pub target rt fn narrow_i8(self) -> Option[I8] }`、`impl[T] Buf[T] { pub target fn zeroed(n: U32) -> Buf[T] uses {Alloc} }`）。他の操作で書けるものは本体ごと std に書き、プリミティブだけを `target` にする。`[T; N]` と `Buf[T]` の受け手は `Span[T]` のメソッドを引く（§5.3）。rt・効果・引数のモード・doc は通常の規則で扱い、`rt.rs` / `effects.rs` の名前による特別扱いを無くす。Rust に残す表は、std の `target` 宣言の修飾名 → `Prim`（std の宣言と 1 対 1 であることをテストで確かめる）、組込み型の trait（§6.3。第 1 期の暫定で、第 2 期に std の `impl` へ移す。S-72）、`as` の可否（§3.3）、Option / Result の lang item（S-71）、`array.from_fn` の展開だけ。理由: 第 2 期に足す API（`Str`、`Map`、`Set`、`Array`、`Bytes`）の大半は組込み型のメソッドで、表に持つと全てがプリミティブになり、各バックエンドで実装し直すことになる。API の追加が std の差分として見え、仕様の一覧と照らしやすい。
- 追記（2026-10-04、レビュー R-79、S-71）: Option / Result も std の enum として宣言する（§4.1）。コンパイラが知るのは lang item の表（std の経路 → 役割）の 2 行だけで、使い道は prelude と `?` に限る。sema は `?` ごとに早期に返る列挙子の番号を決めて Core に渡す。std の `target` 宣言の引数と返り値には Option / Result を使わない（スカラ、配列、タプル、`Span` だけ）。Option を返すメソッド（`get`、`narrow_*`、`checked_*`）は std に Onsa で書き、範囲の比較などの後で、std の中だけで見える（`pub` の無い）プリミティブを使う。バックエンドは Option / Result の配置を知らずに済み、一般の enum に対応すれば動く。
- 追記（2026-10-04、レビュー R-80）: std のモジュールの一覧は、build.rs で `std/` のファイルから生成する（モジュールの経路はファイルの経路から決める。§15.1 と同じ規則）。driver とテストに手書きの表を持たない。std のファイルを足すだけで済む。
- 追記（2026-10-04）: `array.from_fn` の特別な展開（無名関数をその場に展開する）は、Core が関数値を扱えない第 1 期の回避策である。M5 で `std.test.check` のために関数値を降下するときに、普通のプリミティブへ寄せる（R-08 補足）。

### D-08 第 1 期の効果の扱い: `Alloc` だけを認識し、`test` ブロックの中でだけ使える

- 案: 効果行は構文解析と名前解決まで通す。第 1 期で意味を持つのは `Alloc` だけで、他の効果名は E0200。`Alloc` を要する操作（`Buf.zeroed`、`render`、`impulse`）は、`uses {Alloc}` を持つ関数と `test` の本体でだけ呼べる（§8.5 の「テストランナーが `Alloc` を提供する」の部分だけを実装する）。`Buf[T]` はインタプリタの内蔵型で、C / WASM / JS バックエンドは `Buf` を含む関数を出力しない（E0200）。
- 理由: M3 の受け入れ（`resonator decays`）が `impulse(48000) -> Buf[F32] uses {Alloc}` と `o.out: Buf[F32]` を使う。効果の仕組み全体（handler、証拠渡し）を入れずに、この経路だけを通す。
- 代替: `render` を `[F32; N]` を返す形にして `Buf` を避ける。`N` が実行時の値なので無理。
- 追記（2026-10-03、レビュー R-27）: 効果行の変数（`[e]` と `uses {e}`）も第 1 期では宣言の時点で E0200 にする。効果の多相は、第 2 期に handler と一緒に入れる。
- 追記（2026-10-04、レビュー R-129、S-74）: 効果行の名前は、他の名前と同じく解決する（見つからなければ E0302）。第 1 期は、効果の宣言を std の中でだけ受け付け（名前と操作のシグネチャを集める）、利用者の `effect` 宣言は E0200 のまま。std は `pub effect Alloc {}` を宣言して prelude に入れ、コンパイラは lang item として知る。`Random` も std に宣言し（モジュールの名前は仮。第 2 期の std の設計で確定する）、`std/test.onsa` は `use` で取り込む。`Alloc` 以外の効果を効果行に書くと、名前が解決できた上で E0200。

### D-10 C の出力単位と名前

- 案: パッケージごとに 1 つの翻訳単位 `onsa_<package>.c` と、export する flow ごとのヘッダ `onsa_<flow>.h`、共通の `onsa.h`。内部の名前はモジュールパスを `__` でつないだ `static` 関数（`dsp__voice__tick`）。型は `dsp__voice__State`。export は `prefix` + 名前の最後の要素（§14.2）。固定長配列は `struct { T a[N]; }` で包み、値として扱えるようにする。集成体を返す関数は出力ポインタを第 1 引数に取る（§12.7）。
- 理由: 1 翻訳単位なら C コンパイラが `tick` をインライン化できる。配列を struct で包むのは、C の配列が値でないため。

### D-11 WASM の libm は musl を Onsa に移植したもの（= `std.math.exact` の先行実装）

- 案: `expf` / `logf` / `sinf` / `cosf` / `tanf` / `tanhf` / `powf` / `exp2f` / `log2f` と F64 版を、musl の実装から Onsa の `rt fn` に移植して `std/math/soft.onsa` に置く。WASM バックエンドは `std.math` の `target` 宣言をこれに束縛する。移植には `F32.to_bits()` / `F32.from_bits()` が要る（S-09）。
- 理由: WASM には libm が無い。C で書いた libm を wasm に別途コンパイルするとツールチェーンが増える。Onsa で書けば核のまま WASM / JS / C の全てで使え、§19 の `std.math.exact` と、libm の精度が足りない組込み向けの差し替え（§13.4）が同じもので済む。
- 代替: JS の `Math` を import する。AudioWorklet から import 関数を呼ぶ往復が重く、精度も環境依存。

### D-12 精度テストの参照値は mpmath で生成した表

- 案: `tools/gen_precision_tables.py`（mpmath）で、関数ごとに 4096 点（境界値、非正規化数、大きな値、乱数）の正しく丸めた値を生成し、`tests/precision/*.bin` に置く。テストは各環境の結果と比べて ULP 差を測る。
- 理由: MPFR を Rust から使う `rug` は C のビルドが要り、`wasm32` でも CI でも重い。表なら依存が無い。

### D-13 `play` は C → 共有ライブラリ → `libloading` + `cpal`。UI は端末

- 案: `onsa play voice` は M4 の経路で C を出力し、ホストの C コンパイラで共有ライブラリにして `libloading` で読み、`cpal` で鳴らす。パラメータは端末のキー操作（`@param` の一覧をスライダ風に表示）。GUI は IDE 側（M7 の `onsa_web` を使うブラウザ IDE）で作る。
- 理由: インタプリタはサンプル単位の `tick` には遅く、実時間の試聴に向かない。共有ライブラリなら M4 の生成物をそのまま使える。
- 代替: インタプリタで実時間。単純な flow なら動くが、保証できない。

### D-15 処理は一度だけ行い、後の段は前の段が出力した構造を受け取る

- 案: コンパイラの各段は、同じ判断や計算を繰り返さない。ある段が決めたこと（型、移動と破棄、評価順、結果の置き場所、配置、到達）は、その段が出力する構造に書き込む。後の段はその構造を入力として受け取り、次の構造を出力する。後の段が前の段の判断をやり直したり、別の規則で計算し直したりしない。
- 複数の段が同じ定義（`Prim` の表、`as` の表、演算の分類、場所の重なりの判定）を使うときは、宣言的な表か一つの関数として一か所に置き、各段はそれを参照する。
- 検証器（§3.4）も同じ原則に従う段である。前の段が出力した構造（Core）を入力にして、その構造が満たすべき性質を確かめる。前の段の処理をやり直さず、計算の結果も計算し直さない（配置なら、値を再計算せずに、オフセットの整列やフィールドの重なりが無いことを確かめる）。確かめる材料は前の段の出力の構造そのもので、前の段が構造の外に残した途中の記録（降下の補助関数、別の表に置いた移動の記録など）には頼らない。共有する表に誤りがあれば前の段と検証器の両方を通ってしまうので、表は仕様と照らすテストで確かめる。
- 注意: これは「各段が他の段に頼らず、自分で計算する」という意味ではない。そう読むと、同じ処理を複数の段で作り直すことになる。本質は、各段が同じことをせず、処理済みの構造をもとに次の段が進むことである（利用者の指摘、2026-10-05）。
- 理由: 同じ判断を複数の場所で行うと、片方だけが直って食い違う。レビュー R-80 の重複（配置、NRVO、到達解析、効果の集計など）は、全てこの原則の違反だった。
- 代替: 各段が必要な事実をその場で計算する。今の実装の形で、R-80 の食い違いの原因になった。

## 3. 共通の設計

計画 §2 を実装の型に落としたもの。クレートの境界で共有する。

### 3.1 スパンと診断（`onsa_diag`）

```rust
pub struct FileId(u32);

pub struct Diagnostic {
    pub code: Code,                 // D-04 の登録簿
    pub message: String,            // 英語。登録簿のテンプレートに名前を埋めたもの
    pub span: Span,
    pub found: Option<String>,      // 問題の箇所のソース
    pub fixes: Vec<Fix>,            // Fix { title: String, edits: Vec<Edit> }、Edit { span: Span, replace: String }
    pub notes: Vec<(Span, String)>, // 関連位置（「ここで束縛された」など）

```

JSON は §18.1 の形そのもの（`span` は `file` / `line` / `col` / `end_line` / `end_col` に展開し、`end_line` は常に出す。列は文字で数える）。挿入は空の範囲の置き換えで表し、`insert_before` / `insert_after` は持たない（レビュー R-87、S-81）。修正候補の範囲は CST のトークンの範囲から作る（R-86）。

### 3.2 AST（`onsa_syntax`）

- `Token { kind, span }` の列。コメントと空白は `Trivia` としてトークンに付属させる（`fmt` が使う）。
- 構文解析器は CST（全てのトークンを持つ損失の無い構文木）を作り、AST は CST から一つの段で作る（D-02 の改定、レビュー R-86）。CST を出力すると、元のソースと 1 バイトも違わない（性質テストで確かめる）。
- `Item`（`Fn` / `Flow` / `Struct` / `Enum` / `TypeAlias` / `Trait` / `Impl` / `Effect` / `Handler` / `Const` / `Use` / `Extern` / `Target` / `Test`）、`Type`、`Pattern`、`Expr`、`Stmt`、`Attr`。全てのノードが `Span` を持つ。
- 式の二項演算は構文解析では **平らな列** `Binary { operands: Vec<ExprId>, ops: Vec<(BinOp, Span)> }` として保持し、群の検査（E0010）は構文解析の直後の独立した段で行う。これにより E0010 の修正候補（括弧の挿入位置）を列全体から作れる。
- `Call { callee, kind: Plain | Flow (~) | Bang (!) , args: Vec<Arg> }`、`Arg { mode: Borrow | Inout | Move, expr }`。
- `Attr::Param { keys: Vec<(key, const expr)> }` は flow の入力にだけ付く。

### 3.3 型と種（`onsa_sema`）

- `Ty` はインターン（`TyId(u32)`）: `Int(IntKind)`, `Float(F32|F64)`, `Bool`, `Char`, `Unit`, `Array(TyId, u32)`, `Tuple(Vec<TyId>)`, `Named(DefId, Vec<GenericArg>)`, `Span(TyId)`, `Fn(FnSig)`, `Ptr(TyId)`, `Buf(TyId)`（第 1 期はインタプリタ限定）, `Rate(Rate, TyId)`（flow の中だけ）, `Var(TyVarId)`（推論中）。
- 種は `Kind::{Copy, Shared, Affine}` を型の構造から計算して `TyId` ごとにキャッシュする。
- 大きさと配置は、Core の降下の後のターゲットの pass が計算して Module に記録する（レビュー R-80、D-03 の追記）。`onsa interface`、`SIZE`、`_Static_assert`、プローブ、ホットリロードは記録を読む。sema は大きさを計算しない。
- 推論の状態は `Infer { vars: Vec<Option<TyId>>, lits: Vec<LitConstraint> }`。文の順に進め、関数の終わりで未解決の `IntLit` / `FloatLit` を E0405 にする。
- 名前の解決（レビュー R-84、S-78、D-15）: 型付けの前に一つの段を置き、本体の全ての経路と呼び出し先を一度だけ解決して記録する（`PathTarget` / `Callee`）。この段が決めるのは、経路の先頭（ローカル、`self`、型と定数のパラメータ、モジュールの項目、`use` の名前、prelude、組込み型）、モジュールと flow の名前空間の経路、列挙子、型の関連項目（`Point.new`、`F32.PI`、`T.ZERO`、`Fs.read`）、flow の予約名（`prev`、`delay`、`vdelay`、`sample_rate`）。値の後のフィールドとメソッドの呼び出しは、値の型が要るので型付けに残す。型付けは解決の記録を読み、解決をやり直さない。名前の隠蔽は全て E0304（S-79）なので、ある位置の名前が指すものは一つで、優先順位の規則は要らない。
- パッケージのモデル（レビュー R-88、S-83、D-15）: パッケージは ID で識別し、パッケージごとに「見える依存の表（キー → パッケージ ID）」を持つ。同じパッケージ（同じ名前と版）は一度だけ解析し、同じ DefId を共有する（菱形の依存で二重に解析しない）。名前で見えるのは、そのパッケージが宣言した依存と暗黙の `std` だけ（§15.1）。std は名前ではなく役割（driver が読み込んだ埋め込みの std に付ける印）で見分け、std の特権（`target` 宣言、組込み型への `impl`、効果の宣言、lang item）は全てこの役割を読む。依存の図は driver が一度だけ作り、sema は受け取る。今の依存は std だけだが、作りは std 以外の依存を受けられる形にする（取得元と版の解決は第 2 期、計画 §5）。`std = "x.y.z"` は埋め込みの std の版と比べる。
- 束縛の状態（レビュー R-85、R-54、S-80、D-15）: 一つの列挙（所有・不変／所有・可変／借用／`inout`）で表し、借用で書き換えられるような仕様に無い組み合わせを作れなくする。状態は束縛を作るとき（名前の段）に一度だけ決めて記録し、型付け、modes、使用の記録（R-83）、Core への降下（R-81 の移動・コピー・破棄）は記録を読む。§5.4 の表は構文だけで決まるので、型は要らない。判定は表を写す一つの関数で、AST の束縛の場所の種類で `_` 無しに分岐する（文法に束縛の場所を足すと、分類するまでコンパイルが通らない）。表の行ごとにテストを置く。無名関数が Shared 型の値を捕捉する行は未決定なので、E0200 にする（計画 §5 の持ち越し）。
- 署名の段（レビュー R-84、R-50、D-15）: `sig.rs` を、(1) モジュール木と項目の収集（名前空間の表: 列挙子、impl のメンバ、flow の生成項目の名前、効果の操作）、(2) `use` の解決（S-37）、(3) 署名の型の降下、(4) flow の生成項目の型と `@param`、の段に分ける。各段は前の段が作った表を受け取る。本体の型付けは署名の表を読み取り専用で参照し、`Analysis` を `mem::take` で取り出さない。
- 効果と `rt` の判定（レビュー R-83、S-77、D-15）: 型付けと modes（経路を見た破棄の点、R-32）の後に、「使用の記録」を作る段を一つ置く。記録は本体（関数、無名関数、`test`、定数の初期化式）ごとに、使う効果とその位置と理由（呼び出し、関数値の呼び出し、効果の操作、補間などの暗黙の確保、破棄）と、呼ぶ関数（`rt` かどうか）を持つ。E0601、E0901、E0903、第 2 期の E0642 などは、この記録を読む判定にする（E0902、E0904、E0905、E0610 は署名だけで決まる）。効果の判定は全ての関数で同じで、`rt` は効果行の制限と呼び出しの規則を足すだけにする。無名関数の使用は外の関数に数えず、期待する関数型の効果行と照合する（§8.1、R-27）。`test` の本体と定数の初期化式は `Alloc` を与えられる（D-08、§6.6）。報告は S-59 どおり 1 つの関数につき最初の 1 件で、E0601 の形は S-77。効果行は「効果の宣言の ID の集合 + 効果行の変数」で表し（S-74 で名前を解決するため）、`Alloc` は lang item の一つにする。

```
struct resonator.State {
  sample_rate: F32          // S-05: Ctl から参照される
  r: F32, b1: F32, b2: F32  // Ctl レートの let のうち Sig から参照されるもの（S-05）。w は Ctl からしか参照されないので省く
  y1: F32                   // prev(y, 0.0) の保存値
  y2: F32                   // prev(y1, 0.0) の保存値
  poisoned: Bool
}
fn resonator.init(cfg: resonator.Config, sr: F32) -> State { State { sample_rate: sr, r: 0.0, ..., y1: 0.0, y2: 0.0, poisoned: false } }
rt fn resonator.reset(inout s) { s.y1 = 0.0; s.y2 = 0.0; s.poisoned = false }
rt fn resonator.ctl(inout s, p: Params) {
  s.r = exp(-(F32.PI * p.bw) / s.sample_rate)
  let w = (2.0 * F32.PI * p.fc) / s.sample_rate   // 状態に置かないローカル
  s.b1 = 2.0 * s.r * cos(w)
  s.b2 = s.r * s.r
}
rt fn resonator.tick(inout s, x: F32) -> F32 {
  let y1 = s.y1                       // prev の出力は保存値
  let y2 = s.y2
  let y = ((1.0 - s.r) * x) + (s.b1 * y1) - (s.b2 * y2)
  s.y2 = y1                           // prev(y1): y1 を保存
  s.y1 = y                            // prev(y):  y を保存
  y
}
rt fn resonator.process(inout s, p, x: Span[F32], inout out: Span[F32]) {
  // 長さの検査（違えば panic）
  resonator.ctl(inout s, p)
  for i in 0..x.len() { let xi = x[i]; let yi = resonator.tick(inout s, xi); out[i] = yi }
}
```

- `prev` の保存は、その `let` の評価の **後**、`tick` の末尾でまとめて行う（§11.4「出力は保存値で、その後に `e` を保存する」）。複数の `prev` が同じ信号を参照しても、保存は各ノードが独立に持つ。
- `delay` / `vdelay` は §11.4 の演算順をそのまま `tick` の中に展開する（関数にしない。順序を固定したいため）。
- 親の `tick` は子の `tick` を `Call` で呼ぶ。子の `Ctl` 入力に渡す親の値は、親の `ctl` で子の `Params` を組み立てて子の `ctl` を呼ぶ。
- `par` は `[sub.State; N]` と `ForRange` に落とし、`i` はループ変数（`Init` レートの値）。
