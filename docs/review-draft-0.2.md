## 1. 総評

0.1 のレビューで挙げた「例が自分の規則に違反している」「難しい判断が空白」という問題は、0.2 でほぼ解消されている。§17 の例は演算子の群・前方参照・レート・`Alloc` の規則に照らして手で追えるし、メモリ・効果・移植性の判断は一通り下されている。次の点は 0.2 の核として残すべきである。

- flow 本体を「1 サンプルごとに評価される関数の本体」と同じ形にし、因果性を名前の順序の検査に落としたこと（§11.2）
- `Alloc` を明示の効果にし、rt の規則を効果行から導いたこと（§8.2, §10）
- 後置の `~` で状態を持つインスタンスを区別すること（§2.6）。Max/Pd の慣習と一致している
- 状態の大きさ・配置（fast / bulk）・スタックを静的に決める方針（§12）
- 「移植可能な核」が新しい検査なしで既存の規則から決まること（§13.2）

一方で、実装に入る前に決めるべき穴が残っている。重いものは次の 4 つで、いずれも言語の健全性か、標準ライブラリの設計に直接響く。

1. **`Alloc` handler の中で外側の変数を書き換えると、arena のメモリが外へ漏れる**（C-01）
2. **`rt fn` が効果を持てるのに、その効果の handler が rt である保証が無い**（C-02）
3. **ジェネリックな `T` の破棄が要求する効果（`Alloc`、非 rt）が定義されていない**（G-01）
4. **flow の `process` の外で rt 関数が panic したときの挙動が未定義で、C での実現方法も決まっていない**（G-02, I-01）

残りは、構文の細部の空白（タプル、配列リテラル、パターン、関連定数など）と、例の小さな違反である。

## 2. 矛盾・誤り

### C-01 `Alloc` の handler から、外側の変数経由でメモリが漏れる（重大）

§8.4 (`:515`) は、`Alloc` を処理する `handle` 式の **結果** だけを Copy に制限している。しかし `handle { ... }` の本体は普通のブロックで、外側の `var` を参照できる。

```onsa
fn leak(inout scratch: Span[U8]) uses {Alloc} {
  var xs: Array[F32] = Array.empty()
  let n = handle {
    xs = xs.push(1.0)     // push は arena の上で確保する。結果は Copy なので E0640 にならない
    xs.len()
  } with arena(inout scratch)
  // ここで xs は、既に巻き戻された arena を指している
}
```

同じ経路は、外側の `var` を `inout` で渡す呼び出し、`inout self` のメソッド呼び出しでも開く。Perceus の in-place 更新（§12.6）は、一意な値の再確保を arena の中で行うので、`xs` が最初から外側にあっても防げない。

**提案**: `Alloc` を処理する `handle` の本体の中では、外側のスコープの非 Copy 値を **読み取りの借用でしか使えない**（代入・`inout`・`move` を禁止、E064x）。結果が Copy という規則と合わせて、持ち出しの経路が閉じる。

### C-02 `rt fn` の効果の rt 性が局所的に決まらない（重大）

§10 の規則 1〜2 は「`Alloc` も `blocking` も含まない」だけなので、`rt fn f() uses {Log}` は合法である。`f` の本体の `Log.info(...)` は handler へ間接に飛ぶが、handler が rt かどうかは `f` の定義では分からない。§8.3 (`:470`) の「handler の操作が rt なら、handle 式も rt で使える」は `handle` 式の側の規則で、`f` 自身の `rt` を支えていない。

例: ターゲットの `provides` が `Log` をヒープに書く handler で与えると、export された `rt fn f` は実行時にヒープを使う。規則 3「rt でない関数を呼ばない」(`:581`) が効果の操作に対して検査できていない。

**提案**（どちらか）:

- (a) 効果の操作に `rt` を付けられるようにし（`effect Log { rt fn info(msg: Str) }`）、その handler は rt でなければならない。`rt fn` は、効果行の全ての効果の全ての操作が `rt` であるときだけ、その効果を使える。
- (b) `rt fn` の効果行は空に限る（効果行変数も不可）。

(a) の方が `Log` のような rt で使いたい効果に対応できる。どちらにしても §8.2 の「`rt fn` は、効果行に `Alloc` も `blocking` の効果も含まない関数である」(`:462`) は書き直しになる。

### C-03 `spawn` に渡すクロージャが、第二級の規則に反する

§16 (`:1096`) の `s.spawn(...)` に渡すクロージャは、`spawn` の呼び出しが返った後もタスクの終了まで生きる。§5.3 (`:316`) と §13.5 (`:852`) は、捕捉するクロージャは「引数の位置にだけ現れ、環境の寿命が呼び出しの中に収まる」としている。両立しない。

捕捉は値のコピーで `inout` も Affine も捕捉できないので、環境には借用が無く、意味の上では保存しても安全である。禁じている理由は「ヒープに置かずに済む」ことだけ（`docs/onsa-0.2-changes.md` §4）。

**提案**: `spawn` だけを明示の例外にし、「`Spawn` 効果の下では、クロージャの環境はタスクの記憶域（ヒープ）へコピーされる」と書く。または `spawn` の引数を「捕捉の無い関数 + Copy / Shared の引数」に限る。§19 の「逃げるクロージャ」の検討と合わせて決める。

### C-04 シャドーイングの禁止が、字義通りだと厳しすぎる

§5.1 (`:301`)「同じ関数の中で、同じ名前を二度束縛できない」。字義通りなら、一つの関数に `for i in ...` を二つ書けず、二つの `match` で `Some(x)` を使えない。§17.6 は関数ごとに `i` を一度しか使っていないので違反していないが、実用に耐えない。

**提案**: 「ある名前の束縛が見えている間は、同じ名前を束縛できない」（入れ子のシャドーイング禁止）とし、兄弟のスコープでの再利用は許す。flow の本体はブロックが一つなので、§11.2 の規則は変わらない。

### C-05 export の場所が「一つ」になっていない

§14.2 (`:945`)「flow はソースではなくマニフェストの `[export]` で export する。export する場所を一つにするためである」。しかし関数は同じ節でソースの `export "C" fn` で export する。同じ概念（C の ABI に出す）に二つの見た目で、§0.3 の規則 1 に反する。

**提案**: 関数もマニフェストの `[export] fns = [...]` に寄せ、ソースの `export` キーワードを無くす。または両方ソースに置いて `[export]` は prefix だけにする。前者の方が「エージェントにマニフェストを書かせない」運用（§15.4）と相性が良い。

### C-06 C ヘッダの `frames` が `size_t`

§14.2 (`:966`) の生成ヘッダは `size_t frames` だが、§4.1 (`:214`) は添字・長さを `U32` に固定し、`size_t` は FFI の `CSize` だけとしている。export の境界は Onsa 側の意味を出す場所なので `uint32_t` にする。§17.5 (`:1310`) のホストの例も合わせる。

### C-07 例が prelude に無い名前を使っている（P9）

- §6.2 (`:354`) `sqrt`、§10 (`:573`) `abs` に `use std.math.{...}` が無い。prelude は `Option Result Some None Ok Err` と組込み型だけ（§15.1）。
- §17.6 `array.from_fn` は `[voice.State; N]` を返すので `[T: ?Dup]` が要るが、§4.5 (`:271`) は `?Dup` の `T` を「借用・`inout`・`move` でしか扱えない」としており、返り値にできるかが読めない。「複製できない」だけで、生成して返すのは可、と書き直す。

### C-08 `Ord` / `Eq` が Rust の `PartialOrd` / `PartialEq` の意味

§6.3 (`:386`) の `Ord` は IEEE 比較（NaN は比較不能）で F32 が実装し、`TotalOrd` がソート用。Rust ではこれは `PartialOrd` / `Ord` の関係で、`f32` は `Ord` を実装しない。Rust を知る読み手が `[T: Ord]` を全順序と読んで検査を通るので、§0.3 の規則 4 にかかる。`Eq` も同じ（Rust の `f32` は `PartialEq` のみ）。

**提案**: Rust と同じ `PartialEq` / `Eq` / `PartialOrd` / `Ord` にする。意味が一致するなら借りる、が規則 3 なので、ここは借りてよい場所である。

### C-09 「`Init` 以下のレート」の読み方

§11.3 (`:636`)「コンパイル時定数は `Init` 以下のどのレートにもなる」、§11.5 (`:662`)「`Init` 以下のレートの引数でのみ呼べる」。`Init` は最も低いレートなので「以下」は `Init` だけを指し、前者は読めない。意図はおそらく「定数は（昇格により）どのレートにもなる」と「`Init` レートの引数（定数を含む）でのみ呼べる」。定数を「`Init` より低い疑似レート」として表に加えるか、文を直す。

### C-10 §1 と §20 の「最初から」

§1 (`:92`) はネイティブのバックエンドが「言語全体を最初から扱う」とし、§20 は第 1 期の C バックエンドが核だけを扱うとしている。§1 は設計上の区分（段階を設けない）、§20 は実装の順序、という意味なら、§1 の語を「段階を設けない」に変える。

### C-11 README の見出し

`README.md` の見出しが `# orilang` のまま。

## 3. 仕様の空白

### G-01 ジェネリックな `T` の破棄が要求する効果（重要）

§6.3 (`:388`)「値が破棄される位置は、その型の破棄が必要とするもの（`Alloc`、非 rt）を要求する」。`T: Dup` のジェネリック関数の中で `T` の値を破棄すると、`T` が Shared なら `Alloc` が要り、`T` が Copy なら要らない。定義の時点では分からない。

P1（検査は関数の中で閉じる）を守るなら、規則は「`T` の破棄は、`T: Copy` でない限り `Alloc` を要し、rt でない」になる。これは標準ライブラリの設計に直接響く。rt で使う配列関数（`sum`、`fill`、`from_fn`、`map` on `[T; N]`）は `[T: Copy]` で宣言することになる。明文化が要る。

### G-02 `process` の外での rt の panic

§9.2 (`:548`) の表は「rt 関数（flow の `process` を含む）」の panic を「出力をゼロで埋め、インスタンスを poisoned にする」としているが、`Poly.note_on`（§17.6）のようにインスタンスも出力バッファも無い rt 関数を `main` や C のホストから呼んだ場合の挙動が無い。

**提案**: poisoned の規則は「export された flow の `process`」と「export された rt 関数」の境界にだけ定義し、Onsa の中から呼ばれた rt 関数の panic は、最も近い境界（export か `main`）まで伝わる、とする。C での実現方法は I-01。

### G-05 ジェネリクスの呼び出し位置で型が決まらない場合

§4.5 (`:270`) 呼び出し位置で型引数を書けないので、`let n: I32 = parse("3")` のように注釈で決める。返り値だけがジェネリックな関数は常に注釈が要る、と明記する。期待型が無く決まらない場合の診断コード（E04xx）も要る。

### G-06 `Str` リテラルと参照カウントのヘッダ

§4.1 (`:200`) リテラルは静的領域、§4.6 は `Str` を参照カウント。静的な `Str` に減算が走らないよう、ヘッダに「不滅」の印か、参照カウント 0 を「静的」と解釈する規則が要る。§8.4 の「確保元をヘッダに記録する」と合わせて、ヒープオブジェクトのヘッダの形（確保元 + カウント + 不滅印）を仕様か実装ノートに固定する。

### G-08 所有束縛の破棄と、読むだけの反復（G-01 の検討で発見）

「所有する Shared 値の破棄は `Alloc`」（§12.2）を字義通りに適用すると、`for s in xs` の `s` は要素の複製（所有束縛）で反復の終わりに破棄されるので、`Array[Str]` を読むだけの反復に `Alloc` が要る。`let y = x[i]` も同じ。

**提案**: 束縛の種類を初期化の元で構文的に決める借用束縛。`for s in xs` と、借用引数から派生した `let` は借用で破棄を起こさない。所有が要るときは `for s in move xs`。借用が印の無い既定である点は引数モード（§5.2）と同じで、C++ の `const auto&` のような印は要らない。本体の使い方から推論しないのは、エラーを `for` の行に出すためである。あわせて、借用した Dup 値を `move` 引数に渡せる（その場で複製する）ことを明記する。

### G-07 ターゲットの型配置

`SIZE` / `ALIGN`（§12.4）はコンパイラが計算するが、どの配置規則（フィールドの順序、アラインメント）を使うかが無い。ホットリロード（§18.3）とプローブは名前とオフセットの安定に依存するので、「宣言順、自然アラインメント、並べ替えなし」を規則にする。

## 4. 設計提案

### P-01 エラーを「関数ごとに最初の一つ」にする

§18.1 (`:1398`)「エラーは最初に検出された関数の中で止まる」。修復ループ（P8）の回数を減らすには、関数ごとに独立に検査して、全関数分のエラーを一度に返す方が良い。P1 により関数の検査は独立なので、追加の設計は要らない。「一つの関数の中では最初のエラーで止まる。関数どうしは独立に報告する」に変える。

### P-02 レシーバの `inout` を呼び出し位置にも出す

§5.2 (`:313`)「レシーバの `inout` は呼び出し位置に書かない」。同じ節の「読み手は呼び出し 1 行で、何が変わるかを知る」と、§0.3 の規則 1（同じ概念は同じ見た目）に反する。§17.6 の `out.fill(0.0)` は `out` を変えるが、読み手には見えない。

案: `inout out.fill(0.0)` または `out.fill!(0.0)`。前者は引数と同じ見た目になる。主な書き手が LLM で、付け忘れは検査で落ちるので、冗長さのコストは小さい。

### P-03 ブラウザでの試聴は JS 変換より WASM 出力を先にする

§18.3 はブラウザでの試聴を「WASM」とし、§20 の 6 は JavaScript への変換をその手段にしている。しかし §13.3 の WASM は「C 経由または LLVM 経由」で、ブラウザの IDE には C のツールチェーンが無い。

核は「ループとスカラ演算」だけなので、Onsa Core から直接 WASM を出す小さなバックエンドが書ける。WASM の浮動小数は IEEE で FMA も拡張精度も無く、`strict` の基準として C より扱いやすい。JS 変換は AudioWorklet で WASM を使えない場合の経路として残す。実装計画ではこの順にしている。

### P-04 `par` の降下は配列 + ループにする

`par i in 0..N { e }` を N 個に展開すると、組込みでコードが N 倍になる。状態を `[sub.State; N]`、処理をループにすると、コードは 1 つで `i` は実行時の値になる。`i` は `Init` レートの定数（§11.5）なので、`i` に依存する `Init` の値を状態の配列に持てば意味は変わらない。

### P-05 整数オーバーフローの検査の扱いを数値プロファイルに書く

§9.2 は `+ - *` のオーバーフローを常に panic にしている。核の添字計算は `U32` なので、サンプルループの中に分岐が入る。`strict` で検査を保証する方針（§13.4）は正しいが、`relaxed` でも検査を外せないのかを §15.5 に書く。外すなら、外したときの意味（ラップアラウンド）も要る。

## 5. 実装上の懸念

### I-01 rt の panic を C でどう実現するか

「呼び出しを中断して出力をゼロで埋める」(`:548`) には、巻き戻しが要る。選択肢は 2 つ。

- `setjmp` / `longjmp`: export の wrapper で `setjmp` し、panic で `longjmp`。`jmp_buf` を状態か静的領域に置く。ホスト環境と newlib 系の組込み libc では使える。WASM には無い。
- 状態コードの伝播: panic しうる全ての演算の後に分岐を入れる。コードが膨らみ、ビット一致の検証も複雑になる。

推奨は前者を「ホスト向けの既定」、`trap` / `reset` / `halt` を組込み向けとし、WASM はトラップを JS 側で捕まえて poisoned にする。仕様の表 (`:548`) をこの形に合わせる。

### I-02 C でのビット一致に要する条件

`strict` をCで満たすには、生成コードだけでなくコンパイル条件が要る。`-ffp-contract=off`、`FLT_EVAL_METHOD == 0`（x86-32 の x87 を避ける）、`-ffast-math` 禁止、F32 の演算の前後で `(float)` を明示。生成コードに `#pragma STDC FP_CONTRACT OFF` と `_Static_assert(FLT_EVAL_METHOD == 0)` を入れ、ターゲット定義にコンパイラフラグを含める。MSVC では `/fp:strict`。

### I-03 `std.math` を Onsa で書く範囲

`exp`、`cos`、`sin`、`log`、`exp2`、`pow`、`tanh` を Onsa で決定的に実装するのは、それ自体が一つの作業である（範囲縮小と多項式。精度目標も要る）。`sqrt` と `floor` は全てのターゲットで正しく丸められるので、プリミティブにしてよい（JS は `Math.fround(Math.sqrt(x))` で二重丸めが無害）。仕様に「プリミティブの関数の一覧」と「Onsa で書く関数の精度目標（ULP）」を足す。

### I-04 大きな値の返り値をコピーしない保証

§11.6 (`:718`)「大きな値の返り値は、呼び出し側の領域に直接構築される（コピーしないことを保証する）」。`Poly.new` のように `array.from_fn` のクロージャ経由で `voice.State` を返す経路でも保証するには、「Affine と閾値以上の Copy 値は、常に呼び出し側が渡す出力ポインタへ構築する」を ABI の規則にする必要がある。インタプリタでは問題にならないが、C バックエンドの設計の最初に決める。

### I-05 flow の名前空間の実現

`voice.State`、`voice.init` はモジュールと同じ扱い（§11.6）。名前解決で「flow の宣言は、同名の名前空間を同じモジュールに作る」と扱えばよいが、同じモジュールに `voice` という関数や値があると衝突する。命名規則上は flow と関数が同じ `snake_case` なので、検査が要る（E03xx）。

### I-06 関数本体の型推論の形

リテラルに既定の型が無い（§2.4）ので、`var acc = 0.0` の型は後続の文で決まる。前方への一方向の推論では足りず、関数本体の中で単一化変数を使う必要がある。一方、フィールドアクセスとメソッド呼び出しは「その場で既知」(§4.4, E0420) を要求するので、「型変数は後で決まってよいが、`.` の左辺はその時点で解決済みでなければならない」という、一方向と双方向の中間の規則になる。仕様にこの規則を書いておくと、実装と診断が揃う。

## 6. 実装の前に決めること（優先順）

1. C-01: `Alloc` handler の本体での外側の変数の扱い → 第 2 期の前でよいが、`handle` の意味に関わるので早く決める

8. C-04 シャドーイング、C-08 trait 名、C-05 export、P-02 レシーバ → 構文に関わるので M1 の前に決めるのが安い
9. G-01 ジェネリックの破棄 → 第 2 期の前
