# Kumi は Rust に対して何が優れているか

- 対象: [`kumi-lang-spec.md`](../kumi-lang-spec.md)（Draft 0.1）
- 日付: 2026-10-01
- 関連: [`comparison-ori-kumi.md`](comparison-ori-kumi.md)

Kumi は実装の無い仕様なので、以下はすべて **設計上の主張** であり、実証されていない。

---

## 1. 結論

Rust に対して明確に優れていると言える点は 4 つで、いずれも「何を静的に検査できるか」に関わる。

1. 外部への作用（効果）がシグネチャに出る
2. リアルタイム安全性を静的に検査できる
3. 信号処理の構造（因果性・レート・状態）を言語が理解している
4. 型エラーの原因が、その関数の中に閉じる

このうち 2 と 3 の大半は、Rust の上でも近似できる。**新しい言語でなければ得られないのは 1 と 4 だけ** である。したがって、新言語を作る価値は「効果の型付け」と「局所的に閉じる型検査」が、LLM の修正ループで実際にどれだけ効くかで決まる。

---

## 2. 明確に優れている点

### 2.1 外部への作用がシグネチャに出る（Kumi §8）

Rust では、どの関数からもファイル（`std::fs`）、ネットワーク、時刻、乱数を自由に呼べる。シグネチャを見ても、その関数が外部に何をするかは分からない。

Kumi では効果の宣言（`uses {Fs}`）が関数の型の一部なので、次のようになる。

- 監査は、シグネチャを読むだけで済む。
- テストでは handler を差し替えるだけでよい。モック用の trait や依存性注入の仕組みは要らない。
- 時刻と乱数も効果なので、テストは自動的に決定的になる。

これを Rust に後から加えると、既存のコードがすべて壊れる。言語の土台の違いである。

### 2.2 リアルタイム安全性を静的に検査できる（Kumi §10）

Rust には「この関数はメモリ確保もブロッキングもしない」ことを型で表す手段が無い。現在使われている方法は、どれも実行時の検査である。

- `assert_no_alloc` クレート（確保が起きたら実行時に検出する）
- RealtimeSanitizer（実行時に検出する）

実行時の検査は、実際に通った経路しか確かめられない。Kumi の `rt fn` は、呼び出しの連鎖全体をコンパイル時に検査する。`rt` は関数型の一部なので、高階関数を通しても失われない。

C++ には Clang の `[[clang::nonblocking]]` / `[[clang::nonallocating]]` という近い仕組みがある。Rust に対しては明確な差である。

### 2.3 信号処理の構造を言語が理解している（Kumi §11）

Rust で DSP を書くときは、状態を持つ構造体と `process` 関数を手で書く。言語の側は次のことを知らない。

- フィードバックの経路に遅延が入っているか（因果性）
- 係数計算がサンプルループの外に出ているか（レート）
- 状態の初期化とリセットが漏れていないか

Kumi の proc では、これらが型検査と自動生成（`State` / `init` / `reset` / `process`）で保証される。

Rust にも、型レベルの数値でチャンネル数を検査するライブラリ（fundsp）はある。ただし検査はチャンネル数止まりで、型エラーも読みにくい。

### 2.4 型エラーの原因が、その関数の中に閉じる（Kumi §5, §6）

Rust の借用検査のエラーは原因が離れた場所にあることが多く、LLM が生成した Rust のコンパイルエラーの典型でもある。Kumi は参照を値として持たない（第二級に限定する）のでライフタイムが無く、さらに関数のシグネチャはすべて注釈する。そのため、エラーは常にその関数の中で止まる。

ただし、これは「優れている」というより **割り切り** である。代償として次のことができない。

- 構造体のフィールドに参照を持つこと
- コピー無しで、データの一部を指すビューを保持すること
- 参照カウント無しでデータを共有すること

## 3. Rust にもある、または差が小さい点

| 項目 | 実態 |
|---|---|
| JSON 診断・安定したエラーコード | Rust に既にある（`--error-format=json`、`E0382` など）。診断の質はむしろ Rust の方が上。 |
| 決定的なフォーマッタ | `rustfmt` がある。 |
| unsafe の監査 | `cargo-geiger`、`cargo-vet` がある。ただし Kumi の「効果を許可するポリシー」（§13.4）に当たるものは無い。 |
| 浮動小数点の再現性 | Rust は FMA への自動縮約をしないので、半分は既に満たしている。残りは `libm` クレートを使う規律で達成できる。Kumi の利点は、それを規律ではなく保証にしている点だけ。 |
| リアルタイム処理中の panic | Rust では FFI 境界で abort する。Kumi は「出力を無音にし、インスタンスを使用不能（poisoned）にする」と挙動を規定している（§9.2）。小さな利点。 |
| 演算子の優先順位 | clippy の lint で近いことができる。 |
| 書き方の一意性 | Kumi の方が狭いが、Rust でも fmt と clippy でかなり揃う。決定的な差ではない。 |

## 4. Rust が明確に優れている点

- **実在する。** Kumi は仕様でしかない。
- **LLM の事前知識。** Rust のコーパスは膨大で、Kumi はゼロ。現時点では「LLM 向きの性質」よりも、こちらの方が効く。
- **エコシステム。** オーディオ周りにも nih-plug、cpal、fundsp がある。
- **性能を制御できる幅。** 参照、コピーなしの処理、参照カウントなしのデータ共有、async、trait オブジェクト。
- **マクロ。** serde のような定型コードの削減は、Kumi の閉じた `derive` では到底かなわない。
- **ツールと実績。** LSP、デバッガ、プロファイラ、パッケージ、運用実績。

## 5. 先行する言語との関係

Kumi の個々の仕組みは新しくない。

| 仕組み | 先行例 |
|---|---|
| 効果の型付け、Perceus 方式の参照カウント | Koka |
| 可変値意味論、第二級の参照 | Hylo（旧 Val） |
| 同期データフロー、因果性の検査 | Lustre / SCADE |
| 信号処理の部分言語、C への降下 | FAUST |
| virtual モジュール | OCaml / dune |
| 関数単位のリアルタイム検査 | Clang の関数効果解析 |

新しいのは、これらを「LLM が書き、人間が監査し、リアルタイム DSP を C の API として export する」という一つの目的のために組み合わせた点である。個々の言語に対する Kumi の優位は、仕組みそのものではなく、この統合と C への export にある。

## 6. 戦略的な含意

### 6.1 Rust の上で近似できるもの

| Kumi の利点 | Rust 上での近似 |
|---|---|
| 2.2 リアルタイム安全性 | 静的解析ツール（MIR 上で、確保とブロッキングにつながる呼び出しを辿る lint） |
| 2.3 信号処理の構造 | proc-macro による DSL。`proc!` マクロで方程式を書き、因果性とレートを検査して、構造体と `process` を生成する |
| 決定的な浮動小数点 | `libm` クレート + lint |
| ポリシー | `cargo-vet` + 独自の lint |

### 6.2 新しい言語でなければ得られないもの

- 2.1 効果の型付け
- 2.4 ライフタイムの無い、局所的に閉じる型検査

### 6.3 進め方の提案

1. **LLM ベンチマークの対照群に Rust を入れる。** 比較文書（comparison-ori-kumi.md §6）で提案したベンチマークに、Rust で同じ課題を書かせる群を加える。測るものは次の 2 つ。
   - 型検査を通るまでの修正の回数
   - 効果の誤り（禁止された I/O など）が、検査で何件見つかったか
2. **DSP だけが目的なら、Rust 上の DSL を先に作る。** 2.3 の価値は Rust の proc-macro DSL で早く確実に出せ、既存のエコシステム（nih-plug など）にもそのまま乗れる。Kumi の proc の設計は、そのまま DSL の設計として使える。
3. **新しい言語を作る判断は、ベンチマークの結果で下す。** 6.2 の 2 点が修正ループで有意に効くと分かった場合に限り、新言語として実装する価値がある。
