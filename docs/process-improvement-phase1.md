# 再発防止の方法（第 1 期レビューを受けて）

- 日付: 2026-10-02
- 入力: [`review-impl-phase1.md`](review-impl-phase1.md)（R-01〜R-113）
- 目的: M0〜M4 で、テストを通るのに意味が誤るもの、報告されない独自判断、判断の重複が生じた。その原因を挙げ、M5 以降と第 2 期で同じことを起こさないための方法を提案する。提案は Q-01 から番号を振る。項目ごとに判断してほしい。

---

## 1. 原因

レビュー §0 の 4 つの原因を、作業の流れに沿って細かく分けた。

| # | 原因 | 例 |

## 2. 提案

### A. 実装から独立した期待値（原因 a・b・c・d）

Q-01〜Q-08 は、レビューの R-113（テストの基盤）と一緒に一つの設計として決める（2026-10-05、R-113 の決定）。R-113 の本文に、他の項目で決まったテストへの要求を集めてある。

#### Q-01 テストは、実装とは別の担当が仕様から書く
- 案:
  - 各作業で、テストの担当（ワーカー）を実装の担当と分ける。
  - テストの担当には、仕様と CLI の使い方だけを渡し、実装のコードは見せない。
  - 期待値は仕様から手で導き、実装より先に書く。このテストが作業の受け入れ条件になる。
  - テストの担当が仕様の空白に気付いたら、その時点で親へ報告する（Q-10）。実装の前に空白が表に出る。
- 費用: 作業ごとにエージェントを 1 つ足す。期待値を手で導く手間がかかる。
- 推奨: 採る。最も効果が大きい。

#### Q-02 Core を通らない参照を、二つ持つ
- スカラの意味の参照:
  - 仕様 §3.4 は「Rust と同じ」なので、Rust そのものを参照にする。
  - 整数・浮動小数・変換・検査付き演算の式をランダムに作り、Onsa のインタプリタ、C、同じ式の Rust プログラムで評価して比べる。
  - R-04、R-10、R-11、R-19 の種類が対象になる。
- flow の意味の参照:
  - AST から直接、1 サンプルずつ評価する小さな参照評価器を `onsa_tests` に置く。§11 の文言をそのまま書き、数百行に収める。
  - Core を経たインタプリタと C の `render` を、これと比べる。
  - R-13、R-14、R-16、R-22 の種類が対象になる。
- 費用: 中。参照評価器は速さを求めないので、単純に書ける。
- 推奨: 採る。原因 c への唯一の直接の対策。

#### Q-03 生成器による性質テスト
- 案: 文法と型の規則から、型の付いた小さなプログラムを生成し、次の 4 つの性質を検査する。
  1. `check` が通る
  2. インタプリタと C が一致し、Q-02 があれば参照とも一致する
  3. `fmt` の前後で AST が変わらない
  4. コンパイラが panic しない
- 狙い: 生成器は、入れ子、分岐、`par`、クロージャ、総称の組み合わせを自然に作るので、原因 d に効く。
- 範囲: 最初は小さな部分言語（スカラの fn、`prev` / `delay` / 分岐 / `par` を持つ flow）から始める。
- 費用: 中〜高。
- 推奨: Q-01 と Q-02 の後に採る。

#### Q-04 golden を「変化の検出器」と位置付ける
- 案:
  - golden を、意味の正しさの根拠にしない。
  - 各 golden の事例に、期待値付きのテスト（Q-01）を対で置く。
  - `UPDATE_GOLDEN=1` による更新は、親が差分を読んで承認する。ワーカーは更新した golden を報告に列挙する。
- 費用: 低。
- 推奨: 採る。

#### Q-05 仕様の規則とテストの対応表
- 案:
  - 仕様の規則（受理、拒否、意味）に ID を振る。
  - テストは、検査する規則の ID を参照する。
  - `tools/check_spec_examples.py` を拡張して、テストの無い規則を一覧にする。
- 現状: 今の検査は「仕様の例がどれかのテストに逐語的に含まれるか」だけで、例の出力や診断は見ていない。
- 費用: 高い。仕様に ID を振る作業が要る。
- 推奨: 部分的に採る。まず §3〜§5 と §11 の規則に ID を振り、第 2 期で広げる。

### B. 安全網（原因 g）

#### Q-06 検証器と、内部の誤りの扱い
- 案:
  - Core の検証器を、テストと debug では常に動かし、release でも `--verify` で動かせるようにする。不変条件を強める（R-82）。
  - driver で `catch_unwind` を行い、内部の panic を「内部エラー」の診断にする。入力の位置と、再現の手順を出す。
  - 「どんな入力でもコンパイラは panic しない」を性質として、`check` と `fmt` に変異入力を与える短いファズを回す。
- 費用: 低〜中。
- 推奨: 採る。

#### Q-07 生成した C を、複数のコンパイラと sanitizer で検査する
- 案:
  - テストで生成した C を、clang と gcc の両方でコンパイルする。`-Wall -Wextra -Werror` を付け、UBSan / ASan 付きでも実行する。
  - 公開ヘッダを C++ でもコンパイルする。
  - `cc` が無いときは、テストを失敗にする。
  - 飛ばした flow の数を表示する。
- 費用: 低。
- 推奨: 採る。R-10、R-65、R-67 は、これで見つかった。

#### Q-08 一つの検査コマンド（CI の代わり）
- 案: CI を用意しないので、`tools/gate.sh`（仮）で次をまとめて回す。親は作業を受け入れるたびに実行する。
  - fmt、clippy、test
  - 仕様の例の検査
  - Q-07 の C の検査
  - Q-06 の短いファズ
  - Q-10 の印の照合
  - Q-14 の直書きの検査
  - 診断コードの網羅性の照合（2026-10-06、点検 C-26 で追加）: 登録簿の全てのコードが仕様の本文に現れ、仕様の本文の全てのコードが登録簿にある（欠番を除く）
- 費用: 低。
- 推奨: 採る。

### C. 仕様に無い前提を表に出す（原因 e・f）

#### Q-09 仕様に無いものは拒否する（閉世界の原則）
- 案:
  - 仕様の空白に出会ったら、受理する側に倒さず、拒否する（E0200「この版では未対応」、または構文エラー）。
  - 例外は、受理しないと仕様の例が書けない場合だけにする。その場合は Q-10 で記録する。
- 狙い: 今回の「黙って受理」の多くは、この原則で防げた。後で受理を広げるのは互換性を壊さないが、受理を狭めるのは壊す。
- 費用: 低。ワーカーへの指示に一文を足す。
- 推奨: 採る。

#### Q-10 空白に出会ったときの手順と、コードの中の印
- 案: ワーカーは仕様の空白に出会ったら、次のどちらかを取る。
  - (i) 作業を止めて報告する。
  - (ii) 最も保守的な形（Q-09）で実装し、その位置に `// SPEC-GAP: <内容>` の印を付けて報告する。
- 照合:
  - 印を集めるスクリプトで、全ての印が計画の S の表か、`impl-review` 形式の表に載っているかを照合する。
  - 載っていない印があれば、gate（Q-08）を失敗にする。
  - 親は、印の一覧から判断の項目を起こす。
- 狙い: 申告の漏れを、ワーカーの記憶に頼らず機械的に拾う。決まった空白は、印を消して仕様の節を参照するコメントに替える。
- 費用: 低。
- 推奨: 採る。

#### Q-11 報告の主張には証拠を付け、親が抜き取りで再現する
- 案:
  - 報告に「結果は同じ」「〜は E0302 になる」と書くときは、それを示すテストの名前を付けさせる。
  - 親は、報告の主張のうち数件を無作為に選んで、自分で再現する。
- 費用: 低。
- 推奨: 採る。

### D. 作業の分け方と見直し（原因 i）

#### Q-12 作業を小さくし、作業ごとに「壊す側」のレビューを挟む
- 案:
  - L の作業を S〜M に分ける。
  - 各作業の後に、別のエージェントが壊す側として、利用者の 3 つの観点で再現する入力を探す。今回の 6 領域のレビューと同じ形を、規模を小さくして行う。
  - 重大度の高い指摘が残る間は、作業を完了にしない。
  - 親は、降下・modes・C の生成のような危険の大きい経路の差分を読む。
- 費用: 中。今回のレビューは 6 エージェント、それぞれ 15〜20 分だった。
- 推奨: 採る。

#### Q-13 完了の定義（チェックリスト）
- 案: 各作業の受け入れ条件を、次のとおりにする。
  1. 対応する仕様の節を挙げる。
  2. 正例と否定例がある。
  3. 期待値付きのテスト（Q-01）がある。
  4. 関係する組み合わせのテストがある（入れ子、分岐、`par`、クロージャ、総称、モジュール）。
  5. 印と表の照合が通る（Q-10）。
  6. 組込みの名前の直書きが増えていない（Q-14）。
  7. gate（Q-08）が通る。
  8. 壊す側のレビューで、高の指摘が無い（Q-12）。
- 置き場所: この一覧を `implementation-tasks.md` に置き、ワーカーへの指示に毎回含める。
- 費用: 低。
- 推奨: 採る。

### E. 判断の重複を防ぐ（原因 h）

#### Q-14 判断の置き場所の表と、直書きの検査
- 案:
  - 「どの判断を、どのクレートのどのモジュールが持つか」の短い表を計画に置く。
    - 例: 配置は `onsa_core::layout`、組込みは登録簿、生成する名前は一つの名付けのモジュール、NRVO は Core の降下が決めて IR に記録する。
  - 他の場所が同じ判断を再計算することを禁止し、レビューの観点に入れる。
  - 組込みの名前の文字列との比較（`== "zeroed"` など）を、登録簿の外で禁止する。grep と許可リストによる検査を gate に入れる。
- 費用: 低（表と検査）。既存の重複を除くのは、レビューの R-79 / R-80 の作業である。
- 推奨: 採る。

### F. 仕様の側（原因 j）

#### Q-15 意味の次元の点検表
- 案: 仕様に機能を足すとき、次の次元を点検する。
  - 受理と拒否の集合
  - 評価順
  - 状態への影響
  - 生成する名前と、その衝突
  - 上限と溢れ
  - 診断のコード
  - 他の機能との組み合わせ（入れ子、分岐、`par`、クロージャ、総称、モジュール）
- 既存の節にも、第 2 期の前に一度この点検を通す。
- 狙い: レビュー §3 の 20 件は、ほとんどがこのどれかの抜けである。仕様の段で抜けを見つければ、実装の段で空白に出会うこと自体が減る。
- 費用: 中。
- 推奨: 採る。点検表を仕様の付録か計画に置く。

## 3. 推奨の組み合わせと順序

| 時期 | 項目 | 理由 |
|---|---|---|
| すぐ（次の作業の指示から） | Q-09、Q-10、Q-11、Q-13、Q-04 | 費用が低く、ワーカーへの指示と親の手順を変えるだけ |
| W1（テストの基盤） | Q-01、Q-03 の fmt の性質（W1-07。コメントの位置と CST の往復は W3）、Q-05 の軽い形（W1-03）、Q-06、Q-07、Q-08、Q-14 の直書きの検査（W1-02） | 以後の修正の安全網になる |
| W2（W3 と並行） | Q-02 (a) のテストベクトル（W2-01） | 数の意味を直す W2 の作業の期待値になる |
| W7 の初め | Q-02 (b) の flow の参照評価器（W7-01） | flow の意味を作り直す W7 と W8 の期待値になる |
| 全ての段 | Q-12、Q-14 の置き場所の表（計画 §3.6） | 作業の進め方として定着させる |
| M5 の前後 | Q-03 の型の付いたプログラムの生成（T5-8） | 費用が高いが、組み合わせの誤りに効く |
| 第 2 期の前 | Q-15 | 仕様の追加が大きくなる前に |

（2026-10-07、点検 C-112: 段の名前を [`rework-phase1.md`](rework-phase1.md) の W に改め、決定（§4）に合わせた。Q-05 は軽い形で W1 に入れ、規則の ID は必要が分かったら足す。）

採らない場合の代わり:
- Q-01（テストを別の担当にする）を採らない場合は、少なくとも「テストは実装のコードを読む前に、仕様から書く」を同じワーカーに課す。効果は落ちる。
- Q-02 を採らない場合は、Q-01 の期待値付きテストの数で補う。比べる二つが同じ源から出る盲点は残る。

## 5. 仕様の点検表（Q-15）

仕様に機能を足すとき、または既存の節を見直すときに、次の次元を順に確かめる。抜けていれば、その場で仕様に書くか、§19.1 に問いとして残す。

| # | 次元 | 確かめること（例） |
|---|---|---|
| 1 | 受理と拒否 | 書ける形の閉じた一覧。一覧に無いものの診断コード（S-103 の割り当ての原則） |
| 2 | 評価順 | 部分式、引数、代入先の順（§3.5） |
| 3 | 状態への影響 | flow の状態、`reset`、ホットリロードの照合（S-86） |
| 4 | 生成する名前と衝突 | 状態のフィールド、C の名前、`prefix` とランタイムの名前空間（R-48、R-121） |
| 5 | 上限と溢れ、資源が尽きたとき | 大きさ、スタック、長さ（R-100、R-112） |
| 6 | 浮動小数の端の値 | NaN、無限大、符号付きの 0、非正規化数、`strict-ftz`（R-133、S-105） |
| 7 | 診断 | コード、位置、修正候補（読みが分かれるなら読みごと、S-48 / R-124） |
