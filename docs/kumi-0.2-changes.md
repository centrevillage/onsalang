# Kumi Draft 0.1 → 0.2 の変更点

- 対象: [`kumi-lang-spec-0.2.md`](../kumi-lang-spec-0.2.md)（0.1 は [`kumi-lang-spec.md`](../kumi-lang-spec.md)）
- 日付: 2026-10-01

## 0. きっかけ（0.1 へのフィードバック）

1. **既存のコーパスに寄せすぎている。** 例えば `proc` は、他の言語では無名関数やクロージャ（Ruby の `proc`）や手続き一般（Tcl, Nim）を表す。procedure の略で意味が広すぎ、機能の名前に向かない。Ori の `flow` の方が適切。
2. **同じものは似た見た目、違うものは違う見た目の方が、LLM にも人間にも認知の負荷が低い。**
3. **言語の目的は、FAUST のような DSP 開発環境の基盤となること。** 最終的には IDE と各言語へのトランスパイラを用意したい。
4. **組込み環境での DSP 開発にも使う。** メモリ管理には注意が要る。

---

## 1. 原則の変更: P3

| | 0.1 | 0.2 |
|---|---|---|
| P3 | **新規性の予算** — 表面構文は Rust / Swift / Go の最大公約数に寄せ、LLM の事前知識を最大限使う | **同形同義・異義異形** — 既存言語の見た目は、意味が一致するときだけ借りる |

0.1 の問題は、コーパスを **目的** として扱ったことだった。コーパスは、意味が一致するときにだけ役に立つ **手段** である。意味が違うのに見た目を借りると、事前知識はかえって誤った予測を生む。

0.2 では P3 を次の 5 つの規則にした（仕様 §0.3）。

1. 言語の中で、同じ概念には同じ見た目を使う。
2. 言語の中で、違う概念には違う見た目を使う。
3. 既存言語から借りるのは意味が一致するときだけ。借りる先は概念ごとに選ぶ。**汎用の部分は汎用言語から、信号処理の部分は信号処理の言語（FAUST, SuperCollider, Cmajor, Lustre）から** 借りる。
4. 偽の友人を作らない。基準は「既存言語の読み方で読んで、**検査を通るのに意味が違う** もの」。検査で落ちる違いは診断で吸収できるので許容する。
5. 意味の広すぎる語を、特定の概念の名前にしない。

3 の「借りる先を選ぶ」が、0.1 で欠けていた視点である。0.1 は汎用言語のコーパスだけを見て、DSP の言語のコーパスを見ていなかった。DSP の基盤言語なら、DSP の部分は DSP の慣習に合わせる方が、利用者（人間も LLM も）の事前知識に合う。

## 2. 名前と構文の監査

0.1 の全てのキーワードと主要な名前を、上の規則で見直した。

### 2.1 変えたもの

| 0.1 | 0.2 | 理由（どの規則か） |
|---|---|---|
| `proc` | `flow` | 規則 5。`proc` は他の言語で無名関数・手続き一般を指す。`flow` はデータフロー・信号の流れという意味に近い |
| proc の呼び出しは関数と同じ `saw(f0)` | flow の呼び出しは後置の `~`: `saw~(f0)` | 規則 2。0.1 では、状態を持つインスタンスの生成と、状態の無い関数の呼び出しが同じ見た目だった。選んだ経緯は §2.4 |
| proc 本体の方程式 `y = e`（順序は自由） | `let y = e` を上から順に並べ、最後の式が出力 | 規則 2。fn の中で `y = e` は **代入** で、意味が違うのに同じ見た目だった。flow の本体は「1 サンプルごとに評価される関数の本体」と同じ形になり、違いは `prev` / `delay` で過去を参照できることだけになった |
| `sink`（引数モード） | `move` | 規則 4 と 3。DSP では sink は「信号の終点」（audio sink, GStreamer）を指す。所有権の移動は C++ の `std::move`、Rust の `move` と同じ意味 |
| `virtual`（モジュール） | `target` | 規則 4。C++ の `virtual` は動的ディスパッチを指す。Kumi のものは「実装をビルドターゲットが与える宣言」なので、それをそのまま名前にした |
| レート `Const[T]` | `Init[T]` | 規則 2。キーワード `const` はコンパイル時、レートは初期化時で、別の概念に同じ語を使っていた。SuperCollider の `ir`（initialization rate）と同じ考え方 |
| `export proc voice as "kumi_voice"` | マニフェストの `[export]` と `prefix` | 規則 2 と P2。`as` が「数値変換」と「シンボル名」の 2 つの意味を持っていた。また export 先をソースとマニフェストの 2 か所に書いていた |
| `[T: Move]` | `[T: ?Dup]` | 規則 2 と 3。`move` との衝突を避ける。Rust の `?Sized` と同じ「暗黙の制約を外す」形 |
| `p.Inputs` / `p.Outputs`（`Buf` のフィールドを持つ struct）+ `frames` | `Span[T]` の引数 | 規則 3。C++20 の `std::span` と同じ意味の非所有ビュー |

### 2.2 残したもの

| 名前 | 残した理由 |
|---|---|
| `inout` | Swift と同じ意味 |
| `let` / `var` | Swift と同じ意味（JavaScript の `let` は可変だが、Kumi で `let` に代入すると検査で落ちる） |
| `trait` / `impl`, `?`, `match` の `=>` | Rust と同じ意味。`?` に `From` 変換が無い違いは検査で落ちる |
| `as` | Rust の `as` の部分集合。検査を通るものは Rust と同じ意味 |
| `fn(x) { ... }`（無名関数） | Go の `func(x) { ... }` と同じ意味。名前付き関数と同じ概念なので同じ語（規則 1） |
| `effect` / `handler` / `handle ... with` | 効果 handler の文献（Koka, Eff, OCaml 5）と同じ意味 |
| `process`（生成される関数） | JUCE の `processBlock`、CLAP の `process` と同じ意味 |
| `prev` | Lustre の `pre` と同じ意味 |
| `delay` | DSP の遅延線と同じ意味。Arduino の `delay(ms)`（待機）とは衝突するが、flow の中でしか使えず、引数の数が違うので検査で落ちる（規則 4 の許容範囲） |
| `Str` | Rust の `String` / `&str` と書くと名前解決で落ちる |

### 2.3 新しく加えたもの

| 名前 | 理由 |
|---|---|
| `par i in 0..N { e }` | FAUST の `par(i, N, e)` と同じ意味。`for`（順に実行する反復）とは違う概念なので違う語にした（規則 2） |
| 後置の `~`（`saw~(f0)`） | flow のインスタンス生成の印。FAUST の `~`（状態を作るフィードバック）と意味の方向が同じ（§2.4） |
| `Span[T]` | C++20 の `std::span` と同じ意味 |
| `@param(...)` | FAUST の `hslider` などに当たる。ただし式の中ではなくシグネチャに書く |
| `blocking effect` | ブロックしうる効果の印。「blocking I/O」と同じ意味 |

### 2.4 flow の呼び出しの表記を決めた経緯

状態を持つインスタンスの生成（flow の呼び出し）を、状態の無い関数の呼び出しと見分けられるようにしたい。次の案を比べた。

| 案 | 例 | 判断 |
|---|---|---|
| flow 名を UpperCamel にする | `Saw(f0)` | 不採用。型名に見える |
| `@` 始まり | `@saw(f0)` | 不採用。Kumi 自身が `@param` などの属性に `@` を使っている（規則 2）。Python / Java / Kotlin / TypeScript / Swift でもデコレータ・属性を意味し、Ruby ではインスタンス変数（値）を意味する |
| 束縛子 `node` を分ける | `node f1 = resonator(...)` | 不採用。式の中にインスタンスを書けなくなり（ワンライナーの禁止）、制限が大きい |
| 前置キーワード | `let f1 = node resonator(...)` | 不採用。`node` が並んで人間には読みにくい |
| `new` | `new resonator(...)` | 不採用。C++ / Java / JavaScript ではヒープ確保を意味し、組込みでは偽の友人になる |
| `#` / `$` 始まり | `#saw(f0)` | 不採用。`#` は多くの言語でコメントの開始、`$` は変数の参照 |
| `.new` | `saw.new(f0)` | 不採用。サンプルごとに評価される式の中で「毎回新しく作る」と読める |
| `.(` | `saw.(f0)` | 不採用。Julia では要素ごとの適用で、flow の中の rt fn の意味（点ごとの適用）と一致してしまう |
| **後置の `~`** | `saw~(f0)` | **採用** |

`~` を選んだ理由:

- 式の中に書けて、短い。`(f1 + f2) * smooth~(gain, 0.01)` のような書き方ができる。
- 主要な言語に「名前の直後に `~`」という形は無く、偽の友人にならない。
- FAUST の `~` はフィードバック、つまり状態を作る演算子で、「状態を持つものを作る」という意味の方向が同じ。
- flow 名は関数と同じ `snake_case` のままにでき、生成される API は名前空間（`voice.State`、`voice.init`）になる。flow は型に見えない。
- 付け忘れも付け間違いも検査で落ち、修正候補は一意に決まる。主な書き手は LLM なので、1 文字の印でも誤りは残らない。

## 3. FAUST に代わる基盤としての変更

| FAUST | Kumi 0.2 | 仕様 |
|---|---|---|
| point-free のブロック図代数 | 名前付きの `let` と、生成するグラフ（`kumi graph`） | §11 |
| UI の宣言を式の中に書く（`hslider("freq", ...)`） | `Ctl` 入力に `@param` を付ける。パラメータの一覧はシグネチャだけで分かる | §11.7 |
| `par(i, N, e)` | `par i in 0..N { e }` | §11.5 |
| アーキテクチャファイル | ターゲット（`kind`）と生成される C API | §14.2, §15.3 |
| `-lang c / cpp / rust / wasm ...` | 移植可能な核（flow と、そこから呼ばれる関数）を各言語へ変換 | §13 |
| バックエンドごとに libm が違い、出力が一致しない | `strict` では全変換先でビット一致。`kumi test --backends all` で検査 | §13.3 |
| クラスの大きさが静的に決まる。`-mem` で大きな配列の置き場所を変える | `SIZE` / `BULK_SIZE`、fast / bulk の二領域 | §12.4 |
| ポリフォニーは言語の外（`[nvoices]` の慣習とアーキテクチャファイル） | ボイスの割り当てを同じ言語で書け、rt とヒープ不使用が検査される | §17.6 |
| FAUST IDE | `kumi lsp` + `play` / `probe` / `graph`。名前付きの信号なので、プローブとホットリロードでの状態の引き継ぎができる | §18.3 |

「移植可能な核」は、新しい検査を足さずに既存の規則から決まるようにした。flow から呼べるのは効果行が空の関数だけで、0.2 では `Alloc` が効果になったので、効果行が空なら自動的にヒープも使わない。

**変換は段階的に広げる。** 第一段階は移植可能な核だけを全ての変換先へ移し、最終目標は言語全体の変換とする（仕様 §13.1）。そのため、言語機能は最初から「全ての主要な変換先への変換方法を示せること」を条件に設計する（P7、§13.5）。0.2 の設計のうち、この条件に効いているものは次の通り。

- handler を末尾再開に限ったので、継続の捕捉が要らず、関数の表を隠れた引数で渡すだけで変換できる。
- Shared 型は不変なので、参照カウントの言語でも GC の言語でも、観測できる意味が同じになる。
- 破棄の位置はコンパイル時に全て決まるので、GC の言語でもファイナライザに頼らずに `drop` を呼べる。
- 参照とクロージャは第二級なので、変換先でライフタイムや環境の寿命を表す必要が無い。

一方で、ブロックできない変換先での `Block`、言語ごとの FFI、JavaScript の 64 ビット整数、文字列の内部表現、arena の枯渇の 5 点は、言語全体の変換を妨げる既知の差として残っている（仕様 §13.5）。

## 4. メモリ管理の変更（組込み向け）

| 項目 | 0.1 | 0.2 | 理由 |
|---|---|---|---|
| ヒープ確保 | `Alloc` は非 rt の関数に暗黙に含まれ、handler で処理できない | `Alloc` は **明示の効果**。handler（`arena` など）で差し替えられる | ヒープを使うかどうかがシグネチャで分かる。ヒープの無いターゲットでは `main` に `Alloc` を書けないことが、シグネチャだけで検査できる |
| arena | 無い | `handle { ... } with arena(inout scratch)`。結果は Copy に限る | ヒープの無い機器でも、初期化時の一時的な計算に作業領域を使える。型で持ち出しを防ぐ |
| `Block` | 暗黙 | ブロックしうる効果を `blocking effect` と宣言する。関数がブロックしうるかは効果行だけで決まる | ブロックできない環境（ブラウザ、AudioWorklet、GUI スレッド）へ持ち込めるかをシグネチャで判断するため。JS への変換では `async` にする関数がシグネチャで決まる |
| rt の規則 | 4 つの規則（Shared の生成禁止、Drop の禁止などを個別に記述） | `Alloc` を持たない + rt でない関数を呼ばない + 再帰しない | Shared の生成や破棄の禁止は `Alloc` の規則から導かれるようになった |
| 遅延線の長さ | `Const` レート（初期化時に決まる） | コンパイル時定数 | 状態の大きさがコンパイル時に決まる |
| 状態の配置 | 呼び出し側の所有、とだけ | `SIZE` / `BULK_SIZE` / `ALIGN` を出力。fast / bulk の二領域。C API はメモリを呼び出し側から受け取る | 内部 SRAM と外部 SDRAM を使い分ける機器（Daisy など）に対応する |
| スタック | 規定なし | rt は再帰禁止。`kumi audit --stack` で最悪値を報告。`main` のローカルは静的領域に置ける | 組込みではスタックが小さく、溢れても検出されない |
| リテラルの既定の型 | 整数は `I64`、浮動小数は `F64` | 既定の型は無く、決まらなければエラー | 単精度 FPU しか無い機器で、`F64` のソフトウェア浮動小数に気付かず落ちるのを防ぐ |
| クロージャ | 値をコピーで捕捉する第一級の値（環境の置き場所が未定義） | 捕捉するクロージャは引数の位置だけ（第二級） | 環境をヒープに置かずに済む |
| 参照カウント | 原子的かどうか未定義 | 既定は非原子的。スレッドに送った値だけ原子的 | スレッドの無い機器で原子命令を使わない |
| panic | プロセス終了 | OS の無いターゲットでは `trap` / `reset` / `halt` を選べ、メッセージを除ける | フラッシュの節約 |
| `Atomic[T]` | 8 バイト以下 | ターゲットが lock-free で扱える幅まで | Cortex-M（ARMv7-M）は 8 バイトの原子命令を持たない |

## 5. 0.1 の誤りの修正

- **`vdelay` の遅延量の下限。** 0.1 では `d` を `[0, MAX]` に飽和させていたが、`d = 0` で自己参照すると遅延を通らない閉路になる。0.2 では `[1, MAX]` にした。
- **遅延線の長さと「状態は固定サイズ」の矛盾。** 0.1 は遅延線の長さを `Const`（初期化時）レートとしながら、状態を「固定サイズ」と書いていた。0.2 ではコンパイル時定数に限った。
- **シャドーイングが未定義だった。** flow の自己参照（`prev(phase, ...)` の中の `phase`）と、`let x = x + 1` のようなシャドーイングが意味の上で衝突しうる。0.2 ではシャドーイングを禁止した。

## 6. 新たに生じたトレードオフ

1. **汎用コードの `uses {Alloc}` が増える。** 文字列や配列を扱う関数のほとんどに付く。代わりに、ヒープを使わない関数がシグネチャだけで分かる。
2. **flow 本体の順序に意味ができた。** 0.1 の方程式は順序が自由だった。0.2 では依存の順に並べる必要がある（遅延を通る参照は除く）。fn の本体と同じ読み方ができる代わりに、書き手が順序を決める必要がある。
3. **`~` は 1 文字なので、人間が読むときに見落としやすい。** 付け忘れと付け間違いは検査で落ちる（E0811 / E0812）ので、書き手（主に LLM）の誤りは残らない。読み手の側は、IDE の色分けで補う。
4. **捕捉するクロージャを保存できない。** コールバックを struct に持たせる書き方ができない。名前付き関数と状態の struct で書く。
5. **キーワードが 1 つ増えた（`par`）。**
6. **0.1 の「Rust に近い見た目」からは離れた。** その分、LLM が最初に書くコードの誤りは増えうる。診断の修正候補（`proc` → `flow`、`&mut` → `inout` など）で吸収する前提で、測定が要る。

## 7. 決めてほしいこと

次の 5 点は、0.2 で推奨案を採ったが、方針として確認が要る。

1. **`Alloc` を明示の効果にするか。** 推奨: する。組込みを本気で対象にするなら、ヒープの有無がシグネチャに出ることの価値が、記述量の増加を上回る。
2. ~~flow 名を UpperCamel にするか。~~ → 後置の `~` に決定（§2.4）。
3. **flow 本体を順序付きの `let` にするか、順序自由の方程式に戻すか。** 推奨: 順序付きの `let`。fn と同じ読み方ができ、因果性の検査が名前の順序の検査になる。
4. **トランスパイル先の優先順位。** 推奨: C（必須）→ JS（ブラウザの IDE と試聴に要る）→ C++ → Rust。
5. **組込みは当面「C のホストから export した flow を呼ぶ」形だけにするか。** 推奨: そうする。Kumi で書いたファームウェアのエントリ（割り込みとメインループの状態共有）は設計が大きいので、0.3 以降に回す（§19）。

## 8. 確定した方針

| 項目 | 決定 | 仕様 |
|---|---|---|
| 最初の実装の範囲 | 移植可能な核（flow、効果行が空の `rt fn`、Copy 型、`const`）だけを先に作る | §20 |
| コンパイラの実装言語 | Rust。ブラウザの IDE のため WASM にもビルドする | §20 |
| 添字・長さ・大きさの型 | `U32` に固定。`USize` / `ISize` は廃止。C の `size_t` は FFI の中でだけ `CSize` | §4.1, §14.1 |
| ブロックの扱い | 効果の宣言に `blocking` を付ける（案 C）。`Chan` などは `Sync` 効果、待機は `Sleep` 効果。extern は `uses {Block}` で主張する | §8.2, §10, §16 |
| 文字列 | 常に正しい UTF-8。長さと位置はバイト単位（Rust / Go と同じ、案 A）。`s[i]` の添字は無い。順序はバイトの辞書順 | §4.2 |
| `Map` / `Set` の反復順序 | 挿入順。全ての変換先で決定的 | §4.3 |
| 言語の名前（Ori / Kumi） | 未定。改めて決める | — |

`USize` を「32 ビットに固定した `USize`」として残さなかったのは、Rust の `usize` と同じ名前で幅が違うと、検査を通るのに意味が違う（オーバーフローする点が違う）偽の友人になるからである（§0.3 の規則 4）。
