# Onsa ツールの仕様（0.3）

言語の仕様（[`onsa-lang-spec-0.3.md`](../onsa-lang-spec-0.3.md)、以下「基本仕様」）§18 のコマンドのうち、人が見る表示と、道具の書式の約束を書く。

基本仕様との分け方（2026-10-04、S-66。2026-10-08 の S-232 で `onsa fmt` について改めた）:

- **基本仕様**: 言語の規則と、利用者・CI・修復のループが依存する約束。診断と修正候補、`--json` の出力、終了コード、`onsa fmt` の約束（意味を変えない、二度かけても同じ、止める条件）、`onsa interface` の内容と大きさなど。
- **この文書**: 人が見る表示と道具の書式。グラフの形・色・枠、`onsa play` の UI、`onsa probe` の表示、`onsa fmt` の正規形と書き換えの一覧（§3）、コマンドのテキストの出力（§4）など。変えても、書いたコードの受理と意味は変わらない（`onsa fmt` の正規形を変えると `fmt --check` の結果は変わるが、プログラムの受理と意味は変わらない）。

分けるかどうかは記述量ではなく内容で決める。整理の軸は、機械が読むもの（JSON、終了コード）は基本仕様、人が読むもの（テキスト）と道具の書式はこの文書である。基本仕様は `onsa primer` で LLM のコンテキストにも入るので、表示と道具の細部を入れない。

## 1. `onsa graph`

flow の信号グラフを DOT で出す（`--svg` で SVG。Graphviz の `dot` を使う）。

### 1.1 ノード

| ノード | 形 | ラベル |
|---|---|---|
| 入力 | 楕円 | `名前: 型 at クロック`（ソースの宣言と同じ形、基本仕様 §11.3） |
| `let` | 箱 | `名前 = 式の種類: 型 at クロック`。ノード名は `let` の名前（基本仕様 §18.2） |
| 名前の無い状態のノード（式の中に直接書いたインスタンス、`prev~` / `delay~` / `vdelay~`） | 角の丸い箱 | 名前は基本仕様 §11.6 の生成する名前（`a.prev_0`、`saws.saw_0`）。ラベルは修飾を除いた `saw_0 = saw~: 型 at クロック` |
| 出力 | 二重八角形 | `out: 型 at クロック` |

クロックで色を分ける: `init` と定数は灰色、`block` は青、`sample` は黒。

### 1.2 辺

- 値を読む向きに引く（読まれる側 → 読む側）。
- 帰還（`^名前`）と、`prev` / `delay` / `vdelay` の look-back の辺は破線にする。それ以外は実線。
- **実線の辺だけでは閉路を作らない。** flow には遅延を通らない閉路が書けない（基本仕様 §11.2）ので、グラフがそれと矛盾する絵を出さないことを保証する。`tests/spec` の全ての flow について、性質テストで検査する。

### 1.3 `par`

- 複製を枠（Graphviz のクラスタ）で囲む。見出しは `par i in 0..<N（×N）`。
- 複製の添字は、枠の中に `init` のクロックの入力として描く（楕円、灰色）。ノード名は `par` の名前で修飾する（`saws.i`）。入れ子でも重ならない。
- 本体の結果から、`par` の結果のノードへ辺を引く。
- 入れ子の `par` は、入れ子の枠にする。

```dot
subgraph cluster_saws {
  label="par i in 0..<4（×4）"
  "saws.i" [label="i: U32 at init" shape=ellipse color="gray40"]
  "saws.saw_0" [label="saw_0 = saw~: F32 at sample" style=rounded]
}
"f0" -> "saws.saw_0"; "detune" -> "saws.saw_0"; "saws.i" -> "saws.saw_0"
"saws.saw_0" -> "saws"; "saws" -> "out"
```

枠にするのは、`par` が N 個の構造の宣言（基本仕様 §11.5）で、「同じ構造が N 個ある」ことと、添字が各複製の中の値であることを見せるためである。

## 2. ホットリロードとプローブの照合

基本仕様 §18.3 の flow の計画を使い、再コンパイルの前後の状態のノードを対応付ける（2026-10-05、R-98）。生成する名前（基本仕様 §11.6）は表示のためのもので、照合には使わない。

- **鍵**: `let` の名前と flow の入力の名前を鍵にする（React の `key` と同じ役割）。名前を変えた `let` は別のものとして扱う。
- **位置**: 同じ鍵の中では、式の木の中の経路（どの呼び出しの何番目の引数か）と種類で対応付ける。ノードを別の呼び出しで包むと経路が変わり、そのノードは初期化される。
- **差分**: 経路だけでは対応が付かない挿入や並べ替えは、旧新の式の木の差分で補ってよい（Glicol は LCS でノードを対応付ける）。
- **型**: 対応付けたノードでも、型（`onsa interface` の表記、組込みの flow の状態は疑似型）が違えば状態を引き継がない。サブインスタンスは、その flow の計画の中まで同じ規則で辿る。
- **定数の変更**: 上流の定数を変えても、下流のノードの対応は変わらない（構造の同値でノードを見分ける方式は、上流の変更で下流の状態を全て失うので採らない）。
- **照合できなかった部分**: `init` で始める。音の途切れを避けるため、旧と新の出力を短くクロスフェードしてよい（FaustLive、SuperCollider の JITLib と同じ）。
- **プローブ**: 付けていたノードを同じ照合で新しい計画に移す。対応が付かなければ外し、利用者に知らせる。

## 3. `onsa fmt` と `onsa diff --ast`

基本仕様 §18.2 は、fmt の約束（唯一の正規形に書き換える、プログラムの意味を変えない、二度かけても同じ、構文の段の診断のあるファイルは書き換えず終了コード 2、確かめの失敗は内部エラー）を定める。この節は、正規形と書き換えの中身、コメントの置き場所、確かめの手順、止めたときの報告を定める（2026-10-08、S-232 で基本仕様 §18.2 から移した）。どの言語の読み方でも意味が一つの余分な書き方（冗長な括弧、末尾の `return` など）を受理することは、基本仕様の各章の規則である（基本仕様 §0.2 の P2）。

### 3.1 止めたときの報告

- `onsa fmt` が構文の段（基本仕様 §18.1）の診断のあるファイルを書き換えないときは、`onsa check` と同じ選び方（単位ごとに一つ、基本仕様 §18.1）でその診断を報告する。それ以外の診断（命名の E0320、名前の段で出る `Sig[F32]` の E0020 など）は整形を妨げず、fmt は報告しない。
- 複数のファイルを渡したときは、一つのファイルの誤りで止めずに全てのファイルを処理し、構文の段の診断の無いファイルだけを書き換える。
- `onsa diff --ast` も、構文の段の診断のあるファイルは比べず、同じ選び方でその診断を報告する。
- 診断は標準出力に出す（§4）。

### 3.2 正規形

`onsa fmt` の正規形は、次の閉じた一覧で決まる。書き手の改行（並びやメソッドの連鎖をどこで折るか）は保ち、行を自動で折り返さない。

- 字下げは 2 空白で（タブは使わない）、継続した行（基本仕様 §2.5）は 1 段深くする。改行は LF で（CR LF は LF にする、基本仕様 §2.5）、ファイルの末尾は改行一つ。
- 二項演算子、`=`、`->`、`=>`、`as`、`at` の両側に空白を一つ置く。前置の記号、名前に付く印、後置（`-x`、`!x`、`^y`、`f~(x)`、`f!(x)`、`f(x)`、`v.(x)`、`xs[i]`、`.f`、`?`、式の中の型引数 `f::[T](x)`）には空白を置かない（基本仕様 §2.5）。式の中の型引数の並び（基本仕様 §4.5）は、`::[` の前後に空白を置かず、並びの中は型の位置の並びと同じに書く（`, ` で区切り、括弧の内側に空白を置かない）。期待型の注釈と型引数（`let y: U8 = id(250)` と `let y = id::[U8](250)`）は、互いに書き換えない。`,` と `:` の後に空白を一つ置き、前には置かない。丸括弧と角括弧の内側には空白を置かない。struct リテラルとパターンの `{ }` の内側には空白を一つ置き（`Point { x: 1.0 }`）、効果行と `use` の並びの `{ }` の内側には置かない（`uses {Alloc}`、`use a.{x, y}`）。
- 並び（引数、要素、フィールド、列挙子、`match` の腕など）は三つの形のどれかにする。1 行（開き括弧の行に全ての要素がある）、ブロック形（開き括弧の直後で改行し、要素を 1 段深くして全ての要素の後に `,` を置き、閉じ括弧を独立の行に置く）、継続形（最初の要素の下に揃え、末尾の `,` は置かない）。どの形かは書き手の改行で決まる（開き括弧の直後で改行していればブロック形、それ以外で要素の間で改行していれば継続形）。
- 空行は、項目の間でも文の間でも 0 か 1 で、書き手のものを保つ（2 以上は 1 にする）。ブロックと並びの先頭と末尾の空行、継続の間の空行（基本仕様 §2.5）は取り除く。
- `else` と `with` は直前の `}` と同じ行に置く（基本仕様 §2.5）。
- 項目と flow の入力の属性は独立の行に置き、`let` の属性（`@mem(bulk)`）は `let` と同じ行に置く。
- 連続する 1 行の `let` と `var` の `=`（型注釈の付いたもの、分解するものも含む）と、連続する行の行末のコメントは桁を揃える。`=` の列は、空行、複数行の文、属性の付いた `let` で切れ、コメントだけの行では切れない。
- 数値リテラルの綴りを揃える（基本仕様 §2.4）: 接頭辞（`0x` `0b`）と指数（`e`）は小文字、指数の `+` は外す（`1e+3` は `1e3`）、16 進の数字は大文字、`_` は数字と数字の間に一つずつ（`1__000` は `1_000`、`1_` は `1`、`0x_1F` は `0x1F`）、浮動小数の整数部の余分な 0 は外す（`01.5` は `1.5`）。

### 3.3 プログラムの構造を変える書き換え

`onsa fmt` がプログラムの構造（AST）を変える書き換えは、次の閉じた一覧だけである。それ以外は、空白、改行、字下げ、末尾の `,`、数値リテラルの綴り（基本仕様 §2.4）など、AST に現れない表記だけを変える。

- 末尾の位置の `return` の除去（末尾の位置の定義は基本仕様 §6.1）
- `-> ()` と空の `uses {}` の除去（基本仕様 §6.1、§8.1）
- 冗長な括弧の除去（基本仕様 §3.1）
- 既定値と等しいリテラルの `init` の除去（`0`、`0.0`、`false`。`-0.0` は既定値と違うので残す。基本仕様 §11.4）
- 返り値の位置の `move` の除去（基本仕様 §5.2）

外す括弧は次のとおりである（P2）: 強い群の式を弱い群の被演算子として囲む括弧（`(a * b) + c` は `a * b + c`、`(i + 1) < n` は `i + 1 < n`）、名前・リテラル・後置式・括弧を囲む括弧（`(x)`、`((e))`、`(f(x)).y`）、文・引数・要素・見出しの式の全体を囲む括弧（`let y = (a + b)`、`f((a + b))`、`if (c) {`）。同じ群の中の括弧（`(a + b) + c`。書き手のまとまり）、強弱の無い組み合わせの括弧、無いと誤りになる括弧（見出しの struct リテラル、前置演算子の重ね `-(-x)`、`as` / `at` の連鎖）は変えない。構文の段の誤りになる括弧（`(s.f)(x)`、基本仕様 §6.1）のあるファイルは、fmt が書き換えない。

### 3.4 コメント

`onsa fmt` は、コメントを書かれた行に残す（ブロックコメントは無いので、どのコメントも行末にある。基本仕様 §2.1）。行末のコメントは、その行の要素の後ろ（補った `,` の後ろ）に残す。単独の行のコメントは次の要素の前に、次の要素が無ければ閉じ括弧の前に残す。並び（引数、フィールド、列挙子、要素、`match` の腕など）の中でも、式の途中でも同じである。コメントを含む囲みは 1 行にまとめない（空の本体を `{}` にしない）。連続する行の行末コメントの桁揃えは、並びの中でも行う。

### 3.5 書き込む前の確かめと `onsa diff --ast` の比べ方

`onsa fmt` は、書き込む前に出力を解析し直し、元と同じプログラムであることを確かめる。同じとは、両方に §3.3 の一覧の書き換えを施した AST と doc コメントが一致し（数値リテラルは綴りではなく値で比べる）、通常のコメントのテキストが同じ順に並ぶことである。違えば fmt の不具合なので、ファイルを書き換えず、最初に違った項目を示して内部エラー（終了コード 101、基本仕様 §18.2）で終わる。診断コードは付けない（利用者のコードの誤りではない）。`onsa diff --ast` も同じ比較を使うので、fmt の前後で差分を報告しない。

## 4. コマンドのテキストの出力

`--json` を付けない出力の約束（2026-10-08、S-232、S-234、S-233、S-241）。`--json` の出力と、それを出す終了コードは基本仕様 §18.1・§18.2 に定める。

- 全てのコマンドで、診断は標準出力に、診断でない文（使い方の誤り、入出力の誤り、内部エラー）は標準エラーに出す。`--json` の有無で流れは変わらない。`onsa fmt` と `onsa diff --ast` の構文の段の診断は、終了コードが 2 でも診断なので標準出力に出す（終了コード 2 の使い方の誤りや入出力の誤りの文とは流れが違う）。
- 一つの診断は `<ファイル>:<行>:<列>: error[<コード>]: <文面>` の行で始める。ファイル・行・列は `--json` の `span` と同じ値で、ファイルはパッケージのルートからの経路（区切りは `/`）である。続く行（ソースの抜き出しと範囲の印、`note:` の行、修正候補）は人が読むためのもので、形は約束しない。機械が読むのは `--json` である。
- 診断は `--json` の `diagnostics` と同じ順（ファイルの文字列、行、列、終わりの行、終わりの列、コード、文面）に並べる（基本仕様 §18.1）。
- `onsa test` の結果は、テストごとに `test <完全な名前のテキスト> ok` の行で報告し、失敗は `test <完全な名前のテキスト> failed at <ファイル>:<行>: <文面>` の行で報告する（`test dsp "decays" ok`、`test dsp "decays" failed at dsp.onsa:12: assert <式のソース>`）。完全な名前のテキストは基本仕様 §11.8 で定める（2026-10-08、S-233 で基本仕様 §11.8 から移した）。
- panic の文面（組込みの検査の panic、std の補助の失敗の文面）に値を書くときは、その値の型の基本仕様 §6.3 の `Show` の文字列で書く（浮動小数は `1.0e308` の形で、Onsa のリテラルとして読み戻せる）。std の関数の失敗の文面そのもの（`assert_near` など）は、その関数の doc コメントに書く（S-241）。
