# Ori Draft 0.1 と Kumi Draft 0.1 の比較

- Ori: [`ori-lang-spec.md`](../ori-lang-spec.md)（Grok 作）
- Kumi: [`kumi-lang-spec.md`](../kumi-lang-spec.md)（Claude 作）
- Ori のレビュー: [`review-draft-0.1.md`](review-draft-0.1.md)
- Rust との比較: [`kumi-vs-rust.md`](kumi-vs-rust.md)

二つは同じ目的を持つ。「LLM が書き、人間が監査し、コンパイラが局所的に否定する」言語で、汎用コードと DSP を一つの言語で扱う。違うのは、その目的にどう到達するかの判断である。

---

## 1. 要約

| | Ori | Kumi |
|---|---|---|
| 一言で言うと | ML 系の小さな核 + FAUST 由来のグラフ代数 | Rust / Swift 風の表面 + 可変値意味論 + Lustre 系の方程式 |
| 局所性をどこで得るか | 構文（明示的な区切り）と境界だけの型注釈 | 全シグネチャの注釈と、関数内だけの推論 |
| DSP の書き方 | point-free の組合せ子（`seq` / `par` / `rec`）+ 名前付き `let` | 名前付きの方程式と遅延（`prev` / `delay`） |
| 仕様の状態 | 方針の宣言。核となる判断（多相、数値型、メモリ、並行性、FFI）が空白 | Ori レビューのチェックリストの全項目に答えを出した。代わりに仕様は大きい |
| 例の整合性 | 例が自分の規則に違反している（C-01〜C-05）。`formant` は型エラーで、かつ発散する | 例を規則に対して手で検査済み（P7）。コンパイラによる検証はまだ |

Ori は「何を捨てるか」を明確に書いた点が優れている。Kumi は、Ori が捨てた後に残った穴をどう埋めるかを決めた仕様である。

## 2. 判断ごとの比較

### 2.1 表面構文と LLM の事前知識

| 項目 | Ori | Kumi | Kumi の判断理由 |
|---|---|---|---|
| ブロック | `end` / `{}` / 閉じ無しが混在 | `{}` のみ | 区切りを一系統にする。C 系の構文はコーパスが最も厚い |
| コメント | `;;`（OCaml の文区切りと衝突） | `//` | 事前知識と衝突させない |
| 関数の形 | カリー化とタプル形式が混在 | タプル形式のみ。部分適用は無名関数で | アリティを一つの形で検査する |
| 中置演算子 | 「flow の 5 演算だけ」と言いつつ、例では算術を中置で使っている | 演算子を群に分け、異なる群の混在には括弧が必須 | 優先順位表を覚えずに済み、かつ算術は普通に書ける |
| `in` | 4 つの意味 | `for x in` だけ | 一語一義 |
| 文字列補間 | 禁止 | 名前とフィールドパスに限って可 | 頻出する書き方で、関数呼び出しを隠さない範囲なら局所性を損なわない |
| 新規性 | 構文も意味論も新しい | 構文は既存言語に寄せ、新しさは意味論に使う（P3） | コーパスがゼロの言語では、構文の新しさはそのまま誤りの多さになる |

### 2.2 型と推論

| 項目 | Ori | Kumi | Kumi の判断理由 |
|---|---|---|---|
| 推論 | Hindley–Milner + 行多相。注釈は境界だけ | 双方向型検査。シグネチャは全て注釈し、推論は関数内だけ | HM では型エラーが別の関数に現れうる。全注釈にすれば、エラーは常にその関数の中で止まる |
| アドホック多相 | 無い（オーバーロードは禁止なのに `<` を両方の型に使っている） | trait。孤児規則あり、重複なし、ジェネリック trait は型ごとに 1 実装 | 演算子・等値・順序・表示の基盤。解決が局所的になる制約付き |
| 数値型 | `Int`, `Float` | `I8..I64`, `U8..U64`, `F32`, `F64` など | DSP、組込み、FFI に必須 |
| 数値の意味 | 未定義 | オーバーフロー・ゼロ除算・範囲外は panic。ラップは明示 | 「未規定の挙動が無い」を本当に成り立たせる |
| 変換 | 「暗黙変換なし」とだけ書いてある | `as` は情報を失わない拡大のみ。他は名前付きメソッド | 情報を失う変換は、必ず呼び出し位置に名前が出る |
| 単位 | `type Hz = Float`（ただの別名） | `struct Hz(F32)`（newtype）。単位代数は未決定 | 別名は型安全に寄与しない |
| チャンネル数 | `Sig n τ`（型レベル自然数が必要） | ポートごとに名前を付ける。配列ポートは未決定 | point-free でなければアリティの算術は不要。HM の外へ出ずに済む |
| フィールドアクセス | 未定義（HM + 名前的レコードでは曖昧） | 型が既知の場合のみ（E0420） | 逆推論をしない |

### 2.3 状態・メモリ

| 項目 | Ori | Kumi | Kumi の判断理由 |
|---|---|---|---|
| 可変性 | 不変が既定。`Buf` と `mut` 領域内の `Ref` | 可変値意味論（Hylo 方式）。ローカルの `var` と、引数モード `inout` / `sink` | 参照を第二級に限定すれば、ライフタイム無しで局所的な可変性が得られる |
| メモリ管理 | 未定義（"may use a runtime"） | Perceus 方式の参照カウント + 書き込み時コピー。値が不変なので循環しない | GC の停止が無く、一意な値はその場で更新される |
| 一意性 | `Buf` は「書き込みで消費、`copy` しない限り」 | 種（Copy / Shared / Affine）を構造から導出する。Affine は `Buf`、`Drop` 実装型、proc の状態 | ユーザ型やリソース型にも一貫して適用できる |
| 呼び出し位置の表示 | 無い | `f(inout x)`, `f(sink x)` | 何が変わるかを 1 行で読める |

### 2.4 効果・エラー

| 項目 | Ori | Kumi | Kumi の判断理由 |
|---|---|---|---|
| 権限の仕組み | `Cap e`、効果行、handler の 3 系統 | 効果 + handler の 1 系統。`main` の効果はターゲットが handler で満たす | 書き方は一つ |
| 効果行の粒度 | 操作単位と効果単位が混在 | 効果単位。細かくしたければ効果を分ける | 単一化が単純になる |
| handler の意味論 | 不明（`resume` が無い） | 末尾再開のみ、証拠渡しで実装 | ゼロコストで、rt と Affine の両方と健全に共存する |
| エラー | `Either` と `Result` が重複。伝播構文なし | `Result` + `?`（型の完全一致のみ、暗黙の変換なし） | 定型コードを減らしつつ、変換は明示する |
| バグ | 未定義 | panic。挙動を文脈ごとに規定（rt では出力を無音にし、インスタンスを poisoned にする） | RT 中のエラーで、何が起こるかが決まっていること |
| 非決定性 | 未定義 | `Clock`, `Random` を効果にする | テストが handler の差し替えだけで決定的になる |

### 2.5 リアルタイム

| 項目 | Ori | Kumi |
|---|---|---|
| 指定の単位 | `ori build --rt`（ビルド全体、"crate"） | `rt fn`（関数単位、関数型の一部） |
| 検査内容 | GC なし、初期化後のメモリ一定（記述のみ） | `Alloc` / `Block` を含まない、Shared 値を生成しない、Drop を伴う破棄をしない |
| 先行例 | — | Clang の `nonblocking` / `nonallocating` 関数効果解析 |

### 2.6 信号処理

同じ二極レゾネータを並べる。

**Ori（§10.3）** — 出力が 2 チャンネルになって宣言と合わず、符号の誤りで発散する（レビュー C-05）。

```ori
flow formant(fc: Float, bw: Float) : Sig 1 Float -> Sig 1 Float =
  let r    = exp(0.0 - pi * bw / sr)
      w    = 2.0 * pi * fc / sr
      b1   = 2.0 * r * cos(w)
      b2   = 0.0 - r * r
  in  rec (y1, y2 ->
        let y0 = add(in, sub(mul(b1, y1), mul(b2, y2)))
        in  y0 || y1
      )
```

**Kumi（§15.3）**

```kumi
pub proc resonator(x: Sig[F32], fc: Ctl[F32], bw: Ctl[F32]) -> (y: Sig[F32]) {
  r  = exp(-(F32.PI * bw) / sample_rate())
  w  = (2.0 * F32.PI * fc) / sample_rate()
  b1 = 2.0 * r * cos(w)
  b2 = r * r
  y1 = prev(y, 0.0)
  y2 = prev(y1, 0.0)
  y  = ((1.0 - r) * x) + (b1 * y1) - (b2 * y2)
}
```

| 項目 | Ori | Kumi | Kumi の判断理由 |
|---|---|---|---|
| 書き方 | point-free の組合せ子と、変数を使うラムダが混在。`add` が二つの意味を持つ | 名前付きの方程式だけ | 差分方程式は DSP の教科書の記法そのもので、人間にも LLM にも事前知識がある |
| フィードバック | `rec` のラムダ。出力 = フィードバックなので、チャンネルを捨てる演算が要るが無い | `prev` / `delay` による自己参照 | 出力と状態を分けて書ける |
| 入力 | 暗黙の `in` | 名前付きのポート | 暗黙の束縛は禁止のはず |
| パラメータ | `Float` の定数のみ（変調できない） | `Const` / `Ctl` / `Sig` の 3 レート | 係数計算がサンプルループの外にあることを型で保証する |
| 因果性 | E08xx があるとだけ書いてある | 閉路は遅延を通ること（E0801） | |
| サンプルレート | 未束縛の `sr` | `sample_rate()`（Const） | |
| Core からの利用 | 「`Buf Float` 上の Core 関数に降下する」の一行 | 名前空間 `p` に `State` / `Config` / `Params` / `Inputs` / `Outputs` と `init` / `reset` / `process` / `render` を生成する | 状態の所有、初期化、サンプルレートの変更、ホスト API が型で決まる |
| Core 関数の持ち込み | 未定義 | 純粋な `rt fn` は点ごとに適用、非 rt の純粋関数は Const 引数でのみ使え、init で評価 | テーブル生成などを通常のコードで書ける |
| グラフの可視性 | 式の形そのものがグラフ | `kumi graph` で図を生成する | （Kumi の弱点、§3） |

### 2.7 外部との接続

| 項目 | Ori | Kumi |
|---|---|---|
| FFI（C の呼び出し） | 無い | `extern "C"`。効果行と `rt` は検証されない主張として `kumi audit` に出す。`Ptr` を伴う呼び出しは `unsafe` 内のみ |
| export | 無い（C はバックエンドとしてのみ） | `export "C" fn`、`export proc`（C の API とヘッダを生成） |
| 条件コンパイル | 未定義 | 無い。virtual モジュールとマニフェストでの割り当てで代替 |
| ターゲット | バックエンドの一覧のみ | プラットフォーム × 数値プロファイル × 提供する handler × virtual の割り当て × エントリの種類 |
| 決定性 | 「決定的」と主張するが浮動小数の扱いが無い | 数値プロファイル `strict`（FMA なし、再結合なし、自前の `std.math`）でターゲット間のビット一致 |
| 人間の決定の強制 | 役割分担を文章で書いただけ | `kumi.policy`（効果、unsafe、凍結するインタフェース）を `check` で強制 |
| 並行性 | 無い | 構造化並行性、`Spsc` / `Atomic` / `Swap`（rt 安全）、データ競合は型で排除 |

### 2.8 ツール

両者とも、安定した診断コード、JSON 診断、型付きホール、インタフェース抽出、AST 差分を持つ。これは Ori の最も良い部分で、Kumi はそのまま引き継いだ。Kumi が追加したものは次の通り。

- `kumi audit`: 信頼境界（extern、unsafe、`@relaxed`）とポリシーの差分
- `kumi graph`: proc の可視化
- `kumi primer`: 版に固定された言語要約と標準ライブラリのインタフェース（API の捏造対策）
- `kumi explain`: 診断コードの説明

## 3. Kumi の弱点とリスク

Kumi が全ての点で優れているわけではない。

1. **仕様が大きい。** 引数モード 3 種、種 3 種、レート 3 種、効果、trait、proc、ポリシー。Ori が小さく見えるのは空白が多いからでもあるが、学習コストと実装量は Kumi の方が明らかに大きい。
2. **全注釈は冗長。** シグネチャのトークンが増える。局所性と引き換えにした判断。
3. **「偽の友人」のリスク。** Rust に似せたことで、LLM が `&mut`、`<T>`、`::`、`;`、ライフタイム注釈といった Rust の構文を書く危険がある。診断の修正候補で吸収する必要があり、この判断の正否は測定しないと分からない。Ori の ML 風の構文にはこのリスクが小さい。
4. **グラフの可視性。** 方程式で書くと、ブロック図としての形は FAUST や Ori の組合せ子ほど一目では見えない。`kumi graph` で補うが、それはツールの側の話。
5. **暗黙のレート昇格。** 「暗黙変換なし」の原則の、意図的な例外。レビューでは明示的な `lift` を提案していたが、DSP の式が `lift` で埋まるのを避けるために方針を変えた（§5）。
6. **分岐の中の proc は常に進む。** CPU を無駄にし、「止まっているボイス」を表現できない。クロックの導入は未決定。
7. **handler の表現力。** 末尾再開のみなので、generator、async、早期脱出を効果で書けない。Koka などと比べると明らかに弱い。rt との両立を優先した。
8. **panic は効果行に出ない。** 「世界への接触は全てシグネチャに出る」の穴。全関数に panic が付くのを避けた妥協。
9. **`strict` 数値プロファイルの性能コスト。** FMA の禁止と自前の数学関数は遅い。`@relaxed` は監査の対象になる。
10. **未決定事項が残る。** マルチレート（FFT、オーバーサンプリング）と配列ポートは、DSP として実用上の大きな欠落。

## 4. Ori から引き継いだもの

- 目的の定式化（「局所・高速・決定的に否定できる言語」）と、捨てるものの一覧（継承、例外、意味的空白、マクロ、null、オーバーロード）
- 効果をシグネチャに載せること
- ライフタイムではなく一意バッファで RT を賄うこと
- FAUST の性質（状態は遅延だけ、結線の検査、タイトなループへの降下）を DSP の部分言語として持つこと
- 安定診断コード、JSON 診断、型付きホール、`interface`、AST 差分、決定的な `fmt`
- 人間・モデル・コンパイラの役割分担（Kumi はこれをポリシーファイルで強制可能にした）
- 公開関数にはテストを要求する方針

## 5. レビューでの提案から変えた点

| レビューでの提案 | Kumi での扱い | 理由 |
|---|---|---|
| P-01 (b) レートの昇格は明示的な `lift` で | 暗黙の昇格 | 値を変えず向きが一意なので、昇格によって意味が隠れない。明示にすると DSP の式が読めなくなる |
| P-01 (d) `rt` を効果として表す | `rt` 修飾 = 暗黙の `Alloc` / `Block` を含まない効果行 | 形式としては効果のまま。ただし通常のコードで `uses {Alloc}` を毎回書く儀式を避けた |
| P-01 (e) Flow にチャンネルを捨てる演算を足す | 不要 | point-free ではなく名前付きにしたので、使わない信号は参照しなければよい |
| G-05 型レベル自然数 | 不要 | 同上。アリティはポートの名前と数で決まる |

## 6. 推奨

- **核の判断は Kumi の方針で進めることを勧める。** 理由は二つ。Ori のチェックリストの項目は、どれも決めないと実装できない。そして、関数内で閉じる型検査と名前付きの方程式は、Ori 自身の原則（局所性、一意性、暗黙の束縛の禁止）を Ori の現在の案より忠実に満たす。名前は Ori のままでよい（Ori 0.2 として統合する）。
- **表面構文（Rust 風か ML 風か）は測定で決める。** Kumi の最大の賭けは「既存言語に寄せる」こと（§3 の 3）。同じ課題 10〜20 問を、Kumi の構文と Ori の構文の両方でプライマーだけ渡して LLM に書かせ、`check` を通るまでの反復回数を比べる。そのためには最小の構文解析器と検査器が先に要る（Kumi §18 の 1）。
- **最初に作るのは検査器。** 仕様の例を回帰テストにする。Ori の例の誤りは、検査器が 1 本あれば全て機械的に見つかっていた。
