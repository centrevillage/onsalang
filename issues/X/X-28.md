# X-28 生成するコードの最適化の案

- 決めたこと:
  - 置き場所（2026-11-24、182 回目、利用者「最適化の案として控えておきましょう」）: 生成するコード（Core と C）の実行時の性能を上げる案を、性能の作業を作るときの材料としてここに集める。今はどれも作らない。
  - 案:
    - O1 `when~` で止まる部品の中の遅い段（W7-10、S-1228 の議論から）: `when~` の中の格子は動いた刻みで数える（§11.9 の位相のカウンタ、§11.3・§11.10）ので、一度でも止まると外の格子からずれ、中の遅い段は W の段の中で `when~` のカウンタの格子に従って動く。
      `when~` の無い部品の遅い段は外の格子の決まった位置に来るので、`sample` のループを N で切る（遅い段の呼び出しを内のループの外へ出す）・`sample` の処理をまとめて回す、といった手が使えるが、`when~` の中では同じ手が使えない（刻みごとに止める判定は、カウンタが無くてもまとめて回すのを妨げる）。
      今の Core は `when~` の無い遅い段も刻みごとの分岐で呼ぶので、差は分岐一つ（182 回目に Core の写しで確かめた）。
      和らげ方（親の見立て、試していない）: 条件がリテラルの `true` なら、カウンタは外のカウンタと常に等しく畳める。パラメータの種類の条件（`block` など）はホストの区切りの中で全部動くか全部止まるので、区切りの頭でずれの量が決まり、その区切りの中では遅い段の位置が「ずれた格子」として前もって分かる（N で切る手をずらして使える）。信号の条件は刻みごとに決まるので和らげられない（部品が何刻み動くかがデータ次第で、どの設計でもまとめて回しにくい）。
      外の格子に揃える読み（境界だけを外の格子で来させる）は、止まった後の境界で部品が動いていない位置の値を集め、部品の中の `prev~`（動いた刻み）と時間の基準が割れるので採らない（S-172・S-558・S-1217）。
