## Q2 重い項目の入力の選び方

**策**: 絞った回の入力は次の和集合にする。
1. **差分に触れた種**: 差分で足した・変えた `tests/**/*.onsa`（fmt-props は `std/`・`examples/` も）。
2. **決まった抜き取り**: 種の経路と作業 ID のハッシュで選ぶ 1/5（`sha256("W3-13|" + path) % 5 == 0`）。作業 ID を塩にするので、同じ作業の回し直しでは同じ種になり、作業が変われば別の 1/5 になる（作業をまたぐと別の種に当たる）。
3. 保存した入力（`tests/fuzz/`）の再生と実装待ち・許可の一覧の照合は、絞った回でも常に全体で行う（85 件で軽く、回帰の網はここ）。

**全体の回との関係**（実験で確かめた）: `fuzz.py` は `seeds(root)` を全体のまま読み、`corpus`・`tokens`・切り詰めの `counts` は全体から出して、変異させる種だけを絞る。こうすると絞った回の変異体は全体の回の変異体と一文字も違わない部分集合になる（2,720/2,720）。
種の一覧を先に絞ると部分集合にならない（918/2,720）ので、実装はこの順を守る。もう一点、fix の段に通す変異体は「回の中の番号 % FIX_EVERY」で選んでいる（`run` の `chosen`）ので、絞った回では**全体での番号**（種の番号 × per-seed + k）を使って選ぶように変える。そうしないと絞った回と全体で fix の段に通る変異体が変わる。
fmt-props は源ごとに独立の種なので、源を絞るだけで部分集合になる。`--per-kind 1` も前半と一致する。

**同じ作業での回し直し**: 入力は（version、経路、本文、作業 ID）だけで決まり、担当の直しで種のファイルが変わらなければ同じ。種のファイルを変えた直しの後は、その種の変異体が変わる（今と同じ性質）。

**確信**: 高い（部分集合の性質は実験、決定性はコードの `seeded_random` の読み）。

**副作用**: 1/5 の抜き取りは作業ごとに別なので、「この作業の検査で通った」は全体の 1/5 + 差分の種について言えるだけ。網羅の検査が残りを受け持つ（Q3）。

**実装の量**: `tools/fuzz.py` の `mutants`・`truncations`・`run` に「選ぶ種」の引数（約 30 行）と `main` の `--select FILE`／`--sample K --salt ID`（約 15 行）。`tools/fmt_props.py` の `run`・`main` に同じ（約 25 行）。`tools/test_gate.py` の `Fuzz`・`FmtProps` に「絞った回 ⊂ 全体の回」「同じ塩で同じ入力」の自己テスト（約 60 行）。

## Q3 網羅の検査の回し方

**策**:
- **分け方**: 全体の gate を、錠を別々に取る部分に分けて回せるようにする（`tools/gate.sh --only fuzz fix-loop`、`--only fmt-props fmt-comments fmt-cst`、`--only gate-selftest c-clang …`）。
  各部分は今の主のツリーの時間で約 4〜5 分（fuzz 219 + fix-loop、fmt の 3 項目 186+106+46 = 約 5.6 分 → fmt-props と残り 2 つに分けてもよい）。担当の gate は錠の後ろで待っても最長 5 分で済む。
- **合図**: (a) 作業のコミットのたびに、親が `tools/bg.py run` で**一部分**を裏で回す（数回のコミットで一巡）。回す時機は、担当に作業票を渡した直後（担当は設計・実装の間、絞ったテストしか回さないので錠と競合しにくい）。(b) 段の終わり（`--stage-end`）は全体。(c) fuzz・fmt の道具や `tests/pending.toml` の形を変えた作業の後は、その項目を全体で。
- **負荷**: 一部分は gate の錠を取って全コアで回す（並べない。leader-rules 5.8）。`--jobs 5` で錠を取らずに担当の gate と並べる案は、10 コアに 15 の仕事を載せて両方を遅くするので採らない。
- **見つけたものの扱い**: 今の leader-rules 4.5 のまま（入力の保存、R の登録、許可の一覧か `fuzz-input` の項目、直す作業の決定）。差分で入ったかの見分けは Q4 の基のバイナリでなく、「前回その項目が全体で通ったコミット」からの範囲で見る（数コミット）。
- **「最終的に検知できる」の形**: gate が、回した項目ごとに（コミットの SHA、全体か絞ったか、結果、時刻）を `target/gate/last.json` に書き、要約に「fuzz: 全体の最後の PASS は 628f8ec（3 コミット前）」のように出す。保証は二段: 段の終わりの `--stage-end` が全項目を全体で回す（固い保証、今もある）。
  その前に、各項目が N コミット（部分の数、3〜4）に 1 回は全体で回る（親の運用の保証。`last.json` の表示で抜けが見える）。

**確信**: 分け方と記録は高い。合図の守られ方は中（親の運用に依る。`last.json` の表示が忘れを見せるのが要）。

**副作用**: 網羅の検査でしか見つからない差分の誤りは、コミットの後に見つかり、直す票が後で要る（GF-2 の副作用のまま）。`last.json` は機械ごとの状態で、リポジトリには入らない。

**実装の量**: `tools/gate.py` に `--only ITEM...`（約 20 行）、`last.json` の読み書きと要約の行（約 40 行）、自己テスト（約 40 行）。`bg.py` はそのまま使える。

## Q4 差分で入ったか前からあるかの見分け（GF-3）

**策**: 落ちた**入力の本文**を基のバイナリで回し直して決める（型や分類で決めない）。
- `fuzz.py` と `fmt_props.py` に `--base-binary PATH`（fuzz は `--base-cases-binary` も）を足す。新しい型の最小化した入力ごとに、基のバイナリで同じコマンドを回し、同じ署名（fuzz）か同じ性質の失敗（fmt-props）が出れば `pre-existing`、出なければ `new in this tree` と印を付けて出す。
- 判定: 絞った回（作業の検査）では、`pre-existing` の fix の約束の違反と fmt の性質の失敗は項目を落とさず NOTE として並べる（親が区切りで扱う）。内部エラー・異常終了・時間切れは前からあっても落とす（leader-rules 4.5 のまま）。全体の回では今のとおり全て落とす（親が登録・許可する）。
- 基のバイナリは、主のツリーの `target/debug/onsa` と `target/debug/onsa_cases`。gate は基の妥当性を確かめて要約に出す: 主のツリーの HEAD が作業ツリーの `merge-base` と一致し、主のツリーの `crates/ tools/ std/` に未コミットの変更が無く、バイナリの mtime が HEAD のコミット時刻より後。
  満たさなければ「基は不明」として今と同じ（全て落とす）に倒す。親の務めは、コミットの後に主のツリーで `cargo build -q -p onsa_cli -p onsa_tests` を一度回すこと（網羅の検査の一部分を回せば同時に満たす）。

**費用**: 新しい型 1 件につきコマンド 1〜2 回（ミリ秒〜数秒）。最小化は今もしている。ビルドは主のツリーで 1 回。

**なぜ本文で見分けるか**: 変異体はコーパスの全体に依存し、事例を足すと他の種の変異体も変わる（leader-rules 4.5、実験の naive filter の 918/2,720 と同じ性質）。「基の回でその型が出たか」では見分けられず、同じ本文を基で回すのが唯一の確かな方法。

**確信**: 高い（leader-rules 2.7 が今は親の手作業でしていることの自動化）。

**副作用**: 基のバイナリが古いと「基は不明」になり雑音が戻る。gate が要約に明示するので気付ける。作業ツリーで担当が種のファイルを変えた場合も、入力の本文は決まるので見分けは成り立つ。

**実装の量**: `tools/fuzz.py` の `run`（新しい型の後処理、約 30 行）と `main`（約 10 行）、`tools/fmt_props.py` の `run`（約 25 行）、`tools/gate.py` の基の妥当性（約 30 行）、自己テスト（二つのバイナリを `--binary` に偽のスクリプトで渡す形が `test_gate.py` の `Fuzz` に既にあるはず。約 60 行）。

## Q5 親が写した後に回し直す条件（GF-2）

**策**: 回し直すかは、写した結果が担当の gate が見たものと同じかで決める。
- 回し直さない: `take.py check` が「そのまま当たる」で、主のツリーの HEAD が担当の基と同じか文書だけ進んでいる（`take.py patch` が出す「基と HEAD で違うファイル」が `docs/` と仕様だけ）、かつ親がパッチの外に何も足していない。
- 速い項目だけ回し直す（約 10〜20 秒、ビルド無し）: 親が登録で `docs/` の表・`tests/pending.toml`・`tools/builtin_names.toml` を変えたとき → `--only pending ignores gap-marks diag-registry diag-negatives builtin-names spec-examples spec-sections default-inits`。`tests/pending.toml` を dev の版から作り直したとき（leader-rules 3.4）は `cargo test -p onsa_tests` も（事例の器が一覧を読む）。
- 作業の検査を回し直す: 3-way で当てた、主のツリーがコードで進んでいた、親がコードを直した、のどれか。
- 全体の gate は主のツリーで回さない（今は 19 分の大半がこれ）。網羅はQ3 の部分の回で受ける。

**確信**: 高い。

**副作用**: 「そのまま当たる」でも、担当が最後の直しの後に gate を回し直していないと、報告の要約が最終の差分のものでない。作業票で「報告の要約は最後の WIP のコミットの差分で」と明記し、親は `take.py patch` の行数と報告の行数を突き合わせる（leader-rules 4.3 の確かめで兼ねられる）。

**実装の量**: 道具の変更は `--only` だけ（Q3 と共通）。残りは leader-rules 4 章の文。

## Q9 GF-1〜GF-4 への異論、読み違い、リスク、単純な代替

1. **GF-1**: 異論なし。ただし主のツリーの `test` 207 秒は写した後のビルドの冷え込みで、作業ツリーの 46〜98 秒と別物。Q5 で主のツリーの全体の回し直しを止めれば、5 分の基準は作業ツリーの数字で見ればよい。
2. **GF-3 の「基では出ない」の意味**: 「型（class）が基の回で出たか」では見分けられない。変異体は種の全体に依存し（`mutate` の `rng.choice(corpus)`、`tokens`）、種を足すと他の種の変異体が変わる。見分けは**同じ本文を基のバイナリで回す**形に限る（Q4）。GF-3 の文を「基のバイナリが同じ入力で同じ失敗を出すもの」と書き直すことを勧める。
3. **GF-3 の「関わる種」**: 変えた Rust のコードから種を選ぶ対応表（コードの族 → 事例）は持たない。手順 1 の証拠は「fmt のコードの変更 → fmt の性質が当たる」だけで、それは経路の接頭辞の小さな表で足りる（Q1）。それ以上は「まれな形のために複雑さを足さない」に当たる。
4. **GF-4**: 異論なし。`NEW` も含める点を明記する。
5. **手順 1 の読み**: 「fuzz だけ 33 回」には差分の誤り（R-215、R-193、R-205）と前からの形の両方が混じる。A 期の 23 件は新しい網（W3-17）を入れた作業の回で、絞った回では見えなくなるが、「fuzz の道具に触れた作業は全体で回す」の規則（Q1）がこの場合を受け持つ。
6. **見落としやすいリスク**:
   - 基のバイナリが古いままになる（Q4 の妥当性の表示で見える。表示が無いと雑音が静かに戻る）。
   - 作業 ID を塩にした 1/5 は、同じ作業の長い往復で同じ種しか見ないので、往復の中で広がった誤りは網羅の検査まで見えない。受け入れる。
   - 網羅の部分の回が錠を 5 分持つ間、担当の gate が待つ。担当の `cacheTtl` は impl だけ 1 時間なので impl の待ちは費用に効きにくいが、break の掃引と重なると break のキャッシュが切れる（手順 1 §5）。部分の回は担当に票を渡した直後に始める。
   - `fix-loop` を作業の検査から外すと、修正候補の収束の後退が網羅の回まで見えない。info の項目なので今も判定には効いていない。
7. **もっと単純な代替**（道具を変えない）: 担当は報告の前に `--quick` + `fmt-cst`（約 2 分）、親はコミットの後に `bg.py` で全体の gate を裏で回し、gap-marks の FAIL は読み飛ばす。
   時間の利益の大半（515 秒 → 約 120 秒）はこれで得られるが、(a) fuzz の 33 回・fmt の性質の 7 回の「止まる」費用（R の登録、許可の一覧、回し直し）は残り、(b) fmt の作業で当たっていた fmt-props の網を失い、(c) 前からの形の見分けは親の手作業のまま。
   私は U1・U2 を勧めるが、工数を先に抑えたいなら、この代替で始めて U1（見分け）だけ足す順も成り立つ。

## 全体の形（まとめ）

- 作業の検査 = `tools/gate.sh --work ID`（作業ツリー）: 速い項目の全部 + 絞った fuzz・fmt の 3 項目（差分の種 + 作業 ID で決まる 1/5 + 保存した入力の全部）+ 差分が触れた道具・fmt の項目は全体 + `tools/` に触れたら gate-selftest。基のバイナリで見分け、前からの形は NOTE、`PARENT` は落とさない。約 3〜5 分。
- 網羅の検査 = `tools/gate.sh --only …` の部分を親がコミットごとに一つ裏で回し、`--stage-end` で全体。`last.json` で各項目の全体の最後の PASS を見せる。
- 主のツリーでの回し直しは、写し方と親の編集の範囲で決め、全体の gate は回さない。
