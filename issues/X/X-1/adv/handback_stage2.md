## 2. 割れた点（どちらを選ぶと何が変わるか）

### 2.1 M-1 「コードの差分に出る診断コードを期待値に持つ事例」を種に足す

- 第 1 段: コード → 種の対応表は持たない（複雑さ）。親: 診断コードで選ぶ。
- 確かめた事実: `onsa_cases` の一覧の JSON（`path, kind, name, mode, spec, golden, files[].syntax_errors`）に期待する診断コードは無い。
  実現は (a) 一覧の JSON に `codes` の欄を足す（Rust 約 10 行。器のマーカの読みを使うので D-15 に沿う）か、(b) 差分の `E\d{4}` を `tests/**/*.onsa` の本文に grep する（Python 約 10 行。コメントの言及も拾うが、種を増やす向きの過剰なので無害）。
- 判断: 親の案を採ってよい。(b) なら実装の量はほぼ増えず、差分の種を数十件足すだけ。効くのは「診断の文面・候補を変える作業」（W3 の大半）で、そこに R-215 型の誤りが入る。ただし、差分に診断コードが多いとき（登録簿の整理など）は数百件に膨らむので、上限（例 200 件、超えたら抜き取りに落とす）を一つ置く。
- 選ぶと変わること: 採らなければ実装が 10 行減り、診断の作業の差分の誤りは抜き取りに当たらない限り網羅の検査まで遅れる。

### 2.2 抜き取りの割合（親 1 割、第 1 段 1/5）と fmt の `tests/spec/fmt` 全部

- 差: 1 割なら fuzz 約 1,400 変異体、1/5 なら約 2,800。時間差は約 10〜15 秒。
- 判断: 親の 1 割 + 差分の種 + `tests/spec/fmt` 50 件（数えた: 50）でよい。理由は時間の基準より、「網羅は網羅の検査が持つ」と決めた以上、作業の検査の抜き取りは差分の近くの誤りを拾う補助であること。割合は `gate_steps.py` の一か所の定数にし、M-8 の警告を見て動かす。

### 2.3 M-2 の分け方（親: 種を K 分の 1 ずつ全項目、第 1 段: 項目ごとに `--only`）

- 親の形の利点: 1 回の時間が均一で、各回に fuzz と fmt の両方が入る。第 1 段の形の利点: 新しい道具の形（`--sweep` の控え）が要らず `--only` だけで済む。
- 判断: 親の K 分割を採る。ただし二点を足す。
  1. **gate-selftest と保存した入力の再生は半分にならない。** 時間の見積もり「約 10 分 → K=2 で 5 分」は、(219 + 338) / 2 + 62 ≈ 340 秒 + ビルドと `onsa_cases` の一覧の固定費で、約 6 分。10 分の基準の内なので問題はないが、K=2 で「約 5 分」は少し甘い。
  2. **速い項目（表の検査）を網羅の検査にも入れる。** 親の表では速い項目が網羅の検査の列で「—」。M-4 で「そのまま当たるなら回し直さない」とすると、親が写した後に行う登録（`docs/` の表、`tests/pending.toml`、`builtin_names.toml`）の誤りは、どの検査も見ないままコミットされる。
     静的な項目（pending、ignores、gap-marks、diag-registry、diag-negatives、builtin-names、spec-examples、spec-sections、default-inits）はビルド無しで 10〜20 秒なので、`--sweep` に常に含める。
     加えて親は登録の後に `--only` でこの組を回す（M-4 に一行足す。`tests/pending.toml` を dev の版から作り直したときは `cargo test -p onsa_tests` も）。
- 選ぶと変わること: 足さなければ、登録の誤りは段の終わりの `--stage-end` まで見えない。

### 2.4 M-3 の「前から」の扱いの範囲

- 親: 同じ類が基でも出れば判定を落とさない。第 1 段: 内部エラー・異常終了・時間切れは前からあっても落とす。
- 根拠: 手順 2 の GF-3 の文（「内部エラー・異常終了（前からあっても直す。leader-rules 4.5 のまま）」）と leader-rules 4.5（許可の一覧に載せられない）。M-3 の文はこの区別を書いていないので、「落とさないのは fix の約束の違反の類だけ。署名が `signal …` か内部エラー（101）のものは前からでも落とす」と明記する。
- 選ぶと変わること: 区別しないと、担当の作業ツリーで前からの内部エラーが見えても通り、直す票が立たない（網羅の検査では今も落ちるので最終的には見えるが、「前から」の印で親が仕分けを後回しにしやすい）。
- もう一点: **基が無いときの倒れ方**を書く。基のバイナリ（`target/base/<merge-base>/`）が無ければ「基は不明」として今のとおり全て落とす（安全側）。要約にその旨を出す。

### 2.5 M-3 の fmt の性質に見分けを入れない

- 第 1 段は入れたが、親の理由（W3 の実績では fmt の性質の失敗は全て作業の差分）は手順 1 §4 のとおりで、「まれな形のために複雑さを足さない」に沿う。**親の案に従う。** 差分で事例を足したために前からの fmt の誤りが見える形は起こりうるが、担当が dev のバイナリで手で確かめて報告する今の手順（leader-rules 2.7）で足りる。

### 2.6 M-3 の基の置き場所

- 第 1 段は主のツリーの `target/debug/` に妥当性の確かめを付ける案、親は `target/base/<コミット>/` に写す案。**親の案が良い**（コミットごとに決まる、数個残せば dev を途中で取り込んだ担当の基にも当たる、M-2 の「入ったコミットまで絞る」に使える）。
- 足すこと: 文書だけのコミットの後も写す（`cargo build` は差分が無ければ数秒。写さないと次の担当の merge-base に基が無い）。あるいは道具が `git log` で最も近い祖先の基を探す（約 10 行）。どちらかを決める。前者が単純。

### 2.7 M-8 の「絞った作業の検査では time-budget も小さくする」

- 異論。`--time-budget` は切れると項目を**落とす**（「言った数より少ない入力では通さない」）。小さくすると、他の担当のビルドと重なった遅い回が FAIL になり、M-8 自身が「1 回だけの警告では動かない」と言う雑音を判定に持ち込む。
- 代わり: 上限は今の値（fuzz 600 秒、fmt 300 秒）のまま残し、伸びの検知は M-8 の警告だけに任せる。上限を変えるのは、全体の回で上限に近づいたときだけ。
- 選ぶと変わること: 親の案だと遅い回が FAIL で止まり回し直しが要る。私の案だと止まらず、警告の行が報告に残る。

### 2.8 単位の分け方

- 親: U1 = M-1・2・6・7・8（選び方 + gate + 警告）、U2 = M-3・5。見積もりの表で U1 を足すと、共通の部分 40〜60 + fuzz の大半 + fmt 30〜50 + gate 85〜140 で約 230〜330 行、U2 は約 60〜90 行。U1 が §8.5 の目安 300 行の上端に乗り、U2 が小さすぎる。
- 代わり（第 1 段の Q8）: U1 = 道具の側（共通の部分、`fuzz.py` の選び方と M-3 の見分け、`fmt_props.py`。約 150〜230 行）、U2 = gate の側（`--sweep`、`--only`、selftest の条件、M-8、gap-marks。約 120〜180 行）。M-3 の見分けは `fuzz.py` の `run` に書くものなので U1 に置く方が、同じファイルを二つの単位で触らずに済む。
- 選ぶと変わること: 単位の均し方だけで、総量は変わらない。同じ担当が続けて受けるなら差は小さい。

## 3. 見積もりと「確かめていないこと」への指摘

- **M-1 の時間**（fuzz 80 → 20〜30 秒、fmt の 3 項目 300 → 40 秒）: 線形の前提では妥当。ただし fmt の 3 項目はそれぞれ `onsa_cases` の一覧の取得（`cargo run -q … onsa_cases`）と `cargo build` の確かめを払うので、固定費が 3 回乗る。測っていないが各数秒〜10 秒。
  「約 40 秒」は固定費を含めると 50〜70 秒になりうる。全体の見込み 150〜200 秒は、この分を入れても 5 分の内。
- **M-2 の時間**: 2.3 の 1 のとおり約 6 分（selftest と再生は半分にならない）。
- **「作業ツリーから主の `target/base/` を読めるか」**: 読める。作業ツリーは `.claude/worktrees/` の下、つまり主のツリーの中にあり、経路は `git rev-parse --path-format=absolute --git-common-dir` の親ディレクトリ + `target/base/`（gate の `lock_path` が既に同じ手で共通の `.git` を見つけている）。作業票で経路を渡す必要は無い。
- **主のツリーの test 370 秒の内訳**: 分からない 250 秒の見当（推測、未確認）: `cargo test --workspace` は dev プロファイルの `cargo build`（fuzz が使う）と別にテストの標的（各クレートの tests と dev-dependencies、doctest の個別のコンパイル）をビルドする。
  親がパッチを当てた直後の主のツリーは、作業ツリーで既に温まっていたテストの標的を全てビルドし直す。worktree の 40〜100 秒との差はこれで説明がつくが、U1 で測る方針には賛成。測るなら `cargo test --workspace --no-run` の時間と、その後の実行の時間を分ける。
- **break の `cacheTtl`**: ここで扱わないのは妥当。ただし手順 1 §5 の「16/22 回切れた」の原因が掃引か錠待ちかを確かめていないので、別の項目にするなら先に原因を一つ見る。

## 4. M-8 の評価（利用者の案）

- 賛成。判定を落とさず、要約の末尾の `gate:` の行の直前に出す形も、担当が末尾だけ読む実態に合う。目安の値を `gate_steps.py` の一か所に置く点も D-15 に沿う。

## 5. 結論

- 親の案は第 1 段と大筋で一致し、M-3 の置き場所（`target/base/<コミット>/`）と M-5 の検出（作業ツリーの判定）は第 1 段より良い。
