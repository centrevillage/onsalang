## M-1 差分に関わる種と抜き取り

- 差分に関わる種:
  - 作業が足した・変えた事例の源。テストの担当が作業の規則について書いた事例なので、変えた規則の族の代わりになる。
  - コードの差分に出る診断コード（`E0013` など）を期待値に持つ事例。差分の `E\d{4}` を事例の本文で探す（事例の一覧の JSON には期待するコードの欄が無い。コメントの言及も拾うが、種が増える側なので害は無い）。数百件に膨らむ差分（登録簿の整理など）に備え、上限（例: 200 件。超えたら抜き取りに回す）を置く。
    U7（X1-4、2026-10-18、暫定）で、超えたコードの種からも上限までハッシュで取り、残りを抜き取りに回す形に変える（`X-1.md` の「決めたこと（残りの候補）」）。
  - fmt の性質では `tests/spec/fmt` の全て（50 件、全体の約 5%）。
- 抜き取り: 残りから決まった割合（例: 1 割）を、ディレクトリごとに選ぶ（どのディレクトリからも最低 1 件）。経路と作業 ID のハッシュで選ぶので、同じ作業の回し直しは同じ選び方になり、作業が変われば選び方も変わる（作業を重ねると広く回る）。
- 変異体は今と同じものにする。語の集め先と行の差し込み元は今のまま全体を使い、絞るのは「どの種の変異体を回すか」だけにする。修正候補の段に回す変異体は今は回の中の通し番号の 4 の倍数で選んでいるので、絞った回でも全体の回での番号（種の番号 × 1 種あたりの数 + k）で選ぶ。こうすると、絞った回は全体の回の部分集合になり、同じ入力は同じ結果になる。
  全体の回の選び方は変わらないので、変えた後に前からの類がまとめて出ることも無い（advisor の第 1 段の案。advisor の実験で、種の 1/5 の 2,720 変異体が全て全体の回の変異体と一致した。種の一覧を先に絞ると 918 件しか一致しないので、実装はこの順を守る）。
- 抜き取りの割合は `gate_steps.py` の一か所の定数にし、M-8 の警告を見て動かす。
- 見積もり: fuzz の種 1,422 件のうち、差分の種（数十件）と抜き取り（約 140 件）なので、今の 1 割強になる。担当の作業ツリーで fuzz は 80 秒から 10〜15 秒に、保存した入力の再生を足しても 20〜30 秒になる。fmt の性質の 3 項目は合わせて約 300 秒から約 40 秒になるが、3 項目それぞれが事例の一覧の取得とビルドの確かめを払うので、固定費を入れると 50〜70 秒。

## M-2 網羅の検査の分け方と回すとき

- 起こし方（この節）と基の保存（M-3）は U4 で変わった（2026-10-18、`x3_method.md`）。
- 種を経路のハッシュで K 個に分け、`--sweep` は次の一つを回す（どこまで回したかを `target/` の下に控える）。K 回のコミットで一巡する。
  今の重い項目の全体は主のツリーで約 10 分（fuzz 219 秒、fmt の性質 338 秒、gate-selftest 62 秒）なので、K = 2。gate-selftest と保存した入力の再生は分けても減らないので、1 回は約 6 分（(219 + 338) / 2 + 62 秒と固定費）。事例が増えたら、1 回が 10 分以内に収まるよう K を増やす（GF-1）。
- 静的な項目（pending、ignores、gap-marks、diag-registry、diag-negatives、builtin-names、spec-examples、spec-sections、default-inits。ビルド無しで 10〜20 秒）は、毎回の網羅の検査に入れる。親が写した後の登録の誤りを拾うため（M-4）。
- 回すとき: 親が作業をコミットした直後に、`tools/bg.py` で `nice` を付けて起こす。gate の錠を取るので、担当の gate は最大で 1 回分（約 5 分）待つ。
- 変更を定期的に見張る仕組みは置かない。コミットは全て親が行うので、コミットを合図にすれば足りる。
- 結果: 新しい類が見つかっても作業は止めない。親が区切りで読み、leader-rules 4.5 の形で仕分ける（R、許可の一覧、実装待ち）。
- どの作業で入ったかは、M-3 で控えたバイナリで見つかった入力を回せば、入ったコミットまで絞れる。

## M-3 前からある誤りの見分け（GF-3）

- 親が全てのコミット（文書だけのコミットも）の後に、dev のバイナリ（`onsa` と `onsa_cases`）を主のツリーの `target/base/<コミット>/` に控え、最後の数個を残す。網羅の検査がビルドするので、写すだけで済む（差分が無ければビルドは数秒）。担当の作業ツリーは主のツリーの中にあるので、道具は `git rev-parse --git-common-dir` から主のツリーを見つける（gate の錠と同じ手。作業票で経路を渡す必要は無い）。
- 作業の検査のファズが新しい類を見つけたら、最小化した入力を基（merge-base のコミット）のバイナリでも回す。
  - 修正候補の約束の違反の類で、基でも同じ類が出れば「前から」として要約に並べ、判定は落とさない。基で出なければ、差分で入った誤りとして落とす。
  - 内部エラー・異常終了・時間切れは、前からあっても落とす（GF-3、leader-rules 4.5 のまま）。
  - 基のバイナリが無ければ「基は不明」と要約に出し、今のとおり全て落とす。
- 基は U6・U6b（2026-10-18）で広がった: 全体の回と shard で、merge base が HEAD でコードに変更の無いとき（主のツリーの網羅の検査と全体の回）は、コードが HEAD と違う最も近い祖先の基（「the code before HEAD」）と比べる。絞った回は、コードに変更が無くても merge base 自身の基（上のとおり）。未追跡のコードのファイルもコードの変更に数える（`X-1.md` の「実装」）。
- 費用: 新しい類が出たときだけ、入力一つを回す数秒。
- fmt の性質には今は入れない。W3 の実績では、落ちたときはその作業の誤りだった。

## M-4 親の回し直し（GF-2）

- 規則の文だけを変え、道具は変えない。パッチの基が主のツリーの HEAD と同じで（`take.py patch` が表示する）、当て方が「そのまま」なら、追跡しているファイルの中身は担当の作業ツリーと同じになる。そのときは作業の検査を回し直さず、担当の要約を使う。
- 3-way で当てたときと、基の後に dev が進んだときは、今のまま回す。
- 親が写した後に登録（`docs/` の表、`tests/pending.toml`、`tools/builtin_names.toml`）を変えたら、静的な項目を `--only` で回す（10〜20 秒）。`tests/pending.toml` を dev の版から作り直したとき（leader-rules 3.4）は `cargo test -p onsa_tests` も回す。
- 網羅の検査（M-2）はどちらでも回す。

## M-5 担当に直せない項目（GF-4）

- `tools/gap_marks.py`: 「表に無い番号」と `NEW` は、担当の作業ツリー（`git rev-parse --git-dir` が `--git-common-dir` と違う）では親の処理待ち（状態の名前は `PARENT`。gate の `info` とは別の意味なので別の名前にする）として並べ、判定を落とさない。主のツリーでは今のまま FAIL にする（親がコミットの前に登録する）。
- 印の形の誤り（malformed）は担当が直せるので、どこでも FAIL にする。

## M-6 gate-selftest

- 作業の検査では、差分が `tools/` に触れるときだけ回す。網羅の検査では毎回回す。40〜60 秒減る。

## M-7 落ちた後の回し直し

- gate に `--only <項目,…>` を足す。直しの往復では、落ちた項目だけを同じ選び方で回し直す（agent-rules 4 章の「直すたびには回さない」と合わせる）。

## M-8 時間の基準を超えたときの警告（利用者の案、2026-10-16）

- gate の要約で、検査の全体の時間が GF-1 の目安（作業の検査 5 分、網羅の検査の 1 回 10 分）を超えたら、警告の行を出す。行には、超えた時間と、時間の大きい項目の上位 3 つを並べる。判定は落とさない。時間は錠を待った時間を除いた項目の秒の和にする（他の gate の後ろで待っただけで警告が出ないように）。
- 警告の行は、最後の `gate: PASS / FAIL` の行のすぐ前に置く。担当は要約の末尾だけを読むことが多い（手順 1）ため。
- 目安の値は一か所（`gate_steps.py`）に置く。
- 今ある上限（fuzz の `--time-budget` 600 秒、fmt_props の 300 秒）は、走り続けるのを止める上限として今の値のまま残す。警告は伸びを早く知るためのもので、役割が違う。上限は切れると項目を落とすので、絞った回で小さくすると、他のビルドと重なった遅い回が FAIL になる（advisor の指摘で、親の初めの案から外した）。
- 担当は警告を報告に書き、親は区切りで読む。続けて出たら、K を増やすか絞り方を見直す。1 回だけの警告は、他の担当のビルドと重なったせいのこともあるので、それだけでは動かない。
- 履歴: 主のツリーの gate（網羅の検査と親の確かめ）1 回につき、`target/gate/history.jsonl` に 1 行（コミット、形: work / sweep k/K / stage-end、項目ごとの秒と状態、絞った種の数）を足す。
  この一つのファイルから、(a) 時間の伸び、(b) M-2 の「どこまで回したか」、(c) 各項目が全体で最後に通ったコミットが出る（advisor の案で M-2 の控えと一つにした）。要約に「sweep: 次は 2/2。fuzz の全体の最後の PASS: 628f8ec（3 コミット前）」のような一行を足し、網羅の検査の抜けが見えるようにする。
  担当の作業ツリーの履歴は作業ツリーと一緒に消えるので、担当の分は報告の要約で足りる。
- 量: `gate.py` の要約に 15〜25 行、履歴に 10〜15 行、自己テストに 20 行ほど。U1 に入れる。
