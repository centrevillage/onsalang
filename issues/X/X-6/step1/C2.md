## 2. 項目ごとの修正方針

### C2-1 `emit.rs` を役割で分ける（保つ）

- 分ける理由（`rules/refactoring.md` 8.1）: 一つのファイルに、単位の組み立て（何を出すか・名前・順）、型と定数の定義（関数の文脈なし）、関数の本体の翻訳（`FnEmitter`）の三つの層がある。
  `export.rs` は C の字句（`c_string`・`f32_lit`）のためだけに `emit` を引き、`emit_unit` は `export` を呼ぶので、依存が相互になっている。字句を下に置けば `export` → `emit` の向きが `Cx` だけになる。
- 分け方（新しいモジュールと移す関数）は 3 章の C2-1 に書く。`lib.rs` の `emit::emit_unit`・`emit::export_roots` の呼び出しは、`emit/mod.rs` の再公開で変えない。
- `FnEmitter` の構造体と補助（`line`・`open`・`close`・`temp`・`place` など）は `emit/func/mod.rs` に置き、`stmt.rs`・`expr.rs`・`prim.rs` をその子にする。子は親の非公開のフィールドを読めるので、フィールドの公開は変えない。子の間で呼ぶメソッド（`expr` と `block_into`・`switch_into` など）に `pub(super)` を付ける。
- 関数の中身は変えない（`emit_unit` 359 行・`expr` 258 行・`prim` 177 行・`type_def` 110 行は、そのまま移す。関数を割るのは 6 章の候補）。
- 確かめ（C の出力が変わらないこと）: `cargo test -p onsa_backend_c`（`c_string` などの単体テスト）、golden の C（`tests/golden/c/` の 10 ファイル。`onsa_cases --run` が比べる）、`onsa_cases --c <全ての項目>`、`onsa_cases --vectors c`、`gate.sh --work`。
  加えて、基のバイナリ（`target/base/<基>/onsa`）と新しいバイナリで、ターゲットを持つ 8 つのパッケージ（`examples/voice_host`、`tests/vectors/fixture/*` など。`find tests examples -name onsa.toml` で `[targets.*]` を持つもの）に `onsa build --target <t> --out <別の所>` を回し、`.c`・`.h` が 1 バイトも違わないことを `diff -r` で見る（文字列を組む順を変えないので、差は 0 の見込み）。
  `compare.py diags` は差 0 件の見込みだが、確かめにはならない（`onsa check` はこの crate を通らない。`crates/onsa_cli/src/main.rs` の `check` は解析だけで、`lowered` を呼ぶのは `dump`・`test`・`interface`・`build`）。

### C2-2 `onsa_interp/src/lib.rs` を役割で分ける（保つ）

- 分ける理由: 参照の意味（spec §3.3・§3.4 の数の規則）を読みたい人が、木の歩き方（場所・文・式）と同じファイルの 1209〜1362 行と 1632〜1875 行に分かれた数の関数を探すことになる。
  `std` の `target fn` のうちインタプリタが自分で動かすものの知識（`StdPrim`・`std_prim`・`unsupported`・`Interp::std_prim`・`assert_near`）が 2 か所に離れている。一つのモジュールに置けば、関数を足すときに触る所が一つになる。
- 分け方は 3 章の C2-2 に書く。`lib.rs` には公開の型（`Panic`・`CallSite`・`Unsupported`・`Failure`）、`Interp` の構造体と公開の入口（`new`・`fn_by_name`・`call`・`call_inout`・`const_value`）、`MAX_CALL_DEPTH` とその測定の表、`variant_names`・`new_slot` を残す。公開の経路（`onsa_interp::unsupported` など）は再公開で変えない。
- `#[inline(never)]`・`#[inline(always)]` の属性は関数と一緒に移す（R-05 で呼び出しの枠を小さく保つためのもの。`lib.rs` 136・415・426・461・470・526・542・549・830 行）。
- 〔危険〕の中身: 関数を別のモジュールへ移すと、コード生成の単位（CGU）の分け方が変わり、小さな補助（`bool_of`・`int_of` など）のインライン化が変わりうる。すると 1 呼び出し・1 段の入れ子のスタックの量と速さが変わりうる（`onsa_interp` は dev でも `opt-level = 1`、`Cargo.toml` 33〜43 行）。
- 確かめ: `cargo test -p onsa_interp`（`the_limit_comes_before_the_net_under_256_levels` を含む）と、`measure_the_stack_of_calls_and_levels` が出す値を debug と `--release` の両方で、`MAX_CALL_DEPTH` の説明の表（debug 1.0 K・0.3 K・0.7 K・0.8 K、release 0.7 K・0.3 K・0.7 K・0.7〜0.8 K）と並べる。
  値の比較: `onsa_cases --vectors interp`、`onsa_cases --run`（`tests/spec` の `test` の事例）、基と新しいバイナリの `onsa test --json` を同じ入力に回した出力の一致、`gate.sh --work`。
  速さ: `compare.py speed` は `check` と `fmt --check` しか測らないので、インタプリタの速さは測れない。`onsa test` を重い入力（テストベクトルの事例）に基と交互に回して並べる（6 章の道具の案）。

### C2-3 `lower/body.rs` を役割で分ける（保つ）

- 分ける理由: 文と式の降下、パターンの判定木（`pat_test`・`pat_bind`・`lower_match`）、呼び出しと組み込みのメソッドの表（`lower_builtin_method`・`lower_seq_method`・`lower_enum_method`、`target fn` の `lower_target_call`）は、変えるきっかけが違う（パターンは仕様の §8 系、メソッドの表は `std` の関数を足すとき）。
- 分け方は 3 章の C2-3 に書く。`body/mod.rs` が `lower_expr`・`bind_params`・`lower_fn_body`・`FnCx`・`coerce`・`bind_irrefutable`・`materialize` などを再公開し、`lower/mod.rs` と `lower/flow.rs` の `use` は（C2-5 で移す組み立ての関数を除いて）変えない。
- 自由関数だけなので、移すときに変えるのは `use` と `pub(super)` だけ。関数の中身（`lower_expr_at` 157 行、`lower_match` 121 行）は変えない。
- 確かめ（Core が変わらないこと）: 基と新しいバイナリで `onsa dump --core <ファイル>` を回し、出力が 1 バイトも違わないこと。入力は golden の core の写し（9 個）を宣言する事例（`tests/golden/core/` の 3 つの `.onsa` と、`tests/spec/examples/voice.onsa` など `tests/spec` の事例。今のバイナリで `onsa dump --core tests/golden/core/echo.onsa` の出力が `echo.core` と一致することを確かめた）、`tests/spec` の誤りの無い単一ファイルの事例、`std`、`examples`。
  `tests/review-phase1/` と `tests/fuzz/` は除く（`rules/common.md` 3.2）。加えて `cargo test -p onsa_core`、golden の `core`・`interface`、`onsa_cases --c`、`--vectors interp`・`--vectors c`、`gate.sh --work`。

### C2-4 `lower/flow.rs` を役割で分ける（保つ）

- 分ける理由: 一つのファイルに、State の形を決める解析（読む率の歩き `ReadWalk`、節の欄 `node_fields`）、生成する関数の組み立ての道具（`Gen`）、相の関数（init・reset・ctl・tick）、式の中の状態つきの節の値（`lower_flow_expr`・`vdelay_read`、本体の降下から呼ばれる）、境界の関数（process・render・params_default）がある。
  `lower_flow_expr` は `body.rs` から呼ばれる入口で、相の関数とは呼ぶ向きが逆である。
- 分け方は 3 章の C2-4 に書く。`FlowLowerCx` の非公開のフィールドは `flow/mod.rs` に置き、子のモジュールが読む（公開を変えない）。`crate::lower::flow::{FlowFns, FlowMeta}` の経路は変わらない。
- `lower_flow`（181 行）は中身を変えずに `flow/mod.rs` に置く（State の欄を求める 249〜300 行を `state.rs` の関数に出すのは 6 章の候補）。
- `ReadWalk` と `children` は `flow/reads.rs` に単独で置く（RF-8 が書き換える所を一つのファイルに閉じるため。4 章）。
- 確かめ: C2-3 と同じ（`onsa dump --core` の一致、golden の `core`・`interface`・`c`、`cargo test -p onsa_core`、`onsa_cases --c`、`--vectors interp`・`--vectors c`、`gate.sh --work`）。flow を持つ入力（golden の core の `echo`・`voice`・`resonator`・`unison` の事例、`tests/spec` の flow の事例）を必ず含める。

### C2-5 Core の式を組む小さな関数を `lower/build.rs` に集める（保つ）

- 分ける理由: `Expr`・`Stmt`・`Arg` を作るだけの関数が `body.rs` と `flow.rs` に分かれ、`flow.rs` は組み立てのためにも `body` を引いている（55 行の `use super::body::{…, lit, local_expr, stmt, u32_lit, index, field_by_name}`）。降下の全体が使う「Core の部品」を一か所に置くと、`flow` → `body` の依存が本当の依存（`lower_expr`・`coerce`・`bind_irrefutable`・`FnCx`）だけになる。
- 移す関数: 上の表の `body.rs` 93〜169 行と `flow.rs` 596〜641 行（`sfield` から下の flow に固有のもの `member_params`・`init_value`・`sub_inputs`・`instance_args`・`replica_index` は flow に残す）。`materialize` は `FnCx` を受けるが、組み立ての関数なので一緒に移す。
- 名前: `flow.rs` の `binary` は溢れの扱いを常に `Overflow::Checked` にする。共有の場所では名前が役割を表さないので、`checked_binary` に改める（呼ぶ所は `flow.rs` の中だけ。出力は変わらない）。改めないなら説明の 1 行を足す。
- `eq.rs`・`fold.rs`・`body.rs` の中で `ExprKind::Cmp` などを直に組んでいる所（`body.rs` 9 か所、`eq.rs` 9 か所、`fold.rs` 4 か所）を `build` の関数に置き換えるのは、この項目に入れない（6 章）。
- 確かめ: C2-3 と同じ。
