## M4 確かめの進め方

1. 範囲の決定ごとに `python3 tools/docs.py show <S>` を読む（本文と関係）。`path §x.y` で仕様の節を開き、決定の「決定:」の文と節の文を突き合わせる（未反映・矛盾）。
2. `back <S>` で、その決定を指す R・W・他の決定を一段だけ読む。理由の向きが食い違うもの（M1 の 2 の類）と、同じ論点を別の ID で書いているもの（M1 の 1 の類）を候補にする。
3. 重なりの抜き取り: 範囲の決定と同じ節を `spec` に持つ既決の決定を `changes --section §x.y` で挙げ、題と「空白:」の箇条の頭だけを並べて読む（本文の全部は読まない）。同じ論点に見えたときだけ両方を読む。
4. 古い記述: 「今の実装」「今の fmt は」などの現在形の実装の記述は、OPEN の決定と OPEN の R（`list S --status OPEN`、`list R --status OPEN`）だけで見る。DECIDED・DONE は記録なので古くてよい。

6. 規則: 段の間に `rules/`（今は `docs/agent-rules.md`・`leader-rules.md`・計画 §8）が変わっていれば（`git log` の範囲）、変わった番号を他の規則・README・定義から `grep` し、参照の文が意味を保つか読む。

停止の保証: 範囲は票の一覧で固定、各項目を一度ずつ、`back` は一段だけ（二段先へ広げない）。読む仕様は関係する節だけ。文脈が 20 万に近づいたら新しい項目を始めず、残りを「点検しなかったもの」として報告する。計算の量は項目の数に線形（道具の呼び出しは各 1 回の走査、DT-2）。

## M9 リスク、異論、もっと単純な代替

**リスク**:
- 「事実を変えない」の判定を担当が広く読む（言い換えの写しを ID の参照にして細部を落とす）。手当て: 5.5 の「字面が同じか記号の差だけ」と、親の差分のレビュー。
- 点検の収穫が少ない。手当て: W4 の終わりの票で見つけた件数と費用を数え、空振りなら時機を「構造の変更のときだけ」に落とす（規則に書かず、票の運用で）。
- 役が増える費用（定義、規則の章、枠の数え方）は一度きりだが、「5 つ」のような直書きが残ると古くなる。上の M8 で数を書かない形にした。
- 移行で主のツリーを docs が占める間、他の担当を動かせない（DS-9 の前提どおり。移行は一度きり）。

**利用者の観点への異論**:
- 「構造が保たれているかの検証」は道具（`check`）の仕事で、担当の主な仕事にしない。担当の点検は差分の近所の意味だけに絞る（全体を毎回は見ない）。
- 「矛盾・重複」の第一の網は担当でなく、登録と決定の瞬間の親と gap（既にある規則 `leader-rules.md` 5.6、DF-4）。構造と道具で親の読み飛ばしの主因（探せない）が減る見込みなので、担当は後からの二つ目の網。
- 「移行は管理の担当が作業」は賛成。ただし振り分け（持ち越し → R/RF/X/W、✅ と `status`）の判断は親で、担当は一覧と案を出して当てる。

**もっと単純な代替: 担当を置かない**
- 点検は advisor に「文書の点検」の票として頼む（読んで報告。定義に一行足すだけ）。事実を変えない直しは、親が `set`・Edit で当てるか、件数が多ければ impl に「直す一覧」の票を出す。移行の道具と実行は impl（Python の道具を書く役として既にある）。
- 変わること: 新しい定義と規則の節が要らない。代わりに、点検の直しが親の文脈に戻る（W3 で親の文脈の 43% が文書だった原因の一部）、移行の各段が「advisor の一覧 → impl の実行」と担当二つになりうる、advisor の役（判断する）と点検（並べる）が一つの定義に混ざる。
- 私の見立て: 移行の 7 段と段ごとの点検という具体の仕事が見えているので、狭い役を置く方が親の文脈を守れる。差は大きくないので、利用者が役を増やしたくなければ代替でも成り立つ（確信 中）。

**費用の見当のまとめ**: 点検 1 票 10〜15 万トークン（段ごと）、移行 1 段 20〜40 万（7 段、一度きり）。同時に動かす枠は 4 体に数え、点検は段の終わり（W の票が無い時）なので枠を奪わない。
