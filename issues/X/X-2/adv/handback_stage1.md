## Q9 移行の制約と順

**制約**: (1) ID と `§x.y` は変えない。(2) 各段の終わりで gate が通る（道具を先に直す）。(3) 担当が動いていない区切りで行う（経路が足元で変わる）。(4) 元の表から新しいファイルを作る段は、再生成して元と diff する往復の確かめを付ける。
(5) コードの参照（`docs/onsa-tools.md` 197、計画 13、規則 7、rework 5、API 4、レビュー 3）はスクリプトで一括置換し、同じコミットに入れる。(6) 規則の移動は文を変えず、利用者の了承を先に取る。

**順**（小さく、効き目の大きい順）:
1. `repo.py` に経路の抽象（仕様の一覧、ID → 経路、ファイルの欄の読み）を足す。まだ何も動かさない。
2. 規則の分割（Q8）。読む量が最も確実に減り、文書の依存が少ない。
3. 仕様の章の分割と `tools.md` の移動（Q4）。機械的。
4. 決定の切り出し（Q2）と gate の読み先の切り替え。往復の確かめ。
5. 作業の切り出しと持ち越しの解体（Q3）。
6. 履歴の移動と索引（Q5・Q6）。派生の表（変更点 §4、rework §3 の表）は、gate が新しい正本を読むようになってから消す。
7. 規則の文の見直し（`agent-rules.md` 1 章の「小刻みに読まない」の注は整理の後に見直すと書いてある）と、`leader-rules.md` 6.2「揃えて更新する文書」の書き換え。

**手順 3〜6 との境**: 構造（手順 2）が決めるのは、ディレクトリ、ID と経路の規約、ファイルに要る欄の名前（状態、仕様の節、担う作業、改めた鎖）、生成物をコミットしないこと。欄の書き方と本文の形は手順 3。道具の名前と引数は手順 4（ただし「ID と § を指して読む」「一覧は道具が出す」は構造の前提）。手順 5 の管理の担当は、Q6 の機械の確かめで残る「意味の重複」だけを見る役になり、必要かは移行後に判断すればよい。手順 6 は上の順そのもの。

## Q10 異論・読み違い・リスク・単純な代替

- **「issue ごとに起票」への異論は無いが、ID の体系を一つにはしない**。S（決定）と W（作業）は寿命が違い、R は両方の性質を持つ。番号を付け直すと、コミットの題・`SPEC-GAP(S-…)`・ignore の理由・`pending.toml` と切れる。
- **「概要と詳細に分け、各詳細ごとに別ドキュメント」への異論**: 規範の文を書き直して概要と詳細に再構成するのは、構造の整理でなく仕様の改版で、今の 0.3 の § 参照の量（約 8,400）から見て、この回に混ぜると危険。章のファイルと索引で「概要（README）と詳細（章）」の形は得られる。
- **手順 1 の読み方の注意**: 「複数の文書をまとめて grep」の一部は、重複を探しているのでなく「この ID がどこで使われているか」（逆引き）を探している。ID ごとのファイルは正引きを無くすが、逆引きは残る（`grep -rl S-537` で足りる。道具にするなら手順 4）。また仕様の読み（7.11M、最大）は test・gap・advisor の役割の性質で、構造では減らず、索引と節の道具で「探す読み」を減らすのが限度。
- **見落としやすいリスク**: (a) 移行の途中で親の記憶・scratchpad の票が旧経路を指す。(b) 旧ファイルを `history/` に「凍結した写し」として残すと、それ自体が重複になる（git にあるので残さない）。(c) ファイル数 800 超で、`ls` を Read の代わりに使う担当が出る（README と一覧の道具が無いと grep が増える）。
  (d) `leader-rules.md` 6.2 の「揃えて更新する文書」の手順を同時に書き換えないと、親が旧い手順で派生の表を作り直す。
- **もっと単純な代替**: ファイルを動かさず、(1) `id.py show/set` で ID の行を読み書きし、(2) 目次の道具を足し、(3) 規則だけ分ける、という案。手順 1 の費用のうち grep と置換の大部分はこれでも減る。動かす案との差は、Edit ツールが使えること、並行の編集の衝突、履歴と日々のものの分離、決定の重複の欄が構造的に無くなること。この四つを取るなら動かす。
  費用だけなら代替で十分で、この点は利用者の判断に委ねる（私は動かす方を推すが、理由は上の四つで、費用ではない）。
- **決めなくてよいこと**: ディレクトリの名前、`docs/` の下に置くかトップレベルか、履歴の名前。どれでも構造は同じ。
