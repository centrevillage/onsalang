## 0. 考え方

- **機械が読む欄と本文を分ける**: 道具と gate が読む欄（状態、関係する ID、仕様の節）はファイルの頭の決まった場所に置き、本文は今の書き方（「- 論点:」のようなラベル付きの箇条）のままにする。
- **欄は使うものだけ**: 頭の欄は、道具の一覧・逆引き・gate の確かめのどれかが使うものに限る。人が読むだけの事実と、他の欄から道具が出せる値は欄にしない。
- **関係は一方にだけ書く**: 二つのファイルの関係（決定と担う作業など）は一方にだけ書き、逆向きは道具が出す（DS-2 の「担う作業は決定の側だけ」を広げる）。
  例外は「改めた・改められた」で、両側に書いて gate が対称を確かめる（DF-4。前の決定のファイルだけを開いた読み手が、道具なしで後の決定に気付くため）。
- **本文は移すだけ**: 今の文書の本文は形を変えずに移せる形にする（DS-9 の往復の確かめが効くように）。

## DF-1 共通の形（ID ごとのファイル）

```markdown
+++
status = "DECIDED"
spec = ["§3.1", "§2.5"]
tasks = ["W3-13"]
decided = 2026-10-15
+++
# S-537 ブロックに似た式が演算子の被演算子になるときの読み

- 空白: …
- 決定: …
```

- **頭の欄は TOML**（`+++` の行で囲む。Hugo・Zola と同じ区切り）。道具は Python の標準の `tomllib` で読める（YAML は標準のライブラリに無い。今の `tools/` は標準のライブラリだけを使い、`tomllib` を 4 つの道具が既に使っている）。このリポジトリは既にデータを TOML で持っている（`tests/pending.toml`、`tests/fuzz/allowed.toml`、`tools/builtin_names.toml`）。
  - キーは英小文字（TOML の裸のキーは日本語を書けない）。意味は各ディレクトリの README に日本語で書く。
  - 日付は TOML の日付（`2026-10-15`）、ID と節は文字列の配列。
  - 状態は大文字の英語の閉じた値（利用者の例 PLAN / PENDING / DOING / DONE に揃える）。
  - 書き方の約束（README に書く）: 値に `\` を書かない（`"\|"` は `tomllib` が誤りにする。確かめた）、キーを重ねない（誤りになる）、頭の欄の中にコメントを書かない（状態を改める道具が書き直すと消えるため）。
  - 本文の箇条との境が `+++` で明瞭になる。本文も「- 決定:」の箇条なので、頭の欄も箇条にすると、欄と本文のラベルを名前でしか分けられない（DF-10）。
- **見出し**: 一行目の見出しは `# <ID> <題>`。ID はファイル名と一致させる（gate が見る）。ファイル名は ID の綴りのまま（`S-01.md`。0 埋めを足さない）。本文に別の `#` の見出しは使わない。
- **本文**: ラベル付きの箇条（`- 決定:`）。今の D・K・Q・R・空白の資料と同じ書き方。ラベルは種類ごとに決めた一覧から使う（DF-4〜DF-6）。長い本文は 200 字程度で改行する（今の規則）。
- **ID の参照**: 本文でも頭の欄でも、裸の ID（`S-236`）で書く。経路は規約で決まるので（DS-1）、リンクにしない。ID でない文書は `rules/leader.md` 2.6 のようにバッククォートで書く。相対リンクは README だけで使う（DS-6）。
- **仕様の節**: `§6.1` の形のまま。ツールの仕様は `tools.md §3.2`。
- **表**: 短い値のセルだけに使う。数千字のセルの表（今の計画 §2、rework §3）は、ID ごとのファイルにして無くす。
- **日付と発言者**: 規範の文書（`spec/`、`rules/`）には書かない（利用者の 10-12 の方針。費用の目安のように日付が意味を持つものは除く）。
  記録の文書（`decisions/` の経緯、`issues/`、`tasks/`）には書いてよい。決定のファイルでは「決定:」の文に発言者を入れず、「経緯:」に書く。

## DF-2 仕様（`spec/`）

- **章のファイルには頭の欄を置かない**。章のファイル（`spec/02-lexical.md` など）は今の章の文をそのまま持ち、`## 2. 字句` の見出しから始まる。
  道具が章を番号順につなぐと今の一本の仕様と一字も違わない、を保つ（DS-4。移行の往復の確かめにも使う）。
- ファイル名は `<2 桁の章の番号>-<英小文字の短い名>.md`。§ の番号は見出しの中にあり、ファイル名は並べるためだけ。
- `spec/README.md`: 今の H1（`# Onsa 言語仕様 Draft 0.3`）と前書き、§0・§1 の全文、その後に章の一覧の表（§、ファイル、一行の要約）。
- 仕様に決定の ID は書かない（今の仕様と `onsa-tools.md` に S・R・D などの ID は 0 件。確かめた）。理由と経緯は決定のファイル（DS-2）。
- 相互参照は今の「§6.1」の文字のまま。リンクにしない（道具が § から章のファイルを引く）。
- ツールの仕様 `spec/tools.md` も同じ（頭の欄なし、今の文のまま、§ の番号を保つ）。
- 決めないこと: 規範の文の書き方そのもの（今回は本文を書き換えない、DS-4）。

## DF-3 規約（`rules/`）

- **番号付きの規則**: 全ての規則のファイルで、規則を `<章>.<番号>` で番号付けする（今の `leader-rules.md` の 1.1 の形）。他の文書と担当の定義は `rules/common.md` 2.6 のように番号で指す。
  `agent-rules.md` の箇条は番号を持たないので、移すときに親の箇条に番号を振る（子の箇条は番号なし。文は変えない。DS-8）。
- **番号は追記だけ**: 新しい規則は章の末尾に足し、間に入れない。消した規則は番号を残して「（欠番）」と書く（計画 §5 の「欠番:」と同じ）。決定や報告からの番号の参照が古くならない。
- **ファイルの頭**: 頭の欄は置かない。見出しの次の一段落に「誰が、いつ読むか」を書く（例: 「担当の全員が始めに読む」「文書を編集する担当が、編集の前に読む」）。
- **理由と出所**: 規則の理由は今と同じく短く文の中に書き（「…のため」）、出所の決定は文末の括弧に ID で書く（「（Q-11）」）。理由が長くなるものは決定のファイルに置き、規則からは ID で指す。
- 発言者と日付は書かない（DF-1）。手順の主語としての「利用者」（「利用者が了承してから親が書く」）は規範の文なので残す。
- `rules/README.md`: 役割ごとの「始めに読む」ファイルと番号の範囲、「要るときに読む」ファイルと時機の表。担当の定義（利用者が編集する）は、自分の役割の行を指すだけにする（定義に読むファイルの一覧を写さない。規則のファイルが増減しても定義を編集せずに済む）。

## DF-4 決定（`decisions/`）

**頭の欄**（S・D・K・Q・A で共通。使わない欄は書かない）:

| キー | 意味 | 使う道具 |
|---|---|---|
| `status` | OPEN（未決）/ DECIDED / DROPPED（不要になった、取り下げ） | 一覧、gate |
| `spec` | 仕様の節 | gate（§ がある）、逆引き |
| `tasks` | 担う作業（W など。第 2 期は `P2`。`tests/pending.toml` の `until` と同じ語） | 作業ごとの「実現する決定」の一覧、gate |
| `amends` / `amended_by` | この決定が改めた前の決定 / この決定を改めた後の決定（両側に書く） | 逆引き、gate（対称） |
| `found_by` | 見つけた作業の票（`W3-12/t`） | 一覧 |
| `before` | OPEN のとき、決める期限の作業（`W4-02`） | 今の記憶の「空白の後の段」の一覧を道具が出す |
| `group` | 空白の組の番号 | 組ごとの一覧、下書きを並べて開く |
| `decided` | 決めた日 | 変更点の一覧を道具が出す |

- **改めた・改められた**: 改めるときは、後の決定に `amends`、前の決定に `amended_by` を書く。前の決定の `status` は DECIDED のまま（改めた後も前の決定の一部が残ることが多い。S-540 と S-546、S-545 と S-547）。
  一部か全体かは本文の経緯に書く（状態の語を分けない）。gate が両側の対称を確かめる。
- **仮の扱い**（保守的に実装し `SPEC-GAP` の印がある OPEN の S）は状態にしない。印は `tools/gap_marks.py` がコードから集められる。
- **実装済みかは書かない**: 担う作業が全て DONE なら済み、と道具が出す。
  今の S の ✅ は定義が無く、「仕様に反映した」に近い印として使われてきた（S-276 は決定で ✅ なし、W4 以降の段の ✅ が 23〜25 行）。移行で `status` に置き換え、食い違いは移行の道具が挙げる。
- **本文のラベル**:
  - S: `空白`（論点）、`決定`、`補い（<日付>）`（後の補い。今の S-537 の形）、`経緯`（日付、誰が了承したか、下書きと独立のレビューの一致、改めた範囲）。
  - D・K・Q: 今のまま（`論点`、`案`、`決定`、`理由`、`代替`、`費用`、`推奨`）。
  - A: `候補`、`決定`（採用 / 不採用 / 保留）、`理由`。
- **題**: 今の S には短い題が無い（S 551 件のうち、空白の資料に見出しを持つのは 152 件）。移行では資料の見出しを題にし、無いものは `# S-01` だけにする（399 件の題を作らない）。道具の一覧は題が無ければ「空白」の頭を出す。新しい S には題を付ける。
- **変更点（今の `onsa-0.3-changes.md` §4）は書かない**: 決定のファイルの `decided` と `spec` から、道具が変更の一覧を出す（今の §4 は履歴へ、DS-5）。
- **空白の下書き `S-xxx.draft.md`**（DS-2）:
  - 頭の欄: `group`、`drafted`（日付）。状態は持たない（状態は `S-xxx.md` だけ。道具と gate は下書きを正本と見ない）。
  - 本文のラベル: `決定済みで戻さないもの`（`rules/leader.md` 5.6）、今の空白の資料と同じ `論点`、`今の実装`、`案`、`他言語`、`推奨と理由`、`影響`。その後に `独立のレビュー`（伏せた選択と突き合わせ。親が写す）、`回答`。
  - 組ごとの付録（調べる途中で見つけたもの）は新しい S・R の登録として各ファイルへ、組の費用は記録しない（費用の目安は規則の日付付きの目安が担う）。
  - 利用者の回答は今も多くが会話で（第 32 組の「回答:」の行 11 のうち 10 が「会話」）、親が `回答:` と決定のファイルに書く。利用者が文書に書くときは、組の下書きを vim で並べて開く（`vim decisions/S/S-53[4-7].draft.md`）。
  - 下書きは決定の後も `decisions/S/` に残す。
- **設計の本文**（今の計画 §3）: `decisions/design/` の読み物。頭の欄は置かない（規則と同じ扱い）。

## DF-5 報告表（`issues/` と担当の報告）

**R**（`issues/R/R-235.md`）:

```markdown
+++
status = "OPEN"
severity = "低〜中"
aspect = 1
spec = ["§18.1"]
decisions = ["S-236"]
found_by = "W3-13/b"
+++
# R-235 候補の挿入と置き換えが、隣のトークンとつながるかを見ない

- 場所: syntax（`foreign/guard.rs` の守りの挿入、…）
- 内容: …
- 経緯: …
- 判断（2026-10-16、親。`rules/leader.md` 4.5）: 直す。…
```

- `status`: OPEN（直す、作業待ち）/ WONTFIX（直さない、記録）/ DONE。`severity`: 高・中〜高・中・低〜中・低。`aspect`: 1〜3（観点）。
- **直す作業は作業の側に書かない**: R の側の `fix = ["W3-13"]` だけに書く（作業の側の「直す R」は道具が出す）。宛先がまだ無い OPEN の R は `fix` を書かない（道具の一覧で「宛先なし」に出る）。
- **判断が改まったとき**: `判断（<日付>、<誰>）:` の箇条を足していく（今の §8 の表の複数行を、この並びにする）。頭の `status` は最後の判断に合わせる。
- **保存した入力**: テストになるものは `tests/` に置いて経路を書く。テストにしない再現の入力（今の R-235 の `w313b4/repro/`、R-233 の `dd3/call254_*.onsa`）は横のディレクトリ `issues/R/R-235/` に置く（DS-10 の X の材料と同じ規約）。scratchpad の経路は書かない。

**RF**: R と同じ頭の欄から `aspect` を除いたもの。本文は `場所`、`内容`、`経緯`、`判断`。

**X**（`issues/X/X-2.md`）: 頭の欄は `status`（OPEN / DOING / DONE）だけ。本文は利用者の文（`## 問題点`、`## 改善の手順`、今の `process_improvement_after_w3.md` の各章をそのまま）と、その後に `- 決めたこと（手順 <n>、<日付>）:` の箇条（材料のファイル `X-2/step2_structure.md` を指す）。
X は利用者が書く文書なので、見出しは利用者の形を保つ（DF-1 の「本文に `#` を使わない」の例外）。

**宛先の無い持ち越し**: 新しい種類の ID を作らず、移行のときに次のどれかへ分ける。
- 不具合 → R、リファクタリング → RF、進め方の改善 → X、宛先のあるもの → 作業のファイル。
- 票を書くときの手順の注意（今の「W4〜W7 のテストの票: 修正候補の細部で仕様が決めないものは期待値に書かない」）→ `rules/process.md`。X にすると終わらない X ができるため。
- 分けられないものが残ったら、そのとき利用者と決める。

**担当の報告**（今の計画 §8.4、「次の担当へ」、引き継ぎの記録）:
- 形は今のまま（会話の本文で返し、親が scratchpad に保存する）。形の規則は `rules/process.md`（今の計画 §8.4）。変えるのは参照の経路だけ。
- **報告そのものはリポジトリに残さない**（DF-D、決定。全てを残すとリポジトリが大きくなる）。後で要る点があるときだけ、親が要点を絞って宛先のファイルに書く:
  - R・S の登録、単位の分け、親の答え → それぞれのファイル。
  - 引き継ぎで補ったこと、見つけた方法（道具と入力の作り方）→ 作業のファイルの `結果` か、R・RF の `経緯`。
  - 後で要る再現の入力 → R の横のディレクトリ（上の「保存した入力」）。
- 今の `rules/leader.md` 1.4（壊す側の報告は後のリファクタリングの材料なので消さない）は、「要る点は RF・R に移す」に移行の (7) で改める。

## DF-6 作業表（`tasks/` と作業票）

**W**（`tasks/W/W3-13.md`）:

```markdown
+++
status = "DOING"
size = "S"
depends = ["W3-03", "W3-04"]
marks = ["基盤"]
doing = ["U2/i", "U2/b"]
+++
# W3-13 書き換えの仕上げ

- 内容: …（今の表の「内容」）
- 単位: U1 …、U2 …（親の答え、2026-10-15）
- 持ち越し:
  - W3-18/b の報告（2026-10-09）: …
- 結果: …（DONE のとき。一行）
```

- `status`: PLAN（計画にある）/ PENDING（保留: 検討の結果、今はやる必要がないと判断した）/ DOING（票が出ている）/ DONE（DF-C、決定）。
  - PENDING にしたときは、本文に `- 保留（<日付>、<誰>）: <理由>` の箇条を足す（R の判断と同じ形。PLAN に戻すときも箇条を足す）。gate は確かめない（まれな状態で、本文のラベルは確かめない方針）。
  - 着手できるか（依存が済んだか）は `depends` から、決定待ちか（担う決定が OPEN）は決定の `tasks` と `before` から道具が出す。どちらも PLAN のまま。
- `doing`: DOING の中の票（`<単位>/<役割>`、役割は t・i・b、直しは `U2/i-fix1`）。親が票を出したときと報告を受けたときに改める。DOING の外では書かない。
- `marks`: 今の「役割・印」の欄の閉じた値（`危険`、`メモ`、`基盤`、`テスト`）。今の「基盤（U3）」のような修飾は本文の `単位` へ移す（移行の道具が落ちる値を挙げる）。
- `size`: S・M・L。`commit`: DONE のときのコミット。段（W3）は ID から道具が出すので欄にしない。
- **実現する決定は書かない**: 決定の `tasks` と R の `fix` から道具が出す（DS-2）。例外は、正本が履歴にある ID（点検の C など。履歴は直さないので決定の側に書けない）で、作業の `refs` に書く。
- **持ち越し**: 宛先の作業のファイルの `持ち越し` に、出所（票、日付）と一緒に書く。作業が DONE になっても消さない（記録として残す。今の「入れた行はコミットで消す」の規則は、移行の (7) で改める）。
- **段の一覧と診断コードの表**（DS-1）: 段の一覧（今の rework §2）は `tasks/README.md` の表。作業の数の欄は道具が出す（今の欄の W3 の 21 は W3-22〜W3-24 の追加の前の値で古い。行は 105）。

## DF-10 リスクと、もっと単純な代替

- **頭の欄を TOML でなく、決まった名前の箇条にする案**（advisor の第 1 段。`- 状態: 決定`、`- 担う作業: W3-13`。Rust RFC の雛形の頭と同じ形）:
  - 利点: 書き方が一つで、日本語の欄名と値のまま読める。引用符と配列の括弧が要らず、書く摩擦が無い。読む道具は正規表現で約 30 行。
  - 代償: 本文もラベル付きの箇条なので、欄と本文の境を欄名の一覧でしか分けられない（欄名と本文のラベルを重ねない約束が要る）。値は文字列だけで、配列は `、` で切る。文法の誤り（引用符の抜け、キーの重なり）で確実に落ちる性質は無く、値の揺れは閉じた値の確かめだけで捕まえる。
  - advisor の第 2 段の見立ては「どちらでも成り立つ、確信は低い」。親は境の明瞭さと標準の読み手のために TOML を推す（判断を頼む項目の DF-A）。
- **関係を一方にだけ書くリスク**: ファイルを一つだけ読んだ担当は逆向きを知らない（決定のファイルに担う作業はあるが、作業のファイルには実現する決定が無い）。対策は、README と規則で「作業のファイルは道具の `show` で読む」とし、`show` が逆向きを添えること。道具が無い段階では効かないので、移行の順（DS-9）で道具を先に作る。改めの関係だけは両側に書く（DF-4）。
- **題の無い S（399 件）**: 一覧が読みにくい。題を後から足すのは、その S を読み直す作業のついでにする。
- **担当が頭の欄を壊す**: 担当が決定や作業のファイルを編集するのは今も親の写しを通すので、gate の確かめで足りる。
- **大文字の状態と日本語の本文の混在**: 見た目が揃わない。代わりに、本文の言葉（「決定」）と状態の値（DECIDED）を取り違えない。
- **報告を残さないこと**: 原文は scratchpad とともに消える。要る点を親が書き忘れると失われる（DF-D で受け入れた代償）。
