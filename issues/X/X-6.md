# X-6 リファクタリング RF-5〜RF-15・RF-18

## 問題点

巨大なファイルや共通化されていないデータ構造が残っており、この先の開発コストを上げる懸念があるのでリファクタリングを行う。

## 方針

リファクタリングの対象が多いので、可能な限り並列に作業し、gateはマージ後の最終確認でのみ流す。
一つ一つの `RF-*` ではなく、X-6のタスク全体のスループットを上げる。

## 改善の手順

1. 各リファクタリングの修正方針を具体的に検討
  - 始めに、親が持ち越しを済んだもの・RF・範囲の外に仕分け、前の回の scratchpad にある材料の要点を `issues/X/X-6/` に移す。

2. 各リファクタリングが修正/参照するコードを分析し、依存の単位でグループ化
  - グループは「単位の大きさ」（`rules/budgets.md`）でも分ける。

3. グループごとにimpl担当を割り当て、ワークツリーで並行作業

4. break担当は、impl担当の実装完了時に適宜割り当てる。確かめ方は `rules/process.md` 8.5 の「壊す側」に従い、出力を変えない直しは主に `compare.py diags` で確かめる（自作の掃引は合計約 5 分まで）。

5. break担当からの指摘が修正されたら、一旦mergeする。

6. 全てのリファクタリングタスクがmergeされた時点でgateを実行

7. gate でエラーが検出された場合、普段通りの手順に戻り、impl -> break -> impl .. と修正が終わるまで往復する。break の再確認を省くかは `rules/process.md` 8.6 の「直しの確かめ」による。

8. 評価: グループごとに、担当の費用（`handback.py usage`）、実装と壊す側の往復の数、かかった時間、見落とし（最後の gate で見つかり、壊す側が見つけなかったもの）を記録し、前のリファクタリング（12 回目の RF の単位 1・2、2026-10-10〜11）と比べる。
