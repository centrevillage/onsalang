# X-7 イベントのクロックと停止・再開・初期化の設計

- 持ち越し:
  - **W3 の終わり（イベントのクロックとインスタンスの停止・再開・初期化の詳細の検討、2026-10-15、利用者）:** 仕様 §19.1 の次の三つを W4 の前に詳細に決め、第 1 期に入れる範囲を W4〜W10 の作業に割り当てる。
    - 対象: イベント（S-171。イベントの出力、§19.1 の flow の `block` の出力を含む）、インスタンスの停止・再開・初期化（S-170）、それらのホストとの境界（export の形と C の API）。
    - 理由（利用者）: イベントの有無で export の境界とホストのアプリの作りが変わり、アプリを作り始めた後に直すと手戻りが大きい。停止・再開・初期化はイベントの大きな使い所なので、同じ時に決める。
    - 導くクロック（可変の制御レート、オーバーサンプリングとダウンサンプリング）は後回しのまま（使うアプリが限られ、境界を変えない足す向きの変更）。ただし、クロックの順序（今の `init` < `block` < `sample` の全順序）は、導くクロックも後で入る一般の形で設計する。
    - 停止・再開・初期化の構文（利用者の方向。詳細は検討の時に利用者が説明する）: S-170 の `when c` / `reset_if r` の節ではなく、flow の呼び出しに修飾子を関数の連鎖の形で付け、新しい flow を合成する。
      例: `saw~(f0).when(active).reset_if(on_start) + sin~(f0)`。キーワードを消費しないので、後で他の修飾子（`default` など）を足せる。
      あわせて見直すもの: S-170 の節の形の決定と仕様 §19.1 の文、S-169 の `when`・`reset_if` の予約（§2.2。`.` の直後の予約語は S-357・S-371）。
    - 進め方: 空白の流れ（下書きと独立のレビュー）を大きくした形。論点を幾つかの S に分ける（クロックの意味と同じサンプルの中の順序、修飾子の意味、混ぜる規則、境界と C の API、std の型、`onsa test`・`render` でのイベントの与え方など）。
      第 32 組の後の空白の流れの枠で始め、W3-12・W3-13 と並べて進めてよい。決めた後に「第 1 期で作る範囲」を利用者が選び、作業の行に割り当てる（`rules/leader.md` 6.5）。
