# X-7 イベントのクロックと停止・再開・初期化の設計

## ユーザー事前検討: when,reset_ifをメソッドチェイン形式のflow modifierとして抽象化する案の検討

before
```
(saw~(f0) when active reset_if on_start) + sin~(f0)
```

after
```
saw~(f0).when(active).reset_if(on_start) + sin~(f0)
```

利点:
- キーワードがいらない
- 関数呼び出しの構文を流用できる
- 将来的にmodifierを拡張できる余地が生まれる(たとえば `default` )
- 一塊になるので、外側の括弧が不要になる

欠点:
- 存在しないmodifierを入れた時のエラーが構文エラーでなく名前のエラーになる

論点としては、以下の形を許すか:
```
let sig1 = saw~(f0)
let sig2 = sig1.when(active)
let sig3 = sig2.reset_if(on_start)
```

この場合、sig1/sig2/sig3 は別のflowインスタンスとして解釈される。
sig1/sig2 がflow中の他の文で参照されない場合は、内部的には一行で定義した場合と同じく作られるflowインスタンスは一つ、とできれば性能上の影響はないと思われる。

以下の例外形について事前検討が必要:

```
saw~(f0).when(flag1).when(flag2) // flag1 && flag2 の時active?
saw~(f0).reset_if(flag1).reset_if(flag2) // flag1 || flag2 の時reset?
```

呼び出し名についての論点:

- when / reset_if はflowインスタンスを返すので when~ / reset_if~ にすべきかどうか
  - 文脈から十分推測できるので、その意味では末尾の `~` はなくても問題がない
  - しかし、構造体のメソッド呼び出しと区別がしづらい問題はある

```
// 1行の場合 (`~` は冗長に見える)
saw~(f0).when~(active).reset_if~(on_start) + sin~(f0)

// 複数行の場合 (`~` によってメソッド呼び出しとは区別される)
let sig1 = saw~(f0)
let sig2 = sig1.when~(active)
let sig3 = sig2.reset_if~(on_start)
```

`~` の数だけflowインスタンスができる、と考えると一貫性があるとも思える。

もっと抽象化した場合の論点:

flow modifier は flow 自身を入力し、別の flow を返す関数としてもう一段階抽象化できる。
(flow 版の高階関数)

```
// 組み込みの flow modifier
target flowmod when(in: flow, condition: Bool) -> flow

// ユーザー定義 flow modifier
flowmod rondom_when(in: flow, probability: F32) -> flow {
  in.when~(rand~() > probability)
}
```

実際には戻りの型は flow なので省略できる:
```
target flowmod when(in: flow, condition: Bool)

flowmod rondom_when(in: flow, probability: F32) {
  in.when~(rand~() > probability)
}
```
最後の文が flow 以外の場合はコンパイルエラーになる。
flow と違うので、計算レート(at)を指定することはできない。
その意味では fn 世界と flow 世界の中間の存在といえる。

以下の表現は等価になる:
```
saw~(f0).when~(active)
when~(saw~(f0), active)
```

上記の２番目の例では、`when~` が通常の flow とは異なる意味で呼ばれていることになる。
通常の flow であれば、flow が引数に与えられたら、その flow の計算結果が渡るが、flowmod の場合は flow そのものが渡る。
これは異義異形の原則(P3)に反しており、区別可能にすべき。

flow modifier に専用の後置修飾記号を導入すれば区別は可能:
```
when~~(saw~(f0), active) // 単純に `~` を二つ並べる。見落としやすい欠点はあるが、flow に関連する呼び出し、という意味は通りやすい。
when(saw~(f0), active)) // 一番最初の案に戻って、あえて後置修飾しない。fn 世界の関数とは flow が渡されているかどうかで区別。チェイン形式の場合に冗長さがなく読みやすい。fn 世界の関数と名前空間が別れないので競合しやすい欠点あり。
when$(saw~(f0), active) // $を90度回転&反転した `~` に縦棒がついたもの、と無理やり解釈。`~~` と二つ繋げるよりは短く、判別もしやすい。`$` の他の言語での使い方と読みが分かれる欠点あり。
```

他に区別するためのアイデアがあるか？

flow modifier に二つ以上のflowの入力がある場合の論点:

例えば以下のような flow modifier を考える。
(ここでは、flow modifier の後置修飾に `$` を採用したと仮定して進める)
```
flowmod branch(in1: flow, in2: flow, select_flag: Bool) {
  when$(in1, select_flag) + when$(in2, !select_flag)
}
```

上記のように、複数の flow を受ける flow modifier があると便利である。

ただし、この場合にメソッドチェイン形式で呼び出せるかどうかが論点になる。
```
saw~(f0).branch$(sin~(f0), 0.5) // 最初の flow 引数を self として解釈するか？
```

一方メソッドチェイン形式での呼び出しを廃止した場合、 when と reset_if を組み合わせるようなよくあるケースでは見辛くなる。
```
saw~(f0).when$(active).reset_if$(on_start) // before
reset_if$(when$(saw~(f0), active), on_start) // after
```
後者はネストが深く、読みづらい。

現時点での推奨はメソッドチェイン形式の呼び出しを許可し、最初の flow 引数を self 扱いにする。
これで困る場面がないか要検討。

flow modifier を flow trait の実装として捉えた場合の論点:

flow modifier を fn 世界のメソッドにあたるものだと考えると、ある flow が特定の modifier を持つかどうかは flow trait として抽象化することができる。

```
// flow trait があったと仮定した場合の構文
flow trait When {
  flowmod when(self, condition: Bool)
}
impl When for saw {
  flowmod when(self, condition: Bool) {
    ...
  }
}

flow saw(x: F32 at block) {
  ...
}
```

この場合は逆にメソッドチェイン形式でしか呼び出せなくなる:
```
saw~(f0).when$(active)  // OK
when$(saw~(f0), active) // NG
```

ただし、具体的にこれができて嬉しいケースは現時点で想定できない。
もし嬉しい場合があれば検討。

W4前にどこまで決めるかの論点:

ユーザー定義の flow modifier はしばらく未実装で問題なく、将来的に追加された時に問題が発生しなければ良い。
よって最低限決めるべきことは以下。

- `when` / `reset_if` を独立したキーワードとして後置修飾でflowに適用する(元々の案)か、メソッドチェイン案(新案)にするか
- `flowmod` をキーワードとして予約するかどうか
- メソッドチェイン案の場合に、`when` / `reset_if` に特別な後置修飾(`$`, `~~`, ...)をするかどうか
- `when` / `reset_if` を複数回同じflowに対して適用した場合の解釈
