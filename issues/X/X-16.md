# X-16 ディスクの書き込みを減らす（作業ツリーのビルド、`cargo test`、fmt の性質の試験）

## 問題点

利用者（2026-10-26、72 回目）: この PC は SSD で、書き込みの回数に寿命がある。Python の試験の間のディスクの書き込みがいつも激しい。思ったより激しいので、早めに対処したい。

## 測り方と測った数

- 測り方: macOS の `ioreg -c IOBlockStorageDriver` の「Bytes (Write)」（起動してからのディスクの書き込みの累計）を、処理の前と後で読んで差を取る。ディスク全体の数なので、他の処理を止めて一つずつ回した。台本は横の `measure.py` と `run*.sh`（72 回目、dev `64f3a09` の前後）。
- 一回あたりの書き込み:

  | 処理 | 秒 | 書き込み |
  |---|---|---|
  | 作業ツリーの最初のビルド（空の置き場への `cargo test --workspace --no-run`） | 40 | 1990 MB（重なりあり、下の注意） |
  | 同じビルドで `debug = "line-tables-only"`（環境変数で一時に指定） | 29 | 1604 MB（重なりあり） |
  | `cargo test --workspace` を走らせるだけ（ビルドのし直し無し） | 71 | 604 MB |
  | うち `onsa_cli` の結合テスト（ほかの crate は合わせて 50 MB 弱） | 27 | 563 MB |
  | `onsa_cli` の `use_model`・`use_shapes`（`use` の形の掃引） | 7・4 | 213・89 MB |
  | `onsa_cli` の `fmt_lines_lists`・`fmt_comments`・`fmt_spaces_lists`・`fmt_spellings_columns_ranges`（`onsa fmt` にその場で書き換えさせる） | 各 1 | 58・56・49・29 MB |
  | fmt-props の絞った回（`--changed-since c4282d1 --sample 0.1 --salt W4-03`）、X-1 U12 の前 | 76 | 1235 MB |
  | 同じ回、X-1 U12 の後 | 63 | 97 MB |
  | fmt-cst（同じ絞り） | 12 | 28 MB |
  | fuzz（同じ絞り） | 21 | 35 MB |
  | 何もしないとき | — | 0.2〜1.8 MB/秒 |

- 注意（親の誤り）: 一回目の台本（横の `result_run_all.txt`）は、X-1 U12 のコミット `64f3a09` の直後に回したので、コミットの後の網羅の検査（`sweep 0/2`、18:52〜18:57）と重なった。
  重なったのは、その台本の fuzz・ビルドのし直しの無い `cargo test`（701 MB）・空の置き場へのビルド二回の書き込み・最後の何もしない 30 秒（29 MB）で、数は当てにならない。表の fmt-props の前と後、`cargo test` の 604 MB、テストのファイルごとの数は、重ならない後の回（`run2.sh`・`run4.sh`・`run5.sh`）の数。
  空の置き場のビルドの大きさ（`du`）は重なりの影響を受けない: 今の設定 1.9 GB、`line-tables-only` 1.6 GB（約 16% 減）。
  この回では、網羅の検査の fmt-props も、台本の `cargo test -p …` が同じ `target/debug` の `onsa_cases` を置き換えた時と重なって、バイナリが見つからずに落ちた（X-1 U12 の誤りではない）。測るときは網羅の検査が走っていないことを確かめる。
- コミットの後の網羅の検査（X-1 U4）も書き込み元: コードか事例を変えたコミットのたびに、shard 一つの `cargo test`・fuzz・fmt の性質の試験を回す（72 回目は約 8 回）。

- 作業ツリーの一回のビルドの中身（U12 の作業ツリーの `target/debug`）: 差分コンパイルのキャッシュ（`incremental/`）約 1.8 GB、ワークスペースの crate 約 0.93 GB、結合テストのバイナリ（76 ファイル、ファイルごとにワークスペース全体をリンク）約 0.40 GB、外部の依存（`Cargo.lock` の 37 crate）約 0.17 GB。
  種類では、デバッグ情報を持つ `.o`（macOS では実行ファイルの外に置く）が 655 MB で一番多い。外部の依存を先にコンパイルしておいても、減るのは 1 割ほど。
- 原因の分かったもの: `onsa fmt` は書き戻しで一時ファイルに書いて `sync_all()` をしてから rename する（`crates/onsa_cli/src/main.rs::write_replacing`、`spec/tools.md` §3.6）。macOS ではこれが `F_FULLFSYNC` で、fmt-props は絞った回で約 6000 回これを起こしていた（X-1 U12 で 0 にした）。`fmt_*` の結合テストも事例ごとに起こす。
  `use_model`・`use_shapes` は `fmt` も `fix` も呼ばずに約 300 MB 書く。理由は調べていない。

## 案

- A: 開発用のビルドのデバッグ情報を行番号だけにする（`Cargo.toml` の `[profile.dev] debug = "line-tables-only"`）。全てのビルドで約 2 割減。panic の場所の表示は残る。
- B: `cargo test` の書き込みを減らす。`fmt_*` は、書き戻しを確かめるテストを少数に残し、他は整形の結果を書き込まずに受け取る形にする（X-1 U12 の `onsa_cases --fmt` と同じ考え方）。`use_model`・`use_shapes` は書き込みの理由を調べてから直す。
- C: 作業ツリーを作る回数を減らす（同じ単位の直しは同じ作業ツリーで続ける、引き継ぎで前の作業ツリーを使い回す）。72 回目は約 10 回作り、それぞれ最初からビルドした（一回約 2 GB）。担当ごとに新しい作業ツリーを作る道具と規則に関わる。
  - 測り（73 回目）: 道具の単位 1（Python の道具だけ）を主のツリーで担当に作らせた 21 分で、ディスク全体の書き込みは 3716 MB（`ioreg` の差。ほぼ空の `target/debug` からのビルド、自己テスト、作業の検査 1 回、親の作業を含む）。作業ツリーで動かすと、作業ツリーの一からのビルド（約 1.6 GB）が加わる。
    続けて主のツリーで道具の単位 2（Rust のテスト 3 ファイル）を担当に作らせた 13 分は 647 MB（差分のビルドとテストだけ）、その後の親の `gate --quick` は 910 MB（`cargo test` の全体を含む）。
- D: 増分コンパイルを切る（`[profile.dev] incremental = false`）。73 回目に `target/debug` の 2.3 GB の内訳を見ると、増分の控え `incremental/` が 1.5 GB（crate ごとに、ライブラリ・単体テスト・clippy の形で 5 つずつ）、テストの実行ファイルが 391 MB（94 個）、`.o` が 351 MB、ライブラリが 271 MB、`onsa`・`onsa_cases` が 44 MB だった。
  - 測り（73 回目、各 1 回）: `onsa_sema` に関数を一つ足して作り直すと、`onsa` は 1.6 秒 / 150 MB → 2.9 秒 / 81 MB、続けて `onsa_cli` のテストは 3.8 秒 / 505 MB → 3.9 秒 / 189 MB、直してすぐテストまでは 5.2 秒 / 680 MB → 6.6 秒 / 268 MB（増分あり → なし）。
    空の置き場の一からの `cargo test --workspace --no-run` は、増分なしで 13 秒、794 MB 書き、置き場は 803 MB（増分ありは置き場 1.6 GB）。`CARGO_INCREMENTAL` を変えても、変えていない crate は作り直されない。台本は 73 回目の scratchpad の `incr/measure_incr.py`。

- 決めたこと:
  - A を採る（2026-10-26、72 回目、利用者）。B は時期を分けて道具の単位にし、C は区切りで利用者と相談する。
  - D を採る（2026-10-26、73 回目、利用者）: 全ての木で切る（作業ツリーでだけ切る形は、作業ツリーを作る Agent の道具に設定を差し込む口が無く、環境変数を配る仕組みが要る）。小さな直しの作り直しは 1〜1.5 秒遅くなる。
    入れ方（親が主のツリーで）: `Cargo.toml` の `[profile.dev] incremental = false`、主のツリーの `target/debug/incremental/`（2.1 GB）を消した。
  - B の始めの単位（2026-10-26、73 回目、利用者が了承、`77a6653`。onsa-impl 1 体、主のツリー。作業の検査は `--work X-16/U2` で PASS 147 秒。`--work` は `X-n/U<数>` の形だけを受けるので、B を U2 とした）:
    原因: `onsa check` は書かない。`use_model`・`use_shapes` は、候補を一つずつ当てる試行のたびに `test_support/sweep.rs` の `write_texts` がパッケージの全てのファイルを書き直し、ファイル一つで約 4 KB 書く（`use_model` は約 1 万回の試行）。fmt の 4 ファイルは `onsa fmt` に同期の書き込みでファイルを置き換えさせていた。
    直し: `write_texts` は中身の同じファイルを書かない。fmt の 4 ファイルの整形の比べは `test_support/fmt.rs` の `expect_fmt`（`onsa_driver::format_file` を直に呼ぶ）で、書き戻しそのもののテストは `onsa` の起動のまま。
    測り（前 → 後）: `use_model` 209 → 29 MB、`use_shapes` 62 → 46 MB、fmt の 4 ファイル 197 → 3 MB。6 ファイルで 468 → 78 MB、`onsa_cli` の結合テストの全体は 167 MB。`write_texts`・期待の文・不動点を一時に壊すとテストが落ちることを担当が確かめた。
  - A の入れ方（72 回目、親が主のツリーで。担当に頼むと作業ツリーのビルドがもう一度起きるため、利用者が了承）: `Cargo.toml` の `[profile.dev] debug = "line-tables-only"`。
    作業の検査で `onsa_diag::stack` の `with_stack_left_leaves_about_that_much` が落ちた（8 MiB を求めて約 3 K 下）。試験用の補助 `with_stack_left` が `f` を呼ぶ境目（3 × `STEP`、12 K）に、フレームと `f` の頭が収まらなくなった。
    境目を `BAND` = 5 × `STEP`（20 K）にした（9 つの量で余裕 3.8〜12.1 K）。インタプリタの深さと安全網のテストは、変えずに通った。
- 持ち越し:
  - B の残り（73 回目の担当の報告、推測を含む）: `use_shapes`（46 MB）・`use_model`（29 MB）・`use_repair_loop`（13 MB）は、形や種ごとに新しいパッケージを作る分（呼ぶ側で `Dir` を使い回せば減る見込み）。
    他に `flow_syntax` 9 MB、`fmt_rewrites`・`fmt_same_program` 各 7 MB（`onsa fmt` のその場の書き換えなら同じ手当てが効く）、`failed_names`・`type_args_syntax` 各 5 MB。
