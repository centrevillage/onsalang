## 第 1 部（parent_view_guard.md を読む前）

### 1. β（書き直しの歯止め）が防ぐ範囲と抜け

β の形: 書き直す前に、古い写しの組（その K の写しを全ファイルに当てた形。無いファイルは元のまま）と新しい出力の組をそれぞれ検査し、新しい方にだけ出る診断があれば拒む。

防ぐもの: `pkg_rename` の形そのもの。古い `main.onsa.fix1`（使用を改名した形）を当てた検査は何も出ず、新しい出力（宣言だけ改名）を当てた検査は `main.onsa` に E0302 を出すので、拒まれる。空白や順だけの違い、古い写しが隠れていた後の段の誤りを含む場合（両方に同じ診断が出る）、古い写しが仕様に反して新しい出力が正しい場合（診断が減る）は、いずれも通る。

抜け（形ごと）:
- **写しの無い新しい事例（作るとき）**: 比べる古い組が無い。元のファイルと比べると、元には原の診断（例: E0320）があり、新しい出力には別の単位の E0302 が出るので「新しい方にだけ出る」で拒めるが、同じ規則は、原の単位に隠れていた後の段の誤りが出る正しい候補（§18.1 の 26 行が許す形）も拒む。つまり作るときの β は α と同じ問いになり、α の形（下）で判定するしかない。β だけでは新しい事例を守れない。
- **保留の間**: 書き直しが起きないので β は走らない（M2 の m1 のとおり。外した回に走る）。
- **同じ単位の後の段**: 古い写しの組と新しい組の両方で、原の単位に後の段の診断が出うる。β は「新しい方にだけ」なので、古い写しが隠れていた E0401 を一つ出し、新しい出力が別の E0401 を同じ単位に出すとき、コードと単位で比べれば同じに見える。位置まで比べると編集の長さの差でずれる。コードと単位（ファイルと `diagnostic_units` の番号）で比べ、位置は使わないのが安全で、この粒度で見逃すのは「同じ単位に同じコードの別の誤り」だけ。
- **複数のファイル**: 写しは K ごとにファイルの組なので、組で当てて検査すればよい（`fixes.rs` の `compare` は K ごとに全ファイルの当てた結果を持っている）。toml の `fixed` は一つのファイルの例なので、`check_text` で同じことができる。
- **複数の誤りの事例**: 両方の組に元からある診断（他の単位の誤り）が出る。コードと単位で比べれば相殺される。候補 K が触れた単位の数が組の間で違うとき（編集の形が変わって単位が増減する）は、単位の番号が対応しないので、そのときはファイルとコードの多重集合で比べる（粗いが安全側）。
- **消すとき**（K 番目の候補がそのファイルを編集しなくなった）: 古い組にはその写し、新しい組には元のファイルが入る。同じ比べで足りる。
- **診断の位置がずれる**: 上のとおり位置を比べない。
- **候補の順が入れ替わった**（K の対応が変わる）: 古い K 番目と新しい K 番目が別の読みになる（E0010 など）。どちらも clean なら通り、違えば拒まれて手で見る。害は無い。
- **費用**: 書き直すときだけ、K ごとに検査を 2 回足す。普段の gate には影響しない。器の中に `recheck` が既にあるので、実装は 60〜100 行（組を当てる、2 回検査、コードと単位で比べる、文面）。
- **上書きの道**: 拒んだ後に本当に書き直したい場合（古い写しが仕様に反していて、しかも新しい出力が隠れていた誤りを出す）のために、明示の印（`UPDATE_GOLDEN=worse` のような別の値）を要る。印は報告に書き、親が見る。印の無い `UPDATE_GOLDEN=1` では決して通らない。

結論: β は「既にある写し」を書き直すときの危険を機械で塞ぐ。新しい事例と保留の間は塞がない。

### 2. α（約束の器を強める）の健全性

- 定義: 当てる前に診断の無かった単位（触れたかを問わない）に、当てた後に（段を問わず）診断が出れば違反。
- 誤って捕まえる形: 当てる前に診断が無かったのは「全ての段を通った」か「誤りの型で検査を抑えられた」かのどちらか。後者は、構文の誤りで読めなかった部分を使う側に診断を出さない規則（§18.1 の 73 行。実装は `expressions.rs` 174〜176 行の `Ty::Error`）で、その単位は構文の誤りを直した候補の後に本物の誤りを出しうる。器は `Unit`（`span` と `parent` だけ）からこれを知れない。`Analyzed` に「誤りの型に触れた単位」の集合を足せば判定を一か所（sema）に置ける（D-15）。足すまでは `[[test.fix]]` の `leaves` を触れていない単位にも書けるようにして逃がす。
- 実験の数: 近似で当たった候補は 26/2259。うち 22 は私の近似の人工物（`#[…]` の行を項目の始まりに数えず、当てた後に `@` で項目が増えて番号がずれた。`e0020_hash_attribute`、`e0020_derive_attribute*`、`continue_attr_same_line`、`doc_after_attribute_modules` は、当てる前から同じ行に同じ診断があることを確かめた）。本物は `e0320_rename.onsa` の 4 候補だけで、改名の候補が使用を直さず別の単位に E0302 を出す S-82 の形（全体の項目と `fix-contract` の項目で既に保留）。**隠れていた誤りで正しい候補を誤って捕まえた例は 0。** パッケージの事例（`pkg_rename` など 10 件）は実験の外で、`pkg_rename` は α に当たる（`main.onsa` の E0302）。
- §18.1 に文を足すか: 今は足さない。X3-1a で約束の層を閉じたばかりで、α は「触れていない単位」と「後の段」で L1 より強く、誤りの型の例外の文が要る。テストの側の決まり（Q-04 と同じ器の決まり）として置き、違反と逃がしの数がたまってから S にするのが 7.18 と 7.5 に合う（厳しい方から後で緩めても壊れない）。

### 3. 選ぶ組み合わせ: β と α の両方（確信: 中〜高。β 単独なら高、α を足すことは中）

- 役割の分担: α は毎回の gate で働く絶対の網で、写しの有無によらず（新しい事例も）「他の単位を壊す候補」を捕まえる。β は書き直すときの相対の網で、α が見ない「同じ単位の後の段」と「元から診断のある単位」の後退を、古い写しとの比べで捕まえる。β だけでは新しい事例を守れず、α だけでは原の単位の後退（文をまるごと消す形の一部）を見ない。
- 記述に頼る部分: 残るのは (i) 上書きの印を報告に書くこと（Q-04 の「報告に並べる」と同じ）、(ii) α の逃がし（`leaves`）を書く理由を事例に書くこと、(iii) 設計の理由の文書。「外す前に親が仕様と照らす」の規則の文は要らなくなる（β の失敗の文が代わる）。
- X-6 の収束への影響: 出力を変えないリファクタリングでは α も β も鳴らない（α は今の候補で本物の違反が既知の保留だけ、β は書き直すときだけ）。意図して候補を変える回では、β が「悪くなる変化」だけを止め、同じかよい変化は通す。拒まれたときの出口は性質への移行か明示の印なので、作業は止まらない。
- 基準: 7.17（当てた前後の状態だけで判定できる形。α も β も前後の検査結果だけ）、7.18（修復のループは「他の単位を壊さない候補」に実際に頼る）、7.13（α の抑制の情報は sema から出す）、7.5（テストの側の規則は後で緩められる）。
- 別の案「一つの誤りだけの事例で `clean` を既定にする」は、α に含まれる（一つの誤りの事例では、原の単位以外の全てが「診断の無かった単位」）。α の方が複数の誤りの事例にも効き、`clean` の既定化で起きる「原の単位の隠れていた誤り」の偽陽性が無い。採らない。

### 4. 選んだ組み合わせで、M2 の m1 と前の足す点のどれが要らなくなるか

- m1（保留の事例では写しを判定せず、書き直さない）: そのまま要る。β は書き直しのときに走るので、保留を外した回の書き直しも β を通る。
- 足す点 1（要約に名前と件数）: 件数は残し、名前は任意になる。保留の間の後退は、外した回に β が止めるので、名前で親が見比べる必要は薄い。
- 足す点 2（外す手順の規則の文）: 要らない。β の失敗の文「写しが規則を担っている。`[[test.fix]]` の性質か `property` に移してから書き直す。上書きは `UPDATE_GOLDEN=worse` で、報告に書く」が置き換える。
- 足す点 3（写しを待つ理由に数えない理由の明記）: 要る（設計の理由の文書。検知とは別）。
