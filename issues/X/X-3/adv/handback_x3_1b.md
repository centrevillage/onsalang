### 1. 選ぶ案: Q（確信: 高）

約束のテスト（失敗 = 仕様の違反）は、器の L1 と範囲の外の読み（`fix_contract.rs` の 1〜4）、`[[test.fix]]` の `clean`・`same_code`・`leaves`、候補の数（`fixes = N`、toml の `candidates` と `fixed` の個数）にする。全文（`.fixK`、toml の `fixed`）は実装の回帰の写しとして残し、違いは失敗にするが仕様の違反ではなく、道具で書き直せる。

3 点の比べ:

- **X-6 の収束**: X-6 の受け入れ条件そのものが「出力を変えない（例外は列挙）」である（`issues/X/X-6.md` の「出力を変えない条件の例外」、「修正候補が当てた後に読めなくなる後退は 0 件」）。X-6 は既に、コーパスと変異の前後の差分で確かめている。全文の写しは、この条件を gate の中で機械的に確かめる唯一の網で、P はその網を X-6 の直前に外すことになる。
  収束を妨げていたのは文字列の細部ごとに S が立つこと（X-3: 125 件中 71 件）であり、写しの違いそのものではない。Q は、違いを S にせず「書き直して報告、親が差分を読む」に落とすので、収束を妨げない。
- **質の悪い候補を捕まえる力**: 器の 4 つの確かめは、文ごと消す候補、`a + b` を `0` にする候補、改行の置き場所が意図と違う候補を通す（後述 3 のとおり、機械の性質では閉じられない）。全文の写しは「変化の検出器」（Q-04）として、この類を全て見せる。P はこの類に盲目になる。R は見えるが止まらない。
- **管理のコスト**: Q は、書き直し（道具）と差分の読み（親）が要る。今の運用（`.fixK` を仕様から手で書き、細部ごとに S を起こす）より確実に小さい。P が最小だが、X-6 の受け入れ条件の確かめを壊す側の自作の掃引に戻すので、総コストでは Q と変わらないか大きい。

R を採らない理由: 警告は gate の pass/fail に乗らず読まれない（`rules/process.md` 8.5 の表「何も走らずに通る」と同じ失敗の形）。更新の仕組みが無いので警告がたまり、結局黙らせる。既にある Q-04 の形（失敗 + `UPDATE_GOLDEN=1` + 親の承認 + 報告に並べる）と二重の仕組みになる。

基準との照らし: 7.18（約束は頼る使い手を示せるものだけ。L5 に頼る使い手は無い → 約束から外す）、7.6（構造の変更は今のうちに。写しの位置付けの変更は X-6 の前が最も安い）、7.7（第 2 期で候補が増えても、写しの書き直しの費用は線形で、S の数は増えない）、7.13（判断を二か所に置かない: 候補の文字列を決める場所は実装の一か所になり、仕様はそれを決めない）。

### 2. Q の危険と手当て

- **何も見ずに書き直されて後退が隠れる**: 手当ては Q-04 の形をそのまま当てる。(a) 書き直しは環境変数で明示し、担当は書き直した写しを報告に並べ、親が差分を読む（`rules/process.md` 8.2 の 1）。
  (b) 道具が書き直せるのは本文（手順 4 の比べ）だけで、`fixes = N`・`candidates`・`fixed` の個数・`[[test.fix]]` の性質は道具の手の外に置く（数の変化は手で事例を直すので、必ず見える）。(c) 壊す側（/b）の票に、書き直した写しの差分を材料として渡す。
  (d) 失敗の分類を分ける: 写しの違いは `fix-copy`（仮）のような別の種類にし、`tests/pending.toml` の `fix-contract` では黙らせられないようにする（逆も同じ）。
- **写しが「実装の出力」として惰性で固定される**: 写しは意味の根拠ではない（Q-04）ことを `fixes.rs` の頭に書き、仕様から導ける性質（`clean`、`same_code`、数）を増やす方向を残す。一つの誤りだけの事例（`tests/spec/fixes/` の大半）で `clean` が既定で成り立つかは、`onsa_cases --fix-loop` の止まり方で数えられるので、X3-1c か後の回で測って既定化を検討する（今回は求めない）。
- **テストの役割の手順の変更**: 今は `.fixK` を t が仕様から書く（Q-01）。仕様が文字列を決めなくなるので、t は書けない（8.5「仕様が決めないものは期待値に書かない」）。t は `fixes = N` と `[[test.fix]]` の性質を書き、`.fixK` は初回の `UPDATE_GOLDEN=1` で器が出す。`rules/process.md` 8.5 のテストの役割の行に一文足す必要がある。

### 3. L2 前半（最小の編集）を機械で確かめる性質

作れるのは「縮められる・分けられる編集」までで、「必要以上に変える」は作れない。

- **作れる性質（器の 5 番目の確かめ）**: 一つの編集について、範囲に完全に入るトークン列と置換の文字列を字句解析し、(i) 先頭のトークン（種類と字面）が一致、または末尾が一致 → 縮められる、(ii) 範囲の中のコメントが置換にそのまま現れる → コメントを範囲に含めている（R-210 の類）、(iii) 範囲と置換に共通のトークンが中にある（短い列の LCS） → 二つの編集に分けるべき（`<T>` → `[T]` の規則）。
  失敗は `Problem::FixContract` と同じ名前付けで、既存の `fix-contract` の実装待ちで一つずつ黙らせられる。
  費用: `fix_contract.rs` に 80〜150 行、実行時間は無視できる（列は数トークン）。
  粗い字句分けの実験では端が一致する編集が 124 件出たが、大半は私の字句分けの粗さ（文字列リテラルや `--` を一つのトークンにしていない）による偽陽性で、本物の例は `tests/spec/fixes/e0020_clock_after_fn_type.onsa` の「` at block` → `) at block`」（`)` の挿入だけで済む）。
  器の `onsa_syntax::lex` を使えば偽陽性は消える。注意点は `reading_difference` と同じで、トークンの端への挿入はそのトークンの中ではない。
- **作れない部分と理由**: 「文をまるごと消す」のような、共通のトークンが無い過大な編集は、意図した直しの基準（オラクル）が無いと判定できない。
  代わりに試した「編集は診断の `span` の中（端を含む）に収まる」は、今の候補 2259 個のうち 1191 個が外れる（E0020 853: 置き場所の行は主の範囲が記号一つで、編集は前の行の末尾へ動かす。E0013 7: 被演算子の外に括弧を足す。E0002 136、E0003 151、E0004 43、E0401 1）。
  コードごとに例外を書けば使えるが、それは事例ごとの細部そのもので、写し（Q）の方が安い。よって「安全だが意図と違う」候補の網は全文の写しだけで、これが P でなく Q を選ぶ決め手になる。

### 6. 一致と割れ

一致した点:
- 案 Q を選ぶこと、理由（X-6 の差分が見える、書き直しで収束を妨げない、P は L1 を破らない壊れ方に盲目）。
- R を推さない理由（警告は埋もれる）。
- `UPDATE_GOLDEN=1` と Q-04 を `.fixK` に広げる形（私も同じ形を勧める。器は既に候補を当てて比べているので足す量は小さい、も同意）。
- toml の `fixed` と Rust の結合テストの扱いを X3-1c に送ること。

割れた点（推奨の違いではなく、親の案に無い点を足すもの）:
- 親は「最小の編集は機械で見ていない」を P を退ける理由にしているが、L2 前半のうち「縮められる・分けられる編集」は器で機械的に見られる（上の 3）。これを足すかどうかは Q の選択を変えないが、足すと L2 の約束が器で閉じ（今は後半だけ）、写しに頼る範囲が「安全だが意図と違う」だけに絞れる。足さないなら L2 前半は親のレビューと写しに頼り続ける。別の作業（X-6 の前か中）として勧める。
- 親の案には、書き直しの道具の手の届く範囲が書かれていない。数（`fixes = N`、`candidates`、`fixed` の個数）と `[[test.fix]]` の性質を道具の外に置くこと、写しの違いを `fix-contract` と別の種類にして互いに黙らせられないようにすること、を受け入れ条件に足すことを勧める（上の 2）。これを欠くと、Q の危険（何も見ずに書き直して後退が隠れる）が Q-04 の形だけでは塞ぎきれない。
- テストの役割の手順（`.fixK` を t が書かなくなる）の規則の変更が親の案に無い（上の 2 の三つ目）。

### 7. 親の事実の誤り、見落とし

- 事実の数は確かめた範囲で一致: toml の `fixed` 352、`property` 60、`candidates` 50、行 113、例 533。`.fixK` 247（fix1 209、fix2 37、fix3 1）。`[[test.fix]]` は 255 か所（親の「性質で確かめる形 60 か所」は toml の `property` の数で、事例側の `[[test.fix]]` は別に 255 ある。`clean`/`same_code` を持つものの数は数えていない）。
- Rust の結合テスト: 候補に触れる断定を持つファイルは `crates/onsa_cli/tests/` の約 10（`block_operands.rs` 10、`empty_brackets.rs` 9、`foreign_candidates.rs` 8、`flow_syntax_decisions.rs` 8、`diagnostics_json.rs` 7、`operator_groups.rs` 6 など。grep の粗い数え）。`foreign_candidates.rs` の頭の説明どおり、多くは編集の数と位置（L2 前半）の確かめで、写しでなく約束のテストに分類できる。
- rustc の `.fixed` の出典（確かめた）: rustc-dev-guide「UI tests」(https://rustc-dev-guide.rust-lang.org/tests/ui.html) によると、`//@ run-rustfix` の `.fixed` は「候補を当てた後のソース」で、`--bless` で実装の出力から生成し、一致を求め、さらに当てた後のソースがコンパイルできることを求める。
  つまり rustc の `.fixed` は手で書く期待値ではなく、道具で生成する golden と `clean` に当たる性質の組である。7.1 により推奨の理由には使わないが、Q の形（写し + 性質）に対応物があるという事実としては使える。`suggestion_applicability` は私は手元で確かめていない（未確認）。

- 見落とし候補: 「編集が診断の範囲に収まる」性質は、親の票に無いが私が試して使えないと分かった（上の 3）。親が後で同じ性質を考えたときの無駄を省くために記す。
