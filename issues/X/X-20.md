# X-20 コンパイラの性能: 段ごとの時間の測定、性能の要件、対策（今まで性能の要件を明示していない）

- 決めたこと: 79 回目（2026-10-28）、利用者が「コンパイラ検査の件は、どこかでちゃんと性能測定して対策しましょう。コンパイラ自体の性能要件は特にこれまで明示していなかったので、あまり注意が払われていない可能性は高いです。開発速度を全体的に遅くしますし、ユーザー体験も悪くなりますし」と言った。
  性能は、開発の速さ（gate、担当の試行）と利用者の体験（CLI、ブラウザの IDE で書くたびの再検査）の両方に効く。今の規則にある性能の確かめは、リファクタリングの前後の `compare.py speed`（`rules/refactoring.md` 8.2）だけで、単位ごとの検査の時間の変化は見ていない。
- 材料:
  - gate の test の項目が W4-05 の U1・U2 で 53.5 秒から 57.0 秒（足したテストは約 1 秒、残り約 2.5 秒は検査そのものの遅れの見込みで未確認。X-1 の持ち越しの「gate の時間」）。
  - W4-05 で見つけた最悪の形: 宣言を辿る時間が段の数の指数（R-313、今は歩数の予算で有界だが答えなしになる）、別名の鎖の指数（U1/b の F3、U2 で直した）、総称の深い入れ子の 2 乗の時間と記憶（U2/b の B-4、3000 個 × 250 段で 2.5 秒・524 MB、U2/i3 の後 3.1 秒・587 MB）、`Option` の別名の鎖 3000 段（U2 の前 3.3 秒、後 0.16 秒）。
  - 歩きのスタック（W4-05 U2b、80 回目）: 宣言を辿る一段が大きくなり、破棄の要否を問う宣言の鎖が `check` の安全網に当たる段の数が約 10 万から約 5 万に下がった。
  - 降下の配置（R-316、80 回目）: `onsa_core::layout` は答えを覚えず、型を問うたびに平らなフィールドを全て辿る。ふつうの大きさでは小さい見込みで、測定で降下の段が上位に出たら対策の候補にする（利用者）。
  - 仕様は型の深さと大きさの上限（§4.4、S-264）と入れ子の深さ（§2.5）で、検査の時間を入力の大きさの多項式に抑えることを狙っている（上限が処理系で違うと IDE と CLI で合否が変わる、P8）。
- 進め方（案。時期と要件の値は利用者と決める）:
  1. 測定: 代表の入力（`tests/spec` の全体、std、`examples/`、生成した大きめの入力）で、段ごと（構文、名前、署名、型、modes、flow、rt、効果）の時間と記憶を測る。上位をプロファイルで特定する。
  2. 要件: ふつうの大きさのファイルの `check` の時間の目安、入力の大きさに対する増え方（最悪でも多項式）、IDE の再検査の予算を決め、置き場所（`design/` か規則）を決める。
  3. 対策と歯止め: 上位の対策。gate を重くしない形で回帰を見る（単位ごとの `compare.py speed` の前後の報告、区切りでの全体の測定）。
- 持ち越し: 時期は W4 の終わり（X-1 の gate の時間の見直しと一緒、W4-18 のリファクタリングの前）を案とする。それまでは、実装の票の報告に `compare.py speed all` の前後（`check` の欄の壁時計と cpu）を書かせて材料を貯める（負荷の下では同じバイナリでも約 55% 揺れるので、担当が並んでいない時に測る。判定でなく材料とする）。
