# R-89 export の形を、C バックエンドの中で決めている

- 中・直す・観点 2｜`crates/onsa_backend_c/src/export.rs:132`、`:170`
- 内容:
  - `process` の引数を、位置（`skip(2)`）と、`"poisoned"` / `"initialized"` / `"bulk"` の文字列で引いている。
  - `inline_consts` は driver にだけあり、テストの `emit_c` は使っていない。
- 影響: WASM / JS のバックエンドは、同じものを作り直すことになる。
- 直し方: シンボル、入出力、飽和、メタデータを持つ共通の「export の計画」を作り、各バックエンドはそれを読む。
- 範囲（2026-10-05 に追加で確かめた）: `process` の信号の引数を位置（`skip(2)`）で、状態のフィールド `poisoned` / `initialized` / `bulk` を名前の文字列で引いている。`FlowMeta` は入力・出力・パラメータの一覧を持つが、export はそれを使わずにシグネチャから組み立て直す。
  パラメータの情報、シンボルの名前、panic の wrapper、bulk の受け渡しは全て C の生成の中で決めている。`inline_consts`（関数を呼ぶ `const` の初期化式をビルドの時に評価する）は driver の `build` にだけあり、テストの `emit_c` は通らないので、テストとビルドで生成される C が違う。
  R-80 の直し方にあった「定数の畳み込みを Core の pass にする」は、R-80 の決定から漏れていた。
- 決定（2026-10-05）:
  - (1) ターゲットの pass の後に「export の計画」の段を置き、パッケージとターゲットごとに一度だけ作って記録する（計画 D-03 の追記）。シンボル、生成する API と入出力の形、配置への参照、`@param`、panic の扱いと関連するフィールド、関数のシグネチャと panic の通知を持つ。降下が作るフィールドは役割の印で記録し、名前で探さない。
    入出力の役割は `FlowMeta` の明示の一覧から取る。C・WASM・JS・`play`・IDE は計画を読むだけ。R-121 と §11.7 の ID は、計画の中身としてそれぞれの決定で埋める。
  - (2) 定数の評価を、降下と正規化の後・ターゲットの pass の前の一つの段にする（ターゲットによらない。超越関数の扱いは R-108）。R-80 の決定の補い。
  - (3) テストは、ビルドと同じ入口（R-80 (5)）を通り、定数の評価と export の計画まで含める。テストだけが段を飛ばす食い違いを構造で無くす。
- 判断: 直す。(1) ターゲットの pass の後に「export の計画」の段を置き、シンボル・API と入出力の形・配置への参照・`@param`・panic の扱い・関数のシグネチャを一度だけ記録する。フィールドは役割の印で、入出力は `FlowMeta` の一覧で引く。C・WASM・JS・`play`・IDE は計画を読む（R-121、§11.7 の ID は計画の中身として別に決める）。
  (2) 定数の評価を Core の一つの段にする（R-80 の決定の補い）。(3) テストはビルドと同じ入口を通り、全ての段を含める
- 反映: 計画 D-03 に追記（2026-10-05）。実装は (1) W10-01、(2) W9-03、(3) W1-03
