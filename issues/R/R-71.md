# R-71 診断と回復の単位がトップレベルの項目で、正しい関数に偽の連鎖エラーが出る

- 高・直す・観点 1 / 2｜`crates/onsa_syntax/src/parser.rs:257-276`、`:1107`、`:2026`、`crates/onsa_driver/src/lib.rs:299-337`｜§18.1「関数どうしは独立に検査し、全関数分を一度に報告」、T1-7「関数の中では次の文まで」
- impl が 1 単位になる: impl の中の N 個のメソッドの誤りが、合わせて 1 件しか出ない。
- 失敗した項目が AST から消える:
  - `fn f() -> I32 {\n  let = 2\n}` を呼ぶ正しい関数 `g` に、E0302「cannot find `f`」が出る。
  - 修復ループは、正しい `g` を直しに行く。
- 文の単位の回復（T1-7）は未実装である。
- 資料の誤り: `impl-review` P-3 の記述と合わない（§4）。
- 影響: LSP（M7）に要る部分 AST も無い。
- 直し方:
  - 回復点を、impl / trait ではメンバの単位、関数の本体では文の単位にする。
  - 失敗した部分を `Error` ノードとして AST に残す。
  - シグネチャまで読めた関数は、宣言として名前解決に見せる。
  - 診断をまとめる単位を、関数（DefId）にする。
- 範囲（2026-10-04 に追加で確かめた）: シグネチャの誤り（`fn f(a: )`）と struct のフィールドの誤りでも、使う側に E0302 が出る。`}` が一つ足りないと、回復が括弧の深さ 0 に戻らずにファイルの末尾まで読み飛ばし、以降の項目が全て消える（別の関数の E0401 も出ない）。診断も「`fn g` で `(` が要る」で、閉じていない `{` を指さない。
  同じ関数の E0320 が E0002 を隠す（R-69 と同じ形）。6 つの形を `tests/review-phase1/parent/r71/` に置いた。
- 決定（2026-10-04）: 直す。S-59: 単位は宣言（トップレベルの項目と、impl / trait などの各メンバ）。単位の中では構文の診断を優先し、構文の誤りがある単位では本体を検査しない。名前まで読めた宣言は名前解決に見せ、読めなかった部分は誤りの型として連鎖させない。回復は宣言の単位で、閉じていない `{` は字下げで回復点を推定して、開き括弧を指す E0002 を出す。
  文の単位の回復は M7（LSP）で入れ、`Error` の文・式を置ける AST の形は今決める（直し方の「関数の本体では文の単位」を改めた）。
- 判断: 直す。S-59: 診断の単位は宣言（トップレベルの各項目と、impl / trait / effect / handler / extern の各メンバ。impl の見出しの誤りは impl 全体）。単位の中では構文の診断を優先し、構文の誤りがある単位では本体の名前解決と型検査をしない。名前まで読めた宣言は名前解決に見せ、読めなかった部分は誤りの型として使う側に診断を出さない。
  回復は宣言の単位（本体は対応する `}` まで、impl / trait はメンバの単位）。閉じていない `{` は、開いた行と同じか浅い字下げの行頭の項目キーワードで回復し、開き括弧を指す E0002。字下げを見るのは回復だけ（§2.5 に注記）。文の単位の回復は M8。診断を減らす処理は driver の 1 か所へ。再現は `tests/review-phase1/parent/r71/`
