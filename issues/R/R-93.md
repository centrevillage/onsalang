# R-93 評価順が仕様に無く、インタプリタと C で結果が違う

- 高・仕様へ + 直す・観点 1 / 3｜`crates/onsa_interp/src/lib.rs:242`、`:481`、`:635-640`、`crates/onsa_core/src/walk.rs:18`、`crates/onsa_backend_c/src/emit.rs:890-903`、`:962-966`、`:1000`、`:1246-1262`｜§3.4「Rust と同じ」、§13.4（ビット一致）｜再現（親）
- 再現（`next(inout k)` は `k` を 1 増やして返す）:
  - `xs[next(inout k)][next(inout k)]` は、インタプリタが 21、C と Rust が 12。
  - `ys[next(inout k)] = next(inout k)` は、インタプリタが値を先に評価し（Rust と同じ）、C が場所を先に評価する。
  - `f(next(inout c), ps[next(inout c)])` は、C がポインタ渡しの引数を値の引数より先に評価する。
  - `(c as I64) + bump(inout c)` は、C の `is_stable` の誤判定で、インタプリタが 1、C が 101。
  - 添字が二つとも範囲外の `xs[i][j]` では、報告される panic が変わる。
  - `walk.rs` の「評価順」の記述は C と一致し、インタプリタと矛盾する。
- 仕様へ: Rust の規則を書く。
  - 左から右に評価する。
  - 代入は、右辺を先に評価する。
  - 添字の式は、基になる式の後に評価する。
- 直し方:
  - インタプリタと C を、この規則に合わせる。
  - Core の正規化（R-81）で順序を固定し、検証器で検査する。
  - インタプリタと C を比べる差分テストを足す。
- 決定（2026-10-04）: 仕様へ。Rust と同じ規則（S-75、§3.5）。R-81 と一緒に決めた。既存の規則との衝突を確かめた: flow は §11.3 の段の順で、分岐と `&&` / `||` の右辺の中も評価する（§11.5、R-14）。排他性は呼び出しの間について判定する（`xs.fill!(xs.len())` は今も通る）。
  直接構築は、重なるとき一時変数を挟む（S-76）。複合代入は Onsa に無いので、Rust の特例は要らない。短絡評価も書いた。再現は `tests/review-phase1/parent/r93.onsa`（S-75 の期待値で書いた。既存の `core/order*.onsa` は、今の挙動と期待が混ざっている）。
- 判断: 仕様へ。Rust と同じ規則（S-75）: 左から右、代入は右辺が先、添字は基の後、`&&` / `||` は短絡、引数を全て評価してから呼び出す、panic は順で最初のもの、flow は §11.3 / §11.5 に従う。再現は `tests/review-phase1/parent/r93.onsa`
