# R-72 E0010 の修正候補が意味を変える、または不正な形になる

- 高・要判断・観点 1 / 3｜`crates/onsa_syntax/src/groups.rs:29-54`、`:118-119`｜§3.1、§18.1、P8｜再現（親）
- 原因: 「最初に群が変わる位置から、同じ群が続く範囲を括弧で囲む」という独自の規則で、候補を作っている。単体テストは、この出力を期待値にしている。

  | 入力 | 修正候補 | 問題 |
  |---|---|---|
  | `a * b + c * d` | `a * (b + c) * d` | 意味が変わり、しかも検査を通る |
  | `lo <= x && x < hi` | `lo <= (x && x) < hi` | 適用しても E0010 が残る |
  | `a + 1 == b` | `a + (1 == b)` | 型エラーになる |

- 影響: 修正候補は LLM がそのまま適用する前提（P8）なので、意味の違うコードが黙って入る。
- 判断（R-72）:
  - (a) Rust の優先順位で全体を括弧付けした形を候補にする（`(a * b) + (c * d)`）。
  - (b) 意図が一意でないので `fixes` を出さず、メッセージに書き方の例を示す。
  - 推奨は (a)。Rust の読みと一致し、適用後の意味は Rust を知る書き手の意図と同じになる。
- 前提の更新（2026-10-04）: S-45 の後は、上の表の 3 つの入力は全て正しいプログラムになる。今も E0010 になるのは、`&&` と `||`、ビットと他の群、剰余と加法・乗法の混在と、比較の連鎖である。これらは言語によって読みが違うか、よくある読みが誤りの元になる組み合わせで、一つの言語の順位で候補を作ると、E0010 が防ぐ誤読をそのまま適用する。
  (a) の理由（Rust の読み）は推奨の理由に使わない。今の実装の候補は、`a && b || c` → `a && (b || c)`、`x & 1 == 0` → `x & (1 == 0)`、`w + 1 % n` → `w + (1 % n)` で、比較の連鎖とビットの群の連鎖には候補が無い。
- 決定（2026-10-04）: (a) を取り下げ、読みごとに候補を並べる。S-60: 候補は、衝突している群に仮の強弱を置いて式全体を読んだ形で、置き方ごとに一つ。括弧の付け方を全て並べるとカタラン数で増えるのでこの形にした（群は 7 つなので数に上限があり、二つの群なら式の長さによらず 2 つ）。強弱で決まっている部分に括弧を足さず、どの候補も適用後に E0010 にならない。
  違う形が 3 つ以下なら全て並べ、超えれば note だけ。順は、式の中で先に現れる群を強いとした読みを先にする（意図を推す意味は持たない）。比較の連鎖は `a < b && b < c` の一つで、中央が名前・リテラル・フィールドの経路のときだけ。ビットの群の同じ演算子の連鎖は R-123（S-61）で認めた。再現は `tests/review-phase1/parent/r72.onsa`。
- 判断: (a) を取り下げ、読みごとに候補を並べる。S-60: 衝突している群に仮の強弱を置いて式全体を読んだ形を、置き方ごとに一つ（カタラン数の爆発を避け、二つの群なら常に 2 つ）。強弱で決まっている部分に括弧を足さず、適用後に E0010 が残らない。違う形が 3 つ以下なら全て、超えれば note だけ。順は先に現れる群を強いとした読みを先に（意図は推さない）。
  比較の連鎖は中央が名前・リテラル・フィールドの経路のときだけ `a < b && b < c`。再現は `tests/review-phase1/parent/r72.onsa`
- 反映: 仕様 §18.1 に反映済み（2026-10-04）。実装は W3-07（S-45 と同じ回）
