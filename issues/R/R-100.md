# R-100 `vdelay` の `MAX` と F32、状態の大きさの上限

- 低・仕様へ・観点 3｜`crates/onsa_core/src/layout.rs:41`、`lower/flow.rs:431`、`:853`、`:1169`｜§11.4
- `MAX + 1` の溢れ: `vdelay` の `MAX` が `u32::MAX` だと、`MAX + 1` が溢れる。
- F32 での丸め（推測）:
  - F32 で `MAX > 2^24` だと、`MAX as F32` が上に丸まりうる。
  - その結果、添字の計算が下溢して panic しうる。
- 推奨: 次の 2 つを仕様に書き、sema で検査する。
  - 「F32 の `MAX` は 2^24 以下」
  - 「状態が 4 GiB 以上ならエラー」
- 範囲（2026-10-05 に追加で確かめた）:
  - F32 の丸めは推測ではなく起きる: `vdelay(x, 1e9, 16777219, 0.0)`（`F32`）は `check` を通り、実行時に `integer overflow in 0 - 1 (U32)`。`MAX` が `2^24 + 4` に上へ丸まり、`k = MAX + 1` になる。`MAX = 2^24 + 1`（下へ丸まる）では起きない。`F64` では起きない。
  - 大きさの溢れ: 4 GiB の `delay`（`layout.rs:41` の掛け算）、2 GiB の `delay` 2 つ（`layout.rs:111` の足し算）、`F64` の `vdelay` の `MAX = U32.MAX`（`lower/flow.rs:431` の `MAX + 1`）で、`onsa interface` のコンパイラ自体が panic する。どれも `check` は通る。
  - 長さの下限（`N >= 2`、`MAX >= 1`）は E0808 で検査している。大きさの上限は仕様に無い（§4.2 は大きさの型を `U32` とする）。
  - 再現は `tests/review-phase1/parent/r100/`（`delay.onsa` は `check` と `test`、`size.onsa` は `interface`）。既存の `flow/e13/big.onsa` も同じ。
- 決定（2026-10-05）: S-88。
  - (1) `vdelay` の `d` が `F32` なら `MAX <= 2^24`（E0808）。制限は格納する値ではなく、読み出す位置（`d`）の型に掛かる（利用者の確認）。`d` が信号と同じ型なので、今は `F32` の信号に掛かる。`F64` の `d` には掛からない。飽和の比較を丸めた `MAX` で行う案は、意味の崩れた遅延を黙って通すので採らない。
  - (2) 将来の課題: 長いサンプル列は大きな制限なので扱えるようにする。組込みのサンプリングルーパーでは、値は `float`、位置は `uint32_t` や `double` がある（利用者）。API の見直し（値の型と位置の型を分ける、整数の位置で補間しない読み出し、補間の計算の順）が要るので、今は (1) で制限し、§19.1 に挙げた。型の組み合わせを許す方向なので、(1) のコードは壊れない。
  - (3) 型の大きさと flow の状態の各領域は `U32` で表せること。超えたら E0313（新設。点検 C-30、S-142 で E0409 に移した）。配置を計算するとき（ターゲットの pass）に検査し、コンパイラは溢れない算術で計算する。将来上限を変えるにしても、flow と他の型を分ける意味は無い（利用者）。
  - (4) `vdelay` の `MAX + 1` の溢れは (3) で先に止まるので、別の規則は置かない。
- 判断: S-88: `vdelay` の `d` が `F32` なら `MAX <= 2^24`（E0808。制限は読み出す位置の型に掛かる）。長いサンプル列（値と位置の型を分ける）は将来扱えるようにし、API を見直すので §19.1 に挙げた。型の大きさと flow の状態の各領域は `U32` で表せること（超えたら E0313、新設。flow と他の型で分けない）。`MAX + 1` の溢れはこれで止まる。再現は `tests/review-phase1/parent/r100/`
- 反映: 仕様 §4.2 / §11.4 / §19.1 に反映済み（2026-10-05）。E0808 は W7-04、E0409（旧 E0313）は W9-04
