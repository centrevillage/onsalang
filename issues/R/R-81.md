# R-81 Core IR が、評価順・移動・コピー・結果の置き場所・破棄を表さない

- 高・直す + 要判断・観点 2｜`crates/onsa_core/src/ir.rs:151-176`、`:389-400`、`lower/body.rs:770`、`crates/onsa_backend_c/src/emit.rs:888-928`｜D-03、§12.7
- Core に表れていないもの:
  - `let y = move x` と `let y = x` が、同じ `Let(y, Local(x))` になる。
  - 移動の記録は、別の表（`moves`）にある。
  - `Block` / `IfExpr` / `Switch` のように文を含む式が、被演算子や引数の位置に置ける。
- 影響:
  - 巻き上げと評価順の保存は、バックエンドの仕事になっている。
  - C は、出力の文字列の接頭辞（`((int`、`onsa_t`）から「副作用の後でも同じ値か」を推測している（`is_stable`）。これが R-09 と R-93 の誤コンパイルの温床で、JS / WASM でも同じ作業をやり直すことになる。
  - 第 2 期の参照カウント（dup / drop の挿入）と `Drop` も、Core に所有の情報が無いと組めない。
- 直し方:
  - 降下の最後に正規化の段を入れる。被演算子・引数・添字は「場所・一時変数・リテラル」に限り、文を含む式は文の位置にだけ置く（ANF に近い形）。これを検証器で検査する。
  - 移動とコピーを区別して表す。結果の置き場所（sret の宛先）は、降下で一度だけ決めて IR に記録する。
- 判断（R-81）: この変更は、Core の形を変える。第 2 期の前の今、行うか。
  - 推奨は、今行うこと。T4-10（R-90）と同じ回で行う。
- 範囲（2026-10-04 に追加で確かめた）:
  - C の `is_stable` は、出力した文字列の頭（`onsa_t`、`((int` など）で「後の副作用で値が変わらないか」を推測し、後の被演算子が文を出したときだけ前の被演算子を一時変数に取る。`((int` で始まるキャストを「変わらない」とするので、`(c as I64) + set100(inout c)` で誤る（R-93）。
  - `voice.c` の 108 行目（共振フィルタの浮動小数の式）と 331 行目（検査付きの加減算の入れ子）は、どちらも一つの C の式で出ている。
  - 前回示した規則「各ノードで panic しうる子は一つまで」には穴が二つあった。`xs[i][j]` は、外側の範囲検査が内側の結果を待たないので、子とノード自身の検査の順が C で決まらない。`(c as I64) + set100(inout c)` は、書き込みを持つ呼び出しを文の位置へ出すと、左の読み出しを追い越す。
- 決定（2026-10-04）:
  - (1) 正規形は R1〜R4（計画 D-03 の追記）。厳密な ANF にはせず、順序で結果が変わらない純粋な木を残す（DSP の式を読める形で出す）。木の中に書き込みが無く、観測できる演算が一つだけなので、バックエンドは木の評価順を気にしなくてよい。R-93 の 5 つの再現は全てこの規則で Rust と同じ結果になる。演算の分類は Core の一か所と `Prim` の表に置く。
  - (2) 移動・コピー・破棄を全て Core に入れる。元の推奨（破棄は第 2 期）を、利用者の提案で改めた（後の作業で入れ忘れるのを防ぐ）。型ごとの破棄の種類を Core で一度だけ決め、未実装の種類は生成の前に E0200 で知らせる。観測できる効果が無くても、置き場所の誤りは検証器とインタプリタの検査で第 1 期のうちに見つける。参照カウントの実装は、計画 §5 の持ち越しの一覧に載せた。
  - (3) 結果の置き場所を Core に明示する。宛先が構築に使う値（引数、フィールドの値、要素）から読まれうる場合は、一時変数に作ってからコピーする（S-76、§12.7）。判定は §5.2 と同じで、関数は sema の E0702 と共有する。値で返す形（C の `x = swap2(&x)`）にしないのは、C がコピーの省略を保証せず、一つの関数の呼び出し規約は一つで、重なる場合は値で返してもコンパイラが同じ一時領域を作るため（利用者の問いに答えた）。
  - (4) 評価順は R-93 で Rust と同じ規則に決めた（S-75、§3.5）。既存の規則との衝突は無く、flow（§11.3 / §11.5）、排他性（§5.2）、直接構築（§12.7）との関係を §3.5 に書いた。
  - (5) 時期は、レビューを全て終えた後に改めて決める（§6 の判断は保留）。進め方は R-06 と同じ（設計メモ → 最も能力の高いモデル → 別のエージェントが仕様だけからテストを書いて壊しにいく）を、R-81 の全体に当てはめる。
  - 利用者の方針: 表現（IR の構造、表の欄など）は先に入れ、実装していない所は黙って通さず E0200 で知らせる（R-79 (3) と同じ考え方）。後の作業で入れ忘れるのを、構造で防ぐ。
- 判断: (1) 正規形 R1〜R4（書き込みと文を含む式は文の位置だけ、式の木の効果は一つまで、評価順に並べて書き込みの前の読み出しを先に出す、条件の内側は内側に）。(2) 移動・コピー・破棄を Core に入れ、破棄の種類を一度だけ決め、未実装は E0200（元の推奨を利用者の提案で改めた）。参照カウントは計画 §5 の持ち越しへ。
  (3) 結果の置き場所を明示し、構築に使う値と重なれば一時変数（S-76）。(4) 評価順は S-75。(5) 時期はレビュー後に決め、R-06 の進め方を当てはめる。方針: 表現は先に入れ、未実装は E0200 で知らせる
- 反映: 仕様 §12.7 に反映済み、計画 D-03 / §5 に追記（2026-10-04）。実装は W8（W8-01 の設計メモ、W8-03〜W8-05）
