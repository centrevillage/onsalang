# R-84 名前解決が型付けに絡み合い、段の順序が仕様の要求に合わない

- 中・直す・観点 2｜`crates/onsa_sema/src/body.rs:935-1003`、`:1937-2014`、`:1046`、`:2206`、`:1539`、`flow.rs:603-640`、`sig.rs` 全体
- 解決の手順が 5〜6 か所にある: 「先頭がローカルか、モジュールの経路か、組込みの関連項目か」の判定を、`check_chain`、`check_call` の 2 経路、`value_of_entity`、`flow.rs` などで個別に書いている。
- 影響: 第 2 期で増える名前（効果の操作 `Fs.read`、`T.ZERO`、trait のメソッド、`Map.new`）は、これら全部に手を入れることになる。
- `sig.rs`（1618 行）が抱える責務: モジュール木、prelude、収集、import、型の降下、flow API の生成、`@param` を一続きに行う。名前空間の中身を作るのが import の後なので、R-50 になる。
- `lower_type_in_body` の作り: `Analysis` を `mem::take` で取り出す。
- 直し方:
  - 呼び出し先と経路を一度だけ `Callee` / `PathTarget` の列挙値に解決する段を、型付けの前に分ける。
  - `sig.rs` を、収集・import・型の降下・flow API に分割する。
- 範囲（2026-10-05 に追加で確かめた）: 経路の先頭の判定は、`check_chain`（値になる最長の頭を探し、無ければ「組込み型 + 関連定数」を試す）、`check_call`（メソッドの枝で「組込み型 + 関連関数」を試す。単一の名前の枝もある）、`check_flow_call`（予約名を文字列で判定）、`value_of_entity` に分かれ、次を試す順序が箇所ごとに違う。
  同じ単位に型の誤り（3 行目）と名前の誤り（4 行目）があると、今は位置が先の型の誤りを報告する。再現は `tests/review-phase1/parent/r84.onsa`。
- 決定（2026-10-05）:
  - (1) 名前の解決を、型付けの前の一つの段にする（計画 §3.3、D-15）。経路の先頭、名前空間の経路、列挙子、型の関連項目、flow の予約名をこの段で決めて記録し、値の後のフィールドとメソッドの呼び出しだけを型付けに残す。型付けは記録を読み、解決をやり直さない。
  - (2) 検査の段の順を「構文 → 名前 → 型 → 引数のモードと移動 → rt と効果」に改めた（S-78、§18.1）。名前の誤りがある単位では型検査をしない。段を分けた構造に、位置の順を再現する例外を作らない。
  - (3) R-103 を (a) で一緒に決めた（S-79）。
  - (4) `sig.rs` を、収集（名前空間の表を含む）、`use` の解決、署名の型の降下、flow の生成項目の型と `@param` の段に分け、各段は前の段の表を受け取る（計画 §3.3）。本体の型付けは署名の表を読み取り専用で参照し、`mem::take` を無くす。
- 判断: 直す。(1) 名前の解決を型付けの前の一つの段にし、型付けは記録を読む（D-15）。(2) 検査の段の順を「構文 → 名前 → 型 → …」に改めた（S-78）。(3) R-103 は (a)（S-79）。(4) `sig.rs` を収集・`use`・署名の型・flow の生成項目の段に分ける。再現は `tests/review-phase1/parent/r84.onsa`
