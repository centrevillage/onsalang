# R-133 仕様の意味が Rust を規範として参照している。NaN のビット表現が決まっていない

- 高・要判断・観点 3｜`spec/` §3.3、§3.4、§13.4｜§0.3、P9
- 内容:
  - §3.4 は整数と浮動小数の演算の意味を「Rust と同じ（例外は `MIN % -1` を 0 とする点だけ）」と、Rust を規範として参照している。§3.3 の `as` も「Rust と同じ意味を持つ」とする。
  - Rust の意味は版で変わりうる（浮動小数から整数への `as` は Rust 1.45 より前は未定義動作で、以後は飽和）。Rust が決めていないものもある（演算の結果の NaN の符号とペイロード）。Onsa は既に Rust と違う所がある（`min` / `max` の NaN は S-25 で WASM の意味、整数の溢れは常に panic）。
  - Onsa は全ての変換先でのビット一致を約束する（§13.4）が、NaN のビット表現は x86、ARM、WASM で違い、`(0.0 / 0.0).to_bits()` は変換先で違う値になりうる。
  - 利用者の指摘（2026-10-06、Q-02 の議論）: 「Rust と同じ」という規則は Rust の版などに影響されないか。コンパイラの実装を Rust から変えるときにも、特定の言語の環境を基準として残すのは危うい。
- 判断（R-133）: 論点を整理してから決める。
- 経緯: Q-02 の議論で見つけた（2026-10-06）。テストの参照は、仕様から作るテストベクトルにすると決めた（Q-02、計画 D-16）。
- 範囲（2026-10-06 に追加で確かめた）:
  - 規範として Rust を参照しているのは §3.4（演算の意味）、§3.3（`as` は「Rust と同じ意味」）、§6.3（標準 trait の「名前と意味は Rust と同じ」）。他の十数か所は、規則を本文に書いたうえで添えた補足。
  - `(z / z).to_bits()` と `(-(z / z)).to_bits()` を比べると、インタプリタ（arm64）は `0x7FC00000` / `0xFFC00000`、clang の arm64 は `0x7FC00000` / `0x7FC00000`（否定の符号が消える）、clang の x86_64（Rosetta）は `0xFFC00000` / `0xFFC00000`、gcc-15 の arm64 は `0x7FC00000` / `0xFFC00000`。
    再現は `tests/review-phase1/parent/r133/`。
- 決定（2026-10-06）: S-106。
  - (1) §3.4 を、整数・浮動小数・変換の規則の表に書き直した（意味は変えない）。Rust との関係は参考にした。この表が Q-02 (a) のテストベクトルの元になる。
  - (2) NaN の符号とペイロードは演算の結果として未規定。`to_bits()` は NaN を正の quiet NaN にそろえて返す（(b)）。Onsa のプログラムから NaN のビットが見えるのは `to_bits()` だけなので、見える振る舞いは全て決定的になる。ホストに渡る NaN は NaN であることだけを約束し、適合性テストは NaN どうしを等しいとして比べる（§13.4）。全ての演算の後にそろえる案は重いので採らなかった。
  - (3) §0.3 に「既存の言語を挙げる記述は参考で、規範は本文の規則」と書いた。§3.3 の `as` の文を参考の形にし、§6.3 に等値・順序・ハッシュの約束を書いた。
- 判断: S-106: §3.4 を整数・浮動小数・変換の規則の表に書き直し、Rust との関係は参考にした（利用者の指摘: 「Rust と同じ」は版に影響され、実装の言語を変えるときに危うい）。NaN の符号とペイロードは未規定で、`to_bits()` は正の quiet NaN にそろえる。ホストに渡る NaN は NaN であることだけを約束。
  §0.3 に参考の一文、§3.3 の `as` の文は参考に、§6.3 に等値・順序・ハッシュの約束。再現は `tests/review-phase1/parent/r133/`
