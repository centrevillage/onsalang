# R-82 Core の検証器が弱く、debug ビルドでしか動かない

- 高・直す・観点 2｜`crates/onsa_core/src/verify.rs:31`、`:186-193`、`:342-347`、`:357-367`、`lower/mod.rs:147`
- 検査していない不変条件:
  - 局所変数の宣言とスコープ。定義済みの記録は平らで、分岐の中で定義したものを外で読んでも通る。代入でも定義済みになる。
  - Prim の引数と結果の型
  - `as` が §3.3 の表で許される変換か
  - 代入先が可変か
  - `flows` のメタデータ
- 動く条件: `cfg!(debug_assertions)` のときだけ動き、失敗すると panic する。
- 影響: R-06 はここを通った。R-03 の入力は、release では検査されずに誤ったコードになる。
- 直し方:
  - Prim ごとのシグネチャの表、スコープ付きの定義、sema と共有する `as` の表を入れる。
  - テストでは常に検証器を走らせ、失敗は内部エラーの診断として報告する。
- 範囲（2026-10-05 に追加で確かめた）: 借用で受け取った引数への代入も通る（Core のローカルに、書き込めるかの情報が無い）。プリミティブは `Prim::BufZeroed` だけを名前で特別扱いしている（R-79 と同じ問題）。テスト（debug）でも、失敗は内部エラーではなく panic になる。R-81 / R-80 / R-79 の決定で、正規形・所有・結果の置き場所・ターゲットの pass の記録の検査が加わった。
- 決定（2026-10-05）:
  - (1) 常に（release も）段の境目ごとに走らせる（降下と正規化の後、ターゲットの pass の後）。失敗は内部エラー（S-67）で、破った規則の番号・関数名・Core の位置を報告し、その関数の Core のダンプを残す。利用者の手元で誤ったコードが黙って生成されるのを防ぐ。費用は実装の段で計測する。
  - (2) 規則を番号付きの一覧（V-01〜V-16、計画 §3.4）にし、規則ごとに、その規則だけを破った Core を拒む否定のテストを置く。
  - (3) 段の原則を計画 D-15 に書いた: 各段は同じ処理を繰り返さず、後の段は前の段が出力した構造を受け取って次の構造を出す。検証器は前の段の出力の構造から性質を確かめ、処理も計算もやり直さず、前の段が構造の外に残した途中の記録には頼らない。元の案では「検証器の独立性」と呼んだが、利用者の指摘で改めた（独立性と書くと「他の段に頼らず自分で計算する」と読め、同じ処理を複数の段で作り直すことになる。本質は、各段が同じことをせず、処理済みの構造をもとに次の段が進むこと）。
- 判断: 直す。(1) 常に（release も）段の境目ごとに走らせ、失敗は内部エラー（S-67）。(2) 規則は番号付きの一覧（V-01〜V-16）で、規則ごとに否定のテスト。(3) 段の原則（D-15）: 各段は同じ処理を繰り返さず、後の段は前の段が出力した構造を受け取る。検証器は構造から性質を確かめ、処理も計算もやり直さない（「独立性」という元の言い方を、利用者の指摘で改めた）
- 反映: 計画 D-15 / §3.4 に反映（2026-10-05）。実装は W1-05（テストで常に）、W8-02（V-01〜V-14 と release）、W8-07（V-17）、W9-04（V-15 / V-16）
