# R-113 テストが、意味の誤りを検出できる形になっていない

- 中・直す・観点 2｜`crates/onsa_tests/tests/conformance.rs:229-300`、`:266-271`、`tests/poison.rs:44-52`、`tests/c_compile.rs`、`crates/onsa_core/src/tests.rs`、`crates/onsa_interp/src/tests.rs`、`crates/onsa_syntax/tests/fmt_spec.rs`、`groups.rs:118-119`、`tests/spec/`
- **適合性テスト**:
  - 同じ Core から出たインタプリタと C を比べるので、降下の誤り（R-06〜R-08、R-13〜R-17）は両方に同じように出て一致する。
  - `Init` 入力を持つ flow と、出力が F32 でない flow を、件数も出さずに飛ばす。
  - C とインタプリタを比べるのは flow の `render` だけである。整数、変換、`narrow` / `checked` / `div_euclid`、export 関数は一度も実行していない。
- **期待値付きのテスト**:
  - 手で期待値を書いた意味のテストが少ない。`mode: test` は 3 ファイルである。
  - 無いもの: `prev` の入れ子、分岐の中のインスタンス、`par` の look-back、`vdelay` の端点と NaN、`reset` の後の再現、平面の入出力、`match` の各形、評価順、無名関数と `?`、64 ビットの境界
- **Core のテスト**: dump の文字列の部分一致の照合が中心である。
- **fmt のテスト**:
  - 正規形の仕様の例が変わらないことしか見ていない。
  - 正規形でない入力で AST が変わらないことを、検査していない。
- **誤った期待値**: `groups.rs` の単体テストは、誤った修正候補（R-72）を期待値にしている。
- **否定例の数**: E0003、E0011、E0012 は各 1 件で、T1-11 の「各 3 つ以上」に届かない。
- **C のテストの条件**:
  - `cc` が無いと、C のテストは全て黙って成功する。
  - C のコンパイラは clang だけで、GCC、C++、sanitizer では一度も通していない。
- **poison のテスト**: 戻り値しか見ていない。
- 直し方:
  1. `tests/spec/test/` に、期待値を手で書いた意味のテストを足す（上の一覧）。Core とは独立した意味の基準になる。
  2. スカラの export 関数を境界値で呼び、`onsa test` の値と比べる、インタプリタと C の差分テストを足す。整数型ごとの境界値は、表で駆動する。
  3. C のテストを UBSan 付きでも実行し、GCC でもコンパイルする。`cc` が無いときは失敗にする。飛ばした flow の数を表示する。
  4. `tests/spec` の全ファイルに空白・改行・コメントの摂動を加えて fmt し、S-56 の比較で元と同じプログラムであることと、もう一度 fmt しても変わらないこと（冪等性）、各コメントが同じ要素の行に残ること（S-58）を確かめる性質テストを足す。あわせて、CST を出力すると元のソースと 1 バイトも違わないこと（R-86）を確かめる。
  5. 検証器は、テストでは常に走らせる（R-82）。
- 決定（2026-10-05）: 進め方を決めた。直し方の大部分が `process-improvement-phase1.md` の Q-01〜Q-08 と重なる（1 は Q-01、2 は Q-02 / Q-03、3 は Q-07、4 は Q-03、5 は Q-06、golden は Q-04、まとめて回す検査は Q-08）ので、R-113 は Q-01〜Q-08 と一緒に、Q の議論の段で一つの設計として決める（同じことを二度決めない）。§7 の第 1 段であることは変わらない。
  - 判断の要らない直し（記録）: 適合性テストが flow（`Init` の入力を持つもの、出力が `F32` でないもの）を黙って飛ばすのをやめ、飛ばした数を表示する。`groups.rs` の誤った期待値を R-72（S-60）に合わせる。否定例を各コード 3 つ以上（T1-11）にし、数を自動で数える検査を足す。
    poison のテストで、出力のゼロ埋め、以後の無音、`reset` での復帰も確かめる。レビューの再現の入力を回帰テストにする（§7）: 各 R を直すときに、再現の入力の「期待」を `tests/spec` の形式（`//~ E0xxx` のマーカ、`mode: test`）の期待値付きテストに移す（コメントの形のままでは自動で確かめられない）。
  - 決定（2026-10-06）: Q-01〜Q-08 と一つの設計として決めた（`process-improvement-phase1.md` §4、計画 D-16）。Q-02 (a) は、Rust のプログラムを参照にする代わりに、仕様から作るテストベクトルをデータとして持つ形に改めた（利用者の指摘: 「Rust と同じ」は Rust の版に影響され、実装の言語を変えるときに危うい）。仕様の側の自己完結は R-133 として登録した。時期は §7 の第 1 段に書いた。
