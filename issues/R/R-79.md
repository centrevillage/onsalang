# R-79 組込みの知識が、名前の文字列で 6 か所以上に散っている

- 高・直す・観点 2｜各項目に記す
- 散っている場所:
  - `onsa_sema/src/builtin.rs` の文字列の表
  - `body.rs:670` の trait の表
  - prelude
  - std の `target fn`
  - Core の `Prim::Std("std.<module>.<name>")`（`lower/body.rs:1258-1261`、`:1355-1386`）
  - インタプリタが名前で実行する箇所（`onsa_interp/src/lib.rs:1134`）
  - C のヘルパ
- 名前の文字列で分岐している箇所:
  - `name == "zeroed"` が 3 か所にある。
  - Option か Result かを、先頭の列挙子名 `"None"` で判定している（`lower/body.rs:1031`、`:1470`）。
- 影響:
  - std に `target fn` を足すと、降下は黙って `Prim::Std` を作る。インタプリタでは実行時に panic し、C ではビルド時に E0200 になる。
  - `prim.rs` の冒頭の方針（表に無いものはテストで落ちる）と合わない。
  - メソッドを一つ足すのに、4 か所以上を触る必要がある。
- 直し方:
  - sema で、組込みを列挙値（`Prim` 相当）に解決し、Core へ渡す。
  - 組込みの型、メソッド、trait の実装を一つの表に集める。std の `impl` に書けるものは std に書く。
  - Option / Result の種別は `TypeDef` に持たせる。
- 範囲（2026-10-04 に追加で確かめた）:
  - sema（`builtin.rs`）と降下（`lower/body.rs:1318-`）が、同じ振り分けを 2 回行う。`narrow_*` は、sema が `format!` で作り、降下が `starts_with` と `IntKind::parse` で読み直す。
  - `Buf.zeroed` の rt と `Alloc` は、`rt.rs:186` と `effects.rs:70` に名前で書いてある。表に rt と効果の欄が無い。
  - `gen.u32(0, 9)` を呼ぶテストは `check` を通り、`onsa test` の実行時に落ちる（他のテストは走る）。`assert_near` を export する関数で使うと、`onsa build` で E0200。再現は `tests/review-phase1/parent/r79/`。
  - 仕様の空白（観点 3）: §15.2 は `bind` だけを書き、std の `target` 宣言を誰が与えるかは計画の D-07 にしか無い。
  - 議論の中で R-125（テスト用の補助を呼べる範囲）と R-126（組込みのメソッドの一覧が閉じていない）を見つけた。
- 決定（2026-10-04）:
  - (1) 組込み型のメソッド・関連関数・関連定数は、std の `impl` に Onsa で宣言する。他の操作で書けるものは本体ごと std に書き、プリミティブだけを `target` にする（D-07 を広げた）。元の推奨（Rust の表に集める）を改めた。
    利用者の問い「今後 std に足していくとき、管理しやすいのはどちらか」への答え: 第 2 期に足す API（`Str`、`Map`、`Set`、`Array`、`Bytes`）の大半は組込み型のメソッドで、表に持つと全てがプリミティブになり、各バックエンドで実装し直すことになる。
    std に書けば、Onsa で書けるものは一度で全ての変換先に効き、シグネチャ・rt・効果・引数のモード・doc を通常の規則で持て、API の追加が std の差分として見える。§6.6 の `impl F32` の例と R-104 の推奨から、新しい構文は要らない。`[T; N]` と `Buf[T]` の受け手は `Span[T]` のメソッドを引く（§5.3）。
    Rust に残す表は、std の `target` 宣言の修飾名 → `Prim`（1 対 1 をテストで確かめる）、§6.3 の trait（第 1 期の暫定。第 2 期に std の `impl` へ、R-127）、§3.3 の `as`、Option / Result の lang item（S-71）、`array.from_fn` の展開だけ。
  - (2) Option / Result の種別は Core の `TypeDef` に持たせる。std の enum にはしない（言語の設計で既に特別扱いされていて、利用者の定義する Option / Result は今のところ要らない）。→ 同日に改めた（下の改定、S-71）。
  - (3) 実装の無い組込みは、降下の後、実行や生成を始める前に、各バックエンドの対応表と照らして E0200（機能名と変換先）にする。インタプリタも同じ。各バックエンドは `Prim` を `_` 無しで網羅する。
  - (4) S-69: std の `target` 宣言は処理系が与え、`bind` では差し替えられない。全ての変換先が与えるのが原則で、この版で与えない変換先では E0200（§15.2）。R-104 も (a) で同時に決めた（S-70）。
  - 利用者の方針: この段の目的は今のコードを綺麗にすることだけでなく、保守を続けるための硬い土台づくりで、将来の修正を常に考えに入れる。
  - 順序: R-126 で組込みのメソッドの一覧を閉じてから、std に宣言する。
- 改定（2026-10-04）: (2) を改め、Option / Result を std の enum として宣言する（S-71）。
  利用者の問い「今の決定を受けて、Option / Result の扱いも考え直す必要はあるか」への答え: (2) を推した理由は「`?`、修飾の無い列挙子、`narrow_*` / `get` / `checked_*` の返り値は結局 Option を知る必要がある」だったが、(1) で返り値は std のソースに書くことになり、コンパイラが知る必要があるのは prelude と `?` だけになった。
  - 確かめた事実: 特別扱いは sema と Core の 9 ファイル・約 60 か所にある。Option を返すプリミティブは、インタプリタと C の両方で列挙子の番号と配置を直書きしている。特別な経路と一般の経路が別で、`let o = Some(1.5)` は通るのに `let m = Maybe.Just(1.5)` は E0406 になる（R-53 と同じ原因。再現は `tests/review-phase1/parent/r79_enum.onsa`）。
  - 言語の上の扱い（prelude、修飾の無い列挙子、`?`、利用者が Option / Result を定義できないこと）は変わらず、コンパイラの中での表し方だけを変える。コンパイラは lang item の表（std の経路 → 役割）の 2 行で知り、sema が `?` ごとに列挙子の番号を決めて Core に渡す。
  - std の `target` 宣言の引数と返り値に Option / Result を使わず、バックエンドは Option の配置を知らない。§6.3 の Option / Result の行は derive の帰結になり、R-120 は構造上起きなくなる。実装は第 4 段（第 2 段で R-53 を直した後）。
- 判断: (1) 組込み型のメソッド・関連関数・関連定数は std の `impl` に Onsa で宣言し、プリミティブだけを `target` にする（D-07 を広げた。元の推奨の Rust の表を改めた。今後の API の追加で、Onsa で書けるものは全ての変換先に一度で効き、シグネチャ・rt・効果・doc を通常の規則で持てる）。
  Rust に残すのは修飾名 → `Prim` の表（1 対 1 をテストで確かめる）、§6.3 の trait（第 1 期の暫定。第 2 期に std の `impl` へ、R-127）、§3.3 の `as`、Option / Result の lang item（S-71）、`array.from_fn` の展開。
  (2) Option / Result は std の enum として宣言し、コンパイラは lang item の表（prelude と `?`）だけで知る（S-71。当初の「Core の `TypeDef` に種別」を同日に改めた。再現は `tests/review-phase1/parent/r79_enum.onsa`）。
  (3) 実装の無い組込みは、実行・生成の前に E0200（各バックエンドは `Prim` を網羅）。(4) S-69: std の `target` 宣言は処理系が与え、`bind` で差し替えられない。全ての変換先が与えるのが原則。R-125、R-126 を登録した。再現は `tests/review-phase1/parent/r79/`
- 反映: 仕様 §4.1 / §6.3 / §15.2 に反映済み（2026-10-04）。計画 D-07 に追記。実装は W5-02（R-126、R-53 の後）
