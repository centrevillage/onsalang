# R-243 呼び出しの深さの上限の説明の表が測った値と合わず、スタックの量のテストの余裕が debug で約 1.2% しかない

- 場所: `crates/onsa_interp/src/lib.rs` の `MAX_CALL_DEPTH` の説明の表、`crates/onsa_interp/src/tests.rs` の `measure_the_stack_of_calls_and_levels`（486 行の `assert!(at_limit * 2 <= budget, …)`）
- 内容: 説明の表（debug の 1 呼び出し 1.0 K、上限の場合 27 MB など）が、測った値（debug の 1 呼び出し 1198 B、1 段の最大 951 B、128 呼び出し × 256 段で 31.08 MB）と合わない。assert の余裕は debug で約 1.2%（62.15 M / 62.91 M）で、インタプリタの小さな変更やツールチェーンの更新で落ちうる。
- 経緯: X-6 の I（`onsa_interp/src/lib.rs` の分割、2026-10-19、44 回目）の担当が測って見つけた。基のバイナリ（`0c22312`）でも同じで、分割では入っていない（release は X-6 I で `codegen-units = 1` にして基より小さくなった）。
- 判断（2026-10-19、親）: 直す。表を測り直し、余裕の取り方（予算か上限の場合の形）を決める。担う作業は無いので、時機は X-6 の後のインタプリタに触れる作業か、区切りのリファクタリングで決める。
- 補い（2026-11-02、親）: 直す作業を W9-03 にした（W4 の終わりの文書の点検、利用者が了承）。W9-03 の `内容` は、全ての環境で 128 に届く評価器の形（自分のスタックを持つなど）を決めるので、スレッドのスタックの量に頼らなくなれば表と余裕の問題が消える。2026-11-02 に測った値（debug、`match` の形）は 1 呼び出し 959 B、1 段 944 B、128 呼び出し × 256 段で 31,067,541 B（半分の線 31,457,280 B、余裕は約 1.2% のまま）。それまでに余裕が尽きればテストが落ちるので、その作業でスレッドのスタックを増やす
