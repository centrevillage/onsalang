# R-391 Core が型を木のまま写すので、具体化の上限の内でも降下のメモリが機械を超える形がある

- 場所: Core の型の持ち方。`crates/onsa_core/src/ir.rs` の `Expr.ty`・`Local.ty`、`lower/mod.rs` の `fn_ids` の鍵と `worklist`、`moves.rs` の `MoveSite { fn_name, ty }` が `Ty` の木と名前の文字を値で写す。`check` の段は `onsa_sema::ty::Types` で型を共有するので当たらない。
- 内容: 上限の内でも、降下のメモリは「具体化の数 × 本体の式の数」に比例し、型が大きいとさらに増える。超えても診断は出ず、OS に殺されるかスワップで固まる。
  模型（2026-11-07、debug の `onsa`。`issues/R/R-391/gen3.py` で作り、`interface` で測った）: 小さな型は 1 具体化 7 KB ＋ 使用 1 回 1.6 KB、大きな型（約 2000 節）は 1 具体化 0.3 MB ＋ 使用 1 回 0.1 MB。

  | 入力（`gen3.py` の引数） | 具体化 | 最大メモリ | 時間 |
  |---|---|---|---|
  | `fork_small 12 100`（ソース約 30 KB） | 8192 | 1404 MB | 8 秒 |
  | `fork_small 13 100` | 16384 | 2950 MB | 18 秒 |
  | `fork_big 8 20` | 512 | 1220 MB | 12 秒 |

  65536 個なら、小さな型で百行級の本体が約 12 GB、大きな型の二股が約 20 GB の見積もりである。§4.4 と §4.5 はメモリを約束していないので、仕様の誤りではない。
  ふつうの誤りは E0422 で止まる。リポジトリの具体化の最大は 262 で、普通の型は 10 節以下である。`Some(x)` のように宣言した型で包むと、Core では葉になるので写しが縮む。
- 直しの形: W8-01 で Core の型を sema の `Types` と同じく id で引く形にする（`measure` も O(1) になる）。`MoveSite.fn_name` は `FnId` にする。残る本体の分は単相化の出力に比例する。
  比べの入力は `fork_big 8 0`（512 具体化、今 166 MB）。
