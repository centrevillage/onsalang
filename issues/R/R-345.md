# R-345 診断のテキストの表示が診断ごとにその行の全文を出すので、長い一行に診断が多いと出力とメモリが診断の数と行の長さの積で増える

- 場所: 診断のテキストの表示（`onsa check` などの `--json` でない出力）。診断ごとに、その位置の行の全文を引いて出す。
- 内容: 長い一行に診断が N 個あると、出力とメモリが N と行の長さの積で増える。`provides = [0, 1, …, N-1]`（一行、要素は全て整数）は要素ごとに E1103 なので、N = 2000 で出力 32 MB（`--json` は 0.6 MB）、N = 8000 で 560 MB・最大メモリ 1.1 GB、N = 30000 で 10 秒・7.4 GB（W4-02 U2b1 の壊す側）。
  前からある表示の形で、U2a2 の E1102 も `memory = { z0 = 1, …, z7999 = 1 }`（一行）で前も後も 2.1 GB。U2b1 で配列の要素ごとに診断を出すようになり、当たりやすくなった。現実の入力は数百要素までで、実害は小さい。
- 経緯: 97 回目（2026-11-01）、W4-02 U2b1 の壊す側（低 1、`P97/w402u2b1/b/big2.py`）。親が `P97/bin/onsa-w402u2b1` で N = 2000 を再現した（テキスト 32,312,400 バイト、`--json` 636,729 バイト）。
- 判断: 直す時期と形（同じ行の診断の行の引用をまとめる、長い行を切って示す、件数の上限）は段の終わりの見直しで決める。§18.1 は件数の上限と行の表示の省略を決めていない。
- 補い（2026-11-01、親）: W4-02 U3a（98 回目）から、ターゲットの `provides` の `Alloc` 以外の要素がビルドの E0200 になり、`build --target` も同じ形に当たる。一行の `provides` に 8000 要素で出力 752 MB・最大メモリ 1.4 GB、10 万要素で 6.9 GB（壊す側の低 2、`P98/w402u3a/b/`）。前は最初の一つの使い方の誤りで止まっていた。
- 補い（2026-11-01、親）: 直す時期と形を決める「段の終わりの見直し」は W4 の見直しの W4-18（99 回目の文書の点検の 3-G）。
- 判断（2026-11-01、親）: 100 回目（2026-11-01、W4-18 の前の洗い出しの B5、利用者が了承）: テキストの引用行は、範囲の周りの一定の幅（約 120 字）だけを出して切った端に `...` を付け、`^` の位置も切り出しに合わせる。制御文字は見える一字の絵（ESC → `␛`、Unicode の制御文字の絵）に置き換え、一字を一字にして `^` の位置を保つ。候補の行の文字列にも同じ置き換えを当てる。仕様（`spec/tools.md` §4）は引用行の形を約束しないので仕様は変えない。参考: rustc 1.94.1 が同じ形（長い行の `...` と `␛`）。W4-18 で直す。
