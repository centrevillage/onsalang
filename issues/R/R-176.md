# R-176 `?Dup` の型パラメータを含む利用者の型が `Dup` の要求を通る

- 中・直す・観点 1｜型（種の制約）｜§4.5、§4.6
- 内容: `pub struct Wrap[T: ?Dup] { x: T }` の `Wrap[U]`（`U: ?Dup`）は `U` が Affine でありうるので Dup でないが、`need_dup(w)` や `[w; 2]` が通る。種を求める処理が型パラメータを含む利用者の型で種を返さず、要求の検査がそれを「満たす」と扱う。HEAD の modes の E0711 も同じ穴を持っていた。再帰する型も同じく通る。
- 経緯: W2-06/b が見つけた（2026-10-08）。
- 決定（2026-10-08、親）: 直す。型パラメータを含む型の種を、各引数の境界（`?Dup` かどうか）から求める。種の制約を扱う W5-08 で、R-172 と同じ回に行う。それまでの事例は実装待ちの一覧に載せる。
- 判断: 直す（親、仕様が明確）。`?Dup` の型パラメータを含む利用者の型の種を、引数の境界から求める。W2-06/b で見つけた
- 反映: 実装は W5-08
- 補い（2026-10-29、親）: 82 回目の W4-05 U4a/b（onsa-break）: 同じ仲間の形として、`?Dup` の型パラメータや Affine を持つ利用者の型を含むタプル・配列・`Result`（`W[[U; 2]]` の `U: ?Dup`、`C[(Y, Q)]`、`Array[Result[Y, Q]]` の `Q` が `Buf` を持つ struct）は、`kind_of` が `None` で `Copy`・`Dup` を通す。前のバイナリの本体も同じ。
- 補い（2026-10-30、親）: W4-16 U3（85 回目、壊す側の F3）: R-30 の後、`tests/spec/negative/dup_maybe_dup_param.onsa` の `repeated`（`[w; 2]`、`Wrap[U]`、`U: ?Dup`）は E0711 で、候補「`move` を足す」を当てると `[move w; 2]` で診断が 0 件になる（前は何も出なかった）。
  W5-08 で型の段の E0416 を入れると、modes より先に出て候補も付かない。
- 判断（2026-11-05、親）: W5-03 U4 の壊す側で再び確かめた: `Option` が std の enum になり、`Option[U]` も同じ道である。`fn two[T](x: T) -> (T, T) { (x, x) }` に `fn bad[U: ?Dup](w: W[U]) -> (W[U], W[U]) { two(w) }` で渡し、`W[Buf[F32]]` で呼ぶと、`check` が通り `onsa test` で同じ `Buf` が二つになる。`h[T: Copy]` に `Option[U]` を渡す形も E0416 にならない。実害があるので W5-16 で種を計算できない形を通さない。
- 判断（2026-11-05、親）: 時期を改めた（利用者「手戻りがないタイミングで対応しましょう」）。W5-20 に分け、W5-04 の後、W5-05 の前に行う。W5-05 以降の std の総称のコードがこの穴に頼らないようにするため
