# R-343 固定の長さの配列の `.len()` の降下が受け手の式を評価せずに捨てる

- 場所: Core への降下 `crates/onsa_core/src/lower/body/call.rs:371-378` の `len_of`（`Ty::Array(_, n)` の枝が `u32_lit(span, *n)` を返し、受け手の式 `recv` を捨てる。`is_empty` も同じ所を通る）
- 内容: 受け手が固定の長さの配列の `.len()`（と `.is_empty()`）は、降下で長さのリテラルに置き換わり、受け手の式を評価しない。§3.5 は「呼び出しは呼び先の式、レシーバ、引数の順に評価する」とする。
  再現 `issues/R/R-343/len_receiver.onsa`: `fn boom() -> [U32; 3] { assert false … }` に対し、`assert boom().len() == 3` のテストは ok（受け手の `assert false` が走らない）。
  `let xs = boom()` に束ねてから `xs.len()` と書くと、仕様どおり失敗する。
  `dump --core` では `if (!(3:U32 == 3:U32))` になり、`e.boom()` の呼び出しが無い。
  同じ理由で、受け手の中の届く範囲の E0200（§15.2）も出ない（`gen.u32` を使う関数の `digits().len()` は E0200 にならず ok）。C の出力も同じ Core から作るので、受け手の panic と副作用（`inout` の引数など）が消えると見込む（C では確かめていない）。
- 経緯: 95 回目（2026-11-01）、W4-15 U1/b（壊す側）が届く範囲の E0200 の形として見つけ（前からの挙動、dev の `020e8fae` でも同じ）、親が panic の形で再現して原因の行を確かめた。
- 判断: 直す（親）。黙って実行の結果を変える（失敗するはずのテストが通る）。受け手を評価してから長さを使う降下にする。評価順を担う W8-03 で直す
