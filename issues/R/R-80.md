# R-80 同じ判断を複数の場所で行っており、片方だけが直る

- 高・直す・観点 2｜各項目に記す
- 重複している判断:
  - **配置の計算**: `onsa_sema/src/layout.rs`、`onsa_core/src/layout.rs`、`onsa_backend_c/src/emit.rs:229` の 3 か所。sema は `checked_add` を使い、core は検査しない。C は `FlowMeta.layout` を使わずに計算し直す。値が食い違うと、Onsa 側の `voice.SIZE` とヘッダの `SIZE` がずれる。
  - **NRVO の判定**: `onsa_core/src/lower/moves.rs:182`（監査用）と `onsa_backend_c/src/emit.rs:752` が、別の条件で判定する。§12.7 の「全ての経路で同じローカルを返すなら NRVO」は、どちらとも違う。
  - **到達解析**: `onsa_backend_c/src/reach.rs` は `onsa_core::walk` の逐語のコピーである。適合性テストにも 3 つ目のコピーがある。
  - **効果の集計**: `rt.rs` と `effects.rs` に、ほぼ逐語で重複している（R-83）。
  - **浮動小数の字面から値への変換**: `sig.rs:1345`、`:1348`、`consteval.rs:27`、`lower/body.rs:753` の 4 か所（R-20 の原因）。
  - **`subst`**: `layout.rs:65` と `body.rs:831` の 2 か所（R-30 の原因）。
  - **パターンの束縛**: `flow.rs:397-480` の `flow_unify_pat` が `bind_pat` を複製している。
  - **補間の文法**: 検証は lexer、分解は parser の 2 か所にある。
  - **std の一覧**: `onsa_driver/src/lib.rs:15` と `onsa_core/src/tests.rs:14` の 2 か所。
  - **事例の表**: golden と C のコンパイルのテストに 2 つある。
- 直し方:
  - 配置、NRVO の決定、到達解析、const の畳み込みは、Core の pass として一度だけ行い、結果を IR に記録する。
  - その他は、それぞれ一つの関数にまとめる。
- 範囲（2026-10-04 に追加で確かめた）:
  - 配置: sema の `layout.rs` を使うのは `onsa interface` の flow 以外の型だけで、ポインタ幅は 8 に固定している（S-65 の `--target` を満たせない）。Core の `layout.rs` は溢れを検査せず、bulk は閾値の方式のまま（S-43 の前）。C は、降下が記録した `FlowMeta.layout` を使わず、同じ関数を呼び直す。
  - NRVO: `early`（`let b = …` を作り、早期の `return b` と末尾の `b` で返す）で、仕様 §12.7 はコピー 0 を保証する。C は `return` があると NRVO をやめ、`(*out) = b;` を 2 か所に出す。監査用の記録は末尾の `b` を NRVO とみなし、`return b` だけをコピーと数える。
    §12.7 の保証が破れている（観点 1 のずれでもある）。再現は `tests/review-phase1/parent/r80/`。
  - 到達解析: Core の `walk.rs` は製品のコードから使われず、適合性テストが使って超越関数への到達を独自に判定している。定数は降下で畳み込まれるので、C の到達解析が定数の中の定数を 1 段しか辿らないことは問題にならない。
  - 事例の表: golden の C と C のコンパイルの表は既に食い違っている（`voice_poison` は後者にだけある）。適合性テストはディレクトリを走査するが、bulk を全ての事例で `Some(4096)` に固定していて、事例ごとの設定を書けない。
  - 議論の中で R-130（マニフェストの未知のキーを黙って無視する）を見つけた。
- 決定（2026-10-04）:
  - (1) 降下はターゲットによらない形にし、その後にターゲットの pass（R-90 (i) の bulk の分割、配置と溢れの検査）を置いて、結果を Module に記録する。C、`onsa interface`、`onsa audit`、E0820、WASM / JS は記録を読む。sema の `layout.rs` は消す（言語の意味として大きさを使う所は S-32 で無くなった）。
    理由: `check`・LSP・インタプリタが同じ降下を使い回せ、ターゲットで変わる部分が一つの pass に集まる。バックエンドが増えても、足すのはターゲットの設定だけで済む。S-65 の `--target` は記録を表示するだけになる。
  - (2) NRVO は Core の一か所で §12.7 どおり（全ての経路で返すローカルが一つ）に判定して記録し、C と監査はそれを読む。R-81 で結果の置き場所を明示するときに行う。各作業の着手の時期は、レビューを全て終えた後に改めて決める（利用者の方針）。
  - (3) 到達解析は Core に一つ（`reach(module, roots)`）にし、C の生成の範囲、`--backends all` の超越関数の判定（§13.4）、`onsa audit --panics` が使う。`walk` も Core のものだけにし、C のコピーを消す。
  - (4) std の一覧は、build.rs で `std/` のファイルから生成する（モジュールの経路はファイルの経路から。§15.1 と同じ規則）。S-69〜S-74 で std のファイルが増えても、ファイルを足すだけで済む。
  - (5) テストの事例は (a1') と (a2) にする。1 ファイルの事例は、先頭のコメントに `onsa.toml` の断片（`[targets.*]`、`[export]`）を書き、マニフェストと同じ構造体で読む。複数モジュールの事例は、ディレクトリと `onsa.toml` のパッケージにする。
    ファイル単位のテストの設定も断片の `[test]`（`mode = "check"` など）に移し、D-05 の `//! mode:` をやめる（同じことを 2 つの書式で書かない。S-51 で `//!` はモジュールの doc になっていた）。行ごとの期待値 `//~` は今のまま。テストはディレクトリを走査し、Rust に事例の表を持たない。
    ビルドの入口をファイルの読み込みから分け、マニフェストの値とソースの一覧を受け取る関数にする（`onsa_web` も使う）。元の推奨 (a2) を、利用者の問い「(a1) の設定は TOML のパーサーを流用できないか」を受けて改めた（設定の形をマニフェストに一本化したまま、仕様の例の写しとファイルの数を減らせる）。
  - 補い（2026-10-05、R-89）: 直し方にあった定数の畳み込みが、この決定から漏れていた。R-89 で、降下と正規化の後・ターゲットの pass の前の一つの段にすると決めた。
  - その他: パターンの束縛は `bind_pat` に一本化する。補間は字句解析器が分解まで行い、構文解析器はその結果を使う（R-102 で文法が変わっても一か所で済む）。効果の集計は R-83、浮動小数の字面は R-20、`subst` は R-30 で扱う。
- 判断: 直す。(1) 降下はターゲットによらない形にし、ターゲットの pass（R-90 (i) の bulk の分割、配置と溢れの検査）の結果を Module に記録して、C・interface・audit・E0820・WASM / JS が読む。sema の `layout.rs` は消す。
