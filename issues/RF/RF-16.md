# RF-16 実行ファイルの大きさ

- 内容:
  - debug の `onsa` は 20.7 MB、`onsa_cases` は 24.8 MB、release の `onsa` は 5.3 MB（デバッグ情報を `line-tables-only` にする前の測り）。
  - `crates/onsa_cli/tests/` の結合テストが 37 ファイルあり、それぞれが全体をリンクした約 20 MB の実行ファイルになる（`onsa_tests` に 9 ファイル。一からのビルドで実行ファイルが 63 個）。結合テストを少数のバイナリにまとめると、ディスクとリンクの時間が減る見込み。
  - release の 5.3 MB の内訳（埋め込んだ `std` のソース、表、総称の単相化など）は調べていない。調べるなら `cargo bloat` のような道具か、`size` と節ごとの内訳から。
  - `target/debug` の内訳（32 回目、一からのビルドの後に 2〜3 回のビルドが重なった 4.2 GB）: 差分ビルドのキャッシュ（`incremental/`）2,670 MB（64%）、実行ファイル 691 MB（61 種類、1 個 12〜25 MB、一からの 1 回分で約 350 MB）、`.rlib` 637 MB。
    差分ビルドのキャッシュもビルドのたびに増え、自動では減らない（主のツリーの gate の 8 GB の警告で `cargo clean --profile dev`）。`incremental = false` は担当の直すたびのビルドを遅くし、スタックの使い方にも響きうるので入れていない。（X-16 D で入れた、73 回目。入れた後の `gate --quick` で `with_stack_left` と `interp_stack` のテストは通った）
- 経緯: 2026-10-16、32 回目、利用者: 実行ファイルが大きすぎる。リファクタリングに関わるかもしれない
- 判断:
  - （X-16 A で入れた、72 回目。境目を `BAND` = 5 × `STEP`（20 K）にした）デバッグ情報を軽くする案（`[profile.dev] debug = "line-tables-only"` で一からのビルドが 1.6 GB → 1.3 GB、`debug = 0` で 1.0 GB）は、`onsa_diag` の `stack::tests::with_stack_left_leaves_about_that_much` を落とした（8 MB を求めて約 3 KB 少ない）ので入れていない。
    debug ビルドのスタックの使い方がデバッグ情報の量で変わり、呼び出しの深さの上限（`onsa_interp::MAX_CALL_DEPTH`、`Cargo.toml` の `onsa_interp` の注）も debug ビルドの測りに頼っている。入れるなら、先にスタックの測りがプロファイルに左右されない形にする。
- 判断（2026-11-01、親）: 100 回目（2026-11-01、W4-18 の前の洗い出しの B3、利用者が (a) を選んだ）: `crates/onsa_cli/tests/` の結合テスト（85 ファイル、実行ファイル 85 個・計 215 MB）を、W4-18 で一つの実行ファイル（`tests/cli/main.rs` の下の `mod`）にまとめる。下の crate のコードを変えるたびに 85 個がリンクし直される（22:45 の検査で 85 個とも作り直された）ので、試すたびのリンク 85 回と約 215 MB の書き込みが無くなる。自前の器を `test_support` へ寄せる T1（W4-18 の `持ち越し` の「W4-03 の U3b2 の後から」）と同じ単位。環境変数と作業ディレクトリを変えるテストは無い（確かめた）。release の大きさとデバッグ情報の項は残る。
- 反映（2026-11-02、親）: W4-18 U8a（`18fc17a3`）で `onsa_cli` の 85 の結合テストを一つの実行ファイル `tests/cli/main.rs` にした（85 個・226 MB → 1 個・30 MB、リンクの CPU の時間は約 4 分の 1）。release の内訳は調べていない（要れば新しい RF にする）
