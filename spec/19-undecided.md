## 19. 未決定事項と、実装しない機能

### 19.1 未決定事項

- マルチレート（§11.9）で決めていないこと: std の平滑の flow（S-579）、`when~` を配る形の部品（出力が `sample * N` の配列の部品）に付けたときの「最後の出力を保つ」の意味、外で作った係数の取り違えの注意（`onsa audit`、S-569）、状態の配置（カウンタの欄）、ホットリロードの照合、graph と `onsa interface` の表示、後で `sample * N` を境界に開くときの生成する API（S-574）、範囲の構文、遅い制御の値と音声の値の区別、総称の flow（型引数）。
- `sample` の入力に struct を使うこと。struct の入力は今は E0810（§11.6）。flow の `block` の出力は持たず、エンベロープの終了通知などはイベントの出力で書く（§11.11）。
  必要になりうる場面は、struct を出力する flow を別の flow へそのままつなぐとき（`width~(pan~(x, p), w)`）で、今は `let s = pan~(x, p)` と受けて `width~(s.l, s.r, w)` と分解して書く。認めるなら、export の境界の形（`In` の中に入れ子の `Span`）を、実例に合わせて決める
- flow の直列の複製。`par` が全ての複製に同じ入力を配るのに対し、`ser i in a ..< b { e }` は一つ前の段の出力を次の段の入力に渡し、各段が別のインスタンスを持つ（FAUST の `seq` に当たる。名前は `par`（並列）と対の直列（series）から採り、シーケンサの名前に使われやすい `seq` を避けた）。一つ前の段の値を本体で受け取る構文は、機能を入れるときに決める。キーワードは予約済み（§2.2）。
- 後で足す修飾子の方向（§11.10）: 連鎖で呼ぶ利用者の修飾子は、宣言の `self` を頭にし（`flow random_when(self, p: F32 at block) -> F32 at sample { self.when~(…) }`）、頭以外の引数は値とする。
  flow の高階（flow を受ける flow）は、呼ぶ前の flow を名前で、型引数と同じ場所 `::[…]` に渡し（`branch::[saw, sin]~(f0, sel)`、宣言は `flow branch[flow a(F32 at sample) -> F32 at sample, …](…)`）、渡す flow ごとにコンパイル時に展開する（flow は第一級の値ではない、§11.6）。
  利用者の修飾子の本体の `self` は受け手になれる（利用者の修飾子を足すときに、§11.10 の受け手の規則に加える）。どちらの形も今は誤りなので、開いても今のプログラムを壊さない。宣言の語（`flowmod` など）は予約しない。
- イベントの境界（§11.11。S-570〜S-573、第 35 組で決めた。本体の §11.6・§14.2・§18.2 へは第 1 期の範囲を割り当てるときに移す）:
    - イベントの入力（S-570）: 一番外の flow のイベントの入力は、入力の印の付いた一つの列で渡す。入力をまたいだ順は列の順だけで決まる（ホストの列が一つならその順を写し、分かれていればラッパーが宣言の順で混ぜる）。
      生成する API（§11.6）は、名前空間に中身を見せない Copy の型 `voice.Event` と、イベントの入力ごとの作る関数 `voice.Event.<入力の名前>(pos: U32, v: T) -> voice.Event` を置き、`process` は `params`（あれば）の後、`sample` の入力の前に `events: Span[voice.Event]` を取る（イベントの入力が無い flow は取らない。§11.6 の数の規則）。
      C の API（§14.2）は、イベントの入力のある flow に、`<p>_event`（`uint32_t pos`、`uint32_t input`、入力ごとの欄を持つ union `v`。全ての入力の値が `()` なら `v` を置かない）と、入力の番号のマクロ `<P>_EV_<入力の名前の大文字>`（宣言の順に 0 から）を生成する。
      `_process` は、イベントの入力のある flow では `params`（あれば）の後に `const <p>_event* events, uint32_t events_len` を取り、イベントの入力の無い flow は取らない（`sample` の入出力と同じく §11.6 の数の規則。信号の引数は全て flow のシグネチャにあるものだけで、シグネチャと違う呼び出しは C のコンパイルの誤りになる）。
      列の前提: `pos < frames`、列の順に `pos` が減らない、`input` は入力の数より小さい。破れば C は 2（状態を進めず、出力を 0 で埋め、poisoned にしない。重なりと同じ）、生成する API は呼び出しの最初に panic（poisoned。`Span` の長さの不一致と同じ）。
      `frames` が 0 の呼び出しはイベントを持てない（あれば同じ扱い）。
      呼び出しを位置 k で分けると、`pos >= k` のイベントは次の呼び出しの `pos - k` に移り、出力は分けない呼び出しとビットで同じである（`params` が同じとき。`block` は状態を持たず、位相のカウンタはホストの区切りに依らない。`@host` の値はラッパーが分けた位置で進めるので、`@host` を読む flow の出力は最後の桁が変わりうる）。
      呼び出しのイベントの段は、その呼び出しの `params` を読む（同じ位置のパラメータの変化とイベントの順は言語が約束しない。ラッパーは位置 p のパラメータの変化の直前で呼び出しを分け、p のイベントは新しい値を見る）。
      ラッパー向けに、`<p>_event_in_info`（入力ごとの名前と種類。要素の型は `onsa.h` の `onsa_event_in_info`、長さは `<P>_EVENT_IN_COUNT`）、出力のイベントの種類の `<P>_EVENT_OUT_KIND`（この二つは `<p>_param_info` と同じく全ての flow に置き、イベントの入力が無ければ長さ 0、出力が無ければ無しの値）、`onsa.h` の種類の列挙 `onsa_event_kind`（下の境界の型。末尾に足す限り ABI を変えないので、`ONSA_ABI_VERSION` は 1 のまま）を置く。`onsa interface` はイベントの入力と番号を出す。
      この項と下の出力の項の C の名前は、§14.2 の閉じた一覧に足す（重なりは E1011）。遅れ・ホストの情報・`Params` の中の位置の表も足す（下のプラグインの出力の項）。
      構造体の配置は C の自然な整列で決まり、JavaScript と WASM の包みはそれを読む（出し方は M6・M8）。
    - イベントの出力（S-571）: 呼び出し側が容量を持つ列で受ける。
      C は `<p>_out_event`（`uint32_t pos` と値の欄 `value`）と `<p>_events_out`（`<p>_out_event* data`、`uint32_t cap`、`uint32_t len`）をイベントの出力のある flow に生成し、`_process` は出力の位置にそのポインタを取って `len` を書く（イベントの出力の無い flow は取らない。§11.6 の数の規則。`frames` が 0 の呼び出しでもポインタは要り、`len` に 0 を書く）。
      生成する API は `inout output: Span[(U32, E)]`（長さが容量）を取り、出した数を返す（`-> U32`）。
      容量の上限は `A × frames + events_len` で、係数 A はコンパイラが出力のクロックから決めて `<P>_OUT_EVENTS_PER_FRAME` に出す（周期のクロックの出力は 1 刻みに一つで、A は連鎖の `.up~` の比の積。入力のイベントのクロックの出力は、その入力のイベントごとに一つまでで、A は 0。子の flow の出力のイベントのクロックは、子の本体の式のクロックに戻して同じく数える）。
      `process` は呼び出しの最初に、公開した式と同じ式を 64 ビットで計算して容量と比べ、足りなければ C は 2、生成する API は panic（poisoned）。黙って捨てない。
      0 以外を返した呼び出しは `len` を 0 にする（途中の panic でも、その呼び出しで出したイベントは捨てる。音声の出力を 0 で埋めるのと同じ）。
      `sample` の入力が無くイベントを出す flow の、生成する API の `process` は `frames: U32` を取る（`render` と同じ）。イベントを出す flow には `process_inplace` を生成しない（`sample` の入出力が共に無く、数の比べが空で一致してしまうため）。
    - 引数と型の形（52 回目に S-570・S-571 を見直し、S-112 を改めた）: 生成する API と C の API の関数は、flow のシグネチャにある入力と出力だけを引数に取る（§11.6 の数の規則を、`sample` の入出力、イベントの入出力、`block` の入力、`init` の入力の全てに当てる）。シグネチャと違う呼び出しは、Onsa の型の検査と C のコンパイルの誤りになる。
      `block` の入力の無い flow は `params` の引数と `Params`・`params_default`（C の `<p>_params`・`_params_default`）を持たず、`init` の入力の無い flow は `cfg` の引数と `Config`（C の `<p>_config`）を持たない（`process`・`process_inplace`・`render`・`init`、C の `_process`・`_init`・`_new` で同じ）。`bulk` はシグネチャでなくターゲットの設定で決まるので、今のまま常に取る。
      表とマクロ（`_param_info`（長さ 0）・`<P>_PARAM_COUNT`・`_param_index`（常に -1）と、上のイベントの表）は全ての flow に置く。`<p>_params`・`<p>_config` はフィールドのある flow だけに出るので、予約のメンバ `_unused` は要らない。中間表現（Core IR）の内部の `Params`・`Config` の形は約束の外で、実装が変えてよい。
    - 境界の型（S-572）: export（`[export]` の項目と C の API）の境界のイベントの入出力に出せる型は、§11.7 の `@param` と同じスカラ（`F32 F64 I8 I16 I32 U8 U16 U32 Bool`。JavaScript で 64 ビットの整数を境界に出さないため、§13.5）、`()`、std のイベントの型だけで、それ以外は E0810 である。
      flow の中と、Onsa のコードから呼ぶ生成する API（`process`・`render`）では、利用者の型も含めて自由である（外の境界ではないので、ラッパーと ABI に由来する制限は要らない）。
      `std.midi` の `midi.Message` は、MIDI 1.0 の短いメッセージを `U32` に詰めた中身を見せない型である（bit 16〜23 がステータス、8〜15 がデータ 1、0〜7 がデータ 2、24〜31 は 0。UMP の MIDI 1.0 の語の下位 24 ビット、Cmajor の `std::midi::Message` と同じ並び）。C では `uint32_t`。
      判定と取り出しと作る関数を std に置く。SysEx は持たず、MIDI 2.0 は後で別の型として足す。
      `std.transport` の `transport.Event` は、Start / Stop / Continue の中身を見せない型で、C では種類の番号の `uint32_t`。作る側は関連定数 `transport.Event.START`・`STOP`・`CONTINUE`（`continue` は予約語なので関数にしない）、判定は `transport.is_start` など。
      テンポと位置は `block` の入力で渡す（S-172。export での受け方は S-575）。
      `Default` は、`midi.Message` が 0 の語、`transport.Event` が Stop。値の正しさ（未知の種類、上位のビット）は検査せず、std の判定の関数が偽を返す。
      イベントのあった位置で真の脈の flow は `std.dsp` に置き、名前は std の一覧（M5）で決める（S-563 の例の `pulse` は仮の名前で、候補に `trig`）。
    - `render` と `onsa test`（S-573）: `render` は `process` と同じ位置に同じ形のイベントの列を取り、位置は `render` の頭から数える（`frames` が 0 の `render` はイベントを持てない）。出力のイベントは `Rendered` の `o.out: Buf[(U32, E)]`。
      テストは補助を足さず、配列のリテラルと作る関数で列を書く（入力をまたいだ順は列の順に書く）。
      `onsa test --flows` は、イベントの入力に境界の型ごとの決まった列（位置は頭・中ほど・最後と、別の入力の同じ位置を宣言の順と逆の順の両方）を与え、出したイベントの数が上限を超えないことと、同じ入力を二通りの区切りで `process` に渡した出力（音声とイベント）がビットで同じことも確かめる。
- プラグインの出力（S-580〜S-583・S-575・S-576、第 36 組で決めた。CLAP は第 1 期の W10・M5 の後の作業、VST3・AU は第 2 期。本体の §6.5・§11.6・§11.7・§12.4・§14.2・§15.3・§16・§17.6・§18.2 へは第 1 期の範囲を割り当てるときに移す）。
  - 生成するもの（S-580）: `kind = "clap"`・`"vst3"`・`"au"`（AUv2）のターゲットは、C のソースと、ホストの `platform` で PATH の `cc` を使って束（`.clap`・`.vst3`・`.component`）まで作る（束は `staticlib` の `.a` と同じく外部のツールチェーンの出力で、同一性の約束の外）。クロスの `platform` は E0200。
    ラッパーは、形式ごとの固定の C（ランタイムと同じくコンパイラに埋め込む）と、flow ごとに生成する公開しないつなぎ（`onsa__` で始める名前。一様な入口と表）で作る（つなぎ自体は公開の ABI を増やさない。足すものは下の「C の API に足すもの」）。
    CLAP のヘッダ（MIT）と VST3 の `vst3_c_api.h`（MIT に基づく使用許諾）を埋め込み、使用許諾の文を出力に置く。AU は macOS の SDK を使う。AUv3 は後で別の `kind` の値として足す。
  - マニフェスト（S-580）: パッケージの表 `[[plugin]]` に `flow`・`id`・`name`・`vendor`・`version`・`category` を書き（全て必須、閉じた一覧）、AU では `au = { subtype, manufacturer }` も書く。プラグインの種類のターゲットは、全ての `[[plugin]]` を一つの束に入れる。
    `flow` は `[export]` の `flows` に要り、同じ `id` の重複は誤り。`version` は `major.minor.patch`（AU は各 255 以下）。`category` は `instrument`・`effect`・`note-effect` で、AU の型（`aumu`・`aufx`・`aumf`・`aumi`）は `category` と MIDI の入力の有無から決まる。VST3 のクラスの ID は `id` から決まった関数で作る。
  - パラメータ（S-581）: プラグインに出す flow の数値の `@param` は `min`・`max` を要する（無ければそのターゲットのビルドで E0809）。整数は `(max − min) / step ≤ 2^24`（E0809）。AU のターゲットでは `F64` の `@param` は E0200。VST3 の正規化は `scale` で写す。
    ラッパーは、`step` があれば（整数の型は無くても 1）値を `min + k × step` の格子に寄せ、`[min, max]` に収めてから `Params` に書く（C の API の外の層で、C の API が値を飽和させない約束（§11.7）とは別）。変化はラッパーが変化の位置で呼び出しを分けて届ける（S-565、S-570）。
    変調（受けるか）と表示の文字列の形（Onsa が決まった形を持つか、ラッパーごとに定めるか）は CLAP の作業で決める。UI の文脈との受け渡しは、ラッパーが C のパラメータごとの原子的な変数で持ち、言語の同期型（§16.2）は使わない。
  - ホストの情報（S-575）: `block` の入力に `@host(<種類>)` を付けると、export でも `@param` が要らず、ラッパーがその呼び出しの最初のサンプルの時点の値を書く（呼び出しを分けた位置では進めた値）。
    種類は `tempo`（`F64`、BPM、既定 120.0）・`beat`（`F64`、四分音符の数の位置、0.0）・`bar_start`（`F64`、今の小節の頭の位置、0.0）・`sig_num`・`sig_den`（`U16`、4・4）の閉じた一覧（再生の状態は `transport.Event` で受ける）。種類の誤りは E0005、型の違いと `@param` との重なりは E0809。
    ラッパーは種類ごとにホストの値を確かめ、`tempo` が有限で 0 より大きい、`beat`・`bar_start` が有限（負はよい）、`sig_num`・`sig_den` が `U16` に収まる 1 以上の整数、を満たさない値の代わりに、与えられないときと同じ既定の値を書く（C の API の外の層。C の API と `render`・`onsa test` は値をそのまま渡す）。
    C では `Params` の欄に置き、`_param_info` に入れず、表 `<p>_host_info`（名前、種類、位置）・`<P>_HOST_COUNT` と `onsa.h` の `onsa_host_kind`・`onsa_host_info` で示す。`params_default()` は、`block` の入力のある flow で、その全てに `@param` か `@host` があれば生成し、`@host` の欄は既定の値にする。`onsa test --flows` は `@host` の入力に既定の値を与える。`@host` は export しない flow の入力にも付けられ、意味は export でだけ持つ（`@param` と同じ）。
  - ノートとボイス（S-582）: ホストのノートと MIDI は全て `midi.Message` に写す（CLAP のノートのイベントは MIDI 1.0 のノートオン・オフにし、速さは `round(v × 127)`、ノートオンは 1 以上。`note_id` と表情は捨てる）。`midi.Message` の入力ごとに一つのノートのポートを持つ。
    flow の `midi.Message` の出力は、CLAP の `CLAP_EVENT_MIDI`、VST3 はノートのイベントと `LegacyMIDICCOutEvent`、AU は MIDI の出力の block（AUv2 は `kAudioUnitProperty_MIDIOutputCallback`）に写す。
    VST3 の CC・ピッチベンド・チャンネルプレッシャーは `IMidiMapping` の隠したパラメータ（数値の ID は `0x80000000` 以上、保存しない）で受けて MIDI に戻す（同じ位置のノートとの順は保てない）。
    AU のターゲットで `midi.Message` の入力が二つ以上なら E0200 である（AU には、ホストに複数の MIDI の入力を名前付きで示す口が無い。AUv2 の `MusicDeviceMIDIEventList` の UMP のグループと AUv3 の `cable` の番号はあるが、ホストが入力ごとに分けて送るかは確かめていない。後で緩めても壊れない）。
    `transport.Event` の入力には再生の状態の変化を写す（動き出した位置の `beat` が 0 なら `START`、それ以外は `CONTINUE`、止まると `STOP`）。
    ボイスの割り当ては export する flow（利用者の Onsa のコード。イベントの段の状態と `par`）が持ち、`render`・`onsa test` で確かめられる。ボイスの終わりは知らせない。§17.6 の `Poly`（struct と関数）は export できないので、プラグインの入口にはならない。
    §17.6 は `Poly` の例を残し（Onsa のプログラムの中では正しい書き方で、DSP 以外のコードを示す例）、プラグインにするときのイベントの入力の flow の例を並べて足す。
  - 状態と構成（S-583）: 状態は、パラメータの値だけを文字列の ID と値の組で保存する文字の形（1 行目に形の版とプラグインの版、浮動小数はビットの 16 進。知らない ID は捨て、無い ID と型の合わない値は `default`）。`init` の入力（`Config`）を持つ flow はプラグインにできない（そのターゲットで E0200）。
    ラッパーは CLAP の `activate`・VST3 の `setupProcessing`・AU の `allocateRenderResources` で `_init` を呼び（最大のフレームの数でイベントの入力と出力の列の大きさを決め、列が足りなければ呼び出しを分ける）、ホストが求めたときだけ `_reset` を呼ぶ。`_process` が 1 を返したら、次の呼び出しの前に `_reset` を呼び、ホストのログに一度知らせる。
    ラッパーは、自分が起こす初期化（`activate` の後の `_init`、ホストの求めた `_reset`、上の `_reset`）の直後に、短い決まったフェードイン（数 ms。長さと形は CLAP の作業で決める）を出力に掛ける（入力が鳴っている所で状態が初期値に戻ると、クリックになるため）。
    C の API と `render` はフェードを持たず、flow の意味のままである（§13.4）。flow の中の `reset_if~` の乱れは書き手が扱う（`sample_tick()` で作るフェード、std のフェードの flow は S-579）。
    バスは `sample` の入力ごとに一つの入力のポート（最初が主、後はサイドチェイン）で、出力は単一の値なら一つ、struct ならフィールドごとに一つ。型は `F32`、チャンネルは 1（スカラ）か 2（`[F32; 2]`）だけで、他はそのターゲットで E0200。尾は無限として報告し、バイパスのパラメータは持たない（AU には入力をそのまま出す最低限のバイパスを持たせる）。
  - 遅れ（S-576）: C の `uint32_t <p>_latency(const <p>* s)` と、生成する API の `rt fn f.latency(s: f.State) -> U32`（`init` の後の値。未初期化なら 0）で出す。値は一番外の flow の宣言 `@latency(e)`（`e` は `init` のクロックの式）で、宣言が無ければ 0 である（子の宣言は合成しない）。
    コンパイラは報告する値を本体から数えない（フィルタの群遅延は周波数と係数に依り、遅いレートで動く検出の経路の遅れは音の遅れでないので、機械では正しく決まらない）。構造から決まる遅れ（集めて配る N と子の宣言の、経路ごとの値）は解析の道具（`onsa audit`）が出し、形は S-586 で決める。
    `block` のクロックの式は E0815。値は状態の隠れた欄に置き、`reset` は保つ。std の `fir_up2`・`fir_down2` は `@latency` を持つ。
  - C の API に足すもの（W10。`ONSA_ABI_VERSION` 1 を出す前）: `<p>_latency`、`<p>_host_info`・`<P>_HOST_COUNT`、`onsa.h` の `onsa_host_kind`・`onsa_host_info`、`onsa_param_info` と `onsa_host_info` の `uint32_t offset`（`Params` の中の位置。flow を知らずに値を書くホストのため）。
    §14.2 の閉じた一覧に足す。
  - 決めていないこと: プラグインの独自の画面（GUI、S-585）、変調とボイスごとの変調とノートの表情（`note.Event`）、パラメータの変化をイベントの列で届ける形、`scale` と範囲の変更の凍結（§15.4、S-584）。
    CLAP の作業で決めるもの: ラッパーが呼び出しを分ける最小の長さ（密な自動化で `block` の段がサンプルごとに走るのを抑えるか。本物のホストで測って決める）、表示の文字列の形、フェードインの長さと形、状態の形の文法の字、`_init` が 0 以外を返したときのラッパーの振る舞い、スカラと `()` のイベントの入力のプラグインでの扱い、ホストが再生中に起動したときの `transport.Event`。
    候補: `_init` の失敗は起動を失敗として返す（§14.2 では復帰は `init` のやり直しだけで、起動に失敗したインスタンスは `_process` を呼ばれない）。スカラと `()` のイベントの入力はそのターゲットで E0200（ホストに写す元が無い）。再生中の起動は、ラッパーの初めの状態を停止とし、最初の呼び出しの位置 0 に `CONTINUE`（`beat` が 0 なら `START`）を写す。
    VST3・AU の作業で決めるもの: VST3 のクラスの ID の関数の中身、VST3 の隠したパラメータの ID の式と上限（`0xFFFFFFFF` は使わない）、AU の SDK の探し方（§15.3 の環境変数の例外を増やさない形）。
- 総称の型別名（`type Pair[T] = (T, T)`）。境界、`const` のパラメータ、使われないパラメータの扱いを、実例が出てから決める（§4.4）
- 単位の型と newtype。取り違えの検査が要る実例が出たら、newtype（`struct Hz(F32)`）と単位代数（F# の units of measure）を比べて決める。今は、名前付きのフィールドが 1 つの struct で書ける（§4.4）
- 固定小数点型（`Q15`, `Q31`、飽和演算）を標準ライブラリに置くか、言語に入れるか
- 利用者の型への `Float` の実装。今は組込みの浮動小数だけが実装する（§6.3）。開くときは、超越関数と `vdelay` の計算を型ごとに与える形（std の本体か、trait のメソッドか）を決める。制限を外す向きの変更なので、今の規則で書いたコードは壊れない
- 長いサンプル列を扱う遅延と読み出し（組込みのサンプリングルーパーなど）: 値の型（`F32`）と読み出す位置の型（`U32` か `F64`）を分ける。今は `vdelay` の `d` が信号と同じ型で、`F32` の信号では `MAX <= 2^24`（§11.4、48 kHz で約 349 秒）。整数の位置で補間しない読み出し、補間の計算の順（§13.4 のビット一致）、型の混ぜ方を含めて API を見直す。型の組み合わせを許す方向の変更なので、今の規則で書いたコードは壊れない
- enum（列挙子に中身の無いもの）の `block` の入力に `@param` を付けること。波形やモードの選択に使う。表示名（列挙子の名前か `label`）、値の番号（`Ordinal` の番号を使える、§6.4）、C の `Params` と `onsa_param_info` での表現を決める。今は E0809（§11.7）
- ファームウェアのエントリ: 割り込みとメインループの二つの文脈を提供する `target` モジュールの標準形（§16.1）。bulk を持つ flow の状態の持ち方も一緒に決める。
  今は Onsa の中から呼ぶ `init` に bulk 領域を渡す口が無く、bulk を持つ状態を `main` のローカルに置けない（E0819、§12.4）ので、bulk を持つ flow は C のホストから使う（§17.5）。方向の候補は、ターゲットが bulk 領域を与えて `init` が受け取る形と、登録の関数（`device.run`）が状態と bulk 領域の確保を引き受ける形
- ターゲット提供の「後回しの仕事」（サンプルの読み込みなど）: `std.worker.run_later(f, move arg)` のような文脈で、マイコンではメインループで直列に、デスクトップではスレッドプールで実行する案。言語は並列性を約束しない
- デスクトップのターゲットだけが `provides` する並列計算の効果（ライブラリとして。核には触れない）
- `Alloc` の確保失敗を、panic ではなく値として扱う API
- panic の地点の番号: `panic_messages = false` でも位置とメッセージを復元できるよう、ランタイムの panic の関数には地点の番号だけを渡し、番号から「ファイル・行・メッセージ」を引く表を `onsa build` がバイナリの外に出す（組込みの Rust の `defmt`、Zephyr の辞書式のログと同じ考え方）。番号の安定、表の形式、`onsa audit --panics` との関係を決める。今は文字列を除いて行番号を残す（§9.2）
- 補間の中の呼び出しと式。穴の評価順（§3.5）、効果、`!` / `inout` の呼び出し、panic の扱いを決める必要があるので、今は名前の経路だけ（§2.4）
- `panic` のメッセージに、組み立てた文字列（`"index {i}"`）を渡すこと。`Str` の実装と一緒に決める。rt の中では、組み立てにヒープが要る（§9.2）
- ホットリロードで、型の変わったフィールドの扱い
- probe で見るためだけに名前を付け、出力には使わない信号。今は使われない束縛（E0309、§5.1）なので書けない。必要な実例が出たときに、印の形（属性など）を決める（`onsa probe`、§18.2）
- Onsa から `extern "C"` の関数（§14.1）を呼ぶ間の浮動小数の状態。export の入口ではプロファイルの環境に設定する（§15.5）ので、そのまま呼ぶと C の関数はその環境で動く。呼ぶ前後でホストの状態に切り替えるかを、FFI の実装のときに決める
- 変換先の優先順位（C の次に何を作るか）
- F64 のハードウェアが無い機器で、F64 のソフトウェアの演算を、ツールチェーンの soft-float ではなく Onsa の実装（`std.math` の musl の移植と同じ扱い）に差し替えること。FZ の扱いも含めて、全ての機器で同じ計算にできる（今は生成コードがソフトウェアで非正規化数を 0 にする、§15.5）
- クロスのビルドで、外部の C ツールチェーンを指定する形（マニフェストのキーか、探し方の規則）。今は外部のツールチェーンを要するクロスの `kind` は E0200（§15.3）
- `@fp(relaxed)` の flow の、`--backends all` での許容の値を flow ごとに指定する形。今は差を表示するだけで、合否には使わない（§13.4）。どの閾値が妥当かは、指定したい実例が出てから決める
- 超越関数をビット一致させる `std.math.exact`（Onsa 実装）を提供するか
- flow の状態からポインタを無くし、bulk 領域の中のオフセット（`U32`）で持つ案。ベースのポインタは export の wrapper が持つ。状態がポインタを含まない普通のデータになり、複製・退避・ホットリロード（IDE での需要がある）で扱いやすくなるが、C API と入れ子の bulk の作りを変える。言語の部分を固めた後で検討する（§12.4）
- `Map` / `Set` の鍵の要件。§6.3 は `Ord` を鍵に使うと書き、§4.3 は挿入順のハッシュ表としている。`Eq` + `Hash` にするか（第 2 期に `Map` を実装するときに決める）
- `init` のクロックの大きな配列（ウェーブテーブル）を bulk 領域に置く指定（今は `@mem(bulk)` を遅延線にだけ付けられる、§12.4）
- 検査の水準: 整数のオーバーフローの検査をターゲットの設定で外すか（Rust の `overflow-checks = false` に当たる `overflow = "wrap"`。panic しない実行の結果は変わらず、`onsa audit` に表示する）。組込みのターゲットで検査の費用を実測してから決める。添字の検査は外さない（C で未定義動作になり、メモリ安全性が崩れるため）
- 言語全体の変換（段階 2）の既知の差: 言語ごとの FFI、JavaScript の 64 ビット整数と文字列の性能、arena の枯渇（§13.5）
- 逃げるクロージャ（保存できるコールバック）、トレイトオブジェクト
- クロージャの捕捉のモード: 今は値のコピーで捕捉し、読み取り専用である（§5.3）。`move`（Affine の値を移して捕捉する）や `inout`（外側の変数を書き換える捕捉）を指定できるようにするか。クロージャは引数の位置にだけ現れる第二級の値なので、`inout` の捕捉も呼び出しの間だけのものとして安全に定義できる見込みがある。必要な実例が出てから決める。
  既定のモードの関数型の引数を、引数の位置の無名関数が捕捉する形（`array.from_fn(fn(i) { f.(i) })`）も、環境の寿命が呼び出しに収まるので開ける見込みがある（今は E0710、§5.2）。Shared 型の値を捕捉したとき、複製（参照カウントの増加）か借用か（§5.4）も第 2 期に決める
- async / await
- std 以外の依存: 取得元（パス、レジストリ、git など）、版の解決（菱形の依存で、同じパッケージの違う版を同居させるか）、`onsa.lock` の形。第 2 期に依存を入れるときに決める（パッケージの `tests/` の役割も、パスによる依存を前提にするので一緒に決める。この版では `tests/` の `.onsa` は E0200、§15.1）
- 延期（用途が出てから）: `Net` 効果、ユーザ定義型の反復（`IntoIter` の実装）、`Array` の `map` / `filter`、`@deprecated`、`onsa.policy`（§15.4）

### 19.2 実装しない機能（理由付き）

| 機能 | 理由 |
|---|---|
| Onsa からのスレッド・タスクの生成（`spawn`、`scope`、`Task`、`join`）と、ブロックする同期型（`Chan`、`Mutex`）、効果 `Spawn` / `Sync` | 用途（プラグイン、マイコン、worklet、CLI）のどれも実行の文脈をホストが与える。言語がスレッドを作ると、スケジューラで直列化される環境と意味が分かれる。文脈の登録（§16.1）で足りる |
| `Sleep` 効果 | 待機が要る用途が無い。時刻は `Clock` |
| `Str` の文字列処理（部分文字列、検索、文字の反復） | 文字列の用途は作る・比べる・出すだけ。必要になった API から足す（§4.2） |
| Rust の借用検査器、ライフタイム | §0.4 |
| トレイトオブジェクト、マクロ、遅延評価、高階型 | §0.4、§6.3 |
