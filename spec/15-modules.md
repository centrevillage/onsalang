## 15. モジュール・パッケージ・ターゲット

### 15.1 モジュール

- 1 ファイル = 1 モジュール。モジュールのパスはパッケージルートからのファイルパスで、`mod` 宣言は無い。集めた `.onsa` を下に持ち、同じ場所に自分の名前の `.onsa` が無いディレクトリ（`a/b/c.onsa` だけのときの `a` と `a.b`）は、項目の無いモジュールである（`use a` で取り込め、`a.b.c.f()` と下のモジュールに届く）。`.onsa` を下に持たないディレクトリはモジュールでない。
  パッケージルートは `onsa.toml` のあるディレクトリで、その下の `.onsa` ファイルを再帰的に集める（`.` で始まる名前の項目（道具が作るディレクトリとファイル）と、パッケージルート直下の `tests/` と `target/` を除く。`.` で始まる名前のファイルか、`.` で始まるディレクトリの下のファイルを経路で渡したときは、その名前に §2.3 の規則を当てる（E0320）。それより深い `tests/`（`dsp/tests/` など）は普通のモジュールのディレクトリ）。
  名前で除く項目は、種類を見る前に除く（リンクでも除く）。パッケージの木の中のシンボリックリンクは辿らない。名前が `.onsa` で終わる項目が通常のファイルでもディレクトリでもなければ（ファイルやディレクトリを指すリンク、壊れたリンク、FIFO など）、使い方の誤り（終了コード 2）である。
  名前が `.onsa` で終わらないリンクと通常のファイルでない項目は、辿らずに黙って除く。ハードリンクは通常のファイルで、それぞれの経路のモジュールになる。`onsa.toml` を持つ子のディレクトリは別のパッケージ（入れ子のパッケージ）で、その下を集めない（ルート直下の `tests/` が自分の `onsa.toml` を持つときも同じで、E0200 にしない）。
  一つのファイルは、上へ探して最初に見つけた `onsa.toml` のパッケージにだけ属し、ファイルのあるモジュールとファイルの経路は一対一である。名前が `.onsa` の項目だけを誤りにするのは、モジュールにしたい書き手の意図を黙って捨てないためである。
  読めないディレクトリと読めない `.onsa` ファイルは入出力の誤り（終了コード 2）で、黙って飛ばさない。集めないディレクトリ（名前で除くもの、入れ子のパッケージ）の中は開かない。
  ルート直下の `tests/` の役割は第 2 期に決める（§19.1）。この版では、その下に置いた `.onsa` ファイル（深い階層と、その中の `tests/` の下も含む）はモジュールを集めるコマンド（`check`、`test`、`build` など）と LSP で E0200 になり（そのファイルを経路で渡したときと、LSP で開いたときも同じ）、黙って無視されない。
  これらはモジュールでないので、§2.3 の名前の規則は当てない（`.` で始まる名前のファイルを経路で渡したときも E0200 だけ）。`.onsa` でないファイルは読まない。
  マニフェストの無い単一のファイル（`onsa check foo.onsa`）は、そのファイルを 1 モジュールのパッケージとして扱う（モジュール名はファイル名で、§2.3 の規則に従う。違反は E0320。置いたディレクトリはモジュールの経路の要素でないので、その名前には規則を当てない。`.hid/ok.onsa` も誤りにしない）。コマンドは、渡したファイル（無ければ作業ディレクトリ）から上の階層へ `onsa.toml` を探し、最初に見つけたディレクトリをパッケージルートにする。
  渡した経路にリンクがあれば（途中のディレクトリのリンクも）、リンクを解いた場所から探す。解くのは探す起点だけで、見つからず単一のファイルのパッケージになるときのモジュール名と表示の経路は、渡した経路のままである。`onsa.toml` はリンクでも、リンク先をマニフェストとして読む（集める項目ではない）。上へ探すときも、入れ子のパッケージを見分けるとき（子のディレクトリの `onsa.toml`）も同じである。
  経路として渡した `onsa.toml` は、その置き場所のディレクトリを渡したのと同じに扱う（リンクを解くのはディレクトリの部分だけで、`onsa.toml` 自身はリンク先をマニフェストとして読む）。リンク先が無いか読めなければ入出力の誤り（終了コード 2）である。
  ファイルを渡して見つからなければ、単一のファイルのパッケージである。経路を省いて見つからなければ、使い方の誤り（終了コード 2）である。ルート直下の `target/` の下のファイルを経路で渡すのも、使い方の誤り（終了コード 2）である（ビルドの出力の置き場で、モジュールにならない）。
  パッケージを読むコマンドに渡す経路（`.onsa` のファイル、ディレクトリ、`onsa.toml`）は一つで、コマンドの最後の省ける位置の引数である（§18.2）。二つ以上は使い方の誤り（終了コード 2）である（一回の実行は一つのパッケージを扱う。`fmt` と `diff --ast` はファイルごとに処理するので、この規則の外）。パッケージを読むコマンドに `.onsa` でも `onsa.toml` でもないファイルを渡すのも、使い方の誤り（終了コード 2）である。
  ディレクトリの引数はパッケージのルート（`onsa.toml` のあるディレクトリ）を指し、`onsa.toml` を持たないディレクトリを渡すのは使い方の誤り（終了コード 2）である。パッケージの中のファイルを渡したときは、パッケージ全体を集めて解決し（`use` の解決に全体が要る）、結果をそのファイルのモジュールに絞る。
  診断が結果であるコマンド（`check` と LSP）は、そのファイルの診断だけを出す。`interface` はそのモジュールの宣言、`graph`・`play`・`probe` はそのモジュールの中の flow、`audit` はそのファイルの箇所を出す。結果がパッケージの全体である `build` にファイルを渡すのは、使い方の誤り（終了コード 2）である。
  `onsa test` が渡したファイルで選ぶテスト、出す診断、ファイルを複数渡したときの扱いは §18.2 に定める。
- 可視性は `pub`（パッケージ外に公開）、無指定（パッケージ内に公開）、`priv`（モジュール内のみ）の 3 段階。他のモジュールの項目は `use` で取り込んだ名前でだけ参照するので、パッケージ内に公開しても名前は衝突しない。パッケージの外に出るのは `pub` を書いたものだけである。
  可視性を書けるのは、他のモジュールから名前で参照する宣言（トップレベルの名前のある項目、`use`、固有の `impl` のメンバ、extern のメンバ、フィールド）だけである。
  固有の `impl` のメンバは、型の可視性を超えて届かない。型の可視性より広い `pub` をメンバに書くと冗長で E0020（修正候補は外すこと。無指定と `priv` の型のメンバの `pub`）。語の無いメンバと `priv` のメンバは、どの型にも書ける。`priv` の型の `fn` と `priv fn` はどちらもモジュールの中に届き、型の可視性を広げると、`priv fn` はモジュールの中に残り、`fn` は型に連動してパッケージの中まで届く。
  メンバが自分の可視性を持つ容れ物（固有の `impl`、extern のブロック）に書いた `pub`・`priv` は、修正候補の無い E0002 で、可視性はメンバごとに書くと note で示す（語を外すと、メンバが書き手の意図と違う可視性のまま通るため）。
  trait の実装、`test`、持ち主の可視性を継ぐメンバ（trait・effect のメンバ、trait の実装と handler のメンバ）、列挙子に書いた語は冗長で E0020（修正候補は外すこと）。どちらも、語の後ろから宣言を読み続ける（§18.1）。
  `pub(pkg)` の形は無い（E0020、修正候補は外すこと。`pub (pkg)` のように空白を挟んでも一つの誤り）。
  他の言語の範囲を限る可視性（`pub(super)`、`pub(self)`、`pub(in a.b)`）と、`pub(` の後が `crate`・`pkg` でない他の形（`pub()`、`pub(package)` など）は、Onsa に同じ範囲が無いので、候補の無い E0002 で、note にこの 3 段階を示す（空白を挟んでも一つの誤り）。
- フィールドは、struct の可視性を継ぐ（`pub struct Point { x: F32, y: F32 }` の `x` と `y` は `pub`）。モジュールの中に限るフィールドにだけ `priv` を付ける（`pub struct Ring[T, const N: U32] { data: [T; N], priv head: U32 }`）。`priv` のフィールドは、struct の可視性によらずモジュールの中に届く。
  広げる向きの指定は無く、フィールドに `pub` を書くと継いでいるので冗長で E0020（修正候補は外すこと）。`priv struct` のフィールドには、`priv` も語の無い形も書ける。
  どちらもモジュールの中に届き、struct の可視性を広げると、`priv` のフィールドはモジュールの中に残り、語の無いフィールドは struct に連動する（固有の `impl` のメンバの `priv fn` と `fn` と同じ）。`pub struct` のフィールドをパッケージ内に限る書き方は無い。必要なら `priv` にして、作る関数と読む関数を無指定（パッケージ内）で置く。
  `pub struct` のフィールドに書いた `pub(crate)`・`pub(pkg)` は、外すと struct の `pub` を継いでパッケージの外へ広がるので、修正候補の無い E0002 で、note でこの書き方（`priv` にして作る関数と読む関数を無指定で置くか、外へ出してよければ外す）を示す（空白を挟んでも一つの誤り）。
  他の位置（項目、無指定と `priv` の struct のフィールド、`use`）の `pub(crate)`・`pub(pkg)` は、外す修正候補の E0020 のまま。enum の列挙子の中身は、enum の可視性を継ぐ。
- 可視性を持つか継ぐ宣言の見出し（本体と初期化式を除く部分）に書いた名前（型・trait・効果。型の中の型を含む）は、その宣言の届く範囲より狭い可視性を持てない（E0303。位置は書いた名前で、修正候補は無い）。`pub fn f() -> Inner` の `Inner` が無指定なら、パッケージの外の利用者は名前を書けない型を受け取ることになる。
  見出しは、例えば関数の引数と返り値、型別名の右辺、定数の型、フィールドと列挙子の中身、trait のメンバ、固有の `impl` のメンバ（`impl` の見出しの境界を含む）、flow の入力と出力の型、効果の操作の引数と返り値、handler の引数、総称の境界の trait、上位の trait、効果行の効果である。
  届く範囲は宣言の可視性で、固有の `impl` のメンバではメンバの可視性と型の可視性の狭い方である（`priv struct Hidden` の `impl Hidden { fn make() -> Hidden }` の `make` はモジュールの中までしか届かないので通り、`pub struct P` の `impl P { pub fn leak() -> Inner }` は E0303）。
  モジュールの中に限るフィールドは `priv` にする（`pub struct P { priv i: Inner }` の `i` はモジュールの中までしか届かないので通る）。
- 見えないフィールドを読み書きすると E0303。見えないフィールドを持つ struct は、そのフィールドが見えない場所では struct リテラルで作れず（E0303）、作る関数を通す。可視性は必要以上に狭めない。隠すのは、不変条件を守るために外から書き換えられては困るフィールドだけにする。
- `use std.fs.{Fs, Path}`。グロブ import は無い。`use` で取り込んだ名前は、そのモジュールの中でだけ使える（項目と違い、無指定の `use` はパッケージ内に公開しない。`priv use` は冗長で E0020）。再公開（`pub use`）は、std 以外の依存と一緒に第 2 期に決める（§19.1）。
  この版の `pub use` は `pub` の位置の名前の段の E0200 で、修正候補は無く、note で、使う側が定義の経路で取り込む形（`use kp.inner.{g}`）を示す。
  `use` はモジュールのトップレベルの項目の位置ならどこにも書ける（関数の本体の中には書けず、E0002）。同じ名前を二度取り込むと E0304（束縛の重複。失敗した `use` の名前は数えない、§18.1）。モジュールの項目と、同じ名前の子モジュール（`a.onsa` の項目 `b` と `a/b.onsa`、ファイルの無い `a/b/`）も E0304（位置は項目で、ファイルの無い子モジュールの note はディレクトリの下の `.onsa` のうち診断の並べ方で最初のものの先頭）。
  E0304 になるのは、同じ名前の空間の中の二つの名前だけである。空間は、本体（項目、`use` の束縛、prelude、組込み型と、flow の本体では組込みの flow の名前）、モジュールの名前空間（他のモジュールの経路の `main.X` が引く項目と子モジュール）、経路の頭（ルート直下のモジュールと依存のパッケージ名）の三つで、項目は本体とモジュールの名前空間の両方にある。
  この E0304 は、片方がソースの外の名前（prelude、組込み型、組込みの flow の名前、子モジュール、依存のパッケージ名）ならこのモジュールの宣言に、項目と `use` の束縛なら書いた順によらず `use` に、項目どうしか `use` の束縛どうしならソースの順で後の宣言に付け、もう一方を note で示す。その空間では、使う所と他のモジュールの経路はどちらも引かない（§18.1）。
  `use` の束縛と同じ名前の子モジュール（`main.onsa` の `use kp.inner` と `main/inner.onsa`）は重ならず、`main` の本体の `inner` は `use` の束縛を、他のモジュールの `use main.inner` は子モジュールを指す（`main` で子モジュールの項目を使うには `use main.inner.{h}`）。
  子モジュールとルート直下のモジュール・prelude の名前、項目・`use` の束縛とルート直下のモジュールの名前も重ならない。
  他のモジュールの `use` の経路は、途中も最後も、そのモジュールの項目と子モジュールの定義だけを引き、`use` の束縛を引かない（`use` の束縛だけにある名前は E0302）。
- `use` の経路は絶対経路で、頭に書けるのは、自分のパッケージのルート直下のモジュールか、依存のパッケージ名（`[dependencies]` のキーと、暗黙の依存の `std`、§15.3）だけである。
  モジュールの項目や、`use` で取り込んだ名前からは始められない（`use std.math` の後でも `use math.{sin}` は E0302 で、修正候補は `use std.math.{sin}`）。各 `use` は、書く位置にも他の `use` にもよらずに決まる。自分のパッケージは名前で参照しない。
  自分のモジュールも取り込めない（`main.onsa` の `use main`、`dsp/synth.onsa` の `use dsp.synth` は E0302 で、修正候補は無く、note で自分の項目は名前だけで書くことを示す）。
  中からはルートからの経路（`use dsp.synth.{voice}`）、外からはパッケージ名を付けた経路（パッケージ `fx` なら `use fx.dsp.synth.{voice}`）で書く。自分のパッケージ名を頭に書くと E0302（修正候補はパッケージ名を外すこと。同じ名前のルート直下のモジュールがあれば、それを指す）。
  パッケージ名の直後が並びのとき、候補は並びの要素ごとの `use` である（`use fx.{util}` は `use util`、`use fx.{a, b}` は `use a` と `use b` の二行）。パッケージそのものを取り込む `use fx` は、直す形が本体の経路にも及ぶので候補を出さず、note でモジュールを直接取り込む形を示す。
  ルート直下のモジュールの名前か、モジュールを含むルート直下のディレクトリの名前が、依存のパッケージ名（`std` を含む）と重なると E0304（利用者の `std.onsa` も `std/math.onsa` も）。同じ場所の `a.onsa` と `a/` は親のモジュールと子のモジュールで、重ならない（重なるのは、上の `a.onsa` の項目 `b` と `a/b.onsa`）。
- `use` の経路がたどれるのは、パッケージ、モジュール、flow の名前空間（§11.6）だけで、取り込めるのは、依存のパッケージそのもの（`use std`）、ルート直下のモジュール（`use kp`）、モジュールの項目、子モジュール、flow の名前空間（`use dsp.synth.{voice}`）、flow の名前空間の項目である。
  並びの各要素と、並びの無い経路の最後の要素は、どちらも一つの束縛を作る取り込む名前で、宣言の名前と同じ規則で読む（キーワードは E0002、予約語は E0200、`_` は E0002）。
  `use std.test` と `use match` は E0002 で、並びで中の名前を取り込むか、親から辿る書き方（`use std` の後の `std.test.…`）を note で示す。`use kp.clock` と `use clock` は `clock` の位置の E0200 である。取り込む名前より前の経路の要素は、キーワードと予約語もモジュールの名前として読む（§2.2）。
  二つの書き方（`use std.math` と `use std.{math}`）は同じ束縛を作り、fmt は名前が一つだけの並びを並び無しの形に揃える（`use std.{math}` は `use std.math`。並びの中にコメントがあれば残す、`spec/tools.md` §3.3）。並びは一つ以上の名前を `,` で区切り、要素は名前だけである（入れ子、経路、`self`、別名は書けず、E0002）。
  空の並び（`use std.math.{}`）は構文の段の E0002 で、修正候補は `use` の全体を除く形である（中にコメントがあれば候補なし）。括弧だけを除くと、`use std.math` が `math` を取り込む別のプログラムになるからである。
  enum の列挙子（`Type.Variant` と書く、§4.1）、型の関連関数と関連定数（`Point.new`、`F32.PI`、§2.3 / §6.6）、効果の操作（`Fs.read`、§8.1）は取り込めない（E0302。文面で理由と書き方を示す）。
- 他のモジュールとパッケージは、`use` で取り込んだ名前でだけ参照できる（`use std.math` の後の `math.sqrt(x)`、`use std.math.{sqrt}` の後の `sqrt(x)`）。
  暗黙に見えるのは、自分のモジュールの項目、prelude、組込み型だけで、`use` の無い経路（`std.math.sqrt(x)`）は E0302（修正候補は `use` の追加）。
  経路の頭が自分のパッケージ名か、自分のモジュールを名指す部分（モジュール自身の名前か、自分の絶対経路）のときは、修正候補はその部分を外すことで、外した後の頭を取り込む `use` が無ければ足す（パッケージ `fx` の `fx.util.helper()` は `use util` と `util.helper()`、`main.onsa` の `main.other()` は `other()`、`main.inner.g()` は `use main.inner` と `inner.g()`）。
  これらの候補は、当てた後の経路が名前の段で最後まで解決し、足す `use` が循環を閉じないときだけ出し、一要素の頭（`let x = util`）には出さない。パッケージ名の後はルートからの経路として読み、自分の絶対経路が続けばパッケージ名と一緒に外す（`a/b.onsa` の `fx.a.b.f()` は `f()`）。
  頭がルート直下のモジュールの名前でもあるときは、そのモジュールを取り込む読みを先にし、その経路が名前の段で最後まで解決しなければ外す読みに移る（解決するが足す `use` が循環を閉じるときは候補を出さない）。
  循環を閉じるとは、当てた後に足す `use` の辺が循環の上にあることで、既にある循環の中に辺を足すときも含む（`use` の頭の候補も同じ）。
  候補を出さないときは note で正しい形を示す。パッケージ名を外す `use` の頭の候補（上記）とこれらの候補を、循環を閉じるので出さないときは、その形と循環の相手のモジュールを示す。モジュールが何に依存するかは、`use` の一覧を見れば全て分かる。
- 名前が見つからなければ E0302。名前は見つかったが、その位置に要る種類（値、型、モジュール、関数、flow、trait、列挙子、定数）でなければ E0308 で、直し方が違うので分ける。
  E0302 の修正候補は本文が定める形（`use` の無い経路への `use` の追加など）だけで、綴りの近い名前は候補にしない（綴りの誤りは、書き手の意図が一つに決まらないことが多い）。
  E0308 になるのは、型を値の位置に書く（`let a = P`）、値やモジュールを型の位置に書く、flow を型の位置に書く（修正候補は `lp.State`、§11.6）、定数を型引数の位置に書く、型を const 引数の位置に書く、パターンに列挙子でも定数でもない名前（型、trait、総称の定数のパラメータ）を書く（§7）、型でないものを `impl` の対象にする、名前空間でない名前の後に `.` を書く、メソッドを関数の形で呼ぶ（修正候補は `value.m(...)`）場合である。
  値を `x(...)` の形で呼ぶと、型によらず E0020（関数値は `x.(...)`、§6.1）。`.(` で呼んだ値の型が関数でない場合（`x: F32` の `x.(1.0)`）は型の誤りで E0401。
- モジュール間の循環 import は禁止（E0310）。依存は `use` だけで決まるので、この検査は `use` の一覧で閉じる。
  モジュール（パッケージを含む）を取り込む `use` は、取り込んだ束縛から下の全てのモジュールへ辿れるので、そのモジュールと下の全てのモジュールへの依存として数える（自分自身は除く）。本体の経路が実際に指すモジュールは見ない。§18.1 の名前の段の失敗した名前と、E0304・E0305 になった名前は数えない（並びのうち束縛になった名前は数える）。
  この数え方で循環になるときは、取り込む経路を狭めて直し、E0310 の note で狭め方を示す。note を付けるのは、モジュールを取り込む `use` を項目の取り込みに狭めて切れるときだけで（自分のファイルが無くディレクトリだけで在るモジュールは項目を持たないので、その狭め方は数えない）、切れなければ狭めても切れないことを示す。
- 暗黙の prelude は、`Option Result Some None Ok Err panic Alloc`、§6.3 の演算子 trait と標準 trait（数の trait と `Ordinal` を含む）、種の制約 `Copy` と `Dup`（§4.6）、組込み型だけである。
  クロックの名前（`init` `block` `sample` `event`）は prelude ではなく、クロックの名前空間にある（§11.3）。`panic`、種の制約、組込み型はコンパイラが与え、`Option` と `Result`（とその列挙子）、`Alloc`、trait は std の宣言である。
  prelude の名前は隠せないので（§5.1）、同じ名前の項目（型、trait、関数、定数、flow）を宣言するか `use` で取り込むと E0304 になる（`fn panic`、`use kp.panic`。prelude の名前を定義元から取り込み直す `use std.<モジュール>.{Option}` も同じで、修正候補は無い）。他の標準の効果と std の項目は `use` で取り込む。

### 15.2 target 宣言（条件コンパイルの代替）

```onsa
// audio/device.onsa
target type Device
target fn open(sample_rate: F32) -> Result[Device, DeviceError]
target rt fn read_input(inout d: Device, inout buf: Span[F32])
```

`target` 宣言は、**実装をビルドターゲットが与える** 宣言である。実装モジュールはターゲットごとにマニフェストの `bind` で割り当てる（OCaml/dune の virtual library と同じ考え方）。ソースの中に `#if` や `cfg` は無いので、**ソースの意味はターゲットによって変わらない**。

実装モジュールは、同じ名前と同じシグネチャ（`rt` と効果行を含む）の宣言を持たなければならない。これは検査される。検証されない主張である `extern "C"` とは、この点で異なる。

std の `target` 宣言（`std.math` の関数、組込み型のプリミティブのメソッドなど）は、処理系が与える。`bind` は書かず、std のモジュールを `bind` の左辺に書くこともできない。差し替えを許すと変換先ごとに結果が変わり、§13.4 の精度の約束が崩れるからである。速い近似が要るときは、別の名前の関数として書く。

std の `target fn` は、見出しの後ろの `else` に本体を持てる（std だけに許す書き方。`pub target rt fn abs[T: Num](x: T) -> T else { if x < T.ZERO { -x } else { x } }`）。
処理系がプリミティブを与える型（組込み型）ではプリミティブを使い、与えない型（利用者の数の型の `abs` / `min` / `max`、§13.4）では `else` の本体を使う。プリミティブの意味は §13.4 などで定める。
`else` は見出しの最後のトークンと同じ行に書く（§2.5。次の行は E0003）。印の無い `{` の本体は、std を含めてどのパッケージでも持てない（構文の段の E0002）。std の `target fn` は、固有の `impl` のメンバにも書ける（組込み型のプリミティブのメソッド）。
構文の段は trait の実装のメンバの `target fn` も同じに読む（std がそれを使うのは第 2 期、R-127）。`impl` の中の `target type` と `target const` は無く（E0002）、関連定数は値で書く（`0.0 / 0.0` も定数式）。

std の `target` 宣言は、境界を満たす全ての型で使えるのを原則とする。プリミティブも `else` の本体も無い型を受けないよう、弾ける所は境界で弾く（`exp[T: Float]`）。それでも具体化した型にプリミティブも `else` の本体も無ければ、使った位置で E0200（機能名と型を添える）になる。型で決まるので、下の変換先の E0200 と違い `onsa check` も報告する。

この版では、std の外の `target` 宣言は、形（本体の有無、トップレベルか `impl` のメンバか）によらず、名前の段の E0200 である。構文の段は、どのパッケージのファイルも同じ規則で読む。

std の `target` 宣言は、全ての変換先が与えるのを原則とする。この版で与えない変換先があれば、その実行やビルドの入口から届く位置でそれを使うプログラムは、その変換先へのビルドやインタプリタでの実行を始める前に、使った位置で E0200（機能名と変換先を添える）になる。
入口は、`onsa test` では走らせるテスト（`--filter` で選んだもの、§18.2）、ビルドでは export する項目などである。届くとは、入口から、呼ぶ関数、値として使う関数、インスタンスを作る flow、読む `const` の初期化式を静的にたどれることで、実行時に通るかどうかは見ない。`onsa check` は変換先によらないので、これを報告しない。

### 15.3 マニフェスト `onsa.toml`

```toml
[package]
name = "voice"
edition = "2026"

[export]
prefix = "vc_"          # @export の項目を出すビルドで必須。C の名前は prefix + 名前の最後の要素（§14.2）

[targets.cli]
kind = "exe"
platform = "macos-arm64"
fp = "strict"
provides = ["Fs", "Stdout", "Clock", "Alloc"]

[targets.plugin]
kind = "clap"
platform = "macos-arm64"
fp = "strict"
provides = ["Alloc"]

[targets.web]
kind = "source"
lang = "js"             # 移植可能な核だけを変換する（§13）
fp = "strict"

[targets.daisy]
kind = "staticlib"
platform = "thumbv7em-none-eabihf"
fp = "strict-ftz"
provides = []           # ヒープ無し
panic = "reset"         # 本番用。デバッグ時は "trap"
panic_messages = false
main_frame = "static"

[targets.daisy.memory]
bulk = true             # @mem(bulk) の遅延線を bulk 領域へ（§12.4）
fast_budget = 262144    # 任意。export する flow の fast 領域がこれを超えたらビルドで E0820

[targets.daisy.bind]
"audio.device" = "daisy_hal.audio"
```

**ターゲット** は次の組で定義する。

1. プラットフォーム（トリプル）。`platform = "host"` は、コンパイラが動く機械のトリプルを指す（開発とテスト用）。`kind = "source"` では変換先の言語（`lang`）
2. 浮動小数のプロファイル（`fp`、§15.5）
3. 提供する handler の集合（`provides`）。`Alloc` を含むかどうかで、ヒープの有無が決まる
4. `target` 宣言の割り当て（`bind`）
5. エントリの種類（`exe`, `clap`, `vst3`, `au`, `wasm-worklet`, `staticlib`, `source`）
6. メモリの設定（`bulk`、`fast_budget` / `bulk_budget`、`main_frame`）と panic の設定（`poison` / `trap` / `reset` / `halt`、§9.2）、コンパイラフラグ（§13.4）

マニフェストに書ける表とキーは、次の表で全てである。一覧に無い表とキーは E1102（§18.1）。仕様にあってこの版のコンパイラが未対応のもの（`kind` の `clap`、`lang` の `js`、std 以外の依存、`main_frame` など）は、使った位置で E0200 になり、黙って無視されない。
ターゲットに属する値（`kind`、`lang`、`main_frame` など）の E0200 は、そのターゲットのビルドと `--target` を取るコマンドで出す（未対応のターゲットがあっても、`check` と `test` は止まらない）。std 以外の依存の E0200 は、全てのコマンドに効くので、マニフェストの検査で出す。
どの値が未対応かはコンパイラの版で変わり、診断の文面と `onsa explain E0200` で示す。キーは、仕様の版で一覧に加えるときだけ増える。

| 表 | キー | 値と既定 |
|---|---|---|
| `[package]` | `name` | 必須。`snake_case` の識別子（`use` の経路の頭に書くので、モジュールの名前と同じ規則、§2.3）。`std` は書けない |
| | `edition` | 必須。この版で書けるのは `"2026"` だけ。版が意味を変えるときに、暗黙の既定でどちらの意味かが分からなくならないよう、省略できない |
| `[dependencies]` | `<パッケージ名>` | 版の文字列。この版で書けるのは `std` だけ（下記） |
| `[export]` | `prefix` | `@export` の項目（§14.2）を出すターゲットのビルドで必須（無ければ E1104） |
| `[targets.<名前>]` | `kind` | 必須。`exe` `clap` `vst3` `au` `wasm-worklet` `staticlib` `source` |
| | `platform` | ターゲットのトリプルか `"host"`。C かネイティブのコードを出すターゲット（`exe`、プラグイン、`staticlib`、`lang = "c"` の `source`）で必須で、無ければそのターゲットのビルドで E1104（生成物がポインタの幅などで変わるため）。トリプルの OS の欄が `none` のもの（`thumbv7em-none-eabihf`）を OS の無いプラットフォームとし、`panic` の既定（§9.2）と `ONSA_NO_TLS`（§14.2）が変わる |
| | `lang` | `kind = "source"` で必須。変換先の言語（`"c"`、`"js"`、§13） |
| | `fp` | `"strict"`（既定）、`"strict-ftz"`（§15.5） |
| | `provides` | 効果の名前の配列。既定は空で、ヒープ（`Alloc`）を含め、与える効果は全て書く |
| | `panic` | `"poison"`、`"trap"`、`"reset"`、`"halt"`。既定は §9.2 |
| | `panic_messages` | 真偽値。既定は `true`（§9.2） |
| | `main_frame` | `"stack"`（既定）、`"static"`（§12.5） |
| `[targets.<名前>.memory]` | `bulk` | 真偽値。既定は `false`（§12.4） |
| | `fast_budget`、`bulk_budget` | バイト数。任意 |
| `[targets.<名前>.bind]` | `"<モジュール>"` | 実装モジュールの経路（§15.2） |
| `[[plugin]]` | `flow` | 必須。プラグインにする flow の経路で、`@export` を付けた flow でなければ E1103（§14.3） |
| | `id`、`name`、`vendor` | 必須。文字列。同じ `id` の重複は誤り |
| | `version` | 必須。`major.minor.patch`（AU は各 255 以下） |
| | `category` | 必須。`instrument`・`effect`・`note-effect` |
| | `au` | AU のターゲットで必須。`{ subtype, manufacturer }` |

- `main` または export される関数の効果行に、`provides` に無い効果が含まれていれば E0610。
- `@export` の flow と関数は、`staticlib`・プラグイン・`wasm-worklet`・`source` のターゲットに出力される（依存のパッケージの `@export` は出さない、§14.2）。
- ビルドはハーメティック（ネットワークも環境変数も読まない）で、`onsa.lock` が同じなら、Onsa が生成するファイル（C のソースとヘッダ、WASM など）は同一である。`staticlib` の `.a`、実行ファイル、プラグインの束（§14.3）は外部の C ツールチェーンの出力で、この約束の外にある。
  ホストの `platform` では PATH の `cc` と `ar` を使う（環境変数を読む唯一の例外）。クロスの `platform` で外部のツールチェーンを要する `kind`（`staticlib`、プラグインなど）は、この版ではそのターゲットのビルドで E0200 になる（note で `kind = "source"` と `lang = "c"` を示す）。
  ツールチェーンを指定する形は §19.1。
- `std` は、どのパッケージにも暗黙の依存で、`[dependencies]` に書かなくてもキー `std` で使える（単一ファイルのパッケージも同じ）。std はコンパイラに埋め込まれている。`std = "x.y.z"` と書くと版の固定になり、埋め込みの std の版と一致しなければ E1103 になる。埋め込みの std の版は `onsa --version` で表示する。std 以外の依存の取得元、版の解決、`onsa.lock` の形は未決定（§19.1）。

### 15.4 ポリシー `onsa.policy`（延期）

この節は第 2 期の末尾以降に回す（§19.1）。人間の判断に残すもの（効果の付与、unsafe、公開インタフェース）は、ソースとは別のファイルに集める。

```toml
[effects]
main = ["Fs", "Stdout", "Alloc"]   # main の効果行がこれを超えたら E0620

[unsafe]
packages = ["daisy_hal"]           # unsafe / extern を書けるパッケージ

[interface]
frozen = ["voice"]                 # 公開シグネチャとパラメータ ID の変更は E0630
```

凍結の対象の候補には、export の集合（どの項目に `@export` があるか、§14.2）も入れる。`onsa check` はポリシーへの違反をエラーにする。`onsa audit` はポリシーと unsafe・extern の差分を表示する。運用では、エージェントにこのファイルの書き込み権限を与えない。

### 15.5 浮動小数のプロファイル

| プロファイル | 内容 | 再現性 |
|---|---|---|
| `strict`（既定） | IEEE 754、最近接偶数丸め、FMA への縮約なし、再結合なし、非正規化数あり。超越関数は各環境のプリミティブで、精度目標 2 ULP 以内（§13.4）。 | IEEE の演算は全ターゲット・全変換先でビット一致（NaN のビット表現は除く、§13.4）。超越関数は精度目標の範囲で一致 |
| `strict-ftz` | `strict` + 非正規化数をゼロに。入力の非正規化数を符号を保った 0 として扱い（DAZ）、結果の非正規化数を符号を保った 0 にする（FTZ） | 同じアーキテクチャのターゲットの間で、`strict` と同じ条件で一致。違うアーキテクチャの間では、最小の正規化数の境界の結果だけが違いうる（小さすぎるかの判定を丸めの前に行うか後に行うかが、アーキテクチャで違う） |
| `relaxed` | FMA と再結合を許可（ベクトル化のため） | 保証しない |

- `relaxed` が許すのは、FMA への縮約と再結合だけである。それ以外の簡約（`x + 0.0` を `x` にする、`(a + b) - b` を `a` にするなど）、NaN と無限大が無いという仮定、近似はしない。`relaxed` の中では、0 の結果の符号（§3.4）を約束しない。縮約は単独でも符号を変える（`F32` の `1e-23 * -1e-23 + 0.0` は、縮約しなければ `+0.0`、融合すれば `-0.0`）。
- `@fp(relaxed)` の緩和は、それを付けた fn と flow の呼び出しの中で行う全ての演算（そこから呼ぶ関数と flow の演算を含む）に、許可として及ぶ。処理系は一部だけ緩めても、全く緩めなくてもよい。呼び出しの外の演算は `strict` のままである。
  このため、`strict` の関数が約束する正確さと演算の順（`std.dsp.sum` の左から右への畳み込みなど）は、緩和した関数の呼び出しの中では成り立たず、`strict` の関数の中の値による判断（`== 0.0`、浮動小数から求めた添字、変換の panic）も、緩和した側から呼ばれると変わりうる。
- `strict-ftz` の用途: 帰還のある処理（フィルタ、リバーブ、遅延）は、入力が止まると非正規化数の範囲まで減衰し、x86 などでは非正規化数の演算が大きく遅くなる（無音の区間で負荷が跳ね上がる）。FTZ / DAZ はこれを避ける。失うのは約 `1.0e-38` より小さい値（約 −760 dB）だけである。
  結果が変わるので、全ての変換先でのビット一致を約束する `strict` とは別のプロファイルにしている。プラグインのホストは FTZ を有効にしていることが多いが、`strict` のターゲットでは Onsa の処理の中で外れる（下記）。帰還のある処理をプラグインで使うなら `strict-ftz` を選ぶ。
- `strict` と `strict-ftz` のターゲットの C の生成コードは、export した全ての入口（`init`、`process`、`reset`、export した関数。`exe` では `main` の始め）で、浮動小数の状態の全体（設定と例外のフラグ。x86 の MXCSR、ARM の FPSCR、AArch64 の FPCR と FPSR）を保存し、プロファイルの環境に設定する: 丸めは最近接偶数、例外はトラップしない、FTZ / DAZ は `strict` では無効で `strict-ftz` では有効。
  出るとき（panic の `longjmp` で抜けるときを含む）と、`ONSA_PANIC_HANDLER` を呼ぶ前（§14.2）に、保存した状態に戻す。値が既に同じなら書き込まない（ホストが既定の環境なら、読み出しだけで済む）。設定はスレッドごとの状態なので、`init` で一度だけ設定するのでは `process` を呼ぶスレッドに効かない。
  入口ごとに戻すので、ホストの計算に影響せず（Onsa の計算で立った例外のフラグもホストに残らない）、ホストがどう設定していても結果は同じになる。`round` が C の `rint`（今の丸めのモードに従う）に対応するのも、この設定の下で最近接偶数になる（§13.4）。
- 制御レジスタの扱い方を処理系が知るアーキテクチャは、この版では x86 と ARM である。それ以外のアーキテクチャの C の生成コードは、丸め・例外のフラグ・トラップを C の `<fenv.h>`（`feholdexcept`、`fesetenv`）で同じように扱う。FTZ / DAZ は扱えないので、`strict` はホストが FTZ / DAZ を有効にせずに呼ぶことを前提とする（`strict-ftz` は次の項のとおり E0200）。
- 制御レジスタを扱えない変換先（WASM、JavaScript、扱い方を処理系が知らないアーキテクチャ）では、`strict-ftz` はそのターゲットのビルドで E0200 になる。黙って `strict` の動きにはしない。
- インタプリタは、`strict-ftz` のターゲットとして実行するとき（`onsa test --target`、`--backends`）、FTZ / DAZ を模倣する。小さすぎるかの判定（丸めの前か後か）は、そのターゲットの `platform` のアーキテクチャのものを模倣し、同じアーキテクチャの C とビット一致する。
- F64 のハードウェアが無い `platform`（単精度の FPU だけの機器）では、F64 はソフトウェアの浮動小数で計算され、制御レジスタの FZ に従わない。`strict-ftz` では、生成コードが F64 の演算の入力と結果の非正規化数を、ソフトウェアで符号を保った 0 にする。
  F64 のハードウェアの有無によらず、`strict-ftz` の意味は一つである（F32 で処理し、精度の要る所だけ F64 を使う構成でも、`strict-ftz` を選べる）。`const` の評価はターゲットに依らない（§6.6）。焼き込んだ値が非正規化数なら、実行時に DAZ で 0 として読まれる。

ターゲットのプロファイルは、マニフェストの `fp` で選ぶ（既定は `strict`）。`relaxed` はターゲット全体には指定できない（`fp = "relaxed"` はエラー）。flow や関数ごとに `@fp(relaxed)` で付け、`onsa audit` に列挙される。`@fp(...)` の値は閉じた一覧から選び、今は `relaxed` だけである。C の側でファイル全体の精度を諦める方法は §13.4（`ONSA_ALLOW_INEXACT_FP`）。
