## 15. モジュール・パッケージ・ターゲット

### 15.1 モジュール

- 1 ファイル = 1 モジュール。モジュールのパスはパッケージルートからのファイルパスで、`mod` 宣言は無い。
  パッケージルートは `onsa.toml` のあるディレクトリで、その下の `.onsa` ファイルを再帰的に集める（`.` で始まる名前のディレクトリ（道具が作るもの）と、パッケージルート直下の `tests/` と `target/` を除く。`.` で始まるディレクトリの下のファイルを経路で渡したときは、その名前に §2.3 の規則を当てる（E0320）。それより深い `tests/` は普通のモジュールのディレクトリ）。
  ルート直下の `tests/` の役割は第 2 期に決める（§19.1）。この版では、そこに置いた `.onsa` ファイルはモジュールを集めるコマンド（`check`、`test`、`build` など）と LSP で E0200 になり、黙って無視されない。`.onsa` でないファイルは読まない。
  マニフェストの無い単一のファイル（`onsa check foo.onsa`）は、そのファイルを 1 モジュールのパッケージとして扱う（モジュール名はファイル名で、§2.3 の規則に従う。違反は E0320）。コマンドは、渡したファイル（無ければ作業ディレクトリ）から上の階層へ `onsa.toml` を探し、最初に見つけたディレクトリをパッケージルートにする。
  見つからなければ単一のファイルのパッケージである。パッケージを読むコマンドに渡す経路（ファイル、ディレクトリ、`onsa.toml`）は一つで、二つ以上は使い方の誤り（終了コード 2）である（一回の実行は一つのパッケージを扱う。`fmt` と `diff --ast` はファイルごとに処理するので、この規則の外）。
  ディレクトリの引数はパッケージのルート（`onsa.toml` のあるディレクトリ）を指し、`onsa.toml` を持たないディレクトリを渡すのは使い方の誤り（終了コード 2）である。パッケージの中のファイルを渡したときは、パッケージ全体を集めて解決する（`use` の解決に全体が要る）。診断が結果であるコマンド（`check` と LSP）は、そのファイルの診断だけを出す。
  `onsa test` が渡したファイルで選ぶテスト、出す診断、ファイルを複数渡したときの扱いは §18.2 に定める。
- 可視性は `pub`（パッケージ外に公開）、無指定（パッケージ内に公開）、`priv`（モジュール内のみ）の 3 段階。他のモジュールの項目は `use` で取り込んだ名前でだけ参照するので、パッケージ内に公開しても名前は衝突しない。パッケージの外に出るのは `pub` を書いたものだけである。
  `pub(pkg)` の形は無い（E0020、修正候補は外すこと。`pub (pkg)` のように空白を挟んでも一つの誤り）。
  他の言語の範囲を限る可視性（`pub(super)`、`pub(self)`、`pub(in a.b)`）と、`pub(` の後が `crate`・`pkg` でない他の形（`pub()`、`pub(package)` など）は、Onsa に同じ範囲が無いので、候補の無い E0002 で、note にこの 3 段階を示す（空白を挟んでも一つの誤り）。
- フィールドは、struct の可視性を継ぐ（`pub struct Point { x: F32, y: F32 }` の `x` と `y` は `pub`）。狭めたいフィールドにだけ `priv`（モジュール内のみ）を付ける（`pub struct Ring[T, const N: U32] { data: [T; N], priv head: U32 }`）。
  広げる向きの指定は無く、フィールドに `pub` を書くと継いでいるので冗長で E0020（修正候補は外すこと）。`priv struct` のフィールドの `priv` も同じく E0020。`pub struct` のフィールドをパッケージ内に限る書き方は無い。必要なら `priv` にして、作る関数と読む関数を無指定（パッケージ内）で置く。
  `pub struct` のフィールドに書いた `pub(crate)`・`pub(pkg)` は、外すと struct の `pub` を継いでパッケージの外へ広がるので、修正候補の無い E0002 で、note でこの書き方（`priv` にして作る関数と読む関数を無指定で置くか、外へ出してよければ外す）を示す（空白を挟んでも一つの誤り）。
  他の位置（項目、無指定と `priv` の struct のフィールド、`use`）の `pub(crate)`・`pub(pkg)` は、外す修正候補の E0020 のまま。enum の列挙子の中身は、enum の可視性を継ぐ。
- 宣言の外に見える部分（関数の引数と返り値、型別名の右辺、定数の型、フィールドと列挙子の中身、trait のメンバ）に、その宣言より狭い可視性の型を書くと E0303（`pub fn f() -> Inner` の `Inner` が無指定なら、パッケージの外の利用者は名前を書けない型を受け取ることになる）。狭めたいフィールドは `priv` にする。
- 見えないフィールドを読み書きすると E0303。見えないフィールドを持つ struct は、そのフィールドが見えない場所では struct リテラルで作れず（E0303）、作る関数を通す。可視性は必要以上に狭めない。隠すのは、不変条件を守るために外から書き換えられては困るフィールドだけにする。
- `use std.fs.{Fs, Path}`。グロブ import は無い。`use` で取り込んだ名前は、そのモジュールの中でだけ使える（項目と違い、無指定の `use` はパッケージ内に公開しない。`priv use` は冗長で E0020）。再公開は `pub use` のみで、取り込めるのは `pub` の項目だけ（`pub` でない項目の `pub use` は E0303）。
  `use` はモジュールのどの位置にも書ける。同じ名前を二度取り込むと E0304（束縛の重複）。モジュールの項目と、同じ名前の子モジュール（`a.onsa` の項目 `b` と `a/b.onsa`）も E0304。
- `use` の経路は絶対経路で、頭に書けるのは、自分のパッケージのルート直下のモジュールか、依存のパッケージ名（`[dependencies]` のキーと、暗黙の依存の `std`、§15.3）だけである。
  モジュールの項目や、`use` で取り込んだ名前からは始められない（`use std.math` の後でも `use math.{sin}` は E0302 で、修正候補は `use std.math.{sin}`）。各 `use` は、書く位置にも他の `use` にもよらずに決まる。自分のパッケージは名前で参照しない。
  中からはルートからの経路（`use dsp.synth.{voice}`）、外からはパッケージ名を付けた経路（パッケージ `fx` なら `use fx.dsp.synth.{voice}`）で書く。自分のパッケージ名を頭に書くと E0302（修正候補はパッケージ名を外すこと。同じ名前のルート直下のモジュールがあれば、それを指す）。
  ルート直下のモジュールの名前か、モジュールを含むルート直下のディレクトリの名前が、依存のパッケージ名（`std` を含む）と重なると E0304（利用者の `std.onsa` も `std/math.onsa` も）。同じ場所の `a.onsa` と `a/` は親のモジュールと子のモジュールで、重ならない（重なるのは、上の `a.onsa` の項目 `b` と `a/b.onsa`）。
- `use` の経路がたどれるのは、パッケージ、モジュール、flow の名前空間（§11.6）だけで、取り込めるのは、モジュールの項目、子モジュール、flow の名前空間の項目である。enum の列挙子（`Type.Variant` と書く、§4.1）、型の関連関数と関連定数（`Point.new`、`F32.PI`、§2.3 / §6.6）、効果の操作（`Fs.read`、§8.1）は取り込めない（E0302。文面で理由と書き方を示す）。
- 他のモジュールとパッケージは、`use` で取り込んだ名前でだけ参照できる（`use std.math` の後の `math.sqrt(x)`、`use std.math.{sqrt}` の後の `sqrt(x)`）。暗黙に見えるのは、自分のモジュールの項目、prelude、組込み型だけで、`use` の無い経路（`std.math.sqrt(x)`）は E0302（修正候補は `use` の追加）。モジュールが何に依存するかは、`use` の一覧を見れば全て分かる。
- 名前が見つからなければ E0302。名前は見つかったが、その位置に要る種類（値、型、モジュール、関数、flow、trait、列挙子、定数）でなければ E0308 で、直し方が違うので分ける。
  E0308 になるのは、型を値の位置に書く（`let a = P`）、値やモジュールを型の位置に書く、flow を型の位置に書く（修正候補は `lp.State`、§11.6）、定数を型引数の位置に書く、型を const 引数の位置に書く、パターンに列挙子でも定数でもない名前（型、trait、総称の定数のパラメータ）を書く（§7）、型でないものを `impl` の対象にする、名前空間でない名前の後に `.` を書く、メソッドを関数の形で呼ぶ（修正候補は `value.m(...)`）場合である。
  値を `x(...)` の形で呼ぶと、型によらず E0020（関数値は `x.(...)`、§6.1）。`.(` で呼んだ値の型が関数でない場合（`x: F32` の `x.(1.0)`）は型の誤りで E0401。
- モジュール間の循環 import は禁止（E0310）。依存は `use` だけで決まるので、この検査は `use` の一覧で閉じる。
- 暗黙の prelude は、`Option Result Some None Ok Err panic Alloc`、§6.3 の演算子 trait と標準 trait（数の trait と `Ordinal` を含む）、種の制約 `Copy` と `Dup`（§4.6）、組込み型だけである。
  クロックの名前（`init` `block` `sample` `event`）は prelude ではなく、クロックの名前空間にある（§11.3）。`panic`、種の制約、組込み型はコンパイラが与え、`Option` と `Result`（とその列挙子）、`Alloc`、trait は std の宣言である。
  prelude の名前は隠せないので（§5.1）、同じ名前の型や trait を宣言すると E0304 になる。他の標準の効果と std の項目は `use` で取り込む。

### 15.2 target 宣言（条件コンパイルの代替）

```onsa
// audio/device.onsa
target type Device
target fn open(sample_rate: F32) -> Result[Device, DeviceError]
target rt fn read_input(inout d: Device, inout buf: Span[F32])
```

`target` 宣言は、**実装をビルドターゲットが与える** 宣言である。実装モジュールはターゲットごとにマニフェストの `bind` で割り当てる（OCaml/dune の virtual library と同じ考え方）。ソースの中に `#if` や `cfg` は無いので、**ソースの意味はターゲットによって変わらない**。

実装モジュールは、同じ名前と同じシグネチャ（`rt` と効果行を含む）の宣言を持たなければならない。これは検査される。検証されない主張である `extern "C"` とは、この点で異なる。

std の `target` 宣言（`std.math` の関数、組込み型のプリミティブのメソッドなど）は、処理系が与える。`bind` は書かず、std のモジュールを `bind` の左辺に書くこともできない。差し替えを許すと変換先ごとに結果が変わり、§13.4 の精度の約束が崩れるからである。速い近似が要るときは、別の名前の関数として書く。

std の `target` 宣言は、本体を持てる（std だけに許す書き方）。処理系がプリミティブを与える型（組込み型）ではプリミティブを使い、与えない型（利用者の数の型の `abs` / `min` / `max`、§13.4）では本体を使う。プリミティブの意味は §13.4 などで定める。

std の `target` 宣言は、全ての変換先が与えるのを原則とする。この版で与えない変換先があれば、その実行やビルドの入口から届く位置でそれを使うプログラムは、その変換先へのビルドやインタプリタでの実行を始める前に、使った位置で E0200（機能名と変換先を添える）になる。
入口は、`onsa test` では走らせるテスト（`--filter` で選んだもの、§18.2）、ビルドでは export する項目などである。届くとは、入口から、呼ぶ関数、値として使う関数、インスタンスを作る flow、読む `const` の初期化式を静的にたどれることで、実行時に通るかどうかは見ない。`onsa check` は変換先によらないので、これを報告しない。

### 15.3 マニフェスト `onsa.toml`

```toml
[package]
name = "voice"
edition = "2026"

[export]
prefix = "vc_"          # 必須。C の名前は prefix + 名前の最後の要素（§14.2）
flows = ["dsp.voice", "dsp.echo"]
fns = ["util.version"]

[targets.cli]
kind = "exe"
platform = "macos-arm64"
fp = "strict"
provides = ["Fs", "Stdout", "Clock", "Alloc"]

[targets.plugin]
kind = "clap"
platform = "macos-arm64"
fp = "strict"
provides = ["Alloc"]

[targets.web]
kind = "source"
lang = "js"             # 移植可能な核だけを変換する（§13）
fp = "strict"

[targets.daisy]
kind = "staticlib"
platform = "thumbv7em-none-eabihf"
fp = "strict-ftz"
provides = []           # ヒープ無し
panic = "reset"         # 本番用。デバッグ時は "trap"
panic_messages = false
main_frame = "static"

[targets.daisy.memory]
bulk = true             # @mem(bulk) の遅延線を bulk 領域へ（§12.4）
fast_budget = 262144    # 任意。export する flow の fast 領域がこれを超えたらビルドで E0820

[targets.daisy.bind]
"audio.device" = "daisy_hal.audio"
```

**ターゲット** は次の組で定義する。

1. プラットフォーム（トリプル）。`platform = "host"` は、コンパイラが動く機械のトリプルを指す（開発とテスト用）。`kind = "source"` では変換先の言語（`lang`）
2. 浮動小数のプロファイル（`fp`、§15.5）
3. 提供する handler の集合（`provides`）。`Alloc` を含むかどうかで、ヒープの有無が決まる
4. `target` 宣言の割り当て（`bind`）
5. エントリの種類（`exe`, `clap`, `vst3`, `au`, `wasm-worklet`, `staticlib`, `source`）
6. メモリの設定（`bulk`、`fast_budget` / `bulk_budget`、`main_frame`）と panic の設定（`poison` / `trap` / `reset` / `halt`、§9.2）、コンパイラフラグ（§13.4）

マニフェストに書ける表とキーは、次の表で全てである。一覧に無い表とキーは E1102（§18.1）。仕様にあってこの版のコンパイラが未対応のもの（`kind` の `clap`、`lang` の `js`、std 以外の依存、`main_frame` など）は、使った位置で E0200 になり、黙って無視されない。
ターゲットに属する値（`kind`、`lang`、`main_frame` など）の E0200 は、そのターゲットのビルドと `--target` を取るコマンドで出す（未対応のターゲットがあっても、`check` と `test` は止まらない）。std 以外の依存の E0200 は、全てのコマンドに効くので、マニフェストの検査で出す。
どの値が未対応かはコンパイラの版で変わり、診断の文面と `onsa explain E0200` で示す。キーは、仕様の版で一覧に加えるときだけ増える。

| 表 | キー | 値と既定 |
|---|---|---|
| `[package]` | `name` | 必須。`snake_case` の識別子（`use` の経路の頭に書くので、モジュールの名前と同じ規則、§2.3）。`std` は書けない |
| | `edition` | 必須。この版で書けるのは `"2026"` だけ。版が意味を変えるときに、暗黙の既定でどちらの意味かが分からなくならないよう、省略できない |
| `[dependencies]` | `<パッケージ名>` | 版の文字列。この版で書けるのは `std` だけ（下記） |
| `[export]` | `prefix` | flow か関数を export するなら必須（§14.2） |
| | `flows`、`fns` | 項目（flow と関数）の経路の配列（`dsp.voice` はモジュール `dsp` の flow `voice`）。既定は空。見つからない経路は E0302、`pub` でない項目は E0303、種類の違う項目（`fns` に flow を書くなど）は E0308、同じ項目を二度書くと E1103（`span` は `onsa.toml` の中） |
| `[targets.<名前>]` | `kind` | 必須。`exe` `clap` `vst3` `au` `wasm-worklet` `staticlib` `source` |
| | `platform` | ターゲットのトリプルか `"host"`。C かネイティブのコードを出すターゲット（`exe`、プラグイン、`staticlib`、`lang = "c"` の `source`）で必須で、無ければそのターゲットのビルドで E1104（生成物がポインタの幅などで変わるため）。トリプルの OS の欄が `none` のもの（`thumbv7em-none-eabihf`）を OS の無いプラットフォームとし、`panic` の既定（§9.2）と `ONSA_NO_TLS`（§14.2）が変わる |
| | `lang` | `kind = "source"` で必須。変換先の言語（`"c"`、`"js"`、§13） |
| | `fp` | `"strict"`（既定）、`"strict-ftz"`（§15.5） |
| | `provides` | 効果の名前の配列。既定は空で、ヒープ（`Alloc`）を含め、与える効果は全て書く |
| | `panic` | `"poison"`、`"trap"`、`"reset"`、`"halt"`。既定は §9.2 |
| | `panic_messages` | 真偽値。既定は `true`（§9.2） |
| | `main_frame` | `"stack"`（既定）、`"static"`（§12.5） |
| `[targets.<名前>.memory]` | `bulk` | 真偽値。既定は `false`（§12.4） |
| | `fast_budget`、`bulk_budget` | バイト数。任意 |
| `[targets.<名前>.bind]` | `"<モジュール>"` | 実装モジュールの経路（§15.2） |
| `[[plugin]]` | `flow` | 必須。プラグインにする flow の経路で、`[export]` の `flows` にあること（§14.3） |
| | `id`、`name`、`vendor` | 必須。文字列。同じ `id` の重複は誤り |
| | `version` | 必須。`major.minor.patch`（AU は各 255 以下） |
| | `category` | 必須。`instrument`・`effect`・`note-effect` |
| | `au` | AU のターゲットで必須。`{ subtype, manufacturer }` |

- `main` または export される関数の効果行に、`provides` に無い効果が含まれていれば E0610。
- `[export]` の flow と関数は、`staticlib`・プラグイン・`wasm-worklet`・`source` のターゲットに出力される。
- ビルドはハーメティック（ネットワークも環境変数も読まない）で、`onsa.lock` が同じなら、Onsa が生成するファイル（C のソースとヘッダ、WASM など）は同一である。`staticlib` の `.a`、実行ファイル、プラグインの束（§14.3）は外部の C ツールチェーンの出力で、この約束の外にある。
  ホストの `platform` では PATH の `cc` と `ar` を使う（環境変数を読む唯一の例外）。クロスの `platform` で外部のツールチェーンを要する `kind`（`staticlib`、プラグインなど）は、この版ではそのターゲットのビルドで E0200 になる（note で `kind = "source"` と `lang = "c"` を示す）。
  ツールチェーンを指定する形は §19.1。
- `std` は、どのパッケージにも暗黙の依存で、`[dependencies]` に書かなくてもキー `std` で使える（単一ファイルのパッケージも同じ）。std はコンパイラに埋め込まれている。`std = "x.y.z"` と書くと版の固定になり、埋め込みの std の版と一致しなければ E1103 になる。埋め込みの std の版は `onsa --version` で表示する。std 以外の依存の取得元、版の解決、`onsa.lock` の形は未決定（§19.1）。

### 15.4 ポリシー `onsa.policy`（延期）

この節は第 2 期の末尾以降に回す（§19.1）。人間の判断に残すもの（効果の付与、unsafe、公開インタフェース）は、ソースとは別のファイルに集める。

```toml
[effects]
main = ["Fs", "Stdout", "Alloc"]   # main の効果行がこれを超えたら E0620

[unsafe]
packages = ["daisy_hal"]           # unsafe / extern を書けるパッケージ

[interface]
frozen = ["voice"]                 # 公開シグネチャとパラメータ ID の変更は E0630
```

`onsa check` はポリシーへの違反をエラーにする。`onsa audit` はポリシーと unsafe・extern の差分を表示する。運用では、エージェントにこのファイルの書き込み権限を与えない。

### 15.5 浮動小数のプロファイル

| プロファイル | 内容 | 再現性 |
|---|---|---|
| `strict`（既定） | IEEE 754、最近接偶数丸め、FMA への縮約なし、再結合なし、非正規化数あり。超越関数は各環境のプリミティブで、精度目標 2 ULP 以内（§13.4）。 | IEEE の演算は全ターゲット・全変換先でビット一致（NaN のビット表現は除く、§13.4）。超越関数は精度目標の範囲で一致 |
| `strict-ftz` | `strict` + 非正規化数をゼロに。入力の非正規化数を符号を保った 0 として扱い（DAZ）、結果の非正規化数を符号を保った 0 にする（FTZ） | 同じアーキテクチャのターゲットの間で、`strict` と同じ条件で一致。違うアーキテクチャの間では、最小の正規化数の境界の結果だけが違いうる（小さすぎるかの判定を丸めの前に行うか後に行うかが、アーキテクチャで違う） |
| `relaxed` | FMA と再結合を許可（ベクトル化のため） | 保証しない |

- `relaxed` が許すのは、FMA への縮約と再結合だけである。それ以外の簡約（`x + 0.0` を `x` にする、`(a + b) - b` を `a` にするなど）、NaN と無限大が無いという仮定、近似はしない。`relaxed` の中では、0 の結果の符号（§3.4）を約束しない。縮約は単独でも符号を変える（`F32` の `1e-23 * -1e-23 + 0.0` は、縮約しなければ `+0.0`、融合すれば `-0.0`）。
- `@fp(relaxed)` の緩和は、それを付けた fn と flow の呼び出しの中で行う全ての演算（そこから呼ぶ関数と flow の演算を含む）に、許可として及ぶ。処理系は一部だけ緩めても、全く緩めなくてもよい。呼び出しの外の演算は `strict` のままである。
  このため、`strict` の関数が約束する正確さと演算の順（`std.dsp.sum` の左から右への畳み込みなど）は、緩和した関数の呼び出しの中では成り立たず、`strict` の関数の中の値による判断（`== 0.0`、浮動小数から求めた添字、変換の panic）も、緩和した側から呼ばれると変わりうる。
- `strict-ftz` の用途: 帰還のある処理（フィルタ、リバーブ、遅延）は、入力が止まると非正規化数の範囲まで減衰し、x86 などでは非正規化数の演算が大きく遅くなる（無音の区間で負荷が跳ね上がる）。FTZ / DAZ はこれを避ける。失うのは約 `1.0e-38` より小さい値（約 −760 dB）だけである。
  結果が変わるので、全ての変換先でのビット一致を約束する `strict` とは別のプロファイルにしている。プラグインのホストは FTZ を有効にしていることが多いが、`strict` のターゲットでは Onsa の処理の中で外れる（下記）。帰還のある処理をプラグインで使うなら `strict-ftz` を選ぶ。
- `strict` と `strict-ftz` のターゲットの C の生成コードは、export した全ての入口（`init`、`process`、`reset`、export した関数。`exe` では `main` の始め）で、浮動小数の状態の全体（設定と例外のフラグ。x86 の MXCSR、ARM の FPSCR、AArch64 の FPCR と FPSR）を保存し、プロファイルの環境に設定する: 丸めは最近接偶数、例外はトラップしない、FTZ / DAZ は `strict` では無効で `strict-ftz` では有効。
  出るとき（panic の `longjmp` で抜けるときを含む）と、`ONSA_PANIC_HANDLER` を呼ぶ前（§14.2）に、保存した状態に戻す。値が既に同じなら書き込まない（ホストが既定の環境なら、読み出しだけで済む）。設定はスレッドごとの状態なので、`init` で一度だけ設定するのでは `process` を呼ぶスレッドに効かない。
  入口ごとに戻すので、ホストの計算に影響せず（Onsa の計算で立った例外のフラグもホストに残らない）、ホストがどう設定していても結果は同じになる。`round` が C の `rint`（今の丸めのモードに従う）に対応するのも、この設定の下で最近接偶数になる（§13.4）。
- 制御レジスタの扱い方を処理系が知るアーキテクチャは、この版では x86 と ARM である。それ以外のアーキテクチャの C の生成コードは、丸め・例外のフラグ・トラップを C の `<fenv.h>`（`feholdexcept`、`fesetenv`）で同じように扱う。FTZ / DAZ は扱えないので、`strict` はホストが FTZ / DAZ を有効にせずに呼ぶことを前提とする（`strict-ftz` は次の項のとおり E0200）。
- 制御レジスタを扱えない変換先（WASM、JavaScript、扱い方を処理系が知らないアーキテクチャ）では、`strict-ftz` はそのターゲットのビルドで E0200 になる。黙って `strict` の動きにはしない。
- インタプリタは、`strict-ftz` のターゲットとして実行するとき（`onsa test --target`、`--backends`）、FTZ / DAZ を模倣する。小さすぎるかの判定（丸めの前か後か）は、そのターゲットの `platform` のアーキテクチャのものを模倣し、同じアーキテクチャの C とビット一致する。
- F64 のハードウェアが無い `platform`（単精度の FPU だけの機器）では、F64 はソフトウェアの浮動小数で計算され、制御レジスタの FZ に従わない。`strict-ftz` では、生成コードが F64 の演算の入力と結果の非正規化数を、ソフトウェアで符号を保った 0 にする。
  F64 のハードウェアの有無によらず、`strict-ftz` の意味は一つである（F32 で処理し、精度の要る所だけ F64 を使う構成でも、`strict-ftz` を選べる）。`const` の評価はターゲットに依らない（§6.6）。焼き込んだ値が非正規化数なら、実行時に DAZ で 0 として読まれる。

ターゲットのプロファイルは、マニフェストの `fp` で選ぶ（既定は `strict`）。`relaxed` はターゲット全体には指定できない（`fp = "relaxed"` はエラー）。flow や関数ごとに `@fp(relaxed)` で付け、`onsa audit` に列挙される。`@fp(...)` の値は閉じた一覧から選び、今は `relaxed` だけである。C の側でファイル全体の精度を諦める方法は §13.4（`ONSA_ALLOW_INEXACT_FP`）。
