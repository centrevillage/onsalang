## 18. 診断とツール

### 18.1 診断

```json
{
  "code": "E0811",
  "message": "`resonator` is a flow; calling it creates a stateful instance and needs `~`",
  "span": { "file": "dsp.onsa", "line": 12, "col": 13, "end_line": 12, "end_col": 22 },
  "found": "resonator(src, vowel_f1, 80.0)",
  "fixes": [
    { "title": "add `~`",
      "edits": [
        { "span": { "file": "dsp.onsa", "line": 12, "col": 22, "end_line": 12, "end_col": 22 },
          "replace": "~" }
      ] }
  ],
  "notes": []
}
```

- `span` は 1 から数える行と列の半開区間で、`end_col` の文字は含まない。列は文字（Unicode のスカラー値）で数える。`end_line` は常に出す。LSP のサーバは、この列を LSP の単位（UTF-16 など）に変換して返す。
- `fixes` は修正候補の並びである。一つの候補は、短い説明（`title`）と編集の並び（`edits`）を持つ。編集は、範囲（`span`）とそこを置き換える文字列（`replace`）の組で、挿入は空の範囲の置き換えで表す（上の例は `~` の挿入）。一つの候補の編集はまとめて当て、別のファイルにまたがってもよい。同じ候補の編集の範囲は重ならない。
  編集は、変えるトークンだけを置き換える最小の編集で、間の残すトークンとコメントを範囲に含めない（`<T>` を `[T]` にする候補は、`<` と `>` を置き換える二つの編集である）。ただし、消すトークンに挟まれたコメントは、トークンと一緒に消してよい（候補は提案で、書き手は字のまま当てなくてよい）。
  編集の範囲の外にある文字の字句の読み（トークンとコメントの種類と範囲）は、当てた後も変わらない（範囲の外のコードをコメントに取り込むなど、範囲の外の読みを変える候補は作らない）。
  候補を当てる前の単位（下記）のうち、その文字（メンバを持つ項目の単位では、メンバの外の部分）に編集も中への挿入も無く、編集による長さの差だけずらした同じ範囲が当てた後も一つの単位であるものを、その候補が触れていない単位と呼ぶ。
  当てる前と当てた後のどちらでも、他の全ての単位（編集を含む単位、境目が動いた単位、当てて新しくできた単位）を触れた単位と呼ぶ。どの候補も、一つだけを当てて検査し直したとき、元の診断が、当てる前の触れた単位の全てで同じ段かそれより前の段の唯一の誤りなら、当てた後の触れた単位の全てに、同じ段かそれより前の段（段の順は下記）の診断を残さない。後の段の診断は出てよい（隠れていた別の誤りである）。
  この約束を満たす候補を作れなければ、候補を出さない。一つの診断は一つの誤りを指し、候補が複数あるのは直し方が一意に決まらないときだけである。
  本文と既存言語の書き方の一覧（下記）が書く候補の形（置き換える文字列と候補の並べ方）は、候補を説明する例で、約束ではない。
  約束するのは、上の安全と、編集の形（変えるトークンだけの最小の編集と、範囲の外の読み）と、候補の数（候補を出さないことを含む）と、本文が規則として書く候補の意味の性質（値を変えない、など）である。
  一つの構文の形（一つの経路の全ての `::`（`[` が続かない `::` で、`::[…]` の前後を問わない。`Buf::[F32]::zeroed(4)` は一つの誤りで、候補は `Buf::[F32].zeroed(4)`）、一つの型引数の並びの入れ子の括弧（`Option<Option<I32>>`）、続いた `;`（`;;`）、一つの腕のパターンのガードの形の候補を持つもの（§7。構文の段と型の段のそれぞれで一つ））は一つの誤りで、一つの候補がその全てを直す。
  別々の文を区切る `;`（`let a = 1; let b = 2`）は別々の誤りである。
- `notes` は note の並びで、要素は `message` と、位置があるときだけ `span` を持つ。位置の無い note は規則や書き方の説明（E0020 の正しい規則など）で、位置付きの note は関係する位置（閉じていない `{` を開いた宣言など）を示す。並び（`fixes`、`notes`）は空でも出し、値の無い欄（`found`、note の `span`）は出さない。
  `found` は問題のソースの文字列で、範囲が空か空白（§2.5 の U+0020 とタブと改行）だけなら出さない。NBSP などの書けない文字は空白ではないので、その E0001 には `found` を出す。
- `--json` を付けたコマンドの標準出力は一つの JSON のオブジェクトで、診断は `diagnostics` の配列に入れる（診断が無ければ空の配列）。`onsa test --json` は、同じオブジェクトにテストの結果の `tests` の配列を足す（下記）。空白と改行の置き方は約束しない。読み手は知らない欄を読み飛ばし、欄を足すことは互換を壊さない変更とする。
  `span.file` はパッケージのルート（`onsa.toml` のあるディレクトリ）からの経路で、区切りは `/` である（マニフェストの無い入力は、渡した経路の区切りを `/` にしたもの）。
  パッケージの外のファイル（std と依存のパッケージ）は、そのパッケージの名前と、そのパッケージのルートからの経路を `/` でつないだもの（`std/dsp/test.onsa`）である（ルート直下の名前は依存のパッケージ名と重ならない、§15.1）。
  `diagnostics` は、`file` の文字列（コードポイントの順）、行、列、終わりの行、終わりの列、コード、文面の順に並べる（テキストの出力も同じ順、[`spec/tools.md`](tools.md) §4）。作業ディレクトリ、機械、ロケールで出力が変わらないためである。
- `tests` の記録は、`module`（モジュールの経路）、`name`（テストの名前の値）、`status`（`ok` か `failed`）を持ち、失敗した記録だけが `failure` を持つ。`failure` は、`message`（panic の文面）、`span`（panic した式の位置。`assert` は文全体）、`calls`（呼び出しの位置の並び）を持つ。
  `calls` は、panic した位置からテストの本体まで遡る呼び出しの位置を内側から外へ並べたもので、要素は `span` を持つ。最後の要素はテストの本体の中にあり、`calls` が空なら `span` がテストの本体の中にある。`message` が約束するのは、`assert` の失敗の `assert <式のソース>` と、`panic(msg)` の `msg` だけである。
  式のソースは、式の範囲のソースの文字列（`found` と同じ切り出し）を書いたままにしたもので、改行・字下げ・範囲の中のコメントを含み（文の後ろの行末のコメントは範囲の外で、入らない）、改行は LF にそろえる（CR LF を LF にする。`onsa fmt` が揃えるのと同じ、§2.5）。
  検査の誤りや E0200 でテストを走らせなかったときも、`tests` は空の配列として出す（走らせなかったことは `diagnostics` と終了コードで分かる）。`tests` は、`module`、次に `name` の文字列（コードポイントの順）で並べる。

| 範囲 | 分類 |
|---|---|
| E00xx | 字句・構文・演算子の群 |
| E02xx | この版のコンパイラでは未対応の機能（E0200。機能名を添える） |
| E03xx | モジュール・名前解決・シャドーイング・循環 |
| E04xx | 型・アリティ・フィールド・リテラルの型 |
| E05xx | 網羅性・到達しない文と腕 |
| E06xx | 効果・`Alloc`・ターゲットの provides と扱える幅・ポリシー |
| E07xx | 引数モード・排他性・Affine・第二級の値 |
| E08xx | flow（順序と因果性・レート・遅延・@param・`~`） |
| E09xx | rt |
| E10xx | FFI・unsafe・トランスパイル |
| E11xx | マニフェスト（`onsa.toml`） |

- 診断コードは、一つの種類の誤りに一つを割り当てる。単位は、`onsa explain` が一つの直し方を示せる範囲である。直し方が同じならまとめ（効果行に無い効果の使用は、確保も破棄も E0601）、違えば分ける（flow の本体に fn だけの構文を書く E0806 と、flow の外に flow だけの構文を書く E0821）。型の不一致（E0401）は、型の組み合わせごとには分けない。
  直し方は「式か型を合わせる」の一つで、違いは文面と修正候補で示す。仕様が拒否する規則には、全て本文にコードを書く（テストを仕様だけから書き、修復のループが安定したコードに依存できるようにするため、P8）。
- **型付きホール**: 式の位置に `_` を書くと、期待される型、使える効果、スコープ内の候補が報告され（E0421）、ビルドは失敗する。
- 診断の単位は宣言である。トップレベルの各項目と、`impl` / `trait` / `effect` / `handler` / `extern` の各メンバ（メソッド、関連定数）がそれぞれ一つの単位で、flow と `test` も一つの単位である。`impl` の見出し（`impl Tr for Ty`）に誤りがあれば `impl` 全体を一つの単位とし、メンバは検査しない（誤りは見出しの単位に診断の出る誤りで、見出しに書いた失敗した名前（下の誤りのある宣言の段落）は当たらない）。
  どの項目にも入らない余分なトークンは、ひと続きごとに一つの単位とする。ひと続きは次の項目の始まりまでで、行をまたいでも一つである。
  項目の始まりは、見出しを始めるトークン（項目のキーワード（`fn`、`pub`、`struct`、`flow`、`impl` など）と属性の始まり（`@` と、他言語の属性の `#[`））、doc コメント、行頭で見出しの前に並ぶ語（下の読み続ける形の `export fn h`、`export "C" fn h`）である。
  回復が止まる位置（括弧が閉じた位置、閉じない `{` の字下げの規則、メンバの並び）は、どれもこの定義で見る。項目と同じ行の後ろに置いた `;`（`const A: Bool = 1;`）は、その項目の単位に入る（項目を終える書き方の誤りで、その項目の構文の誤りである）。
- 一つの単位の中では、最初のエラーで検査を止める。単位どうしは独立に検査し（P1）、全ての単位のエラーを一度に報告する。修復ループ（P8）の回数を減らすためである。検査の段には依存の順がある（構文 → 名前 → 型 → flow の検査 → 引数のモードと移動 → rt と効果）。ある段が誤りを見つけた単位では、その結果に依存する後の段を行わない。
  失敗した段の結果を前提にすると、偽の診断が出るからである（構文の誤りがある単位では本体の名前解決と型検査をせず、名前の誤りがある単位では型検査をせず、flow の誤りがある単位では引数のモードと移動、rt と効果の検査をせず、移動の誤りがある単位では rt と効果の検査をしない）。
  見えない名前・フィールド・メンバの E0303（§15.1）は名前の段である。見出しに書いた名前が宣言の届く範囲より狭い E0303（§15.1）は型の段である。
  flow の検査のうち名前と字面で決まるものは名前の段である: 呼び先が flow かどうかで決まる `~` の有無と、インスタンスの修飾子の `~` の有無・受け手・名前（E0811、E0812、§11.10）、flow の外の flow だけの構文（E0821）、flow の本体の名前の順（E0801 と、見えている名前への `^` の E0020、§11.2）、本体の制限（E0806。代入の形を含む）、flow の見出しの時計の欠けと、入出力に書いた時計の種類（E0810、§11.3。一番外の flow の境界の `sample / N`・`sample * N` の E0810 は使い方で決まるので flow の検査の段、§11.9）、入力のモード（E0806、§11.2）。
  `if` / `match` の枝の状態を持つものの E0811 と、状態を持つものの無い `if~` / `match~` の E0812（§2.6）は flow の検査の段である。後の段の診断が既に出ていても報告しない。構文の誤りがある単位では、見出しだけを読めた命名の誤り（E0320）も報告しない。依存する段の間では、位置によらず先の段の誤りを報告する。
  残った診断のうち、`diagnostics` の並べ方（上記。開始の位置、終わりの位置、コード、文面の順）で最初のものを報告する（互いに依存しない段の診断は、どれも本物である）。
- Core への降下とビルド（コード生成、配置、リンク）の診断は、検査を全て通った単位にだけ出る。検査の誤りから連鎖しないので、単位で絞らず全て報告し、位置・コード・文面が同じものだけを一つにする（同じ原因が同じ診断になるよう、原因のソースの位置と文面で出し、生成した関数の名前を含めない）。パッケージやターゲットの全体に関わる診断（C の名前の重なりの E1011、容量の E0820、ポリシーなど）は、宣言の単位に入れず、それぞれ報告する。
- マニフェストの誤りも同じ形の診断で、`span` は `onsa.toml` の中の位置を指す。E1101 は TOML として読めない。E1102 は未知の表・キーで、その表で書けるキー（最上位では表の名前）を note に並べる。
  E1103 は値の型や形が規則に合わない（閉じた一覧に無い値、`prefix` とパッケージ名の形、std の版の不一致、`[[plugin]]` の値の形と `id` の重複と `@export` の flow でない `flow`（§15.3））で、閉じた一覧に無い値ではその一覧の値を、std の版の不一致では埋め込みの std の版を note に示す。
  E1102 と E1103 は、綴りの近いキーや値を修正候補にしない（§15.1 の E0302 と同じく、綴りの誤りは書き手の意図が一つに決まらないことが多く、note の一覧から正しい語を選べる）。E1104 は必須のキーが無いで、値が決まるときはキーの挿入を修正候補にする。
  マニフェストは全体で一つの単位（修正候補の安全の約束を当てる範囲）で、単位の中の最初の誤りで止める規則は当てず、全ての誤りを報告する。マニフェストを読む全てのコマンドと LSP は、ソースを読む前にマニフェスト全体（全てのターゲット）を検査し、誤りがあれば終了コード 2 で止まる（§18.2）。
  `onsa.toml` を指す診断（E11xx、マニフェストの E0200）は、全て終了コード 2 である。マニフェストの誤りはソースの編集では直らないので、修復のループが止まるよう終了コードで分ける。
  ターゲットに依る検査（`platform` が要るか、そのプラットフォームを扱えるか、`prefix` が要るか（`@export` の項目を出すか、§14.2））は、そのターゲットのビルドで行う。`--target` に無い名前を渡すのはコマンドの使い方の誤りで、診断コードは付かない。
- E0200 は、この版のコンパイラが扱えない機能や形を、機能名を添えて知らせる。仕様がこの版で未対応と定めたもの、変換先が与えないもの（§15.2、§15.5）、仕様にあってコンパイラがまだ扱えないもの（機能の一部の形を含む）を含む。コンパイラは扱えない形を黙って誤った結果にせず、検出した位置で E0200 にする。この版で書ける別の形があれば note で示す。一つの使用が複数の入口（テスト）や総称の関数の複数の具体化から届いても、位置・コード・文面が同じ E0200 は一件である。
  どの機能が未対応かはコンパイラの版で変わり、`onsa explain E0200` で示す。仕様が意味を定めていない形も、既存の規則の読みで拒めればその規則のコードにし、どの規則にも当たらない読める形だけを E0200 にする（読めなければ E0002）。
  降下やコード生成の予期しない内部の失敗は E0200 ではなく内部エラーで（§18.2 の終了コード 101。診断コードは付けない）、コマンドはそこで止まる。修復のループが、コードの誤りでないものを直しに行かないためである。
- 誤りのある宣言も、名前まで読めれば名前解決に見せる。読めなかった部分（引数の型、フィールドなど）は誤りの型として扱い、それを使う側には診断を出さない。正しい宣言に偽の連鎖エラーを出さないためである。
  名前の段で失敗した `use`（取り込む先が無い、見えない、取り込めない種類）と、取り込む名前まで読めた構文の段の誤りの `use`（`use kp.clock` の E0200、`use std.test` の E0002、§15.1）の取り込む名前も同じで、使う所はその名前を誤りとして扱い、診断を出さない（経路が失敗すれば並びの全ての名前、要素が失敗すればその名前）。
  取り込む名前を全部は読めなかった構文の段の誤りの `use`（並びや経路の途中で切れた形）は、読めた名前を同じく扱い、その `use` のあるモジュールで見つからない名前を使う所にも診断を出さない（空の並びは何も取り込まないので当たらない）。
  失敗した `use` の名前は束縛として数えず、同じ名前の他の束縛との E0304 の相手にせず（同じ名前の本物の束縛が見えていれば、使う所はそれを指す）、依存（E0310、§15.1）にも数えない。一つの `use` で二つ以上の名前が失敗しても、報告は単位ごとに一つである。
  型で有無が決まる flow の生成項目（`process_inplace`、§11.6）を取り込む `use` は、名前の段では解決した束縛で、E0310 の依存に数える。型の段で無いと分かれば、その `use` に E0302 を出し、以後その名前を失敗した名前として扱う（署名に誤りのある flow で有無が分からないときは、E0302 も出さない）。
  E0304・E0305 になった名前も、その空間（本体、モジュールの名前空間、経路の頭、§15.1）では、使う所と他のモジュールの経路はどちらの宣言も引かず、その名前を誤りとして扱う。その名前を取り込む `use` は、報告しなかった側も含めて依存（E0310、§15.1）に数えない。報告しなかった側の宣言の単位は検査する（ローカルの E0304 の後は、上の単位の規則で同じ単位の以後を報告しない）。
  これらの失敗した名前と、構文の誤りで途中まで読んだ struct・enum の読めなかったメンバの名前（`E.Zed`）は、使う単位には診断が無いので、型と宣言の位置では単位の最初のエラーに数えず、読めなかった部分として読み、同じ単位の検査を続ける（止めると、その名前だけで単位の全体が診断の無いまま未検査になるため）。
  型の位置（署名、型引数、関数の型、配列長（配列のリテラルの反復数 `[x; N]` を含む）、`impl` の見出し、本体の注釈）では誤りの型、総称の境界では未知の境界（その型引数が trait を満たすかに頼る判定（演算子、メソッド、他の関数の境界の要求）には診断を出さない）として読む。
  誤りの型の部分は、`match` の網羅性では何にでも一致するとみなし（他の部分の欠けは報告する）、誤りの型の値を呼ぶときは引数のモードと移動を検査せず（呼ぶ先のモードが分からないため）、誤りの型の値への `?` は関数の返り値の側も検査しない。
  効果行では、読めた効果（`Alloc`、効果の変数）を残し、失敗した名前は未知の効果として、行を開いた行にする（その名前が指しえた効果に頼る判定には診断を出さない）。
  値の位置（失敗した名前を経路として書いた式とパターン。flow の定数式を含む）では、その単位の以後を検査しない。呼ぶ先や値が分からないと、後の段（引数のモードと移動、効果、rt、flow の状態の大きさ、定数の評価）の全てがそれを扱う必要があるためである。
  名前の段の E0200 の `pub use`（§15.1）の取り込む名前も失敗した名前で、他のモジュールがそれを取り込む `use main.{g}` の名前も誤りとして扱い、診断を出さない（取り込む名前が子モジュールか項目の定義にあれば、それを指す。`pub use kp.inner` と `main/inner.onsa` の後の `use main.{inner}` は子モジュール）。
  経路の途中にその名前を通す形（`use main.inner.{g}`）は、経路の途中を子モジュールと項目の定義だけから引くので E0302 である。
  名前（extern のブロックでは `{`）より前にある誤りで、範囲が同じ行の中で閉じ、同じ行の後ろに見出しの続き（属性・可視性・`rt`・宣言のキーワード、extern の見出しの `{`）があるものは、形を一つの誤りで報告した後に続きから読み続け、名前まで読めた宣言として名前解決に見せる（単位には構文の誤りがあるので、本体は検査しない）。当たる形を以下に挙げる。
  名前より前（属性と可視性）にある既存言語と旧版の形と Onsa の属性の誤り（E0005 と引数の構文の誤り。`pub(crate)`・`pub(pkg)`・`pub(super)`、同じ行の `#[…]`、`@derive(…)`、`@fp(relaxed, 1 +)` など）は、形の後ろから属性・可視性・宣言を読み続ける。
  読み続けた宣言は、誤りの形を除いた見出しとして記録する。正しく書かれた属性・可視性・`rt` は書かれたとおりで、除いた形が与えうる性質は無指定か未知である。
  可視性は、正しく書かれた可視性が一種類（`pub` だけか `priv` だけ。重なりは一つと数える）で、可視性の形が無ければ書かれたとおり、それ以外は無指定である（`#[inline] pub fn h`・`pub pub fn h` は `pub`、`pub(crate) fn h`・`pub(crate) pub fn h`・`priv pub fn h` は無指定）。置き場所の無い `rt`（`fn` 以外の宣言の前）は記録しない。
  誤りの属性の付いた struct・enum では、derive の一覧と `@repr` の値を読めなかった部分として扱い（属性の中身は読まない）、それに頼る使う側（trait を満たすかの判定、derive が作るメソッド、§6.4 の derive と手で書いた `impl` の重なり、FFI の配置）には診断を出さない。
  項目の位置（トップレベルと `impl` / `trait` / `effect` / `handler` / `extern` のメンバ。その場に書いた handler のメンバも）で、同じ行の見出しの前に表に無い語（他の言語の修飾の `export`、`public`、`static`、`async`、`unsafe` など。予約語の `unsafe`・`static` もこの並びの語に数える）が並び、その直後が見出しを始められるトークン（可視性、`@`・`#[`、項目のキーワード）のときは、並びを一つの E0002 にし（見出しは `pub`・`priv` と宣言のキーワードで始まり、他の言語の修飾は無いと note で示す）、その後ろから同じく読み続ける。
  宣言のキーワード `const`・`extern` の見出しが名前の前で読めず（`extern` は文字列の後の `lib` の前で）、失敗したトークンが同じ行の項目のキーワードのとき（`const fn h`、`extern "C" fn h`）も、キーワードと文字列を一つの E0002 にし（宣言のキーワードの後に別の宣言のキーワードは書けないと note で示す）、項目のキーワードから同じく読み続ける。
  上の並びには、語の後ろの文字列も含める（旧版の `export "C" fn h`）。これらの形のうち、下の既存言語の書き方の一覧にあるものは、その行の診断になる（`const fn` は E0020 で、修正候補は `const` を外す形）。
  extern の見出しが `{` の前で読めず、`{` が同じ行にあるとき（`extern "C" {`、`extern {`）は、`extern` から `{` の前までを一つの E0002 にし（ライブラリの名前は書き手しか知らないので修正候補は無く、`extern "C" lib "…" {` の形を note で示す）、メンバを読み続ける。
  ブロックは一つの単位でメンバは検査せず（`impl` の見出しの誤りと同じ）、ABI とライブラリは、読めなければ未知である。
  項目の頭の `pub`・`priv`・`rt` の重なりと順の誤り（`pub pub fn h`、`rt pub fn h`）と、`fn` 以外の宣言の前の `rt`（`rt struct P`、`pub rt struct P`、`rt impl P {`）は一つの E0002 にし、修正候補は正しい並び（可視性を一つ、`fn` の前だけ `rt` の順で、重なりを除いた形。`pub` と `priv` が両方あれば候補なし）で、読み続ける。
  `impl`・`extern`・`trait`・`handler` の前の `rt` も同じで、メンバへ写す候補は作らない。可視性か `rt` の後ろに書いた Onsa の属性（`pub @fp(relaxed) fn h`、`rt @fp(relaxed) fn h`）と `rt` の後ろの他言語の属性（`rt #[inline] fn h`）は、属性を一つの E0002 にし（属性は可視性と `rt` より前に書くと note で示す）、読み続ける。
  可視性を書けない位置の `pub`・`priv`（§15.1。`pub impl P {`、`pub test "a" {`、trait のメンバの `pub fn`、列挙子の `pub A`）も、語を一つの誤りにして、語の後ろから読み続ける。
  それ以外の語で止まった項目と、閉じない形（`pub(crate fn h()`）、改行を挟む形（`extern "C"` 改行 `{` を含む）は読み続けず、名前解決に見せない。
- 構文エラーの後は、宣言の単位で回復する。本体の誤りは対応する `}` まで読み飛ばしてシグネチャを残し、`impl` / `trait` の中ではメンバの単位で回復する。
  `{` が閉じていなければ、それを開いた行と同じか浅い字下げの行頭にある項目の始まり（上記）で回復し、閉じていない `{` を指す E0002 を出す（どの宣言の本体かを note で示す）。
  字下げを見るのは誤りのあるファイルの回復だけで、正しいプログラムの意味は変わらない（§2.5）。本体の中の文の単位の回復は、単位ごとの報告を変えず、LSP の部分的な解析に使う（§18.3）。
- 既存言語と旧版の書き方（`&mut x`、`<T>`、経路の `::`、`;`、`i32`、`proc`、括弧の前の空白 `f (x)` と行頭の二項演算子（§2.5）、腕の `=> return 0`（§7）、`a . b` と `x ?`（§2.5）、値を `f(x)` で呼ぶ形と `s.f(x)`（§6.1、§6.2）、`@` 束縛と、書けない型の定数のパターンと、補間を含む文字列のパターン（§7）、`x: Sig[F32]`（§11.3））と、書き手の誤解を示す冗長な印（定義済みの名前への `^`（§11.2）、フィールドの `pub`（§15.1）、`@mem(fast)`（§12.4）、型の位置の `Buf::[F32]` の `::`（§4.5）など。P2）を検出し、Onsa での書き方へ置き換える修正候補を作れるときは E0020 とする。
  誤解を正すのが目的なので、E0020 は修正候補に加えて、正しい規則を note で示す（「`^` は下で定義する名前を指す印で、過去の値ではない」など）。候補が一意に決まらなければ、全てを `fixes` に並べる。E0020 は検出できる段で報告する（多くは字句と構文の段で、`Sig[F32]` は名前の段、§11.3）。
  候補を作れないときは、構文の段で見つける形は一般の構文エラー（E0002）とし、後の段で見つける形は E0020 のまま候補を出さない。どちらも Onsa での書き方を note で示してよい。
  E0020 にする形と、候補を作れないので E0002 にする既存言語と旧版の書き方は閉じた一覧で、機械が読むデータのファイル [`spec/foreign-forms.toml`](foreign-forms.toml) にある（FAUST と C 系の書き方を含む。行ごとに、見つける段、コード、正しい規則、例と候補を当てた後の形を持つ）。
  一覧に無い形は E0020 にせず、その形を拒む一般の規則のコード（読めなければ E0002、名前が無ければ E0302 など）で報告する。E0020 の主の範囲は外来の形の範囲（形を作る最初のトークンから最後のトークンまで。`let mut` は `let` から、`<T>` は `<` から `>` まで）である。
  字句・構文の一般のエラーは E0001（不正な文字・リテラル）と E0002（予期しないトークン）。
- flow の本体の代入（E0806）は、代入先がまだ定義されていなければ `let` を付ける修正候補を示す。定義済み（`let y = 0.0` の後の `y = y + x`）なら、累積の意図なので、修正候補は付けず、`let y = prev~(^y) + x` と書く形を note で示す。
- 字面の形の誤り（E0020）の数値リテラルの修正候補は、値を変えず、整数か浮動小数かも変えない（型の誤り E0401 の候補は型に合わせる、§11.7）。既存言語の形（`0o17`、`1.`、`.5`、`1.e3`、先頭が 0 の整数 `017`、型の接尾辞 `1u8` `0x1F_u8` `100ul` `1f32` `2.5f`）は E0020 である。
  接尾辞として認めるのは閉じた一覧（Rust の整数・浮動小数の型名、C の `u` `l` `ul` `ll` `ull` `f` とその大文字）だけで、候補は接尾辞とその前の `_` を除いた形である。整数の形に浮動小数の接尾辞が付いていれば、`.0` を足す（`1f32` は `1.0`）。
  一覧に無い接尾辞（`123abc`）と、接頭辞の後に数字が無いもの（`0x_`）は E0001 で、候補は無い。
- E0010 の修正候補は、衝突している群に仮の強弱を置いて式全体を読んだ形で、置き方ごとに一つである。強弱で決まっている部分には括弧を足さず、どの候補も適用した後に E0010 にならない。
  群の数は決まっているので候補の数には上限があり、二つの群の衝突なら式の長さによらず二つになる（`a && b || c && d` は `(a && b) || (c && d)` と `a && (b || c) && d`）。違う形の候補が三つ以下なら全て並べ、それを超えれば候補を出さず、note で書き方を示す。
  候補の並べ方は読みの確からしさを表さない（`w + 1 % n` では、主要な言語の読み `w + (1 % n)` こそが誤りの元である）。
  メッセージには、衝突している演算子を示す。それぞれの読みは候補が示し、一行に収まる短い式では、候補の題とメッセージにも書く（長さの閾値は実装が選ぶ）。ビットの群の中で違う演算子が衝突するとき（`a & b | c`）は、演算子を一つずつ別の群として扱って候補を作る。
  比較の連鎖（`a < b < c`）の候補は `a < b && b < c` の一つで、中央の被演算子が名前・リテラル・フィールドの経路のときだけ出す（それ以外は 2 回評価されるので、`let` に取る書き方を note で示す）。

### 18.2 コマンド

| コマンド | 内容 |
|---|---|
| `onsa check [--json] [<経路>]` | 型・効果・rt・flow・ポリシーの検査 |
| `onsa fmt [--check] <ファイル>…` | 唯一の表記への正規化（下記。正規形は [`spec/tools.md`](tools.md) §3） |
| `onsa build --target <名前> [<経路>]` | マニフェストのターゲットをビルドし、成果物を `target/<名前>/` に置く（C では `onsa.h`、`onsa__runtime.h`、`<prefix><package>.h`、`<prefix><package>.c`、`staticlib` は加えて `lib<prefix><package>.a`、プラグインは加えて束（`.clap`・`.vst3`・`.component`）と埋め込んだヘッダの使用許諾の文。§14.2、§14.3、§15.3）。`target/` の中の、ここに挙げた成果物以外のファイルは内部の出力で、形は版で変わる。`--target` を省くと使い方の誤り（終了コード 2。既定のターゲットを暗黙に選ばない、§12.1） |
| `onsa test [--json] [--filter <text>] [--backends all] [--flows] [--target <名前>] [--seed <値>] [<経路>]` | `test` を実行。`--filter` で走らせるテストを絞る（下記）。`--target` を付けると、そのターゲットの `fp` と `platform` で実行する（`strict-ftz` の模倣、§15.5）。省けば `strict`。テストの panic は、ターゲットの `panic` の設定によらず、テストの失敗として報告する。`--seed` は性質の検査の種（§11.8）。`--backends` で変換先間のビット一致も検査（§13.4）。`--flows` で export される flow を `@param` の範囲で自動検査する（角と無作為の内点でパラメータを取り、無音・インパルス・雑音を入れ、出力が有限で panic しないこと。`@host` の入力には既定の値を与える。イベントの入力に境界の型ごとの決まった列（位置は頭・中ほど・最後と、別の入力の同じ位置を宣言の順と逆の順の両方）を与え、出したイベントの数が上限を超えないことと、同じ入力を二通りの区切りで `process` に渡した出力（音声とイベント）がビットで同じことも確かめる） |
| `onsa interface [--target <名前>] [<経路>]` | `pub` と無指定の項目とメンバのシグネチャ（可視性はソースと同じ語で示す。`priv` の項目とメンバと、並べない型の `impl` は出さない。並べる struct の `priv` のフィールドは `priv` の語を付けて出す）、イベントの入力と番号（§14.2）、doc コメント（宣言の前に `///` の形で。モジュールの `//!` は先頭に）、種、大きさ（`--target` が無ければ bulk 無効での値。§12.1）、状態のフィールド（§11.6）、効果、rt、属性の `@param`・`@host`・`@latency`・`@export`（書いたとおりの形で）だけを出力。シグネチャの型は、読み直すと同じ型になる形で書く（外側に `uses` か `at` が続く関数型は括弧で囲む: `fn a() -> (fn()) uses {Alloc}` と `fn b() -> fn() uses {Alloc}` は別の型） |
| `onsa audit [--stack] [--memory] [--panics] [<経路>]` | extern、unsafe、`@fp(relaxed)`、ポリシーとの差分。スタックの上限と flow の状態の大きさ、閾値以上の移動（コピー）の箇所（§12.7）。`--panics` は export される rt の経路にある panic しうる箇所（検査付きの演算、添字、`unwrap`、非飽和の変換）を列挙する |
| `onsa graph <flow> [<経路>]` | flow の信号グラフ（SVG / DOT）。ノード名は `let` の名前。描き方はツールの仕様（[`spec/tools.md`](tools.md) §1） |
| `onsa play <flow> [<経路>]` | flow を音で鳴らす。@param から UI を作る |
| `onsa probe <flow>.<name> [<経路>]` | 名前の付いた信号をタップし、波形とスペクトルを表示する |
| `onsa diff --ast <旧> <新>` | 構造的な差分。fmt の書き換えだけの違いと、コメント（doc コメントを含む）の違いは差分にしない（比べ方は [`spec/tools.md`](tools.md) §3.5） |
| `onsa explain <code>` | 診断コードの説明と修正例 |
| `onsa primer [--std]` | この版の言語要約と標準ライブラリのインタフェース（`pub` の項目だけ。doc コメントを含む）を、LLM のコンテキスト向けに出力 |
| `onsa lsp` | LSP。DSP 向けの拡張（グラフ、パラメータ、プローブ、ホットリロード）を含む |

- `<経路>` は、パッケージを読むコマンドの最後の省ける位置の引数で、`.onsa` のファイル、パッケージのルートのディレクトリ、`onsa.toml` のどれかである（§15.1。省けば作業ディレクトリから探す）。名前を取るコマンドは名前を先に置く。
  `graph`・`play`・`probe` の `<flow>` は、モジュールの経路付きの名前（`dsp.voice`）か、選んだ範囲（ファイルを渡せばそのモジュール、無ければパッケージ）で一つに決まる名前（`voice`）である。
  一つに決まらなければ使い方の誤り（終了コード 2）で、候補の経路を並べる。経路付きの名前が、渡したファイルのモジュールと食い違うのも使い方の誤り（終了コード 2）である。
- `onsa fmt` は、ファイルを唯一の正規形に書き換える。正規形、プログラムの構造（AST）を変える書き換えの閉じた一覧、コメントの置き場所、書き込む前の確かめの手順、止めたときの報告、コマンドのテキストの出力は [`spec/tools.md`](tools.md) §3、§4 に定める。fmt はプログラムの意味を変えない（書き換えの前後で、一覧の書き換えを施した AST が一致する）。正規形のファイルにもう一度かけても変わらない。
  書き換えは、どのプログラムでも各段の判定（合否と診断のコード）を変えない（誤りのあるプログラムの誤りを消さず、新しい誤りを作らない）。構文だけでそう決まる書き換えだけを一覧に置く。
- `onsa fmt` は、構文の段（§18.1）の診断が 1 件でもあるファイルを書き換えず、終了コード 2 で終わる（`fmt --check` も同じ）。構文の段の診断はコードによらず、E00xx のほか、予約語の E0200（§2.2）、値を持てない整数リテラルとタプルの添字の E0408（§2.4）、E0006 を含む。名前の段より後で出る E0002 と E0020 は含まない。
  `onsa diff --ast` も、構文の段の診断のあるファイルは比べず、終了コード 2 で終わる。fmt が書き込む前の確かめに失敗したとき（fmt の不具合）は、ファイルを書き換えずに内部エラーで終わる。
- `onsa test --filter <text>` は、テストの完全な名前のテキスト（§11.8。`dsp.voice "decays"`）が `<text>` を部分文字列として含むテストだけを走らせる。コードポイントの並びで比べ、大文字と小文字を区別する。空の値は `--filter` を付けないのと同じで、全てのテストに当たる。`--filter` は一つだけ書ける。
  空でない値が一つも当たらなければ使い方の誤り（終了コード 2）である。`onsa test` は、検査の誤り、変換先によらない E0200、`--filter` の照合、走らせるテストから届く範囲の E0200（§15.2）の順に調べ、誤りがあればそこで止まる。検査の誤りと変換先によらない E0200 は、走らせるテストによらず、パッケージ全体で調べる。
- パッケージの中のファイルを `onsa test` に渡すと（§15.1）、そのファイルのモジュールのテストだけを選び、`--filter` はそれと重ねて絞る。`--filter` の照合（空でない値が一つも当たらなければ使い方の誤り）は、渡したファイルによらずパッケージの全てのテストで行う（綴りの誤りを捕まえるため）。
  当たるテストが選んだ範囲の外にだけあれば、走らせるテストは 0 件で、下の 0 件の規則に従う。走らせるのを止めた診断は、渡したファイルによらず全て出す（§15.1 の「そのファイルの診断だけを出す」は `check` と LSP の規則である）。
  空でない `--filter` が当たらないときを除き、選んだテストが一つも無ければ（テストの無いパッケージ、テストの無いファイルを渡したとき）、何も走らせずに成功（終了コード 0）である。一回の実行は一つのパッケージを扱い、経路を二つ以上渡すのは使い方の誤り（終了コード 2、§15.1）である。
- 終了コードは全てのコマンドで共通である。内部エラーを分けるのは、修復のループ（P8）が正しいコードを直しに行かないためである。

| 終了コード | 意味 |
|---|---|
| 0 | 成功 |
| 1 | コマンドが働いた結果、問題が見つかった（`check` の診断、`fmt --check` の未整形、`diff --ast` の差分、`test` の失敗） |
| 2 | コマンドが働けなかった（使い方の誤り（`onsa test` の空でない `--filter` に当たるテストが無いとき、パッケージを読むコマンドに経路を二つ以上渡したときを含む）、入出力の誤り、`onsa.toml` を指す診断（E11xx など、§18.1）、`fmt` と `diff --ast` の入力の構文の診断） |
| 101 | 内部エラー（コンパイラの不具合。fmt の確認が失敗した場合を含む） |

- `--json` を付けたコマンドが標準出力に JSON を出すのは、終了コードが 0 と 1 のときと、`onsa.toml` を指す診断で 2 になったときだけである。診断の無い 2（使い方の誤り、入出力の誤り）と 101（内部エラー）では、標準出力に何も出さず、テキストを標準エラーに出す。修復のループは終了コードで分かれる。途中までの診断を全てと読ませて、内部エラーの原因かもしれないコードを直しに行かせないためである。JSON の形は §18.1（一つのオブジェクト）である。

### 18.3 IDE

FAUST の IDE に相当する環境は、`onsa lsp` の上に作る。言語の側で次を保証する。

- **局所的な検査**: シグネチャが全て注釈されているので、編集した関数だけを検査し直せばよい。
- **パラメータの UI**: `@param` から自動で作る。パラメータの一覧はシグネチャだけで分かる。
- **flow の計画**: コンパイラは、flow ごとに状態の各フィールドの構造上の位置（含む `let` か出力と、式の中の経路）、種類、型（`onsa interface` の表記。組込みの flow の状態は疑似型、§11.6）、オフセットを出す（LSP の拡張と `onsa interface`）。サブインスタンスは、その flow の計画を指す。
- **プローブ**: 全ての信号に名前があるので、ソースを変えずに任意の信号を観測できる。編集の後のプローブの付け替えは、ホットリロードと同じ照合で行う。
- **ホットリロード**: 再コンパイルの後、旧新の flow の計画を構造で照合し、型が同じノードの間でだけ状態を引き継ぐ。照合できなかったノードは `init` で初期化する。サブインスタンスは、その flow の計画の中まで照合する。生成する名前（§11.6）は照合に使わない。
  状態のノードは各 `let` の式の木の中にあり、一つの名前では木の中の位置を表せない（番号で付けた名前は、編集で番号がずれると、型の同じ別のノードを指す）からである。照合の方法（`let` の名前を鍵とした木の中の位置、差分、照合できなかった部分のクロスフェード）は [`spec/tools.md`](tools.md) に書く。
- **試聴**: IDE は C バックエンド（デスクトップ）または WASM バックエンド（ブラウザ。Onsa Core から直接出力する、§13.3）で flow を実行する。WASM の浮動小数は IEEE で FMA も拡張精度も無いので、`strict` の基準として扱いやすい。`strict` なら、試聴した音と組込み機器で鳴る音は、超越関数の精度目標の範囲で一致する。
