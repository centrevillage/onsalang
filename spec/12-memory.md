## 12. メモリ

### 12.1 記憶域

| 記憶域 | 置かれるもの | 確保の時期 | 大きさ |
|---|---|---|---|
| 静的（読み取り専用） | `const`、補間の無い文字列リテラル | コンパイル時 | コンパイル時に決まる |
| 値 | Copy 値、固定長配列、struct、flow の状態 | 所有者の場所（スタック、他の値の中、静的領域） | コンパイル時に決まる |
| ヒープ | Shared 値、`Buf` | `Alloc` を通じて実行時 | 実行時に決まる |

`onsa interface` は、各型について種と大きさ（値の場合）を表示する。大きさがターゲットで変わるのは、`@mem(bulk)` を自分か入れ子の中に持つ状態（bulk が有効なターゲットではバッファが bulk 領域へ移り、先頭に bulk 領域へのポインタが入る。§12.4）と、ハンドル（Shared 値、`Buf`）を含む値（ハンドルはポインタの幅）だけである。

- `--target <名前>` を付けると、そのターゲットでの大きさと、各 flow の `SIZE` / `ALIGN` / `BULK_SIZE` / `BULK_ALIGN` を表示する。bulk を持つ状態を普通の値に置いた型は、bulk が有効なターゲットでは大きさの代わりに E0819 を示す。
- 付けなければ、bulk 無効（`memory.bulk = false`、既定）での大きさを表示する。bulk 無効の配置にはポインタが入らないので、この値はポインタの幅にも依存しない。`@mem(bulk)` を持つ状態には「bulk が有効なターゲットでは変わる」と添え、ハンドルを含む値には「ポインタの幅による」と表示する。既定のターゲットを暗黙に選ばないのは、出ている数字がどの条件のものかを読み手に分からせるためである。
- 大きさを計算できない flow（この版で未対応の機能を使うものなど）は、その flow にだけ理由を示す。他の flow の大きさは表示する。

### 12.2 `Alloc` が要る操作

| 操作 | `Alloc` |
|---|---|
| Shared 値・`Buf` の生成、補間文字列 | 要る |
| 所有する Shared 値・`Buf` の破棄（参照カウントが 0 になりうる） | 要る |
| Shared 値・`Buf` の借用、読み取り | 要らない |
| 受け取った Shared 値を、そのまま返す・`move` で渡す | 要らない |
| 借用束縛（§5.4）の終了 | 要らない |
| ジェネリックな `T` の値の破棄（`T: Copy` の制約が無い場合、§6.3） | 要る |
| Copy 値・flow の状態の生成と破棄 | 要らない |

`Alloc` の有無はシグネチャに出るので、関数がヒープを使うかどうかはシグネチャだけで分かる。Zig の「隠れた確保をしない」と同じ目的を、allocator の引数ではなく効果で達成する。

### 12.3 ヒープの無いターゲット

- `provides` に `Alloc` を持たないターゲット（§15.3）では、`main` と export される関数の効果行に `Alloc` を書けない（E0610）。この検査はシグネチャだけで閉じる。
- flow は元々ヒープを使わないので、そのまま使える。
- 初期化時に一時的なヒープが欲しい計算は、静的な作業領域の上で `arena` を使う（§8.4）か、`const` にしてコンパイル時に計算する（§6.6）。

### 12.4 flow の状態の大きさと配置

- flow の状態の大きさは、コンパイル時に決まる（遅延線の長さはコンパイル時定数、値型は Copy、ヒープを使わない）。
- 状態は二つの領域に分かれる。
  - **fast**: `@mem(bulk)` の付いていないもの全て（スカラ、短い遅延線、`init` のクロックの配列を含む）。キャッシュや内部 SRAM に置く。
  - **bulk**: flow の本体で `@mem(bulk)` を付けた `let` の遅延線（`delay` / `vdelay` のバッファ）。外部 SDRAM などに置く。入れ子の状態（サブインスタンス、`par` の複製）の中の `@mem(bulk)` も対象で、bulk 領域は最上位の flow に一つだけ作る。
    bulk のフィールドを持つ状態（入れ子のものも）は、それぞれ自分の分の先頭を指すポインタを先頭に持ち、親の `init` がそれを設定する。子の関数は自分のポインタだけを見るので、子を単独で export しても同じコードで動く。
- `@mem(bulk)` を付けられるのは、値が `delay~` / `vdelay~` の呼び出しそのものである `let` だけである（それ以外は E0818）: `@mem(bulk) let line = vdelay~(^y, d, MAX_ECHO)`。式の中の遅延線を bulk に置くには、`let` に分けて名前を付ける。
  `@mem(...)` の値は記憶域の名前で、仕様が定める閉じた一覧（今は `bulk` だけ）から選ぶ。一覧に無い名前も E0818。fast は既定なので `@mem(fast)` は書かない（E0020、修正候補は外すこと）。記憶域を足すときは、C API（`<NAME>_SIZE` / `<NAME>_ALIGN`、`init` に渡すポインタ）とマニフェストの設定を一緒に定める。
  名前はそのまま状態のフィールド名になる（`line.buf`）。
- 大きさによる自動の振り分けはしない。長い遅延線は SDRAM に、コムやオールパスの短い遅延線は SRAM に置く、という判断は書き手が行う。ライブラリの flow は、長い線にだけ `@mem(bulk)` を付けて配布できる。
- 二領域の配置は、ターゲットの `memory.bulk = true` で有効になる（§15.3）。有効でないターゲット（既定。ホストやプラグイン）では `@mem(bulk)` を無視し、全てが fast に入り、`BULK_SIZE` は 0 になる。
- bulk を持つ状態（`@mem(bulk)` のフィールドを、自分か入れ子の中に持つ状態）は、flow の中（サブインスタンス、`par`）か export の境界でだけ所有できる。`memory.bulk = true` のターゲットで、それを普通の値（struct のフィールド、配列の要素、関数のローカル）に置くと、ビルド時に E0819。
  Onsa の中から呼ぶ `init` には bulk 領域を渡す口が無いからである。有効でないターゲットでは `@mem(bulk)` が無視されるので、この制限は掛からない。
- `SIZE` / `ALIGN`（fast 領域）と `BULK_SIZE` / `BULK_ALIGN`（bulk 領域）は、ターゲットの `memory.bulk` とポインタの幅だけで決まり、libc や C コンパイラに依存しない。
  同じターゲットでは、flow を単独で export しても他の flow に埋め込んでも同じ配置になる（埋め込んだサブインスタンスの状態も、単独のときと同じオフセットで読める）。ポインタの幅で変わるのは、bulk を持つ状態の先頭のポインタと、その後の詰め物だけである。
  これらの値は Onsa の名前空間には無く、C のヘッダ（§14.2）と `onsa interface --target <名前>` に出る。
- 容量の確認: ヘッダの `SIZE` / `ALIGN` と `BULK_SIZE` / `BULK_ALIGN` で分かる（§14.2）。ターゲットに `fast_budget` / `bulk_budget`（バイト）を書くと、export する flow の各領域がそれを超えたときにビルドで E0820 にする。
  `onsa audit --memory` は、領域ごとにフィールドの木と大きさを表示し、fast に置かれた大きな配列を大きい順に並べる（`@mem(bulk)` の付け忘れの確認用）。
- 配置の規則: フィールドは宣言順（flow の状態では `let` の順）、各型の自然アラインメント、並べ替えなし。
  `let` に由来しないフィールドは次の順に置く: 先頭に bulk 領域のポインタ（`BULK_SIZE > 0` のとき）、`sample_rate: F32`（`block` / `sample` から参照されるとき）、次に自分のクロックより速いクロックから読まれる入力（`sample` で読まれる `block` の入力など。宣言順）、次に `let` 由来のフィールド（`sample` から参照される `block` のクロックの `let` も含む。ブロックの段とサンプルの段の間で値を渡す場所が要るため。各 `let` の位置に、その `let` 自身のフィールドがあればそれを、続けてその式の中の名前の無いノードを字面の順に置く）、次に出力の式の中の名前の無いノード（字面の順）、次に巻き上げた部分式の値（`let` の順、その中は番号順で、出力の式の巻き上げは最後。§11.3）、次に遅れの値（`@latency` のある flow、§11.6）、末尾に `poisoned: Bool` と `initialized: Bool`（どちらも export の境界が使う印。§14.2）。
  `SIZE` / `ALIGN` はこの規則でコンパイラが計算し、生成コードに `_Static_assert` で検証を出す。同じプログラムでは配置は決定的で、ホットリロードとプローブは flow の計画（§18.3）からフィールドとオフセットを引く。
- C API は二つの領域を別々のポインタで受け取る（§14.2）。Onsa の中から見ると、状態は一つの値である。

### 12.5 スタック

- `rt` 関数は再帰しない（§10）。flow の `process` は関数値を経由しない。したがって、export された flow の `process` のスタック使用量の上限は計算できる。
- `onsa audit --stack` は、各エントリ（export された関数・flow、`main`）の最悪スタック使用量を報告する。関数値を経由する呼び出しや、rt でない再帰を含むエントリは「不明」と報告する。
- スタックが尽きたとき: インタプリタ（`onsa test`）とコンパイル時の評価（定数式、`const` の初期化式、定数のクロックの式、`@param` の値。§6.6、§11.3）は、呼び出しの深さに同じ固定の上限 128 を持つ。深さは評価の入口（`test` の本体、一つの初期化式や式）を 0 とし、そこから入れ子になった呼び出しの数で数える（末尾の呼び出しも数える）。
  `const` の値を読むのは呼び出しではなく、その `const` は自分の入口から数える。入れ子の呼び出しが 128 を超えると panic し、コンパイル時の評価ではその式の位置の E0419（§6.6）になる。上限はビルドの種類と環境（CLI、ブラウザの IDE）によらず同じである。C などの変換先では、ターゲットの機構に従う（多くはプロセスの異常終了で、panic としては扱えない）。
  rt のエントリは再帰しないので、`onsa audit --stack` の上限に合わせてターゲットのスタックを用意する。
- `main` は再入しないので、コンパイラは `main` のローカル変数を静的領域に置いてよい（ターゲットの `main_frame = "static"`）。大きな flow の状態を `main` のローカルに置いても、スタックを消費しない。ソースの意味は変わらない。

### 12.6 参照カウント

- Perceus 方式。所有権の解析により、不要な増減を省き、一意な値はその場で更新する。
- 値が不変なので循環は生じず、循環の回収器は要らない。
- 参照カウントは原子的でない。Onsa はスレッドを作らず、実行の文脈の間を渡れるのは Copy 値（同期型の要素）と、登録時に `move` した Affine 値だけなので（§16）、Shared 値が二つの文脈から同時に参照されることは無い。

### 12.7 返り値の構築

集成体（struct、配列、タプル、enum）の値は、作られた場所から動かさずに使えることを保証する。`echo.State` のような大きな状態をスタック経由でコピーしないためである。

- **集成体を返す式は、その置き場所に直接構築される。** 対象の式は、関数呼び出し、struct / 配列 / タプルのリテラル、`par`、`if` / `match` の各腕。置き場所は、`let` / `var` の束縛、代入先、struct のフィールド、配列の要素、関数の返り値のいずれでもよい。
  §17.6 の `Poly.new` では、`voice.init` の結果が無名関数の返り値、配列の要素、struct のフィールド、`Poly.new` の返り値を経て呼び出し側の `var` に置かれるが、途中でコピーは起きない。
- **名前付きのローカルを返す場合**は、全ての経路で返されるローカルが一つなら、そのローカルを返り値の置き場所に置く（C++ の NRVO と同じ条件）。`if c { a } else { b }` のように二つのローカルのどちらかを返す場合は、コピー（Affine なら移動 = バイトのコピー）が起きる。
- **保証できない場所。** `Result[T, E]` や `Option[T]` に包んだ値を `?` や `match` で取り出すと、一時的な値から中身へのコピーが起きる。生成 API（`init` は失敗しない）では起きないが、利用者の `fn make() -> Result[Poly, E]` では起きる。
- **構築先が、構築に使う値から読まれる場合。** 構築先が、構築に使う値（引数、フィールドの値、要素）から読まれうるとき（`x = f(x)`、`p = P { x: p.y, y: p.x }`）は、一時的な場所に作ってから構築先へコピーする。重なりの判定は `inout` の重複（§5.2）と同じで、違うフィールドは重ならない（`o.a = make(o.b)` は `o.a` に直接作る）。そのため、呼ばれた関数は、出力先が引数と重ならないものとして扱える。
- `onsa audit --memory` は、閾値以上の大きさの値の移動（コピー）が起きる箇所を列挙する。
- 実現: 集成体を返す関数は隠れた出力ポインタを受け取り、`return` の式をそこへ構築する（C の sret 相当）。スカラと `Ptr` だけをレジスタで返す。大きさの閾値を設けないのは、規則をターゲットの語長に依存させないためである。C++ / Rust への変換では変換先の RVO に頼るか、同じ出力ポインタの形で出す。

### 12.8 ヒープオブジェクトのヘッダ

Shared 型と `Buf` のオブジェクトは、データの前に 8 バイトのヘッダを持つ。

| フィールド | 幅 | 意味 |
|---|---|---|
| `count` | U32 | 参照カウント。確保時は 1。**0 は静的（不滅）** を表し、`dup` / `drop` は何もしない |
| `alloc` | U16 | 確保元。0 はターゲットのヒープ、1 以上は `Alloc` handler の入れ子の深さ。解放はこの確保元に戻す（§8.4）。handler を抜けた後にその深さのオブジェクトは残らない（§8.4 の規則）ので、深さで一意に決まる |
| `flags` | U16 | 予約（0） |

- 補間の無い文字列リテラルと、Shared の `const`（§6.6）は、`count = 0`、`alloc = 0` の静的オブジェクトとしてデータごと静的領域に置かれる。静的領域が読み取り専用（フラッシュ）でも、カウントへの書き込みが起きない。
- Perceus の一意性判定は `count == 1` なので、静的オブジェクトは一意にならず、in-place 更新は起きない。
- `Buf` は参照カウントを使わないが、解放に `alloc` が要るので同じヘッダを持つ（`count` は 1 固定）。
- GC のある変換先（JavaScript）にはヘッダが無く、静的かどうかの区別も要らない（§13.5）。
