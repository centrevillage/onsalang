## 8. 効果

### 8.1 宣言と使用

```onsa
pub blocking effect Fs {
  fn read(path: Path) -> Result[Str, IoError]
  fn write(path: Path, data: Str) -> Result[(), IoError]
}

pub fn load(path: Path) -> Result[Str, IoError] uses {Fs} {
  Fs.read(path)
}
```

- 効果行は **効果単位**（`Fs`）で書く。標準ライブラリは `FsRead` と `FsWrite` を分けている。本仕様の例では簡単のため `Fs` を使う。
- 効果行の名前は、他の名前と同じく解決する（§15.1）。標準の効果（`Fs` `Stdout` `Stdin` `Clock` `Random` `Log`）は std の `effect` 宣言で、`use` で取り込む。`Alloc` だけは prelude にある（§8.2）。見つからない名前は E0302 で、`use` の無い標準の効果には `use` の追加を修正候補に示す。
- 本体で使う効果は、効果行に含まれなければならない（E0601）。使用には、効果を持つ関数と関数値の呼び出し、効果の操作のほかに、暗黙の `Alloc`（補間などで Shared 値や `Buf` を作ること、それらを所有する値の破棄、§12.2）を含む。診断は最初の使用の位置に置く。`rt` でない関数では、効果行への追加（署名への挿入）を修正候補に示し、同じ効果の他の使用を note に並べる。
  集成体のリテラルの破棄で `Alloc` が要るときは、リテラルを所有の行にした最初の要素（破棄の要らないリテラルの要素になれないもの）を note で名指す（§5.4）。
  `rt` の関数は効果行に `Alloc` を持てない（§10 の規則 1）ので、修正候補を出さない。
- 効果行が空なら `uses` を書かない。それが純粋関数（`uses {}` と書いても受理し、`onsa fmt` が外す）。
  無名関数の `uses {}` は効果行の注釈で、省くと期待型から決まる形になり意味が違うので、外さない（§6.1）。
- 効果の操作に `uses` は書けない。handler が使う効果は `handle` 式の効果行に加わる（§8.3）ので、操作の契約はシグネチャと `rt`（下記）と効果の `blocking` だけで決まる。
- `blocking` はブロックしうる効果の印である（§8.2）。
- 効果の操作には `rt` を付けられる（`effect Log { rt fn info(msg: Str) }`）。`rt` の操作の handler は `rt` でなければならない（E0613）。`blocking` の効果の操作に `rt` は付けられない（E0614）。全ての操作が `rt` である効果を **rt 効果** と呼ぶ（§10）。
- `load` は受け取った `Str` をそのまま返すので、破棄が起きず、`Alloc` を要しない。
- 効果行は集合で、書く順序は意味を持たない（`uses {A, B}` と `uses {B, A}` は同じ）。
- 関数型どうしの互換: 関数 F を、関数型 G を期待する位置（引数、注釈付きの `let`、返り値、struct のフィールド）で使えるのは、次の全てを満たすときである。制約の強い（できることが少ない）関数は、制約の弱い位置で使える。
  1. 引数と返り値の型が等しい（引数の型の中の関数型も完全に一致する）。
  2. F の効果行が G の効果行に含まれる（純粋な関数は `uses {Alloc}` の位置で使える。逆は E0401）。
  3. G が `rt` なら F も `rt` である（§10）。

  これらに反する使い方は全て E0401 である（E0901 は、`rt` の関数の中での `rt` でない関数と関数値の呼び出しだけに使う、§10）。
- 無名関数は、期待する関数型の効果行と `rt` に照らして本体を検査する。期待する型が純粋なら、本体で `Alloc` を使えない（外側の関数の効果行には数えない）。期待する型が `rt` なら、本体を `rt fn` の規則で検査する。
- 効果の多相（効果行変数は言語の仕組みとして残す。`std` の最初の版には `Array` の `map` / `filter` を置かない、§19.1）。`[…]` の並びでは、小文字で始まる名前が効果行変数、大文字で始まる名前が型パラメータである（§2.3）:

```onsa
pub fn map[T, U, e](xs: Array[T], f: fn(T) -> U uses {e}) -> Array[U] uses {Alloc, e} { ... }
```

### 8.2 `Alloc` と、ブロックする効果

- **`Alloc`** はヒープの確保と解放を表す **明示の効果** である。std で操作の無い効果（`pub effect Alloc {}`）として宣言され、prelude にある（§15.1）。操作を呼ぶのではなく、Shared 値と `Buf` の生成・解放、補間文字列の生成が `Alloc` を要する（§12.2）。
- **ブロックするかどうかは、効果の宣言で決まる。** ブロックしうる操作（ロック、システムコール、待機）を持つ効果は `blocking effect` と宣言する。**関数がブロックしうるのは、効果行に `blocking` の効果を含むときだけ** である。使う側は `uses {Fs}` と書くだけでよく、ブロックの印を二度書く必要は無い。
- `blocking` でない効果の handler は、その操作の中で `blocking` の効果を使えない（E0612）。この検査は handler の定義の中で閉じる。例えば `Log` はブロックしない効果なので、リングバッファに書く handler は書けるが、標準出力に同期的に書く handler は書けない。
- 組込みの `Block` は操作を持たない `blocking` の効果で、extern 関数がブロックすることを主張するのに使う（§14.1）。`Block` は handler で処理できない。
- `rt fn` の効果行には rt 効果しか書けない（§10）。`Alloc` と `blocking` の効果は rt 効果ではない。

標準ライブラリの主な効果:

| 効果 | `blocking` | rt 効果 | 内容 |
|---|---|---|---|
| `Fs`, `Stdout`, `Stdin` | ○ | × | 入出力（`Net` は延期、§19.1） |
| `Clock` | × | ○ | 現在時刻の取得 |
| `Random` | × | ○ | 乱数 |
| `Log` | × | ○ | ログ（handler はブロックもヒープ確保もしない書き方に限られる）。`Str` を受ける操作のほかに、`Span[U8]` を受ける rt の操作を持つ（`FixedStr`、§4.2。名前は §19.1） |
| `Alloc` | × | × | ヒープ（§12） |

`Alloc` を明示にしたのは、組込みではヒープが無いことがあり、またヒープの代わりに arena を使い分ける価値があるからである。ブロックを効果の宣言で表すのは、ブロックできない環境（ブラウザのメインスレッド、AudioWorklet、プラグインの GUI スレッド）へ、どの関数を持ち込めるかをシグネチャだけで判断するためである（§13.5）。

### 8.3 handler

```onsa
handler memory_fs: Fs {
  fn read(_: Path) -> Result[Str, IoError] { Ok("a\nb\n") }
  fn write(_: Path, _: Str) -> Result[(), IoError] { Ok(()) }
}

let r = handle { load(Path.new("x.txt")) } with memory_fs
```

- handler は **末尾再開のみ**。各操作は値を返して呼び出し元に戻る。継続の捕捉、早期脱出、多重再開は無い。
  - 実装は証拠渡し（evidence passing）で、静的に解決できればゼロコスト。
  - Affine 値が複製される経路が無いので、一意性と健全に共存する。
  - handler の操作が `rt` なら、handle 式も `rt` で使える。
  - `blocking` でない効果の handler は、ブロックする効果を使えない（§8.2）。
- handler 自身が使う効果は、`handle` 式の効果行に加わる。
- handler は引数を取れる。引数は第二級（§5.3）で、`handle` 式の間だけ有効: `handler arena(inout mem: Span[U8]): Alloc { ... }`、`handle { ... } with arena(inout scratch)`。引数の無い handler は、宣言でも `with` でも括弧を書かない（`handler h(): Ask` と `with h()` は E0002、§2.5）。
- インライン形式 `handle { ... } with Fs { fn read(...) ... }` も同じ意味。`with` の後の経路の最後の名前が `UpperCamel`（効果、§2.3）ならインライン形式で、本体 `{ … }` が同じ行に続く（本体が無ければ E0002 で、名前の付いた handler は `snake_case` であることを note で示す）。`snake_case` の名前は名前の付いた handler で、引数は `(…)` で続ける。

### 8.4 `Alloc` の handler と、持ち出しの禁止

```onsa
use std.mem.{arena}

const N: U32 = 1024

/// 一時的な Array を使って倍音テーブルを作る（ヒープを使う）
fn harmonics() -> [F32; N] uses {Alloc} { ... }

/// 呼び出し側が渡した作業領域の上で harmonics を実行する。ヒープの無いターゲットでも呼べる
pub fn harmonics_in(inout scratch: Span[U8]) -> [F32; N] {
  handle { harmonics() } with arena(inout scratch)
}
```

- `Alloc` を処理する `handle` 式には、ヒープ上の値をその確保領域の外へ持ち出せないよう、次の 3 つの規則がある。
  1. 結果の型は Copy でなければならない（E0640）。
  2. 本体の中で、外側のスコープにある **ヒープを持つ型**（Shared の型、`Buf`、それらを含む型）の値は、読み取りの借用でしか使えない。代入、`inout`、`move` は不可（E0641）。ヒープを持たない値（Copy 値、flow の状態、`Span`）は通常通り扱える。
  3. 本体の効果行は、処理される `Alloc` を除いて空でなければならない（E0642）。外側の効果の handler が、操作の引数として受け取った値を複製して保存する経路を閉じるためである。
- 規則 2 により、一時領域で計算した結果を実行時の長さのバッファへ直接書くことはできない。固定長の Copy 値を返して外側で書き写すか、固定長の塊ごとに外側で `handle` を繰り返す。
- 確保した領域が尽きた場合は panic する。
- 解放は、その値を確保した allocator に戻る（オブジェクトのヘッダに確保元を記録する）。そのため、外側で確保された値が arena の中で破棄されても正しく扱われる。
- std は `arena`（作業領域の上の bump allocator）を提供する。システムのヒープはターゲットが提供する（§15.3）。`Alloc` の handler を自分で書くには `unsafe` が要る。

### 8.5 main と実行環境

```onsa
pub fn main() -> Result[(), AppError] uses {Fs, Stdout, Alloc} { ... }
```

`main` の効果行の各効果について、ビルドターゲットが handler を提供しなければならない（E0610、§15）。ヒープの無いターゲットは `Alloc` を提供しないので、その `main` は `Alloc` を効果行に持てない。

時刻と乱数も効果（`Clock`, `Random`。どちらもブロックしない）。テストでは handler を差し替えるだけで決定的になる。`test` の本体では、テストランナーが `Alloc` と、テスト名から決めた種の `Random` を提供する。
