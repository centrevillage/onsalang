# 参照評価器の出力のデータの形式（形式の版 1）

`tests/spec/flow_semantics/` の事例（`mode = "test"`）の各 `test` で、参照評価器（`crates/onsa_tests/src/flow_ref/`）が `render`・`process` などの呼び出しに返した値の表（W7-19）。インタプリタとの比べ（U3）は、この表の呼び出しを Onsa の `test` に書き直して走らせ、出力を照らす。規範は**このデータと仕様（§11.6、§11.4、§13.4）**で、評価器ではない。評価器とデータが食い違えば、どちらが仕様に合うかを仕様の文で決める。

## ファイル

| ファイル | 内容 |
|---|---|
| `<事例>.tsv` | 元の事例（ファイルの語幹か、ディレクトリの名前）と一対一。元の事例を消せば、このファイルも消す |
| `MANIFEST` | ファイルごとの行数と頭の数、合計。ハッシュは持たない（データは毎回評価器の出力と突き合わせる） |

`FORMAT.md` 以外は `UPDATE_GOLDEN=1 cargo test -p onsa_tests --test flow_ref` が作る。手で編集しない。評価器と事例の assert が一つでも食い違うと、書き直さずに失敗する。

## 行

LF で区切る。先頭の `# flow_ref 1 source=<事例の経路> tests=… evaluated=… unavailable=… skipped=… waiting=…` が頭で、数は取り出しのたびに数え直す。`waiting` は事例が降下しない（検査が E0200 を出すか、Core に降りない）なら 1。そのような事例が実装待ちの一覧（`tests/pending.toml` の `test-case`）に無ければ、入口のテストが失敗する。
頭以降は test ごとの節で、順は事例に書いた順。

| 行 | 意味 |
|---|---|
| `@ <test の名前>` | 評価して事例の assert と印が成り立った test の始まり。以後の呼び出しの行が、次の節まで続く |
| `- <名前> TAB skipped <理由>` | 評価しない test。理由は `layout`（`In`・`Out`・チャンネルの配列・`Buf`・`process_inplace`・`Span` の値、W7-12）、`statement`（取り出しの形でない文）、`nocall`（生成された関数を、test からも test が呼ぶ補助関数からも呼ばない） |
| `? <名前> TAB unavailable <理由>` | 評価器がまだ評価しない形（理由は評価器の文） |
| `! <名前> TAB failed <文>` | 評価器と test の assert や印が食い違う test。入口のテストは、これが一つでもあるとデータを書かずに失敗するので、置かれたデータには無い |

test の名前の改行とタブは空白にする。

`process` の長さの違う `slice`（入力と出力の `Span` の長さが等しくない）は、評価器が `panic start`（§11.6）にする。`render` を test が呼ぶ補助関数（`fn is_prev(d: F32) -> Bool`）の中で呼んだときも、test が呼んだのと同じ呼び出しの行になる。

### 呼び出しの行

| 行 | 意味 |
|---|---|
| `init <n> <flow> sr=<値> [cfg <名前>=<値> …]` | `var st = F.init(..)`。`n` はその test が作った状態の順（0 から） |
| `process <n> [cfg …] [params …] frames=<数> [in <名前>=[<列>] …]` | `F.process(inout st, ..)`。`in` は `sample` の入力の名前ごとの列で、`frames` は全ての `Span` の長さ |
| `render <flow> sr=<値> [cfg …] [params …] [frames=<数>] [in …]` | `F.render(..)`。`frames` は `sample` の入力の無い flow だけ |
| `reset <n>` | `F.reset(inout st)` |
| `out<経路>=[<フレームごとの値>]` | 直前の `process`・`render` の出力の葉ごと。経路は、スカラが空、`[k]` がチャンネル、`.f` が struct の出力のフィールド、`.f[k]` がそのチャンネル。葉は出力の型から決める（フレームが 0 でも `out.l=[]`・`out.r=[]`、チャンネルの配列は `out[0]=[]`・`out[1]=[]`）。`process` の行も struct の出力のフィールドの名前で書く |
| `panic <段>` | test の最後の行。段は `init`、`start`（入力の長さの比べ）、`block`、`sample <n>`（その呼び出しでフレーム `n`）、`eval`（test の中の式の panic。範囲外の添字など。`xs.slice(from, to)` の `from > to` もここ、S-1148 の仮の扱い） |

印（`TESTFAIL`・`PANIC`）の付いた test を評価して合うのは、どれかの呼び出し（か test の式）が panic し、その前の assert が全て成り立つときである。assert が偽で落ちるだけの印付きの test は合わない。印の付いていない test が panic するときも合わない。

panic した呼び出しの行は残り、`out` の行は無い。panic の後の行は無い（test はそこで止まる）。

## 値

| 型 | 書き方 |
|---|---|
| 整数 | 10 進 |
| `F32` / `F64` | `0x` と全幅（8 桁、16 桁）の小文字の 16 進で、IEEE 754 のビット（`-0.0` は `0x80000000`、入力の NaN もビット） |
| 出力の NaN | `nan`（符号とペイロードは未規定、§3.4、§13.4。どの NaN でもよい。それ以外の出力はビットが一致する） |
| `Bool` | `true` / `false` |
| `Char` | `c<コードポイントの 10 進>` |
| 配列・struct・タプル・enum | `[…]`・`{…}`（フィールドの順）・`(…)`・`#<番号>(…)`（要素は空白で区切る） |
| `()` | `()` |

`out` の列とフレームの数は同じで、`process` の出力は書き戻した局所でなく、その呼び出しの出力。

## インタプリタとの比べ

入口のテスト（`crates/onsa_tests/tests/flow_ref.rs`）は、評価して合った test の呼び出しの行を Onsa の `test` に書き直し、元の事例のファイルの末尾に足して `onsa test` と同じ道で走らせる。データの行から書き直すときの決めごとは次のとおり。

- 入力は `F32.from_bits(0x…)`・`F64.from_bits(0x…)`、整数と `Bool` は書いたまま。整数の列の型（`I32` など）と出力の葉の型は、データには無く、flow の宣言から取る（フレームが 0 の列にも型が要る）。
- 出力は、フレームごと・葉ごとに `to_bits() == 0x…` で比べる（`nan` の葉は `x != x`、§3.4。整数と `Bool` は `==`）。
- `process` の出力先は、呼び出しごとの新しいバッファ（0 で始める）で、元の test の `slice` の位置は写さない。状態は `init <n>` の `n` ごとの `var`。
- `panic <段>` の行は、その呼び出しがインタプリタでも panic することを求め、段（`init`・`start`・`block`・`sample`）も比べる。`sample <n>` は段だけで、フレームは比べない。`panic eval` の test は、呼び出しだけを比べる。
  インタプリタの失敗の記録（§18.1）は段を持たないので、失敗の位置（`span`、次に `calls` を内側から）のうち、最初に flow の `let` か出力の式の中にあるものの、クロックの段をインタプリタの段とする（定数のクロックは `init`）。どの flow にも無い位置（test が書いた呼び出しそのもの）は `start`。
- flow の名前は、test が呼び出しに書いた経路のまま写す（`dup`、`b.dup`。別のモジュールに同じ名前の flow があっても取り違えない）。`init` の経路を、同じ状態の `process`・`reset` も使う。局所の名前は `flow_ref_` で始める（`flow_ref_s0`・`flow_ref_o1_0`・`flow_ref_i1_0`）。事例が `flow_ref_` で始まる名前を書いていれば、その事例の test は書き直さず、数と理由を出す。
- 値が配列・struct・タプル・enum・`Char` の呼び出しを持つ test は書き直さず、入口が数と理由を出す（今の事例には無い）。

## `corpus/`（生成した flow の固定の入力）

`corpus/*.onsa` は、台本が生成した flow と、それを呼ぶ `test`（assert の無いもの、または flow とその双子の出力が等しいことを assert するもの）の固定の入力である。
事例ではなく（`onsa_tests::case::EXCLUDED`）、`.tsv` と `MANIFEST` には載せない（手書きの期待が無く、値の源は評価器とインタプリタの二つで、一致を毎回照らす）。
入口（`crates/onsa_tests/tests/flow_ref.rs`）が、評価器で走らせた test の数と評価した数を `CORPUS_COUNTS` と照らし、評価して合った test を W1-09 の事例と同じ道（上の「インタプリタとの比べ」）でインタプリタと比べる。
生成した flow は `init`・`block` の入力を持たない（`at sample` の入力が一つ）ので、`init` の段の panic は定数のクロックの式の panic（E0419、§11.3）で、入口が失敗にする。

| ファイル | 中身 |
|---|---|
| `expr_a.onsa`、`expr_b.onsa` | 型の付いた式の flow（W7-01 U3 の壊す側の式の生成。種と落とした flow は先頭のコメント）。入力のフレームのうち panic しない分を一つの `render`、最初の panic する一つを `//~ PANIC` の印の test に |
| `clock_twins.onsa` | 定数のクロックの `let` を持つ flow と、`let` をその場に書いた双子（R-488 の双子。種は先頭のコメント）。`process`・`reset` の列で、出力が等しいことを assert する |

corpus は固定の入力で、作り直しは約束しない（生成の台本は木に置かない。種と落とした flow はファイルの先頭のコメントにある）。ファイルを足すときは、入口の `CORPUS_COUNTS` に test の数と評価した数の行を足す。

## 既知の限界

比べるのは、値（ビット）、どの呼び出しで panic したか、その段である。比べないもの:

- panic の種類（0 での割り算、桁あふれ、範囲外の添字、`panic(msg)`）。インタプリタの失敗の記録の `kind` は `assert` か `panic` かだけで、文面は `assert` の文と `panic(msg)` の `msg` しか約束されない（§18.1）。評価器の種類との対応は取れない。
- `sample <n>` のフレームの `n`。記録はフレームを持たない。
- 巻き上げた部分式の panic の段。評価器もインタプリタの側の見方も、失敗を含む `let`（か出力の式）のクロックの段で見る。速い `let` の中の遅いクロックの部分式は、§11.3 では遅い段で評価するので、その panic の段はインタプリタが遅い段で起こしても、段の比べでは区別できない。
- test が呼ぶ補助の関数の中の `render` は、経路が手元に無く、経路の最後の語で書く。同じ名前の flow が別のモジュールにある事例では、偽の失敗になる（見逃しにはならない）。
