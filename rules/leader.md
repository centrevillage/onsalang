# 親の規則

主のセッション（親。監督とレビューの担当）が、担当（`.claude/agents/` の `onsa-*`）と協調して作業するときの規則である。

- 担当と共有する手順（作業票、完了の定義、報告の形、W の進め方、仕様の空白の流れ、検査の回し方）は `rules/process.md`、担当の共通の規則は `rules/` の他のファイル（`rules/README.md`）にある。ここには親だけが使う運用の知識を書き、他の文書にある規則は参照だけにする（同じ規則を二か所に書かない）。
- 親も `rules/common.md` の 1 章（リポジトリとシェル）と 3 章（機械を落とさない）、`rules/documents.md` の 5 章の文書の編集の規則に従う。推奨を出すときは `rules/criteria.md` の 7 章（推奨の基準）を使う。
- この文書は、親が文を提案し、利用者が了承してから親が書く。規則に足す案は、一般の手順として効くものだけにし、一つの不具合から引いた細かい注意にしない。
  ある回の判断の結果（撤回する、後の段へ回す）を一般の規則にせず、評価に含める観点だけを控えめな文で出す。既にある項目と重なれば、その項目への一言にする。
  値の表（`rules/budgets.md`）は親が改め、改めたことを報告する。日付の付いた状態の注意は、直ったら親が消す。他の文書と食い違いを見つけたら、利用者に知らせて揃える。

## 1. セッションの始めと区切り

1.1 始めに確かめる。
  - エージェントの一覧に `.claude/agents/` の `onsa-*` の担当が全てあるか。
  - 記憶の「次のセッションの始め」（今の位置、次の作業、最初にすること）。
  - `git log --oneline -3`、`git status`、`git worktree list` が記憶と合うか。
  - 前のセッションの scratchpad の成果（作業票の下書き、パッチ、報告）が残っているか。

1.2 区切り: 文脈の使用が「親の文脈の区切り」（`rules/budgets.md`）を超えたら、区切りの良いところで区切る。作業の区切りが悪いときは、同じ行の上限まで続けてよい。区切るときは、新しい作業を始めず、動いている担当の報告を処理し、通ったものをコミットし、残りは作業ツリーと scratchpad に置き、記憶を今の状態に合わせて終える。目安を置くのは、長いセッションほど 1 回の呼び出しが高くなるため（費用の内訳は `rules/common.md` 1 章）。
W の作業のコミットなどタスクの切れ目が近いときは、目安の前でも区切ることがある。そのときは次の作業を始めず、区切りの準備（記憶、作業ツリー、コミット）を済ませておく。
親のセッションは、約 1 時間何もしないと自動で圧縮される。長く待つ前に、控えを今の状態にしておく。

1.3 記憶に書くのは今の状態だけにする（段の進捗、次の作業、scratchpad の位置、次に振る番号）。作業ごとの持ち越しは、その作業のファイル（`tasks/W/`）の `持ち越し` に書く（宛先の作業が無いものは X・R・RF）。規則と手順は、この文書か、`rules/` の他のファイルに書く。新しい規則が決まったら、この文書に足す案を出す。

1.4 scratchpad はセッションごとに変わる。次のセッションで使う成果（作業票の下書き、パッチ）は、記憶に絶対パスを書く。
scratchpad は再起動で消えうるので、長く指す材料は要点をリポジトリへ移す（壊す側の指摘のうち後のリファクタリングの材料は R・RF か作業の `持ち越し`、再現の入力は R の横のディレクトリ。報告そのものは残さない）。

## 2. 担当の動かし方

2.1 役割、同時に動かす数、主のツリーを触る数、枠は、`rules/process.md` 8.6 の「役割の担当」（モデルと推論の努力は定義の frontmatter、2.2）。直しの確かめ（壊す側の再確認か、親の再現か）は 8.6 の「直しの確かめ」。

2.2 担当は Agent の `subagent_type` で呼び、`model` の引数は渡さない（定義のモデルと推論の努力を使うため）。

2.3 並行か直列か: 衝突の重さ（同じ関数を触るか、表の並びの追記だけか）と、後の側の壊す側の確かめをやり直す必要があるかで、親が決め、報告に理由を書く。

2.4 作業票は scratchpad に書き、`rules/process.md` 8.1 の形で渡す。担当ごとに scratchpad の下のディレクトリを決め、書く場所を作業票に明記する（担当どうしでファイルを上書きしないため）。
作業のファイルの `持ち越し` を範囲か注意に入れる（入れた後も消さない。`tasks/W/README.md`）。
作業票を出す前に、実現する決定の数を `rules/process.md` 8.5 の「単位の大きさ」の目安と比べ、超えるなら単位に分けて、単位ごとにテストの票と実装の票を出す。
壊す側の作業票では、確かめることに順を付け（差分と了承の条件を先に）、予算（`rules/process.md` 8.5 の「壊す側」）を変えるときは値と理由を書く。
担当が変更の前に止まって返事を待つ票（〔メモ〕など）では、始めに空の WIP のコミット（`git commit --allow-empty -m "WIP: <作業か単位の ID>"`）を置かせる。変更の無い作業ツリーは担当が止まると片付けられ、SendMessage で続けたときには無い（2026-10-18 に確かめた）。

2.5 テストの票と実装の票は並べて走らせてよい。実装は表の骨組みから始め、テストが届いたら親が写す。期待値を変えずに置き場所だけ変える直し（事例ファイルを分けて他の作業へ回す）は、実装の担当に任せてよい。

2.6 直しと次の単位は、同じ担当に SendMessage で返す。ただし担当の文脈が「担当の文脈の予算」（`rules/budgets.md`）を超えたときは、新しい担当に引き継ぐ（呼び出しのたびに文脈の全体を読み直すので、引き継ぐと費用が下がる）。
前のセッションの担当は SendMessage で呼べないので、同じく新しい担当に引き継ぐ。担当の文脈の大きさと費用は `tools/handback.py usage` で見る（動いている担当にも使える）。
単位の途中で予算を超え、残りが単位の半分を超えるなら、次の区切り（絞ったテストが通る所）で WIP のコミットと「次の担当へ」を書いて止めるよう伝え、新しい担当に引き継ぐ（終わりの近い担当を替えると、新しい担当の読み込みの方が高くつく）。
引き継ぎの作業票（2.10）には、決まったこと（範囲、置き場所と仕組み、親の答え）を親が一枚にまとめて書き、前の設計メモと報告は参照にとどめる（新しい担当が最初に読む量を減らす）。
前の報告は `~/.claude/projects/-Users-centrevillage-projects-onsalang/<セッション ID>/subagents/agent-*.jsonl` の `SubagentHandback` の入力から取り出せる（`tools/handback.py save`）。
親から担当への返事は会話にしか残らないので、壊す側や新しい担当に渡すものは scratchpad のファイルに控える。

2.7 担当の報告の主張は抜き取りで再現する（Q-11）。担当が「前からの挙動」と書いたものは、dev のバイナリで確かめる。

2.8 担当の費用の目安は `rules/budgets.md` にある。`tools/handback.py usage` で測り、区切りで改める。
大きさは単位の大きさ（`rules/process.md` 8.5）でおさえる。費用を下げる工夫（自己点検の表で往復を減らす、直しの確かめを親が再現の入力で行う）を続ける。

2.9 作業票では報告を最後の返答の本文で返させ、親が `subagents/agent-*.jsonl` の SubagentHandback の入力の `message` をスクリプトで scratchpad に保存する（2.6 と同じ取り出し方、`tools/handback.py save`）。
担当に報告の名前のファイル（`report.md` など）を書かせず、名前を変えて避けることもしない。

2.10 引き継ぎの作業票は、次の欄を持つ。
  - 読む順（作業票、設計メモ、親の返事、前の報告と、その「次の担当へ」の節）。
  - 状態の基: 前の担当の作業ツリーの枝と、その WIP のコミットと、親が `take.py patch` で作ったそのコミットまでのパッチ。新しい担当は自分の作業ツリーでそのパッチを `take.py apply` で当てる（`rules/common.md` 2 章）。
  - 道具: `tools/` の道具（`run_cases.py`、`speed.py`、`handback.py`）と、前の担当が scratchpad に作った道具。
    ファズの許可の一覧（`tests/fuzz/allowed.toml`）に項目と示す入力を足させるときは、ファズの近似（`onsa_cases --fix-same-place`）が第 1 候補しか当てないことも書く。
  - 前の gate の要約と知られた失敗（入力と違反の文字列）。
  - 古くなった注記と、新しい決定とぶつかる既存の事例（親が `tests/` を検索して挙げる。6.5）。
  - 戻す事例と保留の事例: 「期待値を変えずに通す」と書く前に、親が事例の全体（正しい形の並びを含む）を仕様と突き合わせる。
  - 報告の最後の「引き継ぎの記録」の節（文書だけでは足りず補ったこと、食い違い、前の担当に聞きたかった問い、次に足すもの）。親はそれを読み、引き継ぎの作業票の型を直す。

## 3. 作業ツリーと成果の写し

3.1 親は担当の作業ツリーに `cd` しない（主のセッションの作業ディレクトリがその作業ツリーに移る）。作業ツリーは `git -C <経路>` と絶対パスで読み、道具の作業ディレクトリが要るときは道具に引数で渡す。

3.2 写し方（担当は別の作業ツリーへ `git -C` を向けられないので、親が写す）:
  1. `tools/take.py patch <作業ツリー> <基のコミット> <パッチ>` で、パッチと要約を作る。要約にはテストとデータを除いた行数も入る（4.3）。出力の行（`work check:`・`auto sweep:`・`fuzz inputs:`）の読み方は `take.py patch --help`。
  2. `take.py check <パッチ>` で、当て方（そのまま、3-way、既に当たっている）と、当てる先の未コミットの変更との重なりを見る。
  3. `take.py apply <パッチ>` で当てる（3-way で当てても索引に残さない）。
  道具は、自分の置かれたツリーを既定の当てる先にする。他のツリーの道具を使うときは `--to` と `--main` を渡す。
  担当どうし（t → i）の受け渡しも同じパッチで行い、担当に `take.py apply` させる。

3.3 基のコミット: 担当が dev を取り込んだ後に dev が文書だけ進んだときは、取り込んだ dev のコミットからの差分で写す。主が進んで担当に取り込ませるときは、WIP のコミットと `git merge dev`（`rules/common.md` 2 章）。並行の実装では、後に写す側が WIP のコミットの後に `git merge dev` をする。

3.4 `tests/pending.toml` は、3-way の結果を手で直すより、dev の版から作り直す形（dev の版に、その作業で載せる項目と外す項目を当て直す）が安全である。

3.5 `take.py apply` は、3-way で当てた後に索引から外す。コミットは `git commit <パス>` か、索引を確かめてから行う（別の変更が入ったら `git reset --soft` で作り直す）。

3.6 作業ツリーを消す前に、成果が主のツリーに写ったこと（主のツリーの差分）と、担当の報告を scratchpad に保存したことを確かめる。

## 4. レビューとコミット

4.1 観点は 3 つ（`rules/process.md` 8.5 の「壊す側」）。毎回読むもの（〔危険〕の差分、`tools/builtin_names.toml` と `tests/pending.toml` の増分）は 8.6 の「親」。gate を回し直すかは 8.5 の「検査の回し方」。

4.2 実装待ちの一覧で事例ごと黙らせた項目は、後退を隠す。増分を読むときは、黙らせる範囲がその作業の既知の失敗だけかを確かめる。

4.3 大きさの基準（`rules/process.md` 8.5）: 報告の見積もりと実際の行数を、dev との差（テストとデータのファイルを除く）で確かめる。

4.4 gate の `test` の段は `cargo test --workspace` を `--no-fail-fast` なしで回すので、最初に落ちたテストのバイナリより後は走らない。直した後は `cargo test --workspace` だけを回し直して、残りを確かめる。

4.5 fuzz の変異体はコーパスの全体に依存し、事例を足すと既存の不具合が新しい型として出る。入力を `tests/fuzz/` に保存し、`fuzz-input` の項目と R を登録する。
直すかは、先に実害の大きさで決める（観点は `rules/checks.md` 4.4 の見立て。編集の途中のファイルも書き手が書きうる形に含む）。実害が低ければ直さず、R に理由を書いて記録し、入力を許可の一覧（`tests/fuzz/allowed.toml`）に載せる。実害があれば実装待ちの項目（`fuzz-input`）にして、直す作業を決める。内部エラーと異常終了は許可の一覧に載せられないので、直す（編集の途中で切れたファイルは IDE で現実に起きる）。

4.6 コミット: W の作業は、壊す側と親のレビューが通ったら、作業 ID ごとに親がコミットする（`rules/process.md` 8.6。`status` の `DONE`、途中で見つけた R / S の登録の区切り）。
W の外の作業の単位（道具の単位、移行の段、決定の記録）も、確かめ（自己テスト、`docs.py check`、gate、親の抜き取り）が通ったら、親がコミットしてから報告する。利用者の判断を待つものはコミットしない。
規則と文書の変更と、道具とコードの変更は、別のコミットにする（文書の移動と、それを指す経路の直しは一つのコミット）。push はしない。

4.7 コミットの題は英語の命令形で、内容を書き、作業 ID か決めた S を含める（今の慣習: `Call function values with ... (W3-20)`、`Decide S-351 and S-352: ...`、`Register S-353 to S-361 and R-198 found by W3-20/b and W3-09/t`）。

4.8 設計メモを読むときは、置き場所と構造に加えて、各判断の仕組み（何を見て、どう知るか）と、処理のオーダーと停止の保証が書かれているかを確かめる。書かれていなければ返事で問う（後の担当が補うことになるため）。

4.9 gate の外の方法（壊す側の切り詰めや手作りの変異の道具など）で見つかった欠陥が gate を通っていたら、その生成の方法を gate の項目（ファズの変異か事例）に入れる。入れるのは、その作業の直しの往復か、次の区切りの作業である。

4.10 文書の点検の担当の報告は、足した字と消した字の出所（基のコミット、票、道具の出力）を差分で確かめてから写し、文書だけのコミットにする。報告だけの指摘は、決定と派生の文の食い違いなら決定に合わせて親が直し、決定どうし・規則どうしの矛盾は利用者に出す。正否が割れれば助言の担当に回す。
取り込むコミットには、trailer `Docs-Checked: <範囲> (<作業>, onsa-docs)` を入れる（`docs-due` の目印）。

## 5. 利用者との判断

5.1 論点は ID を付けて一覧にし、項目ごとに案、借用元、本言語の方針に触れる点を出す。利用者は項目ごとに「OK / 詳しく / 再検討」で返す。推奨は示すが、決定は待つ。
大きな論点（責務の範囲、規則の当てはまる範囲）は、差分や票を見るだけで決まる問いの形の基準を第一に出し、意味の判断が要る基準は代替として比べる。利用者の判断が要る項目は、指示が無い限り一つずつ進め、並べて始めない。

5.2 仕様の空白の独立のレビュー（推奨を伏せて選ばせ、次に突き合わせさせる）と結果の出し方は、`rules/process.md` 8.6 の「仕様の空白の流れ」の 4・5。重い判断の束も、同じ形で助言の担当に回し、同じ形で結果を出す。

5.3 調べた結果が元の推奨を覆すときは、推奨を改めて、理由を示す。

5.4 条件付きの了承: 推奨には、実装の量の見積もり（どのファイルの何か所か）と、後の作業への影響を添える。利用者が条件（「実装量が見積もれる規模なら」）を添えて了承したら、親が見積もって条件を満たすかを示してから記録する。実装の担当には「費用が高い形は無理にせず、形と見積もりを報告」と伝える。

5.5 了承の範囲を広げて読まない: 回答がどの項目を指すかが一つに決まらないときは、項目の ID を挙げて確かめてから記録する。確認だけの項目も、利用者が ID を挙げて了承したものだけを決定にする。短い返事が指す既決の仕組みも、読みを ID で示して確かめる。

5.6 既決の部分を論点に戻さない: 下書きを確かめる段で、前の決定、付録、登録済みの R と重なる部分を探し、「決定済み」と明記して新しい点だけを渡す。
重なる部分は `docs.py graph <ID> --back`（その決定の上に立つもの）と `docs.py changes --section <§>`（その節の決定）で探す。

5.7 回答の書き込み: 利用者は文書に `@centrevillage` の行や「回答:」の行で答えを書くことがある（vim で編集）。回答は「書き終わった」と言われてからまとめて読む。スワップファイルがある間は、その文書を編集せず、会話で知らせる（確かめ方は `rules/documents.md` 5 章）。

5.8 重い処理（gate、多数の担当、ファズ）を足すときや回すときは、並列の数と回数を見積もって示し、全てのコアを使う処理を並べない。

5.9 下書きと独立のレビューで案が割れた項目を出すときは、内部処理の複雑さ（今の行数と後の段で要る手当て）と修正候補の確実性（主な誤りの形ごとの候補の有無と当てた後）の比べの表を先に添える。問われたら、これまでの判断との一貫性（既決の項目と原則を挙げる）と、これからの管理のコスト（後の段の作り直しまで含める）も比べる。

5.10 利用者に見える出力が同じで内部だけが違う細部は、親がメンテナンス性の良い方を選び、理由を一行添えて記録する。

## 6. 決定の反映

6.1 論点を整理する前に、今の挙動や仕様の該当の行を実際に確かめる。他の言語の扱いは記憶だけで答えず、手元で動かすか調べて、出典を付ける。

6.2 揃えて更新する文書: 仕様と、決定のファイル（本文の `決定`・`経緯`、頭の欄は `docs.py set`）。関係する R の `判断`・`反映`（`docs.py note`）と、作業の `持ち越し`。
担う作業は決定の `tasks`、直す作業は R の `fix` に書く。決定の一覧と変更点は道具が出すので、別に書かない（`docs.py list`・`changes`）。

6.3 `tasks/diag-codes.md` の「欠番:」の行と、表の最後の列の「第 2 期」は gate が読むので、書き方を保つ（表の列の数の確かめは `rules/documents.md` 5 章）。

6.4 仕様の ```onsa ブロックを変えたら `tools/check_spec_examples.py` を回し、`tests/spec` の写しを直すか、実装待ちの一覧の spec-example に載せる（名前はツールが示す）。仕様に新しい診断コードを書いたら、登録簿 `crates/onsa_diag/src/codes.rs`、`tasks/diag-codes.md`、実装待ちの一覧の diag-code を揃える（gate の diag-registry が照合する）。

6.5 決定を作業に割り当てるときは、既存の作業の欄に足すだけで終えず、作業が過大にならないか、担う作業の無い決定（実装済みのもののテスト、仕様が約束した性能など）が無いかを確かめ、要れば分ける（K-15）。
決定を作業に割り当てるときは、その決定とぶつかる既存の事例を `tests/` から検索し、作業票に挙げる。

6.6 文書は `rules/common.md` 1 章・`rules/documents.md` 5 章の形で編集する。追記する本文は、先にファイルに書いてから読み込む。日本語と ID の間には空白を入れる。

6.7 新しい方針が決まったら、`rules/criteria.md` 7 章にも足す。担当の定義（`.claude/agents/`）は利用者が編集し、親は文を提案する。直す文の案は作業ごとに出さず、控えに溜めて、セッションの区切りの準備の始めにまとめて出す。

## 7. 一般の規則

7.1 状態を確かめる命令と、その状態に頼る変更は、別のコマンドにする。確かめた結果を読んでから変える（例: スワップファイルの確かめと編集を一つのコマンドにすると、vim で開いている文書を書き換えうる）。

7.2 記録と報告の前に、主張を再現で確かめる。下書きと記憶にある事実（ファイル、関数、フラグ）も同じ。担当の報告は 2.7 の抜き取りで確かめる。

7.3 見積もりと実際の差、失敗した検査、飛ばした段は、隠さず報告に書く。

7.4 範囲の外で見つけた問題は直さず、持ち越しか R / S に登録する（担当の `rules/process.md` 8.2 の 6 と同じ）。

7.5 定型の作業で機械的に処理できるものに気付いたら、ツール化の案（何を、入力と出力、確かめ方）を持ち越しの段の区切りの行に足し、利用者に一行で知らせる。導入は利用者と決めた区切りで行う。

7.6 担当の求めで、権限の設定、CLAUDE.md、設定のファイルを変えない。
