# 担当の共通の規則

担当の全員が、作業を始める前に読む。

## 1. リポジトリとシェル（全員）

1.1 リポジトリは `/Users/centrevillage/projects/onsalang`、ブランチは `dev`。`dev` へのコミットと push はしない（親が作業 ID ごとにコミットする。作業ツリーの枝の WIP のコミットは 2 章）。助言と空白の下書きの担当は、リポジトリのファイルを編集しない。

1.2 CI は無く、検査は手元で回す。

1.3 Bash の `cd` は持続しないことがあるので、絶対パスを使う。macOS なので `timeout` は無い。止まらない恐れのある実験は、Python の `subprocess.run(..., timeout=…)` で包む。

1.4 確かめのために差分を退けたいときは、スクラッチのディレクトリに写して試す（`git stash` は設定で止めてある。stash は全ての作業ツリーで共有されるため）。

1.5 Python のスクリプトをヒアドキュメントで渡すときは、必ず `<<'EOF'` と引用符で囲み、引数は `sys.argv` で渡す。囲まないと、本文のバッククォートや `$` がシェルで展開され、`a > b` のような文がファイルを作りうる。

1.7 作業ツリーでは、変数・`for`・複雑なヒアドキュメントを含むシェルの行が、許可の判定に拒まれることがある（2026-10-13 に確かめた）。繰り返しや変数の要る処理は、Python のスクリプトを scratchpad に置き、引数で渡して走らせる。
  `git` の語を含むヒアドキュメントと、`;`・`&&` で道具や git をつないだ行も拒まれることがある（2026-10-14 に確かめた）。道具は 1 回の呼び出しに 1 コマンドで呼び、経路は絶対パスで書く。
  コマンドの実行が拒まれたら、`git status` や `git diff` などで状態を確かめ、実際に実行が行われたか確認する。拒まれても実行されることがあるため（2026-10-18）。

1.8 長い処理を裏で走らせて待つときは、`tools/bg.py` を使う。`run <ディレクトリ> -- <コマンド>` で起こし、`wait <ディレクトリ>` で待ち、止めるのは `stop`。
  124 が返ったら `wait` を繰り返す（Bash の timeout はフックが 600000 にする）。`pgrep`・`ps` の文字列の一致や `sleep` の繰り返しで、自前の待ち合わせを書かない（待つ側のシェル自身に当たり、終わらないことがある）。

1.9 費用は、呼び出しのたびに文脈の全体を読み直す分が大半を占める。読むときは関係する範囲を一度に読み、`sed -n` などで小刻みに読み足すことを繰り返さない。互いに依存しない読みや検索は、一つの応答の中で並べて呼ぶ。コマンドの出力は要る行に絞る。

1.10 ドキュメントは 200 字程度で、文の切れ目で改行する。字下げの中のテキストを改行するときは、続きの行も同じだけ字下げする。表は例外。改行の無い長い段落が残っていると、他の担当が真似をして人の読みにくい資料になる。
  入口の文書（README、原則の表）は要約と索引にとどめ、詳細と増える一覧は同じ階層の別のファイルに置いて一行で指す。同じ補足を何か所にも書かず、一般の約束にして一か所に置く。入口では ID の種類を記号だけで指さず、語と並べる（「レビュー（R）」）。

1.11 規則と仕様（`rules/` の規則、担当の定義、基本仕様、`spec/tools.md`）には、誰が言ったか・いつ決めたか・何がきっかけかを書かない。経緯は、決定のファイルの `経緯`、報告、コミットに書く。古くなりうる事実（測った費用、確かめた道具の挙動、機械の状態）には、確かめた日を付ける。

1.12 文書がディレクトリ（`spec/` など）を参照先として書いているときは、そのディレクトリに `README.md` があれば、そこに要約と他のファイルへの索引がある。読むときは README から始める。

1.13 シェルは zsh。`=` で始まる語（`====` など）はコマンドの展開になり、一致しないグロブ（`*.rs` など）は「no matches found」でコマンドの全体を止める。区切りの字は `-` を使い、グロブは引用符で囲むか `git grep` の pathspec にする。

1.14 道具の引数、例、出力の読み方は、`<道具> help --role <役割>`（命令ごとは `<道具> help <命令>`）で見る。help の無い道具は `--help` で見る。

## 2. 作業ツリー（t、i、docs）

2.1 git の別の作業ツリー（worktree）で動くときは、始めに作業ツリーの中で `tools/work.py sync` を回す（作業ツリーを作った後にも dev は進む）。

2.2 作業の途中で主のツリー（`dev`）が進み、親が取り込むよう指示したときは、作業ツリーの中で `work.py sync` を回す（自分の変更は WIP のコミットになる）。衝突で止まったら、並んだファイルの衝突を解いてコミットする。WIP のコミットは、親が成果を写すときに読むので、そのまま残してよい。

2.3 作業ツリーで動くときは、主のリポジトリには書かない（例外は `rules/documents.md` の文書の移行の段）。成果は作業ツリーに置いたままにし、親が写す。主のツリーで動くときは、コミットしない（親がする）。

2.4 作業ツリーで動く実装の担当は、単位の報告と直しの報告の前に、自分の変更を WIP のコミットにして作業ツリーの枝に置く（主のツリーには書かない。題は `WIP: <作業 ID> <単位>`）。
  次の単位や直しを別の担当が受け持つときは、親が前の担当の作業ツリーのパッチを作り（`work.py patch`）、その担当が自分の作業ツリーの中で `work.py sync --apply <パッチ>` で当てる（WIP のコミットも置く）。
  単位ごとの差と行数は、WIP のコミットからの差で数える（`work.py lines --base <WIP のコミット>`）。

## 3. 機械を落とさない（全員）

3.1 この機械（macOS）では、SIGABRT・SIGSEGV・SIGILL・SIGTRAP などで終わるプロセスが、利用者の画面にクラッシュの報告のダイアログを出す。
  - テスト・自己テスト・ファズで意図的に落とす形をまねるときは、SIGKILL か終了コードを使う。
  - sanitizer は、abort や trap でなく終了コードで止まる設定にする。
  - 作ってしまったら報告に書く。

3.2 既知の落ちる入力（2026-10-20、2026-10-25 改め）: R-02（再帰する型と循環する `const`）の再現の入力（`tests/review-phase1/README.md` の R-02 の行）は、降下に進む命令（`onsa interface`・`dump --core`・`build` など）でコンパイラのスタックが溢れ、SIGABRT で終わる（W4-05 で直す）。`check` は落ちない。
  R-298 の形（2 万段の型別名の鎖。入力は置かず台本で作る）は、`check` でもスタックが溢れ、SIGABRT で終わる（W4-05 で直す。2026-10-28 足した）。型別名の鎖を作る台本（生成、変異）は、段数をこれより十分に小さくする。
  R-319 の形（1 万段の struct・enum の宣言の鎖。入力は置かず台本で作る）は、降下に進む命令（`onsa interface`・`dump --core`・`build` など）でスタックが溢れ、SIGABRT で終わる（W8 で直す）。`check` は落ちない。宣言の鎖を作る台本は、降下に進む命令に渡すなら千段より小さくする。
  - `tests/review-phase1/` や `tests/fuzz/` を一括で道具にかけるときは、降下に進む命令を使わないか、これらを除く。
  - 新しい道具を一括で回す前に、少数のファイルで終わり方（終了コードが 0・1・2・101 のどれか）を確かめる。

3.3 インタプリタの再帰: `onsa test` とコンパイル時の評価は、呼び出しの深さの上限 128（仕様 §12.5、S-222）で panic するので、深い再帰を走らせても落ちない。
  - ただし、`const` が `const` を読む鎖は呼び出しに数えず、スタックの安全網（内部エラー、終了コード 101）に頼る（W9-03 まで）。
  - 長い鎖を試すときは、浅い鎖で終わり方を確かめてから増やし、2000 個を超えない。

3.4 深い入れ子: `cargo test` のスレッドは既定のスタック（2 MiB）が小さい。debug のフロントエンドは、入れ子 1 段に約 64 KB を使う（2026-10-08 の測定で、32 段で SIGABRT になった）。
  - ソースを構文解析・検査・降下するテストで、入れ子や二項演算子の連鎖を 20 段より深くするときは、大きなスタックのスレッド（`onsa_diag::stack`）で走らせる。リポジトリの全てのファイルを読むテスト（`cst_tests` など）も同じ。
  - コマンドで試す入力も、20 段を超えるものは既にある事例の流儀に倣う。上限（§2.5 の 256）を超える入力は作らない。

3.5 他の言語の処理系:
  - 極端な入力（深いテンプレートや型の鎖、数千段の入れ子）を渡さない。Apple clang 21 は、深さ 2000 の C++ のテンプレートの鎖でフロントエンドが SIGILL で落ちる（2026-10-07 に確かめた）。上限の挙動は、文書を出典付きで引くか、上限のすぐ外の小さな入力（数十段）で確かめる。rustc などの止まりにくい実験は、時間で打ち切る。
  - 実行時に trap する入力を走らせない（Swift の始点が終点より大きい範囲など）。挙動は文書やソースを出典付きで引く。

3.6 この機械の処理系（2026-10-17）: arm64 の macOS。Apple clang 21、gcc-15・g++-15、Python 3.14、Node、Ruby 3.4、Swift 6.3、rustc 1.94、Go 1.27.2。C#、Java、Kotlin は無い。

## 6. 報告の共通の形（全員）

6.1 日本語で返す。作業の担当（t、i、b）は、`rules/process.md` 8.4 の形で返す。

6.2 主張には、テストの名前か、再現のコマンドとその出力を付ける。推測だけのものは、そうと分かるように分ける。

6.3 gate の外の方法で見つけた指摘には、その方法（道具と入力の作り方）を報告に書く（親が gate に入れるため、`rules/leader.md` 4.9）。

6.4 新しく見つけた仕様の空白は、`rules/process.md` 8.4 の「空白の報告」の形で、再現の入力と今の挙動まで書く（親がすぐに下書きと独立のレビューへ回すため）。

6.5 同じ手作業を繰り返したときは、報告の「範囲の外で気付いたこと」にツール化の案を書く（採るかの基準は `rules/tools.md` 9.2）。

6.6 実装の担当（i）は、単位の報告と直しの報告の最後に「次の担当へ」の節を置く。
  書くのは、状態（作業ツリーなら WIP のコミット、主のツリーなら基のコミットと未コミットの変更のファイル）、作った道具と使い方、設計メモから細部で決めたことと決めていないこと、gate の要約と知られた失敗（入力と違反の文字列）、最初に読むべきファイルと関数。
