# 作業の手順

テスト・実装・壊す側の担当が、作業を始める前に 8.2〜8.6 を読む。親は作業票を書くとき（8.1）と報告を読むとき（8.4）に使う。空白の下書きと助言の担当は、空白の報告の形（8.4）と仕様の空白の流れ（8.6）を読む。

## 8. 作業の指示の雛形

ワーカーへの指示は、この雛形を埋めて渡す（Q-01、Q-04、Q-09〜Q-14、D-15、D-16）。
作業は `tasks/W/`（段の一覧は `tasks/stages.md`）、その進め方は 8.6 である。8.2 から 8.6 は、担当が定義の指示で自分で読むので、作業票には写さない（作業票は 8.1 の形だけ）。

### 8.1 作業票（親が埋める）

作業票の骨組みは `python3 -B tools/docs.py ticket <W> <単位>/<役割>` が、作業のファイルと決定から出す（作業のファイル、状態、規模、依存、実現する決定、直す R、仕様の節、持ち越し）。決定と R の本文（R の `判断`・`反映` を含む）は、担当が ID のファイルで読む。
親は残りの欄を埋める。作業票に書く ID は登録済みのものにする（`docs.py path <ID>` で引ける）。

```markdown
- 役割と単位: <U1/t など。テスト（仕様だけから） / 実装 / 壊す側>
- する: <...>
- しない: <...>（扱う作業の ID）
- 書く場所: <scratchpad の下のディレクトリ>
- 読むもの: <ファイル>（テストの役割には、仕様と CLI の使い方だけを渡し、実装のコードは渡さない）
- 期待値: <テストの票の ID か、既存の期待値付きテストの場所>
- 危険な経路: <降下 / modes / C の生成 / ターゲットの pass に触れるなら書く。親が差分を読む>
- 進め方: <難しい作業は R-06 の形: 設計メモを先に出し、親が読んでから実装する>
- 見積もり: <実装の役割は、着手の前（設計メモか最初の段）にテストとデータのファイルを除いたコードの行数の見積もりを出す。8.5 の大きさの基準に使う>
- 予算: <文脈の予算（8.5 の「単位の大きさ」）。変えるときは値と理由>
- 受け入れ条件: 8.3 の完了の定義。加えて <作業に固有の条件>
```

### 8.2 守る規則

1. **テストを先に（Q-01）。** 実装の役割は、テストの役割が仕様から書いた期待値を通す。期待値を実装の出力から作らない。golden（修正候補の写しを含む）を作るか更新したら、報告に並べる（Q-04。承認は親）。
   写しの書き直しを歯止めが拒んだら、新しい出力が誤りでないかを確かめる。写しが規則を担っていたなら、その規則を `[[test.fix]]` の性質か toml の `property` に移してから `UPDATE_GOLDEN=worse` で書き直し、報告に分けて並べる。
2. **閉世界（Q-09）。** 仕様にあってこの版で未実装のものは E0200（機能名を添える）。仕様に無いものは、受理せず、最も保守的な拒否にする。黙って受理しない。表現（IR の構造、表の欄）は先に入れ、実装していない所を E0200 で知らせる（R-81）。
3. **仕様の空白（Q-10）。** 基本は、最も保守的な形で実装し、その位置に `// SPEC-GAP(<ID>): <内容>` を付けて報告する（ID は登録済みの S / R / A の番号。無ければ `NEW` と書き、親が登録する）。ただし、その空白を決めないと関連する空白が連鎖して生じると判断したら、作業を止めて報告する。
4. **証拠（Q-11）。** 報告の主張には、テストの名前か、再現のコマンドとその出力を付ける。
5. **判断の置き場所（Q-14、D-15）。** 置き場所の表にある判断を、他の場所で計算し直さない。後の段は、前の段が出力した構造を読む。組込みの名前の文字列との比較は、登録簿の外に書かない。
6. **範囲を守る。** 範囲の外を直したくなったら、直さずに報告する。
7. **規範は仕様。** 他の言語の挙動（「Rust ではこうなる」）を根拠にしない。仕様に書かれていなければ空白として扱う（R-133）。

### 8.3 完了の定義（Q-13）

1. 対応する仕様の節を挙げる（テストの断片の `[test] spec`、Q-05）。
2. 正例と否定例がある。否定例は、診断コードごとに 3 件以上（実際に走って照らしたマーカの数。gate の `diag-negatives` が数え、届かないコードは実装待ちの一覧の `diag-code` に置く。K-13）。
3. 仕様から書いた期待値付きのテスト（Q-01）が通る。
4. 関係する組み合わせ（入れ子、分岐、`par`、クロージャ、総称、モジュール）のテストがある。
5. 算術・変換の意味に触れたら、テストベクトル（D-16）を作り直し、差分を報告する（承認は親）。
6. SPEC-GAP の印が照合を通る（Q-10。gate の `gap-marks`）。
7. 組込みの名前の直書きが増えていない（Q-14。gate の `builtin-names`。許可リストは `tools/builtin_names.toml`）。同じ判断を二か所に置いていない（D-15）。
8. `tools/gate.sh --work <作業か単位の ID>` が通る（受ける形は `tools/gate.sh --help`。Q-08。`--quick` は判定にならない。回し方は `rules/checks.md` 4 章）。
9. 壊す側のレビューで、重大度が高の指摘が残っていない（Q-12）。
10. 仕様、決定・R・作業のファイル（状態は `docs.py set`）、診断コードの表 `tasks/diag-codes.md` と、再現の入力の対応（`tests/review-phase1/README.md`。直した項目の再現の入力は、期待値付きのテストへ移す）を更新した（`docs.py check` が通る）。

### 8.4 報告の形

```markdown
## 作業 <ID> の報告

- したこと: <変更したファイルと要点>
- 主張と証拠: 「<主張>」— テスト `<名前>` / 再現 `<コマンド>` → <出力>
- SPEC-GAP: <ID か NEW> <位置> <内容>（止めた場合は、連鎖すると判断した理由）
- 仕様の空白: 新しく見つけた空白ごとに、下の「空白の報告」の形で書く
- golden とテストベクトルの更新: <一覧>（`UPDATE_GOLDEN=worse` で通した写しは分けて書く）
- 範囲の外で気付いたこと: <...>
- 完了の定義: 8.3 の 1〜10 の各項目の結果
```

空白の報告（全ての役割が使う。下書きの担当が調べ直さずに済むよう、見つけた担当が事実まで書く）:

```markdown
- 仕様の空白: <ID か NEW> <一行の要約>
  - 仕様の文: <節と、該当の文の引用>
  - 割れる読み: (1) <…> (2) <…>
  - 再現: <入力の置き場所> → 今の挙動 <診断・値・終了コード>
  - 仮の扱い: <SPEC-GAP の印の内容、期待値を書かなかった事例、保留の印>
  - 待つもの: <決まるまで進められない作業・事例>
  - 急ぎの見立て: 止める / 次の作業の前 / 後の段
```

文書の点検の報告（文書の点検と移行の担当が使う）:

```markdown
## 文書の点検 <範囲の名前> の報告

- 範囲: <基>..<先>、ID <…>。読んだファイル <数>（一覧は末尾）。`docs.py check`: PASS。点検しなかったもの: <…>（理由）
- 見つけたこと（一件ずつ）:
  - <種類: 矛盾 / 退行 / 重なり / 古い記述 / 未反映 / 関係の抜け> <ID と経路:行>
    - 引用: 「…」（<ID か §>） / 「…」（<ID か §>）
    - 経路: <`show` → `back` → … の辿り>
    - 直し: 直した（<差分の要約、字の出所、確かめ>） / 報告だけ（推奨: <…>、決める人: 親 / 利用者）
    - 確信: 高 / 中 / 低
- 道具の確かめの案: <機械で見つけられた形なら、どう確かめるか>
- 範囲の外で気付いたこと
- 読んだファイルの一覧
```

### 8.5 役割ごとの追記

- **テストの役割:** 仕様と CLI の使い方だけを読む。期待値は仕様から手で導き、実装より先に書く。仕様の空白に気付いたら、その部分の期待値を書かずに報告する（実装の前に空白を表に出す）。
  修正候補で期待値に書くのは、仕様が約束するもの（候補の数と、`[[test.fix]]` の性質）だけにする。
  候補を当てた後の全文（`.fixK`、`spec/foreign-forms.toml` の `fixed`）は実装の回帰の写しで、テストの役割は書かず、実装の役割が `UPDATE_GOLDEN=1` で作る（8.2 の 1）。
  テストの役割は、写しの本文を書かない。新しい事例には `.fixK` を置かず、toml の新しい例の `fixed` には候補の数だけ空の本文（`''''''`）を置く。本文は実装の票が書き、実装の票が無ければ親が書く。
  診断の位置など、ほかにも仕様が決めない細部は期待値に書かない。
- **壊す側:** 3 つの観点（実装が仕様とずれていないか、構造が健全で保守に耐えるか、仕様に無い前提を導入していないか）で、再現する入力を探す。指摘には、再現の入力と重大度を付ける。
  先に差分と作業票を読み、誤りが入りうる所の見当を付ける（境界の形、同じ判断の重複、書かれていない前提、入力の大きさで繰り返す処理）。
  見当ごとに、絞った入力（数十〜数百件の格子や変異）で確かめる。
  広い無作為の掃引は gate のファズ（全体を広く見る役）と重なるので、見当を確かめた後に予算が残るときだけ、差分の通る所に絞って行う。
  ファズが捕まえない形の類に気付いたら、掃引を広げずに、ファズに入れる案として報告する（`rules/leader.md` 4.9）。
  予算は `rules/budgets.md` の「担当の文脈の予算」と「壊す側の自作の掃引」（自作の掃引は、生成した数千件以上の入力を全数で検査する処理）で、作業票が別の値を書けばそれに従う。
  予算に近づいたら新しい確かめを始めず、残りを「未確認」として報告する。
  どこまで深く追うかは、差分で入ったか、了承の条件に触れるか、書き手が書きうる形か、を見て決める。
  前からある挙動（dev のバイナリでも同じ）と分かった形は、再現の入力と重大度の見立てを報告し、変種や分類を広げない。
  報告には、見当ごとの入力の数と結果を短く並べる（確かめなかった見当も分かるように）。
- **実装の役割（難しい作業）:** 設計メモを先に書いて親に渡し、親が読んでから実装する（R-06 の進め方）。
  処理の設計（読み直し、探索、候補の補完など）には、計算量のオーダーと、停止・収束の保証を、根拠と前提を付けて書く。
- **実装の大きさの基準:** リファクタリングを全て後回しにすると、後のリファクタリングの作業が肥大する。
  実装の役割は、着手の前（設計メモか最初の段）にコードの行数を見積もる（作業票の「見積もり」。部分ごとに分けてよい）。見積もりも実際の行数も、テストとデータのファイルを除いて数える。
  実際の行数が「リファクタリングに入る大きさ」（`rules/budgets.md`）を超えたら、手を止めずに、同じ作業の中で、壊す側に渡す前にリファクタリングする（分けられる単位、重複、使われない枝）。報告の先頭に、見積もりと実際の行数とリファクタリングの内容を書く。
  リファクタリング自体が作業票の範囲に収まらないほど大きくなるときは、実装の役割はそこで止めて形と見積もりを報告し、親が直後の作業として切り出して、次の作業より先に行う。例外は親が利用者と決める。
  既に大きいファイル（`parser.rs`、`body.rs`、`emit.rs` など）はこの基準の外で、リファクタリングの候補の一覧に置き、時期を別に決める。
- **単位の大きさ（文脈の予算）:** 一つの単位は、1 体の担当が「担当の文脈の予算」（`rules/budgets.md`）の内で終えられる大きさにする。呼び出しのたびに文脈の全体を読み直すので、費用は文脈の長さのおよそ 2 乗で増える。
  目安は `rules/budgets.md` の「単位の大きさ」で、作業を観察して改める。
  テストの票も同じ単位で分ける。設計メモの見積もりが目安を超える単位は、設計メモの中で分ける案を出す。
- **検査の回し方（親）:** 担当の回し方（役割ごとの、作業の途中・報告の前・回さないもの）は `rules/checks.md` 4 章に定める。ここには親が決めることを書く。
  - 実装待ちの一覧に項目の全体で載る gate の項目は、`--work` がその until のときと段の終わりにだけ回る。作業がその項目の判定に関わると分かっているときは、親が作業票の受け入れ条件に `--work <その項目の until>` を足す（`--work` は重ねられる）。
  - 親は、`take.py patch` の `work check:` の行に従う（三つの答えと意味は `take.py patch --help`）。親がコードを直したときは、主のツリーで作業の検査を回す。
    写した後に登録（文書の表、`tests/pending.toml`、`tools/builtin_names.toml`）を変えたら `--only static` を回し、`tests/pending.toml` を dev の版から作り直したときは `cargo test -p onsa_tests` も回す。文書だけの決定のコミットは `--quick` で確かめる。
  - 網羅の検査: 主のツリーのコードか事例のコミットが、post-commit フック（`tools/after_commit.py`）で網羅の検査と基のバイナリの保存を裏で起こす。親は区切りで、gate の要約と `take.py patch` の `auto sweep:` の行を見る。FAILED なら、行が指す出力を読み、`rules/leader.md` 4.5 の形で仕分ける。
    全体を自分で回す前と、続けて大きく変えるときは止める（止め方と起こし方は `tools/after_commit.py --help`）。
    段の終わりは `--stage-end` で全体を回す（8.6）。
  - `warning:` の行（時間の目安を超えた）は、続けて出たら、分割の数か抜き取りの割合（`tools/gate_steps.py`）を見直す。一度だけなら、他のビルドと重なっただけのことがある。
  - 主のツリーの gate が `target/debug` の大きさの警告を出したら、担当が動いていない区切りで `cargo clean --profile dev` を回す（基のバイナリと履歴は `target/base`・`target/gate` にあり、消えない）。
- **実装の役割の自己点検（報告の前に）:** 壊す側の指摘で繰り返し出た穴の種類である。報告の前に、自分の差分について確かめ、結果を報告に書く。

  | 種類 | 確かめること |
  |---|---|
  | 何も走らずに通る | 対象が 0 件、飛ばし、比べたサンプルが 0 のとき失敗にする。飛ばしてよいものは既にある情報（実装待ちの一覧、事例の設定）で決め、それ以外の飛ばしは失敗にする |
  | 実装待ちの一覧で黙らせる範囲 | 一覧で黙らせられるのは、その項目が指す失敗だけ。内部エラー、事例の誤り、器が回らない誤りは黙らせない。項目の全体で載せると新しい誤りが隠れるので、既知の原因だけを外した形を常に回す |
  | 判断の重複（D-15） | 同じ表、定数、判定を二か所以上に置かない。名前の一覧などは一か所から機械的に出し、自己テストで突き合わせる |
  | 位置と黙った捨て方 | 診断と内部エラーに原因の位置を付ける。`.ok()`、`if let Ok`、`unwrap_or` で失敗を黙って捨てない |
  | この機械 | SIGABRT・SIGSEGV などで終わるプロセスを作らない（クラッシュの報告のダイアログが出る）。作業ディレクトリはプロセスごとにする |
  | 決定性と時間 | 乱数は決まった種にする。gate の項目は時間の予算を持つ |
  | 大きさ | 着手の前の見積もりと実際の行数を報告に並べる。上の「実装の大きさの基準」を超えたら、壊す側に渡す前にリファクタリングする |

### 8.6 レビューの反映の作業（W）の進め方

`tasks/W/` の作業（段 W1〜W10）に共通の規則で、8.1〜8.5 に加えて従う。

- **作業票。** 着手のときに、親が 8.1 の形で埋める。骨格は、作業のファイル（頭の欄の `depends`・`size`・`marks`、本文の `内容`・`単位`・`持ち越し`）と、決定の `tasks`・R の `fix` である。受け入れ条件は 8.3 の完了の定義で、作業に固有の条件は `内容` に書いてある。
- **役割の組（K-06）。** 各作業は「テスト（仕様だけから）→ 実装 → 壊す側」の三つの票で行う（Q-01、Q-12）。票は作業 ID に `/t`（テスト）、`/i`（実装）、`/b`（壊す側）を付けて呼ぶ（`W3-06/t`）。例外は作業のファイルの `marks` に書く。
  - 基盤: テストの役割を置かない（gate など、テストそのものを作る作業）。壊す側は置く。
  - テスト: テストの役割だけ（期待値を先に書く作業）。
  - テスト・壊す側: 期待値を作る作業で、その期待値を仕様と照らす壊す側を置く（参照評価器の W7-01）。
- **役割の担当。** 定義は `.claude/agents/` に置く。モデルと推論の努力は、定義の frontmatter で決まる。
  - 親: 進捗の監督とレビュー。作業票を埋め、各票の結果をレビューし、〔危険〕の差分を読み、`tools/builtin_names.toml`（直書きの許可リスト）と `tests/pending.toml` の増分を毎回読み（どちらも同じ差分で増やせるため）、決定と作業のファイルを揃え、作業 ID ごとにコミットする（`/b` と親のレビューが通った後。push はしない）。
    コミットと同じ回に、作業のファイルの `status` を `DONE` にする（`docs.py set W1-01 status=DONE`）。gate は、外す予定の作業が `DONE` の作業である実装待ちの項目を失敗にする（W1-01）。
  - 実装 `/i`（`onsa-impl`）。
  - テスト `/t`（`onsa-test`）と壊す側 `/b`（`onsa-break`）: 実装と別のモデルにして、見落としを重ねにくくする。
  - 助言（`onsa-advisor`）: 〔メモ〕の設計メモの審査、解決が難しい問題、エージェントの間で意見が割れたとき、仕様の空白の独立のレビューに頼む。
  - 空白の下書き（`onsa-gap`）: 下の「仕様の空白の流れ」の下書きを受け持つ。
  - 文書の点検と移行（`onsa-docs`）: 段の終わり、規則・仕様・担当の定義・README を改めた後（gate の `docs-due` が PARENT を出す。見る文書は `tools/docs.py` の `DUE_DOCS`）、移行の各段、親が求めたときに、親が範囲を決めて呼ぶ。同時に動かす担当の数に数える。
  - 同時に動かすエージェントの数と枠は、`rules/budgets.md` の「同時に動かす担当」（助言も数える）。同じファイルを触る作業は並べず、主のツリーを触るのは一度に一つにし、他は作業ツリーで行う。仕様の空白の流れの枠は、下書きの後に助言が同じ枠を順に使う。空白の流れが空のときは、その枠も W の票が使う。
  - 並べ方: テストだけの作業は、別の作業ツリー（Agent の `isolation: "worktree"`）で、主のツリーの実装の作業と並べる。テストの担当は `tests/pending.toml` の項目を編集せず、載せる項目を報告し、親が足す。親は作業ツリーの結果を主のツリーへ写し、作業ツリーを消す。実装の作業を作業ツリーで行ったときは、差分を 3-way で当てる（W1-07）。
- **印。**
  - 〔メモ〕: 設計メモを先に出し、親が読み、助言の担当が独立に審査してから実装する（R-06 の進め方）。
  - 〔危険〕: 降下・modes・C の生成・ターゲットの pass に触れる。親が差分を読む（Q-12）。
- **新しい構文のテスト。** テストの役割は最終の構文で書く。まだ通らないものは、gate の実装待ちの一覧 `tests/pending.toml` に S / R 番号と外す予定の作業 ID を添えて置く（Q-08。形はファイルの先頭のコメント）。置くのは親で、テストの役割は載せる項目を報告に並べる（上の「並べ方」）。実装した作業が、その一覧から外す。
  一覧にあるのに通るものは gate が失敗にする。gate の項目のうち後の段の決定を待つもの（公開ヘッダの C++ の検査など）も、同じ一覧に置く。
- **後の段で作り直す部分。** 後の段で作り直すコードは、先に直さない（二度手間を避ける、C-01）。そこで黙って誤るものは、その段まで E0200 で止める（Q-09）。ただし、E0200 にするとその段の間のテストを広く塞ぐとき（実行時の振る舞いの誤りなど）は、小さな直しを先に入れてよい（K-09。R-12、R-22）。
- **再現の入力。** R を直す作業は、`tests/review-phase1/` の再現の入力を期待値付きテストへ移し、README の対応を更新する（8.3 の 10）。
- **基盤の作業の設計メモ。** 後の作業がそのまま使う形（テストの形式、器、内部エラーの型など）を作る作業は、〔メモ〕の印が無くても、設計メモを先に出す。親が読んで決め、要点を記録する。
- **直しの確かめ。** 壊す側の指摘を直したら、新しい構造を足した直しは壊す側に再確認を頼む。それ以外は、親が壊す側の再現の入力で確かめる。
- **仕様の空白の流れ。** 利用者が W の票の作業中に判断できるよう、空白は見つけた都度、下書きと独立のレビューまで進めて渡す。作業は止めず、8.2 の 3 の保守的な扱いで進める。
  1. 見つけた担当が、8.4 の「空白の報告」の形で事実まで書く。テストの票は、期待値を書けない事例に保留の印を付けて他の事例を進める。
  2. 親が、受け取った回に `docs.py new S`（主のツリー）で登録し（期限の作業か段を `before`、見つけた票を `found_by`）、振り分ける。説明の誤りのように読みが一つのものは、親が直しの案を書いて「確認だけ」とし、下書きとレビューを通さない。設計の判断が要るものは、急ぎ（止める、次の作業の前、後の段）を付ける。決定を待つ作業は後に回し、依存の無い作業を先に進める。
     登録のときに、その空白の規則の族（仕様の同じ規則の文を一つ直せば決まる形の集まり。§2.5 の行頭の記号など）を頭の欄の `family` に書く。同じ族の未決の S があれば、その組に入れる。
  3. 下書きの担当（`onsa-gap`）が、まだ下書きしていない空白を、族ごとに一つの組として受け持つ（大きさの上限は「空白の下書きの束」、`rules/budgets.md`。超える族は分ける）。
     下書きは、族の全ての形（記号と位置の組み合わせ）を既決の S も含めて表にし、族の一般の規則を一つ案にする。個々の形はその規則から決め、例外だけを並べる。
     例（W3、2026-10-09〜10）: §2.5 の記号と空白の族。括弧の中の行頭の二項演算子（S-370）、腕の区切りの前の行頭の `|`・`-`（S-386）、非対称な空白の `a -b`（S-398）、前置の `+`（S-405）が別々の 4 つの組で決まり、後の決定が前の文を広げ直した。腕の本体の後の同じ行の形（S-423）は、決定の後に本文の抜けとして見つかった。
     一つの族なら、表は記号（`-`・`+`・`^`・`|`）と位置（行頭、非対称な空白、`=>` の前の同じ行、前置）の組になり、S-423 の形は表の空いた欄として初めから見える。
     「止める」の空白が出たときはすぐ、それ以外は空白の流れの枠が空いたときに始める。親は、今の実装のバイナリ（主のツリーのビルドの写し）と、試せる処理系の一覧を渡す。
  4. 親が下書きの要点を再現の入力で確かめ、推奨を伏せた版を作る。新しい助言の担当（`onsa-advisor`、組ごとに新しく立てる）に、伏せた版から原文と仕様で選ばせ、その後で推奨を見せて突き合わせさせる。親が助言の根拠を確かめる。
  5. 親が、確かめた組を下書き `decisions/S/S-<番号>.draft.md`（頭の欄 `group`・`drafted`。組の一覧は `docs.py list S --group <N>`、状態は S の `status`）に置き、会話で「一致した項目は確認だけ、割れた項目と新しい論点は判断を」という要約を出す。渡す単位は、「止める」の空白が 1 件、または 3 件たまったとき。利用者が下書きを vim で開いている間（スワップファイルがある間）は書かず、会話で知らせる。
  6. 利用者は、下書きの「回答:」の行か会話で答える。親は、W のコミットの区切りで、決定だけのコミットとして仕様と決定のファイル（`決定`・`経緯`、`docs.py set <ID> status=DECIDED decided=<日付>`）に反映し、`tools/gate.sh --quick` を回す（8.5 の「検査の回し方」）。
     決定の一覧と変更点は道具が出す（`docs.py list`・`changes`）。コードとテストの直し（保留の期待値、SPEC-GAP の印）は、決定の `tasks` の作業の作業票に入れる。
- **登録とコミットの区切り。** 作業の途中で見つけた R / S の登録は、それを見つけた作業のコミットに入れる。区切れないときは、記録だけの小さなコミットに分ける。
- **段の終わり。** 次の全てを満たしたら、次の段に進む。段の順と依存は、作業の `depends` と `tasks/stages.md` にある（W2 と W3 の並行は K-10）。
  1. gate が通り、実装待ちの一覧にその段の分が残っていない（`tools/gate.sh --stage-end W<n>`）。
  2. その段の R の再現の入力が、期待値付きテストに移っている。
  3. 壊す側の指摘に、重大度が高のものが残っていない。
  4. 仕様と、決定・R・作業のファイルを更新した（`docs.py check` が通る）。
  5. `docs-due` が見る文書を改めた後の文書の点検を取り込んだ（gate の `docs-due` が通る）。
