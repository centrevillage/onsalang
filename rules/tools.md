# 道具の作り方

道具（`tools/`）を作るか直す前と、ツール化の案を出す前に読む。

## 9. 道具の作り方（全員）

9.1 道具は、作業の種類ごとに一つにする（文書は `tools/docs.py`）。仕事ごとに下位の命令を置き、`COMMANDS` に登録する。
  種類をまたぐ共通の処理は `tools/repo.py`、自己テストは `tools/test_gate.py` に置く。既にある道具は、手を入れるときにこの形に合わせる。

9.2 道具にするか、どこまで縛るかは、「あるべき」より実作業の効率で決める。
  - 作業効率を悪化させない（例: シェルでの文書の編集は禁じない）。
  - 改善がわずかで手順が複雑になるものは採用しない。
  - 改善がわずかで実装量が多いものは採用しない。
  - 約束（書式、欄、目印の行）を道具で縛るのは、その約束を読む道具があるときだけにする。そのときは書く側も道具にし、読む側と同じ定義を使う。
    例: コミットの `Docs-Checked:` の行は `docs.py due` が読む。読む道具の無いコミットの分け方は縛らない。
  - 止める（拒む）のは、破ると実害があり、正しい操作をほとんど止めないものだけにする（例: `git stash`）。例外の手続きが要るものと、正しい操作を止めうるものは、知らせるだけにする。

9.3 規則には、どの時機にどの道具を使うかだけを書く。使い方（下位の命令、引数、例）は道具の help に置き、規則からは `<道具> help --role <役割>` を指す。

9.4 下位の命令ごとに、目的の一行・時機・役割・例を、`COMMANDS` の登録の横に日本語で書く（役割の名は `tools/repo.py` の一覧）。
  `<道具> help [--role <役割>] [<命令>]` がそれを出し、自己テストが、全ての命令に四つが揃い、役割の名が一覧にあることを確かめる。
