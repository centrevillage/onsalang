# 推奨の基準

空白の下書きと助言の担当が、推奨と独立の判断を出す前に読む。

## 7. 推奨の基準（gap、advisor）

推奨と独立の判断は、次の方針で比べる。親が作業票で足す方針があれば、それも使う。

7.1 規範は仕様。仕様は自己完結の規則で書き、他言語への言及は参考にとどめる。推奨の理由に「Rust（や他の言語）にあるから」を使わない。

7.2 他言語の扱いは、手元で動かしたものだけを書き、版を添える。rustc は確かめには使えるが、推奨の理由にしない。確かめていないものは「未確認」と書く。規格や文書を引くときは出典（節、URL）を付ける。

7.3 Onsa の主な書き手は LLM と想定する。人なら摩擦を嫌って緩い案に傾く場面でも、厳格な案を選ぶ。ただし、LLM のコーパスに少ない書き方であることだけを理由に、言語の規則の一貫性を崩さない（コーパスとの摩擦は代償として示すが、決め手にしない）。

7.4 既存言語の間で解釈が分かれる書き方は、コンパイルエラーにする（修正候補は読みごとに並べる）。どう読んでも意味が一つの余分（`return`、`-> ()`、冗長な括弧）は fmt で揃える。書き手の誤解を示す書き方や、読み手に別の読み方を与える書き方はエラーにし、note で正しい規則を示す。

7.5 将来開くかもしれない機能でも、今は禁止しておく方を選ぶ（制限を外す変更は後で壊れない）。ただし、境界とは別の条件を足して「特殊な規則が増える」案は不可。推奨では、後で緩められる制限か、規則の数が増えるかを比べて示す。

7.6 構造の変更は今のうちに行う。修正コストを理由に、理想の構造より軽い案を推さない（推すなら、コスト以外の利点を示す）。

7.7 推奨は、今後の追加（第 2 期の `Str`・`Map` などの API、JS / WASM のバックエンド）でどちらが管理しやすいかを比べて出す。今の量だけで比べない。制限を「今は当たる所が少ない」で小さく見積もらない。

7.8 実務の構成を塞がない（F32 主体で精度の要る所だけ F64、など）。検査は代わりの指標ではなく、実際の影響を見る。

7.9 表面の非一貫性を作らない（「`0 - x` が通って `-x` が誤り」のような食い違い）。区別するなら根拠を示す。名前の付いた概念を、能力の組み合わせより好む。

7.10 基本仕様には、言語の規則と、利用者・CI・修復ループが依存する出力（診断、終了コード、interface）を書く。fmt の正規形や人が見る表示の約束は `spec/tools.md` に書く。人が読まない規範の表は、データのファイルに置く。基本仕様に細かすぎる記述を入れない。

7.11 前提を問い直す: 穴を埋める前に、仕様の既存の規則そのものが妥当かを確かめる。同一性は構造で決め、名前は表示に使う。

7.12 必要と分かっていて、一緒に入れてもコストがほとんど変わらないものは、後回しにせず同じ回に入れる。必要が確かめられていないものは、`decisions/A/` の候補にとどめる。

7.13 段の原則（計画 D-15）: 各処理は一度だけ行い、後の段は前の段が出力した構造を受け取る。

7.14 表現（IR の構造、表の欄）は先に入れ、実装していない所は黙って通さず E0200 で知らせる（R-81）。

7.15 仕様の空白は、基本は保守的に実装して SPEC-GAP の印を付けて報告する。決めないと空白が連鎖するものだけ止める。

7.16 ある問題を避けるのに、無関係な名前や構造を変えるしかない設計は推さない。

7.17 一度に報告する誤りは、一つの編集の単位に一つ。誤りをまとめる案は、既にある原則の外に出ないかを確かめる。修正候補の約束は、当てた前後の状態だけで判定できる形にする（検証に因果を持ち込まない）。

7.18 約束（仕様に書く保証）は、それに頼る使い手（CI、修復ループ、テスト）を示せるものだけにする。

7.19 関係する既決の項目の理由を読み、新しい項目に当てたときにどの案になるかを確かめてから推奨する。既決の部分を論点に戻さない。

7.20 方針の字面を当てるだけでなく、効く場面が実際にあるかを確かめる（読みごとに候補を並べる方針でも、その形を正しい形として書く言語が無ければ読みは割れていない）。推奨では、案ごとに、形ごとの出力の違い・増える規則（既にある規則への例外を足す案かを確かめる）・実装の量・既決の出力への影響・効く書き手を並べる。推奨の前に、その形が現実の書き手にどの程度あり得るかと、案の副作用（正しい振る舞いを壊す形）を調べて示す。修正の量の割に利益が薄い案は推さない（S-351）。

7.21 名前は、略語であることが明らかなら短いものを選ぶ（`@mem`、`@repr`、`@param`）。将来の選択肢が増えそうなものは、分類の属性に値を渡す形にする（`@mem(bulk)`、`@repr(c)`）。属性の名前には主語（何に関わるか）を持たせ、利点（fast、opt）でなく、変わる意味の分類で名付ける（`@fp(relaxed)`、S-57）。

7.22 印は、キーワード（`fb y`）より、記号やプレースホルダとして読める簡潔なものを好む（`^y`、S-44）。既にある印の意味を広げて使う形も好む（`if~`・`match~`、S-110）。既に付いている印に別の印を重ねさせない（R-94）。既定の名前は安全な意味に当てる（`Num` は符号なしを含まず、符号なしも受けるときだけ `AnyNum`）。推奨では、ある組み合わせが頻出しないかを用途ごとに見積もって示す。

7.23 キーワードを必要以上に増やさない。将来の機能の形は、既存のキーワードの入れ子や組み合わせで表せるかを先に検討する（テストのまとまりは `test` の入れ子、S-275）。足すなら一語で、命令でなく条件に読める語にする（`reset_if`）。後から足すと既存のプログラムを壊すもの（キーワード、prelude の名前、flow の組込み名）は、実装しない機能でも予約と意味を先に決める。

7.24 今は実装しない機能でも、そのときに構文や意味が破綻しない形を選ぶ。注釈（`at`）と、方法の選択を伴う処理（補間）を同じ構文に混ぜない（C-40）。組込みの型で済む今だけでなく、将来その構文に使える型を広げたときに書けなくなる形が無いかを確かめる（`b + 1` が必ず作れると仮定しない、S-257）。

7.25 処理系の資源の上限（呼び出しの深さなど）は、仕様に固定の数を書き、同じ性質のもので一つの数を共有する。値は一般的なコンパイラの上限を超えないものにし、主な処理系の既定値を手元で確かめて並べる。迷えば小さい値を選ぶ（後で上げても既存のプログラムを壊さない。S-222）。

7.26 書き方を一つにする原則（P2）に触れそうな機能は、残す前に、具体的な利点（代わりの手段が無い用途）と、害になる使い方を示す（R-105）。

7.27 修正候補の規則を推すときは、複数の誤りが並ぶ形で一つずつ当てたときに誤りの無いコードへ収束するかと、どの候補でも安全にできない形を先に示す。安全にできなければ、情報を失っても壊さない候補（削除）に落とす（S-302）。
    確かめは `onsa_cases --fix-loop FILE` で、`--pick first` と `--pick last` の両方を回す（候補が複数ある形は `--branches` も）。止まり方（`clean`、`no-candidate`、`cycle`、`limit`、`diverge` など）と道筋が出る。

7.28 規則を決めるときは、32 の一覧の中で同じ性質を持つ言語（改行で文が終わる JavaScript・TypeScript・Python・Swift、末尾の式で `return` を省ける Rust・Swift など）が同じ問題をどう扱うかを調べ、手元で動かせるものは動かす（C-12）。

7.29 列挙子は整数との変換（保存したデータ、C の API）で順に意味を持つのが慣習で、順を使わない設計は `match` を増やす（C-22）。性質の種類が違うものは別の概念として定めるが、利用側が区別を意識する利益が薄ければ記法は分けない（C-28）。

7.30 組込みの API は仕様の閉じた一覧だけを実装する。必要と分かったものは拒否で終わらせず、`decisions/A/` に候補として挙げる（実例のコードと、無い場合の書き方を添える）。

7.31 少数の言語だけが持つ特殊な規則（MATLAB や Julia の、空白で行ベクトルの要素を区切る書き方など）に合わせるかは、その言語を使う人の数ではなく、合わせるための実装の量と、他の規則への副作用（特殊な規則が増えるか）で決める。厳しい方（誤りにする）から後で緩めても、既存のプログラムは壊れない。迷えば厳しい方を採り、実装が単純な方を選ぶ（S-398・S-400）。

7.32 既存言語の書き方を診断の対象にする言語は、次の一覧に限る: C 系（C、C++、Java、C#）、JavaScript と TypeScript、Python、Rust、Swift。一覧に無い言語だけの書き方には、新しく行（`spec/foreign-forms.toml`）を立てず、一般の規則のコードで報告する。
    読みが言語で割れるかの判断と、仕様の空白の下書きの他言語の調べも、この一覧の言語で行う。既に実装した行は戻さない（旧版と FAUST は下のとおり）。一覧は少なく始め、利用側の書き手（エージェント）が実際に混乱すると分かってから足す（Go、MATLAB、Julia は今は入れない。MATLAB と Julia は考え方が違いすぎて混同しにくい）。
    Onsa の旧版の書き方は、正式なリリースまで対象にしない（リリースの前に旧版で書く利用者はいない）。リリースの後に一覧に足す。既に入れた旧版の行の整理は RF-11。
    FAUST は文法の形を対象にしない。記号に C 系と違う意味を持たせる文法で、読みが他の言語や Onsa の記号（`'`、`~`、`@`、`:`、`_`）とぶつかって管理の費用が大きい一方、Onsa の表面の文法とは似ず、混同する書き手は少ないため。flow などの言語の機能を FAUST の機能と比べることは続ける。FAUST からの移植の助けは、構文の検査でなく仕様などの文書が受け持つ。
    既に入れた FAUST の行は、支障が無い限り残し、対象外であることをコメントで示す。新しい決定とぶつかる、gate を落とす、直しが要る、のどれかになったら、直さずに事例と仕様の一覧の行ごと消す。

7.33 既存言語の書き方の修正候補で名前を写すのは、同じ概念の綴りの違い（`i32` → `I32`）までにする。相手の言語の意味の近似（`Debug` → `Show`）には踏み込まない。外す・写すの根拠は Onsa の規則に置く（S-463）。

7.34 型だけで成り立たないと決まる誤りは検査のエラーにし、値で決まる誤りは実行時の検出にする（符号なしの `-u` は E0401、`a - b` の下回りは panic。R-94）。

7.35 公開の ABI に当たる名前（C の関数名の prefix など）は、決める場所で明示させ、既定の値を置かない（R-121）。

7.36 公開の API（生成する API、C の API）は、利用者に使わない値を作らせて渡させない形を選ぶ。関数の引数と型は flow のシグネチャにある入出力だけにし、flow を調べるための表とマクロは全ての flow に置く。内部の表現（中間表現の形）は約束に含めない（7.18、S-570、S-112）。
