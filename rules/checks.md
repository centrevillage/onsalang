# 検査の回し方

担当の全員が、検査（gate、テスト、ファズ、自作の掃引）を回す前に読む。

## 4. 検査の回し方（全員）

gate の各項目は全てのコアを使い、1 回に数分かかる。検証は機械の寿命を縮め、時間を延ばすので、回す回数と並列の数を抑える。
親が決めること（作業票に until の項目を足す、gate を回し直すか）は、`rules/process.md` 8.5 の「検査の回し方」にある。

| 役割 | 作業の途中 | 報告の前 | 回さないもの |
|---|---|---|---|
| t | 書いた事例だけを絞って確かめる（下の「事例を絞って走らせる」、データのファイルの自己テスト `cargo test -p onsa_tests --test foreign_forms`、変えたファイルへの `onsa check` と `onsa fmt --check`）。載せる項目は仮に実装待ちの一覧に入れて回し、回した後は元に戻す | gate は回さない（親が成果を写した後と、実装の担当の報告の前に回る）。絞った確かめの結果を報告に付ける | fuzz（`tools/fuzz.py`）、fmt の性質（`tools/fmt_props.py`）、C の検査とテストベクトル（`onsa_cases --c`、`--vectors`）は、作業がその道具か生成した C を扱うときだけ |
| i | 変えた所に関わるテストだけを絞って回す（`cargo test -p <crate> <テストの名前>`、変えたファイルへの `onsa check`）。広く確かめたいときは `tools/gate.sh --quick` | 作業の検査を一度、`tools/gate.sh --work <作業 ID>`。要約を報告に付ける。直しの往復では、落ちた項目だけを `--only <項目> --work <作業 ID>` で回し、最後の直しがコードに触れたら、報告の前に作業の検査をもう一度回す | fuzz と fmt の性質の全体の回（作業の検査が差分に合わせて絞って回す）。C の検査とテストベクトル（`onsa_cases --c`、`--vectors`）は、作業がその道具か生成した C を扱うときだけ |
| b | 個々の入力へのコマンドと、絞ったテスト。自作の掃引は、見当を付けた後に `rules/process.md` 8.5 の「壊す側」の予算の内で | — | gate（実装の担当が回し、親が要約を読む）。fuzz・fmt の性質・C の検査は、作業票がそれを対象にするときだけ |
| advisor、gap | 個々の入力へのコマンドだけ | — | gate、`cargo test --workspace`、fuzz、fmt の性質、C の検査。自分でビルドしない（親が渡すバイナリを使う） |

4.1 gate は機械で一度に一つだけ走り、他の gate の後ろで待つことがある。Bash の timeout は 600000 にし、待っている間に打ち切られたら回し直す。

4.2 fuzz の `--deep`（数千段の入れ子の変異体）は、どの役割も回さない。

4.3 作業の検査は、fuzz と fmt の性質を、差分に関わる種と一部の抜き取りで回す（差分がその道具に触れたときは全体）。gate-selftest は差分が `tools/` に触れたときだけ回る。時間が目安を超えると、最後の行の前に `warning:` の行が出る。判定は落とさないが、報告に書く。

4.4 作業の検査の fuzz は、新しい修正候補の類を基のバイナリ（dev のビルドの写し）でも回し、基でも出るものは `pre-existing` の行に並べて判定を落とさない。それらは報告に並べる。落ちた類（差分で入ったもの、内部エラー・異常終了・時間切れ）は、実害の見立て（実際の書き手が書きうる形か、候補が新しい誤りを作るのか、隠れていた誤りが見えるだけか）を報告に書く。直すかは親が決める。

4.5 担当の作業ツリーで書いた SPEC-GAP の印が表に無い番号か `NEW` のときは、gap-marks が `PARENT` と出し、判定を落とさない。その行を報告に並べる（登録は親）。

4.6 gate の出力の FAIL の行は、実装待ちの項目の中身のことがある。判定は最後の行で見る。作業の判定になるのは `gate: PASS` / `gate: FAIL` だけで、`gate (quick): …`・`gate (only): …`・`gate (sweep k/K): …` は一部を回した結果である。

4.7 事例を絞って走らせる: 事例の器 `onsa_cases --run <根>` の引数は `tests/` を持つ根のディレクトリで、ファイルは受けない。一つの事例だけを走らせるには、作業用のディレクトリ（scratchpad の自分の下）に `tests/<元の経路>` の形で事例と `.fixK` を写し、そのディレクトリを根に渡す。結果は JSON の `cases[].problems`。
  `tools/run_cases.py --work <作業用のディレクトリ> <tests/ の下の経路>...` がこの写しと実行を行う。
