## 指摘(重大度の高い順)

### 1. 【高・仕様ずれ】内側の関数型の `uses {}` を落とすと、外側の `uses {…}` が内側に付き替わり、意味が変わる。§3.5 も `diff --ast` も気付かない
- 再現: `P28/w312u1b/t/h1.onsa` の最初の事例。
  ```
  fn make() -> fn() -> I32 uses {} uses {Alloc} {
    fn() -> I32 { 1 }
  }
  fn take(f: fn() -> I32) -> I32 { f() }
  fn go() -> I32 uses {Alloc} { take(make()) }
  ```
- 今の出力: `fmt` は終了コード 0 で `-> fn() -> I32 uses {Alloc} {` に書き換える。
  - `check` の結果は、元が通るのに、出力は `take(make())` で E0401。
  - `diff --ast 元 出力` も終了コード 0。
  - `P28/w312u1b/w/g1.onsa` と `g2.onsa`(`uses {} uses {Alloc}` と `uses {Alloc}`)でも `diff --ast` は 0、`check` の型の表示は違う(`expected fn()` と `expected fn() uses {Alloc}`)。
- 期待: 書き換えない。または `-> (fn() -> I32) uses {Alloc}` のように括弧で囲んで意味を保つ。
- 根拠:
  - 仕様 §18.2(意味を変えない)と、§8.1/§11.4 の「`uses` は近い方の返り値の型に付く」(§11.4 の at の段落の「`uses` と同じく近い方」)。
  - 内側を純粋に、外側に `Alloc` を付ける書き方は、この二重の `uses` しか無い。
  - 型の別名(`type Maker = fn() -> fn() -> I32 uses {} uses {Alloc}`)、無名関数(`fn() -> fn() -> I32 uses {} uses {Alloc} {…}`)、trait のメンバでも同じ構造。
- 原因は二つが重なること。
  - ① `empty_uses`(`rewrites.rs`)が、後ろに別の `uses` が続くかを見ない。
  - ② AST のダンプ(`dump.rs` の `fn_decl` と `TypeKind::Fn`)が、`uses` が関数のものか内側の型のものかを区別せずに同じ文字列を出す。そのため §3.5 の比べが盲目になる(これまでは `uses {}` を fmt が動かさなかったので表に出なかった)。
- 直しの方向は、`empty_uses` が「落とすと後ろの `uses` が付き替わる」形(次のトークンが `uses`)を残すこと。二つ目の `uses` の有無を見る。
- 方法: 手で組んだ入力を `cases.py -v` に流し、`check` の診断コードの前後を比べた。gate の外。
- 追加の気付き: §3.5 の比べがダンプの文字列に頼る限り、`uses`/`at` を落とす書き換えは同じ盲目を持つ。

### 2. 【高・契約】fmt が冪等でない(2 回かけると変わる): 書き換えの順序依存
- 再現: `P28/w312u1b/w/d1.onsa`、`w/d2.onsa`。
  - `type T = fn(F32) -> () // c` 改行 `  uses {}` を 1 回目で `type T = fn(F32) -> () // c` にする(`uses {}` と改行が落ちる)。2 回目は `type T = fn(F32) // c`。
  - 同型: `type T = fn(F32) -> // c` 改行 `  () uses {}`(1 回目 `-> // c` 改行 `()`、2 回目 `fn(F32) // c`)。
  - trait のメンバ、struct のフィールド、effect の操作でも同じ(`mut.py` で 8 件ずつ、`ftype`、`trait`、`effect ops`、`type alias nested`)。
- 期待: 1 回目で不動点(§18.2「二度かけても同じ」)。
- 原因: `choose` は `REWRITES` の順に節を回る。`unit_ret` は、後の `empty_uses` がその先の `uses {}` を落とすことを知らずに、コメントが守る改行のために `-> ()` を残す。`empty_uses` が `uses {}` を落とした後、`-> ()` が末尾で単独になり、2 回目で外れる。
- 方法: `mut.py`(下記)の変異で B(`fmt --check` を出力に)が出た。gate の `fmt-props` の対象の入力では当たらなかった。
- 参照: 連絡のあった S-536 (1) の判定でも、`-> ()` の範囲の外にコメントがあるこの形(コメントは `()` と `uses` の間)で順序依存が残りうる。(1) の「範囲」を書き換えごとに取るなら、同じ頭の中の他の書き換えが落とすトークンも範囲に入れる(まとめて一つの頭の書き換えとして判定する)必要がある。

### 3. 【中・仕様ずれ】無名関数の `-> ()` と `uses {}` を落とすと、エラーが消える(意味が変わる)
- 仕様の文: §6.1「無名関数は…返り値の型は本体から決まる」(期待型が分かる位置)、§8.1「無名関数は、期待する関数型の効果行…に照らして本体を検査する」。
- `check_closure`(`crates/onsa_sema/src/body/expressions.rs:553`)は、`ret = None` なら期待型の返り値(なければ新しい型変数)を使い、`ret = Some(())` なら明示の `()`。`effects` も `None` なら期待型の効果行、`Some(空)` なら純粋と宣言する。名前付き関数の `ret = None` は常に `()` なので、無名関数だけ「省略」と「`-> ()`」が同じではない。
- 再現(`P28/w312u1b/w/c1.onsa`、`w/c2.onsa`、`t/a3.onsa`):
  - `take(fn(x: I32) -> () { x })`(`take` の引数は `fn(I32) -> I32`)は `check` が E0401(`expected ()`)。fmt の出力 `take(fn(x: I32) { x })` は `check` を通る。
  - `let a: fn(I32) -> I32 uses {Alloc} = fn(x: I32) -> I32 uses {} { x }` は E0401。出力 `fn(x: I32) -> I32 { x }` は通る。
- 影響: 通らないプログラムが fmt で通るようになる(S-545 と同じ種類。ただし有効なプログラムが別の有効なプログラムになる例は見つからなかった)。
- 選択肢: (1) 無名関数の `-> ()`/`uses {}` は期待型が決まる位置でだけ落とす(構文だけでは決まらない)。(2) 無名関数では落とさない。(3) 今のまま(S-540 で決定済み)で、エラーが消えることを仕様に書く。
