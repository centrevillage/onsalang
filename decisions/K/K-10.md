# K-10 W2 と W3 の並行と、重なる作業

- 論点: W2 と W3 はどちらも W1 だけを前提にするが、同じ所を触る作業がある（W2 の字句解析の UTF-8 と W3 の字句、W2 の字面から値への変換と W3 の数値リテラルの規則と綴り）。W2 の E0311 / E0312 は `sig.rs` に入るが、`sig.rs` は W4 で段に分ける。一方、スタックの溢れは `catch_unwind` で捕まらずプロセスごと落ちるので、閉路の検出を遅らせすぎると、落ちる入力が長く残る。
- 案: R-01 と R-20 / R-45 を W3 へ移す（W3-04、W3-05）。W2 は W3 と並行で進め、W4 の前提を W2 と W3 にする。宣言どうしの閉路（型の E0311、定数の名前による E0312）は W4-05（署名の段）で検出する。関数を経由する定数の閉路は W9-03 で扱い、仕様の空白として S-173 に登録する。それまで落ちる入力はファズの実装待ちの一覧に置く。
- 決定: 案のとおり（2026-10-07）。レビューは E0312 を W9-03 へ移す案だったが、定数どうしの閉路で落ちる状態が 7 段の間残るので、名前による閉路は W4-05 に置いた。反映のときに、自分をインスタンスにする flow の E0817 も、同じ理由（宣言どうしの閉路で、まだ実装が無く、落ちるとスタックが溢れる）で W2 から W4-05 へ移した。
- 追記（2026-10-07、W1-11 の設計メモで分かった）: W2-08 の依存に W3-10 を足した。W2-08 のテストの票は最終の構文で書くので、その事例は flow の新しい構文が今の sema へ写る W3-10 まで、事例全体で実装待ちになり、W2-08 の直しを手順の器（W1-11）でも壊す側でも確かめられないため。
  古い構文でテストを書く案（`rules/process.md` 8.6 の「新しい構文のテスト」に反し、W3 で書き直しになる）と、先に直して W3-10 の後に確かめる案は退けた。W2 のうち flow の実行時の振る舞いを直すのは W2-08 だけなので、遅れるのはこの作業だけである。
