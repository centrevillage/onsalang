# Q-02 Core を通らない参照を、二つ持つ

- スカラの意味の参照:
  - 仕様 §3.4 は「Rust と同じ」なので、Rust そのものを参照にする。
  - 整数・浮動小数・変換・検査付き演算の式をランダムに作り、Onsa のインタプリタ、C、同じ式の Rust プログラムで評価して比べる。
  - R-04、R-10、R-11、R-19 の種類が対象になる。
- flow の意味の参照:
  - AST から直接、1 サンプルずつ評価する小さな参照評価器を `onsa_tests` に置く。§11 の文言をそのまま書き、数百行に収める。
  - Core を経たインタプリタと C の `render` を、これと比べる。
  - R-13、R-14、R-16、R-22 の種類が対象になる。
- 費用: 中。参照評価器は速さを求めないので、単純に書ける。
- 推奨: 採る。原因 c への唯一の直接の対策。
- 決定: 採る。ただし (a) は改めた: 参照は特定の言語の処理系ではなく、仕様から作るテストベクトル（演算・型・入力・期待する結果か panic の表）をデータとしてリポジトリに置く。ベクトルは仕様の規則から参照モデルで生成し、生成するときだけ独立した実装（Rust、C、Berkeley TestFloat のような既存の生成器）と突き合わせる（規範にはしない）。
  テストは各変換先をベクトルと比べる。コンパイラを別の言語で書き直しても使え、作り直すのは仕様の規則を変えたときだけ（差分は親が仕様と照らして承認）。利用者の指摘: 「Rust と同じ」は Rust の版に影響され、実装の言語を変えるときに特定の言語の環境を基準に残すのは危うい。仕様の側の自己完結は R-133 で決める。
  (b) の flow の参照評価器（AST から直接）は第 4 段の構造の変更の前に作り、決まった事例の期待する出力はデータとして残す。生成したプログラム（Q-03）との比較だけ実行時に動かす
