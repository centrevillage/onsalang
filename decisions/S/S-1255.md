# S-1255 細部: 改行の後の行頭の `/`（導くクロックの続き）を置く所（struct のフィールド・flow の入力・top level の `const`・本体の `let`）ごとに違う報告と候補を揃えるか（仮は今のまま、R-524）

- 空白: クロックの次の行が行頭の `/ 4` のとき（R-524）、struct のフィールドの括弧の中は「remove the clock」の候補が次の行の `/ 4` まで消して一段で通り、flow の入力は候補の無い E0002（比の note 付き）、top level の `const` は E0020 の後に E0002、本体の `let` は改行の E0002 になる。
  §2.5 は「記号の置き場所の規則（二項演算子…は行末）は、括弧の中でも外と同じ」とする。どれも誤りが二つのプログラムで、候補の約束（S-236）の外、当て続ければ止まる。
  案: (a) 今のまま。(b) struct の括弧の中でも行頭の `/`・`*` をクロックへ続けて読まない（`parser/types.rs` の `bare_ratio` の一行。struct の形は E0020 の後に候補の無い E0002 が残って止まり、一段で通らなくなる。flow の入力の E0002 は一般の文面になる。四つの終わり方は揃わない）。
  (c) クロックの後の行頭の `/`・`*` を「行頭の演算子」の E0002 にまとめる（`foreign/lines.rs` の `leading_binary`、約 +8 行。flow の入力・本体の `let`・flow の出力の文面が揃う。R-509 の (2) の形で、隠れた二つ目の診断の文面が変わる）。
  揃わない元は、木の上のクロックの E0020 が位置の順で先に出るかと、`let` の読みの失敗が E0020 を隠すこと（S-1253 と同じ仕組み）。
  試した (b) と (c) のパッチは `target/notes/188/w717/l2/r524_tried.patch`・`target/notes/188/w717/l2/r524/lines_optionA.rs`。
  仮の扱い: (a)。通るプログラムは変わらない。W7 の区切りで確認だけ（案を示す）。
- 決定: 決定（2026-11-26、利用者。189 回目、W7 の区切りの確認だけ。「(A)と(B1)はS-1148以外OKです」）: 仮の扱いのとおり。今のまま。違いは位置の順と型の位置のクロックの E0020 という一般の規則の帰結で、R-524 は理由を付けて閉じる。
  突き合わせ: 助言の担当が固定のバイナリ `onsa-d02ddee` で再現し、仮の扱いが今の挙動と合い、既決とぶつからないことを確かめた（`target/notes/189/reports/onsa-advisor-a4f41d23ad112f9fe-001.md`）。
- 経緯: 188 回目（2026-11-26）、W7-17 L2 の読むだけの設計（onsa-impl）が範囲の外で見つけ（R-524）、L2/i（onsa-impl）が (b) を試して、struct の形の候補が一段で通らなくなる後退と、四つが揃わないことを報告した。親は (b) を採らず、揃え方の選択を細部にした（利用者の方針「『約束の外』を後回しの理由にしない」により、R-524 は閉じない）。
