  - 論点 2 名前（(i)・(ii) のとき）。
    - (n1) `CStr`（利用者の仮の名前）。C と Rust の `CStr` は NUL で終わる文字列（Rust の `core::ffi::CStr`、`c"ab"` は NUL を含む 3 バイト）で、長さを持つ型と意味が違う。
      費用の要因: C の `const char*` を取る関数に渡すと、NUL を探して長さの外を読む書き手の誤解を招きうる（検査を通るのに意味が違う名前、§0.3 の 4）。§14 で本物の C の文字列の型が要るときに、名前が空いていない。
    - (n2) `FixedStr`。§4.1 の「固定長配列」と同じ語で、容量が決まっていることを示す。費用の要因: 「長さが固定」とも読め、使った長さが変わることは名前から分からない。
    - (n3) `InlineStr`。値の中に中身を持つことを示す。費用の要因: Onsa の他の名前に「inline」の語が無く、新しい語になる。
    - (n4) `AsciiStr`。文字の範囲を示す。費用の要因: 論点 4 で後に UTF-8 へ広げると名前が合わなくなる。
    - 他の候補: `Text`（費用の要因: 語が広すぎる、§0.3 の 5）、`ArrayStr`（Onsa の `Array[T]` はヒープの列で、取り違えうる）、`StrBuf`（`Buf[T]` は Affine のヒープで、取り違えうる）。
  - 論点 3 容量の書き方（(i)・(ii) のとき）。
    - (k1) const の型の引数 `CStr[N]`（`N` はバイト、定数式、§4.5）。`Ring[T, N]`・`Spsc[T, N]` と同じ形で、`fn f[const N: U32](t: CStr[N])` と書ける（今の実装で `Text[N]` が通る）。値の大きさは `N + 4` バイト（長さは `U32`、§4.1）、整列 4。
      費用の要因: 容量の違う値は違う型で、`CStr[8]` を `CStr[16]` へ入れるには書き写す（`push_str!`）。
    - (k2) 一つの固定の大きさ（例えば 32 か 64 バイト）。型は一つで済む。費用の要因: 組込みの RAM で短い名前ごとに大きさを払い、長い行（ログ）には足りない。数の選び方に根拠が無い。
    - (k3) いくつかの固定の大きさ（`CStr16`・`CStr32`・`CStr64`）。費用の要因: 型の数が増え、総称の関数を書けない。

  - 論点 4 文字の範囲と単位。
    - (c1) ASCII（0x00〜0x7F、制御文字と NUL を含む）。長さと容量はバイトで、文字の数と同じ。全ての値は正しい UTF-8 でもあるので、`Str` へは検証無しに変換できる。
      費用の要因: 日本語や記号（`°`、`µ`）を書けない。機器の独自の文字表（文字の LCD のカナなど）は、文字列でなく `[U8; N]` で扱う。
    - (c1') 印字できる ASCII（0x20〜0x7E）と `\n`・`\t`。費用の要因: 範囲の規則が ASCII の外に一つ増える。制御の列を送る機器（端末の色）で書けない。
    - (c2) UTF-8（検証する）。長さと容量はバイト。費用の要因: 切り詰めを文字の境界で行う規則が要り、表示の桁の数とバイトの数がずれる（利用者の指摘）。
    - (c3) 検証しないバイト。費用の要因: `Str` への変換に検証が要り、後で ASCII か UTF-8 に絞ると通っていたプログラムが壊れる。
    - 後で広げるとき: (c1) から (c2) へは、通っていたプログラムの値が全て正しい UTF-8 なので壊れない（長さはバイトのまま）。(c2)・(c3) から狭めると壊れる。
  - 論点 5 容量を超えたとき（リテラルが容量を超える・範囲の外の文字を含むときは、どの案でもコンパイルの誤り。論点 8）。
    - (t1) 黙って切り詰める（C の `snprintf`、C++ の `std::format_to_n`）。費用の要因: 失った文字が分からない。
    - (t2) 入る分だけ書き、全て入ったかを `Bool` で返す（Zig の `bufPrint` は書いた上で `error.NoSpaceLeft`）。式の文の値は `()` でなければ E0418（§6.1）なので、書き手は `let _ = t.push_str!(…)` で切り詰めを認めるか、値を見る。費用の要因: 書き足すたびに `let _ =` か判定が要る。
    - (t3) 何も書かずに `Result` か `Bool` を返す（heapless の `push_str`）。費用の要因: 表示の行を桁で切る用途（例 2）では、切り詰めを手で書く。
    - (t4) panic（arrayvec の `push`）。rt の関数でも panic は書ける（§9.2）が、export した flow の `process` では無音と poisoned になる。費用の要因: ログの一行が長いだけで音が止まる。
    - (t5) panic する操作と、`Result` を返す操作の二つ（arrayvec の `push` と `try_push`）。費用の要因: 同じ書き足しに二つの書き方があり、操作の数が倍になる。
  - 論点 6 ヒープを使わずに中身を作る方法（(i)〜(iii) のとき）。
    - (f1) 整数の 10 進（全ての整数の型。`push_int![T: Int](n: T)` の形）。std の Onsa で約 30 行。費用の要因: 桁の詰め（`007`）・16 進・符号の書き方は入らず、要れば操作が増える。
    - (f2) 浮動小数を小数点以下の桁の数を決めて書く（`push_fixed!(v, 2)` で `0.50`）。値は「`F64` で `10^d` 倍し、最近接偶数で整数に丸め、10 進で書いて小数点を入れる」のように式で定め、§13.4 の `strict` の演算でどの後端でも同じ文字になる。NaN・無限大・桁の上限は std の作業で決める。std の Onsa で約 40〜60 行。
      費用の要因: C の `printf` の `%.2f`（2 進の値を正しく丸める）と、`10^d` 倍で丸めが二度起きる値でずれうる。
    - (f3) `Show` と同じ文字（§6.3、浮動小数は読み戻せる最短の表記）。費用の要因: 最短の表記の算法（Ryu などで数百行）が要り、`Show` の操作の形が仕様に書かれていない（新しい S の候補 1）。
    - (f4) 補間を固定長の文字列に書く（期待の型が固定長の文字列なら、`"gain={g}"` を `Alloc` 無しに作る）。費用の要因: 補間で書式の指定ができないので `0.50` は書けない（§2.4）。容量を超えたときの切り詰めか panic がリテラルの中に隠れる（補間を名前の経路に限った理由と同じ所）。一つの構文が期待の型で作り方（ヒープか固定の領域か）を選ぶ。
    - 文字や他の文字列の追加: `push_str!`（リテラルか同じ型の値）と、`Char` を一字足す操作（範囲の外の `Char` は論点 5 の扱い）。`Char` と整数の変換は §3.3 に無い（新しい S の候補 2）。
  - 論点 7 出力の側。
