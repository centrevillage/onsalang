# S-571 境界のイベントの出力: 列の大きさと受け取り方

- 決定済みで戻さないもの: 組の全体は S-570 の下書きの頭（第 33・34 組で決めた §19.1 の三つの項、S-565 の R12、§14.2 の C の API の原則）。
- 論点: §11.6「出力: 単一の値なら `inout output: Span[T]`…」、§14.2「0 以外なら出力は全て 0」。どちらにもイベントの出力が無い。§19.1「第 35 組で決めること: … 出力の列の大きさ。出力の数は入力のイベントの数と `.up~` の倍率にも依るので、フレームの数に固定しない」。
  - 決定済み（S-564、S-567 の E3）: 一つの刻みに一つまで、位置は出した刻みの位置、同じ位置は刻みの順、struct の出力にイベントを含めない。帰結: イベントを出す flow の出力はそれ一つで、`sample` の出力のバッファを持たない。フレームごとの置き場所（`Option` を一つずつ）は、同じ位置の複数の出力を持てず、フレームの数に固定するので案に並べない。
  - (1) 受け取る形と位置の表し方。(2) 容量を超えるときの扱いと、要る容量を書き手が知る方法。(3) `process` が 0 以外を返したときの出力のイベント。
- 今の実装: `-> Done at event` は E0302（`q08`）。`-> F32 at block` は E0810「the output of a flow is at the clock `sample` in this version」（`q07`）。
- 案: 例の flow は `pub flow det(x: F32 at sample) -> E at event`（`E` は境界に出せる型、S-572）。
  - (1a) 呼び出し側が容量を持つ列。
    C: `typedef struct { uint32_t pos; <E の C の型> value; } pz_det_out_event;` と `typedef struct { pz_det_out_event* data; uint32_t cap; uint32_t len; } pz_det_events_out;`。`output` はそれへのポインタで、`process` が `len` を書く。
    Onsa: `inout output: Span[(U32, E)]`（長さが容量）で、出した数を返す（`-> U32`）か、`inout` の数の欄に書く。
  - (1b) ホストの関数に一つずつ渡す（CLAP の `try_push`、AU の `AUMIDIOutputEventBlock`）。費用の要因: Onsa の `process` には同じ形が無い（捕捉は読み取り専用、§5.3）。関数が偽を返したときの扱いが (2) と別に要る。
  - (k1) 静的な上限。コンパイラが出力のクロックから係数 A を決め、ヘッダのマクロ `<P>_OUT_EVENTS_PER_FRAME` にする。上限は `A × frames + （その呼び出しの入力のイベントの数）`。
    `process` は呼び出しの最初に容量と上限を比べ、足りなければ C は 2（状態を進めず、出力のイベントは 0 個）、Onsa は panic（poisoned）。
    A の根拠: 一つの出力は一つのクロックを持つ。周期のクロックなら 1 フレームに `.up~` の倍率の積まで（`sample / N` は 1 まで）、入力のイベントのクロックから来るなら、その入力の数まで（`.up~` の中の `at event` の入力もイベントごとに一回）。後者では A は 0 である。
  - (k2) 容量まで書き、出した数を `len` に書く（容量を超えた分は捨て、`len` が `cap` より大きいことで分かる）。返り値は 0 か、新しいコード 3。費用の要因: 捨てたことを見るのはホストの責務で、見なければ黙って失う。静的な解析は要らない。
  - (k3) (k1) のマクロを大きさの目安として出し、振る舞いは (k2)（最初の比べをしない）。
  - (3a) 0 以外を返した呼び出しは `len = 0`（音声を 0 で埋めるのと同じ）。`process` の途中の panic でも、その呼び出しで出したイベントは捨てる。(3b) panic の前に出したイベントは残す。
- 他言語:
  - CLAP（`events.h`）: `try_push` は「returns false if the event could not be pushed to the queue (out of memory?)」。「The plugin must insert events in sample sorted order when inserting events」。
  - VST3: `ProcessData::outputEvents` はホストの `IEventList` で、`addEvent` で足す。
    AU: `AUMIDIOutputEventBlock` は `eventSampleTime` を付けてイベントごとに呼ぶ。
  - LV2（`atom.lv2/atom.meta.ttl`）: 「Output ports with a variably sized type MUST be initialised by the host before every run() to an atom:Chunk with size set to the available space.」
  - Cmajor: `iterateOutputEvents` の関数は `frameOffset` を受ける（`cmaj_Performer.h`）。`processor.eventBufferSize` は「The maximum number of events that can be buffered per block」で、超えたときの扱いは文書に無い（Language Reference）。
- 推奨と理由: (1a)、(k1)、(3a)。確度: 中。
  - (1a): Onsa と C で同じ形になり、WASM の線形メモリでも同じ配列で書ける。要るメモリが呼び出しの前に決まる（P6）。(1b) は Onsa の形が無い。
  - (k1): 状態を進める前に一度だけ比べる形は、`Span` の長さの比べと同じで、返り値の 0・1・2 を変えない。イベントを黙って失わない。
    上限はフレームの数と入力の数とともに小さくなるので、容量の足りないホストは呼び出しを分ければ収まり、分けても出力は同じ（S-570 の区切り。一つの位置に容量を超える入力のイベントが並ぶときだけは、S-570 の (2b) が無いと分けられない）。(k2) は捨てたことを型に現れない約束でホストに任せる。費用は、クロックの解析（W7-02）が既に決める出力のクロックから A を数えることだけである。
  - (3a): §14.2 の「0 以外なら出力は全て 0」と同じ読みになる。
  - 決定性と区切り: 位置は呼び出しの頭からの相対で、同じ位置は刻みの順なので、分けた呼び出しの出力をつなぐと、分けない呼び出しの出力と同じ列になる。
  - あわせて決めること（`frames`）: `sample` の入力が無くイベントを出す flow（MIDI のエフェクト）では、Onsa の `process` の長さが `Span` から決まらないので、`frames: U32` を取る（`render` と同じ）。
  - あわせて決めること（`process_inplace`）: イベントを出す flow には生成しない（`sample` の入出力が共に 0 個の flow で、数の比べが空で一致してしまうため）。
  - あわせて決めること（名前）: C の閉じた一覧に `<p>_out_event`、`<p>_events_out`、`<P>_OUT_EVENTS_PER_FRAME` を足す。
- 影響:
  - 仕様: §11.6（出力の形、`Rendered`、`process_inplace` の条件）、§14.2（`_process` の形、2 を返す場合、名前の表、0 以外のときの出力）、§19.1 のイベントの項。
  - 診断のコード: 新しいコードは無い。(k2) で返り値を足すなら 3。
  - 作業: W7-02（(k1) の A）、W10-01、W10-03、W8（出力の列への書き出し）、M6・M8。
  - ラッパー: (1a) では、CLAP は `process` の後に列を `try_push` へ写し、偽のときの扱いはラッパーが決める。(k1) の上限は、CLAP の `activate` が渡す最大のフレームの数から、起動のときに大きさを決められる。(1b) は CLAP と AU をそのままつなげる。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - (1)・(k)・(3) は一致した。
  - (1) の C の形は割れた。段 1 は三つの引数（`output, output_cap, uint32_t* output_len`）、下書きは struct `<p>_events_out { data, cap, len }` へのポインタ。段 2 は下書きを採る（`cap` と `frames` が同じ型で並ぶ取り違えを、フィールドの名前で避ける。§14.2 の Config を struct で受ける理由と同じ）。
  - (k) のマクロの形も割れた。段 1 は関数の形のマクロ `<P>_OUT_EVENTS(frames, events_len)`（出力のクロックは周期かイベントのどちらか一方なので、一方の項は常に 0）、下書きは係数 `A` のマクロと上限 `A × frames + events_len`。
    段 2 は下書きを採る（過大だが安全で、式が一つ）。生成したコードの容量の比べは、公開した式と同じ式で、64 ビットで行うと書く（`A ≤ 2^24`、§19.1 の比の積の上限）。
  - 上限の根拠（段 1 が確かめた）: 周期のクロックの出力は 1 刻みに一つで、`.up~(M)` の部品の中から出るものは `M × frames` 以下。入力のイベントのクロックの出力は、その入力のイベントの数以下（別の入力のクロックは混ざらない、E0815）。
    子の flow の出力のイベントのクロックは、その子の本体の式のクロックに戻して同じ場合分けになる。
  - 推奨と理由の補い（段 2）: 「一つの位置に容量を超える入力のイベントが並ぶときだけは、S-570 の (2b) が無いと分けられない」はずれている。(2b) の `frames = 0` の呼び出しでも上限は `events_len` の分が要るので、(2b) があっても容量は減らない。どの案でも、ラッパーが入力を捨てるか 2 を返す（結論は変わらない）。
  - 「あわせて決めること」の `frames`（`sample` の入出力の無い flow の `process`）と `process_inplace`（イベントを出す flow には生成しない）は、この組で決める（段 2）。「CLAP の `activate` が渡す最大のフレームの数」は、`plugin.h` を落としていないので未確認。
- 回答（2026-10-22、会話で利用者。52 回目）:
  - 出力のポインタ: 文書の点検（onsa-docs）と助言の担当の二段で、イベントの出力の無い flow が C の `_process` で出力のポインタを取るかが決まっていないと分かった（(i) 常に取る、(ii) 出力のある flow だけ）。親は (ii) を推し、境界の線（C の形は flow のシグネチャから決まった規則で決まる。シグネチャが変わっても形を保つのは、何も渡さないことが前と同じ動きになる所だけ）を説明した。
    利用者: 「逆方向の話を見落としているような気がします。つまりC APIの呼び出し側からはイベントを渡しているのに、flowには受け取る口がないので黙って入力を処理せず捨てている、ということです。この視点でみると(i)も(ii)も半端に思えます。(i) はsampleだけ例外にし、(ii)はeventの入力を例外にします。…何を受け、何を出すか、は関数のシグネチャーに明示し、期待と違えば全てコンパイルエラーとした方が統一感があると思います(eventの入力も含め)」。
    親は、今の (3b) では入力の無い flow に列を渡すと黙って捨てずに実行時に 2 になることを直したうえで、提案を「C の `_process` の信号の引数（`sample` の入出力、イベントの入力、イベントの出力）はシグネチャにあるものだけを取り（§11.6 の数の規則）、違う呼び出しは C のコンパイルの誤り。`params`・`cfg`・`bulk` は今のまま常に取る。表とマクロ（`<p>_event_in_info`・`<P>_EVENT_IN_COUNT`・`<P>_EVENT_OUT_KIND`）は全ての flow に置き、引数の型は引数のある flow だけ。列の中身の誤りは実行時の 2 のまま」と言い直した。
    利用者: 「はい、上記の認識で問題ないと思います」（あわせて、空の struct は ISO C で書けず、§14.2 の予約のメンバ `uint8_t _unused` で避けていることを確かめた）。
    了承 (ii): C の `<p>_out_event`・`<p>_events_out` と `_process` の出力のポインタは、イベントの出力のある flow だけに置く。`frames` が 0 の呼び出しでもポインタは要り、`len` に 0 を書く。S-570 の (3) も同じ規則に改めた。
