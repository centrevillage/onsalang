# S-718 マニフェストの `[[plugin]]` の `flow` が名指す flow の名前の E0320 の改名の候補（`.onsa` だけを直すと E1103 が残る）

- 決定済みで戻さないもの: 候補が使用箇所を直すこと（S-82）、重なる名前の候補なし（S-652）、モジュールの名前の E0320 の候補なし（§2.3）、`[[plugin]]` の表（S-580）、export の指定は `@export`（S-639）。E1103 の段と終了コードは S-641 のまま。
  第 66 組の下書きの「S-718 の仕組みの出所」と「S-718 の形の表」の節（写しは `target/notes/76/g66/draft.md`）。
- 論点: §2.3「E0320 の修正候補は一つで、宣言と、パッケージの中の全ての使用箇所の名前を直す」と、§15.3 の表「`[[plugin]]` の `flow`: 必須。プラグインにする flow の経路で、`@export` を付けた flow でなければ E1103（§14.3）」。
  「使用箇所」にマニフェストの文字列の経路が入るかが書かれていない。入らなければ、`pub flow BadName` の候補を当てた後に `flow = "synth.BadName"` が古いまま残り、E1103（終了コード 2）になる。
  表の他の所は、モジュールの名前（候補なし）か、この版に無いものか、E0320 のある版に当たらないもので、今当たるのは `[[plugin]]` の `flow` の最後の要素だけである。
- 今の実装: `[[plugin]]` の表を読まない（W4-02）。`@export` は E0005「there is no attribute `@export`」（`probe/m1`）。
  `@export` を外した `pub flow BadName` の E0320 の候補は宣言の `bad_name` だけで、同じファイルの `BadName~(x)` も直さない（`probe/m4`、終了コード 1。使用箇所は U9）。`tests/`・`examples/`・std に `[[plugin]]` を持つものは無い。
- 案: 
  - (a) マニフェストの文字列も使用箇所に数え、同じ候補が `onsa.toml` の経路の最後の要素を直す（候補の編集が二つのファイルにまたがる）。
  - (b) マニフェストが名指す flow の E0320 は候補を出さず、note でマニフェストの位置と揃えた名前を示す（S-652 とファイル名の E0320 と同じ形）。
  - (c) 使用箇所はソースの中だけとし、候補は `.onsa` を直す。後に残る E1103 はマニフェストの誤りとして報告される（`check` かプラグインのビルドかは S-641 の答え）。
  - (d) プラグインにする flow をマニフェストの文字列で名指さない形に改める（ソースの側に印を置く）。S-580 と S-639 の決定を改めることになる。
  - 書き手から見て: (a) は一回で直る。(b) は一回の検査で二つの位置が分かり、書き手が二つのファイルを直す。
    (c) は候補を当てた後に E1103 が残る。S-641 の仮の扱いでは E1103 はプラグインのターゲットのビルドで出るので、`check` は通り、ビルドで終了コード 2 になる（S-641 が `check` で出す答えなら `check` で 2）。§18.1 の作りでは修復のループがそこで止まる（ソースの編集では直らない誤りとして）。原因は候補そのもので、ループの外の手が要る。(d) はこの形が無くなる。
  - 候補を当て続けて: (a) は `clean`、(b) は `no-candidate`、(c) は `check` では `clean` で、ビルドの E1103 で止まる（S-641 の仮の扱い）。揃えた名前が書き手の意図で一つに決まる点は、どの案も同じ。
  - 規則と例外: (a) は使用箇所の定めを広げる。TOML の文字列の書き方（エスケープ、`'…'` のリテラルの文字列、複数行）ごとに最小の編集を作るか、作れない形では候補を出さない規則が要る。
    (b) は「マニフェストが名指す項目の E0320 は候補なし」の一つで、既にある候補なしの形に並ぶ。(c) は規則が増えない。(d) は表・キー・属性の規則が変わる。
  - 実装の量: (a) は改名の所（設計メモの `names/rename.rs`）が、マニフェストの `[[plugin]]` の値と位置（W4-02 の読み）を受け取り、経路を flow に解決し、文字列の中の範囲を作る。約 30〜50 行（文字列の形の扱いを含む）で、器がマニフェストを直す候補を読み直せるかの確かめも要る（未確認）。
    (b) は、マニフェストの経路を flow に解決する所（E1103 にどの案でも要る、S-641 の置き場所）が、名指された flow の名前の位置を集め、その E0320 から候補を外して note を足す。約 10〜20 行。(c) は 0 行。(d) は S-580 と S-639 の範囲の仕様と W4-02 の作り直し。
  - 後の作業: (a) は、ソースの名前を名指すキーやファイルが増えるたびに（第 2 期に利用者の効果を `provides` に書けるなら、§15.4 のポリシーが export の集合を名指すなら）、その文字列の編集を足す。ポリシーは人の判断に留めるファイル（§15.4）で、エージェントが当てる候補がそれを書き換える形は目的に合わない。
    (b) は、名指すキーが増えても「名指された項目」の集まりに足すだけで、文字列の形を扱わない。(c) は続く手当ては無いが、キーが増えるたびに同じ止まり方が増える。
- 他言語: rust-analyzer の rename が `Cargo.toml` を直すかは未確認（文書に記述を見つけられなかった。`Cargo.toml` は Rust の項目でなくファイルの経路を名指す）。
  JetBrains の IDE の rename は、コードでないファイルの同じ字も探す選択肢（「Search for text occurrences」）を持ち、当てる前に変更を見る画面（Preview）がある（[IntelliJ IDEA の rename の画面](https://www.jetbrains.com/help/idea/2019.2/rename-dialog-for-a-class-or-an-interface.html)）。全てを自動で直す約束ではない。

  - (a) の便利さが効くのは、名前が §2.3 に反し、かつプラグインに出す flow という狭い形だけである。そのために TOML の文字列の編集と、後のファイル（ポリシー）の扱いが続く。(b) は既にある「候補なしで note」の形に並び、規則が一つで済む。
