# S-866 C のビルドで、export が読む `const` の初期化式（ビルドで評価する）から届く std の関数の E0200 を、どの変換先の対応で決めるか（`assert_near` は通り、`gen.u32` は C の名で二件）

- 空白: §15.2 の 112 行は「届く」に「読む `const` の初期化式」を含め、111 行は届く位置の使用を「その変換先へのビルド…を始める前に」E0200 にする。§6.6 は `const` の初期化式をコンパイル時に評価し、C には値だけが入る。
  C のビルドで、export が読む `const` の初期化式から、C が与えずインタプリタが与える std の関数（`std.dsp.test.assert_near`）に届く形を、C の E0200 にするかが決まらない。
  今の実装: ドライバがビルドの時に初期化式をインタプリタで評価し、値を C に埋める（`emit/consts.rs` の T4-5）。`assert_near` は評価できるので診断なしでビルドが通る。
  `std.test.gen.u32`（インタプリタも与えない）に届く形は、評価が失敗して初期化式が呼び出しのまま残り、C の到達で「the C backend does not support the `std` function `std.test.gen.u32`」（使用の位置）と「the C backend does not support this `const` initializer (evaluated at build time)」（初期化式の位置）の二件になる（文面は C を名指すが、与えないのはビルドの時の評価器）。
  読み: (1) §15.2 の文のとおり、C の対応で決める（`assert_near` も C の E0200）。(2) 初期化式を走らせるのはビルドの時の評価器なので、その対応で決める（`assert_near` は通る。`gen.u32` は評価器を名指す E0200 を使用の位置に一件）。(3) 今のまま。
  再現: `target/notes/107/s866/assert_near_const.onsa`（U3a のテストの担当が (1) で書いた事例。今は診断 0 件）、`target/notes/107/s866/gen_const/`（`onsa build --target host` で上の二件）。固定のバイナリは `ba995f61`
- 決定: 決定（2026-11-03、利用者が細部 1〜4 を含めて了承。107 回目。独立のレビュー（段 1）と親の読みが一致し、段 2 は省いた）: (2)。入口から読む `const` の初期化式（と、そこから届く関数）は、変換先でなくコンパイル時の評価が届く範囲で、評価器が与えるかで決める。変換先は評価した値だけを受け取る。
  細部 1: 仕様 §15.2 の 112 行の「読む `const` の初期化式」を変換先の到達から外して書き換え、§6.6 の 199 行に一文を足した。`@param` の値と定数のクロックの式も同じ評価器。
  細部 2: 評価器が与えない std の `target` 宣言は、評価を始める前に使った位置で E0200（機能名と、コンパイル時の評価であることを添える。`Feature` は言語の側）。一つの使用に一件（S-309）。どの `const` から届くかは文面に入れない。
  細部 3: 変換先によらないので `onsa check` も報告する（§6.6 の E0419 と同じ）。W9-03 で `check` が全ての `const` を評価すると、どこからも読まれない `const` が与えない関数に届く形も `check` の誤りになる（S-222 の E0419 と同じ変化）。
  細部 4: 評価の段が E0200 を出したら変換先の生成に進まない。C の「this `const` initializer (evaluated at build time)」の E0200 は、値に表せない結果だけに残る。
  理由: §6.6 は初期化式を変換先と別の評価器で評価する（超越関数を `std.math` の Onsa の実装で評価する）と既に書く。(1) は今通るビルド（`Buf.zeroed` を使う補助の関数を初期化式から呼ぶ形など）を止め、第 2 期の後端ごとに結果が割れる。想定漏れの表（16 行、`const` の鎖・flow・`@param`・定数のクロックの式・二つのターゲット・`onsa check` など）に選択を変える行は無かった。
  実装の時期（利用者「手戻りが少ないタイミングで」）: W9-03（定数の評価の段）。W9-03 は評価の段を作り直し、E0419 と `check` での報告のために診断の出口を作るので、そこで足す（見込み 50〜80 行）。助言の担当は W5-02 に単位を足す案（120〜200 行）だったが、`onsa_driver/src/consts.rs` に入れる診断の出口が W9-03 で作り直しになりうる。それまでは今の挙動（C の名の E0200 と初期化式の位置の E0200）のまま。
- 経緯: 107 回目（2026-11-03）、W5-02 U3a のテストの担当（onsa-test）が NEW として挙げ、(1) で事例に書いた。親が `gen.u32` の形を再現した。U3a の実装は関数を経由する形の挙動を保つ（急ぎでない。通るプログラムを変えるのは (1)）。
  U3a の壊す側が、std の関数の使用を初期化式に直に書く形（`target/notes/107/s866/direct_const/`）で出力が変わったことを見つけた（中）。前（`ba995f61`）は初期化式の位置の「this `const` initializer」の一件、U3a の後は同じ一件に加えて使用の位置（4:11）の `std.test.gen.u32` の E0200 が出る。
