# S-866 C のビルドで、export が読む `const` の初期化式（ビルドで評価する）から届く std の関数の E0200 を、どの変換先の対応で決めるか（`assert_near` は通り、`gen.u32` は C の名で二件）

- 空白: §15.2 の 112 行は「届く」に「読む `const` の初期化式」を含め、111 行は届く位置の使用を「その変換先へのビルド…を始める前に」E0200 にする。§6.6 は `const` の初期化式をコンパイル時に評価し、C には値だけが入る。
  C のビルドで、export が読む `const` の初期化式から、C が与えずインタプリタが与える std の関数（`std.dsp.test.assert_near`）に届く形を、C の E0200 にするかが決まらない。
  今の実装: ドライバがビルドの時に初期化式をインタプリタで評価し、値を C に埋める（`emit/consts.rs` の T4-5）。`assert_near` は評価できるので診断なしでビルドが通る。
  `std.test.gen.u32`（インタプリタも与えない）に届く形は、評価が失敗して初期化式が呼び出しのまま残り、C の到達で「the C backend does not support the `std` function `std.test.gen.u32`」（使用の位置）と「the C backend does not support this `const` initializer (evaluated at build time)」（初期化式の位置）の二件になる（文面は C を名指すが、与えないのはビルドの時の評価器）。
  読み: (1) §15.2 の文のとおり、C の対応で決める（`assert_near` も C の E0200）。(2) 初期化式を走らせるのはビルドの時の評価器なので、その対応で決める（`assert_near` は通る。`gen.u32` は評価器を名指す E0200 を使用の位置に一件）。(3) 今のまま。
  再現: `target/notes/107/s866/assert_near_const.onsa`（U3a のテストの担当が (1) で書いた事例。今は診断 0 件）、`target/notes/107/s866/gen_const/`（`onsa build --target host` で上の二件）。固定のバイナリは `ba995f61`
