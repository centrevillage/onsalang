# S-556 修飾子の語の予約と、後で足す修飾子の余地

- 決定済みで戻さないもの: S-169 の `when`・`reset_if` の予約（残すかは (3) で扱う）。S-279（`ser` の予約）。§11.6「flow は第一級の値ではない」「flow 自体は型ではない」。
- 論点: 利用者の定義する修飾子（flow を受けて flow を返すもの）、複数の flow を受ける修飾子、flow の trait として修飾子を持つ形を、後で利用者のプログラムを壊さずに足せるよう、今何を予約し、どの場所を空けるか（X-7 の事前検討。当面は実装しない）。
  §2.2「後から予約すると、その語を名前に使っていたプログラムが壊れるので、先に予約した」。§11.6「flow は第一級の値ではない」「flow 自体は型ではない」。
  - (1) 宣言の語（`flowmod`）を今予約するか。(2) 複数の flow を受ける修飾子を連鎖で呼ぶとき、どの引数を頭（`self`）にするか（X-7 の推奨は「最初の flow 引数を self」）。(3) 組込みの修飾子の名前を、どの名前空間に置くか。
  - S-555 で連鎖（(b) か (c)）を選ぶことを前提にする。後置の節 (a) なら (2) は無く、(3) は予約語になる。
- 今の実装: `flowmod` は普通の名前（p10）。`flowmod rw(in: flow, p: F32) { … }` は E0002「expected a declaration」（b/p19）。`pub flow m(self, c: Bool at block)` は E0002「a flow has no `self`」（b/p17）。`default` は普通の名前（p13）。
- 案:
  - (1a) `flowmod` を今予約する。実装: 字句の予約語の表に一語と、現れた位置の E0200。費用の要因: 予約語が一つ増え、宣言の形はまだ決まらない。
  - (1b) 予約しない。後で足すときは既にある語で書く形（`flow random_when(self, p: F32 at block) -> F32 at sample { self.when~(…) }`。`flow` と `self` はどちらもキーワード）を第一の候補にする。今は E0002 なので、後で開いても壊さない。
  - (1c) 予約するかを今は決めず、正式なリリースの前に決める。リリースの前は外の利用者のプログラムが無く、壊れるのはリポジトリのテストと std だけである。
  - (2a) 最初の flow の引数を頭にする（X-7 の推奨）。(2b) 宣言に `self` を明示し、それを頭にする（fn のメソッドの `self` と同じ）。頭の外の引数は値とし、複数のインスタンスを受ける修飾子は後で決める。
    (2c) 利用者の修飾子は連鎖で呼べないものとする（関数の形だけ。S-555 の (4) と同じ見分けの問題がある）。
  - (3a) 組込みの修飾子ごとに予約語にする（`when`・`reset_if` は今の予約語）。(3b) 修飾子の名前空間を別に置き、`.名前~(` の受け手がインスタンスのときだけ引く。組込みは閉じた一覧（今は `when`・`reset_if`）。
    (3c) flow の組込み名（`prev` と同じ）にする。後で足すと、同じ名前の利用者の flow を壊す（§11.4）。
- 他言語: faust-rs の `ondemand`・`upsampling`・`downsampling` は、回路を一つ包む組込みの形（README）。利用者の定義する包む形を持つ信号処理の言語は確かめていない（未確認）。
- 推奨と理由: (1b)、(2b)、(3b)。確度: 中。
  - (1b): 予約語は必要以上に増やさない。宣言は `flow` と `self` の組で書け、`self` を持つ flow は今は E0002 なので、後で開いても既存のプログラムを壊さない。(1a) は形の決まらない語を一つ増やす。
    (1a) を選ぶなら、名前は略語と分かる短い `flowmod` でよい。
  - (2b): 「最初の flow 引数」で頭を決める (2a) は、次の場面で困る（X-7 の問いへの答え）。
    - 頭の外の flow の引数（`saw~(f0).branch~(sin~(f0), 0.5)` の `sin~(f0)`）は、引数の位置に書いた flow の呼び出しで、普通は値が渡る位置にある。そこだけインスタンスが渡ると、S-555 の (4) と同じ見分けの問題が引数の側に出る。
    - 修飾子の本体で flow の引数を二度使う（`in.when~(a) + in.when~(b)`）と、インスタンスが一つか二つかが決まらない（S-555 の (3) と同じ問題）。後で決めるときは、flow の引数を一度だけ使う規則が要る。
    - 対称な操作（二つのうち一つを選ぶ）が、頭と引数で非対称に見える。最初の引数が flow でない修飾子（`crossfade(t, a, b)`）は連鎖で呼べない。
    - (2b) は頭を宣言で明示し、「最初の flow」の推論が要らない。頭の外の引数は値と決めておけば、複数のインスタンスを受ける形は後で印か規則を足して開ける。
  - (3b): 修飾子は受け手がインスタンスの `.名前~(` にだけ現れるので、名前空間を分けても見分けは字面で決まる。組込みを後で足しても、利用者の修飾子が無い間は誰も壊さない。
    (3a) は予約できない名前（`default`）がある。(3c) は後で足すと利用者の flow を壊す。
  - flow の trait（X-7 の問い）: 嬉しい場面は見つからなかった。`when`・`reset_if` は全ての flow に同じ意味でかかり、flow ごとに実装を選ぶ必要が無い。flow は型でない（§11.6）ので、trait の対象にするには型の規則の拡張が要る。
    flow ごとの能力（エンベロープだけの再始動など）は、`block` や `sample` の入力で表せる。trait の形は連鎖でしか呼べないが、それは (b) の連鎖と食い違わないので、後で必要な実例が出たときに足せる。
  - あわせて決めること（`when`・`reset_if` の予約）: (3b) では、修飾子の名前が予約語である必要は無い。予約を外すのは後でも壊さない変更なので、今は残す。
- 影響:
  - 仕様: §2.2 の予約の文（「インスタンスを条件で動かすことと初期値に戻すこと」を修飾子の名前と言い直す）。§19.1 に「利用者の定義する修飾子は後の版。宣言は `flow` と `self` で書く方向」を一文。§11.4 の組込み名の文は変えない。
  - 診断のコード: (1a) なら E0200 の閉じた一覧に一つ足す。(1b)・(3b) は無い（b/p17 の E0002 のまま）。
  - 作業: 名前の段（W4-04）で修飾子の閉じた一覧を引く。(1a) なら字句の予約語の表（W3-04 の表）に一語。
  - 事例とテスト: (1a) なら `tests/spec/negative/reserved_words.onsa` に `flowmod` の事例が要る。テストベクトルの保留の節は関係しない。
  - 第 34・35 組への影響: 無い。std の型（MIDI など）は型の名前空間で、修飾子の名前空間とぶつからない。
- 独立のレビュー（2026-10-20、助言の担当の二段）:
  - 段 1 は (1)〜(3) と flow の trait の答えが下書きと一致した（中・中・高）。
  - 事前検討と割れるのは (2)。事前検討は「最初の flow 引数を self 扱い」を推奨とし、困る場面がないかを問う。助言の見方: (2a) では、頭の外の flow 引数の位置にインスタンスそのものが渡る形ができ、事前検討が関数の形（`when~(saw~(f0), active)`）に指摘した P3 の問題が引数の側に出る。
    本体で flow 引数を二度使ったときのインスタンスの数の規則も要る。今は実装しないので、変わるのは §19.1 の方向の一文だけである。
  - (1) について: 事前検討の `flowmod` の宣言（`at` を持たない中間の存在）と違い、`flow 名(self, …)` は出力に `-> T at sample` を書く。修飾子の結果は信号なので、§11.3 と合う。予約する語が無くなるので、予約の問いは消える。
  - 事実の直し（親）: (1b) の例に出力のクロック（`-> F32 at sample`）を足した（flow の出力の `at` は必須、E0810）。
  - 新しい S の候補（助言）: 利用者の修飾子の本体で、`self` を受け手に書ける回数（一度だけ、の方向を §19.1 に一文置くか）。利用者の修飾子を入れるときに決める。
  - 高階の補い（2026-10-20、別の助言の担当の二段。利用者の問い「flow の高階を後で入れるときに邪魔にならない書き方」から）:
    - 高階はコンパイル時に決めて flow ごとに展開する形だけが、§11.6（flow は第一級の値でない）・P6（状態の大きさはコンパイル時に決まる）・§6.3（動的ディスパッチは無い）・§19.1（ハンドルを持たない）と合う。
    - 段 1 は、flow を型引数・const 引数と同じ `[…]` / `::[…]` に置く形を独立に出した。
      宣言 `flow branch[flow a(F32 at sample) -> F32 at sample, flow b(F32 at sample) -> F32 at sample](f0: F32 at sample, sel: Bool at sample) -> F32 at sample`、呼び出し `branch::[saw, sin]~(f0, sel)`。
      親の案（値の引数の並びに `a: flow` を置き `branch~(saw, sin, f0, sel)`）は、主要な言語の読みで実行時の関数の値を渡す形に見え（Onsa の fn の値は第一級、§6.1）、`let a = saw` などが全て誤りになる非一貫性を作るので、段 2 で `::[…]` に直した。
    - 名前の衝突: 解決の衝突は E0305 と §5.1 の E0304（R-103、W4-04）で起きない。読み手の取り違え（呼び出しの字面で、どの引数が flow か分からない）は、flow の名前が `::[…]` の中にだけ現れる形で消える。
    - 利用者の修飾子の扉は二つ: どの flow にも付ける修飾子は `self` を頭にした連鎖（(2b)。`self` は本体に一度だけ書ける方向）、複数の flow の合成は `::[…]` の高階。どちらも今は E0002 / E0200 で、開いても壊さない。
    - 足す文の候補: §11.5 に「引数の位置に書いたインスタンスの呼び出し `f~(…)` は、呼び先によらず出力の値」を約束として書く（S-555 (4)）。§4.5 の `::[…]` の文は、高階を入れるときに「flow 引数は flow の名前」を足す。
- 回答（2026-10-20、会話で利用者。47 回目）:
  - H1 (a): flow の高階（flow を受ける flow）は、呼ぶ前の flow を名前で、型引数と同じ場所 `::[…]` に渡す形を第一の候補とし、§19.1 に方向の一文を書く。今の実装は変えない。
  - B3: (2) は (2b)（連鎖で呼ぶ利用者の修飾子は、宣言の `self` を頭にし、頭以外の引数は値。fn のメソッドの `self` と対応するので意外でない）。複数の flow の合成は H1 (a) の `::[…]` で書く。
  - A4・A5（利用者が ID を挙げて了承）: (1) は `flowmod` を予約しない（後で足す形は `flow 名(self, …) -> T at sample` と `::[…]`）。(3) は (3b)（修飾子の名前空間を別に置く。`when`・`reset_if` の予約は残す）。flow の trait は後回し。
