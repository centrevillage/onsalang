# S-601 Rust の `#[link(name = "m")]` 改行 `extern "C" {` を `extern "C" lib "m" {` へ写す候補

- 空白: 今は `#[link(name = "m")]` の行が他言語の属性の E0002（`hash_attribute`）で、属性を外すと `lib` の無い extern のブロック（S-477 の E0002、候補なし）になる。`#[link(name = "…")]` の名前を `lib "…"` へ写す修正候補（E0020 の行、`spec/foreign-forms.toml`）を立てるかが書かれていない。急ぎは低。
- 決定: 決定（2026-11-09、利用者。128 回目、共通の規則 S-965 と利用者の判断 B1〜B8、`target/notes/128/r58/decisions.md`）: （出所: R1、X）Rust の `#[link(name = "m")]` に続く `extern "C" {`（か `extern {`）は、属性の鍵が `name` だけのとき、二つの形にまたがる一つの E0020 の行 `link_attribute` で、候補は属性の行を除いて `extern "C" lib "m" {` にする一つ。名前が属性にあり、§14.1 のライブラリの名前で意味が一つに決まる（S-477 の候補なしの理由「名前は書き手しか知らない」は当たらない）。候補は次の項目のトークンの並びを見るだけで作り、試しに読まない。`kind` などの鍵があれば今の `hash_attribute_no_candidate` の E0002 だけ（`kind = "framework"` は `lib` でない）。
  - 仕様の節: §18.1（S-477 の文の後ろに一文）、一覧の行 `link_attribute`。
  - 今通るプログラム: 変わらない（今は `hash_attribute_no_candidate` の E0002）。当てた後の `extern` のブロックは、この版では後の段の E0200。
  - 実装の見当: `foreign/` の属性の行で、鍵が `name` だけの `#[link(…)]` の後の項目が `extern "C" {` かを見て、行と二つの編集の候補を返す（20〜40 行）。
  - ぶつかる事例: `tests/spec/negative/continue_extern_head_after_word.onsa`（`#[link(name = "m")]` の `//~ E0002 @1`）は E0020 になり、`.fix1` が要る。注記の「S-601 is not decided here」を改める。`tests/cst/err_continue_heads.onsa` は CST だけ。
- 経緯: 55 回目（2026-10-23）、第 38 組（S-593 の表 1 の 23 行）の新しい S の候補を、利用者の回答で登録した。関係: S-477、S-593、S-435。
- 補い（2026-11-10、親）: 壊す側（W5-24 U2b）の低の指摘: 候補は属性の文字列をそのまま `lib` に写すので、空の名前 `""` やエスケープ・補間のある名前でも候補が出る。当てた後は extern のブロックの E0200 だけなので今は害が無い。extern を実装する作業で、§14.1 のライブラリの名前に書けない字の候補を見直す。
