- 論点: §5.4 は「借用の起点は、… 静的な値（`const` と、補間の無い文字列リテラル）である。静的な値は不滅の静的オブジェクト（§12.8）で、解放も in-place 更新も起きない」とし、表の所有の行に「静的でないリテラルや演算の結果」を置く。
  §12.1 は静的（読み取り専用）の記憶域に「`const`、補間の無い文字列リテラル」を置き、§12.8 は「補間の無い文字列リテラルと、Shared の `const`」を `count = 0` の静的オブジェクトとする。
  静的な値だけでできた集成体のリテラル（表の 5〜9・23 行）が「静的でないリテラル」か、書かれていない。
  - 仕組みの出所: S-80 の (4) が静的な値を借用の起点に加えたのは、rt の関数で定数の表や文字列を `let` で受けるためである（§5.4「rt の関数でも、定数の表や文字列を `let` で受けられる」）。根拠は「不滅の静的オブジェクトなので破棄が要らない」で、文字列リテラルは同じ静的オブジェクトの `const` と扱いを揃えるために入った（利用者）。
  - §6.6 は `const` の結果を「Copy か、静的に配置できる Shared（`Str`、`Bytes`、要素が静的に配置できる `Array`）」とする（0.3 の G-06 で `Array` まで緩めた。`Map`・`Set` は表の配置が実装に依存するので外した）。
    §4.6 では `[Str; 2]`、`(Str, U32)`、`Str` を持つ struct は種が Shared だが、ヒープのオブジェクトではない値の型で、一覧に入るか書かれていない（表の 17 行）。
  - §12.2 は「Shared 値・`Buf` の生成」に `Alloc` が要るとするが、Shared を含む値の型を組むこと（`["a", "bc"]` を作る。要素の複製は参照カウントの増加）がそれに当たるか書かれていない。今の実装は当たらないと読む（13 行の返す側が通る）。
  - 第 1 期の扱い: 今の実装は Shared の `const` を E0407「in this version」にする。R-85 の範囲の記録は「この版で未対応は E0200（S-67）に反する」とし、S-87 の決定は「`Str` の `const` は第 2 期」を前提にする。計画 §5 も Shared 型を第 2 期の 2 に置き、今は `Str` の降下が E0200（`onsa test` と `build` の `t.out`・`build.out`）である。

- 案: (a) 今の規則のまま。静的な値は `const` と補間の無い文字列リテラルで、集成体のリテラルは要素によらず新しい値を作る所有の行（§12.7 の「リテラルは置き場所に直接構築する」と同じ見方）。表は `const` で持つ。
  §5.4 に「集成体のリテラルは、要素が全て静的な値でも所有の行。表は `const` に置く」の一文を足す。§12.1・§12.8 は変えない。
  §10: rt の関数の 5〜9 行は、`let`・`for`・`match`・一時の値のどれでも破棄に `Alloc` が要り E0601。C の生成（第 2 期）: リテラルは値として組み、要素の dup / drop は `count = 0` で何もしない。WASM も同じ。JS は GC で区別が要らない。
  実装: 束縛の状態（W4-07）と破棄点（W6-02）に判定を足さない。事例は約 4 件（5・6・8 行の rt の E0601）。費用の要因: `"a"` は rt で `let` に置け、`["a"]` は置けない、という表面の違いが残る。
  (b) 静的な値だけでできたリテラルを静的な値にする。葉が補間の無い文字列リテラル・Copy のリテラル・`const` で、配列（繰り返し `[e; N]` を含む）・タプル・struct・列挙子・括弧で組んだもの（入れ子を含む、5〜9・23 行）。
  §5.4 の静的な値の定義と、表の借用の行を広げる。§12.8 は変えない（集成体は値でヘッダを持たず、中の Shared は既にある静的オブジェクトを指す）。
  置き場所は二つに分かれる: (b1) 約束しない（借用で破棄が無いことだけを約束し、スタックに組んでも静的領域に置いてもよい）、(b2) §12.1 の静的の行に足し、静的領域に置くと約束する。
  §10: 5〜9 行は rt でどの位置でも通る。11・12 行は所有のまま。C の生成: 借用なので dup / drop を出さない（束縛の状態から出る）。(b2) は集成体の静的な初期化子（静的オブジェクトの番地を持つ）を書き出す。JS は GC で区別が要らない。
  実装: 静的なリテラルの判定（列挙子と関数の呼び出しを名前の解決で分け、約 30〜40 行）を束縛の状態の関数と破棄点の列挙が共有する。(b2) は C と WASM の静的な初期化子が約 50 行。事例は約 10 件（形ごとの `let`・`for`・引数と、境界の `["a", x]`）。
  費用の要因: 静的な値の判定が名前の段で式を辿る。`const` と同じ表を書く手段が二つになる。境界が 11 行（`["a", x]` は所有）に移る。
  (c) `const` の初期化式に書ける形と同じ範囲を静的な値にする。fn の本体で、ローカルを読まず、`const`・リテラルと、効果行が空か `{Alloc}` だけの関数の呼び出しで作れる式（`make_names()`、`"v{VERSION}"`）を、`const` と同じ評価器でコンパイル時に評価して静的領域に置く（§11.3 の flow の定数のクロックの式と同じ扱いを fn に広げる）。
  §5.4 の `let y = f(...)` の行と、W9-03 の「fn の本体の式は畳み込まない」を改める。§10: rt の関数が rt でない関数を定数の引数で呼べるようになる（コンパイル時に評価するので E0901 の例外になる）。評価の panic は本体でも E0419。
  実装: 定数の評価器を fn の本体で使う（W9-03 の後で、第 1 期の W4-07 には入らない）。束縛の種類が呼び出し先の効果行で決まる。事例は約 15 件。

  (d) 束縛の種類は今のまま（所有）で、破棄の側で数えない。§12.2 の表に「静的な値だけでできたリテラルで初期化した、書き換えられない束縛（`let`・`for` の要素・`match` の腕）と一時の値の破棄: 要らない」の行を足す。§5.4・§12.1 は変えない。
  §10: 5〜9 行の `let`・`for`・`match`・一時の値は rt で通り、`var` は E0601。C の生成: 変えない（drop は `count = 0` で何もしない）。
  実装: (b) と同じ判定（約 30〜40 行）を破棄点にだけ置く。事例は約 8 件。費用の要因: 所有なのに破棄を数えない例外が §12.2 に増え、`let` と `var` で分かれる。

  §10: 5〜9・11 行は rt で通る。C の生成: 借用の集成体を dup / drop 無しで組む（Affine の要素のハンドルも）。
  実装: 末尾を集める補助を要素へ広げ（約 30 行）、派生元の並びに要素の場所が入り、W4-08 の重なり・W4-09 の E0715・W4-10 の S-42 の無効化が要素ごとに回る。事例は約 15 件。
