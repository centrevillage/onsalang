# S-576 flow の遅れ（レイテンシ）を境界に出す形

- 空白: §14.2 の C の API と §11.6 の生成する API は、flow の遅れ（入力から出力までのサンプルの数）を出さない。プラグインのホストは遅れの報告を求める（CLAP の latency の拡張、VST3 の `getLatencySamples`）。S-568 の std の変換の flow（第 35 組）は決まった遅れを持ち、`.down~(N)` で集めて配る形は N サンプル遅れる（§19.1）。決めること:
  1. 遅れを出す所（ヘッダのマクロ、関数、`onsa interface`）と単位（本体の `sample` の刻み）。
  2. 遅れの決め方（本体から数える、書き手が宣言する、その両方の照合）。条件で動くインスタンス（`when~`）とパラメータで変わる遅れの扱い。
- 決定: 決定（2026-10-22、利用者が ID を挙げて了承。51・52 回目）: 遅れは C の `<p>_latency(s)` と生成する API の `f.latency(s)`（`init` の後の値）で出す。値は一番外の flow の `@latency(e)`（`init` のクロックの式）で、無ければ 0。コンパイラは報告する値を本体から数えず、構造から決まる遅れは `onsa audit` が出す（回答の (r-a)。形は S-586）。仕様 §19.1
  改め（2026-10-24、S-625・S-588）: 生成する API の `f.latency(s)` を外し、遅れは C の `<p>_latency(s)` で出す（S-625）。`@latency(e)` の「`init` のクロックの式」は、定数の項 `samples`・`seconds` と §11.6 の式に改めた（S-588 の (L3)。E0815 は `@latency` に当たらない）。
- 経緯: 第 35 組（X-7）の下書き（onsa-gap、S-568 の新しい S の候補）と、独立のレビューの段 2（別の S にする。利用者の flow の遅れは数えるか宣言するかの設計が要る）から立てた（2026-10-22、51 回目）。関係: S-568、S-566、S-567。
