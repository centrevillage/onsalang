- 案: 第 2 期は「既定メソッドのある項目は足りなくてよい」を除いて同じ読みである。
  - (a) 足りないも余計も E0416: §6.3 の文を読み広げる。「何も足さない」に当たる（新しいコードも、新しい種類の文も足さない）。余計の側は trait を満たさないとは言いにくい。
  - (b) 新しいコード: `impl` のメンバの過不足に一つ（E0410 と同じ見方）。
  - (c) E0410 を広げる: 「struct リテラルとパターンのフィールドの過不足」に「trait の `impl` のメンバの過不足」を足す。
  - (d) 分ける: 足りないは E0416（型が trait を満たさない）、余計は E0413（trait に無いメンバ）。どちらも既にあるコードである。
  - 形ごとの出力: `impl Default for Mode {}` は (a)・(d) E0416、(b) 新しいコード、(c) E0410。`fn other()` は (a) E0416、(b) 新しいコード、(c) E0410、(d) E0413。どの案も足りないの位置は `impl` の trait の名、余計の位置はメンバの名である。
    `fn defualt()` だけの形: どの案も余計を先に報告し（リテラルの `z: 3` の後に足りない、の順と同じ）、note で trait のメンバを示せば一度の改名で両方が消える（編集の単位に一つ）。
  - 書き手から見て（LLM を含む）: どの案も note が trait のメンバの署名（`fn default() -> Self`）を示せば修復は 1 回で、コードの違いは修復の回数を変えない。補助の関数を `impl Default` に書く形は、固有の `impl` に移す note で直る。
    (a) は主文が「trait を満たさない」に読め、余計の直し方と合わない。(b) はコードの意味が一番狭いが、覚えるコードが増える。(c) はフィールドのコードがメンバに及び、JSON でコードを読む道具の意味が広がる。(d) はコードの意味がそれぞれ既にある読みと合う。
  - 修正候補（§18.1）: どの案も足りないの候補は作らない（本体が書けない。`_` の穴は同じ段の E0421 を残し、約束を満たさない）。余計は、消すか固有の `impl` へ移すかが一つに決まらないので候補を作らず note である。止まり方はどの案も `no-candidate` である。
  - 通るプログラム: どの案も変わらない。`tests/` の `impl Default for` の事例のコードが W5-06 で変わる分は、どの案でも同じである。

- 推奨と理由: (d)。確度: 中。
  - 足りない形は「型が trait を満たさない」そのもので、E0416 の読みに合う（S-109 の割り当てと §6.3 の文）。余計な形は「trait に無いメンバ」で、E0413 の未知のメンバに合う。どちらも既にあるコードの読みのままで、新しいコードも、既にあるコードの意味の広がりも足さない。
  - 主文とコードが直し方に合う: 足りないは書き足す、余計は外す。修復の回数はどの案も同じなので、差はコードの意味の正確さと保守である。(b) は第 2 期まで一つの trait のためにコードを増やす。(c) はフィールドのコードをメンバに広げる。
  - あわせて決めること:
    - 報告の順: 余計を先に、足りないを後に出す（リテラルと同じ順）。余計があるときは足りないを報告しない（`fn defualt` は一度の改名で両方が消える）。
    - 足りないの note は trait のメンバの署名を示す。余計の note は trait のメンバの一覧と、補助の関数は固有の `impl` に書くことを示す。
    - 単位: 足りないは見出しの誤り（`impl` 全体が一つの単位）。余計はそのメンバの単位で、他のメンバは検査する。
    - 使う所: 足りない・余計のある `impl Default for P` の後の `P.default()`、`need(x)`（`T: Default`）は診断なし（宣言の誤りの連鎖、§18.1）。
    - 効果の handler の操作の過不足（第 2 期）は同じ読みで決める。
