# S-421 インライン形式の handler の本体の `{` を次の行に書く形

- 空白: その場で書く handler の本体の `{` を次の行に書く形（`handle { … } with Ask` 改行 `{ fn ask() -> I32 { 1 } }`、§8.3 のインライン形式）。
  §2.5 の置き場所の規則は、`{` が属する形として宣言と見出しの本体（「など」）、構造体リテラルと構造体のパターン、効果行の `uses {…}` を挙げ、インライン形式の handler の本体を挙げない。今は、括弧の中（`two(handle { g() } with Ask` 改行 `{ fn ask() -> I32 { 1 } }, 1)`）は通り、fmt が一行にする。
  括弧の外（`let r = handle { g() } with Ask` 改行 `{ … }`）は `Ask` で行が終わり、次の行の `{` は別のブロックとして読まれて `fn` の位置の E0002 になる。
  S-413 と同じく括弧の中は E0003・括弧の外は今の読みのままにするか（`with` の後の名前が handler か effect かは名前の段まで分からない）、本体として括弧の外でも次の行まで見て E0003 にするか。
  W3-06/i の単位 2 の補いの設計メモで見つけた（2026-10-10。親が dev の `ade4450` で、括弧の中が通り fmt が一行にすること、括弧の外が別のブロックになることを確かめた） 直し（2026-10-11、第 24 組の下書き）: 「今は、括弧の中は通り、fmt が一行にする」は W3-06 の単位 2 の前の挙動で、今（`826fc8a`）は括弧の中が E0003（仮の扱い）。
  「handler か effect かは名前の段まで分からない」は、§2.3 の字面（効果は `UpperCamel`、handler は値で `snake_case`）で構文の段でも分かる。
- 提案: 決定（2026-10-11、利用者。下書きの (a) と Fable の (d) が割れ、親が内部処理の複雑さと修正候補の確実性で比べて示した後に (d) を選んだ）: `with` の後の経路の最後の名前が `UpperCamel`（効果、§2.3）なら、インライン形式の handler の本体が必ず続く。
  本体の `{` は宣言の本体と同じく括弧の中でも外でも同じ行（E0003、候補は S-216 の移し方）。
  本体が無い形（`with Ask` だけ、`with Ask(1)`、`with Ask` 改行 `r`）は E0002 と note（効果の名前の後はその場の handler の本体、名前の付いた handler は `snake_case`）。`snake_case` の名前の後の `{` と `(args)` は今のまま。§2.3 の命名の表に handler を足した。
  判定は `naming::is_type_name`（S-413 と同じ字面の判定）と `e0003_unless_on_the_line` を使う（約 6〜10 行）。
  本体を書き忘れた後に無関係のブロックが続く形は、誤りが二つある入力として約束の外（S-413 の `two(N` 改行 `{ 1 })` と同じ）。`SPEC-GAP(S-421)` の印と `layout_tests.rs` の「provisional」の事例を改める。仕様 §2.3、§2.5、§8.3。実装は W3-08
