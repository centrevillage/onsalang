# S-592 族: §15.1 のパッケージの木の集め方

- 決定済みで戻さないもの: `.` で始まるディレクトリは集めず、経路で渡せば E0320（S-313）。ルート直下の `tests/` は E0200、それより深い `tests/` は普通のモジュール（S-96）。ルート直下の `target/` は集めない（§15.1、S-11）。上へ探して最初の `onsa.toml`（S-159、R-47）。
  経路は一つで、ディレクトリはルートを指す（S-312）。ファイル名とディレクトリの名前の E0320（S-300、S-313）。`span.file` はルートからの経路（S-234）。`fmt` に渡した経路のリンクはリンク先を書く（S-535）。依存のパッケージの解決（§15.3、§19.1）はこの族の外。
- 論点: 仕様 §15.1「パッケージルートは `onsa.toml` のあるディレクトリで、その下の `.onsa` ファイルを再帰的に集める（`.` で始まる名前のディレクトリ（道具が作るもの）と、パッケージルート直下の `tests/` と `target/` を除く…）」と、「コマンドは、渡したファイル（無ければ作業ディレクトリ）から上の階層へ `onsa.toml` を探し、最初に見つけたディレクトリをパッケージルートにする」。
  書かれていないのは、(1)「その下」がリンクを辿った先を含むか（表の 1〜9 行）、(2) 中に `onsa.toml` を持つディレクトリの下を集めるか（10・11 行）、(3)「`.onsa` ファイル」が通常のファイルに限るかと、読めない項目（16〜19 行）、(4) 上へ探す起点が渡した経路の字面か、リンクを解いた場所か（20・21 行）、(5) 経路で渡した `target/` の下のファイル（22 行）。
  (2) は、上へ探す規則（最初に見つけた `onsa.toml`）と下へ集める規則が食い違う所である。中のファイルを渡せば中のパッケージになり、外を渡せば外のモジュールになる。一つのファイルが二つのパッケージに属し、`n2` のように意味も変わる。

- 案:
  - (a) 実際の木だけを辿る。リンクは、ファイルを指すものもディレクトリを指すものも辿らず、集めない（黙って除く）。`onsa.toml` を持つディレクトリの下は別のパッケージで、集めない。通常のファイルでない `.onsa`（FIFO など）も黙って除く。渡した経路は、リンクを解いた実際の場所から上へ探す。
    実装: `read_sources` で `DirEntry::file_type()`（リンクを辿らない）を使い、リンクと通常のファイルでないものを飛ばし、子のディレクトリに `onsa.toml` があれば飛ばす（約 10 行）。渡した経路は `canonicalize` してから探す（約 3 行）。モジュールの木は変えない（ファイルの経路が一つに決まる）。テストは約 6 件（リンクを作るので `#[cfg(unix)]`）。
    費用の要因: `.onsa` の名前のリンクを置いた書き手には、モジュールが黙って無い（`use` すれば E0302 になるが、テストだけのファイルは黙って走らない）。
  - (b) (a) に加え、名前が `.onsa` で終わる項目が通常のファイルでもディレクトリでもなければ（ファイルを指すリンク、壊れたリンク、ディレクトリを指すリンク、FIFO など）、使い方の誤り（終了コード 2）にする。名前が `.onsa` で終わらないリンクは (a) のとおり辿らずに除く。
    実装: (a) に分岐を一つと文面（約 5 行）、テストを 2 件足す。費用の要因: 名前で決まる誤りの規則が一つ増える。ディレクトリのリンクの下の `.onsa` は (a) と同じく黙って除かれる。
  - (c) リンクを辿る。リンクを解いた実体で一度だけ集め、輪は一度目で切る。外を指すリンクも集め、モジュールの経路はリンクの経路（ルートからの字面）。同じ実体に二つの経路で届くときは、並べ方で最初の経路を採る。実体の場所に `onsa.toml` を持つディレクトリの下は集めない。渡した経路はリンクを解かずに字面の場所から上へ探す。
    実装: ディレクトリとファイルごとの `canonicalize`、訪れた実体の集合、同じ実体の経路の選び方、壊れたリンクの扱い（約 40〜60 行）。テストは約 8 件。
    費用の要因: モジュールの経路がリンクの置き方と並べ方で決まり、エディタが開く実際のファイルの経路と `span.file` が違う（LSP が両方を対応付ける）。同じ実体の経路の選び方の規則が増える。外を指すリンクで、パッケージの中身がルートの外のファイルに依る（依存のパッケージの代わりになる）。
  - (d) 実際の木だけを辿り、パッケージの木の中のリンクは、名前と指す先によらず全て使い方の誤り（2）。入れ子のパッケージも 2。通常のファイルでない `.onsa` も 2。渡した経路のリンクは (a) と同じく解く。
    実装: (b) と同じ量。費用の要因: `.onsa` を含まないリンク（音の素材、文書のディレクトリ）を置いたパッケージが読めない。入れ子のパッケージを置く構成（ライブラリの中に例のパッケージを置く）も読めず、外に並べることになる。
  - (e) 今の挙動のまま（リンクを辿り、輪は OS の上限で止まる。入れ子も外が集める）。実装の量は 0。費用の要因: 上限は OS で違い（macOS で 32 段。他は未確認）、モジュールの集合が機械で変わる。FIFO で止まる誤りと `ELOOP` を捨てる誤り（付録）は別に直す。
  - 入れ子の扱いは (a)〜(c) では「集めない」、(d) では誤り、(e) では外も集める。リンクの扱いと分けて選んでもよい。

  - cargo 1.94.1（確かめ）: VCS の無いパッケージで `cargo package --list --allow-dirty --offline` は、ディレクトリのリンクを辿り（`linkeddata/x.txt`、`insidelink/s.txt` と `sub/s.txt` の両方）、ファイルのリンクと壊れたリンク（`broken`）も並べる。`loop -> .` は「File system loop found: … points to an ancestor」の警告で飛ばす。`Cargo.toml` を持つ `inner/` は並べない。
    文書は「Any sub-packages will be skipped (any subdirectory that contains a `Cargo.toml` file)」「A directory named `target` in the root of the package will be skipped」（https://doc.rust-lang.org/cargo/reference/manifest.html の「The `exclude` and `include` fields」。リンクには触れない）。
    `inner` で `cargo metadata` は、外に `[workspace]` が無ければ `inner` だけの workspace、外に `[workspace]` があれば「current package believes it's in a workspace when it's not」で止まる。Rust のコンパイルは `mod` の宣言でファイルを決めるので、木を集めない。

- 推奨と理由: (b)。確度: 中（入れ子を集めないことは高）。
  - 上へ探す規則（S-159）は、ファイルを最も近い `onsa.toml` のパッケージに属させる。入れ子の下を集めないと、下へ集める規則はその裏返し（ルートの下で、上へ探してこのルートに着く `.onsa` ファイル）になり、一つのファイルは一つのパッケージに属する。
    (e) の `n2` のように、渡し方で同じファイルの意味が変わることが無くなる。入れ子を誤りにする (d) は、境界とは別の条件を足し、例のパッケージを中に置く構成を塞ぐ。
  - その裏返しの規則の下では、リンクを辿っても新しいファイルは増えない。中を指すリンクの先は実際の経路で既に集めていて、外を指すリンクの先は別の場所に属する。リンクを辿らないことは、別の規則でなく同じ規則の言い換えになる。
    輪の検出が要らず、モジュールと実際のファイルが一対一になる。LSP はエディタが開いた経路をそのまま使える。
  - (c) は同じ実体の経路の選び方の規則を足し、モジュールの経路がリンクの置き方で決まる。外を指すリンクが依存のパッケージ（§19.1 で未決）の代わりになり、依存を決めるときに、リンクで取り込んだモジュールとの関係を決め直すことになる。
  - (b) が (a) に足す一つの規則は、名前が `.onsa` の項目を置いた書き手の意図（モジュールにしたい）を黙って捨てないためである。ルート直下の `tests/` を黙って除かず E0200 にした理由（S-96）と同じで、S-313 も規則に合わない名前を黙って除く案を退けた。今は FIFO で止まり終わらない（17 行）ので、それも防ぐ。
    ディレクトリのリンクは、中身を辿らないと `.onsa` を含むか分からず、音の素材のリンクのように `.onsa` を含まない用途がありうるので、誤りにしない（(d) との違い）。
  - 緩め方: (b) の `.onsa` のリンクの誤りは、後で (a) か (c) へ緩めても、通っていたパッケージは壊れない。ディレクトリのリンクを後で辿る（(c)）と、リンクを置いたパッケージのモジュールが増えて結果が変わる。ただし上の裏返しの規則を採れば (c) へ移る理由は無い。
  - 第 2 期と JS / WASM: 依存のパッケージは別のパッケージとして入り、入れ子を別のパッケージとする規則と合う（`vendor/` のような置き方も同じ規則で読める）。ブラウザで動くコンパイラの仮想のファイルにはリンクが無く、規則はそのまま当たる。
  - 規則から決まる S:
    - S-272: 表の 1・2・7 行（`.onsa` の名前のリンク）は 2。3・4・5・8 行（ディレクトリの名前のリンク）は辿らない。6 行の輪は起きない。9 行のハードリンクは通常のファイルで、二つのモジュール。20・21 行は、渡した経路のリンクを解いた場所から上へ探す（`outfile.onsa` は `base` の `sub.b`）。
    - S-324: 表の 10 行は、外が中のディレクトリを集めない（`n1` は `a` だけ）。11 行は、外のモジュールの経路に入らないので、外からは E0320 も E0304（S-246）も出ない。中のパッケージのルートの名前は規則を当てない（S-313 のとおり）。

    作業ディレクトリは OS が実際の経路で返すので、渡した経路を解くと、ファイルを渡したときと経路を省いたときが同じ規則になる。`fmt` が渡した経路のリンク先を書く（S-535）のとも同じ向き。
