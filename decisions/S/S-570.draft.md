# S-570 境界のイベントの入力: 生成する API と C の API の形、入力をまたいだ順の渡し方

- 決定済みで戻さないもの: 組の全体（第 35 組の全ての下書きに当たる）:
  - イベントの入力ごとのクロック、位置はホストが決める、一つの入力の中はホストの列の順、入力をまたいだ順は境界が渡す順（ホストの列に順があればそれを保ち、無ければ外の flow の入力の宣言の順）（S-560・S-561、S-567 の E4）。
  - flow のイベントの出力は `-> E at event` で本体の式は `Option[E]`、一つの刻みに一つまで、出す位置は出した刻みの位置、struct の出力にイベントを含めない（S-564、S-567 の E3）。`when~` はイベントの刻みの処理を止めない（S-567 の P7）。
  - イベントの値は利用者の型を含む Copy の型で、MIDI とトランスポートは std の型、イベントの型は prelude に入れない（S-171、S-560）。イベントの値は暗黙に最後の値で読め、`latest~` に当たる flow は要らない（S-563 の E7、S-567 の K4）。
  - パラメータは `block` の入力のままで `Params` は呼び出しごと、ラッパーは位置付きのパラメータの変化で呼び出しを分けてよい、パラメータを `at event` で届ける形は今は採らない（S-565 の R12）。
  - §14.2 の C の API の原則（メモリは呼び出し側、返り値の `int` の 0・1・2 と 0 以外のときに出力を 0 で埋めること、生成する名前の閉じた一覧、形は flow によらず一定（`process` の入出力は §11.6 の数の規則）、公開ヘッダは C99 と C++11 から `-pedantic` で警告なし、`ONSA_ABI_VERSION`）。
  - 記号: 例の flow の名前（`syn`、`det`）と prefix `pz_` は説明のためのもの。`<p>` は §14.2 の C の名前、`<P>` はその大文字。
  - 試した入力: 51 回目に dev `4aaa028` の release で試した。入力は `target/notes/51/gap35/probe/`（51 回目の scratchpad の写し。パッケージ `q01`〜`q09`、単一のファイル `r10`・`r11`）、作り方は `probe/mk.py`、回し方は `probe/run.py`、出力は `probe/out.txt`。終了コードは 0・1・2 だけだった。
    イベントのクロック、`at (…)`、修飾子は未実装（新しい構文は W3 以降）なので、試せたのは今の境界の形と、今の誤りの出方だけである。
- 論点: §11.6「`process` の `<入力>` と `<出力>` は、数で形が決まる」。§14.2「関数と型の形は、flow の宣言にもターゲットにもよらず一定で、変わるのはフィールドと定数の値だけである（`process` の入出力の引数は §11.6 の数の規則に従う）」。
  どちらにもイベントの入力の引数が無い。§19.1「入力をまたいだ順は境界が渡す順で、境界はホストの列に順があればそれを保ち…、無ければ外の flow の入力の宣言の順で並べる。渡し方は第 35 組」。
  - 決定済み（S-561、S-567 の E4）: 順の意味。一つのホストの列を一つの入力だけに受けさせる形（入力ごとの列で、またいだ順を持たない形）は、CLAP のように MIDI とトランスポートが一つの列で来るホストで「ホストの列の順を保つ」を満たせないので、案に並べない。
  - (1) 列の形と、入力をまたいだ順の表し方。(2) 列の前提（位置の順、`frames` より小さい）と、破ったときの扱い。`frames` が 0 の呼び出しのイベント。(3) イベントの入力の無い flow の引数と、`process_inplace`・`In` との関係。
- 今の実装: `notes: Note at event` の入力は E0302「cannot find the clock `event`」で、note にこの版のクロックの一覧（`q02`）。
  export の C（`q01`、`build --target src`）は `int pz_gain_process(pz_gain* s, const pz_gain_params* p, const float* x, float* out, uint32_t frames)` で、イベントの引数は無い（ヘッダが flow ごとに分かれるなど §14.2 と違う所は W10 の作業の範囲）。
- 案: 例の flow は `pub flow syn(tr: T at event, notes: N at event, x: F32 at sample) -> F32 at sample`（`T`・`N` は境界に出せる型。どの型かは S-572）。
  - (1a) 入力の印の付いた一つの列。順は列の順だけで決まる。
    C: `typedef struct { uint32_t pos; uint32_t input; union { <T の C の型> tr; <N の C の型> notes; } v; } pz_syn_event;` と、入力の番号のマクロ（`PZ_SYN_EV_TR 0`・`PZ_SYN_EV_NOTES 1`、宣言の順）。
    `pz_syn_process(s, params, const pz_syn_event* events, uint32_t events_len, <入力>, <出力>, frames)`。
    Onsa: 中身を見せない Copy の型 `syn.Event` と、イベントの入力ごとの作る関数 `syn.Event.notes(pos: U32, v: N) -> syn.Event`。引数は `events: Span[syn.Event]`。
    ホストの列に順が無いとき（VST3 の `ProcessContext` のトランスポートと `IEventList`）は、ラッパーが宣言の順で混ぜる。
    実装: 生成する型（C の union、Onsa の型と作る関数）、一本のループ（次のイベントの位置まで `sample` の段を回し、印で分けてイベントの段）。費用の要因: C では印と union の中身の一致が型に現れない（印の範囲は検査できる）。
  - (1b) 入力ごとの列と通し番号。
    C: `typedef struct { uint32_t pos; uint32_t seq; <N の C の型> value; } pz_syn_ev_notes;` を入力ごとに作り、`pz_syn_events { const pz_syn_ev_tr* tr; uint32_t tr_len; const pz_syn_ev_notes* notes; uint32_t notes_len; }` へのポインタを渡す。
    同じ位置は `seq` の小さい順で、同じ `seq` は宣言の順。ホストの列に順があれば `seq` に列の添字を入れ、無ければ 0 にすると宣言の順になる（宣言の順の規則を生成したコードが受け持つ）。
    Onsa: `syn.Events { tr: Span[…], notes: Span[…] }`（`In` と同じ形）。実装: 入力の頭を比べて混ぜるループ。費用の要因: 一つの入力の中の順が、列の順と `seq` の二か所にある（食い違いは検査で誤りにする）。
  - (1c) ホストの関数で読む（CLAP の `size`・`get` の形）。コピーが要らない。費用の要因: Onsa の `process` に同じ形が無い（無名関数は引数の位置だけで捕捉は読み取り専用、§5.3）ので、Onsa の API と C の API が別の形になる。WASM では外の関数をイベントごとに呼ぶ。
  - (1d) 位置を持たない（Cmajor の `addInputEvent`）。イベントは呼び出しの頭にだけ置き、ホストがイベントの位置で呼び出しを分ける。列の形は (1a) か (1b)。
    費用の要因: 分けるたびに `block` の段を評価し直す（結果は同じ）。出力のイベント（S-571）には位置が要り、入出力の形が揃わない。`render` は中で分ける。
  - (2a) 位置は `pos < frames` で、列の順に減らない。破れば、C は 2（状態を進めず、出力を 0、poisoned にしない。重なりと同じ）、Onsa は呼び出しの最初に panic（poisoned。`Span` の長さの不一致と同じ、§11.6）。`frames` が 0 の呼び出しはイベントを持てない（あれば同じ扱い）。
    (2b) (2a) に加えて、`frames` が 0 の呼び出しは位置 0 のイベントを持てる（イベントの段だけを評価する）。同じ位置のイベントを二つの呼び出しに分けられ、CLAP の `flush` に当たる。
    (2c) 生成したコードが並べ直すか、範囲の外の位置を丸める。費用の要因: 並べ直しは作業の領域が要り、同じ位置の順を壊しうる。丸めは誤りを黙って直す。
    (2d) 検査しない（ポインタの長さと同じくホストの責務）。費用の要因: 範囲の外の位置で、生成したループが出力のバッファの外に書く。
  - (3a) イベントの入力の無い flow は引数を持たない（§11.6 の数の規則）。(3b) 常に置く（`params` と同じ。無い flow は NULL と 0）。どちらでも `process_inplace` は同じイベントの引数を持ち、`In` は `sample` の入力だけを持つ。

- 推奨と理由: (1a)、(2a)、(3a)。確度: (1) 中、(2) 中〜高、(3) 中。
  - (1a): 入力をまたいだ順の置き場所が列の順の一つだけで、`render` とテストに順をそのまま書ける（S-573）。CLAP の一つの列はそのまま写せる。
    後でパラメータを `at event` で届けるときも、同じ列に印を足せば、同じ位置のノートとの順が保てる（ABI の形は変わらず、union と印が増えるだけ）。
    (1b) は VST3 のように列が分かれるホストで楽だが、順が二か所に分かれ、テストのたびに `seq` を書く。(1c) は Onsa と C の形が分かれる。(1d) は入出力の形が揃わず、`block` の段の計算が増える。
  - (2a): 呼び出しの最初に一度だけ確かめる形は、`Span` の長さの比べ（§11.6）と同じで、費用はイベントの数に比例する一回の走査だけである。(2b) は後で足しても今のプログラムを壊さない。(2c) は黙って直し、(2d) はメモリの安全を崩す。
  - (3a): 音声だけの flow の呼び出し（§17.5）が変わらない。「形は一定」の原則は、既に `sample` の入出力で数の規則に従うと限られている。
  - 決定性と区切り: (1a) と (2a) で、位置 k で呼び出しを分けると、`pos >= k` のイベントは次の呼び出しの `pos - k` に移り、位置 k のイベントはどちらでも k のサンプルの前に処理される。`block` は状態を持たず、位相のカウンタは区切りに依らない（§19.1）ので、出力はビットで同じである。列の順も保たれる。
  - あわせて決めること（名前）: C の閉じた一覧に `<p>_event` と入力の番号のマクロ `<P>_EV_<入力の名前の大文字>` を足す（重なりは E1011）。Onsa の名前空間の一覧に `Event` を足す。`onsa interface` にイベントの入力と番号を出す。
    型は flow ごとのものなので `onsa.h` は変わらず、`ONSA_ABI_VERSION` は上げない。
  - あわせて決めること（引数の位置と名前）: `params` の後、`sample` の入力の前に置き、名前は `events`（C は `events`・`events_len`。§14.2 の `Span` の写し方）。
