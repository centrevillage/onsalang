# S-986 使う所のフィールド名に書いたキーワード（struct リテラル `P { in: 1.0 }`、パターン `let P { in: v } = p`）に、末尾の `_` の候補を出すか

- 空白: §2.3（S-654）は、宣言の名前の位置と式の位置のキーワードに候補を出す。使う所のフィールド名（struct リテラルの `P { in: 1.0 }`、struct のパターンの `let P { in: v } = p`、短縮形の `let P { in } = p`）は、どちらにも挙がっていない。
  宣言の `in` を候補で `in_` にした後、使う所の「expected field name」に候補が無く、修復がそこで止まる（式の位置に候補を足した理由と同じ形）。短縮形のパターンは束縛を新しく作るので、候補が意味を変えうる。
  決めること: 使う所のフィールド名に候補を出すか。W5-24 U2c は出さない（決定の文のとおり）。
- 決定: 決定（2026-11-12、利用者「(2) にしよう」。140 回目、W5-13 の前。親が (A) の確認だけの一覧から説明を求められて推した）: (2)。使う所のフィールド名（struct リテラルの `P { in: 1.0 }`、struct のパターンの `let P { in: v } = p`、短縮形の `let P { in } = p`）に書いたキーワードにも、式の位置と同じく末尾の `_` の候補 `in_` を出す。宣言を候補で `in_` に直した後、使う所で直す流れが止まらないためで、S-654 で式の位置に候補を足した理由と同じ。当てた後に `in_` のフィールドが無ければ後の段の E0413 が残り、短縮形では束縛の名前も `in_` になる。§2.3 に足した。W5-13 で入れる（`onsa_syntax` の `parser/failure.rs::keyword_name`、十数行と事例数件の見当）。
- 経緯: 133 回目（2026-11-10）、W5-24 U2c の壊す側（onsa-break）が報告し、親が U2c のバイナリで再現して登録した。急ぎでない。
