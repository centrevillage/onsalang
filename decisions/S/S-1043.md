# S-1043 flow の本体の一時の値（`mk(1).len()`、`mk_b(1)[0]`。`mk` は効果行が空の `rt fn` で `Str`・`Buf` を返す）の破棄を、どの診断にするか（今はどれにもならない）

- 空白: §11（`spec/11-flow.md`）は「`Alloc` を持つ関数を呼べないので、flow とその初期化はヒープを使わない」、§12.3 は「flow は元々ヒープを使わない」とする。flow の本体から呼べるのは、効果行が空の `rt fn` と、`init` 以下の引数の非 `rt` fn で、効果を持つ fn は E0805（§11 の呼び出しの表）。
  §12.2 は所有する Shared 値・`Buf` を含む値の破棄に `Alloc` を要るとし、W6-02 U5a で一時の値の破棄を数えた（§12.2 の一時の値の文）。flow の本体の式の中の一時の値（`x * F32.round_from(mk(1).len())`、`x * mk_b(1)[0]`）の破棄が誤りか、誤りならどの診断か（`rt fn` と同じ E0901 か、E0805 の側か、別の誤りか）が書かれていない。名前を付けた形は、flow の `let` に `Str` を置くと E0810 なので、当たるのは式の中の一時の値だけである。
  今（`452cec08`）: 誤りにならない（`fn` の同じ式は E0601）。U5a の前も同じで、U5a の後退ではない。再現は `target/notes/148/w602/u5a/b/repro/r3_flow.onsa`。
  読み: (1) `rt fn` と同じ E0901（flow の本体は rt の規則）。(2) E0805 の側（flow は効果の無い関数だけを呼ぶ）に新しい形を足す。(3) 誤りにしない（効果行が空の `rt fn` が返す `Str`・`Buf` は静的な値か引数から移したものだけで、flow の中では解放が起きない。`tasks/phase2.md` の L2 の見方）。
  急ぎ: W6-03 の前（効果の使用の記録で、本体ごとの暗黙の `Alloc` を数えるとき）。
- 決定: 決定（2026-11-14、利用者。150 回目、第 104 組。下書きと独立のレビューの段 1 が (b) で一致し、段 2 は省いた）: (b)。flow の本体は効果を使わず、暗黙の `Alloc`（§12.2）も使えない。補間文字列と、破棄に `Alloc` の要る所有の値を作る式は、効果を持つ fn の呼び出しと同じ E0805（§11.5）。位置はその式で、修正候補は無い。静的な値と破棄の要らないリテラル（§5.4）は書ける。
  B2（利用者）: (1) 例外を作らない。式のクロックによらず E0805（定数の引数の `uses {Alloc}` の明示の呼び出しが今 E0805 なのと揃う）。`const` の初期化式と同じに許すかは S-1049（W9-03 の前）で決め、許しても通らない形が通るだけで壊れない。
  細部（利用者が推奨のとおり了承）: C1 位置は値を作る式（呼び出し、補間のリテラル、リテラル）で、S-783 に頼らない。C2 作る式は三種（呼び出しの結果、補間、所有の行のリテラルで自分の型が Dup でないもの、`has(None)` の `None: Option[Buf[F32]]`）。型は呼び出しの式の具体化の後の型で見る（`id("abc").len()` も E0805）。
  C3 `move` の引数で呼び先へ移す形（`ids(mk(1))`）も flow で報告する（除く条件は集成体・枝・腕へ広がる）。C4 `init` の計算、ガード、`&&` の右辺、インスタンスの引数も同じ規則。C5 判定は flow の段（`flow/rate.rs` の歩き）が一度だけ行い、W6-03 の使用の記録に flow を入れない。型の判定は `drop_alloc.rs` の一つの関数を共有する。
  C6 実装は W7-04（W7-02 がクロックの解析で `rate.rs` の歩きを作り直すので、その後。第 1 期は Shared の降下が E0200 で急ぐ実害が無い）。R-453 は `fix` を W7-04 のまま同じ判定で閉じる。R-457 は補間がクロックによらず E0805 になるので観測できなくなり、`fix` を W7-02 から W7-04 へ移して一緒に閉じる。
  C7 仕様は §11.5 の最後の項を書き直し、§11.2 の閉じた一覧のリテラル、§12.3、§8.1 の E0601 の項に §11.5 を指す句。登録簿の E0805 の行に暗黙の `Alloc`。文面の note で「flow はヒープを使わない」と Copy の値を返す直し方を示す（文面は約束でない）。C8 補間の正例の flow 4 つ（`tests/spec/lex/interp_paths_locals.onsa` の 3 つ、`tests/spec/packages/interp_path_heads/main.onsa` の 1 つ）は、W7-04 のテストの票で期待を足すか、穴を `fn` の本体へ移す。
  理由: `fn` の世界は明示の呼び出しと暗黙の `Alloc` を一つのコード（E0601、S-77）にまとめる。flow の世界は明示の呼び出しが E0805 なので、暗黙も E0805 にまとめると同じ分け方で、§18.1 の「直し方が同じならまとめる」に合う。flow は Copy でない値に名前を付けられず出力にもできないので、破棄の点を調べずに作る式で決まり、flow の段の一か所で閉じる。§11.5・§12.3 の「flow はヒープを使わない」が字のとおりに成り立つ。
  (a) は効果行の無い flow に「効果行に無い」のコードを当て、flow の破棄の点（modes に flow を通すか、数える所を二か所にする）が要る。(c) は呼び出しと補間でコードが割れ、第 2 期の L2 で緩まない。(d) は同じ式が flow で通り `rt fn` で誤りの食い違いを作り、第 2 期の L2 を flow にだけ先に入れ、後で厳しくすると今通るプログラムを壊す。
  他言語: Swift の `@_noAllocation` は型で判定し、一時の値の式に誤りを出す（実行時に解放しない値でも誤り）。Cmajor・SOUL は確保の要る操作を言語に置かない。
