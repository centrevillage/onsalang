# S-491 `impl`・`test` などに付けた可視性

- 決定済みで戻さないもの（第 39 組の三つの族に共通）: 可視性の 3 段階と `pub(pkg)` の E0020、`use` の束縛はモジュールの中、`priv use` は E0020、`pub use` は `pub` の項目だけ（S-36）。フィールドは struct を継ぎ、狭めるときだけ `priv`（S-35、S-420）。他の言語の範囲を限る可視性（S-417）。メソッドの可視性（R-38）。
  `use` は絶対経路で、頭はルート直下のモジュールか依存のパッケージ名だけ、列挙子などは取り込めない（S-37、S-246）。パスの `.` の後と `use` の経路の頭のキーワードと予約語は名前として読む（S-20、S-357、S-371）。同じ名前の二度目の `use` は E0304（S-17）。構文の段で失敗した `use`（R-180）。
  読み続けた宣言（S-435・S-459・S-464。記録の規則は第 38 組の S-593 で、答え待ち）。E0302 の綴りの近い名前の候補（S-258）と `Self`（S-377・S-446）は次の組で扱い、ここでは関係だけを書く。
- 論点: 仕様 §15.1「可視性は `pub`（パッケージ外に公開）、無指定（パッケージ内に公開）、`priv`（モジュール内のみ）の 3 段階」は、可視性を書ける宣言を挙げない。
  決まっているのは、`use`（`pub` だけ、S-36）、フィールド（`priv` だけ、S-35）、固有の `impl` のメソッド（R-38。§6.3 の例 `pub fn new`）と、列挙子の中身は enum を継ぐこと（§15.1）である。
  名前を持たない宣言（`impl`、extern のブロック、`test`）と、持ち主を通して使うメンバ（trait・effect のメンバ、trait の実装と handler のメンバ、extern のメンバ）に書いた語の意味は書かれていない。仕様の例はこれらに語を書かない。
- 今の実装: 構文解析器の `parse_item`（`crates/onsa_syntax/src/parser/items.rs`）は、位置と宣言の種類によらず可視性を読み、`use` の `priv` だけを E0020 にする。名前の段は `impl` と `test` の語を使わない。
  リポジトリ（tests、std、examples）の `.onsa` に 11〜20 行の形は無い（`git grep` と、ブロックの中のメンバの語を数える小さなスクリプトで確かめた）。

  - (b) 11〜19 行を一つの E0020 の行にし、候補は語を外す形。note で可視性を書ける宣言を示す。
    実装: `parse_item` に、宣言の種類と位置（`ItemCtx`。trait の実装のメンバを固有の impl のメンバと分ける印を足す）で決める判定と報告（20〜30 行）。`spec/foreign-forms.toml` の行と例 3 件以上。

- 他言語:
  - rustc 1.94.1（手元）: `pub impl P {}`、trait の実装のメンバの `pub fn`、`pub extern "C" {}`、trait のメンバの `pub fn`、列挙子の `pub A` は、どれも E0449「visibility qualifiers are not permitted here」。
    extern のブロックのメンバは自分の可視性を持つ（`unsafe extern "C" { pub fn sin(…) }` は他のモジュールから呼べ、語が無ければ E0603「function `sin` is private」）。
  - Swift 6.3.1（手元）: `private extension P { func m() … }` の `m` を別のファイルから呼ぶと「'm' is inaccessible due to 'fileprivate' protection level」（extension の語がメンバの既定になる）。
    プロトコルへの適合を宣言する extension の `public` は「'public' modifier cannot be used with extensions that declare protocol conformances」。
  - Python・JavaScript・TypeScript: 型に後から付ける impl のブロックと、テストの宣言が無い。TypeScript の `export` は宣言ごとに付ける（未確認: 手元に tsc が無い）。
- 推奨と理由: (d)。確度: 中。
  - 一つの規則にまとめる: 可視性は、他のモジュールから名前で参照する宣言（1〜6 行のトップレベルの名前のある項目、7 行の `use`、9 行の固有の impl のメンバ、10 行の extern のメンバ、8 行のフィールド）にだけ書く。
    名前を持たない宣言（`impl`、extern のブロック、`test`）と、持ち主の可視性を継ぐメンバ（trait・effect のメンバ、trait の実装と handler のメンバ、列挙子）には書かない。メンバの可視性がメンバの宣言だけで決まる今の規則（R-38、S-35）を保つ。
  - (a) は、何も変えない語を受理して残す。Rust では誤り、Swift ではメンバの既定と、書き手の読みが割れる形を黙って通す。仕様の例、std、テストに一つも無く、受理する利点が無い。
  - 候補を二つに分ける理由: test、trait の実装、継ぐメンバの語は、外しても今と同じ意味のプログラムになり（`priv use` とフィールドの `pub` の E0020 と同じ冗長な語）、候補が一度で収束する。
    容れ物の語は Swift の読みではメンバの既定で、外すとメンバの可視性が書き手の意図と違うまま検査を通る（`pub impl` のメンバは公開の API から黙って抜け、`priv impl` のメンバはパッケージ内に広がる）。S-420 が、意図と逆の可視性で通る候補を出さず候補の無い E0002 にしたのと同じ考え方である。
    語をメンバへ写す候補は、Swift の読みに寄せた意味の推測になり、第 38 組の S-492 の下書き（答え待ち）も `rt impl` の `rt` をメンバへ写さないので、作らない。
  - (c) は行が一つで済むが、外して安全な形にも候補が無い。(e) は可視性が容れ物とメンバの二か所で決まり、規則と書き方が増える。厳しい (d) から後で (e) へ緩めても、通っていたプログラムは壊れない。
  - 第 2 期と JS / WASM: 可視性の判定はメンバの宣言だけを見るので、公開の一覧（`interface`、export の表）と生成するコードの名前は容れ物を見ずに決まる。
  - あわせて決めること: extern のメンバは (i)（トップレベルの fn と同じく自分の可視性を持つ）。extern のブロックは、名前を持つメンバを並べる容れ物で、固有の impl と同じ形になる。
    確度は低（extern のブロックはこの版では E0200 で、使う所が無い）。(ii) は C の関数の主張を外に出さない利点があるが、無指定を一か所だけ固める規則が増える。FFI を実装する作業で決め直してもよい。
  - あわせて決めること: 誤りの語の後は、§18.1 の読み続ける規則（S-435 の形。名前より前で同じ行に閉じる誤り）で宣言を読み続け、名前解決に見せる。固有の impl のメンバは自分の語のとおりに記録する（第 38 組の S-593 の記録の規則に従う）。
