# S-568 std の変換の flow: 名前、フィルタの係数と演算の順

- 決定済みで戻さないもの: 組の全体は S-570 の下書きの頭（第 33・34 組で決めた §19.1 の三つの項、S-565 の R12、§14.2 の C の API の原則）。
- 論点: §19.1「フレームに集める…組込みの変換（`frame~` など）は持たない」「決めていないこと: std の変換の flow（名前、フィルタの係数と演算の順、§13.4 のビット一致。S-568）」。§13.4「`strict` では、全ての変換先が同じ入力に対して IEEE の演算についてビット単位で同じ出力を出す」「`std.math.sum` は…`xs[0]` から順に左へ畳む（演算順を固定し、ビット一致させる）」。
  flow は型引数を持たない（S-560 の p19 で E0002）。
  - (1) 一覧と名前（比ごとか）。(2) 係数と演算の順をどこに固定するか。(3) 型ごとの扱い。
- 今の実装: 変換の flow は書けない（`at (sample * 2)` は `q06` と同じ E0002、`.up~` は `r11` の E0812）。`std/dsp.onsa` の公開の項目は `sum` と `db_to_amp` だけ。
- 案:
  - (n1) 2 倍の二つ: `up2`（`x: F32 at sample` から `-> F32 at (sample * 2)`、補間）と `down2`（`x: F32 at (sample * 2)` から `-> F32 at sample`、帯域を制限して間引く）。4 倍などは利用者の flow の中で入れ子にする。置き場所は `std.dsp`。
    使い方: `down2~(sat~(up2~(x)).up~(2))`（`sat` は利用者の非線形の flow）。
  - (n2) 比ごとの組（`up2`・`up4`・`up8`、`down2`・`down4`・`down8`）と、フィルタの無い `hold2`・`dec2`。
  - (n3) 第 1 期の std には置かない。仕様の例（§17）に利用者が書く対を示す。
  - (c1) std の Onsa の本体が定義。係数はリテラル（16 進の浮動小数）で、和は書いた順。超越関数を通らないので、§13.4 のビット一致は本体から自然に出る。仕様には形（タップの数、位相、遅れのサンプル数）を書き、数は書かない。
    (c2) 仕様に係数と演算の順を書く。費用の要因: 数の置き場所が仕様と std の二つになる。
    (c3) 係数を窓付きの sinc から `const` で計算する。`const` の評価は Onsa で書いた libm で、機械に依らない（§13.4）。費用の要因: 係数が std の libm の移植の版に依る。
  - フィルタ: (fa) 線形位相のハーフバンドの FIR（遅れは速い側の `(タップ − 1) / 2`）。(fb) 多相の全域通過の IIR（遅れが小さく、位相は線形でない）。
  - (ty1) F32 だけ。F64 と `[F32; 2]` は、総称の flow（S-563 の新しい S の候補）が入るまで利用者が書く。(ty2) F32 と F64 の版を名前で分ける。(ty3) 総称の flow を待ち、今は置かない。
- 他言語: Cmajor（Language Reference のグラフの節）: オーバーサンプリングしたノードは「`sinc` interpolation is used in and out of the processor」、
  アンダーサンプリングは「`latch` is used on input connections, and `linear` is used on output connections」。sinc の係数とタップの数は文書に無い（未確認）。
- 推奨と理由: (n1)、(c1)、(fa)、(ty1)。確度: 低〜中。
  - (n1): マルチレートの主な用途（非線形の処理のオーバーサンプリング）に要り、std に無いと書き手（LLM）がそのたびにフィルタの表を書く。閉じた一覧が小さく、prelude の外なので後で足しても壊さない。(n3) は安全だが、仕様の例が長くなる。
  - (c1): 数の置き場所が std の本体の一つで、ビット一致は他の std の関数と同じ仕組みで保たれる。仕様に細かい表を入れない。(c2) は二か所、(c3) は係数が libm の版に結び付く。
  - (fa): 遅れが整数のサンプル数に決まり、ホストへ報告できる。(fb) は後で別の名前で足せる。
  - (ty1): 総称の flow が入るまで名前を増やさない。
  - あわせて決めること: タップの数と係数の値は std の作業（M5）で決め、そのとき仕様に形を書く。
  - 新しい S の候補: flow の遅れ（レイテンシ）を境界に出す形（ヘッダのマクロか `onsa interface`）。プラグインのホストは遅れの報告を求める（CLAP の latency の拡張など）。
- 影響:
  - 仕様: §19.1 のマルチレートの「決めていないこと」の S-568 を閉じる。std の一覧（`onsa primer --std` に出る）。§17 の例（P9。変換の flow を使う例を書くとき）。
  - 作業: M5（std と適合性テスト。`--backends all` でビット一致を確かめる）。変換の flow の実装（W7〜W10 のマルチレート）の後。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - (n)・(c)・フィルタ・型は一致した。
  - 段 1 の補い: flow は型引数も定数の引数も持てないので、比は名前になる。入れ子の `up2~(up2~(x)).up~(2)` の出力が呼び出し側で `sample * 4` と読めるかは §19.1 の文からは断定できず、仕様の例で一つ書いて検査を通すべき点である。
  - 段 2 は、フィルタ（(fa) 線形位相のハーフバンドの FIR か、(fb) 多相の全域通過の IIR か）を利用者の判断に出す（B-2）。どちらも誤りでなく、位相が直線で遅れが整数のサンプル数に決まる方か、計算量と遅れが小さい方かの、音の性格の選択である。段 1 と下書きは (fa)。
  - 新しい S の候補（flow の遅れを境界に出す形）: 段 2 は別の S にする（利用者の flow の遅れは、本体から数えるか書き手が宣言するかの設計が要る）。S-576 として登録した。
- 回答（2026-10-22、会話で利用者。51 回目。途中）:
  - B-2（フィルタ、(fa) か (fb) か）を出したところ、利用者が名前の論点を出した: 「modifier と同じ名前 `up2~` なのが良いのかどうかというのはちょっとあります。オーバーサンプリングのアルゴリズムがわかる名前の方が良いのではという別の論点があると思います」。範囲（修飾子の語 `up`・`down` を避けるか、アルゴリズムを名前に入れるか）を確かめている。B-2 は名前の後に出し直す。
  - 親が範囲を言い直した（(a) 修飾子の語 `up`・`down` を避ける、(b) アルゴリズムを名前に入れる）。利用者: 「(b)だけでも修飾子との区別はつくので問題ないと思います。(a)と(b)の例では末尾の数値がレート変換率であることが読み取れません（同種のアルゴリズムの2モード目とも読める）。また、標準APIの名前は特別な場合を除き10文字以内に納めたいです」。
    名前の条件: アルゴリズムが分かる、末尾の数が変換の比と読める、10 文字以内（特別な場合を除く）。`up`・`down` の語は使ってよい（(b) だけでよいという答えからの親の読み）。
  - 親が (N1)（`fir_up2`・`fir_down2`、後で足す IIR は `iir_up2`・`iir_down2`）と (N2)（末尾を `2x`）を出し、(N2) を推した。利用者: 「(N1) で十分類推できると思います。番号だとしたら `fir2_up2` という形になります（アルゴリズム名の後ろにつく）。up/downの後ろにつく数値が変換率であることは、修飾子との類似性から十分類推できると思います」。
    名前は (N1) で了承: FIR の版は `fir_up2`・`fir_down2`（`std.dsp`）。IIR の版を足すときは `iir_up2`・`iir_down2`。番号を付けるときはアルゴリズムの名前の後ろ（`fir2_up2`）。
  - B-2 を「第 1 期の std に FIR の版だけ (F) か、IIR の版も (F+I) か」に直して出し、親は (F) を推した。利用者: 「Onsaではコントロールレートをダウンサンプリングで扱うと決めているので、(F+I)両方必要だと思います。コントロール信号の変換にFIRは適切ではないからです」。
    親は、下書きと助言が制御のレートの変換を扱っていなかったこと（下書きは主な用途をオーバーサンプリングとした）を認め、範囲（ここでの IIR が B-2 のハーフバンドの多相の全域通過か、制御の信号の平滑の IIR か）を確かめている。
  - 親は、制御のレートでの変換の要る所（音声 → 制御は変換の flow、制御 → 音声の `at sample` は保持）と、B-2 の IIR（2 倍のハーフバンドの多相の全域通過）も制御の信号には合わないこと（比が 2 だけ、急なフィルタのオーバーシュート）を説明し、(1)「std に制御のレートの変換の flow が要り、FIR でない方式にする」の読みと、(2) 音声のオーバーサンプリングにも IIR の版を第 1 期に入れるかを問うた。
    利用者: 「1のみでも良いかと思いましたが、必要と感じたユーザーが独自に`iir_up2`などを足した場合、標準API側に同じ名前で足すと壊れるので、2(音声用のIIR)も考慮しておいた方が良いかもしれません」。
    (1) は了承として、制御のレートの変換を S-577（第 35 組）に分けて登録した。(2) は、§15.1 にグロブの import が無く std の名前は `use` で名指すときだけ見えるので、後で std に同じ名前を足しても利用者の flow は壊れないことを説明して、確かめている。
  - B-2: 利用者「なるほど、ではひとまず(F)でいきましょう」。(F) で了承: 第 1 期の std は FIR の版（`fir_up2`・`fir_down2`、線形位相のハーフバンド）だけを置き、IIR の版（`iir_up2`・`iir_down2`）は要ると分かったときに足す。制御のレートの変換は S-577。
