# S-667 flow の出力の struct の `priv` のフィールドが、生成項目の `Out` と `process` の引数に flow の可視性で出る（`pub struct P { x: F32, priv tag: F32 }` を返す `pub flow g`）

- 空白: §15.1 はフィールドを struct の可視性を継ぐか `priv` で狭めるとし（S-35）、見えないフィールドを読み書きすると E0303 とする。§11.6 は flow の出力の struct をフィールドごとの `Out` の欄と `process` の `inout` の引数に開く。
  `pub struct P { x: F32, priv tag: F32 }` を返す `pub flow g` は今の `check` を通り（`target/notes/64/g54-advisor/probe/privout.onsa`、終了コード 0）、`onsa interface` は `pub struct g.Out` の `tag: Buf[F32]` と `g.process(…, inout tag: Span[F32])` を出す。`Out` は別の型なので名前の可視性の違反ではないが、`priv` で守った不変条件が `Out` のフィールドとして外に出る。
  出力の型の位置の E0303 にするか、§11.6 に「`Out` のフィールドは出力の struct の可視性を見ない」と書いて許すかを書いていない。族「§15.1 の公開の宣言に書いた型の位置」（S-665）の外（名前でなくフィールドの話）。
- 決定（2026-11-16、利用者、159 回目、第 106 組）: (a)。`Out`・`Rendered` のフィールドと `process`・`process_inplace` の出力の引数は flow の可視性で出て、出力の struct のフィールドの `priv` を見ない。§11.6 に一文、§15.1 から指す。新しい診断は無く、実装は 0 行。
  理由: 境界から外へ出るのは flow が書いたバッファの中身だけで、外から struct の値を作る・書き換える道は無いので、`priv` が守る不変条件は守られる（漏れるのは読みだけで、利用者「見るだけで書き換えができない場合は許容できます」）。見出しの E0303 にする案は §4.1 が勧める newtype（`pub struct Hz { priv value: F32 }`）を出力にする `pub flow` を止め、実装も +15〜25 行要る（段 1、`target/notes/159/g106/advisor/`）。費用: `priv` のフィールドの名前がその flow の API（`Out`・`Rendered`、後の C の `<p>_out`）に出るので、struct の側でフィールドの名前を変えると flow の API が変わる。子の flow の `g~(x).tag` は E0303 で、境界の `g.render(…).tag` は通る差は、境界ではフィールドごとのバッファになることで説明する。
- 経緯: 64 回目（2026-10-24）、第 54 組の独立のレビューの段 1（onsa-advisor）が新しい S の候補として挙げ、親が再現した。関係: S-35、S-665、S-664、R-15。
