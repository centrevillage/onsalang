# S-655 パッケージ名の末尾の `_` が、公開ヘッダのインクルードガードに `__` を作る（`prefix = "vc_"` のパッケージ `voice_` の `VC_VOICE__H`。S-653 は `@export` の項目の名前だけを塞ぐ）

- 空白: §14.2 は公開ヘッダのインクルードガードを `<PREFIX><PACKAGE>_H` とし、`prefix` に `__`（C++ では予約の名前）を禁じる。§15.3 の `[package]` の `name` は `snake_case` の識別子（モジュールの名前と同じ規則、§2.3）で、S-650 の決定で末尾の `_` を書ける。
  そのため `prefix = "vc_"` のパッケージ `voice_` のガードは `VC_VOICE__H` になり、`__` を含む名前が公開ヘッダに出る。S-653 は `@export` の項目の名前の末尾の `_` だけを塞ぐ。
  読みは、パッケージ名の末尾の `_` を `@export` の項目と同じく誤りにする（`@export` の項目を出すときだけか、いつもか）、ガードの作り方を変える（パッケージのヘッダは `#pragma once` にする）、C++ の予約を受け入れる、に割れる。ファイル名（`<prefix><package>.h` など）は C の識別子ではない。
- 決定: 決定（2026-10-24、利用者が了承。63 回目）: パッケージのヘッダ（`<prefix><package>.h`）は二重の取り込みを `#pragma once` で防ぎ、インクルードガードのマクロ `<PREFIX><PACKAGE>_H` を置かない（`__` を含む識別子が生まれない。E1011 の重なりの検査からガードを外す）。
  `onsa.h` と `onsa__runtime.h` はマクロのガードのまま（写しが二つあっても一つだけを読み、`ONSA_ABI_VERSION` で版を確かめる仕組みのため。実害がある所だけの例外）。パッケージ名の規則は変えない（`voice_` は書ける。S-653 のような名前の例外を足さない）。
  代償: `#pragma once` は規格に無く、対応しないコンパイラでは二重に読まれうる。同じパッケージのヘッダの写しを二か所から一緒に取り込むと、再定義の誤りになる。実装は W10-02（パッケージに一つのヘッダを作るとき）。
- 経緯: 63 回目（2026-10-24）、組 52 の仕様への反映（`7c4ba06`）の文書の点検（onsa-docs）が見つけ、親が §14.2 と §15.3 の文で確かめて登録した。関係: S-653、S-650、S-641（`prefix` の既定）。
  登録の後に利用者が 「includeガードは `@pragma once` は使えないんでしたっけ？」と問い、親が確かめた結果を示した: `#pragma once` を採らなかった理由の記録は無い（ガードは C-101 と S-112 で入った）。`onsa.h` の写しが二つあると、`#pragma once` では clang は中身が同じでも、gcc-15 は中身が違うと型の再定義の誤りになり、マクロのガードの仕組み（§14.2 の版の検査）が壊れる。
  パッケージのヘッダは gcc-15・clang の C99 と C++11 の `-pedantic -Wall -Wextra` で警告が無い（入力は 63 回目の scratchpad の `pragma/`）。
  利用者: 「そうですね。実害がある時だけ例外を採用する判断で、パッケージだけ `@pragma once` は良いと思います。」親が範囲を例で言い直し（上の決定の文）、利用者が「良いと思います。」
