# S-632 族: `@param`・`@host`・`@latency` の責任範囲

- 位置付け: 族「`@param`・`@host`・`@latency` の責任範囲」の三件。族の規則の S-632 を先に置いた。S-625 は族の規則（軸 A）から決まる。S-588 は、誤りの段は族の規則（軸 B）で決まり、誤りにするかと `e` の条件だけを項目にした。
  S-625 の期限は W7-03（生成する API の Onsa の側）、S-588 の期限は W10（W10-08）。
- 決定済みで戻さないもの:
  - §6.5 の 1 文目の範囲（S-624）: 属性は、ターゲットに固有の事情が関わらない段までのプログラムの解釈（型と計算の結果）を変えない。C との境界（§14）はターゲットに固有の事情に含める。変えるのは、この範囲に生成する API の読み出しがどう当たるかの扱いだけである。
    ただし案 (v) は段の分け方そのものを改める案なので、(v) の中でだけ 1 文目の書き直しを扱う（下の案 (v) の e）。
  - §6.5 の 2 文目の受理に関わる 4 つ（位置と値の検査、export する flow の `block` の入力の `@param` か `@host`、E0819、`@repr(c)` の FFI）。一覧に無い属性とその場所に付けられない属性は E0005（§6.5）。
  - `@param` の値の型と評価（S-87: `const` の初期化式と同じ規則、E0401・E0809・E0419）、ID と数値の ID（S-104）、プラグインの条件（S-581: `min`・`max` はそのターゲットのビルドで E0809、AU の `F64` は E0200）。
  - `@host` の種類の一覧・型・既定の値、ラッパーの値の確かめ（S-575 の (hv2)）。`@latency(e)` は一番外の flow の宣言だけで、子の宣言は合成せず、構造から決まる遅れは `onsa audit`（S-576 の (r-a)、形は S-586）。
  - 同じ属性を一つの場所に重ねる形（`@host(tempo) @host(beat) x`、`@latency(1) @latency(2) flow`）は族「§6.5 の同じ属性の重なり」（S-490・S-495）で、この組では扱わない。
    今は `@param(default: 0.5) @param(default: 0.25) a` も `@fp(relaxed) @fp(relaxed)` も診断なしで通る（`target/notes/60/gap50/probe/p/e1.onsa`・`e2.onsa`）。
  - S-584（凍結の範囲）は論点にしない。
- 改めうる前提として扱うもの: S-575 の「`params_default()` は `@host` の欄を既定の値にする」、S-576 の「生成する API の `f.latency(s)`」、S-112 の生成する API の形。案ごとに、どの文をどう変えるかを「影響」に書いた。
- 出所と目的:
  - `params_default()` は Draft 0.2 の §11.6 に「全ての Ctl 入力に @param の default がある場合」として入り、§11.7 の用途の行に「IDE の自動 UI、プラグインのパラメータ情報、`params_default()`、C API のメタデータ表」と並んだ（`history/onsa-lang-spec-0.2.md` 711・739 行）。
    入れた理由の記録は、`history/onsa-0.2-changes.md`・`review-draft-0.1.md`・`review-draft-0.2.md` に無い（`default` の語が一つも無い）。使う所から読むと、目的はホストのコード（§17 の `render_vowel`、`Poly.new`、C の `onsa_voice_params_default(&params)`）が既定の値を書き写さずに `Params` を作ることである。
    同じ 0.2 の §11.7 は「Onsa の中からの呼び出しでは飽和させない（メタデータは宣言であり、意味を変えない）」とも書き、属性が意味を変えないという考えと並んでいた。後に S-87 が `default` を必須にし、S-575 が条件に `@host` を足した。計画では T3-5（flow の降下）、T4-3（C の wrapper）、T6-1（WASM の export）に `params_default` がある。
  - `latency(s)` は S-576 の下書きの (o2) で、C の `<p>_latency` と並べて生成する API に置いた。下書きの理由は定数か関数か（サンプルレートで変わる先読み）の比べで、Onsa のコードが読む場面は挙がっていない。値を使うのはホストへの報告（§14.3 のラッパー）である。
  - 目的が今も Onsa の側に当たるか: `params_default()` の使い手は仕様の例（§16.1・§17.4・§17.6）とテスト（`tests/spec/examples/voice.onsa` など）にある。一方、Onsa のコードは `@param` の値に書いた `const` を同じ名前で読める（§11.7、S-87）ので、書き写さない目的は `const` でも満たせる。
    C のホストは Onsa の `const` を読めないので、C の `<p>_params_default` には同じ代わりが無い。
    `latency(s)` の使い手は、リポジトリの事例に無い（`tests/spec/flow/generated_api.onsa` は §11.6 の一覧の写し）。
    `const` で共有する形は、入力ごとに `const` を置いて `@param` の値とリテラルの両方から指す書き方で、`@param` の値を字面に直接書いた flow（§17 の例）には当たらない。`const` を `@param` の値に書けるのは W9-03 の後である（今は E0809、`p/e4`）。
- 試した入力: dev `3c8f87a` の release の `check`・`test`・`interface`・`build`。入力と出力は `target/notes/60/gap50/probe/`（単一のファイルは `p/`、export のパッケージは `pkg/`）と `target/notes/60/gap50-advisor/probe/`（助言の担当の `pkg_missing/`・`pkg_priv/`）。
- 論点: §6.5「属性は、ターゲットに固有の事情が関わらない段までのプログラムの解釈（型と計算の結果）を変えない付与情報である: …UI とホストのための情報（`@param`、`@host`、`@latency`）…」。
  一方 §11.6 の `fn voice.params_default() -> voice.Params`（`block` の入力の全てに `@param` か `@host` がある場合）と `rt fn voice.latency(s)`（一番外の flow の `@latency(e)`、無ければ 0）は、インタプリタと `onsa test` で呼べる。
  属性を外すと、呼ぶコードが誤りになるか（`params_default` が無い）、計算の結果が変わる（`default` の値、`latency` の 0）。
  §6.5 は、どの段がこれらの情報を持ち、使い、誤りを出すかを書かない。誤りの段も、§11.7 が「プラグインに出す flow の…`min`・`max` を要する（無ければそのターゲットのビルドで E0809）」と一か所だけ書き、他（export の必須、`@host`、`@latency`）は書かない。

- 今の実装: 表の「今の実装」の列のとおり。属性の値を Onsa のコードが読むのは、今は 18 行の `params_default()` だけである（`a.onsa` は `test a "pd" ok`、終了コード 0）。
  export の必須（5 行）は `onsa check .` が 0 で、`onsa build --target host` が E0809 を出す。`@param` の自身の誤り（2 行）は `onsa check` が出す。
  - 生成する型を、flow より前の `const` と fn のシグネチャで使うと E0302「cannot find `g.Params`」になり、flow の後に書くと通る（`p/f2.onsa`・`f1.onsa`）。下の「別の問題」に書いた。
- 案: 二つの軸に分けて並べる。軸 A は Onsa のコードから読めるか、軸 B は誤りの段である。軸 A の案は (i)〜(v)、軸 B は (e1)〜(e3) で、族の規則は A と B の組である。
  - (i) 今のまま。Onsa のコードは `params_default()` と `latency(s)` で属性の値を読める。§6.5 に一文足す（例:「属性の値を Onsa のコードが読めるのは、生成する API の `params_default`（`@param` の `default` と `@host` の既定の値）と `latency`（`@latency` の値）だけで、その値と `params_default` の有無は属性で決まる」）。
    仕様: §6.5 に一文。実装: 増えない（`params_default` は今ある。W10-08 の `latency` の Onsa の側は隠れた欄を読む関数で、約 20 行の見込み）。保守の費用の要因: 属性を足すたびに、Onsa の読み出しを持たせるかを決める。属性の有無で名前空間の項目の有無が変わる形（`params_default`）が残る。
  - (ii) 属性の情報は、ターゲットの段（C の API、ラッパー、WASM）と道具（`onsa interface`、`onsa test --flows`、`onsa play`、IDE）だけが読む。§11.6 の一覧から `params_default` と `latency` を外し、§6.5 に「属性の値は Onsa のコードから読めない」の一文を足す。
    要る所は、`Params` のリテラルで全ての欄を書く（§4.4 の struct リテラルは全てのフィールドを書く。`..` で残りを埋める形は無い）。既定の値を一か所に置くには、`const` を `@param` の値とリテラルの両方で使う（§11.7、S-87）。
    仕様: §11.6 の 2 行と `latency` の段落を C の `<p>_latency` の段落に、§11.7 の用途の `params_default()` を C の `<p>_params_default` に、§16.1・§17.4・§17.6 の例を書き直す。
    実装: sema の名前空間から `params_default` を外す。Core の降下と C の `_params_default` は今 sema の項目を引いて作るので、Core の中の関数としては残す（約 10〜20 行）。`latency` は C の側だけ作る。事例の書き直しは 5 ファイル（`影響`）。
    保守の費用の要因: Onsa のホストのコードとテストが既定の値を別に書く。W9-03 より前は `@param` の値に `const` を書けない（今は E0809、`p/e4`）ので、それまでは値が二か所に書かれる。
  - (iii) 属性ごとに分ける。
    - (iii-a) `params_default()` は残し、`latency(s)` は外す。分ける線は「生成する API は、Onsa のコードが flow を呼ぶ引数を作る値を持ち、ホストに報告するだけの値は持たない」。遅れは、範囲・単位・ID（C の `_param_info` にだけある）と同じ側に入る。
      仕様: §6.5 に `params_default` だけを挙げた一文、§11.6 の `latency` の行を外す。実装: W10-08 の Onsa の側が要らない（減る）。保守の費用の要因: (i) と同じく `params_default` の有無が属性で決まる。線の言葉（引数を作る値か報告する値か）を後の属性ごとに当てる。
    - (iii-b) `latency(s)` は残し、`params_default()` は外す。分ける線は「Onsa のコードが同じ値を `const` で書ける値（コンパイル時の `default`）は読ませず、`init` で決まる値（サンプルレートで変わる遅れ）だけを読ませる」。
      仕様: §6.5 に `latency` だけを挙げた一文、§11.6 の `params_default` を外す（例の書き直しは (ii) と同じ）。実装: (ii) の `params_default` の分と W10-08 の `latency` の分。
      保守の費用の要因: `e` を fn に分ければ Onsa のコードも同じ値を作れるので、線が値の性質でなく書き方の手間で決まる。
  - (iv) 値を属性から切り離す。意味を持つ部分を属性でない書き方にする。
    既定の値は入力の宣言（仮に `f0: F32 at block = 110.0`、または語 `default 110.0`）、遅れは flow の宣言の節（仮に `-> F32 at sample latency look(sample_rate())`）にし、`@param` から `default` を、§6.5 から `@latency` を外す。`params_default()` と `latency(s)` は属性でない宣言を読むので、§6.5 の文に当たらない。
    仕様: §11.1 の文法、§11.6、§11.7（`default` の必須を入力の宣言へ）、§6.5、§2.2（語を足すなら予約）、fmt の正規形。実装: 構文解析、fmt、sema、Core、事例（数百行の見込み）。
    保守の費用の要因: `= 110.0` は、C++・Python・Swift・JavaScript で呼び出しの引数を省ける既定の引数と読まれ、Onsa で `voice~(…)` の引数を省けないなら検査を通るのに意味が違う形になる（§0.3 の規則 4）。語にすればキーワードが増える。`@host` の欄の既定の値は種類で決まるので、`@host` も属性の外へ出すかが残る。
  - (v) 段で分ける。
    - コンパイラ部（字句解析から Core IR の生成まで）は、属性で解釈（型、名前の有無、計算）を変えない。属性自身の位置と値の検査（E0005・E0809・E0815・E0419）はコンパイラ部が行う。
    - トランスパイラ部（Core IR から C・WASM を作る所、C の API のヘッダと表、プラグインのラッパーの生成）とランタイム（生成したものの実行と、Onsa のコードの実行。インタプリタを含む）は、属性の値を読んでよい。
    - Onsa のコードは、ランタイムに、リフレクションの API で属性の値を読める。使い方の例は、flow を使う側の fn が、C の API やラッパーと同じく `@param` の情報を読んで入力を確かめる形（下の例 (5)）。
    - リフレクションの API は共通の形にし、属性の有無によらず在り、定義が無ければ空を返す。属性の有無で生成する名前の有無が変わる形（今の `params_default()`）はとらない。
