# S-580 プラグインの出力の全体の形: `kind = "clap"`・`"vst3"`・`"au"` が生成するもの、SDK と使用許諾、マニフェストの書き方

- 決定済みで戻さないもの: 組の全体（第 36 組の全ての下書きに当たる）:
  - 第 35 組の境界（§19.1 の今の作業ツリーの字。利用者の了承の前の見込みで、論点に戻さない）: イベントの入力は印の付いた一つの列 `<p>_event`（`pos`・`input`・union `v`）で、`_process` は常に `params` の後に `events`・`events_len` を取る（S-570、回答の (3b)）。
    出力のイベントは呼び出し側が容量を持つ `<p>_events_out` で、上限は `<P>_OUT_EVENTS_PER_FRAME × frames + events_len`（S-571）。
    境界のイベントの型は `@param` と同じスカラ・`()`・`midi.Message`（MIDI 1.0 を `uint32_t` に詰める）・`transport.Event`（Start / Stop / Continue）だけ（S-572）。境界の `sample / N`・`sample * N` は E0810（S-574）。std の `fir_up2`・`fir_down2` は遅れのサンプル数を仕様に書く（S-568）。

- 案:
  - 生成するもの:
    - (g1) C のソースまで（flow の C、ラッパーの C、記述のファイル）。束（bundle）のビルドと配置は利用者。費用: 束の形（macOS の `Contents/MacOS` と `Info.plist`、Windows・Linux の配置）を利用者ごとに書く。
    - (g2) (g1) に加え、ホストの `platform` で PATH の `cc` を使い束（`.clap`、`.vst3`、`.component`）まで作る。束は `staticlib` の `.a` と同じく外部のツールチェーンの出力で、同一性の約束の外（§15.3）。費用: OS ごとの束の形と `Info.plist` の生成、クロスは E0200 のまま。
    - (g3) CLAP だけを Onsa が出し、VST3 と AU は外の変換の層（clap-wrapper）に任せる（`vst3`・`au` は CMake の雛形を出す）。費用: CMake、C++ のコンパイラ、VST3 の SDK と AudioUnitSDK が要り、`onsa build` だけでは完結しない。clap-wrapper の版に追従する（二つ目の置き場所）。
    - (g4) ラッパーを生成しない。§15.3 の `kind` の一覧から `clap`・`vst3`・`au` を外し、プラグインは `staticlib` と利用者の枠組み（JUCE、nih-plug、DPF、手書き）で作る。費用: 実装は無いが、§0.1・README の「プラグインへの組み込み」を利用者の手に移す。
  - ラッパーの作り:
    - (w1) flow ごとに、形式ごとのラッパーの C を丸ごと生成する。費用: 三つの形式のコードが Rust の生成器の中の雛形になり、形式の変更を Rust で直す。flow の形ごとに出力を確かめる。
    - (w2) 形式ごとの固定の C（ランタイムと同じくコンパイラに埋め込む）が、公開の C の API の表だけを読んで動く。費用: A3・A4 の表と一様な入口が公開の ABI になり、後で変えにくい。固定の C は flow によらず確かめられ、手書きのホストも同じ表を使える。
    - (w3) 形式ごとの固定の C と、flow ごとに生成する内部のつなぎ（公開しない一様な入口と表）。費用: 生成器はつなぎ（入出力の写し、`Params` の欄の読み書き、イベントの写し）だけを書き、固定の C は flow によらず確かめられる。つなぎの形はコンパイラの版の中の約束で、公開の ABI は増えない。
  - SDK と使用許諾:
    - (s1) CLAP のヘッダ（MIT）と VST3 の `vst3_c_api.h`（BSD の三条項の形）をコンパイラに埋め込み（std と同じ扱い）、使用許諾の文を出力に置く。AU は macOS の SDK のヘッダとフレームワークをシステムから使う。費用: SDK の版が出たときに埋め込みを更新する。
    - (s2) 利用者がマニフェストで SDK の経路を渡す（新しいキー）。費用: 閉じた一覧にキーを足し、SDK の版の違いで出力が変わり、ビルドがマニフェストの外の物に依る。
    - (s3) 要る宣言を Onsa が自前で書き、SDK の文を持たない。費用: CLAP の構造体の配置、VST3 の vtable の並びとインタフェースの ID を写し、誤りを見つけにくい。
  - AU の版: (au2) AUv2（C の `AudioComponentPlugInInterface`、`.component` の束）。(au3) AUv3（Objective-C の `AUAudioUnit` の子クラスと、包む app の中の app extension）。費用: (au2) はプロパティの数が多い（形式、パラメータ、状態、遅れ、尾、MIDI）が C で書ける。(au3) は Objective-C のコンパイルと app の束が要る。
  - マニフェスト（例は下）:
    - (m1) ターゲットごとに `flow` と識別子を書き、一つのターゲットが一つのプラグイン。費用: 三つの形式で同じ記述を三度書き、ID の食い違いを照合する規則が要る。
    - (m2) パッケージの表 `[[plugin]]` に flow と記述を書き、プラグインの種類のターゲットは全ての `[[plugin]]` を一つの束に入れる（CLAP の工場の `get_plugin_count`、VST3 の工場のクラスの列、AUv2 の `Info.plist` の `AudioComponents` は、どれも複数を持てる）。費用: 新しい表とキー。
    - VST3 のクラスの ID（16 バイト）は、どちらの案でも `id` から決まった hash で作るか、書かせるかを決める。AU の四文字の型・副型・作り手の符号は意味のある値を作れないので書かせる。
  - 時期: (t1) 形をこの組で決め、第 1 期は C の API に要るもの（A1・A2 など）だけを W10 に入れ、ラッパーは第 2 期（`kind` は E0200 のまま）。(t2) CLAP だけを第 1 期（W10 の後の新しい作業）、VST3・AU は第 2 期。(t3) 三つとも第 1 期。
    費用: (t2)・(t3) は確かめの器が要る（CLAP のホストか検証の道具を落として回す、VST3 の検証の道具は SDK から作る、AU は `auval` がこの機械にある）。

```toml
[[plugin]]                  # (m2) の例。値は例
flow = "dsp.syn"            # [export] の flows にあるもの
id = "com.example.syn"      # 逆ドメインの形。CLAP の id
name = "Syn"
vendor = "Example"
version = "1.0.0"
category = "instrument"     # "effect"、"note-effect"
au = { subtype = "Syn1", manufacturer = "Exmp" }   # au のターゲットでだけ要る。型は category から決まる

[targets.plug]
kind = "clap"
platform = "host"
```

- 推奨と理由: (g2)、(w3)、(s1)、(au2)、(m2)、(t1)。確度: (1) 中、(2) 低〜中、(3) 中、(au) 中、(4) 中、(5) 中。
  - (g2): `kind` はプラグインを名指すので、読み込める束までを出すと名前どおりになる。`staticlib` が既に PATH の `cc` と `ar` を使うので、同じ扱いで規則は増えない。C のソースも残すので、利用者は自分の手順でもビルドできる。
    (g1) は束の形を利用者ごとに書かせる。(g3) は C++ と二つの SDK と CMake に依り、`onsa build` で完結しない。(g4) は実装が無い代わりに、主な機能を仕様から外す。
  - (w3): 公開の ABI をラッパーの都合で増やさず、形式ごとの差を固定の C の一か所に閉じ込める。つなぎはコンパイラが形を知っているので小さい。
    (w1) は三つの形式のコードを Rust の雛形に持ち、形式の直しと flow の形の直しが同じ所で絡む。(w2) は表を公開の ABI にするので、後で形を変えにくい（汎用のホストの要る A3 は、この案と別に決められる）。
  - (s1): ビルドはマニフェストの外を読まず（§15.3 のハーメティック）、SDK の版が出力から決まる。CLAP は 1.x の ABI を保ち、VST3 のインタフェースは変えずに足す形なので、更新は新しい機能を使うときだけで済む。
    (s2) はビルドを手元の SDK の版に依らせ、(s3) は ABI の写しの誤りを生む。使用許諾は MIT と BSD の形なので、文を出力に置けば埋め込める。
  - (au2): C だけで書け、生成するものの言語が増えない。(au3) は後で別の `kind` の値として足しても今のプログラムを壊さない。
  - (m2): 三つの形式で記述が一度で済み、ID が食い違わない。VST3 のクラスの ID は `id` から決まった hash で作る（§11.7 の数値の ID と同じ考え方で、書き手が選ぶのは文字列の ID だけになる）。移す前の製品の ID に合わせるキーは、A-13 と同じく足しても壊さないので候補にとどめる。
    AU の符号は書かせる（au のターゲットで無ければ E1104）。
  - (t1): 第 1 期は言語と C の API を固める段で、この組の決定の C の API の側（A1・A2、必要なら A3）は W10 に入るので、第 1 期でも手書きのラッパー（§14.2 の第一の経路）は書ける。ラッパーは確かめの器（ホストや検証の道具、OS ごとの束）が要り、後で足しても E0200 が動くようになるだけで壊さない。
    利用者が第 1 期にプラグインを求めるなら、(t2) が費用の最も小さい形である（CLAP は C の ABI で、ヘッダが小さい）。
  - あわせて決めること: `[[plugin]]` の `flow` は `[export]` の `flows` に要る（無ければ E1103）。キーの全ては閉じた一覧に置く（`id`・`name`・`vendor`・`version`・`category` は必須で、無ければ E1104）。`category` は閉じた一覧（`instrument`・`effect`・`note-effect`）。
    `[package]` に版のキーは足さない（版はプラグインの記述にだけ要る）。
  - 新しい S の候補: プラグインの独自の画面（CLAP の `gui`、VST3 の `IPlugView`、AU の画面）。§16 の GUI の文脈とパラメータの受け渡しを一緒に決める。
