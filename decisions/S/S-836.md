# S-836 E1104 のキーの挿入の候補を、インラインの表で書いた表（`package = { name = "p" }`）にも出すか（§18.1 の「値が決まるときはキーの挿入を修正候補にする」）

- 空白: §18.1 は「E1104 は必須のキーが無いで、値が決まるときはキーの挿入を修正候補にする」と書き、§15.3 の表で値が一つに決まるのは `edition`（`"2026"`）だけである（U3 の `prefix = "<package>_"` も同じ形、§14.2）。挿入を書く場所の形を書かない。
  TOML では表を四つの形で書ける。見出し（`[package]`）なら次の行に `edition = "2026"` を足せ、表が無ければ末尾に `[package]` と `edition = "2026"` の行を足せ、ドットのキー（`package.name = "p"`）なら最上位に `package.edition = "2026"` の行を足せる。
  インラインの表（`package = { name = "p" }`）は行を足して広げられず（`[package]` も `package.edition` も TOML の誤り。98 回目に親が `tomllib` で確かめた）、`}` の前の行の途中に `, edition = "2026"` を足すしかない。
  設計メモ（`target/notes/95/w402/memo.md` の 2.2）は、マニフェストの候補を行を丸ごと足す形だけとし、`diagnostic_contract` の `onsa.toml` の境界を行の頭とファイルの終わりにした。断片（`.onsa` のコメントの行）では、行の途中に足すとコメントのトークンの中になり、Onsa の字句の境界の判定に当たらない。
  今（W4-02 U2b1 の後）は `edition` が欠けても誤りにならず、インラインの表とドットのキーの `package` も通る（`P98/bin/onsa-632f980` で確かめた）。読みは (a) 行で足せる形だけに候補を出し、インラインの表は候補なし (b) インラインの表も `}` の前に足す、に割れる。どちらも E1104 は出し、通るプログラムは変わらない。

- 経緯: 98 回目（2026-11-01）、W4-02 U2b2 の票を書く前に親が見つけた。U3 の `prefix` の挿入（`export = { … }`）にも当たる。
