# S-528 fmt が改行を足す閉じ括弧を最後の要素の行に書いた形の、閉じ括弧の後ろの行末のコメント

- 空白: ブロック形の並びで、閉じ括弧を最後の要素と同じ行に書き、その後ろに行末のコメントがある形（`g(` 改行 `a,` 改行 `b)  // c`）。§3.4 は「行末のコメントは、その行の要素の後ろ（補った `,` の後ろ）」とし、閉じ括弧がその行で要素の後ろにあるときを書かない。
  今の fmt は閉じ括弧を独立の行に移し（§3.2）、コメントを閉じ括弧の後ろに残す（`b,` 改行 `) // c`。struct リテラルの `y: 2 }  // c` も同じ）。gate の `fmt-comments` は `b, // c` を求めて落とす（break の摂動と合わせた入力の約 2 %。閉じ括弧が `)` のときだけで、道具の読み違いだった）。
  W3-11/t（U4）が見つけた（2026-10-14）
- 提案: 決定（2026-10-14、利用者が ID を挙げて推奨の (2) を了承。下書きと Fable が一致、第 31 組）: 今の挙動。行末のコメントは書かれた行の最後のコードの後ろに残り、fmt が改行を足して行を分けるとき（ブロック形の閉じ括弧、複数行のブロックの `}`）もそうする（`b,` 改行 `) // c`）。コメントを越えて動くのは前の要素の後ろへ移す `,` だけ。
  理由: S-497 の (β) と同じ一つの規則で、印字器に条件が要らない。`spec/tools.md` §3.4。fmt の変更は無く、gate の判定（`tools/fmt_props.py`）を W3-11 の U4 で直す
