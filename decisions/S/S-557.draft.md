# S-557 修飾子の重ねがけと順

- 決定済みで戻さないもの: 無し。§19.1 の「節の順（`when` が先）」は、入れるときに決めることとして残っていた。
- 論点: §19.1 は「節の順（`when` が先）」を入れるときに決めることに挙げる。X-7 は、`saw~(f0).when(flag1).when(flag2)` を「flag1 && flag2 の時 active?」、`reset_if` の二度を「flag1 || flag2 の時 reset?」と問う。
  - 同じ修飾子を二度かけた形の意味（積か和か、誤りか）と、`when` と `reset_if` の順で意味が変わるか。順で変わるなら両方を認めるか、一つに限るか。
  - 修飾子を「左の全体を包む」と定義すると（合成の読み）、`x.when~(a).when~(b)` は `x.when~(a && b)` と同じ出力になり、`x.reset_if~(r1).reset_if~(r2)` は `x.reset_if~(r1 || r2)` と同じになる。
    `x.when~(c).reset_if~(r)` は外側の初期化なので止まっている刻みにも初期化し、`x.reset_if~(r).when~(c)` は内側なので動く刻みにだけ初期化する。
  - 一方、組み立ての型（ビルダ）の読みでは、同じ設定の二度は後の値が勝ち、設定の順は意味を持たない（下の他言語）。読みが二つに割れる。
- 今の実装: どの形も E0413 か E0812 で、意味を持たない（S-555 の「今の実装」）。
- 案:
  - (a) 合成の読みで、順も重ねがけも自由。追加の規則は無い。実装: 修飾子の並びを内側から順に包むコードを作る。費用の要因: 組み立ての読みで書いた形が、誤りにならずに別の意味で通る。
  - (b) 合成の読みで、同じ修飾子は一度だけ。順は両方を認め、意味が違う。実装: (a) に重ねがけの検査。費用の要因: 順の読みの割れは残る。
  - (c) 合成の読みで、順は `when~` の後に `reset_if~` の一つだけ、各々一度だけ。逆の順と重ねがけは誤りで、修正候補を読みごとに並べる。
    - 逆の順 `x.reset_if~(r).when~(c)`: 候補 1 は `x.when~(c).reset_if~(r)`（止まっている間も初期化）、候補 2 は `x.when~(c).reset_if~(r && c)`（動く刻みだけ初期化。合成の読みの意味をそのまま保つ）。
    - 重ねがけ `x.when~(a).when~(b)`: 候補 1 は `x.when~(a && b)`（合成の読み）、候補 2 は `x.when~(b)`（後の値が勝つ読み）。`reset_if~` は `||` と後の値。
    - 実装: 修飾子の並びの検査と候補。flow の計画とコードは固定の二段（`when` の内側、`reset_if` の外側）で足りる。費用の要因: 修飾子を足すときに順の表に一行足す。
  - (d) 順を問わない（集合の読み）。どちらの順も同じ意味にし、fmt が並べ替える。重ねがけは誤り。費用の要因: 合成の読みで書いた `x.reset_if~(r).when~(c)`（動く刻みだけ初期化のつもり）が、誤りにならずに別の意味で通る。
- 他言語: rustc 1.94.1: 組み立ての `current_dir` の二度は後の値が勝ち、反復子の `filter` の二度は積、`skip(2).take(3)` と `take(3).skip(2)` は違う結果（`[2, 3, 4]` と `[2]`）になった（`probe/lang/chain.rs`）。
  Node v26.11.1: `URLSearchParams.set` の二度は後の値、`filter` の二度は積（`probe/lang/chain.js`）。faust-rs の覚え書きは、`upsampling` と `downsampling` の入れ子が係数を合成するとする（`docs/ondemand-note-en.md`）。
  Lustre の初期化（modular reset）の文献は Bourke・Brun・Pouzet の SCOPES 2018（doi:10.1145/3207719.3207732）で、本文は読めていない（未確認）。
- 推奨と理由: (c)。確度: 中。
  - 既存の言語の連鎖は、組み立ての読み（後の値が勝つ、順は意味を持たない）と合成の読み（積、順が意味を持つ）に割れる。割れる書き方は誤りにし、読みごとに候補を並べる。(a) と (d) は、片方の読みで書いた形が別の意味で黙って通る。
  - 順を一つに限っても、書ける意味は減らない。止まっている間も初期化するのは `x.when~(c).reset_if~(r)`、動く刻みだけ初期化するのは `x.when~(c).reset_if~(r && c)` で書ける（合成の読みで逆の順と同じ出力）。
    `when` を先にする順は、S-170 の節の順（`seq~(tick) when running reset_if start`）と同じで、MIDI の Start（初期化と再開を同じ刻み）を素直に書ける。
  - 意味は合成の読みで一度だけ定義する（各修飾子は左の全体を包む）。順の表は「書ける並び」だけを決め、意味の規則を増やさない。後で修飾子（`default` など）を足すときも、包む意味と表の一行で足りる。
  - (b) は意味を持つ二つの順を残し、組み立ての読みの書き手が順の違いに気付かない。
  - あわせて決めること（修飾子の無い呼び出しとの関係）: 修飾子の間に他の後置（`.l` のフィールド、`[0]` の添字）を挟んだ形（`pan~(x).l.when~(c)`）は、受け手が flow の呼び出しでないので S-555 の E0812 になる。
- 影響:
  - 仕様: §19.1 に、修飾子の意味（左を包む）、書ける並び（`when~` の後に `reset_if~`、各々一度）、`r && c` の書き方の note を書く。
  - 診断のコード: 並びの誤りの割り当ては決定の後に親が決める（候補: 誤解を示す書き方の E0020、または修飾子の `~` の E0811 / E0812 の族）。
  - 作業: 名前の段か flow の検査（W7-04）で並びを検査する。修正候補の収束は `onsa_cases --fix-loop` で両方の候補を確かめる。
  - 事例とテスト: 無い（新しい形）。テストベクトルの保留の節は関係しない。
  - 第 34・35 組への影響: イベントを `reset_if~` の条件に書く形（第 34 組）は、この並びのまま使える。
- 独立のレビュー（2026-10-20、助言の担当の二段）:
  - 段 1 は下書きと一致した（中〜高）。事前検討の問い（`when` の二度は `&&` か、`reset_if` の二度は `||` か）への答えは、既存の言語で読みが割れる（rustc と Node で確かめた）ので誤りにし、両方の読みを修正候補に並べる、である（`rules/criteria.md` 7.4）。
  - 積の意味が要るときは、flow に分けて入れ子にすれば書ける。修正候補はどれも当てた後に書ける並びの一つになり、一度で収束する。
  - 高階の補い（2026-10-20、別の助言の担当の二段）: 「同じ修飾子は一度だけ」は組込みの例外にせず、全ての修飾子（将来の利用者の修飾子を含む）の一般の規則にする。順の固定は、読みが割れると分かっている組（今は `when` と `reset_if`）だけの表にし、表に無い組はどの順でも書けて意味は合成で違う。
    制限は直接の連鎖にだけ当たり、flow に分けた入れ子・将来の高階や `self` の修飾子の本体の中では制限が無く、意味は常に合成（`gate::[saw]~(f0, c).when~(d)` の本体の `src~(f0).when~(c)` は `c && d` で動く）。
- 回答（2026-10-20、会話で利用者。47 回目）:
  - B4: (a)（合成の読みで、順も重ねがけも自由。並びの表と修正候補と「一度だけ」の規則は置かない）。理由（利用者）: メソッドを複数回連鎖したときの意味は言語で制限していない。`x = x + 2` と `x = x + 1 + 1` が両方正しいのと同じく、同じ機能の組み合わせが別の書き方と同じ意味になるのは言語の制約の話でない。
  - 親の見直し: P2 は同じことをする機能や構文を複数作らないという原則で、組み合わせの結果の一致には当たらない。7.4 は構文の読みが言語ごとに割れる書き方の規則で、連鎖の繰り返しの意味はメソッドの定義で決まる（Rust の `Command` の後の値が勝つのは `current_dir` の定義）。下書きと助言の (c) の理由はこの二点の当てはめが誤りだった。
  - あわせて: §19.1 の「節の順（`when` が先）」の論点は「どちらの順も書け、意味は合成で決まる」で閉じる。`when~` を重ねたときの保持の欄の名前（§11.6）は、反映のときに決める。S-559 (2) の理由の文を、合成の読みに合わせて直した。
