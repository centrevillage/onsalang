# S-1261 `onsa test` の `assert` の比べ（`==`・`!=`・`<`・`<=`・`>`・`>=`）が失敗したとき、両辺の値を出す

- 位置付け: S-1261（`onsa test` の `assert` の最上位が比べで失敗したとき、両辺の値を出す）の、W8-13 の着手の前に決める残りの点。族の規則の S は立てない（同じ族の未決の S は無い）。
  項目は票の G1〜G6 に、細部の G7 を一つ足した（G5 の中に入れた `Char` の形のエスケープは、`Char` の値の行の形と別に、タプルなどの中の `Char` で必ず出るため。S-270 の一部に当たる）。
- 決定済みで論点に戻さないもの:
  - 採ること、値を出すのは `Show` を実装する型であること（S-1261、2026-11-26、利用者）。実装量が見積もり（Rust 150〜250 行）に収まる場合に採る、という条件（X-27）。
  - §6.3 の `Show` の文字列（整数は 10 進、浮動小数は読み戻せる最短の 10 進で `1.0e21` 以上・`1.0e-7` 未満は指数、`NaN`・`inf`。最上位の `Char` と `Str` はそのまま、中に入れた `Char` と `Str` はリテラルの形、複合の値は Onsa の式の形）。
  - `spec/tools.md` §4 の「panic の文面に値を書くときは §6.3 の `Show` の文字列で書く」（S-241、2026-10-08）と、「失敗の行と続く行の §2.5 の書けない文字は `\u{…}`」（S-299、2026-11-09）、続く行の字下げと「`test` で始まる行だけが結果の行」（S-284）。
  - §18.1 の `failure`（`message`・`span`・`calls`・`kind`）と、`message` が約束するのは `assert <式のソース>` と `panic(msg)` の `msg` だけであること（S-233、S-554）。「欄を足すことは互換を壊さない変更」。通常の実行の panic の文面は約束しない（S-298）。
  - この版では struct・enum の頭の `Show` の derive は E0200、`impl Trait for Type` も E0200（`Option`・`Result` は std が derive している）。数の trait は `Show` を含まない（S-906）。
  - 被演算子は一度だけ評価し、評価の順と panic の位置・種類は今と同じ。C の生成物と通常の実行の文面は変えない（W8-13 の内容）。
- 今の実装の挙動は、親の渡したバイナリ `P/bin/onsa-82c6a6b`（dev `82c6a6ba`）の `test` と `test --json` で確かめた（`P` は scratchpad）。入力は親の `P/g120/probe/a.onsa`・`b.onsa` と、足した `P/g120/probe/gap/c.onsa`〜`g.onsa`。終了コードは 0・1 だけだった。
  他言語の手元の実行は `P/g120/other/` に置いた（rustc 1.94.1、Node v26.11.1、Python 3.14.5、Apple clang 21）。Swift 6.3 の `swift test` は、この環境の許可で走らせられなかった。

## 仕組みの出所と目的

- `spec/tools.md` §4 の `Show` の一文: S-241（`assert_near` の意味）の回で、`assert_near` の文面の数が Rust の書式（`1e308`）だったのを、§6.3 の `Show`（`1.0e308`）に揃えるために置いた。目的は、文面の数を Onsa のリテラルとして読み戻せる形にすることである。std の関数の文面そのものは doc コメントに書く（`std/dsp/test.onsa` の `assert_near` は `assert_near failed: <a> and <b> differ by <abs(a - b)>, more than <tol>`）。
- 同じ節の `\u{…}` の一文: S-299 で、`panic(msg)` の文面の ESC や双方向の制御文字が端末の表示を変えないために置いた。`--json` の `message` は文面のままである。
- §18.1 の `failure`: S-233 が `message`・`span`・`calls` を、S-554 が `kind` を決めた。`message` の約束を `assert <式のソース>` に限ったのは、適合の比べとテストベクトルがインタプリタと C の文面を突き合わせるからである（C の文面は値を持たない）。
- §9.2 の `panic(msg)` は補間の無いリテラルに限る（E0417。組み立てた文字列は §19.1）。§2.4 の補間は値に `Show` を求める（E0416）。したがって今の Onsa には、値を文字列にして出す手段が無い。開発の担当は 1 フレームの値をビットごとの `test` で割り出していた（X-27）。
- §6.3 の `Show` の文字列: 複合の値の形は S-135、タプルと `[T; N]` の `Show` は S-136。`Show` はこの期はメソッドを持たない（S-1014）。中に入れた `Str` と `Char` のエスケープの細部は S-270（未決、第 2 期）。
- §11.8 の `check[T: Show]` は、反例を `Show` で出すために、型パラメータの境界に `Show` を求める（反例の表示は W8-09）。

## 他言語の調べ（まとめ）

項目の「他言語」はこの節を指す。参考にとどめる。

- Rust（rustc 1.94.1、手元）: `assert_eq!(a + 0.2, 0.3)` は `assertion `left == right` failed` と `  left: 0.30000000000000004`・` right: 0.3`。値は `Debug` で、浮動小数は最短の 10 進（`1e21`、`2e-8`、`NaN`）、`char` は `'\u{1b}'`、`&str` は `"a\"b"`、struct は `P { x: 1.0, y: 2 }`。40 要素の配列も切り詰めずに全て出す。
  `Debug` の無い型（`Q`）と、境界に `Debug` の無い総称の `T` を `assert_eq!` に渡すと、どちらもコンパイルの誤り E0277（`T` doesn't implement `Debug`）。`assert!(a < 0)` は値を出さない（`assertion failed: a < 0`）。
  libtest の JSON（`RUSTC_BOOTSTRAP=1 … -Z unstable-options --format json`）は、値を `stdout` の文字列の中に持つだけで、値の欄は無い。
- Python（3.14.5、手元）: 素の `assert a == 2` の `AssertionError` の文字列は空。`unittest` の `assertEqual(0.1+0.2, 0.3)` は `0.30000000000000004 != 0.3`、`'a'` と `'\x1b'` は `'a' != '\x1b'`（引用符付き）。
  48000 要素のリストは `[0.5, 0.5, …[239951 chars] 0.5]` と中を切り、`First differing element 0:` と `Diff is 1200000 characters long. Set self.maxDiff to None to see it.` を出す。
- pytest（手元に無い。文書と原文）: assert 文を書き直し、「showing the values of the most common subexpressions including calls, attributes, comparisons」。長い列は「first failing indices」、長い文字列は差分（https://docs.pytest.org/en/stable/how-to/assert.html ）。
  長い出力は 8 行・640 字で切り、`...Full output truncated, use '-vv' to show` を付ける。`-vv` と CI では切らない（https://github.com/pytest-dev/pytest/blob/main/src/_pytest/assertion/truncate.py 、`_typing.py` の `DEFAULT_MAX_LINES = 8`、`DEFAULT_MAX_CHARS = DEFAULT_MAX_LINES * 80`）。
- JavaScript（Node v26.11.1、手元）: `node:assert` の `strictEqual(0.1 + 0.2, 0.3)` は `+ 0.30000000000000004` と `- 0.3` の差分。文字列は `'a' !== '\x1B'`（引用符付き）。任意のオブジェクトとクラスの値も構造で出す（`C { v: 1 }`）。
  48000 要素どうしの `deepStrictEqual` は 96,006 行・912,070 字の文面を出す（切り詰めない）。1000 要素の 1 か所だけ違う配列は、同じ行を `...` で飛ばす（`... Skipped lines`）。`assert(a < 0)` は値を出さず `The expression evaluated to a falsy value`。エラーの `actual`・`expected`・`operator` の欄に値がある。
- Jest（手元に無い）: `--expand` は「show full diffs and errors instead of a patch」（https://jestjs.io/docs/cli ）で、既定は違う所の周りだけ。任意のオブジェクトの表現は未確認。
- Swift（手元で走らせられなかった）: Swift Testing は値を `String(describingForTest:)` で書き、`CustomTestStringConvertible` が無ければ `CustomStringConvertible` などを経て、最後は `String(describing:)` に落ちる（どの型も出す。https://github.com/swiftlang/swift-testing/blob/main/Sources/Testing/SourceAttribution/CustomTestStringConvertible.swift ）。`#expect` の失敗の文面の形は未確認。`XCTAssertEqual` は未確認。
- C（Apple clang 21、手元）: `assert(a == 2)` は `Assertion failed: (a == 2), function main, file a.c, line 7.` で、値を出さない。C# の xUnit・NUnit の `Assert.Equal` は未確認（処理系が無い）。
- 機械が読む形: JUnit XML の `<failure>` は `message`・`type` の属性と本文の文字列で、値の欄は無い（版ごとに schema が違う。https://sources.debian.org/src/pytest/9.0.2-2/testing/example_scripts/junit-10.xsd ）。
  TAP 14 の YAML の診断は「has not been standardized」で、`found`・`wanted` は例にあるだけ（https://testanything.org/tap-version-14-specification.html ）。

### S-1261 G1 `Show` を実装しない型の比べ

- **論点:** 決定は「値を出すのは `Show` を実装する型」で、§6.3 の表で `Show` の無い型（`()`、`Bytes`、`Array[T]`）、この版の利用者の struct・enum（derive も `impl` も E0200）、`FixedStr[N]`（第 2 期）、それらを中に持つタプル・配列・`Option` を比べた `assert` が失敗したときの出力を書かない。
  決定の字は「`Show` を実装しない型では値を出さない」とも読めるが、出さないことを示す行を置くか、`Show` に無い形で出すか、誤りにするかは書いていない。
- **今の実装:** `a.onsa` の "struct"（`assert p == P { x: 1.0, y: 3 }`）・"enum"、`b.onsa` の "unit"、`c.onsa` の "fixedstr"（`assert t == "ac"`）、`f.onsa` の `(1, P { x: 1 }) == (1, P { x: 2 })` と `Option[P]` の `a == None` は、どれも `failed at …: assert <式のソース>` だけ。
  `impl Show for P {}` は E0200（`this version does not support trait implementations`）、`show_it(p)`（`T: Show`）は E0416（`e.onsa`）。
- **案:**
  - (a) 値を出さず、今の文面だけにする。条件は「両辺の型が `Show` を実装する」の一つ。実装は見積もりの形 A のまま（約 190 行）。
  - (b) 値を出さず、出さない理由の一行（`(values not shown: P has no Show)` の類）を置く。driver に約 5 行。この版の利用者の型では、示す直し（`Show` の derive）が E0200 で書けない。
  - (c) `Show` の無い型も構造で出す。struct と enum は §6.3 の derive の形（`P { x: 1.0, y: 2 }`）、`()` は `()`。§6.3 に無い型（`FixedStr`、`Bytes`、`Array[T]`）の形を `spec/tools.md` に足す。`FixedStr` を構造で出すと内部の `FixedStr { bytes: [97, 98, 0, …], len: 2 }` になり、文字列の値と読めない（字の形にするなら型ごとの規則が増える）。
    見積もりで約 +30〜45 行（型名を `TypeDef` に足す分を含む）。この版では利用者の型の比べ（右辺が大文字の名前の 570 行が上限の見当で、定数を含む）で値が出る。
  - (d) 比べの型に `Show` を求め、無ければ E0416 にする。今通るテストの、利用者の型と `FixedStr` の比べが全て誤りになる（数百行の見込み。型を見ないと数えられない）。この版では直す手段（`Show` の derive）が E0200 なので、直せない。
- **他言語:** 「他言語の調べ」の節。Rust は `Debug` の無い型を誤りにする（(d) の形）。Node と Swift Testing はどの型も構造か既定の記述で出す（(c) の形）。C と Python の素の `assert` は値を出さない。
- **推奨と理由:** (a)。確度: 中〜高。
  - 決定の字に、規則を足さずにそのまま当たる。条件は「両辺の型が `Show` を実装する」の一つで、例外が無い。§6.3 に無い形を作らない。
  - 第 2 期に `Show` の derive と `FixedStr` の `Show` が開くと、規則を変えずに値が出るようになる。(c) は、その後も「`Show` の無い型の形」という別の形を持ち続け、手書きの `Show`（S-1014 で第 2 期に決める）と並ぶ二つ目の書き方になる。出力だけの変更なので、後で (c) に広げても通るプログラムは変わらない。
  - (d) は今通るプログラムを誤りにし、この版では直せない。
  - (a) の費用: この版では利用者の struct・enum の比べで値が出ない。これは版の制限（derive が E0200）による。書き手はフィールドやタプルで比べて値を出せる（`assert p.y == 3`、`assert (i, xs[i]) == (i, ys[i])`）。
  - (b) の一行は、この版では示す直しが書けないので推さない。実装は増えるが効き目が薄い。
  - 見積もりの条件（150〜250 行）に、(a) は形 A のまま入る。
- **影響:**
