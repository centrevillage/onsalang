# S-624 §6.5 の属性が変えないものの「受理されたプログラム」が指す段

- 空白: §6.5 は「属性は、型と、受理されたプログラムの計算の結果を変えない付与情報である」とし、次の文で「どのプログラムを受理するかには関わりうる」とするが、「受理」がどの段（Core を作るまでか、C の API やターゲットごとの生成が通るまでか）を指すかを書いていない。
  `@fp(relaxed)` は C での結果を変えることがあり（§15.5）、`@mem(bulk)` は bulk が有効なターゲットで置き場所を変え E0819 を出す（§12.4）。`rules/criteria.md` 7.23 の「属性（§6.5）はコード生成の注釈にとどめる」（S-615）も、§6.5 の範囲を指す。
- 決定: 決定（2026-10-24、利用者が了承「(ii)で良いと思います」。59 回目）: 属性は、ターゲットに固有の事情が関わらない段までのプログラムの解釈（型と計算の結果）を変えない（利用者「私の意図に近いのはターゲット固有の事情が関わらない部分までは解釈が変わらないという意味での「受理」」）。
  §6.5 の 1 文目の「型と、受理されたプログラムの計算の結果を変えない」を「ターゲットに固有の事情が関わらない段までのプログラムの解釈（型と計算の結果）を変えない」に改める。次の文の受理に関わる 4 つ（位置と値の検査、export する flow の `block` の入力の `@param` か `@host`、E0819、`@repr(c)` の FFI）は、属性自身の誤りかターゲットに固有の事情なので、そのまま。
  C との境界（§14）もターゲットに固有の事情に含める（extern の引数で `unsafe` を要しない型に `@repr(c)` 構造体が入る、§14.1）。範囲を書くのは §6.5 だけにし、7.23 は §6.5 を指すだけにする（記述を重ねない、利用者）。仕様の他の節の規則は変えないので、担う作業は無い。仕様 §6.5
- 経緯: 59 回目（2026-10-24）、58 回目の終わりの文書の点検（onsa-docs）が、7.23 の「コード生成の注釈」と §6.5 の「付与情報」の違いと、受理に関わる属性（`@param`・`@host`・`@mem`・`@fp(relaxed)`）を挙げた。
  親が「外しても、受理されたプログラムの意味は変わらない」の読みを出したところ、利用者は「プログラムの受理」がどこを示すか（Core IR まで作れるか、C API や各ターゲットの生成が通るか）が曖昧だとした。
  親が属性ごとの当てはめ（`@repr(c)` の extern の引数だけが `onsa check` の段で効き、C との境界の事情に含める）を示し、利用者が了承した。置き場所は、7.23 にだけ短く足す形 (i) と比べ、§6.5 にだけ書く形 (ii) を利用者が選んだ。助言の担当には回していない（範囲を書く直しで、規則は変わらないため）。
