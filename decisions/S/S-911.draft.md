# S-911 境界と derive を経る `rt` の再帰（E0903）: `T.default()` の具体化と derive の `default` の呼び出しを辺に数えるか


- **出所:**
  - §10 の規則 5（再帰の禁止と「モジュールの中で閉じる」）と §12.5 の最初の 2 行は、0.2 の版（`history/onsa-lang-spec-0.2.md` 582 行、798〜799 行）から同じ文である。`history/onsa-0.2-changes.md` 143 行の理由は「組込みではスタックが小さく、溢れても検出されない」である。つまり目的は、`rt` の処理のスタックの上限を計算できるようにすることである。再帰そのものが悪いのではない。
  - 「モジュール間の import は循環しない（§15.1）ので、この検査はモジュールの中で閉じる」は、§10 の規則 5 の理由の文で、呼び先が名前で決まることを前提にしている。当時は手書きの `impl Default` が無く、境界のメンバは std の宣言だけだった。
    今の `rt.rs` の `rt_calls` は、呼び出しの先が本体を持つ `rt` の関数のときだけ辺にする。`T.round_from(x)` の先は代表の型の宣言で、`Target::Method` の `of` が型パラメータを指す。
  - `onsa audit --stack`（§12.5）は「関数値を経由する呼び出しや、rt でない再帰を含むエントリは『不明』」と報告する。関数値が外れているのは、呼び先が実行時の値で決まるからである。この版の Onsa にトレイトオブジェクトは無い（§6.3）ので、`T.default()` の呼び先は値でなく型で決まり、具体化すれば一つに定まる。ここが関数値と違う。
    audit は未実装（今の CLI に命令が無い）で、W8-08 の到達の上に作る計画である。`history/implementation-plan.md` 202 行の見積もりの前提は「核は再帰が無いので呼び出しグラフの最大深さ × フレームの大きさ」である。
  - 実行時の上限 128（§12.5、S-222、S-229）: `onsa test` とコンパイル時の評価の上限で、際限の無い再帰と評価の負荷を止めるためのものである。derive を含む処理系の生成する関数も数える。C などの変換先には当たらず、「多くはプロセスの異常終了で、panic としては扱えない」。
  - 関係する形の性質（第 1 期）: `default` は引数が無く、効果行が空である（S-905）。途中の関数は全て `rt` で（下の表の「`rt` でない関数」）、外の状態を読めない。よって `default` に戻る循環に一度入ると、同じ状態で同じ道を通るので、必ず止まらない（途中の `panic` を除く）。逆に、循環を通らない枝を選ぶプログラムは、循環があっても正しく動く。第 2 期の引数のあるメンバには、この性質は無い。
- **論点:** §10 の規則 5 の「再帰しない（直接・相互とも）」は、手で書いた呼び出しの形しか想定していない。手書きの `impl Default`（U4）を開くと、derive と境界を経て `default` に戻る形が書ける。これを E0903 に数えるか、数えるならどの段で出すか、数えないなら §10 と §12.5 の文をどう改めるかを決める。
  - 決定済み（論点から外す）: `default` が `rt` で効果行が空なこと（S-905）。`ordinal`・`from_ordinal` が `rt` で（S-907）、`impl Ordinal` は E0307 なので循環の辺にならないこと。`default` が型の名前の後の `.` の空間に入ること（S-851）。誤りのある単位の呼び出しを辺に数えないこと（S-776）。
  - 別の S のまま: 関数を経る定数の循環（S-173、W9-03）。E0903 の位置（S-778、OPEN。ただし下の「あわせて決めること」）。同じ段の誤りの単位（S-779）。多相再帰と具体化の数（S-290、OPEN）。

  - 形 1 で具体的なフィールドの型なら、循環はモジュールの中で閉じる。`P` のフィールドが `Q` を名指し、`Q.default` が `P` を名指すので、別のモジュールに置くと `use` の循環（E0310）になるからである。総称の `P[T]` と形 2 は閉じない。
  - `default` が必ず `rt` なので、`rt` でない `fn` は循環に入れない（E0901）。循環は全て `rt` の関数だけでできる。
  - 孤児規則（§6.3）により、循環には `Q` と同じパッケージの手書きの `impl Default` が必ず一つ入る。今の std に `T.default()` を呼ぶ関数は無い（`std/` に `.default()` は 0 件）。
  - 通るプログラムの数: どの案でも、今通るプログラムは変わらない。`impl Default` は `tests/` に 2 ファイル（`impl_trait_e0200_hand_written`、`impl_trait_orphan_builtin`。どちらも誤りの事例で本体に循環は無い）、`examples/`・`std/` に 0 件、`spec/` の ```onsa ブロック 39 個に 0 個である。
    §6.4 の文の例 `impl Default for Mode` は他を呼ばない。`tests/spec/derive/` の `T.default()` の事例は `impl Default` を持たないので循環が無い。
- **案:** 下の例を使う。`mk` は上の形 2 の総称の関数である。
  ```onsa
  // E1 形 1: 循環           struct P: Default { q: Q }   Q.default の本体 { P.default().q }
  // E2 形 2: 循環           Q.default の本体 { mk::[Q]() }
  // E3 正しい: 入れ子       impl[T: Default] Default for W[T] { rt fn default() -> W[T] { W { x: T.default() } } }
  //                         の W[W[I32]].default()
  // E4 正しい: 他の型の derive  struct R: Default { x: I32 }   A.default の本体 { A { r: R.default() } }
  // E5 正しい: 別の型の mk  Q.default の本体 { Q { x: mk::[I32]() } }
  // E6 通らない枝           Q.default の本体 { if DEBUG { mk::[Q]() } else { Q { x: 0 } } }（DEBUG は false の定数）
  // E7 使われない総称       W.default の本体 { mk::[W[T]]() } で、W をどこでも具体化しない
  // E8 関数値               Q.default の本体 { app(Q.default) }
  ```
  - (a) 何も足さない: E0903 は名前で呼び先が決まる呼び出しだけを数える。境界のメンバと derive の呼び出しは、§12.5 の関数値と同じく「不明」と報告する。§10 の規則 5 と §12.5 の「`rt` 関数は再帰しない」の文を、この範囲に改める。
  - (b) 形で分ける: derive の呼び出しは宣言と呼び出しの型引数から呼び先が読めるので、`check` の E0903 の辺に足す（フィールドの型をたどる。タプル・配列も）。型パラメータの `T.default()` は呼び先が読めないので (a) と同じく数えない。
  - (c) 検査の段で具体化をたどる: `rt` と効果の段（§18.1）で、呼び出しの型引数を当てて `T.default()` を実際の型の `default` へ解き、derive のフィールドもたどる。辺は（定義、型引数）の組で、自分の型パラメータはそのまま固定の型として扱う。E1〜E2 は `check` の E0903 である。
    型が際限なく大きくなる鎖の止め方が要る（同じ定義が、部分の型でない型引数で再び現れたら循環と見る、など）。
  - (d) 降下の後に具体化した呼び出しで検査する: `check` の E0903 は今のまま名前の循環を報告する。加えて、降下の後の Core の呼び出し（具体化は済んでいる）で `rt` の関数の循環を調べ、同じ E0903 を `test`・`build`・`interface` など降下に進む命令で出す。
    `check` は形 1・形 2 を報告しない。
  - (e) 検査の段で多めに辺を張る: 具体化しない。`T.default()` を、パッケージの全ての手書きの `default` への辺と見る。derive は (b) と同じに正確にたどる。
