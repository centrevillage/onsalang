# S-1116 ビューの位置（`Span`・平面の引数、生成型のフィールド）に置いた `if`・`match` の末尾の種類が違う形を、末尾ごとにビューへ変換して通すか、腕の型を先に合わせて E0401 にするか（第 122 組、S-623 と共通の節を持つ）

- 位置付け: W8-01 の設計メモ部 2（値の形の追加: 平らな `match`、ビューの位置の降下）を書く前に決める 2 件。二つは別の論点で、族の規則の S は立てない。
  背景は W8-01 の地図（`target/notes/191/w801/map/map.md` の 2 の表の 18・22・23、3.2 の U1・U2、4.2 の部 2）。部 1 の設計メモ（`target/notes/191/w801/p1v2/memo.md`）の 11 章の `Switch` の行は「平らな並びは部 2」とし、どちらの案も表せる。
- 決定済みで論点に戻さないもの:
  - S-1116 に関わるもの:
    - 借用の引数の末尾の場所の重なり（S-1113 の (1)、E0702）。部分ビュー・経路・添字の基の末尾（S-1114）。
    - 腕・ブロックの中で宣言した Copy でない束縛の末尾は E0716（S-1115）、破棄の要らない束縛は通る（S-1118）。Copy の束縛の記憶域は関数の高さに出す（R-481、W7-12 U2c2）。
    - 平面の配列リテラルの要素は種類と長さが揃っていなくてよい（S-196）。平面の位置の末尾の配列リテラルは平面と読む（W7-12 U2c2b、S-1113 の実装）。
    - `inout` の位置の `if`・`match` は場所でなく E0415（§5.1）。受け手・`for` の反復元・`match` の対象は型の頭が先に要る（§4.7 の E0420 の規則）。
    - `let` の注釈 `Span[F32]` は変換の位置でない（`let s: Span[F32] = x` は直に書いても E0401。§5.4 の束縛の表に配列からの変換は無い）。
  - S-623 に関わるもの:
    - 選択の全ての枝は同じ名前の集合を束縛し、違えば名前の段の E0314（S-318）。同じ名前の型は全ての枝で同じ（違えば E0401）。
    - 反駁可能な `let` は無い（E0502）。選択の `let (x, _) | (_, x) = p` も E0502 で、ガードを持てるのは `match` の腕だけである。
    - 所有の `match` のガードは腕の束縛を消費できない（E0715）。腕の束縛が中身を所有するのは腕が選ばれた後である（§7）。
    - ガードの付いた腕は網羅に数えない（§7）。範囲・浮動小数のリテラルなどをガードの形に直す修正候補は、置き換えた後の枝の形が違えば作らない（§7、E0002）。
    - 束縛を持つ選択の降下は W8-06（S-318 の持ち越し）。

## 仕組みの出所と目的

### S-1116

- §4.7 の「期待型は式の中へ下向きに伝わる」: 呼び出し先の引数の型、`let` の注釈、フィールドの型が、式の中（`if` の枝、`match` の腕、ブロックの末尾）へ期待型として伝わる。目的は、推論を文の順の一方向で閉じ、誤りを原因の近くに出すことである。
- 同じ段落の「`if` の後の枝と `match` の二つ目以降の腕には前の枝の型」: S-880（2026-11-04）で足した文である。目的は、`narrow_*` の修正候補（S-875）を選ぶ期待型の範囲を、検査がその位置に渡す型として書き出すことだった。ビューへの変換の位置で、外の期待型と前の枝の型のどちらを使うかを決めた文ではない。
  関数型の合わせ（S-1031・S-1061）は、期待型の無い合流で枝の関数型を合わせる規則で、期待型のある位置では各枝が期待型に合わせられる（下の表の 41。`rt` の関数と `rt` でない関数を `fn(I32) -> I32` の引数に `if` で渡すと、どちらの順でも `check` が通る）。
- §5.2 の「位置を継ぐ」: ブロックの末尾の式は、そのブロックが置かれた位置を継ぐ。`move` の印（S-100）、重なり（S-1113・S-1114）、腕の中の束縛（S-1115・S-1118）は、どれも末尾ごとに直に書いたときと同じに読む。
- §5.3 の変換: `Span[T]` の引数には `[T; N]`・`Buf[T]`・`Span[T]`（`Span[U8]` には `FixedStr[N]` も）を渡せ、`[Span[T]; N]` の引数には `[[T; M]; N]`・`[Buf[T]; N]`・`[Span[T]; N]` を「要素ごとに `Span` へ変換」して渡せる。目的は、呼び先が記憶域の種類と長さを知らずに読み書きできること（C++20 の `std::span` と同じ）である。平面の配列リテラル（S-196）は、別々の変数のチャンネルを引数の位置にだけ並べる書き方である。
- 今の型の段（Rust の実装、`crates/onsa_sema/src/body/calls.rs::view_arg`・`expressions.rs::check_viewed`）: ビューの位置の値を、`if`・`match`・ブロック・括弧を節として通り、末尾ごとに `BodyInfo::views` に変換を記録する。
  節の型は今の `if`・`match` の規則（後の枝の期待型は前の枝の型、`join_hint`）で決まり、変換の判定（`views`）は節の全体の型に一度だけ行う。印は `expressions.rs` の `SPEC-GAP(S-1116)`。
  降下（W7-12 U2c2b）は記録だけを読んで末尾ごとに変換し、節の値の写しを作らない（下の C の読み）。

### S-623

- §7 の選択: 「選択の全ての枝は、同じ名前の集合を束縛する（`(x, 0) | (0, x) => x`）」（S-318）。目的は、腕の本体がどの枝で当たっても同じ名前を読めることである。
- §7 のガード: 「ガードは `Some(x) if x > 0 => ...`」。ガードの付いた腕は網羅に数えず、借用の `match` のガードは対象を変更できず（E0715）、所有の `match` のガードは腕の束縛を消費できない（E0715。「ガードが偽なら後の腕が同じ値で判定される」）。
  §3.5 は「`if` / `match` は、取る分岐・腕だけを評価する」とし、§7 の常に評価される部分式の外の一覧に「`match` の腕のガード（常には評価されない）」がある。ガードを一つの腕で何回評価するかと、選択の枝を試す順は、どこにも書いていない。
- §7 のパターンの節の見出しは「パターン（Rust と同じ意味のものだけ）」である。S-318 の空白の文はこれを「選択の枝の束縛の規則を書かない」と読み、空白とした。書ける形の範囲を限る字で、評価の順を決める文としては使われていない。
- §7 のガードの形の修正候補の規則（「置き換えた後も枝の形が違うもの（`(0.5, 1) | (1.5, 2)` など）は、ガードがどの枝で当たったかを区別できず、当たる値が変わるので、候補を作らず E0002」）は、候補を作らない理由で、評価の順を定めていない。
- 道具の層（Rust のテストの器 `crates/onsa_tests/src/flow_ref/pattern.rs`、flow の参照評価器）は、W7-01 U4 の直しで、§7 の見出しの「Rust と同じ」を根拠に、当たる枝ごとにガードを試す読み（下の案 (2)）を実装した。同じ所の `pattern_tests.rs` に 7 件のテストがある。言語の決定ではない。

### S-1116（`P/g122/other/`）

- Rust（rustc 1.94.1、`r_coerce_ok.rs`・`r_coerce_ng*.rs`）: `fn take(s: &[f32])` に `take(if c { &x } else { &y[0..2] })`、逆順、長さ違い（`&[f32; 8]`）、`&Vec<f32>`、`match` の 3 腕、struct のフィールド、`let s: &[f32] = if …` は全て通る。

- Swift 6.3.3（`s_ctx.swift`・`s_ctx_ng*.swift`）: `func takeSeq(_ s: any Collection<Float>)` に `c ? x : sl`（`[Float]` と `ArraySlice<Float>`）は通り、`let s1: any Collection<Float> = if c { x } else { sl }` も通る。

- C++（Apple clang 21、`-std=c++20`、`c_cond.cpp`）: `take(std::span<const float>)` に `take(c ? x : v)`（`std::array<float, 4>` と `std::vector<float>`）は「incompatible operand types」、長さ違いの `std::array` も同じ。`?:` の型は被演算子だけで決まり、引数の型を見ない（[expr.cond]）。各腕を `std::span` にすると通る。
- TypeScript: 手元に tsc が無く未確認。Kotlin は 7.32 の一覧に無く、手元にも無いので未確認。

### S-623（`P/g122/other/`）

- Rust（rustc 1.94.1、`r_guard.rs`）: `(x, _) | (_, x) if x > 5` に `(1, 9)` は 9。束縛の無い `1 | _ if tick(&n)` は `n = 2`、束縛のある形も 2。二つの選択の形は `((1, 2), (3, 9))` で 29、3 枝は 9、ガードの無い形は 1（`(_, x)` に unreachable pattern の警告）。
  Reference の Match expressions の Match guards（https://doc.rust-lang.org/reference/expressions/match-expr.html）は「Multiple matches using the `|` operator can cause the pattern guard and the side effects it has to execute multiple times」とし、`1 | _ if { i.set(i.get() + 1); false }` で 2 になる例を挙げる（手元の `count_nobind` と同じ）。
- Python 3.14.5（`p_guard.py`）: `case (x, _) | (_, x) if x > 5:` に `(1, 9)` は -1。`case 1 | _ if tick():` は `n = 1`。二つの選択の形は -1。選択は左から試し、最初に当たった枝で束縛し、ガードが偽なら次の `case` へ進む（PEP 634 の Or Patterns と Guards）。
- Swift 6.3.3（`s_guard.swift`）: `case (let x, _) where x > 5, (_, let x) where x > 5:` は 9、`case 1 where tick(), _ where tick():` は `n = 2`。`where` はその直前の一つのパターンにだけ付き、`case (let x, _), (_, let x) where x > 5:` は `(1, 9)` で 1（一つ目のパターンにガードが無い）。コンパイラは「'where' only applies to the second pattern match in this 'case'」と警告する。
- C#（手元に無い）: `or` パターンの中で変数を宣言できない（CS8780「A variable may not be declared within a 'not' or 'or' pattern」、https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-messages/pattern-matching-warnings）。束縛を持つ選択そのものが書けない。
- Java、JavaScript・TypeScript、C、C++: 束縛を持つ選択のパターンが無い（Java 21 の `case` の複数のパターンは束縛を持てない。未確認の部分あり）。
- 一覧の外（参考、手元に無い）: OCaml の手引き 13.5.4（https://ocaml.org/manual/5.2/comp.html）は、選択を左に寄せ、左の枝が当たればその束縛でガードを一度だけ評価し、右の枝は試さないとする。警告 57（ambiguous-var-in-pattern-guard）は、ガードが二つの枝で値の違う部分に束縛された名前を読むときに出る。Scala・F# は未確認。

### S-623 束縛を持つ選択の腕のガードが偽のとき、同じ腕の次の枝を試すか

- **論点:** §7 は「選択の全ての枝は、同じ名前の集合を束縛する（`(x, 0) | (0, x) => x`）」とし、腕にガードを持てるが、二つ以上の枝が同じ値に当たり、名前を値の違う部分に束縛するとき、どの枝で束縛するかと、ガードが偽のときに同じ腕の次の枝を試すかを書いていない。
  `match p { (x, _) | (_, x) if x > 5 => x, _ => -1 }` に `(1, 9)` を渡すと、(1) なら -1、(2) なら 9 になる。§3.5 の「取る腕だけを評価する」はガードの評価の回数を決めない。§7 の見出しの「Rust と同じ意味のものだけ」は書ける形の範囲を限る字で、S-318 も評価の順を空白とした。
  S-318 の決定の文は「腕のガードと枝の順は S-623」とするので、ガードの無い腕の枝の順（14）もここで決める。
- **今の実装:** 束縛を持つ選択は、`check` が通り、`test` と `build` は Core の降下の E0200 `OrPatternBindings`（当たる形の表の 1〜8・11〜14、`P/g122/probe/s623/`）。束縛の無い重なる選択 `1 | _ if tick(inout n)` は `test` が通り、ガードを一度だけ評価する（9、`n = 1`）。
  道具の層の flow の参照評価器は (2) を実装し、`pattern_tests.rs` の 7 件のうち 6 件が (2) の値を確かめる（18）。今の事例 `pattern_choice_bindings_same.onsa` の `with_a_guard`（`(x, 0) | (0, x) if x > 1`）は `check` が通る（17）。
- **案:**
  (1) 選択は左の枝から試し、最初に当たった枝の束縛でガードを一度だけ評価する。偽なら次の腕へ進み、同じ腕の後の枝は試さない。
  (2) 選択は左の枝から試し、当たる枝ごとにその束縛でガードを評価し、真になった最初の枝で腕を選ぶ。入れ子や複数の選択は、後の選択の枝を先に進める順（表の 7 の 29）。ガードは同じ腕で複数回評価されうる。束縛の無い選択にも同じに当てるか（9 の値が変わる）、束縛を持つ選択に限るかを併せて決める。
  (3a) ガードを持つ腕で、同じ値に当たりうる二つの枝が、ある名前を値の違う部分（タプルの位置、フィールド、列挙子の中身の経路）に束縛すると誤りにする。当たりえない枝の組は、同じ位置に違う列挙子か違うリテラルを持つものとし、定数は当たりうるとする。残る形は (1) の規則で評価する。修正候補は無く、note で二つの書き方（枝ごとに腕を分ける、条件を本体へ移す）を示す。
  (3b) 束縛を持つ選択の腕にガードを付けると全て誤りにする（4 の別の列挙子の形も）。残る形は (1) の規則で評価する。
- **他言語:** 上の「他言語の調べ」。Rust は (2)、Python と OCaml は (1)、Swift は `where` を付けたパターンごとに試し、C# は束縛を持つ選択を書けない。
- **推奨と理由:** (3a)。確度: 中。
  - 同じ書き方で、一覧の言語の間で値が割れ（Rust の 9 と Python の -1）、panic と `?` で関数を抜けるかまで割れる（11・13）。書き手がどちらの読みで書いたかは字から分からず、どちらに決めても他方の読みの書き手には黙って違う値になるので、値が割れる形だけを誤りにする。
  - (3a) は後で (1) にも (2) にも、誤りだった形を開くだけで移れる。残る形は (1) と同じに一度だけガードを評価するので、今の束縛の無い選択の挙動（9）を変えず、W8-06 の降下は (1) と同じ簡単な形で済む。生成コードも (1) と同じで、ガードの写しや評価の回数が増えない。
  - 費用: 新しいコードと二つの枝を並べて歩く判定（見込み 40〜80 行）が増える。重なりの判定は値を見ないので、3・17 の `(x, 0) | (0, x) if g` のように、重なる点で値が同じ形も誤りにする（今の事例 1 件の期待値が変わる）。参照評価器の 6 件の事例も改める。
  - (3b) は判定が短いが、DSP で書きうる 4 の形（別の列挙子の枝にガード）を、値が割れないのに誤りにする。(2) は読みの一つを選ぶ案で、ガードの評価の回数が書き方で増え、降下は当たる組の数に比例して大きくなる。(1) は最も簡単だが、Rust の読みの書き手に黙って違う値を返す。
  - あわせて決めること: 選択の枝は左から試し、ガードの無い腕は最初に当たった枝で束縛する（14。どの案でも同じ）。ガードは腕ごとに一度だけ評価する（(3a) の残る形）。誤りのコードは名前の段（E0314 と同じ所、列挙子の解決の後）か型の段かを、登録のときに決める。
  - 別の S にしてよい論点: 重なりの判定を、重なる点で値が同じ形（3・17）まで通すように細かくするか（規則が増える）。
