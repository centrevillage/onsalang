# S-581 プラグインのパラメータの写し方: `@param` とホストのパラメータ、変化の届け方、変調

- 決定済みで戻さないもの: 組の全体は S-580 の下書きの頭（第 35 組の境界の見込み、S-565 の R12、`@param` と数値の ID、S-172、§14.2 の C の API の原則、ランプは扱わない）。第 35 組の C の API への影響（A1〜A8）は S-580 の下書きの「影響」。
- 論点: §11.7「用途: IDE の自動 UI、プラグイン（CLAP / VST3 / AU）のパラメータ情報…」「制約が無ければ `min` / `max` / `step` を書かない（`step` が無ければ、浮動小数は連続、整数は全ての整数の値）」。
  ホストの値の表し方は形式で違う: CLAP は値そのもの（`double`、範囲は「Must be finite」）、VST3 は 0〜1 に正規化した値と `stepCount`、AU は `float` の値（`AUValue`）。
  - 決定済み: 数値の ID（§11.7、S-104）。値を飽和させない（R-21）は C の API の約束で、ラッパーはホストの側に立つ。分ける形の意味と同じ位置の順（S-565 の R12、S-570）。直線の変化は扱わない。
  - (1) 値の対応（範囲の無い `@param`、VST3 の正規化と `scale`、`step`、`Bool`、AU の `float`）。(2) 変化の届け方。(3) 変調。(4) 表示の文字列。UI の文脈とオーディオの文脈の受け渡しは (2) とあわせて書く。
- 今の実装: export の C の `pz_gain_param_info` は `{ "level", "level", -60.0f, 12.0f, 0.0f, NAN, "dB", "linear", "Level" }` の形で、数値の ID と型の種類が無い（`t01_kinds`。§14.2 の `onsa_param_info` にするのは W10-03）。
  `Bool` の `@param(default: false)` は E0809「`@param` `default` must be a numeric literal」（`t05_bool`。R-99・S-87 で既知）。
- 案:
  - 値の対応:
    - (q1) プラグインのターゲットに出す flow の数値の `@param` は `min`・`max` を要する（無ければそのターゲットのビルドで E0809）。VST3 の正規化は `scale` で写す（線形は `(v − min) / (max − min)`、`"log"` は `ln(v / min) / ln(max / min)`）。
      `step` があれば（整数の型は無くても 1）ラッパーは `min + k × step` の格子の最も近い値に丸めて `Params` に書き、ホストには離散の値として示す（CLAP の `CLAP_PARAM_IS_STEPPED`、VST3 の `stepCount` は格子の数）。`Bool` は 0 と 1 の離散の値。費用: ラッパーの丸めと照合の規則が一つ。
    - (q2) (q1) と同じだが、`step` は表示だけで丸めない（浮動小数は連続、整数は CLAP の「converted to integer using a cast (equivalent to trunc)」と VST3 の格子に任せる）。費用: 規則は少ないが、同じ自動化で形式ごとに値が違いうる。
    - (q3) 範囲を要しない（整数は型の範囲、浮動小数は決まった大きな値を範囲にする）。費用: 正規化した値の分解能が範囲で決まり、決まった値を仕様に書く。
    - AU の `float`: どの案でも、`F64` と 2^24 を超える範囲の整数の `@param` は AU で正確に渡らない。
  - 届け方:
    - (d1) ラッパーが変化の位置で呼び出しを分ける（S-565・S-570 の形）。CLAP は一つの列を順に、VST3 は `IParameterChanges` の各列の点（`sampleOffset`）を位置の順に混ぜ、AU は `AURenderEventParameter` の時刻を位置にする。費用: C の API は変わらない。変化ごとに `block` の段を一回評価する。
    - (d2) C の API のイベントの列に、パラメータの変化の印（添字と `double`）を足し、生成したコードが中で `Params` の写しを書き換えて `block` の段を評価し直す（言語の意味は `block` の入力のまま。A5）。費用: `<p>_event` と生成した `_process` の両方が変わり、値を渡す道が `params` と列の二つになる。
    - (d3) 分けない。呼び出しの中の変化は全て呼び出しの前に当てる。費用: 最も少ないが、出力がホストのブロックの長さで変わる。
  - 変調（CLAP の `CLAP_EVENT_PARAM_MOD`）: (mo1) 第 1 期は受けない（`CLAP_PARAM_IS_MODULATABLE` を立てない）。(mo2) 全体の変調（`note_id` が −1）を受け、ラッパーが値と変調の量の和を `Params` に書く（変化と同じく分ける）。費用: 和が範囲を出たときの扱いを決める。
    (mo3) (mo2) とボイスごとの変調（`note_id` 付き）。費用: ボイスを特定するノートの型（S-582 の (n2)）とボイスへの写しが要る。
  - 表示の文字列: (tx1) ラッパーが数と `unit` から作り、文字列から値へは数の部分だけを読む（形は約束しない）。(tx2) 書き手が Onsa の関数で文字列を作る（`Str` の要る第 2 期）。
- 他言語:
  - CLAP（`ext/params.h`）: 変化は「send automation points during clap_plugin.process()」か `flush` で届き、`flush` については「the plugin may use the sample offset in process(), while this information would be lost within flush()」。
    変調は「The value heard is: param_value + param_mod」（`events.h`）。`CLAP_PARAM_IS_ENUM`、`CLAP_PARAM_IS_BYPASS`、ノート・キー・チャンネルごとの自動化と変調の印がある。
  - VST3（`ivsteditcontroller.h`）: `ParameterInfo::stepCount` は「0: continuous, 1: toggle, discrete value otherwise」、既定は正規化した `defaultNormalizedValue`。`normalizedParamToPlain`・`getParamStringByValue` を持つ。
  - AU（`AUParameters.h`）: `typedef float AUValue`。表示の単位は `kAudioUnitParameterUnit_*`（`AudioUnitProperties.h`）。
  - nih-plug（`src/plugin.rs`）: `SAMPLE_ACCURATE_AUTOMATION` は既定で偽で、真なら「the audio processing cycle may be split up into multiple smaller chunks if parameter values change occur in the middle of the buffer」「Bitwig Studio sends at most one parameter change every 64 samples」。
    CLAP の包みは、変化とトランスポートの変化で分け、ボイスごとの変調では分けずノートのイベントに変える（`src/wrapper/clap/wrapper.rs`）。DPF は `kParameterIsAutomatable`・`kParameterIsBoolean`・`kParameterIsInteger`・`kParameterIsLogarithmic` の印（`DistrhoDetails.hpp`）。
- 推奨と理由: (q1)、(d1)、(mo1)、(tx1)。確度: (1) 中、(2) 中〜高、(3) 中、(4) 中。
  - (q1): 範囲の無い値は、CLAP の有限の範囲にも VST3 の正規化にも表せないので、今は誤りにする（(q3) へは後で緩められる）。格子に丸めると、flow が読む値が三つの形式で同じになる。(q2) は同じ自動化で形式ごとに値が違いうる。
  - (d1): 第 35 組の形のままで C の API を変えず、手書きのホストも同じ規則で書ける。`block` は状態を持たないので、出力は変化の位置だけで決まり、ホストのブロックの長さに依らない。
    (d2) は値の道が二つになり、イベントの列の形を変える（後で足すなら、flow ごとのヘッダを作り直す形で入る）。(d3) は出力がホストの区切りで変わる。
  - (mo1): 変調の和の扱い（範囲を出たとき、表示との違い）がまだ決まっていない。変調の印は後で立てても、ホストが保存したプロジェクトを壊さない（変調はホストの側にある）。(mo2) は後で小さく足せ、(mo3) は S-582 の (n2) とあわせて決める。
  - (tx1): 第 1 期に `Str` が無く、表示の形は人が読むもので約束しない（基本仕様に書かない）。(tx2) は後で足しても壊さない。
  - UI の文脈とオーディオの文脈: ラッパーは C で、パラメータごとの今の値を原子的な変数に持つ（主のスレッドの `get_value` と状態の保存が読む）。言語の同期型（§16.2）は使わないので、言語の論点にならない。
  - あわせて決めること: AU のターゲットでは、`F64` の `@param` と、範囲が 2^24 を超える整数の `@param` を E0200 にする（変換先が与えない値）。VST3 の隠したパラメータ（S-582）は数値の ID の 31 ビットの外（`0x80000000` 以上）に置く。
  - 新しい S の候補: `scale` と範囲の変更を、凍結（§15.4）で止めるか。VST3 は正規化した値を保存するので、`scale` か範囲を変えると、保存した自動化の音が変わる。
- 影響:
  - 仕様: §11.7（プラグインのターゲットの範囲の規則、格子）、§14.2（ラッパーの節）。(d2) なら §19.1 の境界の項と §14.2 の `<p>_event`。
  - 診断のコード: E0809（範囲の無い数値の `@param`、(q1)・(q2)）、E0200（AU の値）。
  - 作業: ラッパーの作業（S-580 の時期）。(d2) なら W8 の `process` のループと W10-03。(q1)〜(q3) と (d1)・(d3) は flow の生成コードを変えない。
    (d1) の分けるループと (q1) の丸めは、S-580 の (w2)・(w3) なら形式ごとの固定の C の共通の部分に一つ、(w1) なら生成器に置く。
  - 後で足す変更: パラメータの変化の列は、(d1) の上に (d2) を足せる。ボイスごとの変調は (mo1) の上に S-582 の (n2) と (e2) を足して入る。enum の `@param`（§19.1）は CLAP の `CLAP_PARAM_IS_ENUM` と VST3 の `kIsList` に写せる。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - (2)・(4) は一致した。(1) は (q1) で一致し、段 2 は、整数の `@param` の上限（`(max − min) / step ≤ 2^24`。VST3 の `stepCount` が `int32`、AU の値が `float` のため）を三つの形式で共通の E0809 にし、`F64` は下書きのとおり AU のターゲットで E0200 にする（後で緩められる）。
  - (3) は割れた（段 1 は (mo2) 連続の浮動小数の `@param` の全体の変調、下書きは (mo1)）。段 2 は下書きを採る: (mo2) は CLAP の作業の中で決めても遅くなく、ホストが保存したプロジェクトも壊さない。「連続の浮動小数の `@param` だけを変調でき、値と変調の量の和は `[min, max]` に収める」を候補として残す。
  - 事実の直し（段 1）: VST3 の `stepCount` は格子の点の数ではなく区間の数（点の数 − 1。1 が toggle）。
  - 補い（段 1）: ラッパーが値を格子に寄せて `[min, max]` に収めるのは C の API の外（ホストの側）で、C の API が飽和させない約束（R-21、§11.7）と矛盾しないことを仕様に明記する。
  - 新しい S の候補（`scale` と範囲の変更を凍結で止めるか）: 段 2 は別の S にする（§15.4 の延期と同じ時期）。
- 回答（2026-10-22、会話で利用者。52 回目）:
  - 届け方（(2)）: 利用者: 「（2）について、なるほどブロックレートを可変にしてホストから来たイベントのタイミングを保持する考えですね。パフォーマンスの影響はありますが、組み込みではなくPCホスト用であれば多少のパフォーマンス低下は受け入れられるかもしれません。
    組み込みの場合はDMAのレートに合わせて更新するのが自然なので、固定ブロックレートの方が都合が良いですが、それはC APIの外の話なので、影響はないと思います。ブロックレートにflowが依存しない設計を貫いたのが効いてますね」。
    親は、分けても出力が変わらないのは `block` のクロックが状態を持てないためで、`onsa test --flows` が二通りの区切りで確かめること、C の API は区切りと `Params` の更新を呼び出し側に任せ、組み込みのホストは決まったブロックで呼んで呼び出しの間に `Params` を書けばよいことを答えた。
    利用者が、ホストがサンプルごとに変化を送ると `block` の段が実質サンプルごとになる欠点を問い、親は認めた（nih-plug の `src/plugin.rs`「Depending on the host these blocks may be as small as a single sample」。nih-plug の既定は分けない）。
    親は (sp0) 変化ごとに分ける（今の字）と、(sp1) ラッパーが分ける最小の長さ L を持ち、起動からの通しのサンプル数で数えた L の格子に変化を寄せ、枠の中は最後の値を当てる（評価は呼び出しあたり `frames / L` 回まで、変化は最大 L − 1 サンプル遅れ、出力はホストのブロックの長さに依らない）を出した。
    どちらにするかは CLAP の作業で本物のホストで測ってから決めることを推した（(t2) と同じ理由。プラグインを出す前に決まる）。利用者: 「はい。追記してください」。§19.1 のプラグインの項の「決めていないこと」に足した。
  - 残りの項目: 利用者: 「(3)はCLAPのラッパーを作る時に考えるでOK。(4)はOnsaの仕組みとして規定の表示フォーマットを用意するのか、それともラッパーごとに定義を入れるのか論点がありそうですが、これも(3)と一緒の時期に考えましょう。その他の点は異論ないですので、新しいSの候補の登録をお願い」。
    (3) 変調と (4) 表示の文字列の形（Onsa が決まった形を持つか、ラッパーごとに定めるか）は、CLAP の作業で決める（(mo1)・(tx1) は採らず、時期だけを決めた）。
    (q1)（`min`・`max` が要る、格子と `[min, max]` に収めるのはラッパーの層、整数は `(max − min) / step ≤ 2^24` で三つの形式で共通の E0809、AU のターゲットの `F64` は E0200）、(d1)、UI の文脈との受け渡し、VST3 の隠したパラメータの ID（`0x80000000` 以上）は了承。
    下書きの古い字を直す: 「あわせて決めること」の 2^24 を超える整数の AU での E0200 は、独立のレビューの段 2 の共通の E0809 に置き換わる。(q1) の「VST3 の `stepCount` は格子の数」は、区間の数（点の数 − 1）。
    新しい S の候補（`scale` と範囲の変更を凍結で止めるか）は S-584 として登録した。
    §19.1 のプラグインの項の「変調は第 1 期は受けない。表示の文字列はラッパーが数と `unit` から作る（形は約束しない）」を、CLAP の作業で決める一文に直した。
