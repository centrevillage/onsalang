# S-565 制御のレートと、`block` のクロックの位置付け

- 決定済みで戻さないもの: 第 33 組（S-555〜S-559）。とくに `when~` の `sample_rate()` は外と同じ（S-558、周期が無いため）。§19.1 のマルチレートの方向のうち「単位はインスタンス」「比は 2 のべき乗」「÷H のクロックでは `sample_rate()` は 1/H」。§11.3 の `block` の定義（ホストの区切り）、§11.6 の長さ 0 の呼び出しと `render` の一ブロック。
- 論点: S-565 の空白の 1〜3。この組の確認の E4（組込みの遅延をクロックに対して総称にする）の議論で、利用者が次の見方を出した: `block` は真の制御のレートまでの妥協で、ホストの設定でレートが変わるクロックを入れたこと自体が決定性の考えと合わない。制御の信号を `block` で扱う今、遅延が使えないのは大きな制限で、`block` は「制御のレートがたまたまブロックと一致したもの」と読み、遅延を許すべき。今直さないと後でもっと大変。
  親は、`block` に状態を許すとホストのバッファの設定・長さ 0 の呼び出し・`render` の一ブロックで結果が変わると説明し、(b) を推した。利用者は助言の担当に聞くよう求めた（二段で、利用者の見方と親の案は段 1 で伏せた）。
- 今の実装: `onsa-4aaa028 check`（入力は 47 回目の scratchpad の c01〜c06）: `x * prev~(p)`（`p` は `block`）は E0813 で候補は `prev~(p at sample)`。`p at sample` を `prev~(^y)` で平滑化する形は 0。`(…).when~(every)` は E0812（修飾子は未実装）。`lfo~(rate)` を `sample` で書く形は 0。
- 案: 
  - (a) `block` に状態を許す（`prev~` は前の `process` の呼び出しの値）。実装は小。前のブロックの値は、区切り・長さ 0 の呼び出し・`render` で変わる。`block` には `sample_rate()` に当たるレートが無く、LFO や平滑化の時定数がブロックの数になり、ホストで変わる。呼び出しを分割すると結果が変わる。
  - (b) `block` は状態を持たず、制御のレートの状態は `x.when~(tick~(N))`（N サンプルごとに真の `Bool`）で書く。実装は 0。中の `sample_rate()` は外のまま（S-558）なので、時定数を手で N で割る。忘れると黙って N 倍ずれる。後で `with` を足すと二つ目の書き方になる。
  - (c1) 名前付きの制御のクロック（`clock ctl = sample / 64`、`at ctl`、遅延の総称）を今入れる。実装は大（宣言の構文、利用者名のクロック、半順序、クロックごとの段と保持、W4〜W10）。インスタンスを別のクロックで動かすには `with` が別に要り、第 33 組の修飾子と二重になる。
  - (c2) 修飾子 `x.every~(N)`（周期の部分クロック）。K の N 刻みに 1 回動き、位相のカウンタは状態（`init` と `reset` で 0）、最初の刻みで動く。出力は保持（S-558）。中の `sample_rate()` は K の 1/N、`prev~` は動いた刻み。`N` は定数式で `N >= 2`、2 のべき乗（後で緩められる）。
    合成は S-557 のまま（`x.every~(64).when~(c)` など）。名前は修飾子の名前空間に足すので予約語は増えない。実装は `when~` の上に、名前一つ（W4-04）、カウンタの欄と条件（W7-03）、子の `sample_rate` を `sr / N` で初期化（W8）、C（W10）で、`when~` の 1〜2 割の増分。
  - (d) `block` そのものを固定の周期（`sample / N`）に読み直す。今のプログラムの意味が変わる（パラメータの反映が最大 N-1 サンプル遅れる、長さ 0 の呼び出しで `block` の段が走らない、係数の計算が N サンプルごと）。N を誰が決めるかが境界に出る。
  - (e) パラメータを `at event` で届け、`block` を廃する。全てのパラメータに保持の変換が要り、今の API と例が全て壊れる。
- 他言語: SuperCollider の `kr` は、サーバの固定の `blockSize`（既定 64）を制御の周期とする（ServerOptions、UGens-and-Synths の文書）。Pure Data のブロックは 64 で固定。Cmajor は固定の比のノード単位のレート（`MyProcessor / 2`、`processor.frequency`）。
  Faust の制御は compute の頭で一度読み、平滑化はサンプルのレートの状態（`si.smoo`）。CLAP・VST3 のパラメータの変化はブロックの中の位置を持ち、CLAP には音声の無い `flush()` がある。JUCE の `SmoothedValue` はサンプルのレートの状態。
  制御のレートを持つ環境は周期を固定の比で持ち、ホストの API はブロックに状態を持たない（参考で、根拠は §11 と §19.1）。
- 推奨と理由: (c2) と、`block` は変えない形。組込みの遅延は、第 1 引数のクロックで刻む（`sample` かイベントのクロック）。確度: `block` を変えない 高、(c2) の形 中。
  - 原則（§11.3 と §19.1 に一文）: 状態を持てるのは、刻みがプログラムの入力だけで決まるクロック（`sample`、修飾子が作る部分クロック、イベントのクロック）。`block` の刻みはホストが決めるので状態を持てない。
  - `block` の値がホストの区切りに依ることと、計算がホストの区切りに依ることは別である。`block` の値（パラメータ）はホストが渡す入力で、イベントの位置と同じ側にある。状態が無いので、出力は状態とその位置の入力と効いているパラメータだけで決まり、`render` と細切れの `process` が一致し、ラッパーが呼び出しをパラメータの変化の位置で分割しても結果が変わらない（CLAP・VST3 の位置付きのパラメータを、言語を変えずにサンプル精度にできる）。
    `block` に `prev~` を置くと、プログラム自身の時定数が区切りに依り、同じ入力から違う出力が出る。`block` にはレートが無く、「一致」も定義できない。
  - 利用者の「今やるべき」には同意し、やる中身を「`block` を触らないことと、制御のレートの形」とする。`block` の意味を後で変える方が、アプリができた後の手戻りが大きい（X-7 が導くクロックを後回しにした理由は「境界を変えない足す向き」で、(a)・(d) はそれを満たさない）。
  - (c2) を (b) より採る理由: (b) の中の `sample_rate()` は外のままなので、`smooth~(g, 0.01)` を間引きの下で使うと黙って N 倍遅くなる（コンパイラは気付かない）。(c2) では同じ `smooth` が秒のまま正しく動く。仕様の例と std は `every~` だけを使う。
  - 遅い向きの導くクロックは修飾子で閉じ、`clock` / `with` / `at (sample / 32)` は速い向き（オーバーサンプリング）の候補だけに残す。§19.1 の「`block` と導くクロックには大小が無い」は、導くクロックをインスタンス単位にすると論点が消えるので外す。
  - パラメータ（第 35 組の前提）: `@param` は `block` の入力のまま、`Params` を呼び出しごと。ラッパーは位置付きのパラメータの変化で呼び出しを分割してよい。長さ 0 の呼び出しは `flush` に当たる。パラメータを `at event` で届ける形は今は採らない（後で足しても壊さない）。
  - 組込みの遅延（E4 の改め）: 第 1 引数は `sample`（インスタンスのクロック）か、イベントのクロック。`block`・`init`・定数は E0813 のまま（note に `prev~(p at sample)` と「flow に分けて `.every~(N)`」）。イベントのクロックの `prev~(n)` の出力はそのイベントのクロックの値で、`sample` の式では読めない（S-563 (1c)）。
  - 例: `let g = smooth~(db_to_amp(level), 0.01)`（サンプルごと）、`let m = lfo~(rate).every~(64)`（制御のレート）、`let c = cutoff_path~(cutoff, 0.005).every~(32)` を `biquad~(x, c)` に渡す（係数の設計を 32 サンプルに 1 回）。
  - `block` の `prev~` の唯一の実用（パラメータの変化の検出）は `p != prev~(p at sample)` で同じ結果になる（呼び出しの先頭のサンプルで真）。
