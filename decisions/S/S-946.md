# S-946 具体化の上限の中で、Core のメモリが機械を超える形

- 空白: 具体化の上限（§4.4、§4.5）の内でも、降下のメモリが 16 GB を超える形がある。S-290 の下書きは最悪を「15 段で約 750 MB」と見ていたが、実測で覆った。診断は出ず、OS に殺されるかスワップで固まる。測定と原因は R-391 にある。
  案: (a) 規則を足さず記録し、W8-01 で Core の型を共有する。(b) 数の上限を下げる。(c) 数え方に型の大きさを入れる。(d) 型の大きさの合計に別の上限を置く。(e) 今 Core の型を共有する。(h) 展開した全体の大きさに上限を置く。実際のメモリの量で止める案は §4.4 の理由に反するので外した。
- 決定: 決定（2026-11-07、利用者。122 回目）: (a)。規則を足さず、値も変えない。仕様は変えない。測定と直しの形は R-391 に記録し、Core の型を id で引く形は W8-01 で行う。
  理由: メモリには本体の大きさと型を使う回数が掛かるので、(b)・(c)・(d) はどの値でも抑えられず、規則と例外だけが増える。(e) は正しい直しだが、W8-01 が Core を作り直すので今は二度手間である。問題の形はふつう現れず、メモリの上限に頼る使い手も今はいない。
  (h) は本当に効く唯一の規則の形で、(e) の後に頼る使い手が出たら候補にする。
- 経緯: 122 回目（2026-11-07）、W5-23 U2 の実装の測定で見つけた。親は初め (c) を見込んでいたが、独立のレビュー（段 1、伏せた版）が型の小さい形でも機械を超えることを実測で示し、(a) を選んだ。親が再現して (a) に改めた。段 2 は省いた。
- 回答: (a)（2026-11-07、利用者）。規則の文は「共通のルールとしては特殊すぎる」ので、機械に高負荷を与えない規則の例として足す
