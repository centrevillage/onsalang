# S-725 署名と型の定数式（配列の長さ、const 引数）が、ソースで後ろに書いた `impl` の関連定数を読む形（宣言の順に頼るか）

- 決定済みで戻さないもの: 同じ `impl` のメンバを署名の前に表へ入れること（W4-04 U6）、関連定数を定数式に書けること（§4.5）、定数の評価の循環の E0312（§6.6）。
  第 67 組の下書きの「S-725 の仕組みの出所」と「S-725 の形の表」の節（写しは `target/notes/78/g67/draft.md`）。
- 論点: §4.5「定数式は…定数を指す名前（`cfg.N` のような修飾した名前と、`I32.BITS` のような具体的な型の関連定数を含む）」と、§15.1 の名前の解決。署名と型の定数式の参照が、項目の宣言の順に頼るかが書かれていない。
  表のとおり、最上位の定数・本体・`const` の初期化式・同じ `impl` のメンバは順に頼らず、他の `impl` の関連定数を署名から読む形だけが順に頼る。モジュールをまたぐと、ファイル名の順で結果が変わる。
- 今の実装: 表のとおり（`d1`・`d2`・`d4` は E0302「cannot find `S.N`」「cannot find `P.N`」、`d3` は通る。登録のときと同じ）。
  別に、同じ根の誤りを見つけた（親が R-299 に登録した）: 後ろに書いた最上位の `const K: I32 = 2` を署名の配列長に書く `type A = [F32; K]`・`fn f(a: [F32; K])` は通る（`ty2.txt`、`onsa-5fc054e` と `onsa-4fb3fda` も同じ）。
  先に書けば E0401「a constant expression has the type `U32`; `K` is `I32`」である。定数の型が、使う所の検査のときにまだ下ろされていないため（推測。コードの確かめは `sig.rs` の def の順まで）で、§4.5 に反する形が黙って通る。
- 案: 
  - (1) 順に依らずに引く。全ての `impl` のメンバ（関連定数と関連関数）は、どの署名からも引ける（自分の型のフィールドの長さが自分の `impl` の関連定数を読む `d1` も、閉路でなければ通る）。閉路は定数の評価の E0312 のまま。
  - (2) 署名の段では、先に宣言した `impl` のメンバだけを引き、後ろは E0302 とする（note で `impl` を前に移すことを示す）。モジュールをまたぐ順（今はファイルの経路の順）を仕様に書く必要がある。
  - 書き手から見て: Rust の慣習の並べ方（型の宣言の後に `impl`、型別名は先頭）で `type Frame = [F32; Cfg.N]` を書くと、(2) では E0302 になる。E0302 は「名前を足すか綴りを直す」の直し方で、名前が在る誤りの直し方と違う（(2) は note を足しても、コードは見つからない名前と同じ）。
    モジュールをまたぐ形は、(2) では書き手がファイルの名前で決まる順を知る必要がある。(1) はどちらも通る。
  - 修正候補: どちらの案も新しい候補は無い（(2) は note だけ）。
  - 通るプログラム: (1) は今 E0302 の形を通す（増える）。(2) は今と同じ（同じ単位のメンバとファイルの順の扱いを仕様にする）。(2) から (1) へ緩めても既存のプログラムは壊れないが、(1) から (2) へは壊れる。
  - 規則と例外: (1) は、最上位の定数と本体と同じく順に頼らない、の一文で、例外は無い。(2) は「署名の関連定数だけは先に宣言したものを引く」の例外と、モジュールの順の規則が増える。
  - 実装の量（W4-05、署名の型）: (1) は `lower_signatures` の前に、全てのモジュールの全ての `impl` のメンバの名前を `assoc` に入れる段を置く（今の `impl` の枝の表の入れ方と E0304「defined twice」をそこへ移す。約 15〜25 行）。
    関連定数の型も、引いた時点で下ろされている必要がある（`ty.txt` の `assoc_before_i32` の E0401 を保つため。別名の `alias_ty` と同じく使う所で下ろすか、前の段で下ろす。約 +5〜10 行）。上の最上位の `const` の誤りも同じ所で直る見込みである。
    (2) は今の順を残し、E0302 に note を足す（約 +5〜10 行）が、ファイルの順を仕様に書き、モジュールを集める順（`package_tree`）をその約束にする。
  - 後の作業: (1) は第 2 期の trait の関連定数（`T.ZERO` の利用者の trait 版）も同じ段で入れればよい。(2) は trait の関連定数と `impl Tr for P` の関連定数にも順の規則を広げることになる。
- 他言語: 
  - rustc 1.94.1（`probe/rs/s725.rs`、edition 2021）: `struct S { a: [f32; S::N] }` の後の `impl S { const N: usize = 2; }`、`type A = [f32; P::N];` と `fn f(_a: [f32; P::N])` の後の `struct P; impl P { const N: usize = 2; }` は、どれも通る（使わないフィールドの警告だけ）。
  - Apple clang 21（C++20、`probe/rs/s725.cpp`）: `struct S { float a[P::N]; };` を `struct P { static constexpr int N = 2; };` より前に書くと、「incomplete type 'P' named in nested name specifier」の誤り（宣言の順に頼る）。
  - Swift と Zig は未確認（Zig は手元に無い）。
- 推奨と理由: (1)。確度: 高。
  - 最上位の定数、本体、`const` の初期化式、同じ `impl` のメンバは既に順に頼らない。署名の関連定数だけが順に頼るのは実装の段の順から来た違いで、書き方（どこに `impl` を置くか、ファイルの名前）だけで結果が変わる。
  - (2) は例外の規則と、仕様に無いモジュールの順の約束を足す。E0302 は名前の在る誤りの直し方を取り違えさせる。
  - 実装は署名の段の前に表を作る一段（約 20〜35 行）で、W4-05 に閉じ、第 2 期の trait の関連定数も同じ段で受けられる。
  - あわせて決めること: 後ろに書いた最上位の `const K: I32` を署名の配列長に書くと黙って通る誤り（上の今の実装の欄）は、親が R-299（重大度は中、W4-05）に登録した。同じ W4-05 で直す（定数の型を引いた時点で下ろす）。
  - 別の S にしてよい論点: 無い。
- 影響: 仕様 §15.1 か §4.5（(1) は「項目と関連の名前の引きは書いた順によらない」の一文、(2) は例外と順の規則）。`tasks/diag-codes.md` は変わらない。
  作業は W4-05（署名の型と整形性）。W4-04 の U6 の同じ `impl` の扱いは (1) の段に含まれる。テストの票に表の E0302 の行（同じモジュール、他の型の `impl`、二つの `impl`、自分の型のフィールド、const 引数、他のモジュールの両方の順）と、型の誤りの `assoc_before_i32`・後ろの最上位の `const` を足す。
