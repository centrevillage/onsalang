# S-639 export する項目を指定する場所: マニフェストの `[export]` の `flows`・`fns` か、ソースの属性 `@export` か

- 空白: §15.3 は、export する flow と関数をマニフェストの `[export]` の `flows`・`fns`（項目の経路の配列）で指定し、§11.7 は「export する flow の `block` の入力には `@param` か `@host` が必須（E0809）」とする。
  「export するか」はマニフェストに、「export する flow の入力の情報（`@param`・`@host`）」はソースにあるので、二つにまたがる検査をどの段で出すか（第 50 組の S-632 の軸 B）が問題になる。今の実装は、export の必須も `[export]` の経路の誤り（E0302・E0303）も `onsa build` でだけ出し、`onsa check` は 0 である。
  指定の置き場所を、ソースの属性（`@export`）にするかを決める。
- 決定: 決定（2026-10-24、利用者が了承。60 回目、第 51 組）: (a)。export する flow と関数は、宣言に属性 `@export` を付けて指定し、マニフェストの `[export]` は `prefix` だけにする（`flows`・`fns` を外す。両方には書かない）。印は属性でキーワードにしない（51-A1）。
  付けられるのはトップレベルの `fn` と `flow` だけで、引数は取らない。他の場所と `@export(…)` は E0005（修正候補は `@export`）。`pub` は S-165 のまま（E0303 は宣言の検査）（51-A2）。
  export の必須（E0809）と境界の型（E0810）は `onsa check` が宣言の位置で出す（終了コード 1）。ターゲットで決まるもの（E0610・E0820・E1011、S-581・S-583）はそのビルド（51-A3。S-632 の軸 B はこれで決まった）。
  `prefix` は `@export` の項目を出すターゲットのビルドで必須（無ければ E1104、修正候補は `prefix = "<package>_"`。(p2)）で、`prefix` があって `@export` が無くても誤りにしない（(q1)。51-A4）。出すのはビルドするパッケージの `@export` だけで、依存のパッケージ（`std` を含む）の `@export` は出さず誤りにもしない。宣言の検査はどのパッケージでも同じ（(dp1)、51-A5）。
  `onsa interface` に `@export` を出す（51-A6）。`[[plugin]]` の `flow` が `@export` の flow でなければ E1103（`onsa.toml` の位置、終了コード 2。51-A7）。
  §18.1 のマニフェストの診断の一覧から `[export]` の経路の E0302・E0303・E0308 を外し、理由の文を改めた。`spec/foreign-forms.toml` の `extern_fn`・`export_c` の文を `@export` に直した（候補は作らないまま。51-A8）。
  §6.5 の一覧と受理に関わる検査、S-574 の誤りの位置（51-A9）。§14.2 の「エージェントに書き込み権限を与えないファイルで管理する」の理由を消し、内容を人の判断に留める仕組みはポリシー（§15.4）と書いた。§15.4 の凍結の対象の候補に export の集合を足した（51-A10）。
  W4-02 の閉じた表から `flows`・`fns` を外し（書けば E1102、専用の候補は無い）、事例（93 ファイル）は道具で一度に書き換える（51-A11）。export する関数のシグネチャの誤りのコードは S-640。
  理由（段 2、利用者の言葉から）: export の検査に要る情報（export するか、`pub`、`@param`・`@host`、境界の型）が全て宣言にそろい、`check` と LSP が宣言の位置で出せる。経路の文字列の規則（E0302・E0308・E1103 の三行）が消え、改名や移動で経路が古くならない。
  マニフェストに置く理由（書き込みを人が管理する）は、守るのが集合と名前だけで、利用者が把握したいのは書き込む内容なので決め手にならない。仕様 §6.5、§11.7、§11.9、§11.11、§14.2、§14.3、§15.3、§15.4、§18.1、§18.2、§19.1
- 経緯: 60 回目（2026-10-24）、第 50 組の B2（export の必須を `check` で出すか）を説明した会話から。利用者「なるほど、これはexport対象か？という情報と、エクスポートされる物の詳細情報(param等)が別々の場所にあるから生じる問題ですね」、「なるほど、ではflowに`@export`アノテーションを足すのはどうですか？これで記述場所は揃うと思いますが？」。
  出所（親が確かめた）: Draft 0.1 はソースの `export proc voice as "kumi_voice"` とマニフェストの export 先の二か所に書いていた。
  Draft 0.2 は「書く場所を一つにする」と「`as` の二つの意味（数の変換とシンボル名）をやめる」ためにマニフェストの `[export]` と `prefix` にした（`history/onsa-0.2-changes.md` 50 行、`history/onsa-lang-spec-0.2.md` 948 行）。
  ターゲットごとに定義するためではなく、今の `[export]` もパッケージの表である（§15.3）。
  親の言い直しへの利用者の回答（案 `@export` の範囲）: 1「導入するなら`@export`だけにすべきですね」（`flows`・`fns` を置き換え、両方には書かない）。2「prefixはマニフェストのままでいいと思います」。
  3「fnの場合、`@param` のような事情がないので、マニフェストに残してもそれほど問題ないですが、扱いを揃えてコード側に`@export`指定でも良いと思います」。
  4（依存のパッケージの `@export`）「依存パッケージの分は出さない、で良いと思います。そういうケースが必要になったら、依存パッケージだけはマニフェストにかけるようにする、という回避策は考えられます。そのとき、`@export`指定のないものまでマニフェストにかけるか、は必要になったら検討で良いと思います」。
  期限は W4-02（マニフェストのキーの検査。§15.3 の表に `flows`・`fns` がある）。決め方は空白の流れ（第 51 組）。S-632 の軸 B はこの結果で決まる。
  60 回目（2026-10-24）、第 51 組（下書き `S-639.draft.md`、助言の担当の二段）。下書きと段 2 は (a)、段 1 は (m)（今のまま）で、主な理由はマニフェストを人が管理する目的だった。段 2 は、段 1 の後の利用者の言葉（「ユーザーが把握したいのは、書き込むファイルではなく、書き込む内容です」）と親の添えた事実からその理由を決め手でないとし、(a) を採った。
  利用者が (a)（「(a)で良いと思います」）と確認だけの項目 51-A1〜51-A11 を了承した（「A1: `@export`で良いです。A2: OK … A11: OK」）。
