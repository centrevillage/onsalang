# S-1264 検査付きの添字の代入先に集成体を直接構築する形（`ps[i] = mk(k)`）で、右辺の panic と添字の検査のどちらが先か（§3.5 の「右辺を先に評価し、その後に代入先の場所」と、§12.7 の代入先への直接構築がぶつかる）

  - §3.5 の評価順（S-75、R-93、2026-10-04）。代入は右辺を先に評価し、その後に代入先の場所（添字の式）を評価する。panic しうる式が複数あれば、この順で最初に panic する式を報告する。下の案 (c) だけがこれを改める案で、項目の中で名指しする。

## 仕組みの出所と目的

- §3.5 の代入の順: R-93（インタプリタと C で評価順が違い、`ys[next(inout k)] = next(inout k)` で C が場所を先に評価していた）を受けて、S-75 で「Rust と同じ」規則を書いた。目的は、全ての変換先で同じ順にすること（§13.4）と、書き手が読める一つの順を約束することである。
  「最初に panic する式が報告される」も同じ回の文で、例は `xs[i][j]` で両方が範囲外なら `i`（`r93.onsa` の "two out-of-range indices"）。代入の右辺と代入先の添字が両方 panic する形の例は無い。
- §12.7 の直接構築: 0.3 の改訂の I-04（「大きな返り値をコピーしない保証の範囲が無い」、`history/onsa-0.3-changes.md`）で置いた節で、0.2 の `init` の「呼び出し側の領域に直接構築される」を広げた。目的は節の頭の字のとおり「`echo.State` のような大きな状態をスタック経由でコピーしない」ことである。§17.6 の `Poly.new` の `voice.init` の結果を、途中で写さずに呼び出し側の `var` に置くことを例に挙げる。
  置き場所の一覧（束縛、代入先、struct のフィールド、配列の要素、返り値）の「配列の要素」は、例から読むと配列のリテラルや `array.from_fn` の要素で、`ps[i]` の形の代入先は「代入先」に入る。
  重なりの段落は S-76（R-09: `x = swap2(x)` が `al__swap2(&x, &x)` になり C が壊れた）で足した。
- 正規形（D-03 の R-81 の追記）: R1 は書き込みと文を含む式を文の位置に置く。R2 は文の位置の木の効果を一つまでにする。R3 は評価順に並べ、書き込みの前の読みを先に出す。R4 は条件の内側から出す文を内側に置く。
  目的は、C の `is_stable` のような出力の字からの推測をやめ、評価順を Core の文の並びだけで決めることである。インタプリタも C も同じ正規化の後の Core を読むので、両者の順は Core で一つに決まる。
- 宛先と NRVO（W8-05、R-80 (2)、R-81 (3)）: 集成体を作る式は宛先の位置にだけ置き、宛先は構築に使う値と重ならない（V-13）。メモ 4.3 は S-1264 の二つの読みを Core の形で示す。
  (1) 右辺が先なら `Let(t, mk(k)); Assign(ps[i], Move(t))`。(2) 添字が先なら `Alias(r, ps[i])`（ここで検査）`; Assign(r, mk(k))`。
- 衝突の場所: 検査付きの添字は、検査の前には番地が決まらない（範囲外の番地には書けない）。直接構築は、右辺を評価する前に番地が要る。§3.5 は番地の検査を右辺の後に置く。この三つが同時には成り立たない。
  添字の無い代入先（局所変数、フィールド、`inout` の引数そのもの）と、検査の無い添字（`Bounds::Known`、flow の `process` のサンプルのループ）には衝突が無い。

### インタプリタと C の今の食い違い（R の候補、番号は振らない）

- C の `assign_into` は、集成体を返す呼び出しと `if`・`match` の腕の右辺に、代入先の場所 `&ps.a[onsa_idx(…)]` を出力の引数として渡す。そのため C は、代入先の添字の式と検査を右辺より先に評価する。
  panic の報告が変わる（3・5・6・9・10・12）だけでなく、通るプログラムの値が変わる（15・16・17、読みの見込み）。インタプリタは三つとも §3.5 のとおりである。
  スカラの §3.5 の例（`ys[next(inout k)] = next(inout k)`）も、今の C は場所の `next` を先に一時に取る（`c3/`）。R-93（OPEN、直しは W8-03）の根と同じなので、新しい R でなく R-93 の補いの候補である。集成体の形（15〜17）を W8-03 の評価順の事例に入れる。
- 18 と、局所変数の `p = swap_nrvo(p)`（`c4/`）は、C が同じ場所を出力と引数に渡す（`swap_nrvo(&p, &p)`）。NRVO の本体が先に `*out` を 0 で埋めるので、C の値は壊れる見込みである（インタプリタは通る）。R-09（OPEN、W8-05）と同じ形で、添字の形は補いの候補である。

## 他言語の調べ（まとめ）

項目の「他言語」はこの節を指す。参考にとどめる。

- Rust（rustc 1.94.1、手元 `r.rs`）: `ps[idx(i)] = rhs(k)` は「rhs、index expr、範囲の検査」の順で、両方が失敗すると `attempt to divide by zero` を報告する。`Vec` も同じ。
  `--emit=mir` では `_4 = rhs(…)` を一時の局所に作り、`idx`、`assert(Lt(…))` の後に `(*_1)[_5] = move _4` で写す（右辺が先で一時から写す形）。Reference の「Assignment expressions」は、右辺を先に、代入先を後に評価すると書く。
- C（clang 21・gcc-15、`-std=c11`、`c.c`）: 代入の左右の評価は順序付けられない（C11 6.5.16p3）。手元の両者は `-O0`・`-O2` とも左の添字を先に評価した。
- C++（clang++ 21・g++-15、`c.cpp`）: C++17 は代入の右辺を左辺より先に順序付ける（[expr.ass]/1）。`-std=c++17` は両者とも「rhs、index expr、operator[]」で、`v.at(idx(5)) = rhs(0)` は右辺の例外になる。
  `-std=c++14` の g++ は左が先で `out_of_range` になり、clang++ は右が先だった（C++14 では順が決まっていない）。代入はコピー省略の対象でなく（C++17 で省略が保証されるのは初期化だけ）、右辺の一時から移動代入する。
- Python 3.14.5（`p.py`）: 右辺を先に評価し、その後に添字の式と `__setitem__`（範囲の検査）。両方が失敗すると `ZeroDivisionError`。
- JavaScript（Node v26.11.1、`n.js`）: 添字の式、右辺、プロパティのキーへの変換、書き込みの順。配列の範囲の検査は無い（型付き配列の範囲外の書き込みは黙って捨てる）。
- Swift 6.3.3（`s.swift`）: 添字の式、右辺、accessor（`set` も `_modify` も右辺の後に始まる）。`Array` の範囲の検査は accessor の中なので、右辺の後の見込み（範囲外は trap するので走らせていない）。
- Java（手元に無い。JLS 21 §15.26.1）: 配列の参照、添字の式、右辺を評価し、その後に `null` と範囲を検査する。Example 15.26.1-1 の出力では、`null` の配列に例外を投げる右辺を代入すると右辺の例外になる（`null[1]=throw => RightHandSideThrow`）。
- C#（手元に無い）: 規格（§12.24.2 Simple assignment）は「`x` を評価し、その後に `y`」で、配列の要素の評価が範囲を検査するので、規格の字では範囲の検査が右辺より先である。
  Microsoft の実装は右辺の後に `null` と範囲を検査し、規格と食い違う（dotnet/csharpstandard の issue #1478、2025-11-23）。
- まとめ: 添字の式を先に評価する言語（Java、C#、JavaScript、Swift）もあるが、範囲の検査を右辺より先にするのは、手元と文書で確かめた中では C# の規格の字だけである（実装は後）。Rust、C++17、Python は右辺が先である。

### S-1264 検査付きの添字の代入先に集成体を作る形の、右辺の panic と添字の検査の順

- **論点:** §3.5 は「代入は右辺を先に評価し、その後に代入先の場所（添字の式）を評価する」「この順で最初に panic する式が報告される」とする。§12.7 は「集成体を返す式は、その置き場所に直接構築される」とし、置き場所に代入先を含める。
