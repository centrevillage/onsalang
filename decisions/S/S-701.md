# S-701 第 1 期の std が宣言するファイルの効果の名前（§8.1 の「標準ライブラリは `FsRead` と `FsWrite` を分けている」と、仕様の例・§8.2 の表・§15.3 の `provides` の `Fs`）

- 空白: §8.1 の 16 行は「効果行は効果単位（`Fs`）で書く。標準ライブラリは `FsRead` と `FsWrite` を分けている。本仕様の例では簡単のため `Fs` を使う」とする。一方、§8.1 の標準の効果の一覧、§8.2 の表、§15.3 の `provides`、§17 の例は `Fs` だけを書く。
  第 1 期の std が効果を宣言するとき（S-659 の (A)）、宣言する名前が `Fs` か、`FsRead`・`FsWrite` か（両方か）が決まっていない。
- 決定: 決定（2026-10-26、利用者。71 回目、第 63 組、(B)）: (1)。第 1 期の std が宣言するファイルの効果は `Fs`。§8.1 の「標準ライブラリは `FsRead` と `FsWrite` を分けている。本仕様の例では簡単のため `Fs` を使う。」を消す。
  理由（利用者）: 読み書きの権限で効果を分けると、ファイルの権限と開く形（`w`・`w+` など）を扱いにくくなる。効果は外部の資源に触れる権限で、資源ごとの権限は別のものである。
  第 2 期に `Fs` の操作を入れるとき、資源ごとの権限（読みか書きか、開く形）は効果に分けず、操作の側（開く操作の引数など）で扱う（`tasks/phase2.md`）。この解釈は仕様の一般の原則としては書かない（利用者: 拡大解釈を防ぐ）。当てるのはファイルの効果の中の権限だけである。実装は W4-03 の U5。
- 経緯: 70 回目（2026-10-26）、第 63 組（S-659）の下書き（onsa-gap、`target/notes/70/g63/draft.md`）が新しい S の候補として挙げ、親が仕様の文を確かめた。S-659 の (A) で std が標準の効果を宣言するなら、U5 の前に決める。
  71 回目に親が確かめた出所: 16 行の文は最初の仕様（`history/kumi-lang-spec.md`）の「粒度が要るなら効果を分ける（標準ライブラリは `FsRead` と `FsWrite` を分けている…）」の例えの名残で、std が宣言したことは無い。
