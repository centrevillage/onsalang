# S-672 `priv struct` のフィールドに書いた `priv` を冗長の E0020 にするか（S-662 では `priv` の型の `priv fn` を、型を広げてもモジュールの中に残す印として許した）

- 決定済みで戻さないもの: フィールドは struct の可視性を継ぎ、狭めるときだけ `priv`、フィールドの `pub` は E0020（S-35）。`pub struct` のフィールドの `pub(crate)`・`pub(pkg)` は候補なしの E0002（S-420）。可視性の 3 段階（S-36）。
  可視性を書ける項目（S-491）。メンバの届く範囲と、型より広い `pub` の E0020、`priv` の型の `fn` と `priv fn` の両方を許すこと（S-662）。`onsa interface` の表示（S-660）。タプル形の struct の候補のフィールド（S-494）。表の 1〜9・11 の行。
- 論点: §15.1「広げる向きの指定は無く、フィールドに `pub` を書くと継いでいるので冗長で E0020（修正候補は外すこと）。`priv struct` のフィールドの `priv` も同じく E0020」。
  同じ節のメンバの文は「語の無いメンバと `priv` のメンバは、どの型にも書ける。`priv` の型の `fn` と `priv fn` はどちらもモジュールの中に届き、型の可視性を広げると、`priv fn` はモジュールの中に残り、`fn` は型に連動してパッケージの中まで届く」（S-662）。
  同じ理由はフィールドにも当たる（二つ目の表）。`priv struct` を広げると全てのフィールドが型に連動し、モジュールの中に残したいフィールドに前もって印を付けられない。フィールドの `priv` を今のまま E0020 にするか、メンバと同じく許すかを決める。
  - 仕組みの出所と目的:
    - フィールドが struct を継ぐ規則は S-35（2026-10-03、R-38）から。理由は「データをまとめるだけの struct が多いので既定は継ぐ形にし、必要以上に可視性を狭めて利用側が回り道をするのを避ける」（`history/onsa-0.3-changes.md` の S-35 の行。R-38 の「OOP 的なカプセル化は好まない」）。
      フィールドの `pub` を E0020 にしたのは、継ぐので広げる指定が無く、`pub` を書くことが既定の誤解を示すからである（§0.5.1 の例に「フィールドの `pub`」）。
    - `priv struct` のフィールドの `priv` の E0020 は、`5d74cbf`（2026-10-03、R-50・R-106 の決定で可視性を 3 段階にした回、S-36）が §15.1 に「同じく E0020」と足した。決定の文（S-35・S-36）にこの文の理由は無い。
      「同じく」は、フィールドの `pub` と同じく継いだ可視性を重ねて書く形として扱ったと読める。当時はメンバの可視性と型の可視性の関係が決まっていなかった（S-662 は 2026-10-25）。
    - 実装は W3-08（`47651d5`、2026-10-13）の構文の段の行 `field_priv_in_priv_struct`（`crates/onsa_syntax/src/foreign/decls.rs` の `field_visibility`、`rows.rs`、`spec/foreign-forms.toml` の行、origin は「Java と C++」）。
      S-494（2026-10-13）は、この文を理由に、`priv struct Level(I32)` の候補のフィールドを `priv value` でなく `value` にした。
- 今の実装: `priv struct Hidden { priv x: I32, y: I32 }` は `priv` に E0020「the fields of a `priv struct` are `priv` already」、候補「remove `priv `」、note「a field inherits the visibility of its struct; only `priv` is written on a field, to keep it within the module (§15.1)」（`priv_field.onsa`）。
  一つの宣言の単位に一つなので、`priv` のフィールドが二つの struct は一つずつ出て、候補を二度当てると診断なしになる（`two.onsa`、`two_step1.onsa`、`two_step2.onsa`）。
  `priv` の型の `impl` の `priv fn`・`fn`・`pub fn` は、今はどれも通る（`members.onsa`。`pub fn` の E0020 は U4）。
  `onsa interface` は、`pub struct Shown { priv x: I32, y: I32 }` を `x: I32` と `y: I32` で出し、`priv` の語を付けない（`widened.onsa`。S-660 の表示は U4）。`priv struct` は並べない。

- 案: 
  - (a) 今のまま。`priv struct` のフィールドの `priv` は冗長の E0020（候補は外す）。
    - 書き手から見える違い: 表の 10 は E0020。候補を当てると一度に一つずつ外れ、診断なしで止まる。
    - 型を広げたとき: 全てのフィールドが型に連動する（二つ目の表の `x` の行）。モジュールの中に残すフィールドには、広げるときに `priv` を書き足す。`pub` に広げると、書き足し忘れたフィールドはパッケージの外まで届く。
    - 型を狭めたとき: `struct P { priv inv: I32, data: I32 }` を `priv struct` にすると、`priv inv` が E0020 になり（`narrow.onsa`）、候補で印が消える。もう一度広げると `inv` は型に連動する。メンバの `priv fn` は狭めても残る。
    - `onsa interface`: `priv struct` は並ばない。広げた後は、書き足した `priv` のフィールドだけが `priv` 付きで並ぶ（S-660）。
    - 実装の量: 0 行。
  - (b) 許す。`priv struct` のフィールドの `priv` は通り、fmt も残す。
    §15.1 の「`priv struct` のフィールドの `priv` も同じく E0020」を消し、メンバと同じく「語の無いフィールドと `priv` のフィールドは、どの struct にも書ける。`priv struct` ではどちらもモジュールの中に届き、struct の可視性を広げると、`priv` のフィールドはモジュールの中に残り、語の無いフィールドは struct に連動する」とする。
    - 書き手から見える違い: 表の 10 が通る。フィールドに書ける語は、どの struct でも `priv` だけになる（今の note の「only `priv` is written on a field」がそのまま当たる）。

    - 読み手から見える違い: `priv struct` の中で `priv x` と `y` が並ぶと、`y` の方が広く届くと読まれうる（どちらもモジュールの中）。S-662 の `priv` の型の `priv fn` と `fn` と同じ形である。
    - `onsa interface`: `priv struct` は並ばない（どの案でも同じ）。広げた後は、前もって付けた `priv` のフィールドが `priv` 付きで並ぶ。

- 他言語: （参考。型と同じか狭い可視性をフィールドに書くのを冗長とするか）
  - rustc 1.94.1（手元、`other/lib.rs`・`lib2.rs`）: 非公開の `struct Hidden { pub(crate) x: i32, pub(self) y: i32, z: i32 }` と、非公開のモジュールの `pub(super) struct S { pub(super) a, pub(self) b, pub c }` は、`#![warn(unreachable_pub)]` でも何も出ない。
    同じ lint は、非公開のモジュールの `pub struct S` と `pub fn g` には「unreachable `pub` item」を出すが、フィールドの `pub c` には出さなかった。既定と同じ範囲の `pub(self)` も黙って通る。
  - Swift 6.3.1（手元、`other/a.swift`、`-typecheck`）: `private struct Hidden { private var x; fileprivate var y; var z }`、`fileprivate struct F { fileprivate var a; private var b }`、`internal struct I { internal var c; public var d }` は、どれも何も出ない。
  - Apple clang 21.0.0（手元、`other/a.cpp`、C++20、`-Weverything`）: `class` の中の `private:`、`struct` の中の `public:`（既定と同じ指定）に何も出ない。
  - Kotlin（未確認、手元に無い）: 文書（https://kotlinlang.org/docs/visibility-modifiers.html ）は、メンバの既定を `public` とし、「`public` means that any client who sees the declaring class sees its `public` members」とする（型の可視性で抑える）。冗長な語の検査は未確認。
  - Java、TypeScript: 未確認（Java は手元に無い。TypeScript のクラスの `private` はモジュールの可視性と別の仕組み）。
- 推奨と理由: (b)。確度: 中。
  - フィールドの `priv` は、型の可視性を広げた後の届く範囲を決める。`priv struct` の中で今は同じ範囲でも、広げると `priv x` はモジュールの中に残り、`x` は型に連動する。`priv` の型のメンバの `priv fn` を許した理由と同じ形で、印は書き手の意図を表し、誤解を示さない。
    フィールドの `pub` は広げる指定が無いので誤解を示すが、`priv` はどの struct でも意味のある唯一の語である。
  - フィールドでは、この印がメンバより効く。`priv struct` を `pub struct` に広げると、語の無いフィールドは一度にパッケージの外まで届く（メンバの `fn` はパッケージの中に留まる）。不変条件を持つフィールド（§15.1 の「隠すのは、不変条件を守るために外から書き換えられては困るフィールドだけ」）に前もって印を付けられると、広げたときに外へ漏れない。
    (a) では、型を一度狭めると候補が印を消し、もう一度広げたときにそのフィールドが外へ出る（`narrow.onsa`）。
  - 規則と実装: (b) は E0020 の行を一つ消し、フィールドとメンバの `priv` を「どの型にも書ける」の一つの文で揃える（表の 10 の違いが無くなる）。残る違いは、決定済みの語の無い形の意味（S-35 と S-662）だけになる。消す向きで約 35 行減る。(c) は (b) に fmt の規則を足し、印の意味を消す。
  - 厳しさ: (a) から (b) へ後で緩めても壊れない。代わりに、既にある決定（S-662）と同じ状況で表面の扱いが違う形を残すことになり、メンバとフィールドを並べて書く書き手が、片方だけで E0020 に当たる。決定を実装する W4-03 の中で揃える方が、後の手戻りが少ない。
  - 代償: `priv struct` の中で `priv x` と `y` が並ぶと、`y` が広く届くと読まれうる。S-662 のメンバで同じ形を受け入れたのと同じ代償で、`onsa interface` は `priv` の型を並べないので、外への表示には出ない。
