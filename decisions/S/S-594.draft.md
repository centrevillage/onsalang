# S-594 族: §15.1 の use の経路と並び

- 決定済みで戻さないもの（第 39 組の三つの族に共通）: 可視性の 3 段階と `pub(pkg)` の E0020、`use` の束縛はモジュールの中、`priv use` は E0020、`pub use` は `pub` の項目だけ（S-36）。フィールドは struct を継ぎ、狭めるときだけ `priv`（S-35、S-420）。他の言語の範囲を限る可視性（S-417）。メソッドの可視性（R-38）。
  `use` は絶対経路で、頭はルート直下のモジュールか依存のパッケージ名だけ、列挙子などは取り込めない（S-37、S-246）。パスの `.` の後と `use` の経路の頭のキーワードと予約語は名前として読む（S-20、S-357、S-371）。同じ名前の二度目の `use` は E0304（S-17）。構文の段で失敗した `use`（R-180）。
  読み続けた宣言（S-435・S-459・S-464。記録の規則は第 38 組の S-593 で、答え待ち）。E0302 の綴りの近い名前の候補（S-258）と `Self`（S-377・S-446）は次の組で扱い、ここでは関係だけを書く。
- 論点: 仕様 §15.1「`use std.fs.{Fs, Path}`。グロブ import は無い」「`use` の経路がたどれるのは、パッケージ、モジュール、flow の名前空間（§11.6）だけで、取り込めるのは、モジュールの項目、子モジュール、flow の名前空間の項目である」と、§2.2「パスの `.` の直後と `use` の経路の頭は、他のキーワードと同じく名前として読む」。
  書かれていないのは、(1) 取り込む名前がキーワード・予約語のとき（表の 18・19 行。S-443。並びの要素の 33・34 行とは今の扱いが違う）、(2) 並びの形のうち、空の並び（25・26 行。S-515）と、入れ子・経路・`self`・別名（29〜31 行）、(3) 並びの無い経路で項目や名前空間を取り込む形（16・17 行）と、並びで子モジュールを取り込む形（24 行）が、同じ束縛の二つの書き方か、である。
  (1) は、経路の要素としては名前として読めるのに、取り込んだ束縛を式の頭、型の位置、補間のどこにも書けない所である。

- 案:
  - (a) 取り込む名前を束縛の名前として読む。
    一（経路）: 取り込む名前より前の経路の要素は、モジュールの名前として読む（キーワードと予約語も。決定済み）。
    二（取り込む名前）: 並びの各要素と、並びの無い経路の最後の要素は、どちらも一つの束縛を作る取り込む名前で、同じ規則で読む。キーワードは E0002、予約語は E0200（34 行の S-371 と同じ）、`_` は E0002。取り込む先の種類（モジュール、項目、名前空間）によらず、二つの書き方は同じ束縛を作り、fmt は書き手の形を残す。
    三（並び）: 並びは一つ以上の名前を `,` で区切り、要素は名前だけ（入れ子、経路、`self`、別名、グロブは無く、今の E0002）。空の並びは構文の段の E0002（S-513 の要素の無い括弧と同じ）で、候補は `use` の全体を除く形（中にコメントがあれば候補なし、note で規則を示す）。
    実装: `parse_use` で、並びの無い経路の最後の要素を並びの要素と同じ検査に通す（5〜10 行）。空の並びの報告と候補（10〜15 行）。fmt は変わらない。
    事例: 否定例は E0002（キーワードの束縛、空の並び）と E0200（予約語の束縛）を各 3 件以上、候補の事例 1 件。
    費用の要因: `pub use kp.clock`（再公開した予約語の名前のモジュールを、他のモジュールが `use main.clock.{tick}` で通る形。38 行。モジュールの再公開は書かれておらず、今は通る）も誤りになる。キーワードの名前のモジュールは、並びで中の名前を取り込むか、親から辿って使う（`use kp` の後の `kp.clock.tick()`）。
  - (b) 書ける所で受け、使えない所で誤りにする（今の実装）。取り込む名前のキーワードと予約語を受理し、束縛を使う所で誤り（キーワードは E0002、予約語は E0200）。空の並びも受理し、fmt は残す。二つの書き方は (a) と同じ。
    実装: 0 行。§15.1 に 3 文。費用の要因: `use std.test` は使わなければ通り、使えば使う所ごとに、原因（束縛の名前がキーワード）を示さない「expected an expression, found `test`」が出る。空の `use` は何も取り込まず、E0310 と経路の E0302 にだけ効く。
  - (c) (a) の一・二で、空の並びは受理し、fmt が `use` ごと除く（`spec/tools.md` §3.3 の一覧に足す）。
    実装: (a) の空の並びの報告の代わりに fmt の書き換え（10〜15 行）。費用の要因: 空の `use` は依存の辺を作るので、除くと E0310（25 行の `a`・`b`）と経路の E0302（`use nosuch.{}`）が消え、§3.3 の「一覧の書き換えは、どのプログラムでも各段の判定を変えない」に反する。
    §3.3 が返り値の `move` を判定が変わるので除かないのと同じ形で、この案は成り立たない（受理するなら (b) のように残す）。
  - (d) (a) に加え、式の頭と型の位置で、空白なしの `.` が続くキーワードを名前として読み、`use std.test` の後の `test.check()` を書けるようにする。予約語は S-371 と §2.2（現れた位置で E0200）のまま。
    実装: 式と型の頭の読み（10〜20 行）と、`true`・`false`・`self`・`Self` の後の `.`（値のメソッドと `self.x`）を除く分岐。費用の要因: キーワードごとの例外の規則が増え、`match.f1()` と `match x {` の読み分けが次のトークンに依る。
  - (e) 別名 `as` を足す（`use kp.clock as clk`、`use a.{g as h}`）。
    実装: 構文、名前の段、fmt、`interface`（30〜60 行）と仕様の新しい規則。費用の要因: 一つの項目に二つの名前ができ、名前を探す道具（grep、LSP の参照）が別名を辿る。言語の機能を足す。
- 他言語:
  - rustc 1.94.1（手元）: `use a::match;` は「expected identifier, found keyword `match`」（`use` の位置で誤り）。キーワードの名前のモジュールは `r#match` と書く。`use std::f32::{};` と `use std::{};` は受理し、警告「unused import」を出す。
  - Python 3.14.5（手元）: `from os import class` と `import a.class` は SyntaxError（ソフトキーワードの `match` は通る）。`from math import ()` は SyntaxError、`from math import (sqrt,)` は通る。
  - Node v26.11.1（手元、ES モジュール）: `import { class } from "./kw.mjs"` は「SyntaxError: Unexpected reserved word」、`import { class as c }` は通る。`import {} from "./a.mjs"` は通る（モジュールを評価する意味を持つ）。
  - Go 1.27.2（手元）: 空の `import ()` は通り、gofmt も残す。Go の import は名前を選んで取り込まない。
  - TypeScript: 未確認（手元に tsc が無い）。
- 推奨と理由: (a)。確度: 中。
  - 取り込む名前は、そのモジュールに作る束縛で、宣言の名前と同じく、式・型・経路に書けなければ使えない。キーワードの束縛は、どこに書いても使えない（18・19 行の今の実装）。使えない束縛を作る `use` を誤りにすると、原因の位置に一つの誤りが出て、使う所ごとの原因を示さない誤りより直しやすい。
    並びの要素（33・34 行）は既に同じ扱いで、並びの無い経路の最後の要素だけが違う。(a) はこの違いを無くすだけで、新しい規則を足さない。
  - 経路の要素（4・5・10 行）は今のまま名前として読むので、決定済みの §2.2 と S-20・S-37・S-371 に触れない。std の `use test.{Gen}` も変わらない。
  - 空の `use` は何も取り込まずに依存の辺だけを作り、§15.1「モジュールが何に依存するかは、`use` の一覧を見れば全て分かる」の一覧に名前の無い行を足す。fmt が除くと判定が変わる（(c)）ので、受理するなら残すしかない。S-513 は要素の無い括弧を構文の段の E0002 にしたので、同じ向きにそろえる。
    候補は `use` の全体を除く形で、除いても他のどの束縛も変わらず、一度で収束する。括弧だけを除く S-513 の候補にしないのは、`use std.math` が `math` を取り込む別のプログラムになるからである。
  - 二つの書き方（16・17・24 行）は、どれも一つの名前を取り込む同じ束縛で、読みは割れない。仕様の例が両方を使い（`use std.audio.wav` と §11.6 の `use dsp.synth.{voice}`）、揃えるなら向きは構文だけで決まらない（最後の要素がモジュールか項目かは名前の段で分かる）。今のまま残し、揃えるかは別の S にしてよい。
  - (d) は値のメソッドと `self.x` を除く例外が要り、(e) は機能を足す。どちらも (a) の後で足せる（(a) で誤りだった `use` を通すだけで、通っていたプログラムは壊れない）。(b) から (a) へ移ると、通っていた `use std.test` が誤りになる。
  - 第 2 期と JS / WASM: 第 2 期の std のモジュール（`Str`・`Map` などの API）の名前は普通の名前で、この規則に当たらない。生成するコードの名前は束縛でなく経路の要素から作る（§11.6 の `__`）ので、キーワードの名前のモジュールもそのまま写る。
  - 規則から決まる S:
    - S-443: 表の 19 行（`use kp.clock`、`use clock`、`pub use kp.clock`）は `clock` の位置の E0200（34 行の `use kp.{clock}` と同じ）。15 行の `kp.clock.tick()` と 10 行の `use kp.clock.{tick}` は今のまま通る。
