# S-576 flow の遅れ（レイテンシ）を境界に出す形

- 決定済みで戻さないもの: 組の全体は S-580 の下書きの頭（第 35 組の境界の見込み、S-565 の R12、`@param` と数値の ID、S-172、§14.2 の C の API の原則、ランプは扱わない）。第 35 組の C の API への影響（A1〜A8）は S-580 の下書きの「影響」。
- 論点: §14.2 の C の API と §11.6 の生成する API は、flow の遅れ（入力から出力までのサンプルの数）を出さない。プラグインのホストは遅れの報告を求める。§19.1「集めて配ると N サンプル遅れる（`delay~(x, N)` と同じ）」。
  - 決定済み: `.down~(N)` で集めて配る所の遅れはちょうど N（S-566 の A3、S-578）。std の `fir_up2`・`fir_down2` は遅れのサンプル数を仕様に書く（S-568）。
  - 遅れの意味: AU の文書は、遅れを処理による遅れ（フィルタ、FFT）とし、効果として掛ける遅延や残響を含めない。`delay~` が効果の遅延か処理の遅れかは、本体からは分からない。
  - (1) 出す所と単位。(2) 決め方。(3) 条件で動くインスタンスと、パラメータで変わる遅れ。
- 今の実装: `delay~(x, 64)` の flow `dl` の `onsa interface` は状態（`delay_0.buf: 256 bytes` など）を出し、遅れは出さない（`t03_lat`）。`@latency(64)` は E0002「expected attribute argument, found integer literal」（`r11`。今の構文解析器は属性の引数にリテラルを読まない）。
- 案: 例:

```onsa
@latency(64)                // 先読みの遅れ。delay~ は効果と区別できないので書く
pub flow limit(x: F32 at sample, …) -> F32 at sample { … delay~(x, 64) … }
```

  - 出す所（単位は本体の `sample` の刻み）:
    - (o1) 定数: C のマクロ `<P>_LATENCY`、生成する API の定数 `limit.LATENCY: U32`、`onsa interface`。費用: 名前が二つ。サンプルレートで変わる遅れ（ミリ秒の先読み）を書けない。
    - (o2) `init` で決まる値: C の `uint32_t <p>_latency(const <p>* s)`（`init` の後の値。未初期化なら 0）、生成する API の `rt fn limit.latency(s: limit.State) -> U32`、`onsa interface` は式を出す。費用: 定数でないとき、状態に隠れた欄を一つ置く（§12.4 の配置）。
    - (o3) 両方（定数の flow にはマクロも出す）。費用: 名前が三つと、マクロの無い flow の扱い。
  - 決め方:
    - (k1) 書き手が flow に宣言する（`@latency(e)`。`e` は (o1) なら定数、(o2) なら `init` のクロックの式）。無ければ 0。子の宣言は合成せず、報告するのは一番外の flow の宣言だけ。費用: 属性を一つと式の評価。std の変換の flow を使う書き手が、自分で足し合わせる。
    - (k2) 合成する: 宣言があればそれ、無ければ本体から数える。直列は和、経路が分かれれば大きい方、`.down~(N)` で集めて配る所は N、`.up~(M)`・`.down~(N)` の中の値は比で本体の `sample` の刻みに換える。`delay~`・`vdelay~` と帰還の輪は数えない。費用: flow の計画（W7）の上の最長の経路の計算。
    - (k3) (k2) に照合を足す: 宣言の無い flow で、入力から出力への経路の遅れが違えば誤り（宣言を求める）。費用: 診断が一つ。`delay~` で乾いた経路を補った正しい書き方も誤りになる（`delay~` を数えないため）。
  - パラメータで変わる遅れ: どの案でも `block` のクロックの式は書けない（E0815）。`when~` で止まるインスタンスと、選ぶ形（`if~`・`match~`）は、(k2)・(k3) では動いているものとして数え、大きい方を取る。
- 他言語:
  - CLAP（`ext/latency.h`）: `get` は「[main-thread & (being-activated | active)]」で、`changed` は「The latency is only allowed to change during plugin->activate」。
  - VST3（`ivstaudioprocessor.h`）: `getLatencySamples()`。AU（`AUAudioUnit.h`）: `latency` は秒で、「This should reflect the delay due to signal processing (e.g. filters, FFT's, etc.), not delay or reverberation which is being applied as an effect」、
    「a latency that varies with parameter settings, including bypass, is generally not useful to hosts」。
  - DPF: `setLatency(uint32_t frames)`（`DistrhoPlugin.hpp`）。JUCE、nih-plug、Faust、Cmajor の遅れの出し方は未確認。
- 推奨と理由: (o2)、(k2)。確度: 低〜中。
  - (o2): CLAP は起動のとき（サンプルレートが決まるとき）に遅れを変えられ、ミリ秒の先読みは `init` で決まる。関数の形は定数も含み、(o1) を選んで後で関数を足すと書き方が二つになる。費用は、定数でない flow の隠れた欄一つである。
  - (k2): std の変換の flow と `.down~(N)` の遅れが自動で報告され、`fir_up2` を包む書き手が足し忘れない。書き手の意図した遅れ（`delay~` の先読み）だけを宣言すればよい。
    (k1) は足し合わせを書き手に任せ、誤っても黙る。(k3) は補った正しい書き方も誤りにするので、正しいコードと誤ったコードを分けない。(k1) から後で (k2) へ移ると、宣言の無いプラグインの報告する遅れが変わるので、今決める。
  - 弱いところ: 経路の大きい方を取るので、乾いた経路と遅れた経路を混ぜる誤り（櫛形のフィルタになる）は検査で止まらない。
  - あわせて決めること: 端数（`.up~(M)` の中の奇数の遅れ）は最後に最も近い整数へ丸める（半分は切り上げ）。属性の引数の形（`@latency(64)` か鍵の形）は §6.5 に属性を足すときに決める。ホストへの報告は CLAP の `latency`、VST3 の `getLatencySamples`、AU の `latency`（遅れ ÷ サンプルレート）。
  - 新しい S の候補: `onsa audit` で、入力から出力への経路ごとの遅れを示すこと（上の弱いところの確かめ）。
- 影響:
  - 仕様: §11.6（名前空間の閉じた一覧に `latency` か `LATENCY`）、§14.2（`<p>_latency` か `<P>_LATENCY`。A1）、§6.5（`@latency`）、§12.4（(o2) の隠れた欄）、§19.1 のマルチレートの「決めていないこと」から S-576 を外す。
  - 診断のコード: E0815（`block` のクロックの式）、E0005（属性の位置）。(k3) なら新しいコードか E0810 の範囲を広げる。
  - 作業: W7（flow の計画で遅れを数える、(k2)・(k3)）、W10-01・W10-03（C の名前）、M5（`fir_up2`・`fir_down2` に `@latency`）、W3 の後の属性の構文。
  - 後で足す変更: S-583 の (by2) はこの値を使う。パラメータで変わる遅れは、どの案でも後で開くと起動のやり直しの約束が要る。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - 一致した。段 1 の補い: 宣言は全体の値の上書きで、子と自分の先読みの両方を持つ flow は書き手が和を書く（子の値は `onsa interface` に出る）。「自分の分だけ宣言して合成に足す」形は、乾いた経路を `delay~` で揃えた並列の経路で二重に数えるので採らない。
    (o2) の値は `init` で決まり、状態の隠れた欄（§12.4 の `let` に由来しないフィールドの列）に置き、`reset` は保つ。
  - 新しい S の候補（`onsa audit` で経路ごとの遅れを示す）: 段 2 は別の S にする（道具。優先は低い）。
- 回答（2026-10-22、会話で利用者。52 回目）:
  - 決め方（(2)）: 利用者が、遅れには `.down~`・`.up~` の連鎖で決まる遅れとフィルタなどによる遅れの二種があり、(k2) は前者だけから数えるので正確にならないが、参考となる基準値の算出には使えると述べた。
    親は、(k2) はフィルタの遅れを子の `@latency`（std の `fir_up2`・`fir_down2`）からだけ取り、書き手が作ったフィルタ（`delay~` のタップの FIR、IIR）は数えないこと（下書きの「書き手の意図した遅れ（`delay~` の先読み）だけを宣言すればよい」は誤解を招く字）、IIR の群遅延は周波数で変わり、タップの FIR は係数が対称のときだけ一定なので、コンパイラには数えられないことを答えた。
    あわせて逆向きの問題を示した: 検出を遅いレートで動かすコンプレッサ（`x * lin_up32~(gain_ctl~(avg_down32~(x * x), thr).down~(32))`）では、音の経路は遅れないのに、(k2) は検出の経路の集めて配る遅れを報告し、ホストが出力を前へずらす（下書きと助言の二段は挙げていなかった）。
    親は (r-a) ホストに報告するのは `@latency` の宣言だけ（無ければ 0）で、合成した値は参考に見せる、(r-b) 今の (k2) のまま合成した値を既定にする、を出し、推奨を (k2) から (r-a) に改めた（どちらの向きのずれも機械では正しくできない、報告の値が書いた値のまま、最長の経路の計算を W7 から道具へ回せる）。
    利用者: 「(r-a)の意図でした。解析ツールが構造的に決まるレイテンシーを出力するイメージ」。(r-a) で了承: ホストに報告する値は一番外の flow の `@latency(e)` だけで、無ければ 0（下書きの (k1)。子の宣言は合成しない）。
    構造から決まる遅れ（集めて配る N と子の宣言の、経路ごとの値）は解析の道具（`onsa audit`）が出し、形は別の S で決める（下書きの新しい S の候補を、この役に広げて登録する）。W7 で最長の経路を数える作業は要らない。出す所（(1)）の推奨 (o2) は変えない。
    道具: 利用者「他に適切なツールがなければ `onsa audit` で良いと思います。このために専用のツールを作るまでは不要かと」。親が §18 の CLI の一覧を確かめた: `onsa graph` は信号グラフの描画、`onsa interface` は公開のシグネチャと状態で、エントリごとに数えた値（`--stack` の最悪のスタック使用量など）を出すのは `onsa audit` なので、`onsa audit` に置く（旗の形は別の S）。
  - 了承（52 回目）: 利用者: 「第36組の残り(S-582、S-583、S-575、S-576)は異論ありません」。§19.1 に書いた字（下書きの推奨、独立のレビューの補い、上の答え）で了承。
