# S-389 パターンの中の `||`

- 空白: パターンの中の `||`（`0 || 1 =>`、`|| 0 =>`）。今は E0002「expected `=>`, found `||`」と「expected a pattern, found `||`」で候補なし。rustc は「use a single `|`」と示し、Node は `case 0 || 1:` を式 `0 || 1`（`case 1:`）と読む。
  読みが割れるので、E0020 で `|` の候補（とガードの形）を並べるか。第 18 組の下書きで見つけた（2026-10-10）
- 提案: 決定（2026-10-10、利用者が ID を挙げて推奨の (a) を了承。下書きと Fable が一致、第 19 組）: パターンの中の `||` は、位置によらず構文の段の E0020（データのファイルに新しい行）で、修正候補は `||` を `|` にする形一つ。`||` を `|` にした後の位置の誤りは次の検査で報告する（`|| 0 =>` は S-383、行頭の `0` 改行 `|| 1` は S-380 の行が出し、二回で直る。S-326・S-386 と同じ一つずつ）。
  行頭の `||` はパターンの中では演算子でないので S-370 の行に入れない。
  候補を出すのは `||` の次のトークンがパターンを始められる字句のときだけで（字句の条件、D-15）、後ろにパターンが続かない形（`0 || =>`、`0 || if c =>`、`Some(0 ||)`、`|| =>`）と `0 ||| 1`（`|` にすると後ろの `|` と接して `||` に読み直される）は候補なしの E0002。
  ガードの形の候補は並べない（ガードの付いた腕は網羅に数えない）。`0.5 || 1.5`、`n @ (0 || 1)`、`1..<3 || 5` は、前の位置の行（`float_pattern`・`at_binding`・`range_pattern`）が先に報告する。データの行の origin は C 系・JavaScript・Ruby（W3-06 の作業票で決める）。仕様 §7。
  実装は W3-06
