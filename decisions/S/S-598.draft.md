# S-598 `use` の二つの書き方（`use a.b` と `use a.{b}`）を揃えるか

- 決定済みで戻さないもの: `use` は絶対経路で、頭はルート直下のモジュールか依存のパッケージ名だけ。自分のパッケージ名を頭に書いた `use` は E0302（S-37）。その候補の形（`fx.` を外す、`use fx.{a}` は `use a`、`use fx.{a, b}` は二行、`use fx` は候補なしで note。S-663）。
  取り込めるものにパッケージそのものとルート直下のモジュールを足し、モジュールを取り込む `use` は下の全てのモジュールへの辺として数える（自分自身は除く。S-594 の (x1)）。取り込む名前の読みと、二つの書き方が同じ束縛を作ること（S-594 の二）。
  `use` の束縛と子モジュールの名前の空間（S-611）。名前の段で失敗した `use` の名前は使う所で黙る（S-462）。ディレクトリだけのモジュールの取り込み（S-666）。E0302 の候補に綴りの近い名前を出さない（S-258）。
  族の表（族の全ての形、31 行）と族の規則から決まる部分は、第 58 組の下書きの「族の表と既決の規則（S-594）」の節（写しは `target/notes/66/g58/draft.md`）。
- 論点: §15.1「二つの書き方（`use std.math` と `use std.{math}`）は同じ束縛を作り、fmt は書き手の形を残す」（S-594 の二）。S-594 は揃えるかをこの S に残した。重なるのは、二要素以上の経路の最後の一つの名前を取り込む形だけである（表の 20〜22 行）。一要素の `use std` は並びに書けず（23 行）、二つ以上の名前は並びだけ（24 行）。
  仕様の例は、モジュールを並び無しで（`use std.audio.wav`、§17 の `use std.array`、§16 の `use std.audio.device`）、項目を並びで（`use std.math.{sqrt}` など約 15 か所）書くことが多いが、並びのモジュール（§15.1 の `use std.{math}`、`use main.{inner}`）と並びの flow の名前空間（§11.6 の `use dsp.synth.{voice}`）もある。
  std の `use` は並びだけで、一つの要素の並びは `use math.{pow}`・`use test.{Gen}` の 2 行。テストは、一つの要素の並びの行を持つファイルが約 130、二要素以上の並び無しの行を持つファイルが約 130 ある（grep の概数）。
- 今の実装: 両方が通り、同じ束縛を作る（`two_forms`、終了コード 0）。fmt は書き手の形を残し、並びの中の空白と末尾の `,` だけを揃える（`use std.{ math }` → `use std.{math}`、`use util.{helper,}` → `use util.{helper}`。`fmt2.onsa`）。並びの中のコメントも残す（`fmt3.onsa`）。
  `diff --ast` は `use std.math.{sqrt}` と `use std.math.sqrt` を違う項目として報告する（`ast_a.onsa` と `ast_b.onsa`、終了コード 1）。
- 案:
  - (a) 今のまま。両方を書け、fmt は書き手の形を残す。実装は 0 行で、仕様も変えない。費用の要因: 同じ束縛に二つの綴りが残り、grep で取り込みを探すとき両方を探す。修復のループや書き手が書くたびに形が揺れても、差分にしか出ない。
  - (b1) fmt が一つの要素の並びを並び無しに書き換える（`use a.{b}` → `use a.b`）。並びの中にコメントがあれば残す（`spec/tools.md` §3.4 の括弧と同じ）。
    S-594 の読み（同じ束縛）のまま表記を一つにする。`spec/tools.md` §3.3 の構造を変える書き換えの一覧に一行を足し、`diff --ast` と fmt の確かめの正規化（§3.5）にも同じ書き換えを足す。通っていたプログラムは壊れず、判定（合否とコード）も変わらない（どちらの書き方も同じ誤りになる、27 行）。
    実装は fmt の書き換えと正規化で約 30〜40 行と事例。仕様の例を正規形に直す（`use std.math.{sqrt}` など項目の約 15 か所と §11.6 の `use dsp.synth.{voice}`）。
    費用の要因: 仕様の例の多い項目の書き方（`use std.math.{sqrt}`）が fmt で `use std.math.sqrt` に変わり、例に倣って並びで書く書き手のコードを fmt が毎回書き換える。
  - (b2) fmt が二要素以上の並び無しの経路を一つの要素の並びに書き換える（`use std.math` → `use std.{math}`）。実装と正規化の量は (b1) と同じ。
    費用の要因: 仕様の例の多いモジュールの書き方（`use std.audio.wav`、`use std.math`）がほぼ全て変わり、§15.1 の本文の例も直す。
  - (c1) 一つの要素の並びを構文の段の E0020（冗長な括弧、候補は括弧を外す形）にする。実装は構文の検査と候補で約 15〜20 行と、`spec/foreign-forms.toml` か §15.1 の冗長な印の一覧への一行。
    費用の要因: 通っていたプログラムを止める。テストの約 130 のファイル、std の 2 行、仕様の例の約 20 か所を直す。構文の段の誤りなので、そのファイルは fmt も書き換えない。S-594 の段 2 は、この向きなら W4-03 の前に決めると補った。
  - (c2) 取り込む先の種類で書き方を一つにする（パッケージとモジュールは並び無し、項目と flow の名前空間は並び）。種類は名前の段で分かるので、名前の段の E0020（候補は他方の書き方）。
    実装は名前の段の検査と候補で約 30 行と、種類の境（flow は項目で名前空間でもある）の規則。費用の要因: 通っていたプログラムを止め（§15.1 の `use std.{math}`、`use main.{inner}`、テストの `use kp.{inner}`・`use util.k`）、書き方が取り込む先に依る規則が一つ増える。fmt はファイルごとに名前を解決せずに動くので、fmt では揃えられない。
- 他言語:
  - rustfmt 1.8.0（手元、既定の設定）: `use crate::{util};` を `use crate::util;` に、`use std::{fmt};` を `use std::fmt;` に書き換え、`use std::io::{self};` と二つ以上の並びは残す（行は並べ替える）。`imports_granularity` の既定は `Preserve` で、`Crate` は `use a::b;` と `use a::c;` を `use a::{b, c};` にまとめ、`Item` は分ける。
    rustc 1.94.1（手元）の lint `unused_import_braces`（既定は allow）を warn にすると、`use crate::{util};` に「braces around util is unnecessary」。
  - gofmt（Go 1.27.2、手元）: 一つの要素の括弧の `import ( "fmt" )` と `import "os"` をどちらも残す。
  - Python 3.14.5: `import a.b` は `a` を束縛し、`from a import b` は `b` を束縛するので、二つは意味が違い、この S の比べには当たらない。`from a import (b)` と書ける。formatter の black の扱いは未確認（手元に無い）。
  - TypeScript: 名前の取り込みは `import { b } from "a"` の一つの形で、二つの書き方は無い。tsc の挙動は未確認（手元に無い）。
- 推奨と理由: (a)。確度: 中。
  - 二つの書き方は一つの意味しか持たず（S-594）、読みは割れないので、誤りにする (c1)・(c2) の理由が無い。どちらも通っていたプログラムを止め、(c2) は書き方が取り込む先に依る規則を足す。
  - fmt で揃えると、仕様の例が使い分けている二つの書き方（モジュールは並び無し、項目は並び）のどちらか半分を、fmt が毎回書き換える。使い分けの境は取り込む先の種類で、ファイルごとに動く fmt には見えないので、fmt はこの使い分けを守れない。
  - 揃える向きの (b1) は、後で入れても通るプログラムを壊さず、判定も変えない（表記だけが変わる）。今入れる利益は grep と差分の揺れが減ることで、その量の割に、仕様の例の約 20 か所の書き直しと §3.3・§3.5 の一覧の変更が要る。
  - 反対の考え: 一つの要素の並びの括弧は、どう読んでも意味が一つの余分で、冗長な括弧と同じく fmt で揃えるという読みもできる。揃えるなら (b1) の向きで、Rust の書き手に馴染んだ形（rustfmt と同じ）で、括弧の中のコメントで止める規則が §3.4 にある。
  - 第 2 期と JS / WASM: 別名（`use a.{b as c}`）や `self` を並びに足すと、一つの要素の並びにしか書けない形が生まれ、(b1) には例外が要る。(a) は何も戻さずに済む。生成するコードは束縛でなく経路から名前を作るので、どの案でも変わらない。
- 影響: (a) は仕様も実装も変わらない。(b1)・(b2) は §15.1 の「fmt は書き手の形を残す」の一句と、`spec/tools.md` §3.3 の一覧と §3.5 の正規化。(c1) は §15.1 と冗長な印の一覧（E0020）、(c2) は §15.1 の新しい規則（名前の段の E0020）。
  作業: W5-11（字句・構文・fmt の残りの空白）。(c1)・(c2) は通っていたプログラムを止めるので、W4-03 の前に決める（S-594 の段 2 の補い）。
  事例: fmt の事例（`tests/spec/` の fmt の確かめ）に二つの書き方の正規形を足すのは (b1)・(b2)。(c1)・(c2) はテストの約 130 のファイルと std の 2 行（`std/dsp.onsa` の `use math.{pow}`、`std/test/gen.onsa` の `use test.{Gen}`）を直す。
  今の実装と違う案: (b1)・(b2)・(c1)・(c2)。テストベクトルの保留に関係する項目は無い。作業ツリーの事例に関係する期待値は無い。
