# S-573 `render` と `onsa test` でのイベントの与え方

- 決定済みで戻さないもの: 組の全体は S-570 の下書きの頭（第 33・34 組で決めた §19.1 の三つの項、S-565 の R12、§14.2 の C の API の原則）。
- 論点: §11.6「`render` はテストと一括処理用。全体を 1 回の `process` として処理するので、`block` の入力は全区間で一定」「`Rendered` は、出力を `Buf` で持つ struct」。§18.2「`--flows` で export される flow を `@param` の範囲で自動検査する（…無音・インパルス・雑音を入れ、出力が有限で panic しないこと）」。
  §19.1 は `render` の書き方（入力をまたいだ順を書ける形）を第 35 組に送った。
  - (1) `render` の引数のイベントの形と、出力のイベントの `Rendered` での表し方。(2) テストでイベントの列を書く書き方。(3) `onsa test --flows` が、イベントの入力に何を与えるか。
- 今の実装: `render` は `osc.render(osc.Config {}, osc.Params { f0: 4800.0 }, 4, 48000.0)` で 4 フレームを返し、
  `gain.render(…, impulse(4), 48000.0)` も通る（`r10`、3 件とも ok、終了コード 0）。`onsa test --flows` は「unexpected argument '--flows'」で終了コード 2（今は無い）。
- 案:
  - (r-a) `render` は `process` と同じ形のイベントを取り、位置は `render` の頭から数える（`frames` は `Span` の長さか引数）。S-570 の案ごとの形:
    (1a) なら `events: Span[syn.Event]` で、入力をまたいだ順は列の順に書く。(1b) なら `syn.Events` で、順は `seq` で書く。(1c) なら Onsa に同じ形が無いので、`render` だけ列を取る（C と別の形）。(1d) なら `render` は位置付きの列を取り、中で呼び出しを分ける。
    出力のイベントは、S-571 のどの案でも `o.out: Buf[(U32, E)]`（`render` は上限の大きさを確保できるので、容量の問題は無い）。
  - (r-b) `render` はイベントを取らない。イベントを使うテストは `process` を自分で繰り返す（ブロックごとにパラメータを変えるテストと同じ、§11.6）。
  - (w1) 補助を足さない。配列のリテラルと、(1) の作る関数と std の作る関数（S-572）で書く。(w2) `std.dsp.test` に補助を足す（秒で書いた時刻を位置にする、入力ごとの列を一つの順の列に混ぜる、など）。
  - (f1) イベントを与えない。(f2) 境界の型ごとの決まった列を与える（S-572 (b1) の型の閉じた一覧: スカラは 0 と 1、`Bool` は偽と真、`()`、MIDI はノートオン・オフ、CC、ピッチベンド、Clock・Start・Stop、トランスポートは Start・Stop・Continue）。
    位置は頭、中ほど、最後と、別の入力の同じ位置（宣言の順と逆の順の両方）。(f3) `--seed` から無作為の列を作る。
- 他言語: 手元で確かめたものは無い。
- 推奨と理由: (r-a)、(w1)、(f2)。確度: 中。
  - (r-a): 同じ形の列でテストと実機をつなげ、§19.1 が求めた「入力をまたいだ順を書ける形」を `render` が受け持つ。(r-b) はイベントの位置をテストのたびに呼び出しの区切りで書くことになる。
  - (w1): S-570 の形と std の作る関数で書けるので、補助の名前を増やさない。必要が分かったら (w2) を後で足せる。
  - (f2): シンセのようにイベントで鳴る flow は、イベントが無いと無音で、(f1) では検査が空になる。型の一覧が閉じているので列は表で決まり、無作為（(f3)）にしなくても決定的で、`--seed` と独立に再現できる。
  - 新しい S の候補: `--flows` に「同じ入力を二通りの区切りで `process` に渡し、出力がビットで同じこと」を足す（S-570・S-571 の区切りの約束を直接確かめる）。
- 影響:
  - 仕様: §11.6（`render` の引数と `Rendered`）、§11.8、§18.2（`--flows` の与えるもの）。
  - 作業: `render` の生成（W8・W10）、テストの器。`--flows` は今は無く、受け持つ作業は第 1 期の範囲を割り当てるときに決める。
  - S-570 が (1c) なら `render` と C の形が分かれ、(1d) なら `render` の中に分ける処理が要る。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - (r)・(w)・(f) は一致した。
  - (f2) に、出力のイベントの数が上限（S-571）を超えないことの検査も足す（段 1。コンパイラの係数の確かめになる）。
  - 新しい S の候補（`--flows` に「同じ入力を二通りの区切りで渡し、出力がビットで同じこと」を足す）: 段 2 は、この組で (3) の一文として決める（`--flows` を受け持つ作業は未定だが、約束の文は今書ける）。
  - 論点の抜け（段 1。段 2 はこの組で決める）: `render` のイベントの引数の位置は `process` と同じ（`sample` の入力の前）。`frames` が 0 の `render` はイベントを持てない（S-570 の (2a) と同じ）。
