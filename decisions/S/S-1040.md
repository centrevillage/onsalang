# S-1040 要素が Copy でない `[T; N]` の `fill!`（`pub rt fn fill(inout self, v: T)`）が要素を上書きで破棄する形と、std の宣言（`rt` で `Alloc` が無い）

- 空白: std の `impl[T, const N: U32] [T; N]` の `pub rt fn fill(inout self, v: T) { for i in 0 ..< N { self[i] = v } }`（`std/core/seq.onsa`）は、S-853 の決定で要素が Dup のとき持つ（Shared の `fill!` を残す）。R-32 の上書きの破棄と総称の `T` の破棄（W6-02）を数えると、要素が Copy でない `T`（Shared）では `self[i] = v` が前の要素を破棄するので、`rt` で `Alloc` の無い本体が E0901 になる（推論）。
  今（`702a4619`）: `rt fn f(inout xs: [Str; 2], s: Str) { xs.fill!(s) }` と総称の同じ形が通る（`target/notes/146/w602/review/r2.txt` の `fill_str_rt`・`fill_generic_rt`）。`tests/spec` の `fill!(` は約 70 ファイル・210 か所。
  読みの候補: (1) `fill` を `T: Copy` に絞る（S-853 の「Dup のとき」を改める） (2) `rt` を外して `uses {Alloc}` にする (3) Copy と Dup の二つの宣言に分ける（`rt` の版は Copy だけ） (4) 上書きの破棄を `fill` の本体だけ数えない例外。同じ形の総称の `swap[T]`・`W[T].set` の事例（`tests/spec/effects/fn_compat_*.onsa`）も同じ問いに当たる。
  急ぎ: W6-02 の上書きの単位（U5）と総称の `T` の単位の前。S-1038（`inout` への代入の破棄）と組になる。
- 決定: 決定（2026-11-13、利用者。146 回目、第 101 組。中立の要約と独立のレビューの段 1 が (1)、第 100 組の段 1 も同じ向き）: (1)。`[T; N]` の `fill!` は要素が Copy のとき持つ（S-853 の「`get`・`fill!` は要素が Dup のとき」を改め、`fill!` は `slice`・`copy_from!`・`add_from!` と同じく Copy。`get` は Dup のまま）。満たさなければ呼び出しの位置の E0416 で、note に `xs = [v; N]` を示す。
  std は `fill` を `impl[T, const N: U32] [T; N]` から新しい `impl[T: Copy, const N: U32] [T; N]` へ移す（本体と生成は今のまま。配列の自前の `fill` を消して `Span[T]` の `fill` から引く形は C の生成が変わるので採らない）。頭の文書コメント（「`get` and `fill` of an array need a Dup element」）を直す。
  理由: S-853 の理由（各メソッドの条件は、そのメソッドがすることと既にある規則から決まる）を当て直すと、`fill!` は複製に加えて上書きをし、上書きの破棄（S-1038）は `rt` の本体に書けないので、条件は Copy になる。規則は「`len` は任意、`get` は Dup、要素を上書きするメソッドと `slice` は Copy」で `Span`・`Buf` と揃う。(3) の二つの宣言は今の仕組みで書けない（同じ名前を境界で分けると E0304）、(2) は `rt` の Copy の `fill!` を壊し、(4) は不健全。
  利用者は、将来は総称の境界による多重定義で解決できると見た。親は、§6.1・§6.3 が多重定義と特殊化を意図して持たないこと、具体の型の呼び出しは解決するが総称の呼び出し側は残ること（型パラメータの破棄に依る条件付きの効果なら残らない）を示し、両方を A-20 に登録した。(1) は絞る向きなので、後で緩めても通るプログラムは壊れない。
  直す事例は 3 ファイル 5 関数（`values/seq_get_shared.onsa` の 3 関数、`negative/seq_methods_shared.onsa` の 1 関数、`values/seq_generic_receivers.onsa` の `fill_all` に `T: Copy`）。作業は W6-02 の U5b（上書きの破棄と同じ単位で std の宣言と事例を直す。無いと std が E0901）。仕様 §5.3

- 補い（2026-11-13、親）: 中立の要約（Q2）と独立のレビューの段 1（onsa-advisor、146 回目）: (1) `fill!` を要素が Copy のときに絞る（S-853 と S-847 の一部を改める）。(3) は書けない（同じ名前のメソッドを境界で分けると E0304、配列の受け手は自分の `impl` の表を名前で引く。`target/notes/146/g101/advisor/probe/q2.txt` の `a_two_impls_same_name_by_bound`）。(2) は `rt` の Copy の `fill!` を壊し、(4) は不健全。規則は「`len` は任意、`get` は Dup、要素を上書きするメソッド（`fill!`・`copy_from!`・`add_from!`）と `slice` は Copy」で `Span`・`Buf` と揃う。std は `fill` を新しい `impl[T: Copy, const N: U32] [T; N]` へ移す（本体と生成は今のまま）。直す事例は 3 ファイル 5 関数（`values/seq_get_shared.onsa`、`negative/seq_methods_shared.onsa`、`values/seq_generic_receivers.onsa`）。代わりの書き方 `xs = [v; N]` を E0416 の note に。S-1036〜S-1038 の段 1 も同じ向き（配列の `fill` を消して `Span` の `fill` を引く形）を挙げた。利用者の判断が要る（決定済みの S-853 を改め、今通る形を誤りにする）。段 1 の範囲の外の候補: 型パラメータの破棄を呼ぶ所で数える仕組み（A の候補、必要は未確認）。
