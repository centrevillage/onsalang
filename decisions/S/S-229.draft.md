# S-229

- 決定済みで戻さないもの: 上限の値 128、入口を 0 とすること、末尾の呼び出しを数えること、`const` を読むのは呼び出しでないこと、コンパイル時の評価が同じ数え方で E0419 になること（S-222）。C などの変換先はターゲットの機構に従うこと（§12.5）。
  第 78 組の下書きの「仕組みの出所」と「族の形の表」・「形の表」の節（写しは `target/notes/105/g78/draft.md`）。
- 論点: §12.5（67 行）は深さを「入れ子になった呼び出しの数」で数えるとするが、何を呼び出しと数えるかを書いていない。
  std の関数（Onsa の本体を持つものとプリミティブ）、組込みのメソッド、演算子の trait の実装、処理系が構造から与える実装（タプル・配列・`Option` の `==`、derive）を数えるかで、同じ利用者のプログラムが上限で panic するかが変わる。
- 今の実装: 形の表のとおり。本体のある関数（利用者、std、処理系が作る `==`）は数え、プリミティブと展開する `from_fn` は数えない。
  そのため、`std.dsp.db_to_amp` を呼ぶ形は境界が 1 つ、`[[U32; 2]; 2]` の `==` は 2 つずれ、`sqrt`・`xs.get`・`abs` はずれない。W5-02（`get` などを std の本体に）と W5-07（`abs`・`min`・`max` の本体）で、同じプログラムの境界が動く。
- 案: どの案も、利用者の関数・メソッド（利用者の演算子の trait の実装を含む）は数え、組込み型の演算子は数えない。C・JS・WASM の後端は数えない（ターゲットの機構）ので、数え方を揃えるのはインタプリタとコンパイル時の評価器（W9-03）だけである。
  - (a) 本体を持つ関数の呼び出しを全て数える（今の実装の読み）: std の Onsa の本体の関数・メソッドと、処理系が作る `==`・derive の関数も、その中の入れ子も数える。プリミティブ（`target fn`）と、その場に展開する形は数えない。
  - (b) std の外で宣言した関数の呼び出しだけを数える: 利用者のパッケージ（依存のパッケージを含む）の関数・メソッド・無名関数は、どこから呼んでも（std の本体から呼ぶ無名関数や trait の実装も）数える。
    std の関数（本体の有無によらない）と、処理系が構造から与える実装は数えない。
  - (c) 利用者のコードに書いた呼び出しと、利用者の関数への呼び出しを数える: (b) に加え、利用者のコードに書いた std の関数・メソッドの呼び出し（プリミティブを含む）を 1 回に数え、std の本体の中の呼び出しは数えない。
  - 形ごとの出力（`down_x(127)` の底）: `db_to_amp`・`sum` は (a)・(c) で panic、(b) で通る。`sqrt`・`xs.get`（今）・`checked_add` は (a)・(b) で通り、(c) で panic。W5-02 の後の `xs.get` は (a)・(c) で panic、(b) で通る。
    複合の型の `==` は (a) で型の入れ子の段だけずれ、(b)・(c) で通る。`from_fn` の無名関数の中の呼び出しは、(a) で今のまま、(b)・(c) で無名関数の呼び出しが 1 つ足される。
  - 書き手から見て: 上限の近くで panic するかが、(a) では std の書き方（どれがプリミティブか、std の中の補助の関数の数）と、`==` の型の形で決まり、ソースを読んでも分からない。std の版を上げると、変えていないテストが落ちうる。
    (b) は利用者のソースだけで決まる。(c) もソースだけで決まるが、`sqrt(x)` は数え、`a + b` と `a == b` は数えないという、呼び出しの書き方の区別を覚える。修正候補は、上限の panic にはどの案も出さない（実行時の失敗）。
  - 通るプログラム: 今の事例はどの案でも変わらない。(a) は今の実装のままで、W5-02・W5-07・§6.6 の musl の移植のたびに、上限の近くで std を呼ぶプログラムの結果が変わる。
    (b) は今の `db_to_amp`・複合の `==` の形が通るようになる。(c) は今の `sqrt`・組込みのメソッドの形が panic になる。
  - 規則と例外: (a) は §12.5 に「std と処理系の与える実装の本体も数える」の一句だが、結果を再現できるようにするには、std のどの関数が本体を持ち、`==` が何段の呼び出しになるかを仕様に書くことになる（書かなければ版で変わる）。
    (b) は一句（std の外で宣言した関数を数える）で例外が無い。(c) は二句（書いた呼び出しと、利用者の関数への呼び出し）で、書いた呼び出しとそうでない形（演算子、`==`）の区別を足す。
  - 実装の量（見込み）: (a) は 0 行。ただし降下とインタプリタで std の関数をその場に展開したり、`==` をループにしたりすると深さが変わるので、その最適化をするたびに数を合わせる手当てが続く。
    (b) は Core の関数に「数える」の印を一つ足し（降下が利用者・std・処理系の作る関数を分けて付ける）、`call_with` で見る。約 +10〜20 行と、Core を直接作るテストの補い。W9-03 の評価器も同じ印を見る。
    数えない std の本体と `==` の入れ子もスタックを使うので、R-05 の測り（128 の呼び出しのそれぞれに std の最も深い鎖が乗る形）を W9-03 で確かめ直す。
    (c) は (b) に、呼び出しの式が利用者のコードにあるかの印と、プリミティブの式の前後で深さを足し引きする処理（インタプリタのよく通る道）を足し、約 +25〜40 行。
  - 後の作業への手当て: (a) は W5-02・W5-07 と §6.6 の musl の移植、`==` と derive の降下を変える作業（derive の順序の Core は W8-10）のそれぞれで、境界の事例と仕様の一覧を直す。(b)・(c) は、std の本体を足すか形を変えても手当てが要らない。

- 推奨と理由: (b)。確度: 中。
  - 上限は、止まらない再帰を、機械を落とさずにどの環境でも同じ所で止めるためにある。止まらない再帰は利用者の関数を通ってしか起きず、std と処理系が与える実装はそれだけで再帰しない。数えなくても守りは減らない。
  - 境界が利用者のソースだけで決まる。どれをプリミティブにするか、std の中の補助の関数、`==` をどう降下するかは std と処理系の選択で、(a) ではそれが仕様の見える振る舞いになり、W5-02・W5-07 と musl の移植のたびに境界が動く。(c) は書いた呼び出しと演算子の区別を足し、よく通る道に処理を足す。

  - あわせて決めること: 引数の位置の呼び出しは、§3.5 の評価の順のとおり動的な入れ子で数える（`f(g(x))` の `g` は `f` の中でない）と §12.5 に一句書く（今の事例の読み）。関数値の呼び出し `f.(x)` は、指す関数が std の外のものなら 1 回に数える。
  - あわせて決めること: std の本体から呼ぶ利用者の無名関数（`array.from_fn` の引数）も 1 回に数える。今の展開は数えないので、`from_fn` を普通の呼び出しにする作業（D-07 の追記。関数値の降下と同じ時期）か、それまでの展開の前後で深さを足す。
