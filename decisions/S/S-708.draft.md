# S-708 型の位置に経路の形で書いた `src.process_inplace`（flow が `process_inplace` を持たない）の診断（関数の名前の E0308 か、見つからない E0302 か。S-694 は `use` した名前の形だけを言う）

- 決定済みで戻さないもの: 第 64 組の下書きの「決定済みで戻さないもの」と「形の表」の S-708 の表（写しは `target/notes/74/g64/draft.md`。表の行の番号はその表のもの）。
- 論点:
  - 出所と目的: §11.6 の `process_inplace` は `sample` の入力と出力の型で有無が決まり、無いと分かるのは型の段である。S-694 は、名前の段で有無を決める後に回す束縛が収束しなかったので、名前の段では解決したとし、型の段で無いと分かれば `use` に E0302、以後は失敗した名前とした（§18.1）。
    §11.6 は加えて「署名の型の位置に書いた `process_inplace` は関数の名前で、有無によらず型でない名前の誤りである」とする。署名を降ろす順で有無がまだ分からなくても、種類の誤り（§15.1 の E0308、S-103）に一つに決まるようにするためである。
  - S-707（R-147）は、本体の値の位置の経路が型で無いと決まった生成項目を引く `one.process_inplace(…)` を E0302（§15.1 の名前が見つからない誤り）とした。
  - §11.6 の文は `use` の段落にあり、経路の形（`src.process_inplace`）を名指さない。本体の注釈は「署名」にも当たらない。有るときは E0308（S-103）で決まり、無いときが E0308 か E0302 かが書かれていない。当たる形は表の 1・2・4〜6 行。
- 今の実装: 署名の位置は有無によらず E0302「`process_inplace` is not a type」（U7 のコードの割り当てで E0308 になる）。本体の注釈は、無いと E0302「cannot find `src.process_inplace`」、有ると「is not a type」。
  `use` で取り込んだ名前（9 行）は、`use` の E0302 の後、本体の注釈では黙る（S-694）。
- 案:
  - (a) 型の位置（署名、型引数、関数の型、`impl` の見出し、本体の注釈）の `src.process_inplace` は、有無によらず E0308。`use` の形の §11.6 の文を、経路の形と本体の注釈に広げる。
  - (b) 経路の形は有無で分ける: 無ければ E0302（S-707 と同じ、名前空間に無い名前）、有れば E0308。署名では、型の段の後まで判定を待つ。
  - (c) 署名は有無によらず E0308（§11.6 の文の「署名」）、本体の注釈は有無で分ける（無ければ E0302）。今の実装の分け方。
  - 一回の検査で出る誤り: どの案も一つ（単位ごとに一つ）で、候補は無い。無い flow で (b)・(c) の E0302「cannot find」を見た書き手は、flow を直して `process_inplace` を作りうるが、作っても型の位置では E0308 が残り、二回目の検査が要る。(a) は一回目から「関数の名前を型の位置に書いた」を示すが、無い flow では、文面が flow に無い関数を指す。
  - 揃い: (a) は全ての型の位置と二つの名前の形で同じコード。(b) は署名で `use` の形（S-694 で有無によらず E0308）と経路の形が分かれる。(c) は同じ型を署名と本体の注釈に書くと、無い flow で分かれる。
  - 通るプログラム: どの案も変えない（全て誤り）。
  - 実装: (a) は `sig/types.rs` の型の経路の解決が失敗した所で、flow が作って生成しなかった項目（今の `not_generated` の判定）を関数の名前として E0308 にする（約 +10。本体の注釈も `lower_type_in_body` で同じ関数を通る）。(c) は 0 行（U7 のコードの割り当てだけ）。
    (b) は、署名の型の位置の生成項目を記録して型の段の後に判定する処理（約 +30〜50）が要る。6 行（自分の見出しで自分の生成項目を読む）では有無が自分の署名に依り、§18.1 の「署名に誤りのある flow で有無が分からないときは E0302 も出さない」に当たって診断が消える形になる。
- 他言語:
  - rustc 1.94.1: 型の位置の関数 `src::process_inplace` は E0573「expected type, found function」、無い名前 `src::nosuch` は E0425「cannot find type `nosuch` in module `src`」。
    有無が型で決まる近い例は、境界を満たさない `impl<T: Copy> S<T>` の関連関数 `S::<String>::m()`（値の位置）で、E0599「exists for struct `S<String>`, but its trait bounds were not satisfied」と、見つからない名前と分ける。
  - Swift 6.3.1: 型に書いた static func `Src.processInplace` は「static method 'processInplace()' is not a member type of 'Src'」、無い名前は「'nosuch' is not a member type of struct」。
  - C++（g++ 15.2、Apple clang 21）: 名前空間の関数を引数の型に書くと構文の誤りになり、無い名前は「'nosuch' is not a member of 'src'」（g++）・「no type named 'nosuch' in namespace 'src'」（clang）。TypeScript: 未確認。
- 推奨と理由: (a)。確度: 高。
  - 型の位置では有っても誤りなので、有無は直し方を変えない。種類の誤りを示せば、書き手は一回で型の名前（`src.State` など）に直せる。値の位置（S-707）は有れば正しいので、無いことを E0302 で知らせる。
    「有れば正しい位置でだけ有無を見る」という分け方で、S-707 と矛盾しない。
  - §11.6 の文は形を限らずに「署名の型の位置に書いた `process_inplace`」と言い、(a) は字面どおりの読みを本体の注釈まで揃える。
    (b) は S-694 が避けた「型の段の後まで判定を待つ」仕組みを署名に持ち込み、6 行で診断が消える穴を作る。(c) は同じ型の書き方が署名と本体で分かれる。
  - 実装は約 +10 行で、W4-04 の U7（S-103 の E0308）と同じ回に入り、後の段に手当ては続かない。
  - あわせて決めること: §11.6 の文を「型の位置（署名と本体の注釈）に書いた `process_inplace` は、`use` で取り込んだ名前も経路の形も関数の名前で、有無によらず E0308」に改める。
