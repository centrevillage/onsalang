# S-654 予約語を名前の位置に書いた E0002（`fn f(in: F32)`・`let type = 1`）に、S-243 と同じ末尾の `_` の候補（`in_`・`type_`）を出すか

- 空白: §2.2 の予約語を名前の位置に書くと E0002 で、今は候補が無い（`fn f(in: F32)`、`let type = 1`。dev `fdc4fa5`、`target/notes/62/gap52f-advisor/probe/` の `r_param_in`）。
  S-243 は E0320 の候補が予約語になるときに末尾の `_` を足す（`match_`）が、書き手が初めから予約語を名前に書いた形の候補は決めていない。S-650 の決定で末尾の `_` は全ての形で書けるので、`in_` は規則に合う。
- 決定: 決定（2026-11-09、利用者。128 回目、共通の規則 S-965 と利用者の判断 B1〜B8、`target/notes/128/r58/decisions.md`）: （出所: R11、既存 §2.2、X、Y）宣言の名前の位置（束縛、引数、フィールド、項目・メンバ・列挙子の名前、型パラメータ）に、その位置で他の意味を持たないキーワードを書いた形（`fn f(in: F32)`、`let type = 1`、`struct P { in: F32 }`、`match x { in => … }`）は今の E0002 で、名前の形が `snake_case` の位置（束縛、引数、フィールド、fn・flow・メソッドの名前）にだけ末尾に `_` を足した名前の候補（`in_`）を付ける。他の位置（型、列挙子、型パラメータ、定数の名前）と `use` の取り込む名前には候補を出さない（`in_` はその位置の名前の形に合わず当てた後に E0320 が残り、`use` の名前は相手のモジュールの名前、Y）。`@export` の項目の名前には付けない（§2.3 の既にある規則）。意味を持つ語（`self`、`Self`、`true`、`false`、`_`）はそれぞれの規則。(i) 式の位置に、その位置で式も文も始められないキーワード（`in`・`type`・`as`・`at`・`uses` など。集合は文法の先頭集合で決まり、仕様に列挙しない）を書いた形（`let a = in + 1`）も同じ E0002 に候補 `in_`（当てた後に宣言が無ければ後の段の E0302。`return`・`match`・`fn` は式か文を始めるので候補なし。宣言の位置だけに付けると、`fn f(in_: I32) { in + 1 }` の修復が使う所で止まる、X）。(ii) 宣言の名前の予約語（`let clock = 1`）は §2.2 のとおり E0200 で候補なし（X）。
  - 仕様の節: §2.3（予約語の候補の文の後ろに二文）。
  - 今通るプログラム: 変わらない。
  - 実装の見当: `parser/signatures.rs` の `parse_name`、パターンの束縛、フィールドと項目の名前の入口と、式の被演算子の入口に候補を足す（30〜50 行）。
  - ぶつかる事例: なし（`naming_shapes.rs` は S-654 を対象の外と書いている）。候補の名前が既にある名前と重なれば、当てた後に名前の段の E0304 が残りうる（後の段なので約束の内）。
  - 注: 既にある §2.3 の規則で `fn Clock()` は E0320 と候補 `clock_` を出し、`fn clock()` は E0200 で候補なし（X が確かめた）。この表面の差は元からあり、直すなら別の S。
- 経緯: 62 回目（2026-10-24）、族「§2.3 の名前の形」（S-650）の独立のレビューの段 1・段 2 が新しい S の候補として挙げ、S-650 の決定の後に親が登録した。DSP の入力の名前の `in` など、LLM の書き手に多い形。関係: S-243、S-650、S-648。
