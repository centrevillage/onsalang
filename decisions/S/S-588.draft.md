# S-588 `@host` と `@latency` の場所と値の誤り、`@latency` の値の持ち方

- 位置付け: 族「`@param`・`@host`・`@latency` の責任範囲」（族の規則は S-632。決定済みの事項、出所と目的、族の表は `decisions/S/S-632.draft.md`）。誤りの段は S-632 の軸 B で決まり、この項目は誤りにするかと `@latency` の値の持ち方を扱う。
- 試した入力: dev `3c8f87a` の release の `check`・`test`・`interface`・`build`。入力と出力は `target/notes/60/gap50/probe/`（単一のファイルは `p/`、export のパッケージは `pkg/`）と `target/notes/60/gap50-advisor/probe/`（助言の担当の `pkg_missing/`・`pkg_priv/`）。
- 論点: §11.7「`block` の入力に `@host(<種類>)` を付けると…種類の誤りは E0005、型の違いと `@param` との重なりは E0809」。§11.6「値は一番外の flow の宣言 `@latency(e)`（`e` は `init` のクロックの式）…`block` のクロックの式は E0815」。§6.5「付けられる場所の中での意味の条件と値の誤りは、各属性のコードで報告する」。
  書いていないこと: 1. `@host` を `sample`・`init`・イベントの入力に付けたとき。2. 同じ種類の `@host` を二つの入力に付けたとき。3. `e` の型と値の条件、子の flow の `@latency`。4. `@latency` を付けられない場所。
  - 論点から外すもの: 誤りの段は S-632 の軸 B で決まる（族の表の 9〜14 行）。4 は §6.5 の 2 文目（`@latency` は flow に付け、他の場所は E0005）で決まる。子の flow の `@latency` は誤りにしない（S-576: 子の宣言は合成せず、std の `fir_up2`・`fir_down2` は `@latency` を持って子に使われる）。
  - 1 は §6.5 の 3 文目の「各属性のコード」で決まる。`@host` の意味の条件のコードは §11.7 の E0809 で、`@param` の `sample` の入力（E0809「`@param` goes on `block` inputs only」、`p/d5`）と同じ形になる。文面は「`@host` goes on `block` inputs only」の形。
  - 残る論点は 2 と、3 の `e` の型・値・評価の panic である。
  - 3 の前に、`@latency` の値の持ち方が決まっていない。§11.6 は `e` を `init` のクロックの式とし、`init` で計算して状態の隠れた欄に置く。この形では、属性の式の計算が Core IR（`init`）に入り、その panic が `init` を失敗させる。
    3 の `e` の型と panic の論点は、この持ち方の上に立つ（持ち方によっては要らなくなる）。S-576 の決定の「`@latency(e)`（`init` のクロックの式）」は改めうる前提として扱う。
- 今の実装: `@host(tempo)` は E0005「there is no attribute `@host`」（`b.onsa`）、`@latency(n)` は E0005（`p/d3`）、`@latency(4)` は構文の段の E0002「expected attribute argument, found integer literal」（`c.onsa`）。どれも W10-08 で入る。
- 案:
  - 2（同じ種類を二つの入力に）: (d1) `onsa check` で E0809。二つ目の入力に付け、note で一つ目を指す。(d2) 認める。ラッパーは両方の欄に同じ値を書き、`_host_info` に同じ種類が二つ並ぶ。(d3) export のビルドでだけ E0809（S-632 の (e3) の形）。
    例: `@host(tempo) a: F64 at block, @host(tempo) b: F64 at block`。flow は一つの入力を二か所で読めば足りるので、二つに分ける用途は見当たらない。
    費用の要因: (d1) は診断の形が一つ増える（否定例と note）。(d2) は読み手の場合分けが残る。(d3) は (e3) と同じく export しない flow の誤りを通す。
  - `@latency` の値の持ち方（3 の前提）:
    - (L1) 注釈の中で計算する（今の §11.6）。`e` は `init` のクロックの式で、Core IR の `init` で計算して状態の隠れた欄に置く。例: `@latency((look_s * sample_rate()).trunc_u32())`（`look_s: F32 at init`）。
      仕様: 今のまま（3 の型・panic・名前の範囲を足す）。実装: 属性の引数に式を読む構文、`init` のクロックの検査（E0815）、Core の `init` に式の降下と隠れた欄（W10-08）。
      費用の要因: 属性の式の計算がコンパイラの出力（Core IR）に入り、その panic で `init` が失敗する（3 の (p1)〜(p3)）。`e` が読める名前の範囲（本体の `let` か）を決める。`onsa interface` は式を出す。`cfg` とサンプルレートのどんな関数も書ける。
    - (L2) 定数だけ。`e` はコンパイル時の定数のサンプル数（`@param` の値と同じ評価で、panic は E0419）。例: `@latency(64)`。
      仕様: §11.6 の「`init` のクロックの式」を「定数」に。実装: 定数の評価（`@param` の値と同じ道）と、C の `<p>_latency` が定数を返す形。隠れた欄は要らない。
      費用の要因: サンプルレートで変わる遅れ（ミリ秒の先読み）と `cfg` に依る遅れを書けない。書き手は一つのサンプルレートでのサンプル数を書くので、他のサンプルレートではホストへの報告がずれる（S-576 の下書きの (o2) の目的を満たさない）。
    - (L3) 注釈は計算するための情報だけを持ち、計算はトランスパイラ部とランタイムが行う。例: `@latency(samples: 64)`、`@latency(seconds: 0.005)`、`@latency(samples: 32, seconds: 0.005)`。報告する値は「サンプル数の項 + 秒の項 × サンプルレート（丸める）」。Core IR は値を運ぶだけで、C の `<p>_latency`・ラッパー・（読むなら）生成する API が計算する。
      仕様: §11.6 の `@latency` の段落を、項の種類・型・丸め・溢れの規則に書き換える。S-576 の決定の「`init` のクロックの式」を改める。実装: 項の定数の評価（`@param` の値と同じ道）、各後端（C、後に WASM・JS）が式一つを `init` か呼び出しのときに計算する（数行ずつ）。Core の `init` に属性の計算は入らない。
      費用の要因: 計算の式を後端ごとに書く。`cfg` に依る遅れと、サンプルレートに比例しない遅れ（サンプルレートで FFT の長さを 2 の冪で選ぶ形など）を書けない。本体が自分の遅延の長さを同じ丸めで計算しないと、報告と実際が 1 サンプルずれうる。
    - (L3) の中の論点:
      - 各項はコンパイル時の定数か: (k1) 定数だけ（`const` の名前と効果行の空の関数の呼び出しは書ける、§6.6）。(k2) 項ごとに `init` のクロックの式（計算が Core IR に戻り、(L1) の費用の要因に近づく）。
      - `cfg` に依る遅れ（`look_ms: F32 at init` で先読みの長さを受ける形）: (g1) 書けない。`Config` を持つ flow はプラグインにできない（S-583、E0200）ので、ラッパーの報告には当たらない。C のホストは自分の渡した `cfg` から計算する。
        (g2) 項の値に `init` の入力の名前を書ける形（仮に `seconds: look_s`）にし、後端が `init` で入力の値を読んで計算する。項の種類が増え、属性が入力を名前で指す。(g3) その flow だけ (L1) を使う（書き方が二つになる）。
      - 項の種類と型: サンプル数（`samples`、`U32`）と秒（`seconds`、`F64`）の二つ。秒は有限で 0 以上（違反は `@latency` の値の誤り。コードは E0809 の範囲を `@latency` に広げるか、新しいコード）。ミリ秒の項は秒と重なるので置かない。
      - 丸め方: (r1) ゼロ方向の切り捨て（本体が `trunc_u32()` で同じ値を作れる）。(r2) 最近接、半分は偶数。(r3) 切り上げ（報告が実際より小さくならない）。計算は `F64` で、`sample_rate` を `F64` にして掛ける。
      - 溢れ: 和が `U32` を超えたら `U32` の最大に飽和させる（サンプルレートはコンパイル時に分からないので、検査の誤りにできない）。
      - `e` の評価の panic: 項は定数で、コンパイル時の評価の panic は E0419、実行時の計算は飽和なので、3 の (p1)〜(p3) は要らない。
      - `onsa interface` は書いたとおり（`@latency(samples: 32, seconds: 0.005)`）に出す。
      - S-576 の下書きの (o2) の目的（CLAP は起動のときに遅れを変えられ、ミリ秒の先読みは `init` で決まる）: サンプルレートに比例する先読みは満たす。`cfg` に依る先読みは (g1) では満たさない。
  - 3 の型（(L1)・(L2) のとき）: (t1) `e` の型は `U32` だけ（§3.3 の暗黙の変換は無いので、`F32` や `I32` は E0401。リテラル `64` は `U32` に型付く）。(t2) 整数の型なら何でもよく、`U32` に変換する（負と範囲外の扱いが要る）。(t3) `F32` のサンプル数も認め、丸める。
    `latency` と `<p>_latency` は `U32`・`uint32_t` を返す。
    費用の要因: (t1) は浮動小数や符号付きで計算した遅れを、書き手が `trunc_u32()` などで変換して書く。(t2) は負と範囲外の規則、(t3) は丸めの規則が要る。
  - 3 の値（(L1)・(L2) のとき）: `U32` の全ての値を認め、上限を置かない（CLAP の `get` は `uint32_t`）。0 は宣言が無いのと同じ報告になる。
  - 3 の評価の panic（(L1) のとき）: `e` は `init` のクロックの式で、`(0.005 * sample_rate()).trunc_u32()` のように panic しうる（§3.4、`trunc_<型>()` は範囲外で panic）。
    (p1) `e` の評価は `init` の一部で、panic は `init` の panic（`_init` は 1、`onsa test` はテストの失敗）。定数の式ならコンパイル時に評価し、panic は E0419（§11.3、§6.6）。(p2) `e` の panic を `init` の panic にせず、報告する値を 0 にする。(p3) `e` を、panic しない形（定数の式と飽和の演算）に限る。
    費用の要因: (p1) は遅れの宣言の誤りで flow の `init` が失敗する（音の処理は正しくても使えない）。(p2) は誤りを黙って 0 にする。(p3) は式の形の検査が要る。

  - (d1): 用途の無い形を今は誤りにし、要れば後で緩められる（緩めても既存のプログラムを壊さない）。`@param` の `id` の重複が同じ flow の中で E0809（S-104）なのと同じ形になる。(d2) はラッパーと `_host_info` の読み手に、同じ種類が二つ並ぶ場合を残す。(d3) は S-632 の推奨 (e2) と違い、export しない flow の誤りを通す。

  - (L1) を採るときの (p1): `e` は flow の他の `init` の式と同じ評価で、値で決まる誤りは実行時に検出する形（`rules/criteria.md` 7.34）に揃う。(p2) は誤った宣言の報告を黙って 0 にし、ホストの補いが静かにずれる。(p3) は `trunc_u32` のような普通の書き方を塞ぐ。
