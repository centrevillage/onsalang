# S-597 E1102・E1103 の「綴りの近い」の基準

- 決定済みで戻さないもの: マニフェストの閉じた表と E1101〜E1104 の範囲（S-99、R-130）。E0302 には綴りの近い名前を候補にしない（S-258）。
- 論点: 仕様 §18.1「E1102 は未知の表・キーで、綴りの近い既知のキーを修正候補にし（`panik` は `panic`）、無ければその表で書けるキーを note に並べる。E1103 は値の型や形が規則に合わない（閉じた一覧に無い値、`prefix` とパッケージ名の形、std の版の不一致）で、綴りの近い値を修正候補にする」。
  R-130 の決定の (2)（S-99）も「修正候補は綴りの近いキーや値と必須のキーの挿入」とする。書かれていないのは、(1) 近さの基準（距離、上限、大文字・小文字、同じ距離、短い語）、(2) 「綴りの近い値」が E1103 の全ての形に当たるのか閉じた一覧だけか、(3) E1103 に候補が無いときの note（E1102 にはある）、である。
  候補の数は §18.1 の約束（「候補を出さないことを含む」）なので、基準が無いとテストの役割が数を書けない。§15.3 の表から数えた対象は次のとおり。

  | 診断 | 対象 | 数 |
  |---|---|---|
  | E1102 の表の名前 | 最上位の表（`package`、`dependencies`、`export`、`targets`、`plugin`） | 5 |
  | E1102 のキー | `[package]` 2、`[export]` 3、`[targets.<名前>]` 10（`memory`・`bind` の表を含む）、`[targets.<名前>.memory]` 3、`[[plugin]]` 7、`au` 2 | 27 |
  | E1102 に当たらない開いたキー | `[dependencies]` のパッケージ名（`stdd = "0.1.0"` は std 以外の依存の E0200）、`[targets.<名前>.bind]` のモジュールの経路 | — |
  | E1103 の閉じた一覧 | `edition` 1、`kind` 7、`lang` 2、`fp` 2、`panic` 4、`main_frame` 2、`category` 3 | 7 キー、21 値 |
  | E1103 の他の形 | `prefix` とパッケージ名の形、std の版、`version` の形、`flows`・`fns` の重複、`[[plugin]]` の `id` の重複と `flows` に無い `flow`、真偽値などの型 | — |

  一つの一覧の中で距離 1 の組は `[targets.<名前>]` の `kind` と `bind` だけで、距離 2 は `[[plugin]]` の `id` と `au`、`lang` の `c` と `js`。他の組は距離 3 以上である（`near.py`）。

- 今の実装: E1102・E1103 をまだ出さない（W4-02）。`[targets.host]` の `panik = "poison"`、`[package]` の `verison`、`[target.host]`、`panic-messages = false` は `check --json` も `build` も通る（`man1.py`）。
  `fp = "strct"` と旧名の `numeric = "strict"` も `build` まで通る（実装は `numeric` を読む。W4-02 の持ち越し）。`[pakage]` は「TOML parse error … missing field `package`」で終了コード 2。
  `kind = "staticlb"`・`"StaticLib"` は `build` で「this version does not support `kind = "staticlb"` (only `staticlib` and `source`) (E0200)」、`panic = "poisen"` は `build` で「unknown panic setting `poisen` (poison / trap / reset / halt)」（コードなし）。`check` はどれも通る。
  `provides = ["Allc"]` は `build` で E0200「does not support `provides` other than `Alloc`」、`category = "efect"` の `[[plugin]]` は `check` を通る（`man2.py`）。
  - 試した入力: dev `2ebd664` の release の写しの `check`・`check --json`・`build`・`interface`。
    入力は `target/notes/57/gap41/probe/` の `man1.py`・`man2.py`（S-597）と `rx1.py`〜`rx4.py`（S-596）で、`python3 -I harness.py <名前>.py` がパッケージを `pk/<名前>/` に作り直して走らせる（20 秒で打ち切る）。
    綴りの近さの表は `near.py`、他言語の入力は `probe/other/`。終了コードは全て 0・1・2。
- 案: (a) と (b) は同じ比べ方を使う。ASCII の大文字を小文字に揃えてから、文字の挿入・削除・置き換えと隣の二字の入れ替えを一回と数えた最小の回数を距離とする。
  E1102 は同じ表のキー（最上位では表の名前）、E1103 はそのキーの閉じた一覧の値を比べ、上限の中で最も近いものが一つだけなら、それに置き換える一つの候補を出す。二つ以上なら候補を出さない。候補が無ければ、表のキーか一覧の値を note に並べる。
  当て続けたときは、どの候補もトークン一つを一覧の語に置き換えるので、その位置の誤りが一つ減り、候補どうしが戻し合うことは無い。誤りの無い形に収束するか、候補の無い誤りで止まる。
  ただし §18.1 の安全の約束から、置き換えた後に同じ段の誤りが残る形は候補を出せない（`panik = "abort"` は `panic = "abort"` の E1103、同じ表に `panic` が既にあれば重なりの E1101、`kind = "sourc"` は `source` にすると `lang` の E1104）。
  書き手の意図が一つに決まらないのは、一字の違いで意味の違う語（`kind = "vst2"` の `vst3`、`edition = "2024"` の `2026`）と、同じ距離の二つの語（`find = "exe"` の `kind` と `bind`）である。
  - (a) 一字の違い。上限は 3 字以上で 1、3 字未満で 0（大文字・小文字だけの違い）。
    実装: 距離の関数（20〜30 行）、表ごとの比べる集合と同じ距離の判定（20〜30 行）、置き換えた形を検査し直して同じ表に誤りが残れば出さない所（10〜20 行）。事例: 閉じた一覧ごとに候補ありと候補なしを 1 件以上、同じ距離、安全で出さない形。
    費用の要因: 仕様の版でキーや値を足すたびに、既にある書き誤りの候補が変わりうる（足した語と同じ距離になると候補なしになる）。
  - (b) 長さに比例。上限は書いた文字数の 3 分の 1（切り捨て。3 字未満は 0）。S-258 の下書きの (b) の一と同じ形。実装と費用の要因は (a) と同じで、(a) との違いは 6 字以上の語で二字以上の違いを拾うことだけ。
  - (c) 綴りの近いものを候補にしない。E1102 は今の文の後半（その表で書けるキーを note に並べる）だけにし、E1103 の閉じた一覧に無い値は、その一覧を note に並べる。§18.1 の「綴りの近い既知のキーを修正候補にし（`panik` は `panic`）」と「綴りの近い値を修正候補にする」を消す。
    実装: note の文（10〜15 行。どの案でも要る）だけ。事例: 候補なしと note を見るもの。当て続けると、候補が無いのですぐに止まる。
    費用の要因: R-130 の決定の (2) と、それを反映した §18.1 の文を改める。`panik` の候補を期待するテストの注記（下の「影響」）を書き直す。

- 推奨と理由: (c)。確度: 中。
  - マニフェストの候補を当てる使い手がいない。§18.1 は `onsa.toml` を「エージェントが書き換えないファイル」とし、終了コード 2 でソースの誤りと分ける。修復のループはこの候補を当てない。
    読むのは人（端末と LSP）で、人には、表のキー（多くて 10）か一覧の値（多くて 7）を並べた note があれば、推測の無い正しい語を選べる。候補の数を約束しても、それに頼る使い手はテストだけである。
  - note はどの案でも要る（E1102 の候補が無いときの文）。(c) は全ての案に共通の部分で、(a)・(b) はその上に距離の関数、同じ距離の判定、大文字・小文字と短い語の規則、置き換えた形の検査し直し（値が合うか、キーが重ならないか、隠れた E1104 が出ないか）と、一覧ごとの数の事例を足す。
  - 一覧の中に、一字の違いで意味の違う語がある（`vst2` と `vst3`、版の `2024` と `2026`、キーの `kind` と `bind`）。近さで選ぶと、これらに推測の候補が出るか、例外の規則が要る。
    キーと値は仕様の版で増える（第 2 期の VST3・AU の `kind`、`[[plugin]]` の表）。(a)・(b) では、語を一つ足すと既にある書き誤りの候補が変わり、約束した数が版ごとに動く。(c) では note の並びが一つ増えるだけである。
  - 後で変えられるか: (c) から (a) へ移っても、候補が増えるだけでプログラムは壊れない（テストの期待値は書き直す）。逆も同じで、どちらの向きでも手戻りは事例だけである。
  - 代償: R-130 の決定の (2)（S-99）が決めた「修正候補は綴りの近いキーや値」を改める。§18.1 の例の `panik` と、R-130 の再現の注記の期待を書き直す。改める理由は、§18.1 が `onsa.toml` をエージェントの書き換えない所と定め、候補の使い手が人だけであることである（親の確かめ: この文と綴りの候補の文は、同じ R-130 の決定のコミット `62cfb53` で入った。決定の後に変わった事情ではない）。
