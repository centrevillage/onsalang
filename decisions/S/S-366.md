# S-366

- 空白: 構造体のパターンの `..` の E0020（S-109、§7「残りを省く `..` は無い（E0020。修正候補は残りのフィールドを `_` で並べる形）」）を出す段。残りのフィールドは宣言を引かないと分からず、構文の段では別のモジュールの struct を引けない。データのファイルの `struct_pattern_rest` は stage = "syntax"。
  W3-21/i の設計メモは、構文の段で E0020 と仮の候補（`..` を消す）を出し、後の段で宣言を引けたら候補を差し替える形を出した。W3-21/i で見つけた（2026-10-09）
- 提案: 決定（2026-10-09、利用者。親の案 (B)）: 構文の段は構造体のパターンの `..` を受理して AST に残し、フィールドの過不足（E0410）を見る段が E0020 と、残りのフィールドを宣言の順に `_` で並べる候補（全てのフィールドを書いた上の `..` は `, ..` を消す候補）を出す。
  データのファイルの `struct_pattern_rest` の `stage` をその段に改める。名前が解けない形は、名前の段の誤り（E0302 など）がその単位の一つの誤り。この位置から見えないフィールドが残る形は候補を作れないので、その段の一般の誤りの E0410 と note。
  構造体のパターンの検査（今は sema の本体と旧い flow の検査の二か所）を一つの関数にまとめる（利用者の指示。この先検査が膨れるため）。
  退けた案 (A): 構文の段で E0020 と仮の候補（`..` を消す）を出し、後の段で宣言を引けたら候補を差し替える（名前の解決を別の関数で繰り返し、前の段の診断を後の段が書き換えるので D-15 に触れる。実装も約 140 行で、(B) の約 60〜85 行より多い）。仕様 §7。実装は W3-21
