# S-323 コマンドが受ける経路の引数の形

- 決定済みで戻さないもの: 経路は一つで、二つ以上は 2。ディレクトリはルートを指し、そうでなければ 2（S-312）。経路を省けば作業ディレクトリから上へ探す（§15.1、S-159）。`check` は渡したファイルの診断だけ（§15.1）。
  `test` は渡したファイルのモジュールのテストだけを選ぶ（S-286、S-311）。`fmt` と `diff --ast` はファイルごとで、この規則の外（S-261、S-312）。`build` の `--target` を省くと 2（§18.2、W10-06）。
- 論点: 仕様 §18.2 の表は `onsa check [--json]`、`onsa fmt [--check]`、`onsa test [...]`、`onsa build --target <名前>`、`onsa audit [...]` の経路を書かない。`onsa interface [--target <名前>] <mod>`、`onsa graph <flow>`、`onsa play <flow>`、`onsa probe <flow>.<name>` は名前を受ける形で書き、`onsa diff --ast` は二つのファイルを書かない。
  §15.1 は「パッケージを読むコマンドに渡す経路（ファイル、ディレクトリ、`onsa.toml`）は一つ」「渡したファイル（無ければ作業ディレクトリ）から上の階層へ `onsa.toml` を探し」とする。
  決まっていないのは、(1) `interface` の `<mod>` がモジュールの経路か、ファイルシステムの経路か。(2) `interface`・`graph`・`build` にファイルを渡したときの意味（そのモジュールに絞るか、パッケージを探す起点だけか、誤りか）。(3) flow の名前と経路を両方取るコマンドの引数の順と、経路を省けるか。
  (4) `.onsa` でも `onsa.toml` でもないファイル。(5) 経路を省き、作業ディレクトリの上に `onsa.toml` が無いとき。
- 今の実装:

- 案:
  - (a) パッケージを読む全てのコマンドで、経路は最後の省ける位置の引数（`.onsa` のファイル、ルートのディレクトリ、`onsa.toml`）。名前を取るコマンドは名前を先に置く（`graph <flow> [<経路>]`、`play <flow> [<経路>]`、`probe <flow>.<name> [<経路>]`）。
    ファイルは結果をそのファイルのモジュールに絞る。`check` は診断（決定済み）、`test` はテスト（決定済み）、`interface` はそのモジュールの宣言だけ、`graph`・`play`・`probe` は flow の名前をそのモジュールの中で探す、`audit` はそのファイルの箇所。`build` はファイルを使い方の誤り（2）にする。`interface` の `<mod>` は `[<経路>]` に改める。
    実装: clap で `check`・`test`・`interface`・`graph` の経路を省けるようにし、`graph` の引数の順を入れ替える（5 か所）。`interface` の出力をファイルのモジュールに絞る（約 5 行）。`graph` の名前を探す範囲を絞る（約 5 行）。
    `build` の経路を `input.rs` の読み込みに通し、ファイルを 2 にする（約 10 行。今は `build` だけが別の読み方をしている）。テストは約 8 件。費用の要因: ファイルの意味は「そのモジュールに絞る」の一つで、`build` だけが絞れないので誤りになる。
  - (b) (a) と同じ形で、ファイルは `interface`・`graph`・`build` ではパッケージを探す起点だけにする（全てのモジュールを出す、パッケージの全体から名前を探す、全体を作る）。
    実装: (a) から `interface` と `graph` の絞りと `build` の誤りを除く（約 15 行少ない）。テストは約 6 件。費用の要因: ファイルの意味がコマンドで二通り（`check`・`test` は絞り、`interface`・`graph`・`build` は起点）。`interface pkg/a.onsa` の出力が、今（そのファイルだけ）から全体に変わる。
  - (c) 仕様の表のまま、`interface <mod>` と `graph <flow>` は名前だけを受け、パッケージは作業ディレクトリから探す。経路を受けるのは `check`・`test`・`build` だけ。
    実装: `interface` の位置の引数をモジュールの経路にし（約 10 行）、`graph` の経路を外す。`interface` に経路を渡す CLI のテスト（`interface_fn_return.rs` の 2 件、`check_json_document.rs` の `interface_json` の 2 件、`syntax_units.rs` の 2 件）を、作業ディレクトリを変えて走らせる形に書き換える。
    費用の要因: 他のパッケージを見るには作業ディレクトリを変える（`--dir` は S-312 で足さないとした）。位置の引数が名前か経路かがコマンドで分かれる。
  - (d) 今の実装の形を仕様にし、§15.1 のとおり `check`・`test`・`interface` の経路を省けるようにする。`graph <経路> <flow>` は経路が先で、省けない。ファイルは `interface`・`graph` では起点だけ（(b) と同じ）。`build` にファイルを渡すのは 2（今の TOML の読み誤りを直す）。
    実装: clap の 3 か所と、`build` のファイルの誤り（約 3 行）。テストは約 4 件。費用の要因: `graph` だけ経路が先で省けず、仕様の `graph <flow>` と順が逆になる。
- 他言語:
  - rustfmt 1.8.0（手元）: ディレクトリを渡すと「`…/src` is a directory」で 1。ファイルを渡すと、そのファイルと `mod` で辿れるファイルを整える（`--check src/main.rs` が `src/m.rs` の差分も出す）。リンクの経路（`link.rs -> real.rs`）を渡すと、差分を `real.rs` の名で出し、リンクを残してリンク先を書く。
  - Go 1.27.2（手元）: `go list ./linked/...` のように、位置の引数はファイルシステムの経路かインポートの経路で、どちらも同じ位置に書く（`go help packages`）。
  - cargo 1.94.1（確かめ）: パッケージは `--manifest-path` か作業ディレクトリから上へ探して決め、位置の引数は名前（`cargo test <filter>`、`cargo run --bin <名前>`）である。
- 推奨と理由: (a)。確度: 中。
  - ファイルの意味が一つ（そのモジュールに絞る）になる。S-286 が `test` に決め、§15.1 が `check` に決めた形を、他のコマンドへそのまま広げる。(b) と (d) は、同じ引数がコマンドで違う意味になる。1 ファイル = 1 モジュールなので、ファイルの経路はモジュールを正確に指す。
  - (c) の名前で指す形は、作業ディレクトリに縛られ（`--dir` は S-312 で足さないとした）、同じ `interface` の位置の引数が、名前（仕様）か経路（今の実装と CLI のテスト）かで書き手が迷う。
  - `build` の結果はパッケージの全体で、絞れない。ファイルを渡す書き手は「そのモジュールだけを作る」と読んでいる恐れがあるので誤りにし、文面でディレクトリか `onsa.toml` を渡すことを示す。後でファイルを起点として受けるよう緩めても、通っていた実行は壊れない。
  - `graph` の名前を先に置くと、仕様の `graph <flow>` がそのまま正しい書き方として残り、経路を省ける。今の順 (d) では、経路を省けるコマンドの中で `graph` だけが例外になる。今の順に頼るテストは無い（CLI のテストに `graph` は無く、golden の比べは driver の関数を呼ぶ）。
  - `interface` の絞りは、今の出力（ファイルを渡すとそのファイルだけ）に近い。W4-14 の上の階層の探索の後は、モジュールの名前が正しく（`sub.b`）なり、`use` が解決する。
  - (a) は (d) より約 25 行多いが、費用の差だけで、規則は少ない。第 2 期の LSP とエディタの連携は開いたファイルを渡す形で、全てのコマンドが同じ意味になる。JS / WASM のターゲットは `build --target` の側で、経路の規則に関わらない。
  - あわせて決めること: `.onsa` でも `onsa.toml` でもないファイルを、パッケージを読むコマンドに渡すのは使い方の誤り（2）。今は `README.md` をソースとして読み E0002 で 1 になり、修復のループがそのファイルを直しに行く。`fmt` は今のまま名前を問わない（ファイルごとの処理で、どちらでも 2）。
  - あわせて決めること: 経路を省き、作業ディレクトリから上に `onsa.toml` が無ければ使い方の誤り（2）。単一のファイルのパッケージはファイルを渡したときだけ。
  - あわせて決めること: `<flow>` は、モジュールの経路付きの名前（`dsp.voice`）か、選んだ範囲（ファイルを渡せばそのモジュール、なければパッケージ）で一つに決まる名前（`voice`）。決まらなければ 2 で、候補の経路を並べる（今の実装のまま）。
  - あわせて決めること: §18.2 の表に `onsa fmt [--check] <ファイル>…` と `onsa diff --ast <旧> <新>` を書く（今の実装のまま）。`audit`・`play`・`probe` は、実装する作業で上の形に従う。
