# S-784 `?` の被演算子が Affine の場所のとき（消費するか、どう書くか）

- 決定済みで戻さないもの: `move` の被演算子の形と、場所でない値への `move` の E0711 と候補（S-605・R-198）。Dup の場所の印（S-609）。借用・`inout` の Affine の場所の候補なしの E0711（S-41・R-117・S-609）。
  フィールドの取り出しで根の全体を消費すること（S-85）。配列の要素を取り出せないこと（§5.2 の 57 行）。`?` の脱出先と E0414（S-192・S-175）。`map_err` の形（S-143）。`move` の引数に新しい値を印なしで渡すこと（S-605・S-609）。
  第 75 組の下書きの「S-784 の仕組みの出所」と「S-784 の形の表」の節（族は「S-786 の族の形の表」。写しは `target/notes/86/g75/draft.md`）。
- 論点: §9.1（14〜16 行）は `?` の型と脱出先を書くが、被演算子が場所のとき、それを消費するか借用するかを書かない。
  §5.2（39・40 行）は消費する位置の一覧に `?` を含まず、印の要らない例外を返り値だけとする（69 行の `move self` の受け手も印を書かない）。§5.4 の表にも `?` の行が無い。
  そのため、所有の Affine の `r` に `let b = r?` と書いたとき、(1) `r` を消費して印が要る（書く形が無い。`move r?` は S-605 の場所でない値の E0711）、(2) 消費しない、(3) 印なしで消費する、のどれかが決まらない。
  今は全ての形が通り、借用の引数から Affine の中身を取り出す形と、同じ `r` から二度取り出す形が Core と後端に届く。
- 今の実装: 形の表のとおり。modes は `?` の被演算子を読む位置で歩くので、どの場所も消費せず、何も出さない（`p10` は取り出した後の `move r` も通る）。
  `take(r?)` は E0703 で、候補の `take(move r?)` が借用の `r` でも通る（R-198 の形）。`let b = move r?` は候補なしの E0711 である。
- 案: どの案も、場所でない値（`mk()?`）は一時の値を消費し、Dup の場所（Copy・Shared）は複製する。`?` の型、脱出先、E0414 は変えない。
  - (a) 印なしで消費する: `?` の被演算子は消費する位置で、`move self` の受け手と同じく印を書かない。場所の扱いは §5.2 の消費の規則のまま（所有の局所の全体は移す、フィールドの経路は根の全体を消費、添字の経路と借用・`inout` の Affine の場所は候補なしの E0711）。
    読む位置（`r?.len()`）でも同じく消費する。`move r?` は S-605 のまま E0711 で、候補は `move` を消す形。
  - (b) 印を書いて消費する: 消費は (a) と同じで、所有の Affine の場所には印を書く。書く形は `move r?` で、`r` を移してから `?` と読む（§5.2 の `move` の被演算子に「場所に `?` を続けた形」を足す。構文は変えない）。
    印の無い `r?` は消費する位置で E0711、`move` の引数で E0703（どちらも候補は `move` の挿入）。印を書けない位置（受け手、演算子の被演算子、条件）の Affine の場所は候補なしの E0711 で、`let b = move r?` と束縛してから使う形を note で示す。
  - (c) 消費しない: `?` の被演算子は読む位置で、中身を写す。被演算子が Dup でない型の場所なら、所有でも借用でも候補なしの E0711 で、`match move r { Some(v) => move v, None => { return None } }` の形を note で示す。
  - (d) `match` と同じに読む: `e?` を `match e { Ok(v) => v, Err(x) => { return Err(x) } }`（`Option` は `Some`・`None`）と同じ規則で検査する。場所の被演算子は借用の `match` の対象なので、`let b = r?` の `b` は借用束縛で、`r` を消費しない。
    消費する位置（`var b = r?`、`take(r?)`）では腕の末尾が借用の Affine で候補なしの E0711。`Err` の道は借用の `x` を返すので、場所の被演算子の `E` が Affine なら E0711（`c04` と同じ）。§5.4 の表に `?` の行を足す。

- 他言語: 
  - rustc 1.94.1（`other/r1.rs`〜`r4.rs`）: 所有の `r: Option<Vec<f32>>` に `r?` を二度書くと E0382「use of moved value: `r`」（note「`branch` takes ownership of the receiver `self`, which moves `r`」）。読む位置の `r?.len()` を二度書いても E0382。
    `&Option<_>` への `r?` は E0277（`Try` を実装しない）で、`(*r)?` は E0507「cannot move out of `*r`」。`r.as_ref()?` と Copy の `Option<u32>` は二度書ける。Rust には呼ぶ側の移動の印が無く、移動は全て印なしである。
  - swiftc 6.3.1（`other/s1.swift`〜`s5.swift`、`-emit-sil`）: `~Copyable` の `consuming B?` に `guard let b = r` を二度書くと「'r' consumed more than once」、`borrowing B?` の `guard let`・`r!`・`r?.n` は「'r' is borrowed and cannot be consumed」。
    `consuming` の `r?.n` を二度書く形（`s5`）は通った。Swift の `try` は投げる関数の呼び出しに付ける印で、場所を被演算子にしない（`s4`）。Swift の `consume x` は任意の印で、消費に必須ではない。
  - Zig: `try a` は `a catch |err| return err` と同じ（[Zig Language Reference、Operators の表](https://ziglang.org/documentation/master/)）。所有の移動の規則が無く、値は写す。手元に処理系が無く、動かしていない。
  - Kotlin の `!!`・`?:` は所有の規則を持たない。手元に処理系が無く未確認。C#・Java・TypeScript・Python には同じ演算子が無い。
- 推奨と理由: S-786 の規則から (a)。確度: 中。
  - `?` の被演算子を消費する位置と読めば、所有・借用・`inout`・フィールド・添字・Dup の答えが §5.2 の消費の規則からそのまま出る。`?` に固有なのは「印を書かない」の一点で、印を書かない消費の位置は `move self` の受け手に既にあり、その理由（観測できる効果は以後使えないことだけで、検査器が局所的に捕まえる）がそのまま当たる。
    構文の読み替えも、§5.4 の表の行も足さない。`r?` の後も `r` が残ると思う書き手は、後の使用の E0704 で局所的に止まり、通るのに意味が違う形は無い。
  - (b) は印の一様さを保つが、`move r?` を場所でない値の E0711 から外す読み替えと、印を書けない位置の規則を足す。`move` の被演算子の形の規則に例外が入り、`move` の位置を足すたびに `p?` を考えることになる。
  - (c) は後で緩められるが、所有の値を `?` で取り出す書き方が無くなり、4 行の `match move` に手で書き直す（候補は作れない）。取り出しが消費か借用かの読みは他の言語でも割れておらず、禁じて守るものが少ない。
  - (d) は既存の `match` の規則から決まるが、§5.4 の表に行を足し、W4-16 の済んだ束縛の状態と §7 の派生元を開け直す。消費する位置では短い形が無く、`E` が Affine の場所はいつも誤りになる。
