# S-609 Copy の変数を `move` の引数に渡す印の非対称（直接の `tk(move n)` と腕の `tk(if c { n } else { 0 })`）

- 空白: §5.2 は、Copy の変数も `move` の引数に直接渡すときは `move` を書く（`make_op(1, move inc)`）とし、S-100 はブロックの末尾の新しい値と Copy の値には `move` を書かないとする。Dup の値の `move` は複製になる（§5.2）。
  そのため、直接の `tk(n)`（`tk` は `move n: U32` の引数）は E0703 で `tk(move n)` だけが正しく、腕では `tk(if c { n } else { 0 })` と `tk(if c { move n } else { 0 })` がどちらも正しい形になり、同じ意味に二つの書き方がある。Copy の変数の印を「直接も腕も要る」か「どちらも要らない」か（か別の形）に一つに決める。
  今の実装は腕の二つとも E0703（W4-09 で直す誤り）。
- 決定: 決定（2026-10-23、利用者が了承。58 回目、第 44 組）: (b)。`move` の印は、所有が移って前の値が以後使えなくなる所にだけ付ける。`move` の引数では Affine の場所にだけ `move` を書き、Dup の場所（Copy、Shared、関数値の変数）には書かない（`tk(n)`、`ts(s)`、`ap(f)`）。
  書くと E0703 で、修正候補はその `move` を消す形（ブロックの末尾も同じで、末尾ごとに一件）。総称の `T: ?Dup` の値は Affine でありうるので書く。`let` などの位置の Dup の値の `move`（`let y = move s`）は所有の束縛を選ぶ印で、今のまま受け付ける。S-605 の E0711 の候補は、どの位置でも各末尾の Affine の変数に `move` を置く形のまま。
  理由（利用者）: `move` を明示するのは所有権の移動が発生するからで、そうでない所に明示すると逆に混乱する。関数の引数の形（関数の項目、捕捉しない無名関数、関数値の変数、Copy のリテラルと変数）が統一される。種を途中で変えるのは大きな影響があるので、`move` の有無で誤りが出る方がむしろ親切という見方もある。
  関数の項目の名前は `move` の被演算子の場所に含めない。`move inc` は位置によらず E0711（候補は `move` を消す形）で、`make_op(1, inc)`、§16.1 は `device.run(move st, inout params, on_audio, on_control)`。理由（利用者）: 関数はローカルの場所を持てず、`move` の後は前の値が使えないという規則が成り立たない。S-190 の呼び出し側の形を改める。
  借用の Affine（`T: ?Dup` の借用を含む）の場所を `move` の引数に置いた形（`take(a)`、`take(if c { a } else { b })`）は、印の有無によらず候補なしの E0711（S-604 の `let` の末尾と同じ）。理由（利用者）: 誤りの出る場所と直す場所が離れ、直しが局所的にならない。
  借用の `T: ?Dup` の `put(move v)` が通る誤りは R-253。仕様 §5.2、§16.1

  利用者が関数の項目の (ii) の理由（所有権の移動が無い所に印を付けない）を挙げ、親がその当たる範囲を読み 1（(a)）と読み 2（(b)）で確かめた。利用者の指摘（読み 1 でも種の変更で前の値を使う所は誤りになる）と (ii) との組み合わせで親が推奨を (b) に改め、利用者が (b) を選んだ。
