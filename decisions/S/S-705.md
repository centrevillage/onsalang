# S-705 extern が効果行で主張した効果を、handler で処理したとき（C の関数は handler を通らない）

- 空白: extern 宣言の効果行は検証されない主張である（§14.1）。handler で処理した効果は `handle` 式の効果行から消える（§8.3）が、extern の C 関数は handler を通らない。
  `uses {Fs}` と主張した C 関数を呼ぶ関数を `handle { … } with memory_fs` で包むと、`Fs` は効果行から消えるが、C の関数は本物のファイルに触れる。`uses {Alloc}` と主張した C 関数を `arena` で包むと、ヒープの無いターゲットでもシグネチャの検査を通るが、C の関数は本物のヒープを使う。
  §8.3 と §14 にこの関係の規則が無い。§8.2 の「`Block` は handler で処理できない」は、この場合の一つが `Block` で表に出たものである（S-704）。
- 決定: extern が主張した効果を handler で処理したときの正しさは言語の保証の外で、書き手が負う（`unsafe` と同じ考え方。2026-10-26、利用者）。この形に診断は足さない。仕様 §14.1 に「extern の関数が主張した効果を handler で処理しても、extern の関数は handler を通らない（主張の正しさは書き手が負う）」の一文を足す。
  `Block` の handler を書くには `unsafe` が要る（§8.4 の `Alloc` の handler と同じ）。§8.2 の「`Block` は handler で処理できない」をこれに改める。検査は第 2 期の handler の作業（`tasks/phase2.md`）。
- 経緯: 71 回目（2026-10-26）、S-704 の議論で親が見つけた（§8.3・§14 を読み、extern と handler の関係の文が無いことを確かめた）。
  利用者: `Block` を処理できる穴は使う側の問題で、`unsafe` を使うようなものである。言語が保証する範囲の外と思う。
  親の初めの案は、一般の場合を保証の外とし、`Block` の禁止は残す形だった。利用者の問い（`Block` を付けるかは API の設計者が決めるが、使う側が差し替えられずに困る場面は無いか）を受けて、親が場面を挙げた。
  一つは待たない効果（`Log`・`Clock`・`Random`）の handler の中（E0612）で、OS の無い機器で UART に書き終わるまで待つ `Log` の handler は、HAL が `Block` を正しく主張していても書けない。もう一つは、待たない関数を求める関数型の引数（E0401）である。
  どちらも、使う側の逃げ道は他人の extern 宣言の書き換えだけになる。`rt` の文脈で短い待ちを呼べないのは、API が `rt` と主張するかの問題で、handler では解けない（E0901）。
  案は、(A) 処理できないまま、(B) 普通に処理でき保証の外、(C) `unsafe` を要する（`Alloc` の handler と同じ。`unsafe` はポリシーで許可されたパッケージだけで書け、`onsa audit` に出る）の三つで、利用者は (C) を選んだ。
