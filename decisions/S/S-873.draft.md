# S-873 §9.1 の `unwrap`・`map_err` の宣言に `rt` が無く、`rt` の関数から呼べるか（今は組込みの表の `unwrap` が通り、std の `map_err` が E0901）

- 決定済みで戻さないもの: 二つのメソッドの一覧と受け手のモード（S-785、§9.1）、`f` の効果行が空（S-143）、flow の本体の関数値（E0806）。`f` の型の引数のモードは S-872。
  第 80 組の下書きの「S-873 の仕組みの出所」と「S-873 の形の表」の節（写しは `target/notes/110/g80/draft.md`、入力は `target/notes/110/g80/probe/`）。
- 論点: §9.1 は `unwrap` と `map_err` の宣言に `rt` を書かず、§10 の規則 4 は `rt` の関数が `rt` でない関数を呼べないとする。字のとおりなら、W5-03 で `unwrap` を std の宣言にすると、`rt` の関数と flow の本体の `unwrap` が誤りになる。
  一方、§9.2 の表と §18 の `audit --panics` は、`rt` の経路の `unwrap` を前提に書いてある。`map_err` は `rt` でない関数型の `f` を呼ぶので、宣言に `rt` を付けるだけでは本体が E0901 になる。
  - 付随の論点（どの案でも決める）: prelude の `panic` を `rt` の関数から呼べるか。§9.2 の表は `rt` の関数の中の panic が境界まで伝わるとし、§15.1 は `panic` をコンパイラが与えるとするが、`rt` かは書いていない。今の実装は `panic` を E0200 にしている（この版は prelude の `panic` を扱わない）。
    (b)〜(d) では、std の `unwrap` の本体が `panic` を呼ぶなら `panic` が `rt` でないと `rt` の宣言が通らない（本体を組込みの原始の操作にする道もある）。(a) でも、`rt` の関数で `unwrap` を `match` と `panic` に書き換える形は、`panic` が `rt` であることを要る。`assert` も同じ扱いかは、この S の範囲の外である。
- 今の実装: 形の表のとおり。`unwrap` は `rt` の中で通り、`map_err` は E0901。
- 案: 
  - (a) 字のとおり: どちらも `rt` でない。`rt` の関数では `match` で書く。
  - (b) どちらも `rt`: `pub rt fn unwrap(move self) -> T` と `pub rt fn map_err[F](move self, f: rt fn(move E) -> F) -> Result[T, F]`。
  - (c) `unwrap` だけ `rt`。`map_err` は `rt` でない（§9.1 のまま）。
  - (d) `unwrap` を `rt` にし、`map_err` は「`f` が `rt` なら、その呼び出しを `rt` と数える」（`rt` の多相）。
  - 形ごとの出力: `rt` の関数の `r.unwrap()` は (a) で E0901、(b)〜(d) で通る。flow の本体の `sample` の `o.unwrap()` は (a) で E0815（今の実装の符号は E0805）、他で通る。
    `rt` の関数の `r.map_err(conv)` は (a)・(c) で E0901、(b)・(d) で通る。`rt` の関数の `map_err` の無名関数は、(b) で本体を `rt` の規則で検査して通り、(d) では無名関数を `rt` に推論する規則が要る。
    `rt` でない関数の `map_err(wrap)`（`rt` でない項目）は (a)・(c)・(d) で通り、(b) で E0401。flow の本体の `map_err` はどの案でも E0806。
  - 書き手から見て（修復のループの回数）: `rt` の関数で `unwrap` を書く書き手は、(a) で 1 回（`match` と `panic` に書き換え）。`rt` の関数で `map_err` を書く書き手は、(a)・(c) で 1 回（`match` に書き換え、4 行ほど）。
    (b) は `rt` でない関数で `map_err` に普通の項目を渡す書き手が 1 回（変換関数に `rt` を足す）。こちらの方が書く頻度は高い（`tests/` の 61 か所の形）。
  - 修正候補: E0901 と E0401 は候補を持たない。どの案も変わらない。
  - 通るプログラム: (a) は今通る `rt` の関数と flow の本体の `unwrap` を誤りにする（`tests/`・`examples/` に当たる形は無い）。(b) は `rt` でない項目を `map_err` に渡す 61 か所（11 ファイル）を E0401 にする。(c) は今の挙動のまま。(d) は (c) に加えて `rt` の関数の `map_err(conv)` を通す。
  - 規則と例外: (a)・(c) は §9.1 の宣言の字で、規則を足さない（(c) は `unwrap` に `rt` を書く）。(b) は §9.1 の宣言の二句。(d) は §10 の規則 4 に、引数の型で呼び出しの `rt` が決まる例外を足す（効果行変数に当たる仕組みが `rt` に無い）。
    (b)〜(d) は、`unwrap` の std の本体が `panic` を呼ぶなら、`panic` を `rt` とする一句も要る（付随の論点）。
  - 実装の量（W5-03）: std の `unwrap` は二つの型で各 5 行ほど（`match move self` と `panic`）で、(a)・(c) は `rt` の有無だけが違う。(b) は `map_err` の宣言の二語と、事例の変換関数（約 25 の宣言）に `rt` を足す。
    (d) は rt の検査に呼び出しの引数の型を読む分岐（約 +15〜30）と、無名関数の `rt` の推論の規則。後の段（降下、C、インタプリタ）は `rt` を見ないので、どの案も手当てが無い。

  - `unwrap` の本体は確保も待ちもせず、再帰もしない。panic は既に `rt` の関数の中で起こりうる（溢れ、添字、§9.2 の表）。§18 の `audit --panics` は `rt` の経路の `unwrap` を列挙すると書いており、`rt` の `unwrap` と整合する。
