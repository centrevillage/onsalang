# S-575 export する flow の `block` の入力でホストの情報（テンポ、拍の位置）を受ける形と、`@param` の必須（E0809）

- 決定済みで戻さないもの: 組の全体は S-580 の下書きの頭（第 35 組の境界の見込み、S-565 の R12、`@param` と数値の ID、S-172、§14.2 の C の API の原則、ランプは扱わない）。第 35 組の C の API への影響（A1〜A8）は S-580 の下書きの「影響」。
- 論点: §11.7「export する flow（§15.3）の `block` の入力には `@param` が必須（E0809）」。S-172 はホストの情報を `block` の入力で渡す方針で、S-572 もテンポと位置を `block` の入力に置いた。このままでは、テンポや拍の位置が自動化できるパラメータとしてホストに見える。
  - 決定済み: `block` の入力で渡す（S-172）、組込みの関数にしない（S-172）、イベントにしない（S-572）。
  - (1) 印の形と C での扱い。(2) 情報の一覧、型、ホストが与えないときの値。(3) 値の時点とブロックの中の進み。
- 今の実装: `@param` の無い `bpm: F64 at block` を export すると、`check .` は 0 で、`build` で E0809「the exported flow `dsp.tempo` needs `@param` on its `block` input `bpm` (§11.7)」、修正候補は `@param(min: 0.0, max: 1.0, default: 0.0) ` の挿入（`t02_noparam`）。
  `@host(tempo)` は E0005「there is no attribute `@host`」で、note に属性の閉じた一覧（§6.5）（`r10`）。
- 案: 例の flow:

```onsa
pub flow arp(
  notes: midi.Message at event,
  @host(tempo)
  bpm: F64 at block,
  @host(beat)
  beat0: F64 at block,
  @param(min: 1, max: 8, default: 4)
  div: U8 at block,
) -> midi.Message at event { … }
```

  - 印:
    - (h1) 属性 `@host(<種類>)` を `block` の入力に付ける（上の例）。種類は閉じた一覧で、種類ごとに型が決まる。export では `@param` か `@host` のどちらか一つが要る。費用: §6.5 に属性を一つ足し、種類の一覧を仕様に置く。
    - (h2) std の struct の型（`transport.Info`。フィールドにテンポ、拍の位置などの全て）の `block` の入力を、export で `@param` なしに認める（型で分ける）。費用: 情報を足すと std の型と C の struct が変わる。
    - (h3) マニフェストで入力の名前と情報を対応させる（`[[plugin]]` の `host = { bpm = "tempo" }`）。ソースには印が無い。費用: シグネチャと `render`・テストからは見えず、マニフェストのキーが増える。
  - C:
    - (hc1) `<p>_params` の欄に置き（ラッパーが書く）、表 `<p>_host_info`（名前、種類、位置）と `<P>_HOST_COUNT`、`onsa.h` の `onsa_host_kind`（末尾に足す限り ABI を変えない）を置く。`_param_info` には入れない。費用: 名前の閉じた一覧に三つ。A3 の位置が要る。
    - (hc2) `<p>_params` に置かず、`_process` に常に `const onsa_host* host`（`onsa.h` の決まった struct。NULL なら下の既定の値）を置き、生成したコードが写す。費用: `_process` の形が変わり（S-570 の回答）、struct に情報を足すと ABI の版が上がる。
  - 情報の一覧（(h1) の種類の例。型と、ホストが与えないときの値）: `tempo`（`F64`、BPM、120.0）、`beat`（`F64`、四分音符の数の位置、0.0）、`bar_start`（`F64`、今の小節の頭の位置、0.0）、`sig_num`・`sig_den`（`U16`、4・4）、`playing`（`Bool`、false）。
  - 時点: どの案でも値はその呼び出しの最初のサンプルの時点で、ブロックの中の進みは flow が `tempo` と `sample_rate()` から数える。呼び出しを分けるラッパーは、分けた位置の値を渡す。
- 他言語:
  - CLAP（`events.h`、`process.h`）: `clap_event_transport` は `flags`（`CLAP_TRANSPORT_HAS_TEMPO`、`HAS_BEATS_TIMELINE`、`HAS_TIME_SIGNATURE`、`IS_PLAYING`）、`song_pos_beats`、`tempo`、`bar_start`、`tsig_num`・`tsig_denom` を持ち、
    `clap_process::transport` は「time info at sample 0」「If null, then this is a free running host」。同じ形のイベント `CLAP_EVENT_TRANSPORT` が列の中にも来る。
  - VST3（`ivstprocesscontext.h`）: `projectTimeMusic`（「musical position in quarter notes」）、`barPositionMusic`、`tempo`、`timeSigNumerator`・`timeSigDenominator`（`int32`）と、`kTempoValid` などの有効の印。
  - AU（`AUAudioUnit.h`）: `AUHostMusicalContextBlock` は `currentTempo`、`timeSignatureNumerator`（`double`）、`timeSignatureDenominator`、`currentBeatPosition`、`currentMeasureDownbeatPosition`。再生の状態は `AUHostTransportStateBlock`。
  - nih-plug: トランスポートの変化（テンポ、拍子、位置）で常に呼び出しを分ける（`src/wrapper/clap/wrapper.rs`）。Cmajor のトランスポートの受け方は未確認。
- 推奨と理由: (h1)、(hc1)、一覧は上の六つ。確度: (1) 中、(2) 低〜中、(3) 中。
  - (h1): `@param` と同じく、flow が何に依るかがシグネチャに出て（本体を読まずに分かる）、入力ごとに名前を選べる。種類を後で足しても、属性の値と `onsa_host_kind` の末尾が増えるだけで壊れない。型を種類ごとに一つに決めるので、変換の規則が要らない。
    (h2) は情報を足すたびに std の型と C の struct が変わる。(h3) は意味がソースから見えず、`render` とテストで同じ値を書く手掛かりが無い。
  - (hc1): 第 35 組で決めた `_process` の形を変えず、ホストは `@param` の欄と同じく書ける。`Params` は Onsa でも C でも全ての `block` の入力を持つ（§11.6）ので、言語と C の形が揃う。(hc2) は `_process` を変え、同じ値を二か所に持つ。
  - 一覧: 三つの形式が共通に与える情報に限った（秒の位置、ループ、録音中は足しても壊さない）。`beat`・`bar_start` は長い曲で位置の精度が要るので `F64`（`F32` は 8192 拍で分解能が 2^-10 拍、48 kHz・120 BPM で約 23 サンプル）で、`tempo` も三つの形式が `double` で渡すので同じ型にそろえる。
  - 時点: 呼び出しの頭の値にすると、`block` の入力の意味（呼び出しごとの値）に収まる。弱いところ: ラッパーが分けた位置で計算し直した拍の位置と、flow が数えた拍の位置は最後の桁で違いうるので、分けると出力の最後の桁が変わりうる（パラメータの変化と同じ）。
  - あわせて決めること: `params_default()` は、全ての `block` の入力に `@param` か `@host` があれば生成し、`@host` の欄は上の既定の値にする（§11.6）。`onsa test --flows` は `@host` の入力に既定の値を与える。
    `@host` は export しない flow の入力にも付けられ、意味は export でだけ持つ（`@param` と同じ）。種類の誤り（`@host(tmpo)`）は E0005（修正候補は一覧の値、`@fp` と同じ）、型の違いと `@param` との重なりは E0809。t02 の E0809 の修正候補に `@host` を足すかは、種類と入力の名前が合うときだけにするかを W10-01 で決める。
  - 新しい S の候補: ブロックの中の拍の位置（拍に合わせた位相）を与える std の flow（M5）。
- 影響:
  - 仕様: §11.7（export の `block` の入力の規則）、§6.5（属性の一覧）、§11.6（`params_default` の条件）、§14.2（(hc1) なら `<p>_host_info`・`<P>_HOST_COUNT`、`onsa.h` の `onsa_host_kind`・`onsa_host_info`。(hc2) なら `_process` の形）、§19.1 の境界の項（S-575 を閉じる）。
  - 診断のコード: E0809、E0005。新しいコードは無い。
  - 作業: W10-01（export の計画で `@host` の入力を分ける）、W10-03（C の表）、W3 の後の属性の構文。`onsa interface` に `@host` を出す。
  - 後で足す変更: 種類を足す形はどの案でも壊さないが、(h2) と (hc2) は struct が変わる。MIDI 2.0 とボイスごとの変調には関わらない。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - (1)・(3) は一致した。(2) は (hc1) で一致し、段 1・段 2 は A3（`offset`）を今入れる（`@host` の欄が混ざると、C の自然な整列から欄の位置を数える今の方法が黙って壊れる）。

- 回答（2026-10-22、会話で利用者。52 回目）:
  - 異常な値（ホストの値の確かめ）: 利用者が、`@host` の入力には値の制限を書けないので、ホストが異常な値を渡したときに Onsa 側へそのまま流すのか、ラッパーで除くのかを問うた。
    親は、今の字（この下書きと §19.1）はホストが値を与えないときの既定の値だけを書き、そのままではラッパーが値を写して Onsa 側へ流れる（書き落とし）と答えた。
    三つの形式のヘッダに範囲の約束は無い: `tempo` は三つとも `double`、拍の位置は CLAP が固定小数点の `clap_beattime`（有限）で VST3・AU が `double`、拍子は CLAP が `uint16_t`、VST3 が `int32`、AU が `Float64`。nih-plug の CLAP のラッパーは印だけを見て値をそのまま写す（`transport.tempo = Some(context.tempo)`）。
    そのまま流すと、`tempo` が 0 なら `60.0 / tempo` が無限大、NaN は出力まで伝わり、`sig_den` が 0 の整数の割り算は panic（`_process` が 1 を返し、ラッパーが `_reset` とフェードイン、S-583）。
    親は (hv1) そのまま流す（ラッパーは型の変換だけ）、(hv2) ラッパーが種類ごとの決まった条件で確かめ、外れた値はホストが与えないときと同じ既定の値にする、(hv3) 書き手が `@host(tempo, min: 20.0, max: 300.0)` で範囲を書く、を出して (hv2) を推した（条件は書き手の好みでなく種類の性質、端の値に寄せる根拠が無いので既定の値、拍子の変換の規則はどの案でも要る、(hv3) は後で足しても壊れない）。
    利用者: 「(hv2) で良いと思います」。(hv2) で了承: 条件は `tempo` が有限で 0 より大きい、`beat`・`bar_start` が有限（負はよい）、`sig_num`・`sig_den` が `U16` に収まる 1 以上の整数で、種類ごとに確かめる。
    条件はラッパーの約束（C の API の外の層）で、C の API と `render`・`onsa test` は値をそのまま渡す（`@param` と同じく、直接呼ぶときは呼び出し側の責任、§11.7）。
  - 了承（52 回目）: 利用者: 「第36組の残り(S-582、S-583、S-575、S-576)は異論ありません」。§19.1 に書いた字（下書きの推奨、独立のレビューの補い、上の答え）で了承。
