# S-704 関数が外の出来事を待つことの印を、効果（`Block`）で表すか、専用の印（`blocking fn`）で表すか

- 空白: §8.2 はブロックを効果の宣言の性質（`blocking effect`）とし、関数がブロックしうるのは効果行に `blocking` の効果を含むときだけとする。資源を持たない `Block` は、extern 関数がブロックすることの主張に使う（§14.1）。
  効果は外部の資源に触れる権限と読める（S-701 の利用者の理由）が、`Block` は資源ではなく、関数が外の出来事を待つかの印である。これを効果で表すか、`rt` と同じく関数の印（`blocking fn`）で表すかを議論した記録が無い（0.2 の「ブロックの扱い」の案 C、`history/onsa-0.2-changes.md:190`。案 A・B と選んだ理由は残っていない）。
- 決定: 効果のまま表す（2026-10-26、利用者）。関数が外の出来事を待ちうることは、効果行に `blocking` の効果を含むことで表す。資源を持たない待ちは `Block`（`std.core` の `pub blocking effect Block {}` で prelude にある、S-702）で主張する。専用の印（`blocking fn`）は足さない。仕様の文は変えない。
  理由: 専用の印は、関数型の新しい次元と、互換・呼ぶ側への伝わり・高階関数の多相・資源の効果との関係・`rt` との排他の規則を足し、資源の効果と二度書けば handler の精度を失う。効果なら `Block` 固有の扱いは三つで、二つ（prelude にある、操作が無い）は `Alloc` と同じ、残る一つ（handler で処理できない）は S-705 の場合の一つである。
- 経緯: 71 回目（2026-10-26）、S-702 の説明で利用者が問うた。親が確かめた経緯: 最初の仕様は `Alloc` と `Block` を `rt` でない全ての関数の暗黙の効果とした。0.2 で案 C（効果の宣言に `blocking`、待機は `Sleep`、同期は `Sync`、extern は `uses {Block}`）にし、0.3 で `Sync` と `Sleep`（「待機が要る用途が無い」）を消した。
  利用者: 組込みではペリフェラルの応答を待つ busy wait が一般的で頻出する。資源へのアクセスにはほとんど暗黙の待ちがある（`Alloc` の確保の時間は非決定的、`Fs` は OS による）。
  親: 「待つ」には (a) 時間が決まらない、(b) 外の出来事を待って止まる、の二つがある。`rt` は両方を除くので、音声のスレッドの安全は `rt` で足りる（`rt fn` は `rt` でない関数を呼べない、E0901）。`blocking` は (b) で、§8.2 の七つの効果のうち `Fs`・`Stdout`・`Stdin` だけである。
  `fn` と `blocking fn` の区別が要るのは、(a) は許すが (b) は許さない文脈である。ブラウザのメインスレッドでは同期の待機ができず（`Atomics.wait` は TypeError、MDN）、JavaScript への変換で `async` にする関数（§13.5）、GUI のスレッド、E0612 がこれに当たる。区別が要るかは、言語全体の変換（§13.5）を目標に残すかとほぼ同じ問いである。
  利用者の問い: 効果で表すのと専用の印にするのとで、どちらが例外の規則を増やすか。親: 効果なら `Block` 固有の扱いは、prelude にあること（`Alloc` と同じ）、操作が無いこと（`Alloc` と同じ）、handler で処理できないこと（S-705）の三つである。伝わり（E0601）、関数型の互換、効果行変数による高階関数の多相、E0904、E0612、`async` は一般の規則のまま働く。
  専用の印なら、関数型の新しい次元と互換の規則、呼ぶ側への伝わりの検査と診断、高階関数の多相（印の変数か、常に待つ側に置くか）、資源の効果との関係（待つ理由が二つになるか、`Fs` を使う関数に二度書く。二度書くと `handle { load() } with memory_fs` が待たないのに印が消えない）、`rt` との排他と E0612 の書き直しが要る。
  参考: Koka は関数の性質を操作の無い効果で表す（`div`「a divergent function may not terminate」、`ndet`。`div` は「handled by the system」、https://koka-lang.github.io/koka/doc/std_core_types.html）。
  利用者: 説明を聞く限り、効果のままにした方が良さそう。
- 補い（2026-10-26、親）: S-705（2026-10-26）で、理由の三つ目の「`Block` は handler で処理できない」を「`Block` の handler を書くには `unsafe` が要る（`Alloc` の handler と同じ）」に改めた。これで三つとも `Alloc` と同じになり、`Block` だけの扱いは残らない。効果で表す決定は変わらない。
  経緯の「七つの効果」は決めた時の §8.2 の表で、表は S-659 の反映（`499c9be`）で `Block` の行が入った。
