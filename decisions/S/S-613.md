# S-613 Copy の型の要素に任意の式を持ち、Shared の葉が静的な値の集成体（`("gain", v)`、`Param { name: "gain", value: v }`）を、破棄の要らない値として扱うか

- 空白: S-610 の (b1) で、全ての要素が静的な値（`const`、補間の無い文字列リテラル、Copy のリテラル、ペイロードの無い列挙子と、その集成体）のリテラルは静的な値で借用の行になった。静的な値は構文で決まり、演算子・呼び出し・ローカルの名前を含む式は所有の行である。
  そのため、Shared の葉は静的な値で Copy の型の要素に任意の式を持つ集成体（`("gain", v)`、`Param { name: "gain", value: v }`、前置の `-` の `("gain", -1)`、`("gain", n + 1)`。`v` は `F32`、`n` は `U32`）は所有の行で、破棄に `Alloc` が要る（rt の関数では E0601）。
  実行時には、`"gain"` は不滅の静的オブジェクトで、`v` や `n + 1` は Copy の値なので、破棄で何も起きない。§12.3 のヒープの無いターゲットでは、`main` と export する関数の効果行に `Alloc` を書けないので、この形をどの関数のローカルにも置けない（利用者「組み込みで書けないとなると制限が大きそう」）。
  束縛の状態は名前の段で構文から一度だけ決める（R-85 (2)、D-15）ので、`v` の型（`F32` なら破棄が要らず、所有する `Str` なら要る）を見られない。型を見る規則（Copy の型の要素は任意の式でよい、など）を足すか、破棄の側で数えないか、今のまま所有にするかが決まっていない。
- 決定: 決定（2026-10-24、利用者が了承。58 回目、第 45 組）: (b)。破棄の要らないリテラルを借用の行に加える（rt の関数とヒープの無いターゲットでも `let p = Param { name: "gain", value: v }`、`for x in [("a", v), ("b", w)]`、`g(("gain", v))` が通る）。
  破棄の要らないリテラルは、静的な値でない集成体のリテラル（配列・`[e; N]`・タプル・struct・ペイロード付きの列挙子・括弧、入れ子を含む）で、各要素が静的な値か、第一級の Copy の型の式か、破棄の要らないリテラルであるもの。第二級の値（§5.3）を要素に持つ形は E0710 で、この判定に入らない。派生元は無く、§7 の重なる束縛の無効化と E0715 は当たらない。値は使う所で組み、S-612 の対象でない。
  理由（助言の担当）: S-610 の根拠（不滅の静的オブジェクトと Copy の値だけの破棄は何もせず、式の形の区別に意味の根拠が無い）が Copy の要素にもそのまま当たる。(a) ではヒープの無いターゲットで `Str` を持つ型をローカル・反復・一時の値に置けず、データの型を書き換えることになる。
  §5.4 の冒頭は「初期化の元の形と、集成体のリテラルの要素の種によって決まる」に改め、「構文で決まり、型を見ない」は静的な値に限る（S-610 の文を改める）。S-610 で所有の例とした `("a", 1 + 2)`・`("a", -1)`・`("a", v)` は破棄の要らないリテラルの例に移す。
  要素が Copy かは本体の型の推論の後の型（既定を当てた後）で決め、`T: Copy` は Copy、境界の無い `T` と `T: ?Dup` は Copy でない。束縛の状態は本体の型の推論の後、modes の前に一度だけ確定する（R-85 (2) の「名前の段で」と `design/03-types.md` の「型は要らない」を改める。一か所で一度決め、全ての段が読む目的は保つ）。細部の作りは W4-07 の設計メモで決める。
  §12.2 の行を「静的な値と破棄の要らないリテラルの複製と破棄（一時の値を含む）: 要らない」に広げ、§10 は変えない。E0601 の note で、集成体のリテラルを所有の行にした最初の要素を名指す（§8.1、W6-03）。rt の関数の誤りの文面の `(Str, <0>)` は R-256。
  範囲の外: `var`、呼び出しの結果、借用の `Str` の要素、束縛の名前の要素（下の補い（L4）で入れた）は、この S では所有のまま。利用者は「実際に Alloc が必要な場面とそうでない場面、今の制限についてまとめておきたい。対応時期は個別のケースで考えましょう」とし、まとめの後にケースごとに対応の時期を決める。仕様 §5.4、§12.2、§8.1
  補い（2026-10-24、利用者が了承「F7はOKです」。58 回目の第 45 組の文書の点検の F7）: 自分の型が `Drop` を実装する（Affine の）リテラルと列挙子は、要素によらず静的な値にも破棄の要らないリテラルにもならず、所有の行（破棄で `drop` が呼ばれる。§4.6、§6.3）。S-610 からの抜けで、S-610 にも同じ補いを書いた。
  第 1 期は `impl Drop` が E0200 で書けないので、事例は第 2 期（`tasks/phase2.md` の trait の行）。W4-07 の判定はリテラルの型の `Drop` の実装を見て除く。
  補い（2026-10-24、利用者が了承「L4 は、(b) を W4-07 に入れる形で良いと思います。既存の決定と整合性の取れない形は早めに対処しましょう」。範囲の外のまとめ `target/notes/58/alloc58/draft.md` の L4）: 破棄の要らないリテラルの要素に、破棄の要らない束縛の名前とその経路を足す（`let nm = "gain"; (nm, v)`、`W { p: p, k: 1 }`）。
  破棄の要らない束縛は、静的な値か破棄の要らないリテラルで初期化した借用束縛と、そこから派生した借用束縛（`let q = p`、分解、`for`、`match` の腕）。値は静的なオブジェクトと Copy の値だけで、名前を要素にしてもその場にリテラルを書いたのと同じなので、どの文脈でも解放は起きない。理由（親）: リテラルを `let` に置くだけで E0601 になる表面の違いを残さない。W4-07 の確定の判定が先に確定した束縛の状態を引く（約 10〜15 行）。
  範囲の外の残り（`var`、呼び出しの結果、借用の `Str` の要素）は、利用者がケースごとに第 2 期と決めた（`tasks/phase2.md` の「解放の起きない破棄」の L1〜L3）。
