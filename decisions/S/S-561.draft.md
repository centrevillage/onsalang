# S-561 同じサンプルの位置のイベントの順

- 決定済みで戻さないもの: S-171（同じ位置のイベントはキューに溜め、イベントごとに一回刻んで順に処理する。`sample` の式からは全て処理した後の状態が見える）。§11.3（`block` の段は `process` の呼び出しごとに一回）。
- 論点: 記号: E(e) は「イベントの入力 `e` のイベントの刻み」を指す説明の記号で、Onsa の構文ではない。入力の番号（p01 など）は、47 回目に dev `4aaa028` の release の `check` で試した入力（S-560 の「今の実装」の表）。
  §19.1「同じ位置のイベントはキューに溜め、イベントのクロックがイベントごとに一回刻んで順に処理する」。何の順かが書かれていない。
  - (1) 一つの入力の同じ位置のイベントの順。(2) 二つ以上のイベントの入力が同じ位置にイベントを持つときの入力の間の順と、その順が結果に現れる場面。S-560 で (1c)（入力は一つまで）を選べば (2) は無い。
  - (3) 同じ位置のイベントの刻みの間で見える値。
  - 決定済み（§11.3）: (3) の `block` と `init` は、その `process` の呼び出しの値で、同じブロックの全てのイベントで同じである（`block` の段はサンプルのループの前に一回）。論点から外す。`sample` の値を読めるかは S-563 の (2) で扱う。
- 今の実装: イベントは無い（p01、p14 の E0302）。
- 案:
  - (1a) ホストが渡した列の順（位置が同じなら列の中の順を保つ）。実装: 列を前から読むだけ。
  - (1b) 言語が並べ直す（同じ高さのノートオフをノートオンの前に、など）。費用の要因: 型の意味を言語が知る必要があり、利用者の型では決まらない。
  - (1c) 決めない（処理系が並べ直してよい）。費用の要因: 同じ入力で結果が変わりうる（§13.4 のビット一致と `render` の比較が成り立たない）。
  - (2a) 入力の宣言の順。同じ位置では、先に宣言した入力のイベントを全て処理してから次の入力へ進む。実装: 境界に何も足さない。
  - (2b) ホストの順。入力をまたいだ順を境界で受ける（列に通し番号、または入力の印付きの一つの列）。第 35 組の境界の形が決める。
  - (2c) 順が結果に現れない形にする。「一つのインスタンス（修飾子の連鎖を含む）の引数と条件に現れるイベントのクロックは一つまで」を規則にする。
    S-560 の (2) で二つの E(e) を比べられないとし、S-563 の (2) でイベントの段から `sample` の値を読めない形（(2iii)）を選ぶなら、ある入力のイベントの処理から、同じ位置の他の入力のイベントの処理の結果が見えないので、順は結果に現れない。仕様は「順は結果に現れない」と書き、処理系が選ぶ。
  - 順が結果に現れる場面（(2c) の規則が無いとき）: `x.when~(a の条件).reset_if~(b の条件)` は、`x` が `a` のイベントごとに動き、`b` のイベントで初期化される。同じ位置に両方があると、「初期化して一歩」と「一歩して初期化」で出力が違う。
- 他言語:
  - Pure Data（手引き §2.6.1）: 「If two message cascades are scheduled for the same logical time, they are carried out in the order they were scheduled」。各カスケードは次のメッセージの前に走り切る（深さ優先）。
  - CLAP（`events.h`）: 入力の列は位置の順で届くが、同じ位置の順は書かれていない。列は一つで、種類の違うイベントも同じ列に入る作り（`type` と `space_id`）。VST3 の `Event` の文書にも順の記述は無い。
  - Esterel v5（primer §4.4.2）: 同じ瞬間の複数回の送出は「combined using the specified binary function or operator that must be commutative and associative」で、順を持たない作りにしている。
  - Cmajor: 同じフレームの、別の端子のイベントの処理の順は、Language Reference に書かれていない（未確認）。
- 推奨と理由: (1a)、(2c)。確度: (1) 高、(2) 中。
  - (1a): MIDI は順に意味がある（同じ位置の同じ高さのノートオフとノートオン）。順を知っているのはホストである。同じ列からは同じ結果になり、位置はブロックの区切りによらないので、ホストの区切りに結果が依存しない。(1c) は決定性を壊し、(1b) は利用者の型で決まらない。
  - (2c): 順の規則を足さずに、境界に入力をまたいだ順を持たせずに済む。Esterel が同じ瞬間の順を持たない作りにしたのと同じ考えである。
    (2a) は簡単だが、一つの MIDI の流れを二つの入力に分けて渡すと、宣言の順がホストの順と食い違う。(2b) は境界の形を重くする。(2c) で始めれば、後で (2a) か (2b) に緩めても今のプログラムを壊さない（今は誤りの形だけが開く）。
  - 入力をまたいだ順が要るときは、一つの入力に和の型で受ける（ホストの順がそのまま残る）。
  - あわせて決めること（(2c) の誤りのコード）: 一つのインスタンスに二つのイベントのクロックが現れる形は、E0815 の範囲（候補）にし、note で「一つの入力に和の型で受ける」を示す。
- 影響:
  - 仕様: §19.1 のイベントの文（同じ位置の順）、(2c) なら §11.5 か §19.1 の修飾子の項に規則を一文。§13.4 は変えない（(1c) だけが関係する）。
  - 診断のコード: (2c) なら E0815 か新しいコード（親が決める）。(2a)・(2b) は無い。
  - 作業: (1a) は C の生成（W10）で列を前から読む。(2c) はクロックの解析（W7-02）か本体の検査（W7-04）で検査する。(2a) は列を混ぜるループの順。
  - 第 35 組への影響: (2b) なら境界に入力をまたいだ順が要る。(2a)・(2c) なら入力ごとの列で足りる。どの案でも、同じ位置の列の中の順はホストのものを保つ。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-20、助言の担当の二段）:
  - (1) は一致した（高）。
  - (2) は割れた。段 1・段 2 は (2a)（宣言の順）、下書きは (2c)（一つのインスタンスの連鎖にイベントのクロックは一つまで）。助言の見方: 順が結果に現れる形は `alloc~(m).when~(is_note(m)).reset_if~(is_start(tr))`（ノートで一歩、Start で初期化、入力は別）で、§19.1 の MIDI の文の自然な拡張である。
    (2c) ではこれが誤りになり、`pulse~` で `sample` の `Bool` に変えると初期化は常に一歩の後になるので、別の入力のままでは「Start と同時のノートを鳴らす」書き方が無い（一つの入力に和の型で受けるには std に合成の型が要り、第 35 組の仕事が増える）。
    (2a) は規則も検査も足さず、書き手が `tr` を先に宣言して順を選ぶ（仕様に注意として書く）。第 33 組の見方（制限は読みの割れる所に絞り、実装の簡単な方）に照らすと、(2c) は制限が過ぎている。下書きの Esterel の引き合いは、結合の関数で順そのものを消す作りで、イベントごとに一回刻む S-171 とは前提が違う。確度: 中。

- 回答（2026-10-21、会話で利用者。50 回目）:
  - 親は、S-567 の答えの上で入力をまたいだ順が結果に出るのは、`reset_if~` の条件のイベントと部品の中で畳み込むイベントが別の入力から来る形（`synth~(m).reset_if~(is_start(tr))`）だけだと説明してから、(2a) 宣言の順、(2b) ホストの順、(2c)（その形を誤り）を出し、(2a) を推した。
  - 利用者は「発生源（外の入力）なら宣言の順、そうでなければ flow の引数の順」を出した上で、「ホストから渡されたイベントの順序を保証しないのは問題となるケースがある。MIDI CLOCK と START は、順序が入れ替わると位相が 1 clock（24 ppqn）ずれる」とした。
    親の答え: 引数の順はライブラリの問題を消すが、部品ごとに順が違い生成が重くなる。大きいのは、コードで決める順（宣言でも引数でも）がホストの順と食い違うこと（`count~(clk).reset_if~(is_start(tr))` がちょうど当たる）。
  - B5（(2)）: (2b) を直した形で了承（利用者「方針としては良い」）。言語の規則は「入力をまたいだ同じ位置の順は、境界が渡す順」。
    境界に求めること: ホストの列に順があるとき（一つの MIDI ポート、CLAP の一つの列）はその順を保つ。順が無いとき（別のホストの列から来るとき）は外の flow の宣言の順で並べる（入力が同じなら結果も同じ、§13.4）。
    渡し方（イベントごとの通し番号か、一つのホストの列は一つの入力だけに受けるか）と、`render` に渡すイベントの書き方（入力をまたいだ順を書ける形）は第 35 組。(2c) の規則（一つのインスタンスにイベントのクロックは一つまで）は採らない。
  - 影響の直し: 第 35 組への影響は「(2b) なので境界に入力をまたいだ順が要る（形は第 35 組）」。仕様は §19.1 のイベントの文に順の規則を一文。診断のコードは無い。作業は C の生成（W10）で列を位置と順で混ぜて回すループ。
  - flow の出力のイベントと入力のイベントの順は、出した刻みの位置で決まり、境界の順には依らない（S-567 の E3・E4）。
