# S-287 `@fp(relaxed)` の緩和が及ぶ範囲

- 空白: `@fp(relaxed)`（今の `@relaxed`）の緩和が関数をまたぐ範囲。緩和した関数が厳密な関数に inline されたとき（逆の向きも）、呼び出し側の演算も緩むか。W2-09 は Clang のプラグマと GCC の関数属性で関数ごとに緩めるが、inline の後の扱いはコンパイラの仕組みで決まる。
  GCC の ISO モードで `-ffp-contract=fast` を明示したビルドは、検出できるマクロが無く `#error` の検査をすり抜ける（関係する事実）。W2-09/t で見つけた（2026-10-08）
- 提案: (b) 緩和は、`@fp(relaxed)` を付けた fn と flow の呼び出しの中で行う全ての演算（呼んだ関数と flow を含む）に許可として及び、処理系は一部だけ緩めても全く緩めなくてもよい。
  strict の関数が書く正確さと順の約束（`std.dsp.sum` の左から右へ）は緩和した関数の呼び出しの中では成り立たず、strict の関数の中の値の判断（`== 0.0`、浮動小数から求めた添字、変換の panic）も変わりうる（§15.5 と `std/dsp.onsa` の doc に但し書き）。
  S-54 は変えない（C では関数ごとの緩和として出し、GCC は関数属性、Clang はプラグマ）。§13.4 の「関数ごとの緩和」の文はそのまま。あわせて §13.4 の「守られていないことが分かるフラグ」に、分からないフラグ（GCC の ISO モードと Clang に明示した `-ffp-contract=fast`）は止められず、必要なフラグを渡すのはビルドする者の責任と足した。
  呼ばれる側が緩和を断る形（`@fp(strict)` など）は、必要になったら `docs/api-candidates.md` の候補にする（(b)。推奨の (a) から利用者が改め、ID を挙げて了承。第 7 組の下書き。仕様 §13.4、§15.5。2026-10-08 決定。実装は W2-09）
