# S-669 std の `target fn` の本体の書き方（宣言に書いた本体が、組込み型でも走るように読める）

- 決定済みで戻さないもの: S-108 の意味（組込み型はプリミティブ、それ以外の型は本体、単相化で選んで Core には決めた方だけを出す）。`Float` は組込みの浮動小数だけ（E0307）。
  S-208（組込みの浮動小数の `abs` は符号のビットを 0 にし、std の本体は利用者の数の型のため。doc コメントは W5-02）。S-69 (4)。R-94（`min`・`max` の境界は `AnyNum`。std の `[T: Num]` は W5-05 が直す）。
- 論点: §15.2「std の `target` 宣言は、本体を持てる（std だけに許す書き方）。処理系がプリミティブを与える型（組込み型）ではプリミティブを使い、与えない型（利用者の数の型の `abs` / `min` / `max`、§13.4）では本体を使う」。
  §13.4「`abs` / `min` / `max` は、std に比較と否定で書いた本体（`abs(x)` は `if x < T.ZERO { -x } else { x }`、…）を持ち、利用者の数の型ではこの本体で計算する」。
  宣言に本体を書くと、組込み型では走らない本体が宣言の中にあり、std のソース（doc コメントや定義へ飛んだ先）を読む書き手は、全ての型でその本体が走ると読みうる。
  `F32` では端の場合で結果が違う（下の今の実装）。問いは二つある。(1) 本体をどの形で書くか。(2) プリミティブも本体も無い型で呼べるときの扱い。
  - 仕組みの出所と目的: 点検 C-16（`history/consistency-check-phase1.md`）は、利用者が `impl Num for Q15` を書けるのに `abs(q)` に実装が無いことを挙げた。
    同じ所で「浮動小数の NaN の伝播と符号付きゼロは、`PartialOrd` だけの総称の本体では表せない」とし、組込み型ではプリミティブに置き換え、「`target` 宣言が既定の本体を持つ形を std の特権に足す」案を出した。S-108（2026-10-06）がそれを決めた。
  - 今の実装で本体が走る型は無い。利用者の型への `impl Trait for Type` が E0200（`Feature::TraitImpls`、`q15num.onsa`）なので、`Num`・`AnyNum` を満たすのは組込みの数の型だけで、全てプリミティブを持つ。
    計画は利用者の `impl Num` / `impl AnyNum` を第 2 期の輪郭の表に置き、「受け付けたら、本体の経路をテストで確かめる」とする（`history/implementation-plan.md` の 246 行）。
    ただし W5-04 の持ち越し（2026-10-23、X-8）は、std の trait を利用者の型に手で実装する形をどの作業で受け付けるかを作業票で確かめるとしていて、第 1 期に開くかはまだ決まっていない（利用者が宣言した trait は第 2 期、`tasks/phase2.md`）。（親の追記）
- 今の実装: std の `abs`・`min`・`max` に本体は無く、組込み型はプリミティブで走る（`zero.onsa` を `onsa test` で 4 件通る。終了コード 0）。
  `F32` の `abs(-0.0).to_bits()` は `0`（`+0.0`）、`min(1.0, NaN)` は NaN、`min(0.0, -0.0).to_bits()` は `0x80000000`（`-0.0`）、`I32` の `abs(-3)` は 3。§13.4 の本体の式どおりなら順に `-0.0`、`1.0`、`0.0` で、三つとも食い違う。
  総称の `fn mag[T: Num](x: T) -> T { abs(x) }` は `F64` と `I8` で通る（`mag.onsa`、`reach.onsa`）。プリミティブも本体も無い型は、表の 15 のとおり今は書けない。
- 案:
  - 本体の書き方（語はどれも仮）。
    - (i) 宣言の本体に印を付ける。印の無い `{` は今の E0002 のまま。
      - (i-1) 既にあるキーワード `else`: `pub target rt fn abs[T: Num](x: T) -> T else { if x < T.ZERO { -x } else { x } }`。「処理系が与え、与えなければこの本体」と読む。`else` は宣言の見出しの最後のトークンと同じ行に書く（次の行は E0003）。
      - (i-2) 文脈だけの新しい語: `… -> T fallback { … }`。見出しの後ろには今どの語も書けないので、識別子を壊さない（`fn fallback()` は今通る、`word_fallback.onsa`）。
    - (ii) 本体を持つ std の関数を、`target` と別の宣言の語にする（宣言と本体は一か所）: `pub builtin rt fn abs[T: Num](x: T) -> T { … }`。`target` はどこでも本体を持たない。
    - (iii) 宣言と定義を分ける。`target` は本体を持たないまま残し、同じシグネチャの別の定義に本体を書く（`pub target rt fn abs[T: Num](x: T) -> T` と `builtin rt fn abs[T: Num](x: T) -> T { if x < T.ZERO { -x } else { x } }`）。
      `target` だけの関数は実装が処理系の組込み、別の定義はプリミティブの無い型の分の実装、と対応が分かれる。std は利用者の型を名指せないので、別の定義は宣言と同じ総称のシグネチャで一つになる。
      シグネチャ（`rt` と効果行を含む）の一致は、`bind` の実装モジュールと同じく検査する。
      - (iii-b) 別の定義を別のモジュール（`std/math/` の下など）に普通の `fn` で置き、宣言との対を処理系の表（R-79）の一列で結ぶ。同じモジュールの名前の重なりは起きない。
    - (iv) trait の既定のメソッドと、std の組込み型の `impl` での上書き（`Num` に `fn abs(self) -> Self { … }` を置き、`impl Num for F32` の中で `target` にする）。
      `x.abs()` の呼び方ができ、§3.4 の「`abs` などにメソッドの形は無い（E0413）。同じ計算に二つの呼び方を作らない（§6.2）」を改めるか、`std.math.abs` を消すことになる。利用者の `impl Num` が `abs` を上書きでき、意味が型ごとに変わりうる。
    - (v) 形は今のまま（宣言に本体）で、std のソースに注記（`///` の doc コメントか `//`）で「組込み型ではプリミティブ」と示す。
    - (vi) 今のまま（S-108 の形）。
    - (vii) 形は今のまま、本体を組込み型でもプリミティブと同じ結果になる式で書く（読み違えても結果が同じになる）。
      `abs` は `if x < T.ZERO { -x } else if x == T.ZERO { T.ZERO } else { x }` で `-0.0` に `+0.0` を返す。`min`・`max` は NaN の分岐と 0 の符号が要り、`AnyNum` の演算だけでは `min` の `-0.0` を `(a * b) * (a + b)` のような読みにくい式で作ることになる。
    - (viii) 本体を書く時期を、利用者の数の型を開く第 2 期の作業に移し、形もそのときに決める。第 1 期は全ての `target` 宣言が本体を持たない（§15.2・§13.4 の本体の文は §19.1 へ）。
    - 宣言と定義を分ける形（(iii)）と分けない形（(i)・(ii)・(v)〜(vii)）の比べ:
      - 読み手: 分けない形は宣言と本体が一か所にある。本体が何のためかを語で示すのは (i)・(ii) で、(v) は注記、(vi) は示さない。(iii) は宣言が「処理系が与える」だけを言い、本体は別の項目にあり、読み手は二か所を見る。
      - シグネチャ: (iii) だけがシグネチャを繰り返し、一致（`rt`・効果行・型パラメータと境界・引数のモード）の検査が要る。§15.2 の `bind` の実装モジュールの検査と同じ形の検査が、std の中にもう一つできる。
      - `bind` との対応: (iii) は「宣言と実装を別に置く」形で、`bind` の実装モジュールと同じ構図になる。(i) は「処理系か `bind` が与え、無ければ `else` の本体」と一文で書ける。
      - `onsa interface`・`primer --std`: どの案でも出すのはシグネチャと doc コメントで、本体は出さない（§18.2）。(ii) は `target` と `builtin` の二つの語が出る。定義へ飛ぶ先は、分けない形は一か所、(iii) は宣言と定義の二か所。
      - 名前の重なり（E0304）: (iii) の同じモジュールの形だけが、同じ名前の二つの項目を対として許す例外を要る。
      - 印の読み: (i-1) の宣言の後ろに置く `else` は他の言語に無い形である（`if` の無い「成り立たなければ」の `else` は、Rust の `let … else` と Swift の `guard … else` にある）。(i-2) の `fallback` は語の意味がより直接だが、文脈の語を一つ増やす。(v) の注記は検査されず、本体と食い違っても止まらない。（親の追記）
      - 書き手の直し（利用者が印の無い `{` の本体を書いたとき、S-670 の二つ目の表）: (i)〜(iv)・(viii) は、構文の段の E0002「takes no body」の後、本体を消すと名前の段の E0200 に変わり、二つの誤りを順に直す（`target` を外せば一度で通る）。
        (v)〜(vii) は本体の有無によらず E0200 一つで、`target` を外せば一度で通る。（親の追記）
      - 予約（§2.2）: (i-1) は既にあるキーワード。(i-2) は見出しの後ろだけの文脈の語。(ii)・(iii) の項目の頭の語は、予約すると今の識別子を壊す（`fn builtin()` は今通る、`words.onsa`）。
        文脈の語にすると、項目の頭の表に無い語を他の言語の修飾として一つの E0002 にする §18.1 の読み（表の 12）に例外が一つできる。

  - プリミティブも本体も無い型で呼べるときの扱い。
    - (x) 呼んだ位置（単相化の後）で誤りにする。`fn mag[T: Num](x: T) -> T { abs(x) }` は境界で通り、`mag(q)` で初めて `abs(x)` の位置が落ちる。
      §15.2 の変換先の E0200（入口から届く使用、S-242・S-309）と同じ仕組みに型の条件を一つ足す形になる。変換先によらず型で決まるので、`onsa check` も報告する。
      文面は「この版で未対応」ではなく「この型には実装が無い」で、E0200 の機能の一行か新しいコードになる。総称の関数の本体は境界で一度検査する（呼び出しで初めて落ちる誤りは無い）という性質が崩れる。
    - (y) 利用者には見せず、std の側で保つ。処理系の表（プリミティブを与える型）と std の宣言の境界を突き合わせる単体テスト（W5-02 の「宣言と `Prim` の 1 対 1」のテストの隣）で、境界が受ける型の全てに実装があることを保つ。
      条件は、境界を満たす組込み型の全てにプリミティブがある（`from_fn`・`check`・`gen.pair` のように全ての型に与えるものを含む）ことと、仕様の上で利用者の型も満たしうる境界（`Float` のように E0307 で閉じた境界の外）なら本体があることの二つ。
      満たせない宣言は、std の境界を狭めて弾く（`Float` と同じ形）。仕様には「std の `target` 宣言は、境界を満たす全ての型で使える」と一文を書く（言語の規則ではなく std の約束）。
      `from_fn` のように処理系が全ての型に与える `target` があるので、言語の規則（コンパイラが std を読むときに検査する形）にすると「全ての型に与える」印が宣言か表に要る。単体テストなら表の欄で足りる。
    - (x)・(y) の選び方は、S-669 の形の案でほとんど変わらない。(iv) だけは trait の既定のメソッドで全ての実装が持つことを型が保つので、どちらも要らない。
      (iii) は (y) の条件の「本体がある」が「対の定義がある」になる。(viii) は、利用者の数の型を開くときに (y) のテストが `abs`・`min`・`max` で落ち、本体を書く作業を強いる。
- 他言語:
  - Rust（rustc 1.94.1 の標準ライブラリのソース）: `#[rustc_intrinsic] pub const fn fabsf32(x: f32) -> f32;` は本体が無く、`f32::abs` はそれを呼ぶ（`core/src/num/f32.rs`）。
    `rotate_left` は同じ属性で本体を持つ（`core/src/intrinsics/mod.rs`）。本体は「fallback body」で、専用の実装を持たないコード生成のバックエンドが使い、「仕様の有効な実装でなければならない」。
    仕様と等価な本体には `#[miri::intrinsic_fallback_is_spec]` を付ける（[std::intrinsics](https://doc.rust-lang.org/nightly/std/intrinsics/index.html)）。本体を使うかはバックエンドごとで、型ごとではない。
  - C++（g++ 15.2.0、`other/c*.cpp`）: 宣言だけの主テンプレートと `float` の明示的な特殊化で、利用者の `Q15` の `mag(q)` はコンパイルを通り、リンクで落ちる（`c1.cpp`、undefined reference）。
    主テンプレートを `= delete` にすると、`mag` の中の呼び出しの位置で「use of deleted function 'T my_abs(T) [with T = Q15]'」（`c3.cpp`。具体化の後の誤り）。
    主テンプレートに総称の本体 `x < T{} ? -x : x` を置き `float` だけ特殊化すると、`my_abs(-0.0f)` は `+0.0`、`my_abs(-0.0)`（`double`）は `-0.0` になる（`c2.cpp`。読み手が主テンプレートの本体から読む結果と、特殊化の結果が分かれる）。
  - Swift 6.3.1: 標準ライブラリの `abs<T: SignedNumeric & Comparable>` は一つの総称の本体の中で型を調べ（`if T.self == T.Magnitude.self { … x.magnitude … }`）、それ以外は `x < (0 as T) ? -x : x`（`stdlib/public/core/Integers.swift`）。
    手元で `abs(-0.0)` は `+0.0`。`min(1.0, .nan)` は `1.0`、`min(.nan, 1.0)` は NaN、`min(0.0, -0.0)` は `+0.0`（`other/s1.swift`。§13.4 の約束とは違う）。
  - Julia（手元に無い）: 総称の `abs(x::Real) = ifelse(signbit(x), -x, x)`（`base/number.jl`）と、浮動小数の型ごとのメソッド `abs(x::IEEEFloat) = abs_float(x)`（`base/float.jl`）が別の定義で、多重ディスパッチがより具体的な方を選ぶ。総称の本体も `signbit` を使うので `-0.0` で同じ結果になる。動作は未確認。
  - GCC: `__builtin_fabs` などは C のライブラリの関数と同じ意味で、「if they are not optimized in a particular case, a call to the library function is emitted」（[Library Builtins](https://gcc.gnu.org/onlinedocs/gcc/Library-Builtins.html)）。手元では未確認。
  - Zig: `@abs` は言語の組込みで、ライブラリの本体を持たない（`@fabs` を置き換えた変更、[commit 5af5d87ad2](https://git.medv.io/zig/commit/5af5d87ad2227b6a7b5347c7217312ef8a83de12.html)）。手元に無く未確認。
- 推奨と理由: 本体の書き方は (i-1)、プリミティブも本体も無い型は (y)。確度: 中。
  - 読み違いの元は、本体が「全ての型の実装」と「プリミティブの無い型の分の実装」のどちらかを、書いた形が言わないことである。(i-1) は本体の前の語でそれを言い、読み手は宣言の一か所で、処理系が与える型とそれ以外の型の分かれを知る。
