# S-725 署名と型の定数式（配列の長さ、const 引数）が、ソースで後ろに書いた `impl` の関連定数を読む形（宣言の順に頼るか）

- 空白: §4.5 は配列の長さと const 引数に関連定数（`P.N`）を書けるとし、§15.1 は項目の名前の解決を書くが、署名と型の定数式の参照が項目の宣言の順に頼るかを書いていない（本体の名前は順に依らずに引ける）。
  例: (a) `type A = [F32; P.N]` を `impl P { pub const N: U32 = 2 }` より前に書く。(b) `impl` の外の fn の署名 `fn f(a: [F32; P.N])` を `impl P` より前に書く。(c) struct のフィールドの長さが自分の型の関連定数を読む `struct S { a: [F32; S.N] }`（`impl S` に `N`）。
  読みは二つに割れる。(1) 順に依らずに引く（(c) は型の大きさが自分の `impl` に頼る形で、閉路でなければ通す）。(2) 署名の段では先に宣言した項目だけを引き、後ろは E0302。
  今の実装: (a)〜(c) は E0302「cannot find `P.N`」で、`impl` を先に書くと (a)・(b) は通る。同じ `impl` のメンバの署名の長さ（`fn f(a: [F32; Self.N])`）は W4-04 U6 から通る（メンバの名前を署名の前に表へ入れる）。再現は `target/notes/78/s725/`（`d1`〜`d4`、U6 の前の dev `5fc054e` も同じ）。
- 決定: 決定（2026-10-28、利用者が ID を挙げて了承。78 回目、第 67 組）: (1)。
  項目と `impl` のメンバの名前は、署名と型（定数式を含む）からも書いた順によらずに引く。後ろに書いた `impl` の関連定数を、前の署名・型別名・フィールド・const の型・const 引数の定数式に書いてよく（自分の型のフィールドが自分の `impl` の関連定数を読む形も、閉路でなければ通る）、他のモジュールの項目を引く結果もモジュールを読む順（ファイルの名前）によらない。今 E0302 の形が通るようになる。
  定数の型も書いた順によらずに確かめる（後ろに書いた `const K: I32`・`impl` の `const N: I32` を配列長に書くと §4.5 の E0401。前者が今黙って通るのは R-299 で、同じ作業で直す）。
  仕様は §15.1 に一文、§4.5 に参照を書いた。実装は W4-05（約 +25〜40 行。全てのモジュールの `impl` のメンバの名前を署名の段の前に表へ入れる前段、定数の型を引いた時点で下ろす遅延、その循環の守り）。
  利用者の条件: 循環への守りが想定より膨らむようなら考え直す（W4-05 の止まる条件にした）。
  親の見積もり（78 回目）: 守りそのものは型別名の展開の守り（`sig.rs` の `alias_ty` の `expanding`）と同じ形で数行である。
  この版では、定数の型が自分を読む形（`impl S { const N: [F32; Self.N] = [0.0; 2] }`）は式で計算した定数の配列長の E0200 になり（`target/notes/78/g67/parent/s725x/cyc.onsa`）、守りは落ちないためのもので新しい診断は要らない。
  膨らみうるのは、遅延の下ろしを `constarg`（`Analysis` だけを受ける）へ渡す道筋である。
- 経緯: 78 回目（2026-10-27）、W4-04 U6/b（onsa-break）の仕様の空白。U6 の実装の報告の範囲の外 4 も同じ形を挙げた。
