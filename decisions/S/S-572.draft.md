# S-572 境界のイベントの値の型と、std のイベントの型（MIDI、トランスポート）

- 決定済みで戻さないもの: 組の全体は S-570 の下書きの頭（第 33・34 組で決めた §19.1 の三つの項、S-565 の R12、§14.2 の C の API の原則）。
- 論点: §11.6「`sample` の入出力の値型は、スカラ、`[スカラ; N]`、または（出力のみ）それらをフィールドに持つ struct」。§14.2「この版で export の引数と返り値に使えるのは、スカラとスカラの `Span` だけである（`@repr(c)` の構造体…は E0200）」。
  §19.1「値は利用者の型を含む Copy の型で…、MIDI と組込みのイベント（トランスポートの Start / Stop / Continue など）は std の型にする（組込みかどうかは型で分かれる。C の ABI での表し方…は、std の型ごとに境界の形として決める）」。
  - 決定済み（S-563 の E7、S-567 の K4）: 最後の値は暗黙に読めるので `latest~` は要らない。std に要る変換は「イベントのあった位置で真の `sample` の脈」の flow（`flow pulse(b: Bool at event) -> Bool at sample`、名前は例）である。
  - (1) 境界のイベントの入出力に出せる型と、C の表し方。(2) std の MIDI の型と、トランスポートの型、置くモジュールと名前。(3) 脈の flow の名前と置き場所。
- 今の実装: std に MIDI の型は無い（`std/` は `dsp`・`math`・`array`・`test`）。enum の `block` の入力に `@param(default: Mode.A)` は E0809「`@param` `default` must be a numeric literal」（`q03`）。
  `@param` の無い enum の `block` の入力を export すると、`check` は 0 で、`build` で E0809（`q09`）。`-> Option[F32] at sample` は E0810（`q04`、文面は R-245）。struct の `sample` の入力は `check` が 0 で、`build` で E0200（`q05`、R-41）。
- 案:
  - (b1) スカラ（§11.7 の `@param` と同じ `F32 F64 I8 I16 I32 U8 U16 U32 Bool`）、`()`、std のイベントの型だけ。利用者の struct・enum・配列は、境界では E0810（flow の中では自由）。
    C: スカラは §14.1 の対応、`()` は値の欄を持たない（`pos` だけ）、std の型は型ごとに §14.2 の表で決める。
  - (b2) (b1) に加えて、`[スカラ; N]` と、`@repr(c)` の利用者の struct（§14.1）。export の `@repr(c)` の E0200（§14.2）を、同じ回に開くことになる。
  - (b3) 全ての Copy の型（enum は印と union、`Option` を含む）。費用の要因: enum の C の表し方（番号と中身）を決める（enum の `@param` の表し方も §19.1 で未決）。
  - MIDI: (m1) MIDI 1.0 の短いメッセージを `U32` に詰めた `midi.Message`（中身を見せない型。bit 16〜23 がステータス、8〜15 がデータ 1、0〜7 がデータ 2、24〜31 は 0）。C では `uint32_t`。判定と取り出しと作る関数を std に置く（`is_note_on`、`note`、`velocity` など）。SysEx は持たない。
    この並びは UMP の MIDI 1.0 の 32 ビットの語の下位 24 ビット、Cmajor の `std::midi::Message` と同じである。
    (m2) UMP の一つのパケット（`[U32; 4]`）。MIDI 2.0 の高い分解能を含む。費用の要因: 16 バイトの値、判定の関数が増える、MIDI 1.0 のホストでは変換が要る。
    (m3) 種類ごとの列挙子を持つ enum（`NoteOn { ch, key, vel }` など）。費用の要因: C の表し方が (b3) と同じ問題になり、後から種類を足すと利用者の `match` が壊れる。
  - トランスポート: (tr1) 別の型を持たない。Start / Stop / Continue は MIDI の System Real-Time のメッセージとして `midi.Message` で受ける。費用の要因: ホストのトランスポートと機器からの MIDI が同じ型になり、ラッパーはどの入力にホストのトランスポートを渡すかを型で決められない。
    (tr2) 別の型 `transport.Event`（中身を見せない型で、種類は Start / Stop / Continue、判定の関数 `is_start` など）。C では種類の番号の `uint32_t`。テンポと位置は、S-172 のとおり `block` の入力で渡す。
    (tr3) 状態の写し（再生中、テンポ、拍の位置、小節の頭、拍子。CLAP の `clap_event_transport` の形）をイベントにする。費用の要因: テンポと位置の置き場所が、S-172 の `block` の入力と二つになる。F64 を含む大きな値。
  - 脈の flow: (p1) S-563 の例の名前のまま `pulse`（`std.dsp`）。(p2) 矩形波の発振器と読まれにくい名前（`trig` など）。(p3) この組では置き場所だけ決め、名前は std の閉じた一覧（M5）で決める。
- 他言語:
  - CLAP（`events.h`）: `clap_event_midi` は `uint8_t data[3]`、`clap_event_midi2` は `uint32_t data[4]`。`clap_event_transport` は `flags`（`CLAP_TRANSPORT_IS_PLAYING` など）、`tempo`、`song_pos_beats`、`bar_start`、`tsig_num` を持つ。
  - VST3（`ivstprocesscontext.h`）: `ProcessContext` に `tempo` と状態の印（`kPlaying`、`kTempoValid`）。AU: `AUMIDIEvent` は `data[3]`、MIDI 2.0 は `AUMIDIEventList`。
  - Cmajor（`standard_library/std_library_midi.cmajor`）: `struct Message { int32 message; }` で、
    `getByte1()` は `(this.message >> 16) & 0xff`。`std_library_notes.cmajor` は `NoteOn { int32 channel; float32 pitch; float32 velocity; }` などの構造化した型を別に持つ。
  - UMP（MIDI Association M2-104-UM。種類の番号は Linux の `include/sound/ump.h` で確かめた）: 0x1 が System、0x2 が MIDI 1.0 Channel Voice（32 ビット）、0x4 が MIDI 2.0 Channel Voice（64 ビット）。
- 推奨と理由: (b1)、(m1)、(tr2)、(p3)。確度: (1) 中、(2) MIDI は中、トランスポートは低〜中、(3) 中。
  - (b1): ABI で約束する表し方が最も少なく、(b2) へは後で開いても壊さない。利用者の型は一番外の flow が std の型から作って中へ渡せる。スカラの一覧を `@param` と揃えると、JavaScript で 64 ビットの整数（§19.1）を境界に出さずに済む。(b3) は enum の表し方の決定を前倒しにする。
  - (m1): 今のホスト（CLAP の `data[3]`、AU の `AUMIDIEvent`、JUCE）が渡す形で、4 バイトで、JavaScript の型付き配列と WASM に素直に載る。並びが UMP と Cmajor と同じなので、ラッパーはずらすだけで変換できる。MIDI 2.0 は後で別の std の型として足せる（prelude の外なので壊さない）。
  - (tr2): §19.1 の「組込みかどうかは型で分かれる」のとおり、ラッパーは型でホストのトランスポートの入力を見分けられる。テンポと位置は S-172 の方向の `block` の入力に置き、置き場所を一つにする。(tr1) は入力を見分けられず、(tr3) は S-172 と重なる。
  - (p3): prelude の外の std の名前は後で足しても壊さないので、今決めることは無い。`pulse` は矩形波の発振器と読まれうる（§0.3 の 5）。
  - あわせて決めること（モジュール）: `std.midi`（`midi.Message`。§19.1 の例の綴り）と `std.transport`（`transport.Event`）。脈の flow は `std.dsp`。std の型から C の型への表は §14.2 に置く。
  - 新しい S の候補: export する flow の `block` の入力にホストの情報（テンポ、拍の位置）を渡す形。§11.7 は export の `block` の入力に `@param` を必須にする（E0809）ので、S-172 の方向のままでは、テンポが自動化できるパラメータとしてホストに見える。
- 影響:
  - 仕様: §11.6・§14.2（境界に出せるイベントの型、std の型の C の表し方の表）、§19.1 のイベントの項、std の一覧（M5）。(b2) なら §14.2 の `@repr(c)` の E0200。
  - 診断のコード: E0810（境界に出せない型）。R-245 の文面の直し（W7-04）は、イベントの型の誤りの文面と一緒に見る。
  - 作業: W10-01（export の計画の型の検査）、W10-03、M5（`std.midi`・`std.transport`・脈の flow）、M6・M8。
  - ラッパー: (tr2) なら、ホストのトランスポートを `transport.Event` の入力へ、MIDI を `midi.Message` の入力へ型で振り分ける（同じ型の入力が二つあるときの振り分けは、ラッパーの作り方の作業で決める）。(tr1) では、どの入力に渡すかを別の手段（マニフェストなど）で決める。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - (1)・MIDI・トランスポートは一致した。脈の flow は小さく割れた。
  - (1) のスカラの集合: 段 1 は §11.6 の `sample` の境界と同じ集合（`I64`・`U64` を含む）、下書きは §11.7 の `@param` の集合（含まない）。段 2 は下書きを採る（JavaScript で 64 ビットの整数を境界に出さない理由は §13.5 の既知の差に沿う。狭い方は後で広げられる）。仕様には、`onsa_param_kind` と同じ並びの `onsa_event_kind` を置けることを、理由と一緒に書く。
  - トランスポートの作る側の名前（段 1）: `continue` は予約語（§2.2）なので関数 `transport.continue_()` を避け、関連定数 `transport.Event.START`・`STOP`・`CONTINUE` にする（判定は `is_start` など）。
  - 脈の flow: 段 1 は名前を今決める (p2)（候補 `trig`。`pulse` は SuperCollider の `Pulse` のように矩形波の発振器の名前）、下書きは (p3)。段 2 は下書きを採る（ABI に触れず、書けるプログラムも変わらない。誤りでない二択は簡単な方）。§19.1 の例の `pulse` に「名前は仮」と添え、M5 の候補に `trig` を挙げる。
  - 論点の抜け（段 1。段 2 はこの組で決める）: std のイベントの型の `Default`（最初のイベントの前の値、E0816）。段 1 の案は、`midi.Message` は 0 の語、`transport.Event` は Stop。
  - 新しい S の候補（export の `block` の入力でホストの情報を受ける形と、§11.7 の `@param` の必須）: 段 2 は別の S にする（イベントでなくパラメータの話で、この組の範囲の外）。S-575 として登録した。
- 回答（2026-10-22、会話で利用者。51 回目）:
  - 利用者が「struct の出力にイベントを含めない」（S-564）の読みを問い、親は、フィールドごとに別のイベントのクロックは持てない（一つの出力は一つのクロック）こと、struct を値に持つイベントは Onsa の中では出せ、export の境界では (b1) により E0810 であることを答えた。
    その際、親が §19.1 に書いた「境界のイベントの入出力に出せる型」の「境界」が、(i) export だけか、(ii) Onsa から呼ぶ生成する API も含むかを書いていないことを知らせ、(i) を出した。
    利用者: 「(i)でしょうね。Onsa内の話であれば、外部境界ではないので、プラグインのラッパーに由来する問題はなく、あえて型を制限する必要はないはずなので」。(i) で了承: (b1) の制限は export（`[export]` の項目と C の API）だけに当たり、Onsa のコードから呼ぶ `process`・`render` では利用者の型も含めて自由。
