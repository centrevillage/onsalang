# S-570 境界のイベントの入力: 生成する API と C の API の形、入力をまたいだ順の渡し方

- 空白: §19.1 のイベントの項（S-560・S-561）は、イベントの入力の意味（入力ごとのクロック、位置はホストが決める、一つの入力の中はホストの列の順、入力をまたいだ順は境界が渡す順で、ホストの列に順があればそれを保ち、無ければ外の flow の入力の宣言の順）を決め、渡し方を第 35 組に送った。§11.6 の `process` と §14.2 の C の `_process` には、イベントの入力の引数が無い。決めること:
  1. 生成する API（§11.6、Onsa のコードから呼ぶ `process`）と C の API（§14.2）のイベントの入力の形（入力ごとの列か、入力の印付きの一つの列か。位置と値の表し方）と、入力をまたいだ順の渡し方。
  2. 列の前提（位置の順に並ぶこと、位置が `frames` より小さいこと）と、守られないときの扱い。`frames` が 0 の呼び出しのイベント。
  3. 関数と型の形を flow によらず一定に保つ約束（§14.2）との関係（イベントの入力の無い flow の引数）と、`process_inplace`・`In` との関係。
- 決定: 決定（2026-10-22、利用者が ID を挙げて了承。51 回目）: イベントの入力は、入力の印の付いた一つの列で渡し、入力をまたいだ順は列の順で決まる。生成する API は `voice.Event` と入力ごとの作る関数を置き、`process` は `params` の後に `events: Span[voice.Event]` を取る（イベントの入力が無ければ取らない）。
  C はイベントの入力のある flow に `<p>_event`・`<P>_EV_<名前>` を生成し、`_process` は `events`・`events_len` を取る（イベントの入力の無い flow は取らない。§11.6 の数の規則で、シグネチャと違う呼び出しは C のコンパイルの誤り。回答の (3b) を 52 回目に (3a) に改めた）。`params`・`cfg` も同じく、`block`・`init` の入力のある flow だけが引数と型を持つ（52 回目、S-112 を改めた）。
  列の前提（`pos < frames`、減らない、入力の番号）を破れば C は 2、生成する API は panic で、`frames` が 0 の呼び出しはイベントを持てない。
  呼び出しを分けても出力はビットで同じ。イベントの段はその呼び出しの `params` を読む。ラッパー向けに `<p>_event_in_info`・`<P>_EVENT_IN_COUNT`・`<P>_EVENT_OUT_KIND` と `onsa.h` の `onsa_event_kind` を置く。仕様 §19.1
- 経緯: X-7（W3 の終わり、2026-10-15、利用者）で、W4 の前に決めて第 1 期の範囲を W4〜W10 に割り当てることになった。第 35 組（境界）の一つで、第 33 組（S-555〜S-559）と第 34 組（S-560〜S-567）の決定を前提にする。パラメータは `block` の入力のままで、ラッパーは変化の位置で呼び出しを分けてよい（S-565、決定済み）。関係: S-171、S-560、S-561、S-565。
