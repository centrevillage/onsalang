# S-583 プラグインの状態と構成: 状態の保存と読み込み、サンプルレートとブロックの長さ、バス、尾

- 決定済みで戻さないもの: 組の全体は S-580 の下書きの頭（第 35 組の境界の見込み、S-565 の R12、`@param` と数値の ID、S-172、§14.2 の C の API の原則、ランプは扱わない）。第 35 組の C の API への影響（A1〜A8）は S-580 の下書きの「影響」。
- 論点: §14.2 の C の API は `init`（サンプルレート）、`reset`、`_new`・`_free`、`@param` の表を持つが、ホストが求める状態の保存と読み込み、最大のブロックの長さ、バスの構成、尾の長さ、バイパスは書かれていない。
  `init` の入力（`Config`）を、ホストに読み込まれたプラグインで誰が与えるかも書かれていない。
  - 決定済み: 遅れは S-576。出力のイベントの容量の式は S-571。
  - (1) 状態。(2) `activate` と `init`、`Config`、`reset` を呼ぶ所と poisoned。(3) `sample` の入出力とホストのバス。(4) 尾とバイパス。
- 今の実装: `pan(x: F32 at sample, sc: F32 at sample, …) -> St at sample` の C は `pz_pan_process(s, p, const float* x, const float* sc, float* l, float* r, frames)`（`t04_stereo`。§14.2 の `In`・`Out` の struct にするのは W10）。他は試していない。
- 案:
  - 状態:
    - (sv1) パラメータの値だけを、文字列の ID と値の組で保存する（版の番号の付いた決まった形。浮動小数はビットの並びで書き、丸めと地域の設定に依らない）。読むとき、知らない ID は捨て、無い ID と型の合わない値は `default` にする。費用: 形を仕様に一つ書き、ラッパーが読み書きする。
    - (sv2) (sv1) に `init` の入力の値を足す（下の (cf3) と組む）。費用: (cf3) の表と、読み込みの後の起動のやり直し。
    - (sv3) (sv1) に状態の写し（`SIZE` のバイト列）を足す。費用: 配置は編集とコンパイラの版で変わり（§12.4）、bulk の領域のポインタを含むので、読み込みの照合（ホットリロードと同じ、§18.3）が要る。
  - `Config`: (cf1) プラグインのターゲットに出す flow は `init` の入力を持てない（そのターゲットのビルドで E0200）。(cf2) `[[plugin]]` に値を書く（`config = { len = 4096 }`）。費用: TOML の値から `Config` の型への写し。
    (cf3) 利用者が選ぶ設定にして状態に保存し、変えたらホストに起動のやり直しを求める（CLAP の `request_restart`）。費用: 表（A7）、ホストへの示し方。
  - `activate` と `init`（どの案でも）: CLAP の `activate`、VST3 の `setupProcessing` と `setActive`、AU の `allocateRenderResources` で `_init` を呼ぶ（サンプルレートを変えるときも `init` のやり直し）。最大のフレームの数は、ラッパーのイベントの入力と出力の列の大きさに使い、列が足りなければ呼び出しを分ける。
    `_reset` を呼ぶ所: (rs1) ホストが求めたときだけ（CLAP の `reset`、AU の `reset`、VST3 の `setActive` の切り直し）。(rs2) (rs1) に加えて、トランスポートの停止と位置の飛び。費用: (rs2) は停止の判定と、エフェクトの尾を切ること。
    poisoned（`_process` が 1）: (pz1) ホストが `reset` か起動のやり直しをするまで無音。(pz2) ラッパーが次の呼び出しの前に `_reset` する。費用: (pz2) は毎回の panic で無音と再開を繰り返しうる。
  - バス:
    - (b1) `sample` の入力ごとに一つの入力のポート（最初が主、二つ目からはサイドチェイン）。スカラはモノ、`[F32; 2]` はステレオ。出力は単一の値なら一つ、struct ならフィールドごとに一つのポート。ポートの名前は入力とフィールドの名前。費用: 形はシグネチャから決まり、キーは増えない。
      二つのスカラの入力（`l`、`r`）や二つのフィールドの struct（§11.6 の `swap`）はステレオでなく二つのモノのポートになり、ステレオは `[F32; 2]` で書く。
    - (b2) 全てのチャンネルを一つの主のポートにまとめる。費用: サイドチェインを表せない。
    - (b3) マニフェストでポートを書く（`ports = [...]`）。費用: シグネチャと同じことを二か所に書き、照合の規則が要る。
    - どの案でも: プラグインのターゲットの `sample` の入出力の型は `F32` だけ（他はそのターゲットで E0200）で、ポートのチャンネルは 1 か 2。VST3 で主でないバスをホストが有効にしなければ、ラッパーは 0 のバッファを渡す。
  - 尾: (ta1) 無限として報告する（CLAP は `tail` の拡張で `INT32_MAX`、VST3 は `kInfiniteTail`。ホストは処理を止めない）。(ta2) `[[plugin]]` に書く（`tail = 48000` か `"infinite"`）。(ta3) コンパイラが数える。費用: (ta1) は無音でも処理を続ける。(ta3) は帰還のある flow で決まらない。
  - バイパス: (by1) プラグインはバイパスを持たない（ホストのバイパスを使う）。(by2) ラッパーがバイパスのパラメータ（CLAP の `CLAP_PARAM_IS_BYPASS`、VST3 の `kIsBypass`、AU の `shouldBypassEffect`）を持ち、入力を遅れ（S-576）だけ遅らせて出力へ渡す。費用: (by2) は入出力の形が対になる flow だけで、遅れの分のバッファ。
- 他言語:
  - CLAP: `ext/state.h`「save and restore both parameter values and non-parameter state」。`ext/params.h`「Plugins are responsible for persisting their parameter's values between sessions by implementing the state extension」。
    `plugin.h` の `reset` は「kills all voices」「The parameter's value remain unchanged」。`ext/tail.h`「Any value greater or equal to INT32_MAX implies infinite tail」。`ext/audio-ports.h`「32 bits support is required for both host and plugins. 64 bits audio is optional」、主のポートは添字 0、`CLAP_PORT_MONO`・`CLAP_PORT_STEREO`、`in_place_pair`。
  - VST3: `IComponent::getState`・`setState` と `IEditController::setComponentState`、`ProcessSetup::maxSamplesPerBlock`、`kNoTail`・`kInfiniteTail`、`setBusArrangements`、バスの種類 `kMain`・`kAux`（「The kMain busses have to place before any others kAux busses」）、`ParameterInfo::kIsBypass`。
  - AU: `fullState` は「A persistable snapshot of the Audio Unit's properties and parameters」で、既定はパラメータの木の値を保存する。`maximumFramesToRender`、`tailTime`（秒）、`shouldBypassEffect`、`channelCapabilities`。
  - nih-plug（`src/wrapper/state.rs`）: パラメータを文字列の ID で、正規化しない値で保存し（「These are stored unnormalized」）、印を付けたフィールドを加え、JSON で書く。DPF は状態を鍵と値の文字列の組で持つ（`DistrhoPlugin.hpp` の `initState`・`setState`）。
- 推奨と理由: (sv1)、(cf1)、(rs1)、(pz1)、(b1)（`F32`、1 か 2 チャンネル）、(ta1)、(by1)。確度: (1) 中〜高、(2) 中（(pz) は低〜中）、(3) 中、(4) 中。
  - (sv1): 文字列の ID は既に保存のための名前として約束され（§11.7、凍結 §15.4）、入力の名前を変えても並べ替えても読める。音の状態（遅延線など）はホストの約束でも保存しない（CLAP の `reset` は値を保つ）。
    (sv3) は配置が版で変わりポインタを含むので、読み込みの照合が要る。(sv2) は (cf3) を採るときだけ要る。ビットで書くと、地域の設定（小数点の字）と丸めに依らず読み直せる。
  - (cf1): プラグインでは値を与える所が無く、今は誤りにすると (cf2)・(cf3) へ後で緩められる。
  - (rs1): 頭出しの意味はホストが決め、(rs2) はホストごとに違う停止の扱いでエフェクトの尾を切る。
  - (pz1): §9.2・§14.2 の poisoned（`reset` まで出力 0）と同じ読みで、誤りを隠さない。(pz2) は panic を繰り返して気付きにくい（確度が低いのは、利用者には読み込み直しまで無音になるため）。
  - (b1): 形がシグネチャから決まり（二か所に書かない）、サイドチェインを表せ、キーが増えない。ステレオを `[F32; 2]` で書かせると、チャンネルの組がシグネチャの一つの値になり、二つのモノの入力と読み分けられる。
    `F32` だけにすると変換の規則が要らず（CLAP は 32 ビットが必須）、1 か 2 チャンネルは三つの形式が共通に名を持つ。他の型とチャンネルの数は後で緩められる。
  - (ta1): 長い尾を切らない。CPU の費用は無音の間も処理を続ける分で、(ta2) は後で足しても壊さない。(ta3) は決まらない flow がある。
  - (by1): ホストのバイパスで足りる。遅れのある flow では、ホストのバイパスで時刻がずれるので、(by2) は S-576 の後に足す（足しても壊さない）。
  - あわせて決めること: VST3 は単一の部品（処理と制御を一つの物にする。`getControllerClassId` の扱いは文書で未確認）。CLAP の `in_place_pair` は、`process_inplace` が生成される形（§11.6）でだけ示す。
    状態の形の版の番号は 1 から始め、形を変えるときに上げ、古い版も読む。
- 影響:
  - 仕様: §14.2（プラグインのラッパーの節: 状態の形、起動、ポート）、§15.3（(cf2)・(ta2)・(b3) なら `[[plugin]]` のキー）。状態の形は利用者のプロジェクトが依る出力なので、基本仕様に置く。
  - 診断のコード: E0200（`init` の入力、`F32` でない入出力、3 チャンネル以上）。
  - 作業: ラッパーの作業（S-580 の時期）。C の API は (sv1)・(cf1) なら変わらない（A6・A7）。S-580 の (w2) なら A3 が要る。
  - 後で足す変更: GUI の状態（パラメータでない設定）は、状態の形の版を上げて節を足す形で入る。ボイスごとの変調と MIDI 2.0 は状態に関わらない。
  - 事例とテスト: 無い。テストベクトルの保留の節は関係しない。
- 独立のレビュー（2026-10-22、助言の担当の二段）:
  - 状態・`Config`・`_reset`・バス・尾は一致した。
  - poisoned は割れた（段 1・段 2 は (pz2) ラッパーが次の呼び出しの前に `_reset` する、下書きは (pz1) ホストが `reset` か起動のやり直しをするまで無音）。段 2 は利用者の判断に出す（B）: 下書きの理由（§9.2 の poisoned の読みと同じ、誤りを隠さない）は言語の側の筋、段 1 の理由（三つの形式で同じに書ける唯一の復帰の形。AU には起動のやり直しを求める口が無い）は器の側の筋。
    どちらでも、panic はホストのログへ一度知らせる（固定の C が `ONSA_PANIC_HANDLER` を定義する）。
  - バイパスは割れた（段 1 は (by2)、下書きは (by1)）。段 2 は下書きを採る: AU は `shouldBypassEffect`（AUv2 の `kAudioUnitProperty_BypassEffect`）をプラグインが実装する形なので、AU の固定の C には入力をそのまま出力へ渡す最低限のバイパスを持たせる。(by2) は S-576 の値が実装された後に足す。
  - 補い（段 1）: 状態の形は文字で、1 行目に `onsa-state 1 <プラグインの版>`、以後 `<id> = <値>`（浮動小数はビットの 16 進、整数は 10 進、`Bool` は `true`・`false`）。形はこの組で決め、文法の字は CLAP の作業で仕様に書く。
  - 事実の補い（段 2）: `getControllerClassId` は `vst_ivstcomponent.h` に宣言がある（単一の部品の扱いの SDK の文書は未確認のまま）。
- 回答（2026-10-22、会話で利用者。51 回目）:
  - panic の後の復帰（B）: 親は (pz1) と (pz2) を出し、演奏者はコードの不具合を直せないので勝手に戻る方が実害が小さく、誤りは途切れた音とホストのログで見えるとして (pz2) を推した。利用者: 「(pz2)でいきましょう」。
    (pz2) で了承: ラッパーは `_process` が 1 を返した次の呼び出しの前に `_reset` を呼ぶ（その呼び出しだけ無音。状態は初期値に戻り、パラメータは残る）。panic はホストのログに一度知らせる。
  - 初期化の直後の乱れ（利用者の問い）: 利用者は、集めて配る N の遅れ（S-578）と `lin_up` の 0 からの立ち上がり（S-577）から、「flowが初期化されてから安定化するまで一定の期間があり、その間の音声が乱れる」とし、フェードインをホスト・ラッパー・C の API の内部のどこの責任にするかを問うた。
    親は、乱れは入力が鳴っている所で状態が初期値に戻るとき（(a) `activate` の後の `_init`、(b) ホストの求めた `_reset` と (pz2) の `_reset`、(c) flow の中の `reset_if~`）に起きるとし、(a)・(b) はラッパーが起こす操作なのでラッパーが短いフェードインを掛け、C の API は flow の意味のまま（`render` とビットで同じ、§13.4）、(c) は書き手の責任（`sample_tick()` の書き方の例か std のフェードの flow、S-579）を出した。
    利用者: 「良いと思います。追記してください」。
    了承: ラッパーは、自分が起こす初期化（(a)・(b)）の直後に、短い決まったフェードイン（数 ms。長さと形は CLAP の作業で決める）を出力に掛ける。C の API と `render` はフェードを持たない。`reset_if~` の乱れは書き手が扱う。
