# S-660 `onsa interface` に無指定（パッケージ内に公開）の項目を並べるか

- 決定済みで戻さないもの: 再公開（`pub use`）の表示は第 2 期（S-596）。この版の `pub use` は E0200 なので、通るプログラムに無い。`use` の束縛はモジュールの中だけ（§15.1）で、どの案でも並べない。
- 論点: §18.2 の `onsa interface` は「公開シグネチャ、…だけを出力」。§15.1 は「可視性は `pub`（パッケージ外に公開）、無指定（パッケージ内に公開）、`priv`（モジュール内のみ）」「パッケージの外に出るのは `pub` を書いたものだけ」、経路にファイルを渡したときは「`interface` はそのモジュールの宣言」を出す。
  「公開」が他のモジュールへの公開（`pub` と無指定）か、パッケージの外への公開（`pub`）かを書いていない。可視性を表示するか、`priv` の項目をどうするかも書いていない。
- 今の実装: `interface.rs` の `module_items` は `def.vis == Vis::Pub` の項目だけを並べる（W3-08 の注記「無指定はモジュールの中と読む」）。
  `pcheck64/vis.onsa`（無指定の `fn f` と `pub fn g`）は `pub fn g() -> I32` だけ。`probe/onlydefault.onsa`（無指定の `fn f` だけ）は `module onlydefault` の見出しだけで終了コード 0。
  `probe/pk2` では、`pub struct Point` の `priv tag: U32` が印なしの `tag: U32  // offset 4` と出る（JSON のフィールドにも可視性の欄が無い）。無指定の `struct Inner` と `priv struct Hidden` は出ないが、その `impl` の `pub` のメンバは出る（S-662 の今の実装）。JSON の項目には今も `vis` の欄がある（無指定は空の文字列）。
- 案: 例のモジュール（`pub fn g`、無指定の `fn f`、`priv fn h`、無指定の `const K: I32 = 3`、`pub struct Point { x: F32, priv tag: U32 }` と `impl Point { pub fn origin() -> Point  fn helper(self) -> F32 }`）で書く。
  - (a) `pub` の項目と `pub` のメンバだけ（今の実装）。例の出力は `pub fn g`、`pub struct Point`、`impl Point` の `pub fn origin` だけ。無指定だけのモジュールは見出しだけになる。
  - (b) `pub` と無指定の項目とメンバを並べ、可視性はソースと同じ語で示す（テキストは `pub fn g() -> I32` と `fn f() -> I32`、JSON は今の `vis` の欄）。`priv` の項目とメンバは並べない。例の出力は (a) に `fn f`、`const K`、`fn helper` が加わる。
  - (c) 引数で切り替える（例えば `--package` で無指定も並べる。既定をどちらにするかも決める）。出力は (a) と (b) の二通り。
  - (d) 渡した経路で変える。ファイルを渡せばそのモジュールの `pub` と無指定（§15.1 の「そのモジュールの宣言」をこの意味に読む）、パッケージを渡せば `pub` だけ。同じモジュールでも引数の形で内容が変わる。
  - 用途ごとの違い: 同じパッケージの中で別のモジュールを書く LLM が骨格を読む（Ori 以来の用途）のに要るのは `pub` と無指定である。第 1 期は std 以外の依存が E0200 なので、利用者のパッケージの外の使い手はいない。依存のパッケージの利用者（第 2 期）に要るのは `pub` だけで、(b) では `pub` の語で選り分けることになる。
  - 実装の量: (a) 0 行。
    (b) 10〜20 行（`module_items` の 6 か所の `public &&` を「`priv` でない」に変え、`impl` のメンバの絞り込みを S-662 の規則に合わせ、テキストの見出しは今の `vis_str` のまま）と golden の書き直し（`tests/golden/interface/voice.txt` に `const MAX_ECHO` と `const MAX_VOICES` の 2 行）。
    (c) (b) に加えて CLI の引数、§18.2 の一句、両方の形の事例、LSP と `onsa_web` の `interface` の引数で 25〜40 行。(d) 10〜15 行。
  - 保守の費用の要因: (a) は無い。(b) は一つの出力で、`primer --std` と第 2 期の凍結のポリシーが `pub` だけを選ぶ規則を持つ。(c) は二つの形を事例と仕様で保つ。(d) は引数の形と内容の対応を仕様に書き、同じモジュールの出力が二通りになる。
- 他言語:
  - Go 1.27.2（`other/gomod`）: `go doc -all .` は公開の名前だけを出し、非公開の型 `inner` とその公開のメソッド `Get` も出さない（公開の `func New() inner` は出す）。`go doc -u -all .` は非公開の `helper`、`type inner`、`func (i inner) Get() int` も出す（`go help doc` の `-u`「Show documentation for unexported as well as exported symbols, methods, and fields」）。
  - Rust: `cargo doc --help`（cargo 1.94）に `--document-private-items  Document private items` がある（既定は公開の項目だけ）。
  - OCaml（未確認、手元に無い）: マニュアルの `ocamlc -i` は「print all defined names (with their inferred types or their definitions)」で、出した後に「remove all declarations of unexported names」して `.mli` にする使い方を示す（https://ocaml.org/manual/5.2/comp.html ）。
  - まとめ: 文書の道具は外に見えるものを既定にし、内側を見る引数を持つものが多い。ただしどれもパッケージの中の可視性の段（Onsa の無指定）を持たない言語で、既定が何を指すかは比べられない。
- 推奨と理由: (b)。確度: 中。
  - 第 1 期にこのコマンドを使うのは、同じパッケージの中でコードを書く LLM と人である。他のモジュールから使えるのは `pub` と無指定で、無指定はパッケージの中で共有する既定の形（S-36）なので、(a) では骨格を読む用途がほとんど働かない。
  - (b) は出力が一つで、可視性はソースと同じ語で見える。外へ出るものだけが要る使い手（`primer --std`、第 2 期の依存の利用者と凍結のポリシー）は `pub` の語か JSON の `vis` の欄で選べる。第 2 期に依存の利用者向けの見方を足すなら、再公開の表示（S-596）と一緒に決めればよく、足しても今の出力を壊さない。
  - (c) は、今は使い手を示せない二つ目の形を約束し、試す形と CLI の面が増える。(d) は §15.1 の「結果をそのファイルのモジュールに絞る」を可視性の範囲の切り替えに使うので、同じモジュールが引数の形で違って見える。
  - (a) の利点は、S-144 の理由（`interface` に外から引けない名前が出ない）と字面が合い、実装を変えないことである。ただし (b) でも、外から引けない名前は `pub` の語の無い行として区別して見える。
  - あわせて決めること（`priv` のフィールド）: `pub struct` の `priv` のフィールドは、大きさと配置の表示のためにどの案でも並ぶ。今は印が無く、外から読み書きできるフィールドと同じ見た目になる。テキストに `priv tag: U32`、JSON のフィールドに `vis` を出す（数行）。別の S にしてもよい。
  - あわせて決めること（`priv` の項目）: (b) は `priv` の項目を並べない。そのモジュールを書く者はソースを読むので、並べても骨格の用途に足すものが少ない。並べる案（全ての宣言）も取れる。
