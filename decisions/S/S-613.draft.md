  - ヒープの無いターゲット（`heapless.out`）: `provides = []` のパッケージで、export する `run` から呼ぶ `fn label(v: F32)` の `let p = Param { name: "gain", value: v }` は E0601（note「`p` owns a `Param`, whose destruction needs `Alloc`」）。
    `label` と `run` に `uses {Alloc}` を書くと `check` は通り、`build` が E0610「the exported function `main.run` uses `Alloc`, which the target does not provide」を出す。`Str` を持たない `Pc { id: 1, value: v }` は `build` まで通る。
- 論点: §5.4 は「静的な値は不滅の静的オブジェクト（§12.8）と Copy の値だけでできた値で、複製も破棄も何もせず、解放も in-place 更新も起きないので、起点にしても安全である」とする。
  一方で同じ節は静的な値を構文で列挙し、「演算子・呼び出し・ローカルの名前を含む式は静的な値でない（`("a", 1 + 2)`、前置の `-` の `("a", -1)`、`["a", x]`、`("a", v)` は所有の行）。構文で決まり、型を見ない」とする（S-610）。
  `("gain", v)`（`v: F32`）は実行時には不滅の静的オブジェクトと Copy の値だけでできており、破棄で何も起きないが、所有の行で、§12.2 の「所有する Shared 値…と、それらを含む値の破棄（参照カウントが 0 になりうる）」に当たって `Alloc` が要る。
  §10 の規則 1 から rt の関数では E0601 になり、§12.3 のヒープの無いターゲットでは `main` と export する関数の効果行に `Alloc` を書けない（E0610）ので、どの関数のローカルにも置けない（形の表の 11〜15 行）。
  S-610 はこの形を決めず（C6）、実例が出たら広げる候補とした。
  - 仕組みの出所: 束縛の状態を構文だけで決めるのは、借用か所有かの判定が 3 か所でずれていた（R-85）のを、一つの関数で一度だけ決めて全ての段が読む形に直すためである（R-85 (2)、D-15、`design/03-types.md`「§5.4 の表は構文だけで決まるので、型は要らない」）。
    構文で決めることは手段で、目的は判定を一つにすることである。`v` が Copy かは型を見ないと分からない（`v` が `Str` なら破棄で解放が起きうる）ので、この形を広げるには、どこかの段で要素の種を見る必要がある。
  - 型だけでも決まらない: 値の型 `(Str, F32)` は、`("gain", v)` でも `("gain", t)`（`t` は所有の `Str`、行 10）でも同じで、後者の破棄は解放を起こしうる。決め手は「Shared の葉が静的な値か」（構文）と「他の要素が Copy か」（型）の組である。

- 案:
  - (a) 今のまま。静的な値は S-610 の構文の判定だけで、行 2〜8 は所有。表を持つには、名前を `const` の表と添字か列挙子にし、`Str` を実行時の集成体に入れない（`Param { id: Id.Gain, value: v }` と `const NAMES: [Str; 2]`）。
    仕様: 変えない。実装: W4-07・W6-02 に判定を足さない。事例は約 4 件（rt の `let`・`for`・借用の引数・`match` の E0601）。費用の要因: `Str` を持つ型（`Param`）がヒープの無いターゲットでは返り値と `move` の引数にしか置けず、データの型を書き換えることになる。`("gain", 0.5)` は通り `("gain", v)` は通らない、という表面の違いが残る。
  - (b) 借用の行に加える。新しい概念「破棄の要らないリテラル」: 集成体のリテラル（配列・`[e; N]`・タプル・struct・ペイロード付きの列挙子・括弧、入れ子を含む）で、各要素が静的な値か、Copy の型の式か、破棄の要らないリテラルであるもの。
    §5.4 の表の借用の行と、`for`・`match` の見出しの借用の行（S-604: 場所か静的な値）に加える。派生元は無い（要素は複製した Copy の値と静的オブジェクトだけ）ので、§7 の重なる束縛の無効化（S-42）と E0715 は当たらない。
    段: 名前の段は S-610 の静的な値の印に加えて、要素の種で決まるリテラルに印を付ける。型の段の終わり（推論の解決の後）に、印の付いたリテラルの要素の種を見て借用か所有に確定し、束縛の状態に一度だけ書く。modes・使用の記録・W6-02 の一時の値の破棄は確定した印を読む。
    仕様: §5.4 の冒頭の「構文的に決まる」と静的な値の項、§12.2 の「静的な値の複製と破棄: 要らない」の行。R-85 (2) の「名前の段で」と `design/03-types.md` の「型は要らない」を改める。§10 の規則 1 は変えない（所有でないので）。
    実装: 名前の段の印（S-610 の再帰に一つの答えを足す、約 15 行）、型の段の終わりの確定（約 30〜40 行）、束縛の状態の所有の欄を型の段の後で書く作り（W4-07 の設計）。modes と破棄点は読むだけ。事例は約 12 件。
    費用の要因: 束縛の種類が要素の型で変わる（`("gain", v)` の `v` を `Str` に変えると、離れた所で E0601 が出うる。所有になった理由を note で示せる）。所有の欄を書く段が名前の段から型の段の後へ移る。
  - (c) 束縛の種類は所有のまま、破棄の側で数えない。W6-02 の破棄点（型の段の後）が、(b) と同じ判定の値と、それで初期化した書き換えられない束縛（`let`、分解、所有の `for` の要素、所有の `match` の腕）の破棄を `Alloc` に数えない。
    `let q = p` の複製や `if` の末尾（S-604）を通すには、束縛ごとに「破棄の要らない値を持つ」印を伝える。`var` は書き換えで静的でない `Str` が入りうるので数える。
    仕様: §5.4 は変えず、§12.2 に例外の行を足し、§10 の規則 1 の「所有する Shared 値…の破棄もできない」に例外を書く。R-85 (2) は変えない。

- 他言語: 手元で動かした結果（入力は `target/notes/58/grp45/probe/other/`）。どれも参考で、Onsa の規則の理由にはしない。
  - Rust 1.94.1（`r1.rs`）: `std::mem::needs_drop` は `(&'static str, f32)` と `&'static str` の struct で `false`、`(String, f32)` で `true`、`(Cow<'static, str>, f32)` で `true`。
    破棄の要否は型で決まり、静的な文字列でも所有でもありうる型（`Cow`）は、値が借用でも破棄が要る型になる（`needs_drop` の文書は「dropping values of type T matters」かを返す最適化の手がかりとする。https://doc.rust-lang.org/std/mem/fn.needs_drop.html）。
  - Swift 6.3.1（`s1.swift`・`s2.swift`）: `_isPOD`（標準ライブラリの公開でない関数）は `(StaticString, Float)` で `true`、`(String, Float)` で `false`。
    `String` のリテラルを持つ struct の束縛は、`-Onone` の SIL で `release_value` が出て（実行時はリテラルが不滅で何もしない）、`-O` で消える。言語の意味は型で決まり、値で省くのは最適化である。
