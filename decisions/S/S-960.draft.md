# S-960 印と前置の記号と相手の間のブロックコメントの誤りの順（`-` 改行 `/* c */ m` と `~` 改行 `/* c */ m`、同じ行の `~ /* c */ m`、文の頭の `@ /* c */`）

- 決定済みで戻さないもの: S-961 の決定と、その決定済みで戻さないもの。第 94 組の下書きの全文（「族の仕組みの出所」「族の形の表」）の写しは `target/notes/127/g94/draft.md`、入力は `P127/g94/probe/`（消えうる。`P127` は 127 回目の scratchpad）
- 論点: §2.1 は閉じたブロックコメントを E0020 とし、候補はトークンの並びと行の切れ目を変えない。S-957 は境界の `?`・属性の `@`・前置の `~` の後の改行について「ブロックコメントはそれ自体の E0020 が先」とした。
  他の記号（前置の `-`・`!`・`^`・`+`、メンバの `.`、`::`、印と `(`、増減）と、同じ行にブロックコメントを挟む形（`- /* c */ x`、接する `-/* c */x`）の順は書かれていない。
  コメントは記号の後ろにあるので、位置の順では記号の隙間の誤りが先になる。コメントを隙間の一部と読むか、別の誤りと読むかで割れる。
  - 決定済み（論点から外す）: ブロックコメントの候補の形（§2.1、S-247）、`?`・`@`・`~` の改行の後のブロックコメントが先であること（S-957）、記号より前に挟む形（`o /* c */ ?`、`id /* c */ ::[`。構文解析器がコメントで先に止まり、どの案でも同じ）。
- 今の実装: 表の「ブロックコメント」の行のとおり。記号と位置で割れる。
  同じ行の `-`・`!`・`^`・`~`・`.`・`::`・印と `(`・文の頭の `@` は一般の E0002 で候補が無く、`--fix-loop` は 0 回で `no-candidate`（`pm_bc_same`、`pt_bc_same`、`ca_bc_same`、`dot_bc_after`、`ta_bc_after`、`tp_bc`、`ats_bc_same`）。
  接する `-/* c */x` はコメントが先（2 回）、`~/* c */m` は `~` が先（3 回）。改行の後は `-`・`!`・`^`・`.` が記号が先、`?`・`@`・`~` がコメントが先（S-957）。`+` はどれも `+` が先で、改行の後の候補はコメントごと消す。
  `--fix-same-place` の違反は無い（`pm_bc_touch`、`pt_bc_touch`、`bq_bc_same`、`pm_nl_bc`、`pt_nl_bc`）。
- 案: 
  - (a) 記号と位置によらず、記号と相手の間（同じ行、接する、改行の前後）のブロックコメントは、その E0020 が先。候補は §2.1 の今の形で、残る隙間（空白か改行）は次の回の記号の E0020 である。ブロックコメントを挟む形は、コメントと隙間の二つの誤りを持つ入力とする（S-957 の事例の `leaves` と同じ読み）。
  - (b) (a) で、同じ行に挟むときは、コメントの候補が記号と相手を接する形にする（`- /* c */ x` は `// c` を上の行に置いて `-x`）。改行の後は (a) と同じ二回。
  - (c) 位置の順で記号が先: コメントを隙間の一部と読み、記号の E0020 の候補が記号をコメントの先へ移す（`/* c */ -x`）。コメントは次の回。S-957 の `決定` の「ブロックコメントはそれ自体の E0020 が先」を改める。
  - (d) 今のまま（記号と位置ごと）。
  - 形ごとの出力: `- /* c */ x` は、(a) がコメントの E0020 で候補の後に `- x`、(b) がコメントの E0020 で候補の後に `-x`、(c) が `-` の E0020 で候補 `/* c */ -x`、(d) が E0002。
    `-` 改行 `/* c */ x` は、(a)・(b) がコメントが先、(c)・(d) が `-` が先。`?` 改行 `/* c */ Dup` は、(a)・(b)・(d) がコメントが先、(c) が `?` が先。
  - 書き手から見て: (a) は二回、(b) は同じ行で一回・改行の後で二回、(c) は二回、(d) は同じ行の多くの形で候補が無く、文面（「expected an operand…」）がコメントを指さない。`~/* c */m` は (d) で三回。
  - 修正候補: (a)〜(c) は当て続けて止まる。(a) と (c) は二つの誤りの入力として一つずつ直し、各候補は自分の誤りを残さない。(d) は候補の無い形で止まる。
  - 通るプログラム: どの案も変わらない（ブロックコメントは全て誤り）。S-957 の三つの事例は、(a)・(b)・(d) で変わらず、(c) で主の位置と `leaves` が変わる。
  - 規則と例外: (a) は §2.1 か §2.5 に一文（S-957 の文を全ての記号に広げる）。(b) は (a) に候補の形の一句（候補の形は約束でないので、例の文）。(c) は一文と S-957 の改め。(d) は記号と位置ごとの一覧になる。
  - 実装の量: (a) は `faust.rs::comment_after_tilde` を族の記号に広げ、`foreign.rs::at_failure` の一か所で「止まった所が族の記号で、改行と行コメントの先がブロックコメントなら、ブロックコメントの行だけ」とする約 +10〜15、`~` だけの分岐を除いて約 −8。`prefix_plus` の候補がコメントを消す形もこれで当たらなくなる。
    (b) は (a) に `comments.rs::block_comment` の削除の範囲の分け（前置か二項かで、`a - /* c */ b` の空白は残す）約 +15〜25。
    (c) は各行（`spaces.rs`、`lines.rs`、`faust.rs`、`paths.rs`、`assign.rs`）の相手の探し方がブロックコメントを越え、読んだ所で照合する `?`・`@` が構文解析器のコメントでの停止より先に当たるようにする約 +30〜60。(d) は 0。
  - 後の作業への手当て: (a)・(b) は、族の記号が増えても一覧に足すだけである。(c) は行を足すたびにコメントを越える処理が要る。
- 他言語: C（clang 21）、Rust（1.94.1）、JavaScript（Node 26.11.1）は `- /* c */ x` を `-x` と読んで通す（`other/c1.c`、`r1.rs`、`j.js`）。swiftc 6.3.3 は `-/* c */x` も「unary operator cannot be separated from its operand」とし、コメントを隙間に数える。どれも Onsa のブロックコメントの誤りとの順の参考にはならない。
