# S-596 モジュールの再公開（`pub use kp.inner` の後の他のモジュールの `use main.inner.{g}`）

- 決定済みで戻さないもの: 可視性の 3 段階、`use` の束縛は無指定でもモジュールの中、再公開は `pub use` だけで `pub` でない項目の `pub use` は E0303、flow の生成項目は flow の可視性を継ぐ（S-36）。同じ名前の二度目の取り込みは E0304（S-17）。
  `use` の経路は絶対経路で、頭はルート直下のモジュールか依存のパッケージ名だけ（S-37）。取り込める一覧に依存のパッケージそのもの（`use std`）とルート直下のモジュール（`use kp`）と flow の名前空間を足し、モジュールを取り込む `use` は下の全てのモジュールへの辺として数える（S-594 の (x1)）。
  名前の段で失敗した `use` の取り込む名前は、使う所を黙らせる集合に入れ、E0304 の相手にしない（S-462）。モジュール間の循環は E0310（§15.1）。
- 論点: 仕様 §15.1「`use` で取り込んだ名前は、そのモジュールの中でだけ使える（…無指定の `use` はパッケージ内に公開しない…）。再公開は `pub use` のみで、取り込めるのは `pub` の項目だけ（`pub` でない項目の `pub use` は E0303）」。
  モジュールはファイルで宣言が無く、§15.1 の「可視性を書けるのは…宣言…だけ」により可視性を持たない。「`pub` の項目だけ」を字のまま読めばモジュールとパッケージは再公開できないが、そうと書かれてはおらず、今の実装は通す。
  §15.1 は「各 `use` は、書く位置にも他の `use` にもよらずに決まる」とし、W4-03 は「`use` は絶対経路で独立に解決し、モジュールの間は依存の順」とする。再公開した束縛を経路の途中に通すと、`use` が他のモジュール（や同じモジュール）の `use` に依る。
  S-462 は、失敗した `pub use` の名前を他のモジュールが取り込む形をこの S に送った。形は次のとおり（「今の実装」は `check`。`rx1.py`〜`rx4.py`）。

- 今の実装: 表の列のとおり。`resolve_imports`（`crates/onsa_sema/src/sig/collect.rs`）はモジュールを依存の順に、モジュールの中の `use` を書いた順に解決し、経路の各要素をモジュールの束縛の表（項目と `use` の束縛）から先に引き、無ければ子モジュールを引く（`resolve.rs` の `member`）。
  このため、再公開の束縛が経路の途中に通り（6〜12 行）、同じ名前の子モジュールより束縛が先に当たり（18 行）、自分のモジュールの中では書く順で結果が変わる（17 行）。

- 案:
  - (a) 再公開できるのは項目だけ。経路の途中は定義だけをたどる。
    一: `pub use` で取り込めるのは `pub` の項目（flow とその生成項目を含む）だけで、モジュール・ルート直下のモジュール・依存のパッケージの `pub use`（6〜11 行）は E0303。note で、モジュールとパッケージは可視性を持たず再公開できないことと、中の項目を並びで再公開する形（`pub use kp.inner.{g}`）を示す。
    二: `use` と本体の経路の、最後より前の要素は、子モジュールと定義した flow だけを引き、`use` の束縛を引かない（12・14・17・22 行は E0302）。最後の要素（取り込む名前、本体の最後の名前）は、項目・子モジュールと、見える `pub use` の束縛を引く（1・4・5 行）。
    `pub` でない `use` を `pub use` に直しても 14 行は通らない。`use` が他の `use` に依るのは最後の要素だけで、それは別のモジュールの `pub use` なので、モジュールの間の依存の順（E0310 の辺）で決まる。自分のモジュールの最後の要素は同じ名前の二度目（E0304）にしかならないので、書く順に依らない。
    実装: W4-03 の `use` の解決で、経路の途中を引く所を定義の表に限る（作り直すので数行の違い）、`pub use` の取り込む先の種類の検査（5〜10 行）。事例: 6〜12・14・17・22 行の否定例と、1・4・5 行の正例。
    費用の要因: 今通る 6〜12 行（`reexp.py`、`rx1.py`）が誤りになる。モジュールの別名の経路は作れず、使う側は定義の経路（`use kp.inner`）を書く。`use main.{lp}` の後の `lp.State` は通るが、`use main.lp.{State}` と本体の `main.lp.State` は E0302 になる。
  - (b) 取り込めるもの全てを再公開でき、経路は見える再公開の束縛を途中にも通る（今の実装の形）。
    §15.1 の文を「`pub use` で取り込めるのは、`pub` の項目と、モジュール・パッケージ・flow の名前空間（可視性を持たない）」に改め、「各 `use` は…他の `use` にもよらずに決まる」を経路の頭だけの文に狭める。
    モジュールの中の `use` も互いの依存の順で解決し（17 行を書く順によらず通す）、モジュールの中の循環（`pub use a.p.{q}` と `pub use a.q.{p}` の類）を誤りにする新しい規則が要る。18 行の `pub` でない `use` が子モジュールへの経路を隠す形（r39）を無くすため、`use` の束縛と子モジュールの名前の重なりを E0304 にするか、途中の要素は子モジュールを先に引く規則が要る。
    実装: モジュールの中の依存の順と循環の検査（30〜50 行）、失敗した束縛を経路の途中に通したときの扱い（20 行の黙らせ方、5〜10 行）、`interface` に再公開したモジュールを出す所。事例: 6〜12・17・20 行の正例と黙る例、モジュールの中の循環の否定例。
    費用の要因: 一つのモジュールに経路が幾つもできる（`std.math` を `main.math` としても書ける）。名前を探す道具（grep、LSP の参照）は再公開を辿る。
    依存のパッケージを再公開すると、外のパッケージが `[dependencies]` に書かないパッケージを経路で引ける（R-39 の「依存は `use` だけで決まり、宣言していないパッケージを名前で引ける問題も無くなる」が、再公開の分だけ弱まる。今は依存が std だけなので、第 2 期の依存で効く）。
  - (c) モジュールとパッケージも再公開できるが、経路の途中は定義だけをたどる。再公開したモジュールは最後の要素としてだけ取り込め（`use main.{inner}`、`use main.inner`）、本体で `inner.g()` と使う。`use main.inner.{g}` と本体の `main.inner.g()` は E0302。
    実装: (a) から `pub use` の種類の検査を除いたもの。費用の要因: `use main.inner` が通って `use main.inner.{g}` が通らない、表面の食い違いができる。依存のパッケージの再公開は (b) と同じ。

- 推奨と理由: (a)。確度: 中。
  - 一は §15.1 の今の文を字のまま読んだ形で、新しい規則を足さない。モジュールとパッケージは可視性を持たず、「取り込めるのは `pub` の項目だけ」に入らない。S-36 の E0303 の文がそのまま当たる。
    二は、一の後に残る二つの形（再公開した flow を通る 22 行と、モジュールの中だけの束縛を通る 14 行）を閉じる一文で、どちらも今は通らない（22 行は R-50 で、14 行は E0303）。
  - モジュールは可視性を持たないので、どのモジュールも定義の経路で既に取り込める。モジュールの再公開が足すのは同じモジュールへの別の経路だけで、できることは増えない。項目の再公開（外のパッケージに見せる入口をまとめる形）は (a) でも残る。
  - 解決が単純になる。経路の途中は定義の木だけを見るので、`use` が他の `use` に依るのは最後の要素の、別のモジュールの `pub use` だけで、モジュールの間の依存の順で一度ずつ解決すれば止まる。
    モジュールの中の順の規則と、モジュールの中の循環の新しい規則が要らず、§15.1 の「書く位置にも他の `use` にもよらずに決まる」と W4-03 の「独立に解決」を保つ（17 行の、今の書く順で変わる挙動も無くなる）。
  - `pub` でない `use` の名前が他のモジュールの経路に混ざらない（14・18 行の r16・r39 で、モジュールの中だけの束縛が他のモジュールからの子モジュールへの経路を隠す形が、(a) では起きない）。
  - 依存の関係が `use` と `[dependencies]` で閉じたままになる。依存のパッケージを他のパッケージの経路から引けない（R-39 の決定の性質を、第 2 期の依存でも保つ）。
  - 後で緩められるか: (a) から (c)・(b) へは、誤りだった `pub use` と経路を通すだけで、通っていたプログラムは壊れない。逆は壊す。今の書き手にとって (a) の制限は、定義の経路を書けばよいだけで、回避策がある。
  - 第 2 期と JS / WASM: 生成するコードの名前は定義の経路から作る（§11.6 の `__`）ので、どの案でも変わらない。第 2 期の std の `Str`・`Map` などの API を入口のモジュールにまとめる形は、項目の再公開で書ける。
  - あわせて決めること: 6〜11 行のコードは E0303（「`pub` でない項目の `pub use` は E0303」の延長。直し方が「項目を並べる」で、種類の違いとして E0308 にする読みもある）。確度は中。
  - あわせて決めること（S-462 の残り、19・2 行）: `pub use` で失敗した名前を他のモジュールが取り込むと、取り込んだ名前も失敗した名前として扱い、その `use` にも使う所にも診断を出さない（`main` の `use` を直せば全てが直る、一つの誤りの連鎖のため）。
    `pub` でない失敗した `use` の名前は、解決した `pub` でない束縛と同じく他のモジュールから見えない（3 行と同じ E0303。直しても見えないので本物の誤り）。20 行（失敗した `pub use` を経路の途中に通す形）は、(a) では `main` の `use` によらず E0302 で、本物の誤りとして出す。確度は中。
  - あわせて決めること（18 行）: モジュールの名前（項目と `use` の束縛）と同じ名前の子モジュールは E0304（§15.1 の「モジュールの項目と同じ名前の子モジュール」に `use` の束縛を含める）。(a) では経路の途中は必ず子モジュールなので読みは割れないが、他のモジュールから最後の要素で `use main.{inner}` と書いたとき、子モジュールと再公開した項目のどちらかが決まらない。確度は低。
  - 別の S にしてよい論点: `onsa interface` が `pub use` の再公開（項目）を出すか（23 行。項目の再公開は決定済みなので、どの案でも残る。新しい S の候補）。
