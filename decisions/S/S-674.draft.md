# S-674 予約語の名前で始まる本体の経路（ルート直下の `static.onsa` の後の `static.tick()`）の診断のコードと修正候補

- 決定済みで戻さないもの: `use` は絶対経路で、頭はルート直下のモジュールか依存のパッケージ名だけ。自分のパッケージ名を頭に書いた `use` は E0302（S-37）。その候補の形（`fx.` を外す、`use fx.{a}` は `use a`、`use fx.{a, b}` は二行、`use fx` は候補なしで note。S-663）。
  取り込めるものにパッケージそのものとルート直下のモジュールを足し、モジュールを取り込む `use` は下の全てのモジュールへの辺として数える（自分自身は除く。S-594 の (x1)）。取り込む名前の読みと、二つの書き方が同じ束縛を作ること（S-594 の二）。
  `use` の束縛と子モジュールの名前の空間（S-611）。名前の段で失敗した `use` の名前は使う所で黙る（S-462）。ディレクトリだけのモジュールの取り込み（S-666）。E0302 の候補に綴りの近い名前を出さない（S-258）。
  族の表（族の全ての形、31 行）と族の規則から決まる部分は、第 58 組の下書きの「族の表と既決の規則（S-594）」の節（写しは `target/notes/66/g58/draft.md`）。
- 論点: §2.2「`clock`・`ser`・`static` は構文として受け付けない（現れた位置で E0200、機能名を添える…）」「パスの `.` の直後と `use` の経路の頭は、他のキーワードと同じく名前として読む（…`clock.onsa` のモジュールは `kp.clock.tick()` で使える）。ただし `use` で取り込む名前…は、現れた位置で E0200」。
  名前として読む位置の一覧に本体の経路の頭は無いので、字のとおりなら `static.tick()` の `static` は E0200 である（読み (2)）。頭を名前として読めば、本体の空間に無いので §15.1 の `use` の無い経路の E0302 になる（読み (1)）。§2.4 の補間の経路は「予約語が頭なら E0200」と書く。
  ルート直下の予約語の名前のモジュールの中に届くのは、`use static.{tick}`（表の 28 行）と `use static.sub`（子モジュール）だけで、`use static` は E0200（29 行、R-266）なので、本体の頭の `static` を束縛にする書き方は無い。コードとあわせて候補の形を決める。
- 今の実装: `clock`・`ser` は、本体の頭（深い経路、型の位置、一要素を含む）で構文の段の E0200「this version does not support the declaration of a derived clock (the reserved word `clock`)」で、候補なし。`fmt --check` は終了コード 2（`rw_clock_body`、`rw_clock_body_deep`、`rw_clock_type`、`rw_clock_single`、`rw_ser_*`）。`use clock` は通るが、その後の `clock.tick()` も E0200（`rw_clock_use_whole`）。
  `static` は予約がまだ入っていない（S-615 の予約は W5-11。`pub fn static()` が通る、`rw_decl.onsa`）ので普通の名前と同じで、`static.tick()` は E0302 と候補 `use static`（`rw_static_body`）、`use static` の後の `static.tick()` は通る（`rw_static_use_whole`）。
  `clock` では `use clock` が通っても、使う所が E0200 である。`use static.{tick}` の後の `tick()` は通る（`rw_static_use_head`）。
- 案:
  - (a) §2.2 の字のとおり、構文の段の E0200 で候補なし。note で `use static.{tick}` の後の `tick()` を示す。§18.1: 候補が無いので約束は当たらず、修復のループは止まる。
    実装は、`static` の予約（W5-11）が入れば `clock`・`ser` と同じ経路で済み、足すのは note の文（数行）。§2.2 は変えないか、「本体の経路の頭も現れた位置」を例として一句足す。
    費用の要因: 書き手は note から二か所を直す。予約語の名前のモジュールは並びでしか使えない（S-594 で受けた費用）。
  - (b) (a) の E0200 に候補を付ける（`use static.{tick}` を足し、`static.tick` を `tick` にする。子モジュールなら `use static.sub` と `sub.h()`）。
    §18.1: 構文の段はモジュールの木と名前を知らず、`static.onsa` があるか、`tick` の名前が空いているか、循環しないかを確かめられない。名前の段は構文の誤りのある単位を見ない（§18.1 の段の順）。
    確かめない候補は、当てた後の名前の段の誤り（E0302・E0304）を「後の段の診断」として約束の外に出すだけで、修復のループに無関係の編集をさせうる。確かめるなら、構文の段の誤りのある単位を名前の段でもう一度見る例外が要る。
    実装は候補の組み立てで約 30〜40 行と、段の例外。費用の要因: 各処理を一度だけ行う段の原則から外れる。
  - (c) 本体の経路の頭の予約語を、後に `.` が続くときは名前として読み、名前の段の E0302（候補なし）にする。§2.2 の名前として読む位置に一つ足す。束縛を作る書き方が無いので、この E0302 は必ず出る。
    実装は字句か構文の読みで `.` を先読みする分岐（10〜20 行）と、§2.4 の補間の頭（今は E0200）を揃えるかの判断。
    費用の要因: 予約語を名前として読む位置が増え、`static.x` の形が構文の段を通るので fmt がそのファイルを書き換える。後で `static` に意味を与えるとき（§19.1 の静的なものだけを指す印）、本体の `static.` の読みと衝突しうる。
  - (d) (c) に加え、名前の段で候補（`use static.{tick}` を足して `tick()`、子モジュールなら `use static.sub` と `sub.h()`）を出す。名前の段なら、`tick` の名前が空き、経路が最後まで解決し、循環しないことを確かめられる。S-673 の論点 1 の (b) と同じ「頭を外し、次の要素を `use` で取り込む」形。
    実装は (c) に約 30〜40 行（S-673 の (b) と共有できる）。費用の要因: (c) と同じ。候補の判定が他の名前（`tick`）の束縛の状態に依る。
  - R-266 との関係: どの案でも `use static` は E0200（R-266、U3b）なので、`use static` を足す候補は作れない。読み (1) のまま今の `not_in_body` を残すなら、予約語の頭では `use` を足さない判定が要る（W4-03 の持ち越しの「`use` で束縛できる名前か」の一つの述語）。
    (a)・(b) では、予約語の E0200 が構文の段で出るので名前の段に届かず、その判定は要らない。

- 推奨と理由: (a)。確度: 中〜高。
  - §2.2 は予約語を名前として読む位置を一覧（`.` の直後と `use` の経路の頭）で書き、本体の経路の頭は一覧に無い。字のとおりの読みは E0200 で、`clock`・`ser` の今の実装もそうである。§2.4 の補間の「予約語が頭なら E0200」とも揃う。
    (c)・(d) は一覧に位置を足す例外で、将来 `static` などに意味を与えるときに読みの余地を狭める。
  - 候補は、構文の段では当たるかを確かめられず、確かめるには段の例外が要る（(b)）。予約語の名前のルート直下のモジュールを本体の頭に書く形は、そのファイルを作った書き手にしか起きず、少ない。修正の量の割に利益が薄い。

  - あわせて決めること: W4-03 の U3a1 の仮の約束（コードを約束せず、候補が無い）は、`30b09c5` では満たされない（候補 `use static`）。U3a1 の「`use` で束縛できる名前か」の述語が `static` を予約語として数えれば W5-11 を待たずに満たし、数えなければ `static` の予約（W5-11）で満たす。
