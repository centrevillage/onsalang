# S-462 名前の段で解決できなかった `use` から使う所への E0302 の連鎖

- 決定済みで戻さないもの: 構文の段で失敗した `use`（並びの途中の `use util.{g h}`、S-594 の表の 22・29〜31 行の形）は R-180（親の決定）で、W4-03 が、失敗した `use` のあるモジュールの E0302 を出さない形にする。単位と段の依存（§18.1、S-59・S-64）。
- 論点: 仕様 §18.1「誤りのある宣言も、名前まで読めれば名前解決に見せる。読めなかった部分（引数の型、フィールドなど）は誤りの型として扱い、それを使う側には診断を出さない。正しい宣言に偽の連鎖エラーを出さないためである」。
  名前の段で失敗した `use` は、取り込む名前まで読めているが、取り込む先が無い（E0302）、見えない（E0303）、取り込めない種類（E0302・E0308）である。その名前を使う所が「誤りを使う側」なのか、ただの見つからない名前なのかが書かれていない。R-180 は構文の段の失敗だけを扱う。
- 今の実装: `chain1.py`。

  | 形 | 例 | 今の実装（`check`） |
  |---|---|---|
  | 並びの名前が無い | `use std.math.{nosuch}` と `nosuch(a)` | `use` の 1:15 と使う所の 4:3 に E0302 が二つ。別の関数にも使う所があれば、その数だけ増える |
  | 綴りの誤り、他のモジュールに無い | `use std.math.{sqr}`、`use util.{nope}` | 同じく `use` と使う所に E0302 |
  | 見えない | `use util.{h}`（`priv fn h`）と `h()` | `use` の E0303 と、使う所の E0302「cannot find `h` in this scope」 |
  | 経路の頭・途中が無い | `use nosuch.{a}`、`use std.nosuch.{a, b}`、`use std.nosuch` と `nosuch.f()` | 経路の E0302 と、使う所の E0302 |
  | 取り込めない種類 | `use util.E.{A}` と `A`、`use util.g.{x}` と `x()` | `use` の E0302 と、使う所の E0302 |

  | 同じ名前の項目、引数 | `use std.math.{nosuch}` と `pub fn nosuch()`、`fn f(nosuch: F32)` | `use` の E0302 だけ（今は隠蔽を E0304 にしない。W4-04 で E0304、S-79） |

  | 循環、二度目（参考） | `use b.{}` と `use a.{f}`、`use util.{g}` を二度 | E0310、E0304 だけで、使う所は通る（名前は解決している） |

  - 試した入力: `target/notes/55/gap39/probe/chain1.py`（`python3 harness.py chain1.py`）。
- 案:
  - (a) 名前の段で失敗した `use` の取り込む名前を、誤りの定義に束縛する（R-180 の考え方を名前の段へ、名前ごとに延ばす）。経路が失敗したら並びの全ての名前を、要素が失敗したらその名前を誤りにする。
    使う所は、その名前を誤りの型として扱い、診断を出さない（E0302、型の誤り、メンバの探索など）。`pub use` で再公開した誤りの束縛を取り込む他のモジュールの `use` も、誤りの束縛を受け取り、診断を出さない。
    実装: W4-03 で作り直す `use` の解決（`names/imports.rs` の見込み）の束縛の表に「誤り」の値を足す（10〜20 行）、使う所の解決が誤りの束縛を誤りの型にする所（5〜10 行）、再公開（数行）。
    事例: 形ごとに使う所が黙ることを見る事例（否定例は `use` の診断で数える）。費用の要因: R-180 のモジュール単位の印と、名前ごとの誤りの束縛の二つの仕組みが並ぶ。
  - (b) R-180 と同じく、名前の段で失敗した `use` のあるモジュールの、名前の見つからない E0302 を全て出さない（モジュール単位）。
    実装: R-180 の印を名前の段の失敗でも立てる（5 行程度）。費用の要因: そのモジュールの、`use` と関係の無い本物の E0302（別の綴りの誤り）も、`use` を直すまで隠れ、修復のループが一周増える。再公開を取り込む他のモジュールの `use` には E0302 が残る（そのモジュールにも印が立ち、使う所は黙る）。
  - (c) 今のまま。§18.1 に「名前の段で失敗した `use` の名前を使う所も E0302」と書く。実装: 0 行。
    費用の要因: 一つの誤りが、使う所の数だけの E0302 になる。W4-04 が使う所の E0302 に `use` の挿入の候補を付けると（§15.1 の `use` の無い経路と §8.1 の効果。名前だけの使う所に付けるかは W4-04 の設計）、例えば `use std.maths.{sqrt}` と `sqrt(x)` の使う所に `use std.math.{sqrt}` を足す候補が出る。
    修復のループは失敗した `use` と別に二つ目の `use` を書き、元の `use` を直すと E0304 になる。
  - どの案でも決めること: 見えない項目（E0303）の取り込みを誤りの束縛にするか、本当の定義に束縛するか（使う所は署名で型を検査する）。誤りの束縛を、同じ名前の他の束縛（項目、引数、`let`）との E0304 の相手にするか。
- 他言語:
  - rustc 1.94.1（手元）: `use std::f32::nosuch;`、`use std::maths::sqrt;`、`use nosuch::{a, b};` は E0432、非公開の `use util::h;` は E0603 だけで、使う所（`nosuch(a)`、`sqrt(x) + a()`、`h()`）には何も出ない。
    `i32` を返す非公開の `h` を `f32` の関数の末尾で呼んでも型の誤り（E0308）は出ない（同じファイルの別の関数の型の誤りは出る）。`use util::nope;` と同じ名前の `fn nope()` も E0432 だけで、E0255 は出ない。
  - Python 3.14.5（手元）: `from math import nosuch` は実行時の ImportError で止まり、使う所に届かない。Go 1.27.2（手元）: 無いパッケージの `import` は「no required module provides package」で止まり、使う所を報告しない。
  - Node v26.11.1（手元、ES モジュール）: `import { nope } from "./a.mjs"` はリンクの「does not provide an export named 'nope'」で止まる。TypeScript: 未確認（手元に tsc が無い）。
- 推奨と理由: (a)。確度: 中。
  - 名前の段で失敗した `use` は、取り込む名前まで読めている。§18.1 は名前まで読めた誤りの宣言を名前解決に見せ、使う側を黙らせるとする。取り込む名前は、使う所にとって宣言と同じ役をするので、(a) は §18.1 の文を `use` にそのまま当てる読みで、新しい規則でない。
  - (a) は、黙らせるのをその名前を使う所だけに限る。§18.1 は全ての単位の誤りを一度に報告して修復の周回を減らすとし、(b) はモジュールの他の本物の E0302 を一周遅らせる。R-180 がモジュール単位なのは、構文の段の失敗では読めなかった名前が分からないためで、名前の分かる名前の段では要らない。
  - 修復のループ: (a) では誤りは `use` の一つで、その候補（S-37 の自分のパッケージ名、次の組の S-258 の綴り）を当てれば束縛が本物になり、使う所の本物の誤りは次の周に出る。使う所に `use` を足す候補が出ないので、(c) の二つ目の `use` の形が起きない。
  - 実装の量: W4-03 は `use` の解決を作り直すので、束縛の表の誤りの値は作る時に入れられる。(b) より 15〜25 行多い。R-180 の印は構文の段の失敗に残り、二つの仕組みは、読めた名前が分かるかどうかで分かれる。
  - 第 2 期と JS / WASM: 名前の段の中の扱いで、生成するコードには届かない（誤りのある単位は降下しない）。
  - あわせて決めること: 見えない項目（E0303）の取り込みも誤りの束縛にする（一様な扱い）。本当の定義に束縛すると、使う所の型の検査が見えない項目の署名に頼り、書き手が `use` をやめて別の関数を書く直しでは偽の誤りになる。確度は中。
  - あわせて決めること: 誤りの束縛は E0304（S-79 の隠蔽と、同じ名前の二度目）の相手にしない。同じ名前の他の束縛があれば、使う所はそれを指す。重なりは `use` の直し方（名前を直す、除く）で消えるので、`use` の誤りに続く偽の誤りになりうる。今の実装も E0304 を出さない。確度は低。
  - あわせて決めること: 一つの `use` の並びで二つ以上の名前が失敗したときも、報告は単位ごとに最初の一つ（§18.1）で、束縛は失敗した全ての名前を誤りにする。
  - 関係（ここでは決めない）: W4-04 の E0302 の `use` の挿入の候補は、(a) では誤りの束縛を使う所に出ない。次の組の S-258（綴りの近い名前）は、`use` の要素の候補だけを出す形になり、名前を直した後の使う所は次の周で解決する（S-258 で決める）。
    R-246（E0200 にした extern のブロックのメンバが名前解決に見えない）は宣言の側の同じ種類の連鎖で、W4-03 で直る。
- 影響: 仕様 §18.1（(a) は「誤りのある宣言も…」の段落に、名前の段で失敗した `use` の取り込む名前の一文。(b) は R-180 の扱いを名前の段へ広げる一文。(c) は使う所の E0302 の一文）。(a) は §15.1 の `pub use` の文に、再公開した誤りの束縛の一句。
  診断のコードは変わらない（(a)・(b) で E0302 の数が減る）。作業: W4-03（`use` の解決。R-180 と同じ回）。W4-04 の使う所の解決と `use` の挿入の候補は、(a) では誤りの束縛を、(b) ではモジュールの印を見る。
  テストの事例: 今のテストは失敗した `use` の名前を使わない（`tests/spec/fixes/e0302_use_path.onsa` の注記、`tests/spec/negative/names.onsa` の `use std.nothing.{x}`、`tests/spec/packages/visibility`）ので、どの案でも今の期待値は変わらない。
  (a)・(b) では、使う所が黙ることを見る事例を足す（`onsa_cases --fix-loop` で、候補のある形が一度で clean になることも）。テストベクトルの保留に関係する項目は無い。作業ツリーは空。
- 独立のレビュー（2026-10-23、助言の担当の二段）:
  - 一致: (a)（名前ごとの誤りの束縛）。見えない項目（E0303）の取り込みも誤りの束縛。一つの `use` で複数の名前が失敗したら、束縛は全て誤りで報告は単位ごとに一つ。段 2 は確認だけ（A）に置いた。
  - 割れ（細部）: 誤りの束縛を E0304 の相手にするか。段 1 は相手にする（重なりは `use` の存在に依り失敗に依らない）、下書きは相手にしない。段 2 は下書きを採る: `use` を除く・綴りを直すの直しでは E0304 が偽の連鎖になり、§18.1 の「正しい宣言に偽の連鎖エラーを出さない」に下書きの方が近い。
    決定の文は「失敗した `use` の名前は束縛の表に入れず、見つからない名前を黙らせる集合に入れる。同じ名前の本物の束縛が見えていれば、使う所はそれを指す」の形にし、実装の形も一つに決める。下書きの理由の「今の実装も E0304 を出さない」は根拠にならない（今の実装は S-79 の隠蔽の E0304 をまだ出さない。W4-04）。
    二つ目の `use`（失敗した `use std.math.{g}` の後の `use util.{g}`）も E0304 を出さず、使う所は `util.g` を指す。S-17 の「同じ名前の二度目の `use` は E0304」は、解決した `use` の間の規則と読む。
  - 補い（段 1、段 2 は直して採る）: R-180 のモジュール単位の印は「取り込む名前を全部は読めなかった `use`（並びの途中で失敗した形）」に限る。S-594 の構文の段の誤り（`use kp.clock` の E0200 など）は取り込む名前が読めているので、誤りの印付きで名前の段へ渡せば S-462 の集合に入れられる。空の並びの E0002 は何も取り込まないので印を立てない。
    S-462 の決定か W4-03 の設計メモに置く（R-180 の決定は戻さない。範囲の言い直し）。
  - 再公開: 「再公開した誤りの束縛」の文は、モジュールの再公開（S-594 の新しい S の候補）を決めないと書けない（段 1）。
- 回答（2026-10-23、会話で利用者。55 回目）: (a)、E0303 の取り込みも誤りの束縛、誤りの束縛は E0304 の相手にしない（独立のレビューの段 2 のとおり）、複数の失敗は束縛を全て誤りにして報告は一つ、R-180 の印は名前を全部は読めなかった `use` に限る、を了承（(A)）。
