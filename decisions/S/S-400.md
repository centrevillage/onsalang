# S-400 名前の直後に接する文字列・文字のリテラル

- 空白: 名前の直後に空白を空けずに接する文字列リテラル（`f(b"x")`、`f(r"x")`、`f"{x}"`、`u8"x"`。Python の接頭辞付き文字列、Rust の `b""`・`r""`、C / C++ の `L""`・`u8""`）。今は E0002「expected `)`, found string literal」で候補なし。
  S-387 の (a) をそのまま当てると `f(b, "x")` の候補が出て、接頭辞の意図を `,` の抜けに読み替える。既存言語の形として先に検出する行を立てるか（候補を作れるものは E0020、作れないものは E0002 と note）。S-388（隣り合う文字列リテラル）とは別の形。
  文字列の直後に空白なしで接する名前（C++ のユーザ定義リテラル `"x"_s`、C# の `"x"u8`）も同じ検出関数で扱えるので、この S で決める（第 20 組の Fable のレビュー）。第 19 組の Fable のレビューで見つけた（2026-10-10）
- 提案: 決定（2026-10-10、利用者は (b) 寄りとし、(a) との実装の差が小さいので作業の進めやすさで親に委ね、親が (b) を選んだ。下書きと Fable の推奨は (a)、第 20 組）: 名前の直後に空白なしで接する文字列・文字のリテラル（`f"{x}"`、`r"\d"`、`b"x"`、`u8"x"`、`L"x"`、`b'x'`）と、リテラルの直後に空白なしで接する名前（C++ のユーザ定義リテラル `"x"_s`、C# の `"x"u8`）は、構文の段の失敗の所で一つの形として検出し、E0002 と note（Onsa の文字列の書き方: UTF-8 の `"…"`、補間は `"{x}"`、バイト列は `"x".as_bytes()`）。
  候補は出さない。S-387 の `,` の挿入より先に検出し、`,` の候補を出さない。`extern` の見出しの `lib"m"` は見出しの文法で読み、当たらない。後で (a)（接頭辞の閉じた表で候補を出す E0020。`$` を含む本体には出さない）へ広げても壊れない（利用者）。
  データのファイルに code = "E0002" の行（例: `f"{x}"`、`r"x"`、`b"x"`、`"x"_s`）。仕様 §2.4。
  実装は W3-06（約 20〜30 行）（読みの補い、2026-10-10、親: 名前に接するリテラルが閉じていないか不正なとき（`f"abc` 改行、`x'ab'`）は §2.4 の E0001 が誤りで、この E0002 は出さない。W3-06/b が見つけた）（改め、2026-10-11、利用者、S-406: 名前に接するリテラルが閉じていないか不正なときも、この E0002 を報告して中身を読まない。範囲は名前から同じ行の閉じの区切りまで、閉じが無ければ開きの区切りまで。実装は W3-05）
