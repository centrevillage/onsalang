# 組込み API の候補（A）

仕様に無い組込みの API（組込み型のメソッド、`std` の関数）を、実装が黙って足すのをやめ、必要かどうかを議論してから決める（2026-10-03、レビューの R-18 / R-96 の議論から）。
一覧は `python3 -B tools/docs.py list A`。

## 方針

- 組込みの API は、仕様に載っているものだけを実装する（閉じた一覧）。
- ただし、事前に設計した API が十分とは限らない。実装や Onsa のコードを書く中で「無いと煩雑」と分かったものは、拒否で終わらせず、ここに候補として挙げて議論する。
- 「Rust などの既存言語にあるから」だけの理由は採らない（コーパスの重力）。名前と意味を借りるのは、Onsa で必要と分かった後で、意味が一致するときだけ（§0.3 の規則 3）。
- 不採用の候補も理由とともに残す。同じ API が再び足されるのを防ぐためである。

## 手順

1. 候補を挙げる。担当は実装せずに報告し、親が `docs.py new A` で登録する。次のことを書く。
   - 名前と型
   - 無いと煩雑になる実例（Onsa のコード）と、無い場合の書き方
   - 借用元と、意味が一致するか（§0.3 の規則 3、4）
   - 既存の書き方と重ならないか（§0.3 の規則 1、P2）
2. 利用者が判断する（採用 / 不採用 / 保留）。採用したら仕様に載せる。
3. 実装した API が仕様の一覧に無ければ、レビューで指摘する（Q-10 の印の照合と同じ扱い）。

## 本文のラベル

`docs.py new A` は、この節のラベルを新しい A の雛形にする。

- `候補`: 名前と型。
- `決定`: 採用・不採用・保留と、その日付。
- `理由`: 実例、無い場合の書き方、借用元、決めた理由。

`status` は、採用と不採用が `DECIDED`、保留が `OPEN`。第 2 期に決める保留は `before = "PH2"`。
