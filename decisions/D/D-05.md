# D-05 `tests/spec` の形式はインラインのマーカ

- 案: 期待する診断を、同じ行の末尾に `//~ E0010` と書く（rustc の UI テストと同じ形。`//~ E0010 @13` で列も指定できる）。マーカの無いファイルは診断 0 件を期待する。ファイルの先頭行で検査の深さを指定する:

```
//! mode: none      // 収録のみで実行しない（`...` を含む断片、最上位の文、擬似コード）
//! mode: parse     // 構文解析だけ（第 1 期で未対応の fn 世界の例）
//! mode: check     // check --json の結果をマーカと比較（既定）
//! mode: test      // check の後、test ブロックをインタプリタで実行する
```

- 理由: 別ファイルの `.expect` より、否定例の意図が行の横に見える。仕様の例を含むファイルにマーカを足しても、§6 の同期検査（D-06）はマーカを無視して照合できる。
- 代替: 計画 §1 の `.expect`。JSON の全文を比較できるが、行番号のずれで壊れやすい。
- 改定（2026-10-04、レビュー R-80）: ファイル単位のテストの設定は、先頭のコメントに書く `onsa.toml` の断片に一本化し、`//! mode:` をやめる（S-51 で `//!` はモジュールの doc になり、同じ見た目で違う意味になっていた）。
  断片は `// onsa.toml` の行の後に続くコメントで、マニフェストと同じ構造体で読む（未知のキーは E1102 で、断片だけが `[test]` の表を持てる。S-99）。テスト専用の設定は `[test]` の表に置く（`mode = "none" | "parse" | "check" | "test"`、既定は `check`）。
  C などのバックエンドの事例は、同じ断片に `[targets.*]` と `[export]` を書き、事例とターゲットの組ごとに期待値を置く（`tests/golden/c/echo.poison.c`）。テスト専用の既定値は作らず、ターゲットの欄は全て書く。
  複数モジュールの事例は、ディレクトリと `onsa.toml` のパッケージにする（§15.1 の単一ファイルのパッケージとパッケージの 2 つの形と同じ対応）。行ごとの期待値 `//~` は今のまま。golden・C のコンパイル・適合性のテストは、ディレクトリを走査して事例を集め、Rust に事例の表を持たない（表が二つに分かれて食い違っていた）。
  ビルドの入口をファイルの読み込みから分け、マニフェストの値とソースの一覧を受け取る関数にする（テストと `onsa_web` が使う）。D-06 の同期検査は、ファイルの先頭に断片があっても、仕様のブロックがそのまま含まれていればよい。
- 実装（2026-10-07、`rework-phase1.md` の W1-03）:
  - 断片は 1 行目がちょうど `// onsa.toml` の行から、空行かコメントでない行まで。1 行目の見出しの誤記と、`//!` の行の旧い `mode:` は事例の誤り。断片の最上位のキーは、マニフェストの最上位のキー（driver の `Manifest::TOP_LEVEL_KEYS`）と `test` に限る。
  - `[test]` は閉じた表で、キーは `mode`、`spec`、`golden`（`"core"` / `"interface"` / `"c"`）、`golden_graph`（flow の名前）、`conformance`（インタプリタと C を比べる）。`[test]` だけの断片はマニフェストの無い単一のファイルのパッケージで、他の表を持つ断片は `[package]` が要る。パッケージの事例は、中の高々一つのファイルに `[test]` だけの断片を置く。
  - golden は `tests/golden/<種類>/<事例>.<ターゲット>.<拡張子>`（グラフは `<事例>.<flow>.dot`）。宣言した golden の欠けと、どの事例も宣言しない golden は失敗。ターゲットを持つ事例は、全てのターゲットをビルドしてコンパイルする。
  - check の診断が 0 件なら、ターゲットごとにビルドの段（`build_analyzed`。export の検査、ターゲットの設定での降下、`inline_consts`、C）を回し、マーカと比べる。マーカはターゲットを指定できる（`//~ E0820 [poison]`。指定の無いものは全てのターゲット）。
  - `conformance = true` の事例は、全ての `pub flow` を export し、比べた flow が 1 件以上であること。
  - 走査は `tests/` の全体で、`tests/review-phase1/`（再現の入力で、期待値付きの事例ではない）を除く。実装待ちの一覧の `test-case` を照合する。
  - 本物のビルドなら E0809 になる構成を golden から外した（unison と resonator の C の golden、voice の export は `voice.voice` と `voice.echo`）。
- 改定（2026-10-07、`rework-phase1.md` の K-14）: export の境界で呼び出しの手順ごとに確かめる事例（仕様 §9.2 の poison の表、§14.2 の状態の値、§15.3 の `panic` の設定）は、断片の `[test]` を広げた `[[test.host]]` の配列に書く。
  欄は `name`、`target`、`flow` か `fn`（`[export]` と同じ経路）、`steps` で、手順の欄は `call`（`init` / `process` / `reset` / `fn`）、`config`、`params`、`input`、`frames`、`output`、`status`、`inplace`、`fill`（呼ぶ前の出力の中身）、`null`、`args` / `result`。
  実行器が手順から C の driver を作って走らせ、仕様 §13.4 の比べ方（ビット一致、NaN どうしは等しい）で期待値と照らす。期待値は出力の型で正確に表せる値に限り、`panic = "trap"` / `"halt"` のターゲットは手順を走らせない。
  `crates/onsa_tests/tests/poison.rs` が Rust の文字列に持つ C の driver は事例へ移す。実装は W1-11。
- 実装（2026-10-07、W1-11）:
  - 手順の組は事例の実行器が、check が診断 0 件でビルドできたターゲットの上で走らせる（`cargo test` の `cases` と gate の `test`）。C の検査の項目は走らせない。プログラムは (事例, ターゲット) ごとに一度 `c-clang` の行でコンパイルし、組ごとに別のプロセスで走らせる。値は標準入力のバイトで渡し、記録を Rust の側で §13.4 の比べ方で照らす（NaN どうしは等しく、`-0.0` と `0.0` は違う）。
  - 欄: `init` の手順に `sample_rate`（必須、決定の一覧に足した）。`config`・`params`・`args` は空でも常に書き（`{}`）、省くのはその引数が構造上無いとき（`null` の `"cfg"` など）だけ。`output` を省いた `process` は書けない。
    `fill` を省いた出力は器が 0xA5 の模様で埋め、書かれないままなら「書かれていない」と報告する（期待値が模様と同じビットなら事例の誤り）。状態の記憶域も `init` の前に模様で埋める。値は型で正確に表せるものだけ（F32 の `0.1` や整数の `2` は事例の誤り）。`i64::MAX` を超える `U64` は書けない。
  - 何も走らずに通る形（手順 0 件、`mode` が `none` / `parse`、`panic = "trap"` / `"halt"`、ホストでないプラットフォーム、ビルドの診断を期待するターゲット）は事例の誤り。`panic = "reset"` は走らせ、panic した手順は失敗。
  - 実装待ちの一覧の項目は `"<パス>::<組の名前>"`（`test` の名前と一つの名前空間）。黙らせるのはその組の手順の失敗（値の違い、手順の中でプロセスが終わった、今の C API で書けない手順）だけで、組の全ての手順に及ぶ。
    黙らせる範囲は組の分け方で絞る: 落ちる原因の手順（R の誤り、今の C API で書けない手順）は、その手順と状態を作るのに要る前の手順だけの組に置き、前の手順は実装待ちでない別の組でも照らす（W1-11/b の指摘）。今の C API で書けない手順の後の手順は走らせず、前の手順は照らす。
  - C の名前と形は、C バックエンドが記録する `CUnit::fns`・`take_panic`・`FlowApi` の引数の並びから取る（生成する C は変えない）。今の C API の呼び方は `onsa_tests::capi` 一か所に置き、適合性テストの driver も使う。W10-02 / W10-03 で API が変わったら、直すのはここだけ。
- 実装（2026-10-08、`rework-phase1.md` の W3-17。修正候補の約束、仕様 §18.1、S-236、S-266）:
  - 実行器は、`mode` が `check` か `test` の全ての事例で、check が報告した全ての診断の全ての修正候補を一つずつ当て（`onsa_diag::apply_mapped`。`apply` と同じ一か所）、事例と同じ入口（`Loaded::from_input` から `analyze_loaded`）で検査し直す（`onsa_tests::fix_contract`）。
    触れた単位は補集合で定める（S-302。W3-15 で改めた）: 当てる前の check の単位の表（`Analyzed::units`、D-15）のうち、その文字（メンバを持つ項目はメンバの外の部分）に編集も中への挿入も無く、前にある編集の長さの差でずらした同じ範囲が当てた後も単位であるものが触れていない単位で、当てた後の他の全ての単位が触れた単位。元の診断の単位は加えない（S-266）。
    そこに元の診断と同じ段以前（`Stage::CHECK_ORDER`）の診断が残れば違反。既定は「報告された診断は、当てる前の触れた単位の全てで唯一の誤り」（一つの構文の形は一つの誤り、S-248。器は前提を計算せず、他の誤りがある事例は `leaves` で表す、S-314）。後の段の診断は見ない。
    全ての候補は、編集の範囲の外の字句の読み（トークンとコメントの種類と範囲。空白は比べない。前にある編集の長さの差でずらし、端に接する挿入は中に入れない）を変えない（S-302）。ファズの近似（`same_place`）も同じ字句の検査をする。
  - 断片の `[[test.fix]]`（`[test]` の配列）は一つの候補について書く: `at`（元の診断の主の位置 `"<行>:<列>"`、パッケージは `"<ファイル>:<行>:<列>"`）、`code`、`candidate`（1 から）、`leaves`（当てた後に触れた単位に残る同じ段以前の診断 `"<行>:<列> <コード>"`。当てた後の位置。既定は無し）、`clean`（当てた後の check が何も報告しない、S-253）、`same_code`（コメントでないトークンの種類と字面と、それらの間の行の切れ目が、当てる前と同じ。コメントは動いてよい、S-247）。
    指す診断か候補が無い項目、既定しか言わない項目、`clean` と `leaves` の両方を書く項目は事例の誤り。`mode` が `none` / `parse` の事例には書けない。性質だけで確かめる候補は `fixes = N` を書かずにこれで約束できる。
  - 違反は候補ごとに `"<リポジトリの根からのファイル>:<行>:<列> <コード> fix<K>"` で、実装待ちの一覧の種類 `fix-contract` がその候補だけを黙らせる（事例の全体の `test-case` の項目では黙らない）。指す候補の無い項目と、約束を満たした候補を指す項目は失敗。
    確かめられない候補（事例の外のファイルを編集する、当てられない、検査し直すと内部エラー、降下・ビルド・`onsa test` の段の候補）は、一覧で黙らせない失敗。確かめた候補が全体で 0 件なら失敗。要約に確かめた数を出す。
  - ファズ（`tools/fuzz.py`）は、決まった規則（変異体の 4 つに 1 つ）で選んだ変異体と保存した入力を `onsa_cases --fix-same-place` にかける。診断ごとに最初の候補だけを当てて検査し直し、元の診断の範囲と置き換えの範囲を当てた後へ移した所（「同じ箇所」の近似）に、元の段以前の診断が出れば違反。
    入力が元からその箇所に持っていた誤り（同じコードと文面の、単位ごとに選ぶ前の診断）は数えない。型は「コード・候補の title・残ったコード」で、既知の型は保存した入力（`fuzz-input`。意味を「まだ落ちる、または約束を破る」に広げた）で示す。
