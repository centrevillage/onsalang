# D-04 診断の登録簿はマクロで作る Rust の表。`explain` の本文は markdown ファイル

- 案: `onsa_diag/src/codes.rs` に `codes! { E0010 => { category: Syntax, message: "..." }, ... }` の形で全コードを書き、`explain` の本文は `onsa_diag/explain/E0010.md` を `include_str!` で埋め込む。テストで「仕様 §18.1 の範囲に収まる」「本文のファイルが全コード分ある（M9 の受け入れ）」を検査する。
- 理由: コードの追加漏れをコンパイルエラーにしたい。本文は長文なので Rust ソースから分ける。
- 代替: TOML の登録簿を実行時に読む。`wasm32` で `include_str!` にするなら差は無いが、型の検査が無い。
- 追記（2026-10-05、レビュー R-87、D-15）: 登録簿の各コードに、段（S-78 の構文・名前・型・引数のモードと移動・rt と効果と、降下・ビルド）と、修正候補が必須かを持たせる。CLI、fmt、テストはこの属性を読み、番号の範囲（`number() <= 20`）やテストの中のコードの一覧で判定しない。修正候補が必須のコードで候補が無ければ、全てのテストで落ちる。
  既存言語の書き方の検出（E0020）は一つのモジュールの規則の表に集め（文脈、検出する形、候補の組）、構文解析器は解析に失敗した点でそこに問い合わせる（候補を作れなければ E0002、S-48）。E0020 は名前の段（`Sig[F32]`、S-120）と flow の検査（見えている名前への `^`、S-116）でも出るので、その段も同じ表の項目を引いて出す。
  fmt を止めるかは、コードではなく診断を出した段（字句解析と構文解析）で決める（S-120）。キーワードの判定は、`TokenKind` の宣言の順序に依らない明示の一覧にする。
