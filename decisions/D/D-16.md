# D-16 テストの基盤は、実装から独立した期待値を層で持つ

- 決定（2026-10-06、レビュー R-113 と `process-improvement-phase1.md` の Q-01〜Q-08）。層と時期:
  1. 仕様から書く期待値（Q-01）: 実装と別の担当が、仕様と CLI だけから、実装より先に書く。事例は R-80 (5) のファイル（`onsa.toml` の断片と `[test]`、`//~` のマーカ）。断片に節の番号を書き（`[test] spec = ["§11.4"]`、Q-05）、テストの無い節を一覧にする。第 1 段。
  2. 仕様から作るテストベクトル（Q-02 (a)）: 整数・浮動小数・変換・検査付き演算の、演算・型・入力・期待する結果か panic の表をデータで持つ。仕様の規則（R-133 で自己完結にする §3.3 / §3.4）から参照モデルで生成し、生成するときだけ独立した実装（Rust、C、Berkeley TestFloat など）と突き合わせる。テストは各変換先をベクトルと比べる。第 2 段と並行。
  3. flow の参照評価器（Q-02 (b)）: AST から直接 1 サンプルずつ評価する小さな評価器を `onsa_tests` に置く。決まった事例の期待する出力はデータとして残す。第 4 段の構造の変更の前。
  4. 性質テスト（Q-03）: fmt の性質（摂動、S-56 の比較、冪等性、R-70、R-86）は第 1 段。型の付いたプログラムの生成（`check` が通る、インタプリタ・C・参照が一致、コンパイラが panic しない）は M5 の前後。
  5. golden（Q-04）: 変化の検出器で、意味の根拠にしない。更新は親が承認する。
  6. 安全網（Q-06、Q-07）: 検証器は常に（R-82）、内部の panic は `catch_unwind` で S-67 の内部エラーに、`check` と `fmt` の短いファズ。生成した C は Clang と gcc-15 の `-std=c11 -Wall -Wextra -Werror -pedantic`、UBSan / ASan、公開ヘッダを C99 / C++11 で。`cc` が無ければ失敗。x86 は `-arch x86_64` と Rosetta。
  7. 一つの検査コマンド（Q-08）: `tools/gate.sh`。仕様の例の検査は、実装待ちのブロックの明示の一覧（S 番号付き）と照らす。診断コードの網羅性の照合（S-109、点検 C-26）: 登録簿の全てのコードが仕様の本文に現れ、仕様の本文の全てのコードが登録簿にある（計画 §5 の欠番の一覧を除く）。
     登録簿は仕様の全てのコードを持ち、否定例が 3 件に届かないコードを、実装待ちの例と同じく S / R 番号を添えた明示の一覧に置く（2026-10-07、`rework-phase1.md` の K-12、K-13）。一覧は `tests/pending.toml` の一つで、仕様の例・診断コード・gate の項目・テストの事例・ファズの入力を同じ形で持つ（W1-01）。
      gate の項目は `tools/gate_steps.py` に並ぶ（W1-04 の後: fmt、clippy、test、fuzz（`tools/fuzz.py`。決まった種の変異と、ファイルの終わりで切った入力（FZ-1）を `check` と `fmt --check` にかけ、保存した入力 `tests/fuzz/` を再実行する。深い入れ子と、希少な記号の直後の全ての位置で切った入力は `--deep` のときだけ、S-183、FZ-1）、spec-examples、spec-sections、pending、diag-registry、diag-negatives、gap-marks、builtin-names、ignored-files、gate-selftest、golden と spec-coverage は情報。W1-06 の後は、生成した C の検査 c-clang、c-gcc、c-sanitize（ASan と UBSan、終了コードで止める）、c-x86（`-arch x86_64` と Rosetta）、c-header（C11）、c-header-strict（C99 / C++11）が続く（W2-09 で外していた警告が無くなり、同じ検査になった c-gcc-strict を消した）。C のコンパイルと適合性テストは `cargo test` でなく gate のこれらの項目が回す。`-strict` の 2 項目は項目の全体で実装待ち）。
     追記（2026-10-08、利用者の指定。機械の負荷と待ち時間を減らす）: gate は機械で一度に一つだけ走る（git の共通ディレクトリのロックを主のツリーと作業ツリーで共有し、走っている gate があれば表示して待つ）。
     実装待ちの一覧に項目の全体で載る項目は落ちると分かっているので、`--work <その until>` か `--stage-end` のときだけ回し、それ以外は SKIPPED と表示する。
     `--quick` は遅い項目（fuzz、gate-selftest、C の検査、vectors-c、fmt の性質）を除いた作業の途中の確かめで、最後の行が `gate (quick): …` になり、判定にはならない。回し方は 8.5 の「検査の回し方」。
- 時期の読み替え（2026-10-07）: 上の「第 N 段」はレビュー §7 の旧い段の番号である。今は [`rework-phase1.md`](rework-phase1.md) の作業に置いた: 1 は W1-08 / W1-09 と各作業のテストの票、2 は W2-01、3 は W7-01、4 の fmt の性質は W1-07（コメントの位置と CST の往復は W3）・生成は T5-8、6 と 7 は W1。
- 理由: M0〜M4 のテストは、期待値を実装の出力から作り、実装と同じ担当が書き、同じ Core から出た二つを比べていたので、意味の誤りを検出できなかった（レビュー R-113、`process-improvement-phase1.md` の原因 a〜d）。参照を特定の言語の処理系にせずデータにするのは、その言語の版に影響されず、コンパイラの実装の言語を変えても残るため（利用者の指摘）。
- 代替: Rust のプログラムを実行時の参照にする（元の Q-02 (a)）。Rust の版で意味が変わりうる（浮動小数から整数への `as` は 1.45 で変わった）うえ、Rust が決めていないもの（NaN のビット表現）があり、仕様の規範にできない。
