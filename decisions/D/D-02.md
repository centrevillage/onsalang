# D-02 AST はアリーナ + ID。スパンはバイトオフセット

- 案: 各ノードは `Vec` に置き、`ExprId(u32)` などの ID で参照する。スパンは `Span { start: u32, end: u32 }`（ファイル内のバイトオフセット）。行・列は `LineIndex` で必要なときに計算する。トークンの前後の空白とコメント（trivia）はトークン列に残し、AST はトークン列への索引を持つ（`fmt` と `diff --ast` が使う）。
- 理由: `Box` のツリーは `wasm32` でも動くが、LSP で部分的に差し替えるのと、`fmt` でトークンの前後の空白を再現するのに、ID と索引の方が扱いやすい。rust-analyzer と同じ方向。
- 代替: `Box` のツリー。最初は速いが、`fmt` でコメントの位置を失う。
- 改定（2026-10-05、レビュー R-86）: 段を「字句解析 → CST → AST → sema」にする。CST は全てのトークン（コメント、改行、空白を含む）を持つ損失の無い構文木で、構文解析器が作り、誤りの回復（S-59）もこの木の上で行う。AST は CST から一つの段で作り、ここに書いたアリーナと ID の形のまま sema が使う。
  `fmt` は CST を読み、S-56 の書き換えの一覧も CST の上で行う（取り除くノードに付いたコメントは残す）。診断の修正候補の範囲（R-87）と LSP の位置は、CST のトークンの範囲で表す。CST は自前の簡単な作りにし、外部のライブラリは使わない（D-09）。
  元の案（AST がトークン列への索引を持つ）は実装されず、`fmt` は AST の位置からコメントと区切り文字を推測していた（R-70 の 17 の形のうち 15 を書き換える）。
  トークン列に索引を持つ形より CST を選んだのは、trivia の位置が構造で保証され（ノードの範囲とトークンの境界の一致という不変条件に頼らない）、誤りを含むコードにも完全な木があり（LSP）、差分での再解析と構造を書き換える編集（第 2 期以降の補完やリファクタリング）の土台になるため。S-58（コメントの結び付け）は CST の上で作る（CST が先か同じ回）。
- 改定（2026-10-15、S-534）: AST は doc コメントを持たない。どの宣言に付く doc かは構文解析器が CST の上で決め（E0004 も CST の上）、要る所（fmt の書き込む前の確かめ）は CST から引く。`diff --ast` は AST の構造だけを比べる。
- 実装（2026-10-08、`rework-phase1.md` の W3-01）:
  - 構文解析器はイベントの列（`Start` / `Token` / `Finish`）を出し、ビルダが一度の走査で CST（自前の平らなアリーナ。子は連続した範囲、親への道、絶対の位置）を作る。ノードを開く入口は一つ（`enter`）で、`precede` で左を後から包む。ノードは最初のトークンが来たときに木に置き、それより前の消費されていないトークン（trivia）は外側のノードに付く。trivia の付く場所の規則はビルダの一か所にある（S-58 の結び付けは W3-11）。
  - ノードの種類は一つの列挙 `NodeKind`。構文解析器の分類はノードの種類に記録し、低下（CST → AST）は決め直さない（`_` の無い `match`）。宣言が導入する名前は `Name` のノード、項目の doc コメントは `Item` の最初の子の `Docs` のノード（doc を項目に付ける判断は構文解析器の一か所）、`#[..]` は `HashAttr`。項目のキーワードは一つの表 `DECLARATIONS`。
  - 誤りで抜けたノードは種類を保って不完全の印を持ち（空のこともあり、種類は開いたときの仮のもの）、回復で読み飛ばしたトークンは `Error` のノード（失敗した項目の最後の子か、成功した項目の後ろの余分なトークンは `SourceFile` の子）にする。
  - 低下は根から辿れる完成した項目だけを AST にする（失敗した項目の部分木の孤児を作らない。D10）。これにより、失敗した項目の中で構文の誤りより前に出ていた診断（E0010、E0011、E0012、E0320 など）が、構文の誤り（E0002 など）に代わる。リポジトリでは `tests/review-phase1/` の 3 つの再現の入力が S-59 の期待の向きに変わった。
    それ以外の受け付ける言語・診断・fmt の出力・AST の位置は 81fa1bd と同じで、古い構文解析器と並べて全てのファイルと変形 249,258 件で比べてから切り替えた。位置の癖 3 つ（`#[..]` は `]` を含まない、`loop` の `true`、負の const 引数の数字）は `SPAN-QUIRK` の印で残した。
  - `Parsed { ast, cst, map, diagnostics }`。`AstMap` は AST のアリーナのノードから CST のノードへの表（指す先が式のノードとは限らない）。アリーナに無い部分構造の位置は `covering_node(s)` / `covering_node_of` / `tokens_in` で CST から引く。各ノードは木の高さを持ち、W3-14 の深さの上限は `Parser::height` の一か所で数える。
  - `validate()`（木の不変条件）は全ての `parse()` で回し（R-82 と同じく常に）、崩れは位置付きの内部エラー（101）。`onsa dump --cst [--tree] <file>` は往復のテキスト（既定）か木の表示を出す。gate の `fmt-cst`（実装待ちにできない項目）が、`tests/` の全てのファイル（W3-01/t の往復の入力 `tests/cst/` 160 件を含む）と摂動で往復を確かめる。
